# 03. 如何处理跨服务事务和数据一致性

## 第一步：识别 Invariant

哪些必须立即一致？哪些允许短暂 Stale？错误能否补偿？若两个数据总要原子修改，先重新评估它们是否应属于同一 Service/Aggregate。

## 推荐模式

- Service 内：本地 ACID。
- 业务数据 + Event：Transactional Outbox。
- 多步骤：Saga Orchestration/Choreography。
- Consumer：Idempotency + Version。
- 长期保证：Reconciliation。

## 示例

Order 创建后 Reserve Inventory，再 Authorize Payment。每步保存状态；失败执行 Release/Refund。API 返回 PENDING，Client 查询或接收通知。

## 2PC

若强原子且参与者支持，可评估 2PC，但要说明 Availability、Lock 和运营代价。大多数独立 Microservice 更适合显式业务流程。

## 异常

- Duplicate：Idempotent Key。
- Out-of-order：Sequence/Version。
- Timeout：Unknown State + Status Query。
- Compensation Failure：Retry/DLQ/Manual。
- Missing Event：Outbox + Reconciliation。

## 用户体验与 SLO

定义中间状态、最大收敛时间和失败沟通。最终一致性不是无限等待。

## 面试亮点

把一致性按 Operation/Invariant 分层，而不是说“使用 Kafka 达到最终一致”。说明恢复和对账。
