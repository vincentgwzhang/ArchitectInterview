# 05. 服务粒度、分布式复杂度与演进式拆分

## 粒度不是代码行数

判断粒度看业务内聚、Transaction、Change Coupling、Team Ownership、Scale 和 Failure Isolation。服务小到每个请求必须跨十几次网络调用，通常过细。

## 分布式成本

- Network Latency/Partial Failure。
- 数据重复与 Eventual Consistency。
- Contract/Version。
- Deployment/Configuration。
- Security Identity。
- Observability/On-call。
- Local Development/Test。

每拆一个服务都要支付固定 Platform 成本。

## 拆分信号

- 模块变化频率与其他部分不同。
- 需要独立 Scale/Isolation。
- 团队发布被协调阻塞。
- 数据和 Domain 已清晰。
- 模块可以通过小而稳定 Contract 交互。

## 合并信号

- 高频 Chatty Call。
- 必须同步部署。
- 大量共享 Transaction。
- 同一团队维护且独立价值低。
- Contract 随内部实现频繁变化。

## 演进式拆分

1. 在 Monolith 中建立 Module Boundary。
2. 禁止跨模块直接表访问。
3. 引入内部 API/Event。
4. 使用 Strangler Proxy 抽取一个 Capability。
5. 迁移数据 Ownership。
6. Shadow/Canary 后切流。
7. 删除旧路径。

## 总结

服务粒度需要持续调整。以可逆、小步和可测量方式演进，比一次性设计“完美服务地图”更可靠。
