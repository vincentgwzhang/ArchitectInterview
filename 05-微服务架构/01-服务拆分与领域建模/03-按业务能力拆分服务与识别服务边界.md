# 03. 按业务能力拆分服务与识别服务边界

## 边界信号

- 不同业务目标与语言。
- 不同变化原因和发布节奏。
- 清晰数据 Ownership。
- 独立扩缩容/安全要求。
- 团队能够端到端负责。
- 边界内部强内聚、跨边界交互相对少。

## 发现方法

Event Storming：从 Domain Event、Command、Actor、Policy 和 Hotspot 识别流程与 Context。结合业务 Capability Map、组织结构、代码依赖和数据库访问验证。

## 不按技术层拆

`User API Service`、`Business Logic Service`、`Database Service` 会让每个 Use Case 跨所有服务，形成高耦合。服务应拥有完整业务能力，而非只拥有一层。

## Granularity

过大：团队无法独立、部署影响广。  
过小：网络调用、Transaction、仓库和 On-call 成本过高。

不追求“一个 Service 一个 Entity”。Order 与 OrderItem 常属于一个 Aggregate/Service。

## Boundary Test

- 能否一句话描述职责？
- 是否有明确 Owner 和 Source of Truth？
- 大多数变更是否留在内部？
- API 是否比内部模型稳定？
- 能否独立部署而无需同时修改邻居？

## 演进

先在 Modular Monolith 内建立 Module 与 Public API，测量 Change Coupling，再拆有明确驱动力的部分。边界错误时合并 Service 也应被允许。

## 总结

服务边界来自业务能力、变化和 Ownership。部署单元只是结果，不是发现 Domain 的起点。
