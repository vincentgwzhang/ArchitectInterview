# 04. 消息顺序、重复消费、丢失处理与死信队列

## Delivery Semantics

- At-most-once：可能丢，不重复。
- At-least-once：不轻易丢，可能重复。
- Exactly-once：通常只在限定系统/边界内成立，外部 Side Effect 仍需幂等。

生产系统通常使用 At-least-once + Idempotent Consumer。

## 顺序

只对需要顺序的 Aggregate 保序，用 `orderId` 等作为 Partition Key。Consumer 使用 Version/Sequence，旧 Event 可忽略。全局单 Partition 会限制吞吐与可用性。

## 重复

通过 Unique Constraint、Processed Event、Upsert、State Version 或自然业务 Key 去重。先 Side Effect 再 Commit Offset 可能重复；先 Commit 则可能丢失，需要明确取舍。

## 丢失

- Producer Ack 与 Retry。
- Transactional Outbox 避免 DB/Event Gap。
- Broker Replication/Durability。
- Consumer 只有成功后 Ack/Commit。
- Reconciliation 检测缺失。

## DLQ

用于无法自动处理的 Poison Message，不是垃圾桶。保留原 Payload、Header、Error、Attempt、Schema Version 和 Trace。设置 Alert、Owner、Triage SLA、Replay Tool。

Replay 前修复根因并保证幂等，避免把同一毒消息无限送回主队列。

## 总结

消息系统应假设重复、延迟和乱序。端到端正确性来自 Outbox、幂等、Version、DLQ 运营与对账。
