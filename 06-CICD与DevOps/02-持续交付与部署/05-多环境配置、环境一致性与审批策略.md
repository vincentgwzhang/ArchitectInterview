# 05. 多环境配置、环境一致性与审批策略

## 环境原则

Build Once，配置外部化，同一 Artifact 在 Dev/Test/Staging/Prod Promote。环境差异应是数据、规模和 Endpoint，而非不同代码分支。

## 配置

- 类型与 Schema Validation。
- 默认值安全。
- Secret 由 Secret Manager 注入。
- 配置进入 Version/Audit。
- Dynamic Change 有 Rollback。

不要在 Repository 保存生产 Secret，也不要通过手工 SSH 修改实例。

## 一致性

IaC 创建环境，Policy 检查 Drift。Staging 重点保持拓扑/版本/安全策略相似，不一定与生产同规模。性能测试需要独立接近生产的容量环境。

## Preview Environment

为 PR 临时创建，自动 TTL 清理，使用合成/脱敏数据并限制权限。控制 Cost、Quota 和外部 Side Effect。

## 审批

风险型策略：低风险标准变更自动；高风险、合规、特殊时间窗需要审批。Approver 看到 Diff、Test、Scan、Artifact、影响和 Rollback。

## 权限

CI 使用 OIDC/短期 Credential，环境 Role 分离，生产最小权限，Break-glass 有审计。批准者与执行系统职责可分离。

## 总结

环境管理应可重复、可审计且尽量相似。审批关注真实风险与证据，而不是每次发布的形式步骤。
