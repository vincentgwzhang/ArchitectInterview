# 01. SPA、MPA、SSR、SSG、ISR 与 React Server Components

> 本章按“业务要求 → 执行与交付机制 → 缓存和失败 → 选型”展开。核验日期2026-11-22：React官方文档标19.3，Next.js App Router文档标16.4.6。通用架构概念与特定框架缓存行为分开，示例不假定任何框架的默认缓存永久不变。

## 一、这些名词回答的不是同一个问题

SPA（Single-Page Application，单页应用）与MPA（Multi-Page Application，多页应用）主要描述导航与文档组织；CSR、SSR、SSG描述UI何时何地生成；ISR描述静态结果如何增量更新；RSC描述组件执行与客户端模块边界。它们不是六个只能选一的互斥框架。

CSR（Client-Side Rendering，客户端渲染）在浏览器执行组件生成界面。SSR（Server-Side Rendering）在请求阶段生成HTML。SSG（Static Site Generation）预先生成内容。一个应用可以首次SSR，随后像SPA一样客户端导航；一个MPA也可在每页嵌入客户端交互岛。RSC可以构建期执行，也可以请求期执行，不能简单等同“每次请求SSR”。

HTML决定初始可见内容，JavaScript决定交互实现，数据与缓存决定内容是否正确。面试先澄清“首屏可见”“首次可交互”“后续导航”“刷新与分享”分别要什么，而不是用一个渲染名词代替完整体验设计。

## 二、SPA/CSR：把应用运行成本更多交给浏览器

### 2.1 首次访问与后续导航

典型CSR首访先取HTML壳，再下载解析JavaScript，执行路由、取数据、计算并绘制。若数据请求直到组件Effect才启动，会形成HTML→JS→数据的瀑布。后续导航可复用应用壳与内存状态，只加载目标代码和数据，适合频繁操作的工作台。

客户端路由通常管理History API、URL解析、返回前进和深链接。服务器仍需将合法应用路由映射到正确壳，而不是访问深链接就404；同时不能把真实不存在的静态资源或错误页面全部伪装200。资源使用内容hash命名并与HTML缓存策略配套，避免旧壳引用已删除chunk。

SPA不是自动离线：Service Worker、资源缓存、数据同步与离线冲突策略需要另设计。离线只读可缓存已授权数据，但共享设备、退出登录和缓存加密/清除边界必须明确；离线付款不能因为界面可操作就宣称成功。

### 2.2 适用与代价

内部Dashboard通常无需公共索引，长会话和强交互使SPA合理；但首屏预算、无障碍与低端设备性能仍重要。大bundle会增加传输、解析和执行负担，即使CDN快也不能省掉CPU。按路由拆代码、并行预取必要数据、限制全局依赖，并测量真实设备。

CSR不等于搜索引擎一定看不到，但依赖爬虫执行JavaScript增加抓取和延迟的不确定性，社交预览抓取器更可能只读取HTML。若公共落地页的标题、摘要和正文必须立即可抓取，优先预渲染，不以“某搜索引擎理论支持JS”作为全部SEO方案。

## 三、MPA：每次导航获得新文档

MPA完整导航通常向服务器取得目标HTML，浏览器替换文档。服务端模板、静态文件或SSR都能生成它，因此MPA不等于每次必须动态查库。页面边界让部署、缓存、权限和错误状态更直观；链接与表单可先用浏览器原生行为工作，再渐进增强。

Progressive Enhancement（渐进增强）先提供可用HTML与原生表单，JavaScript增强局部交互。内容站、简单业务流程、多个相对独立站点适合此思路；不是所有界面都值得建立客户端路由与全局Store。

跨页内存状态会因文档切换消失，需用URL、服务器会话或持久草稿恢复，不能依赖某组件仍在内存。连续复杂编辑、实时协作和跨页拖拽更适合持久应用壳或局部SPA。MPA也可保留浏览器回退体验，但草稿与鉴权仍需显式验证，不能靠浏览器缓存当业务持久化。

## 四、SSR：请求期HTML与水合是两个阶段

### 4.1 执行机制与成本

动态SSR典型链路为请求进入渲染区域、验证身份、取必要数据、生成HTML、发给浏览器，再加载客户端代码Hydration（水合）。水合让React接管已有HTML并建立交互；HTML可见不代表所有按钮已可执行。

SSR可减少浏览器等数据后才见正文的问题，但增加服务器CPU、内存、连接与依赖调用。若每次请求串行等待慢数据库，TTFB（Time to First Byte，首字节时间）可能很高。边缘渲染也不自动低延迟：渲染节点靠近用户但远离数据库，跨区往返可能抵消收益。部署位置应按用户、数据主区与依赖关键路径综合选择。

“SSR每请求生成”描述未命中共享页面缓存的动态模型。实际系统可缓存公共HTML或片段，缓存命中时不必重新渲染，所以容量估计必须区分边缘请求量、源站请求量和动态渲染量。个性化页面不能因节省成本就按URL共享缓存。

### 4.2 何时适合与不适合

动态公共内容、搜索入口重要的商品页、用户需要马上看到个性化摘要时可选SSR。完全登录后的长会话工具若没有首屏/抓取收益，SSR可能只增加部署和水合复杂度，应与CSR实测比较。

SSR不是安全授权层的替代品。服务器渲染前应按请求鉴权，后续API同样鉴权；初始HTML与序列化数据不能包含本不应发送的字段。框架转义应保持，禁止将未转义用户内容拼进script。失败要返回合适整体状态，若已流式发头，后续区域失败只能局部呈现并上报，不能期望把已发200改为500。

## 五、SSG：用预计算换运行时稳定性

构建期按内容和路由生成HTML与相关资源，部署后可由CDN（Content Delivery Network，内容分发网络）就近提供。文档、营销、帮助页常适合：内容可接受发布周期更新，无需每个请求等待渲染服务，源站计算压力小。

代价转移到构建与发布：大量路由、语言、地区和版本组合可能使构建时间与产物膨胀。数据错误也可能在构建期复制到所有页面，所以需要预发布校验、预览、版本化制品和可回滚部署。旧内容不是“静态就永远正确”，内容Owner和更新时限仍需管理。

SSG页面可以有客户端交互与动态片段，例如静态说明加实时库存；静态结果只应宣称它确实知道的事实。不能把构建时库存当结算保证，也不能把个性化用户名烘焙到公共制品。若部署是纯静态导出，没有运行时再生成服务，就不能仅配置一个revalidate数字假装具备ISR。

## 六、ISR：增量更新的状态机与过期窗口

### 6.1 时间触发不是定时完成承诺

ISR（Incremental Static Regeneration，增量静态再生成）保留已生成结果，按时间或事件使其重新生成，减少全站重建。具体是同步等待还是后台再生、何时清缓存和失败如何退回，属于框架/平台协议，不是HTTP或React统一保证。

以本次核验的Next.js App Router时间再验证示例为例，TTL到期后的请求仍可得到旧结果，并触发后台生成；成功后后续请求见新结果。TTL不是严格刷新周期，更不是“数据最多旧TTL秒”：低流量无请求、生成耗时、失败重试和多级缓存都扩大实际旧窗口。

虚构时序：t=0生成v1，TTL=60秒；t=65首次过期访问拿v1并触发生成，t=69生成v2完成，后续访问才可能见v2。若内容在t=1改变，旧内容持续约68秒；若生成失败，旧版本可能保留更久。严格价格/授权不能依赖这一弱新鲜度。

### 6.2 事件失效与并发失败

CMS发布事件可触发路径或标签失效；失效不一定等于立刻生成完成。Next.js当前指南中revalidatePath的相关场景是后续请求再生成；不能把它与其他路由API的主动再生混为一谈。Webhook需验证签名、权限、重放和幂等，避免任意调用者清全站缓存造成源站洪峰。

再生应处理并发合并，避免同页大量过期请求同时压数据库；旧版本与新版本切换应按平台原子发布机制核验。多个实例若使用各自本地缓存，一处失效不自动使其他实例同步，应使用平台协调或共享缓存方案，测试不同副本、区域和CDN的实际可见性。

当前Next.js指南说明再验证异常时可继续提供上次成功数据，再在后续请求重试。这提高可用性却延长陈旧时间；监控最后成功生成时间和内容版本，超过业务最大允许陈旧期应告警、降级或停止展示关键数据，不把“页面200”当全部成功。

## 七、React Server Components：执行边界与交付边界

### 7.1 RSC与SSR如何组合

RSC在客户端应用之外的服务器环境执行，生成组件输出的可传输表示，再与Client Component引用组合。服务器组件本身的执行实现不必随客户端bundle发送，适合数据访问和依赖重的纯展示；仍可能发送它读取后渲染出来的数据，所以“不发组件代码”不等于“不泄露数据”。

SSR可将组合结果生成初始HTML，客户端随后水合需要交互的组件；客户端导航也可取得框架RSC载荷来更新树，而非每次完整文档。RSC载荷不是简单HTML，也不是业务REST API的通用替代。构建期RSC可与SSG组合，请求期RSC可与SSR/Streaming组合。

React19的RSC特性稳定不代表自行实现框架/打包器的底层API都遵循相同semver承诺；官方仍提示框架集成API可能在19.x minor变化。应用应使用兼容框架并锁定依赖、验证升级，而不是自行复制内部协议。

### 7.2 use client与依赖图

'use client'标记模块及其传递依赖进入客户端代码边界，不只是标记一个DOM子树，也不等于“此组件永远不参与服务端初始预渲染”。在RSC框架中，需要state、事件处理器、Effect或浏览器API的组件通常是客户端边界；初始预渲染阶段仍不能随意读window。

边界尽量靠近需要交互的叶子：把整个页面标client，会将它导入的许多依赖拉入客户端图，削弱减JS收益。Client模块不要直接导入数据库或秘密管理模块；服务器父级可以把已渲染的服务器内容作为children等位置传给客户端外壳，这是组合，不是客户端运行服务器模块。

跨边界props要遵守React支持的可序列化类型，不应笼统说“仅JSON”，也不能传数据库连接或任意闭包。Server Function引用有专门协议与安全职责，普通函数并不会自动远程执行。只传客户端真正需要的字段，避免把完整User实体交给浏览器再隐藏字段。

### 7.3 最小组合示例与失败含义

以下为支持RSC的框架模块示意，不是普通Vite CSR项目直接可运行代码。

~~~jsx
// ProductPage.jsx：服务器模块
import BuyButton from './BuyButton.jsx';
import { getPublicProduct } from './product-data.js';

export default async function ProductPage({ productId }) {
  const product = await getPublicProduct(productId);
  if (!product) return <p>商品不存在</p>;
  return <article>
    <h1>{product.name}</h1>
    <p>展示价格：{product.displayPrice}</p>
    <BuyButton productId={product.id} />
  </article>;
}
~~~

~~~jsx
// BuyButton.jsx：客户端模块
'use client';
import { useState } from 'react';

export default function BuyButton({ productId }) {
  const [message, setMessage] = useState('');
  return <button type="button" onClick={() =>
    setMessage('准备购买：' + productId)}>
    {message || '选择商品'}
  </button>;
}
~~~

getPublicProduct是应用提供的数据访问函数，需处理超时、结构校验、公开字段筛选及当前页缓存策略。示例没有实现下单，也不宣称数据库访问自动缓存。真正购买由服务器重新验证当前价格、库存、身份和幂等，不信任客户端传回的展示价格。

不存在商品的生产页面还需框架正确404/metadata机制，不能只返回一段文字而保持所有错误200。失败放在适当路由/区域边界，慢推荐可在独立Suspense中流式补齐；主商品不可用时不能把旧页面装作购买已确认。

## 八、缓存、Hydration与运行时治理

### 8.1 缓存不是一个开关

至少区分数据缓存、渲染结果缓存、CDN响应缓存、浏览器资源缓存与客户端路由缓存。只失效数据不保证所有旧页面立即消失，服务器刷新也不保证某个已打开浏览器立刻更新。写操作后明确哪些键、路径、区域和客户端视图要更新，以及允许多久旧。

Cache Key（缓存键）除路径还可能包含语言、币种、地区和租户；维度增加会降低命中率并扩大容量。个人敏感结果默认避免共享缓存，安全的公共壳与私人片段分开。缓存策略必须测试匿名/登录、不同用户/租户与退出登录，不以“CDN默认聪明处理cookie”作安全假设。

Next.js在不同版本、路由和Cache Components配置下默认行为与API有差异。当前16.4.6缓存指南介绍'use cache'/cacheLife等能力，不应把旧教程的“所有fetch默认缓存”复制为通用保证。确定项目版本、配置、运行时和部署方式后，实际观察生产构建行为。

### 8.2 水合、载荷与可交互

Hydration要求服务端与客户端初次UI匹配。随机数、当前时间、时区格式、浏览器存储、非法HTML嵌套和不同初始数据都可能产生Hydration Mismatch。传递确定初始数据，浏览器特有部分在明确客户端阶段处理；不要大面积suppressHydrationWarning掩盖错误。

关注HTML大小、内联初始数据、RSC载荷与客户端JS总量。SSR可能让用户早看见，却仍因大量JS水合而晚交互；RSC减少某些客户端代码，也可能因为输出过大和重复数据增加传输。应测首屏内容与真实交互，不以一个“使用RSC”标签保证性能。

流式SSR先发Shell再逐步补内容，可缩短慢区域拖住全部内容的时间。代理/CDN缓冲会消除逐段到达收益；还需CSP、断连清理、截止时间和资源限额。已发HTTP响应头后不能任意改状态，所以服务器与客户端错误监控必须关联。

### 8.3 区域容量与成本

服务器SSR/RSC把部分CPU、内存和数据访问移到服务端。应估动态渲染QPS、缓存命中、依赖并发、平均与尾延迟，并为故障副本留容量。静态内容CDN化降低动态负担，个性化区域拆分减少缓存碎片，但工程复杂度也增加。

虚构估算：边缘1000请求/秒、公共页缓存命中率90%，源站约100请求/秒；每请求平均渲染占用0.2秒，则平均在途约20。它不是20个CPU核心需求：若大部分时间在等I/O，CPU预算另算，尾延迟、重试与副本故障也未包含。用负载与故障实验验证容量，不凭平均算术承诺SLO。

## 九、按Route选择混合策略

| 场景 | 常见起点 | 条件与失败策略 |
| --- | --- | --- |
| 内部Dashboard | SPA/CSR | 强交互与长会话；治理首屏、错误和离线边界 |
| Marketing、Documentation | SSG | 发布新鲜度可接受；构建校验、回滚与元数据 |
| 新闻、公共商品详情 | SSG/ISR或SSR | 按内容更新时限、长尾规模和源站成本选择 |
| 高度个性化首屏 | 动态SSR或CSR | 比较首次可见收益与成本；私人缓存隔离 |
| 数据密集公共页面 | RSC配合预渲染/SSR | 小客户端交互岛；控制输出载荷与依赖瀑布 |

同站首页可静态、商品详情增量、结算动态、后台CSR。Hybrid Rendering（混合渲染）减少一刀切，但要统一URL、认证、错误、遥测与发布资源版本。不要为每个页面引入一套无治理的框架。

选择时依次澄清用户设备/网络、SEO与Social Preview、新鲜度、个性化、交互、离线和预算。再指定每条Route的生成时机、缓存键/最大旧窗口、依赖区域、水合范围及失败兜底。可填写决策句式：“本路由服务[用户]，首屏需[目标]，内容允许旧[时限]，敏感范围[范围]；采用[策略]，缓存[层与键]，失败[动作]，用[指标]复核。”

演进优先从一个有明确问题的路由开始：先基线测量，抽出公共内容与交互叶子，建立缓存隔离和回滚，再灰度比较。不要同时把路由、认证、缓存和数据模型全部重写，否则故障归因困难。

## 十、完整面试回答与追问

### 10.1 电商前端如何选？

“先区分公共获客和交易。营销页SSG，商品页根据更新频率与允许旧窗口用ISR或SSR；购买按钮是客户端交互，结算由动态且鉴权的服务确认价格与库存。可用RSC减少展示逻辑进入客户端，但不把展示缓存当交易真相。按路由设计缓存、错误、元数据和发布回滚。”

追问：ISR展示旧价格怎么办？明确展示与结算边界，允许旧才缓存；点击购买必须服务器重新报价并让用户确认差异，严格实时价则不依赖宽松再生窗口。

### 10.2 内部系统为什么不直接SSR？

“内部工具通常长会话、无需公共SEO，CSR可能更简单。但若低端设备首屏或关键摘要确有问题，我会比较SSR实际收益与服务端成本、水合负担，不机械排除。先优化bundle与数据瀑布，再用同条件测量决定。”

追问：SPA能离线吗？需要单独的资源/数据缓存、权限与冲突策略；导航模型不自动提供离线写入可靠性。

### 10.3 RSC与SSR有什么区别？

“RSC决定哪些组件在客户端之外执行及如何跨边界组合，可在构建或请求时运行；SSR生成初始HTML并由客户端水合交互部分。两者可以组合，Client Component也可能预渲染。服务器模块不进bundle不等于它输出的数据不会进入浏览器。”

追问：use client放根部最省事？实现可能方便但会扩大客户端依赖图，增加JS；应将交互边界靠近实际需要处，同时保持props可序列化与秘密隔离。

## 十一、扫雷自测与推理答案

1. **SPA与SSR互斥吗？** 不，初次SSR后可客户端导航；导航组织和HTML生成时机是不同维度。
2. **SSG内容会过期吗？** 会，制品反映生成时数据，需发布/失效机制；静态不是永久正确。
3. **ISR TTL=60是否最多旧60秒？** 不，过期请求触发、生成时间、失败和多层缓存均可延长；严格新鲜度需另外设计。
4. **SSR是否一定更快？** 不，服务器排队、跨区依赖和水合可抵消收益，必须比较可见与可交互时间。
5. **use client是否禁止SSR？** 不，在RSC框架中它定义客户端模块边界，初始页面仍可预渲染HTML。
6. **RSC是否只在请求期运行？** 不，也可构建期；其服务器环境不是浏览器执行环境。
7. **个性化页面按URL共享缓存可行吗？** 通常危险，同URL不同身份内容不同，需作用域隔离或不共享。
8. **刷新数据为何还见旧页面？** 数据、页面、CDN与客户端路由缓存可能分别存在，需明确失效传播与旧窗口。
9. **RSC props只允许JSON吗？** 过度简化，应遵守React支持的可序列化类型；任意闭包和连接不可直接传递。
10. **首屏HTML存在就能交易吗？** 不，交互代码与水合可能未就绪，交易还需服务器重新鉴权和验证事实。
