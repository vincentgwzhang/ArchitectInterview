# 05 微前端、Module Federation、独立部署与团队边界

## 一、先判断组织问题，再选择技术

微前端（Microfrontend）把前端按业务能力划分为可独立交付的应用，由各团队负责构建（Build）、测试（Test）、部署（Deploy）及线上支持，再组合为用户看到的产品。它首先解决发布协调和所有权问题，不是让一个页面同时使用多个框架的技巧。

假设商品、结算、账户由三个长期团队维护。结算的小改动必须等商品团队完成回归，说明交付边界可能不合理。若拆分后结算能够在兼容现有外壳和服务端接口的条件下发布、观察、回滚，才取得了独立交付收益。仅把代码分到三个仓库，却必须每周一起上线，得到的是分布式单体（Distributed Monolith）：部署分散，协调依赖仍然集中。

决策前收集发布等待时间、跨团队修改比例、故障影响范围、重复依赖体积和平台维护投入。用真实基线判断拆分是否减少等待，而不要承诺某个没有测量依据的性能提升。多仓库不等于微前端，单仓库（Monorepo）也可以产出独立部署的应用。

适合的条件是业务域相对稳定、团队能够端到端负责、有兼容性测试与灰度能力，并且发布协调成本确实显著。一个小团队、业务边界不断变化、所有功能都必须同步发布，通常应优先模块化单体：在一个应用内按领域组织代码，限制模块依赖，复用成熟构建和发布流程。微前端不能替代组织边界设计，也不能凭空提供平台工程能力。

## 二、五种集成方式如何取舍

| 方式 | 如何工作 | 发布与失败边界 | 适用场景及代价 |
| --- | --- | --- | --- |
| 构建期包（Build-time Package） | 应用在构建时安装并打包领域或组件包 | 消费者升级包后重新构建发布；运行时没有额外远程容器 | 类型检查和依赖追踪直接；不提供消费者的运行时独立升级 |
| 运行时模块联邦（Module Federation） | Host 在运行中取得 Remote 暴露的模块，并可协商共享依赖 | Remote 可独立部署，但加载、版本与契约错误进入用户请求路径 | 适合同一页面的可信业务模块组合；需要运行时治理 |
| 路由级组合（Route-level Composition） | 不同 URL 前缀进入不同应用，可通过网关或外壳分派 | 页面边界清楚；跨应用跳转可能整页加载 | 适合业务域清晰、整页迁移；全局体验与登录仍要统一 |
| 服务端或边缘组合（Server/Edge Composition） | 服务端或边缘把各域提供的 HTML 片段组合输出 | 组合层必须控制各片段超时、缓存和降级 | 适合内容页面；交互激活、个性化缓存与脚本协调更复杂 |
| iframe | 在独立浏览上下文中嵌入应用 | DOM、样式和全局对象天然分开；安全性还依赖源与 sandbox 策略 | 适合遗留或隔离要求强的系统；增加导航、通信、焦点和可访问性成本 |

构建期包的 TypeScript 类型兼容只能检查编译时可见的形状，不能证明业务语义兼容。运行时 Remote 即使提供类型声明，实际部署的 JavaScript 也可能与声明不一致，因此仍需要运行时检查和契约测试。

服务端组合不是无成本并行化：假如非关键推荐片段很慢，组合层应在预算耗尽后省略推荐，而不是拖住主内容。涉及用户身份的片段必须按身份与权限设计缓存键，避免把个人内容共享缓存给其他用户。对需要服务端渲染的交互页面，还需约定客户端激活（Hydration）如何接管对应 HTML；不能把分别生成的脚本直接拼接就认为一致。

选型时先问最小必要组合粒度。如果路由级即可消除发布等待，就不必为了复用一个按钮引入运行时联邦。设计系统通常用版本化包分发，比把每个基础组件都做成远程模块更容易控制可用性。

## 三、按业务能力划分所有权

商品（Catalog）、结算（Checkout）、账户（Account）是业务能力；Header、Button、Table 是视觉或技术层次。按业务能力划分可以把一次需求涉及的界面、接口、测试与线上责任放在一个团队。按页面零件拆成很多团队，会让一个结算需求需要多方同步，削弱自治。

| 责任 | 主要所有者 | 必须约定的边界 |
| --- | --- | --- |
| 全局路由、导航、布局、登录状态接入、异常兜底 | 外壳 Shell 团队 | 路由前缀、登录状态更新、加载失败体验、外壳兼容周期 |
| 领域功能、领域 API 契约、测试、值班与生产支持 | 领域团队 | 功能行为、权限需求、输入输出、可回滚版本 |
| 设计令牌、设计系统、监控 SDK、发布工具 | 平台团队或明确维护者 | 版本策略、支持窗口、升级路径、故障响应 |
| 搜索到商品到支付的跨域旅程 | 指定旅程负责人及相关领域团队 | 验收标准、关联追踪、联合事故流程 |

外壳应提供稳定能力，而不是不断接收领域判断。例如“用户是否已登录”可由外壳提供，“该订单是否允许退款”属于订单业务规则，并由后端最终校验。把所有业务权限和流程编排集中到 Shell，会让它成为每次发布的协调中心。

独立部署也不要求团队完全没有依赖。关键是日常兼容改动不必同步发布，破坏性演进有明确迁移窗口。如果某两个模块频繁互相修改内部对象，应重新审视领域划分，必要时合并，而不是继续增加通信层。

## 四、Module Federation 到底执行了什么

以下讨论以 webpack 5 的 ModuleFederationPlugin 为基础，不把其他联邦运行时或构建工具的配置当成相同标准。Host 是消费远程模块的构建，Remote 是暴露模块的构建；一个构建也可以同时承担两种角色。

以 Shell 加载结算页面为例，典型流程是：

1. Host 确定 Remote 容器入口地址，加载入口脚本；入口通常称为 remoteEntry。
2. 联邦运行时初始化共享作用域（Share Scope），让容器接入已提供的共享模块。作用域是依赖共享与版本协商的逻辑空间，不是安全沙箱。
3. 从容器取得暴露模块的工厂，过程中可能继续下载代码块（Chunk）。
4. 执行工厂得到模块导出，再由应用调用组件或挂载接口。

底层容器接口包含 init 和 get；普通业务代码通常使用编译后的 import，由生成的运行时代为处理。remoteEntry 加载成功不代表页面加载成功：后续 chunk、共享依赖、模块求值和渲染都可能失败。远程模块仍在宿主页面的 JavaScript 执行环境中运行，错误代码可能影响整个页面。

下面是两个独立工程的配置片段，展示边界而非完整可运行项目。两边均需安装 webpack 5、配置源代码转译、实际入口与开发或生产服务器；代码未实际执行构建。

Remote 工程：

```js
const { container: { ModuleFederationPlugin } } = require("webpack");
const deps = require("./package.json").dependencies;

module.exports = {
  output: { uniqueName: "checkoutApp", publicPath: "auto" },
  plugins: [
    new ModuleFederationPlugin({
      name: "checkout",
      filename: "remoteEntry.js",
      exposes: { "./Page": "./src/CheckoutPage" },
      shared: {
        react: { singleton: true, requiredVersion: deps.react, strictVersion: true },
        "react-dom": { singleton: true, requiredVersion: deps["react-dom"], strictVersion: true }
      }
    })
  ]
};
```

Host 工程：

```js
const { container: { ModuleFederationPlugin } } = require("webpack");
const deps = require("./package.json").dependencies;

module.exports = {
  output: { uniqueName: "shellApp", publicPath: "auto" },
  plugins: [
    new ModuleFederationPlugin({
      name: "shell",
      remotes: {
        checkout: "checkout@https://static.example.com/checkout/v17/remoteEntry.js"
      },
      shared: {
        react: { singleton: true, requiredVersion: deps.react, strictVersion: true },
        "react-dom": { singleton: true, requiredVersion: deps["react-dom"], strictVersion: true }
      }
    })
  ]
};
```

Host 的异步业务入口可使用 import("checkout/Page") 消费暴露项。示例域名和 v17 是虚构占位值；部署地址必须真实存在且获得信任。两个工程的依赖范围应由团队批准，并在锁文件中固定实际安装结果。uniqueName 降低不同构建运行时命名冲突；publicPath: "auto" 帮助运行时推导资源基础地址，仍需在 CDN、代理和嵌套路径环境验证 chunk 地址。

Host 的初始入口通常只做异步 import("./bootstrap")，把消费共享依赖的业务代码放在 bootstrap 内，为共享模块的异步准备留出边界。遇到 eager consumption 错误，应检查启动顺序和共享配置；把所有依赖设为 eager 会提前打包和加载，可能增加首屏成本，不能作为普遍修复。

## 五、共享依赖：去重不等于兼容

singleton 的目的，是在一个共享作用域内限制某个共享模块使用单一版本；requiredVersion 表达消费者接受的版本范围；strictVersion 在不满足指定版本要求时启用拒绝逻辑。具体选择还受已加载模块、提供者和运行时配置影响，不应假定页面中途能安全替换已经使用的 React。

React 组件跨构建组合时，重复 React 可能导致 Hook 调用等问题，因此通常协调 react 与 react-dom 的共享策略和兼容版本。singleton 本身不证明两个版本兼容：不严格拒绝时可能只是警告并继续使用不满足需求的版本；严格拒绝则把问题显式变成加载失败，需要前面的降级能力。还应保证相关子路径导入与构建产物使用一致策略，并通过实际依赖图和产物验证，而不是看到一个配置项就宣称全页只剩一份代码。

上下文（Context）还有身份问题：Provider 和消费者必须引用同一个 Context 对象。即使 React 被正确共享，两份各自执行 createContext 的“平台上下文模块”仍是不同对象。可以共享稳定的平台契约模块，也可以通过普通属性传递小型、明确的数据，避免隐式上下文耦合。

不要默认共享所有依赖。领域内部工具允许各自打包，换取独立升级；大而稳定的框架共享可以减少重复下载，但扩大共同升级与故障影响范围。每增加一个共享包，都要问它是否真的值得成为跨团队兼容性承诺。旧框架迁移时，路由级或 iframe 隔离可能比强迫互不兼容版本共用 React 更合理。

## 六、运行时契约与生命周期

可独立交付的 Remote 必须暴露稳定接口。直接暴露 React 组件便于组合，但耦合 React 版本和渲染语义；暴露 mount/unmount 适合较粗粒度边界，却需要自行治理资源清理、导航和异常上报。

下面是挂载契约示意，类型只表达接口，还需运行时检查 Remote 的导出结构：

```ts
type CheckoutInput = {
  contractVersion: 1;
  locale: string;
  orderId: string;
  onNavigate: (relativePath: string) => void;
};
type Mounted = { unmount(): void };
type CheckoutModule = {
  mount(element: HTMLElement, input: CheckoutInput): Mounted;
};
```

契约还必须说明语义：element 的子节点由 Remote 管理；Remote 不修改外部 DOM；unmount 可重复调用并移除监听、定时器、订阅和自己的渲染根；orderId 变化是重挂载还是显式更新，必须选定一种。网络请求可以被取消时应取消，即使取消失败也应忽略已卸载实例的返回结果。不要依赖“切路由会自动回收所有资源”。

加载边界和 React 错误边界（Error Boundary）分工不同：加载器处理脚本下载、容器初始化、超时与导出校验；错误边界处理其子树渲染等 React 捕获范围内的错误。普通事件处理器或独立异步回调的异常不能依靠错误边界统一接住，应在相应调用边界处理并上报。

超时表示用户等待预算已耗尽，不等于远程脚本停止执行。Promise.race 只决定谁先完成，不能取消已经开始的脚本执行。假如用户从结算跳到账户，结算随后加载完成，Host 必须通过导航序号或实例标识识别过期结果，禁止再次挂载；超时后的迟到结果同样不能覆盖兜底。

兜底应与业务风险匹配：推荐失败可隐藏；结算失败应展示明确不可用、重试或受控跳转，不能显示“支付成功”。支付请求超时后的真实状态应通过服务端订单查询和幂等机制确认，重新加载前端不是事务恢复协议。

## 七、独立部署、缓存和回滚是一套协议

独立部署意味着可以单独发布兼容实现，不意味着可以随时删除暴露模块、改属性含义或升级到不兼容框架。把静态产物上传成功只是发布的一部分，还需要选择用户会加载哪组版本。

一种可治理方案是版本化清单（Manifest）：维护路由、Remote 地址、契约版本、构建标识和兼容外壳范围；Host 在会话开始或受控导航时解析清单，并为本次会话固定解析结果。动态清单需要相应动态加载适配层；前面固定 remotes URL 的配置不会自动变成清单加载器。

发布顺序应为：上传完整新版本产物，验证入口和所有 chunk 可用，运行兼容测试，再以灰度方式切换清单指针。产物路径采用版本或内容哈希，避免覆盖旧文件；可变清单设置较短缓存或重新验证，不可变 chunk 可长缓存。remoteEntry 是否可长缓存取决于 URL 是否不可变，不能把所有入口一律当成永久可变文件。

回滚主要是把新会话选择恢复到已验证版本，同时恢复相容的外壳与服务端行为。旧产物必须保留到覆盖支持中的浏览器会话和缓存窗口，否则旧标签页稍后加载懒 chunk 会报错。仅给 remoteEntry 加时间戳，无法修复其引用的 chunk 被删除。

已经执行的 JavaScript 不会因清单回滚自动卸载；单例依赖尤其不能随意热换。对已受影响会话，按风险提供重载或明确引导，并保护未提交表单。回滚流程应演练“新入口错误”“入口成功但 chunk 404”“旧标签页继续使用”“后端已经演进”四类情况。后端字段先扩展、兼容旧读写，再迁移并清理，是保持前端可回滚的重要前提。

## 八、状态共享与平台能力

跨应用状态应尽量小且显式：

- URL 表达可分享、可刷新恢复的页面位置和筛选条件；禁止在 URL 放凭证或敏感个人数据。
- 后端保存订单、购物车等业务事实；浏览器内的事件不能作为最终交易结果。
- 明确的属性或版本化事件传递少量交互通知；需要规定发送者、订阅者、字段含义、版本和清理规则。
- 平台 API 提供稳定能力，例如导航、语言、埋点与登录状态读取，不暴露任意内部全局对象。

例如 cart.changed.v1 只通知“购物车可能变化”，消费者随后按权限重新查询后端。事件可带 eventId 和业务实体标识，避免把支付信息或令牌广播给所有 Remote。重复通知应能安全处理；同页事件通常不持久化，晚订阅者可能错过，所以首次挂载也要主动读取当前状态。需要跨设备可靠传递的业务事件应由后端承担。

把所有应用接到一个大型全局 Store，会使字段结构、更新时序和内部动作变成公共协议。一个团队重构 reducer 可能迫使其他团队同步升级，这就是分布式单体的另一种表现。确需共享时，应共享稳定读模型或命令接口，明确所有者和兼容策略。

设计系统（Design System）和设计令牌（Design Token）适合版本化发布，并提供弃用窗口。一个巨型 shared 包同时承载 UI、鉴权、订单状态与工具，会扩大升级影响面。应按变更频率和职责拆分，而不是追求所有应用随时使用“最新公共包”。

## 九、安全、路由与用户体验边界

### 9.1 Remote 是可信代码执行，不是权限隔离

通过联邦加载的代码通常拥有页面脚本的能力，可以访问可见 DOM、非 HttpOnly 存储及页面可调用的接口。来自不同 CDN 域名不等于在另一个权限沙箱中执行。CORS 解决部分跨源读取约束，不负责证明远程业务代码可信，也不是用户授权机制。

应限制 Remote 来源和发布权限，保护产物与清单，审核依赖及构建链，记录谁发布了哪个版本。内容安全策略（CSP）限制脚本来源有价值，但被允许来源遭篡改仍可能受害；入口完整性校验也不能自动覆盖动态 chunk，完整性治理必须覆盖实际加载链并验证工具支持。服务端仍需对每个请求做身份和权限检查，Shell 隐藏菜单不构成授权。

### 9.2 iframe 的隔离也有前提

跨源 iframe 受同源策略限制，sandbox 可进一步限制脚本、表单或导航等能力。不要把同源 iframe 配上 allow-scripts 和 allow-same-origin 就宣称是可靠的不可信代码沙箱；该组合对同源嵌入存在逃逸限制的风险。隔离敏感第三方时应采用独立源和最小能力，并测试实际浏览器行为。

postMessage 发送应指定精确 targetOrigin；接收应同时检查 event.origin、event.source、消息类型、版本和字段，避免其他窗口伪造“登录完成”或“付款成功”。不要通过宽泛消息广播长期令牌。若 sandbox 导致不透明源，不能照搬普通 origin 校验方案，应另行设计并审查通信认证；没有可靠方案时缩减能力而不是放开全部消息。

### 9.3 同一个产品仍需一致体验

Shell 统一全局路由所有权，各域遵守 base path，避免多个路由器同时争夺浏览器历史。域内跳转通过约定接口发出，刷新深层路径也必须由服务器正确分派；否则站内点击正常，直接打开 URL 却 404。

CSS 可使用局部化类名、命名空间等减少污染；全局 reset、字体和主题令牌由明确所有者控制。Shadow DOM 可用于某些样式隔离需求，但会增加主题、弹层和可访问性集成成本，不能自动解决所有体验问题。导航后更新标题、焦点、加载状态和读屏提示，错误页允许键盘操作。iframe 还需处理 frame 标题、内部滚动和焦点跨边界，验收不能只看截图相似。

## 十、性能、监控与测试

性能成本来自额外网络依赖、下载瀑布、重复框架、初始化和多个团队缺少统一预算。remoteEntry 之后才发现 chunk，可能增加关键路径；共享框架虽然减少重复字节，也可能使启动依赖更集中。应测量冷缓存、热缓存、低带宽、弱设备与深链接场景，区分网络耗时、脚本求值和业务数据等待。

按路由懒加载可减少首屏下载；在用户有明显导航意图时预取下一域可降低等待，但全量预取会浪费带宽并抢占关键资源。给每域设置资源和交互预算，超出后定位具体构建，而不是笼统要求“用联邦优化性能”。后台管理系统也需关注长会话内存泄漏和重复订阅。

监控中为一次错误关联 Shell 构建、Remote 构建、清单版本、契约版本、路由及 traceId，并避免写入令牌或完整敏感订单。Dashboard 同时列出 Owner、当前灰度、兼容范围和回滚入口。将入口失败、chunk 404、版本拒绝、挂载失败、领域 API 错误分开统计，才能找到正确值班团队。

测试采用分层组合：

1. 领域单元和集成测试验证自己的业务规则及失败路径。
2. 契约测试验证导出名称、输入、输出、事件与生命周期；加入不兼容版本被拒绝的反例。
3. 兼容矩阵覆盖仍受支持的 Shell 与 Remote 组合，至少验证候选 Remote 配当前及支持中的旧 Shell，以及候选 Shell 配支持中的 Remote。不是无边界穷举所有历史组合。
4. 跨域端到端测试（E2E）验证登录、商品到结算、返回修改等关键旅程，注入超时、资源缺失和回滚。
5. 灰度按稳定会话或用户分组，观察错误率、旅程完成率和性能；不要让同一会话随机切换不兼容版本。

通过兼容策略缩小矩阵，比指望生产环境自然组合正确更有效。监控与契约测试也不能替代真实业务 E2E：字段都存在，仍可能把金额单位理解错。

## 十一、渐进迁移与退出策略

以一个低风险、边界清楚的路由试点，先确定 Owner、挂载契约、版本发布与监控，再将流量逐步转入新实现。保留旧路由回退能力，检查登录、深链接、埋点、可访问性和关键旅程。不要第一次就拆支付按钮和余额组件，制造高频跨域交互。

验收既看交付也看运行：发布等待是否减少、跨团队同步修改是否下降、线上失败是否能归属与回滚、性能是否在预算内、平台维护是否可持续。如果新模块每次仍需 Shell 一起改，先修正契约或合并边界；不要把失败归因于“还不够微”。

迁移完成后清理旧路由和重复构建，但按会话与缓存保留策略处理旧产物。若收益长期小于复杂度，可以收回到模块化单体，保留领域接口和所有权。优秀架构应允许这种演进，不把工具选择变成不可逆目标。

## 十二、面试完整回答与深入追问

### 问：为什么引入微前端？什么时候不引入？

答：我先确认瓶颈是多团队发布协调，而不是单个构建慢。按稳定业务能力划分端到端 Owner，让各域在兼容契约内独立构建、测试、灰度和回滚。代价是运行时加载、兼容矩阵、统一体验和平台维护，因此小团队或边界不清时优先模块化单体。采用后用发布等待、同步修改比例、故障范围和性能预算检验收益，而不是用应用数量证明成功。

追问：拆仓库后还是一起上线怎么办？答：检查是否共享内部状态、公共包强制升级、服务端接口破坏兼容或 Shell 承担领域逻辑。先减少这些同步约束，无法分离的能力可合并。仓库划分本身不能消除业务耦合。

### 问：Module Federation 如何支持独立部署？

答：Host 在运行时加载 Remote 容器，从暴露接口取得模块，并通过共享作用域协调依赖。Remote 可以独立产出资源，但 Host 能否安全使用它取决于接口、版本和完整加载链。我要同时设计可信来源、依赖兼容、超时兜底、版本固定和回滚，而不是只配置一个远程地址。

追问：singleton 是否保证 React 升级无风险？答：它限制共享实例，不证明 API 和行为兼容。版本范围和严格拒绝策略需要显式配置，并验证 react-dom、子路径和 Context 模块身份。大版本升级可能需要分阶段兼容、路由隔离或新的部署边界。

### 问：Remote 挂了会不会拖垮整个站点？

答：加载器可以将下载、初始化失败限制为局部不可用，错误边界可以兜住一定范围的 React 渲染错误；但联邦代码与 Host 共享执行环境，恶意脚本、无限循环和全局污染不能靠这些机制可靠隔离。关键页面设置等待预算并提供真实失败反馈；更强信任隔离考虑独立源 iframe，并评估体验与通信成本。

追问：超时后能直接重试挂载吗？答：先识别当前路由和实例，忽略迟到结果，清理旧实例并限制重试。对支付等副作用，查询服务端状态并使用幂等协议，不能把加载重试当成交易重试。

### 问：独立部署如何快速回滚？

答：发布不可变资源，再切换版本清单，灰度验证错误和旅程。回滚把新会话指向兼容的旧版本，保留旧 chunk 支持旧标签页。已经执行的脚本不会自动撤销，需要有会话恢复方案，后端也要维持支持窗口内的兼容。观测应带上整组版本，否则无法确认到底哪一组出问题。

追问：直接清 CDN 缓存够吗？答：不够。旧页面已持有旧入口或运行时引用，删除旧资源反而造成 chunk 404；缓存清除也不撤回正在执行的代码。应修正版本指向、保留产物并处理受影响会话。

### 问：跨应用通信如何避免新的耦合？

答：先把业务事实放在后端，把导航放在 URL，少量通知使用小型、版本化事件或属性。明确事件语义、重复与漏收处理、订阅清理及 Owner；拒绝让所有域直接修改一个公共 Store 的内部结构。共享平台能力通过稳定 API 提供，领域规则留在领域团队。

追问：购物车事件丢失怎么办？答：事件只用于提示刷新，消费者挂载时也读取后端当前状态，不能把同页广播当作可靠消息队列。若要求持久和跨设备一致，应由后端事件或查询协议提供保证。

## 十三、扫雷自测：答案与推理

1. **三个仓库、一次联合发布，算完成自治吗？** 不算。代码位置变化没有消除交付依赖，应检查契约和所有权，使兼容变更能单独发布；若业务本来不可分，应接受合并。
2. **remoteEntry 返回 200 就代表 Remote 正常吗？** 不代表。chunk 下载、共享版本协商、模块求值、挂载和 API 都可能失败，因此监控与测试必须覆盖完整链路。
3. **把所有库 singleton 是否性能最好？** 不能这样判断。共享增加共同兼容约束，也可能形成启动依赖；小工具各自打包有时更简单，必须根据真实字节与启动测量取舍。
4. **React 共享了，Context 就一定共享吗？** 不一定。两份 Context 模块各自创建的对象不同，消费者读不到另一对象 Provider 的值；应统一模块身份或改用显式数据契约。
5. **Error Boundary 能接住脚本超时和按钮异步异常吗？** 不能统一处理。脚本超时由加载层处理，事件或独立异步回调在自己的边界处理；React 错误边界负责其约定捕获范围。
6. **加载超时后返回的模块还能挂载吗？** 不能直接挂载。用户可能已离开或已见兜底，必须核对导航与实例有效性，防止旧结果覆盖新页面；超时不等于执行被取消。
7. **清单回滚后旧脚本是否停止？** 不会。旧会话可能继续执行和请求旧 chunk，因此要保留产物并制定必要的重载及状态保护方案。
8. **外壳检查登录后，Remote 请求可省略服务端鉴权吗？** 不可以。浏览器代码与状态可被篡改，最终资源授权必须在服务端执行，菜单可见性只是体验。
9. **跨源 Remote 是否等同跨源 iframe？** 不等同。Remote 脚本通常在 Host 页面环境执行；iframe 有独立上下文，访问限制还依赖源和 sandbox。来源不同不自动隔离执行权限。
10. **兼容矩阵是否需要测试所有历史版本排列？** 不需要无限排列。先确定支持窗口、契约版本和会话固定策略，再覆盖支持组合及关键负例；随意保留所有版本会使治理成本失控。
