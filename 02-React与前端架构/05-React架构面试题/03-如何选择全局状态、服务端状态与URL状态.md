# 03 如何选择全局状态、服务端状态与 URL 状态

状态选型首先是确定数据归属和更新协议，然后才是选择 Redux、Zustand 或 Query。页面复杂不意味着全部状态必须全局化；数据被多个组件读取也不意味着客户端拥有它。高级面试应能说明状态从哪里来、谁能改、何时失效、刷新和后退后发生什么，以及并发失败怎样恢复。

本文使用虚构电商案例，不代表用户项目经历。React 基本示例适用于 18+；服务端缓存术语按 TanStack Query v5，React Query 是其常用旧称。资料于 2026-11-27 核验；代码是可审查的教学片段，未安装运行 React、Router 或状态库。

## 一、对每份状态先问六个问题

| 问题 | 推理方向 | 例子 |
| --- | --- | --- |
| Source of Truth 在哪里 | 谁拥有最终事实和校验权 | 订单归服务端，输入草稿归当前编辑会话 |
| 谁读取与修改 | 最小共享范围和唯一写入责任 | 一个表单内共享不必放应用级 Store |
| 生命周期多长 | 组件、路由、登录会话、跨设备 | 弹窗关闭状态和跨页草稿不应同寿命 |
| 是否可分享、Bookmark、Back/Forward | 是否属于导航状态 | 筛选和分页应能从 URL 恢复 |
| 是否有 Staleness、Cache、Retry | 是否是远程副本及同步协议 | 商品列表需过期、重试和失效 |
| 是否敏感 | 暴露渠道、持久化和清理 | 身份令牌不应进入 URL 或普通日志 |

真相来源（Source of Truth）不是“哪个对象当前保存了一份值”，而是发生冲突时由谁裁决。Query Cache 保存用户资料，但服务端仍拥有最终资料；本地编辑表单可以保存一份有意独立的草稿，必须明确它是草稿而非第二份权威资料。

例如账户名出现在头像、表单和订单历史。头像读当前用户查询，表单使用编辑副本，订单历史可能保存当时快照，三者语义不同。强行只存一份对象也可能错误地让修改账户名改变历史订单展示。先区分事实含义，再讨论去重。

## 二、分类表与选型顺序

| 类别 | 典型内容 | 推荐位置及边界 |
| --- | --- | --- |
| Local UI | Modal、展开项、临时输入 | useState/useReducer；放在最小共同使用范围 |
| URL | Query、Filter、Page、Sort | Router/Search Params；必须可解析、验证和恢复 |
| Server | User、Order、Product、服务端购物车 | Query Cache，如 React Query/RTK Query；有新鲜度与失效 |
| Global Client | 跨路由未提交 Draft、Workflow | Redux/Zustand 等明确 Slice；定义写入动作和重置 |
| Context 传递 | Theme、Locale、Auth Service 实例 | Context 是传递/订阅机制，并非独立事实类型 |
| Form | Validation、Touched、Dirty、字段草稿 | 表单库或局部状态；提交前不等于服务端事实 |
| Derived | 合计、筛选结果、是否可提交 | Render/Selector 计算，通常不额外存储 |

选型顺序可以是：能从现有输入推导就不存；属于服务端事实就选远程缓存协议；属于导航就选 URL；其余先局部，确有跨页共享再上移或引入 Store。Context 可以传递这些状态或服务，但不能因为“用了 Context”就免除生命周期设计。

库不是类别的硬边界。Redux 可通过 RTK Query 管服务端缓存，React Query 也可以被全局多个组件读取；“全局”描述可见范围，“服务端”描述所有权，两者不互斥。

## 三、局部 UI、表单与全局客户端状态

### 3.1 局部优先，但不是禁止状态提升

输入框值、对话框是否打开、当前 hover 一般属于局部。多个兄弟组件需协调时提升到最近共同父级，让它传值和动作；提升到应用根部会扩大依赖与重渲染范围，也使卸载后的重置难以判断。

useReducer 将状态转换集中为动作，适合多字段联动和有约束的流程。不要同时用 isLoading、isSuccess、isError 三个可任意组合的布尔值表达互斥阶段，可以用 idle/submitting/succeeded/failed 状态并明确合法转换。Reducer 便于审查，不自动解决异步取消和后端事务。

### 3.2 表单有独立编辑语义

Touched 表示用户是否接触过字段，Dirty 表示与编辑基线是否不同；它们用于决定何时显示校验和离开提醒。表单库可管理验证、字段订阅和复杂数组，但简单两字段表单未必需要重型依赖。

从查询结果初始化表单后，后台刷新不应无条件覆盖用户正在编辑的内容。可保存编辑基线版本、检测远程更新，再提示合并/重载；提交带版本或 ETag，由后端检查冲突。切换实体 ID 时要明确重置，不可让上一位用户的地址留在下一条记录。

把查询复制到草稿是合理的，条件是区分 draft 与 saved、明确开始编辑和提交/取消动作。每次查询更新都用 Effect 覆盖草稿，或把草稿实时写回所有展示组件，则容易破坏用户修改和双向同步。

### 3.3 什么时候需要全局 Store

跨多个路由的未提交申请、客户端编辑器会话等，可能需要脱离单个组件的状态。Store Slice 是按领域划分的状态与动作边界，例如 checkoutDraft；所有者负责 schema、重置、派生选择器和副作用入口，不应暴露任意字段随意修改。

Redux 的集中动作与工具生态有助于复杂协作和追踪，但会增加规范与样板；Zustand 等轻量 Store 降低接入成本，但团队仍需定义动作、模块边界和订阅策略。小范围状态用局部和组合就够，不能只因未来“可能变大”提前全局化。

全局 Store 通常仍是单页面实例内状态，不保证跨标签或跨设备一致。SSR 时每个请求需独立实例，不能在服务器模块全局保存用户草稿。跨设备恢复若是业务要求，应设计服务端草稿资源与版本协议。

## 四、URL 状态：把页面变成可重现的导航结果

### 4.1 URL 是协议，不是随意字符串

筛选、分页、排序与搜索词应有默认值、合法范围和规范格式。不要把参数直接拼 SQL 或当可信业务值；服务端仍校验请求权限和输入。重复参数、无效枚举、负数页码和过长搜索词要有明确处理。

下面解析器采取教学政策：重复键使用首值；页码只允许 1 至 1000 的规范十进制字符串；非法值回退默认。真实产品可选择显示错误，但前后端及分享链接必须一致。

```js
export function parseProductSearch(search) {
  const p = new URLSearchParams(search);
  const rawPage = p.get('page') ?? '1';
  const page = /^[1-9][0-9]{0,3}$/.test(rawPage) &&
    Number(rawPage) <= 1000 ? Number(rawPage) : 1;
  const rawSort = p.get('sort');
  const sort = ['relevance', 'price-asc', 'price-desc'].includes(rawSort)
    ? rawSort : 'relevance';
  const q = (p.get('q') ?? '').trim().slice(0, 200);
  return { page, sort, q };
}
```

URLSearchParams 负责编码解码，修改时由 Router 提供导航 API，保留不属于本功能的必要参数，并在改筛选时重置页码。需要稳定缓存键时先解析成规范状态，再构造请求，避免 page=01 和 page=1 等被不同层解释为不同值。

### 4.2 区分输入草稿与已提交查询

搜索输入的每个按键可以暂存局部，点击搜索或防抖结束后提交到 URL；商品查询从已提交 URL 状态派生。不要让 URL 和 Store 都独立拥有“当前筛选”，再用两个 Effect 互相同步，这会制造循环、竞态和后退失效。

Push 新增历史项，适合用户想后退恢复的明确导航；Replace 替换当前项，适合默认值规范化或不希望每个按键都增加历史的更新。防抖计时应在后退、离开或输入变化时取消，避免迟到回调把用户后退后的 URL 改回旧查询。

URL 改变后重置局部输入需按交互约定处理，特别是未提交文字和浏览器后退发生冲突时。测试刷新、复制链接、新标签打开、后退前进和非法参数，不能只测一次点击筛选。

敏感个人信息、Token、支付资料不放 URL，因为历史、服务日志、分享和分析系统都可能记录。可分享筛选也要考虑用户搜索词是否敏感；“可以技术上编码”不等于“适合公开”。

## 五、服务端状态：缓存副本必须有同步语义

### 5.1 查询键和身份范围

Query Key 标识一份请求结果，应包含影响结果的参数，例如租户、语言、筛选和页码。多个组件用相同键订阅同一结果有利于复用；漏掉租户会错用数据，加入每次都变的随机值则破坏复用。

```js
const productKey = (tenantId, locale, filters) => [
  'products', tenantId, locale,
  { q: filters.q, page: filters.page, sort: filters.sort }
];
```

这里 filters 来自规范 URL 解析，不把令牌塞进 key。登录身份改变时清理或隔离所有受身份影响的数据，包括持久化副本和在途请求；仅把新用户名写入 Context 不能防旧响应迟到。

TanStack Query v5 的 staleTime 控制数据多久视为新鲜，gcTime 控制不活跃查询可被回收前保留多久；新鲜不等于永久保留，不新鲜也不等于立即删除或每毫秒自动请求。挂载、聚焦、重连、失效等触发与配置共同决定是否重取。应显式按业务配置，不把库默认值当服务等级。

### 5.2 读取、修改与错误

初次加载没有数据与后台刷新已有数据是不同体验：后者通常保留旧内容并显示刷新提示，失败时说明可能过期，而非清空全页。缓存只能提高体验，结账金额、库存和资源权限仍由服务端最终裁决。

Mutation 后可以使用可信返回更新精确缓存，或失效相关查询再读取；必须同时考虑详情、列表及统计是否受影响。不要将服务端响应额外复制到 Redux 的 user 字段：一处刷新、一处仍旧，会出现头像更新但权限页面不更新的双真相。若遗留架构必须并存，应规定唯一写入与读取路径并安排迁移，不能永久用 Effect 对拷贝。

Retry 应区分瞬时网络/服务故障与权限、校验和业务冲突；写操作超时可能已在远端成功，需幂等键或状态查询。Query 库不会自动把业务写入变成事务。AbortSignal 可用于取消读取，但不能据此宣称服务端写入回滚。

### 5.3 乐观更新与并发

乐观更新先在 UI 呈现预期结果，失败再恢复，适合低风险可逆动作。单个快照回滚在并发下可能错误：A 乐观修改，B 随后成功，A 失败回滚旧快照会覆盖 B。可串行同实体写入、使用按操作叠加的乐观层，或完成后重新读取权威状态，选择取决于业务。

搜索 A 先发 B 后发，A 晚返回不能覆盖 B。让请求身份和查询键对应当前参数，按需取消旧请求；自行维护同一个 data 变量时还需序号检查。相同页面组件复用不代表请求语义相同。

## 六、Context：解决传递，不自动解决所有更新

Context 让深层组件读取最近 Provider 的值，适合主题、地区和稳定服务实例。它本身不是请求缓存、持久化或 selector Store。认证可通过 Context 传递 Auth Service，具体会话状态、续期、过期和安全边界仍需设计。

Provider value 变化会使相应消费者更新；React 使用 Object.is 比较前后值。每次渲染都创建大对象会增加更新，memo 包裹消费者也不会阻止接收变化后的 Context。按变化频率和职责拆分 Context，并保持必要的对象引用稳定；高频细粒度数据可考虑选择器 Store。

不要把 useMemo 当成语义正确性的锁。若组件只有在某引用永远不变时才不出错，通常是依赖或副作用设计问题。Context 的默认值只是找不到 Provider 时的回退，不会自动从服务端加载或跨根共享。

## 七、Derived State 与计算成本

派生状态（Derived State）能从已有 props/state 唯一算出，通常直接在渲染或 Selector 中计算。例如整数最小货币单位的商品小计：

```js
const totalMinor = items.reduce(
  (sum, item) => sum + item.unitPriceMinor * item.quantity, 0
);
```

该例假设数值在安全整数范围、单位一致，不包含优惠、税和运费；最终支付金额来自后端。不要用 Effect 把 total 再写入 state，否则多一份同步目标，可能出现一次渲染用新 items 却显示旧 total。

Memoization 缓存计算结果或稳定引用，适用于经过测量的昂贵计算或依赖引用身份的组件边界。依赖改变仍需重算，原地修改 items 却保持引用可能导致错误缓存；不可变更新和正确依赖比加 memo 更重要。普通少量求和不必先优化。

派生值如果后来拥有独立业务含义，例如用户锁定的报价，就不再只是当前 items 的函数，应作为有版本和有效期的业务对象处理，而不是继续叫“缓存合计”。

## 八、Persistence：只保存有明确恢复价值的数据

持久化（Persistence）让状态超过当前页面生命周期，也把数据迁移、权限和损坏问题带进来。只保存需要恢复的草稿、偏好等，并明确 schemaVersion、用户/租户范围、expiry 和迁移函数。未知未来版本或损坏 JSON 应安全丢弃并提示可恢复，不要在启动时崩溃。

旧草稿升级可能丢字段，迁移要验证必要信息并保留用户确认，不能静默提交旧语义。过期按实际业务时间判断，设备时钟不可信的安全决策交服务端。存储可能满、被禁用或写入失败，表单仍应可用，并提示无法跨刷新保留。

Token、PII（个人可识别信息）和 Server Cache 不应随意进入 localStorage。它对同源脚本可读，客户端加密若密钥也在同一页面，不能消除 XSS 风险。确有离线缓存需要时，最小化数据，定义过期、用户隔离、登出清理和重连冲突。

离线操作队列需要操作 ID、重试预算和服务端幂等；多标签同时写草稿需冲突政策，不能把 storage 通知当事务锁。登出时取消或隔离在途请求，清理 Store、Query、持久存储及相关缓存，防止旧请求又把数据填回。SSR 应为每请求创建隔离状态，并只脱水传给浏览器可见的数据。

## 九、电商完整决策与迁移排障

虚构场景：商品筛选进入 URL，输入中的未提交词留 Local；商品列表按租户、地区和规范筛选进入 Query Cache；服务端拥有的购物车也由 Query 管理。购物车抽屉开关是 Local，不因购物车数据在服务端就一起远程化。

结账 UI Step 若只是当前展示可留局部；若支持分享/返回可进入 URL，但服务器仍验证前置步骤和权限，用户把 step=paid 写到 URL 不能完成付款。跨页面未提交地址草稿可进 Global Client Store，需身份范围和完成/取消清理；真正跨设备草稿则设计服务端资源。主题由受控 Context 传递，持久偏好只存允许的标识。

| 症状 | 优先检查 | 修复方向 |
| --- | --- | --- |
| Mutation 后部分页面旧值 | Query 与 Store 双副本、失效范围 | 单一读取来源，更新/失效相关键 |
| 后退后筛选又跳回 | 双向 Effect、迟到防抖 | URL 为已提交真相，取消迟到动作 |
| 切用户看到旧订单 | 查询键、全局实例、持久层和在途请求 | 身份隔离与完整清理 |
| 打字整页卡 | 状态提升过高、Context 大对象 | 缩小范围、拆分订阅，测量后优化 |
| 编辑内容被刷新覆盖 | 查询到表单无条件同步 | 独立草稿基线和冲突提示 |

从全局大 Store 迁移时，先列每个字段的所有读写位置和所有者，把纯派生值删除，再迁 URL 和远程缓存；按领域切换读取入口后移除旧副本。不要一次重写所有状态库。验证后退刷新、失败重试、并发返回、登出换租户和草稿升级，而不仅是成功路径。

## 十、面试完整回答与深入追问

**问：怎样选择全局状态、服务端状态和 URL 状态？**

答：我先看真相来源、共享范围、生命周期、导航重现、远程同步和敏感性。服务端事实由 Query 缓存管理，筛选分页用 URL，临时 UI 和表单尽量局部，跨路由客户端流程才进入明确 Store Slice。Context 用来传主题或服务，不把它当完整缓存工具。派生值计算而不复制，持久化另行设计版本、过期和身份清理。

追问“多个组件都读用户是否放 Redux？”答：共享范围不改变所有权，可以让它们订阅同一用户查询；额外复制一份会增加同步风险。复杂客户端工作流若需要 Store，应只保存独立交互状态或身份引用。

**问：为什么筛选不全放 Store？**

答：筛选通常需刷新、分享与后退恢复，所以 URL 应是已提交筛选的真相。输入草稿可以局部，提交后更新 URL，查询从规范解析结果派生。避免 Store 与 URL 双向同步。

追问“每个按键都 push 吗？”答：不必，可以提交时 push，或防抖 replace，并取消离开/后退时的迟到回调，避免污染历史和覆盖导航。

**问：编辑表单复制 Server State 是否违反单一真相？**

答：不一定，编辑草稿有独立生命周期，关键是明确它不是保存后的事实。记录基线版本，后台更新不覆盖 dirty 字段，提交由服务器检查冲突；取消和切实体时重置。

追问“用 Effect 自动同步不是更实时吗？”答：它可能在用户输入时覆盖草稿，实时远程数据与编辑意图冲突时必须有明确合并策略，不能机械同步。

**问：持久化 Redux 是否能保证刷新不丢状态？**

答：可以恢复部分数据，但必须处理 schema、迁移、过期、写失败、用户范围和登出清理。服务端缓存与敏感数据不应默认落盘，跨设备和离线一致性还需要服务端协议。

追问“浏览器加密够吗？”答：若恶意脚本能同时访问解密能力，仍可能读取数据；加密不能替代减少持久化、XSS 防护及授权。

**问：乐观更新如何处理两个请求竞态？**

答：不能简单用每次旧快照任意回滚，应按实体串行、按操作叠加或重新读取权威结果。UI 速度与一致性成本要权衡，支付等高风险流程更倾向确认后推进。

追问“取消旧请求就解决了吗？”答：取消有资源和传播边界，远端可能已经处理，尤其写入不能当成回滚；仍需身份、版本和幂等控制。

## 十一、扫雷自测与速记

1. **全局与服务端状态互斥吗？** 不互斥，全局描述共享范围，服务端描述事实归属，同一查询可被全局订阅。
2. **Context 会自动避免无关更新吗？** 不会，value 变化影响消费者，应按职责拆分并关注引用，必要时用细粒度选择器。
3. **staleTime 等于删除时间吗？** 不等于，新鲜度和不活跃回收由不同机制处理，过期也不等于立即发请求。
4. **把所有服务器响应存 Redux 更统一吗？** 形式统一但可能重复实现缓存协议；若与 Query 并存更容易双真相，应明确唯一来源。
5. **表单草稿必须跟随后台刷新吗？** 不是，需尊重用户未提交修改并显式处理版本冲突。
6. **后退只改 URL、不改 Store 会怎样？** 若 Store 仍作为筛选事实，页面可能不匹配地址；应从 URL 派生已提交状态。
7. **total 应放 Effect 更新吗？** 通常不用，直接从 items 计算避免同步滞后；独立锁定报价属于另一个业务对象。
8. **全局 Store 能保证跨标签一致吗？** 不能，它通常只存在当前运行实例，多标签需同步及冲突协议。
9. **退出清空 localStorage 就够吗？** 不够，内存查询、Store、持久副本和在途响应都可能恢复旧数据，需要完整身份切换流程。
10. **付款页面 URL 的 paid 状态可信么？** 不可信，URL 可改，服务端支付结果才是事实，前端状态不能替代授权和交易确认。

速记：先归属、再范围和寿命；URL 负责导航重现；Query 负责远程副本；Store 管明确客户端流程；Context 管传递；Form 管编辑；派生少存；持久化要版本、过期、身份与失败恢复。
