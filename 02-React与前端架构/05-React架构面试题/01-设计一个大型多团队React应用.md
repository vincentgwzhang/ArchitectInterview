# 01 设计一个大型多团队 React 应用

本题考察的是如何让多个团队长期交付同一个产品：模块怎样协作、变更怎样发布、失败怎样隔离、用户体验怎样保持一致。回答必须连接业务目标、组织责任与运行机制，不能只画组件树或报框架名称。

以下使用**虚构的多团队电商平台**演示设计：目录、结账、账户分别有负责人，公开商品页需要搜索引擎收录，登录后的购买流程强调可靠性。数字和目标应由真实需求填入，本文不把示例冒充用户经历或性能实验。代码为接口与组合示例，未实际编译或运行。React 示例使用 18+ 可用的 lazy/Suspense 模式；版本敏感资料于 2026-11-26 核验，具体路由、构建和服务端渲染能力依所选框架版本。

## 一、先澄清哪些约束真正改变方案

### 1.1 把问题转为可检验的决策输入

大型可能指代码量、团队数、页面量、流量或组织复杂度，这些不是同一问题。大量用户主要影响 CDN、服务端容量和数据请求；大量团队主要影响边界、接口、发布和维护责任。不能因为用户多就直接采用微前端。

| 澄清维度 | 应问到的具体信息 | 如何影响设计 |
| --- | --- | --- |
| 团队与领域 | 谁维护目录、结账、账户，谁值班，跨域变更多不多 | 模块及 Owner 边界、公共接口和审批 |
| 用户规模与区域 | 活跃与峰值、移动设备、弱网、地区、登录比例 | 缓存、容量、首屏预算和区域部署 |
| 发布 | 频率、等待原因、是否必须独立上线和回滚 | 统一部署还是独立制品及运行时组合 |
| SEO 与内容 | 哪些路由需要收录、社交预览、新鲜度多久 | SSR、SSG、缓存及失效策略 |
| 品牌与体验 | 多品牌、语言、可访问性目标 | Token、设计系统和内容规范 |
| 遗留系统 | 登录、路由、API、嵌入要求及迁移期限 | 适配层、渐进替换和兼容窗口 |
| 非功能需求 NFR | 可用性、延迟、隐私、安全、成本和支持周期 | 故障域、监控、测试及运维预算 |

NFR（Non-functional Requirements，非功能需求）要变成用户任务和验收方法。例如“结账可靠”应明确成功率分母、超时处理、重复提交和故障恢复；“加载快”应说明设备、网络、路由及现场指标分位数。没有这些条件，“所有页面一秒打开”无法有效评估。

### 1.2 明确假设并保留替代方案

面试信息不全时可说：“我先假设团队需要清晰所有权，但没有证据表明必须独立部署；因此采用模块化单应用。若发布等待主要来自跨团队统一发布，而非审批或后端依赖，再评估按路由拆分。”

公开商品页可采用框架支持的 SSR/SSG，登录后交互可在客户端完成；这并不强迫整个系统只选一种渲染方式。SSR 增加服务端计算、缓存隔离和水合复杂性，SSG 面临更新时效，纯客户端页面则需评估首屏和收录。选择应按路由需求解释，而不是认为 React 天然只适合 SPA。

## 二、推荐基线：Monorepo 加模块化前端

### 2.1 仓库、模块、构建、部署是四个维度

Monorepo 是多个项目或包放在同一仓库；Modular Frontend 是按职责限制依赖的模块化前端；它们既不等于全部放一个大目录，也不必然意味着同一部署。反过来，多仓库也不能自动消除耦合。

没有明确独立发布需求时，基线采用一个应用入口，按领域模块组织，设计系统和平台能力通过包交付。可以原子修改相关接口，减少运行时版本组合；代价是共享构建、发布和治理需要控制影响范围。以应用规模而非目录美观决定是否独立打包某个领域。

| 路径示例 | 内容 | 禁止放入的内容 |
| --- | --- | --- |
| apps/web | 页面组合、启动、路由配置 | 所有领域的细节实现 |
| features/catalog | 商品展示模型、查询及 UI | 直接操纵 checkout 内部状态 |
| features/checkout | 草稿、提交和失败恢复 | 整个后端订单 Entity |
| features/account | 账户流程及用户偏好 | 全站通用组件的副本 |
| packages/design-system | 语义 Token、基础组件与交互规范 | 某业务的权限判断 |
| packages/platform | Router 接入、Auth、Telemetry、API Client、Flag、CI 模板 | 所有团队业务逻辑的集中容器 |

Feature 是围绕业务能力的模块，Owner 要负责 API、测试、文档和运行结果，不能只写一个名字。Platform 团队提供通用能力和支持承诺；业务团队仍负责自己的失败体验。设计系统负责一致性、键盘焦点和基础可访问性，但使用者要提供正确文案、字段标签和完整流程。

### 2.2 公共接口与依赖规则

每个 Feature 通过明确入口导出少量能力，例如页面入口、受控命令和稳定类型。跨模块不能深层导入内部 Hook、Reducer 或请求文件，否则每次重构都变成协调项目。index 文件只是约定，必须结合静态规则、依赖图和评审才能执行。

依赖方向可以规定：应用组合领域与平台；领域依赖平台、设计系统及自身；平台不依赖具体领域；领域之间通过受审查公共契约或应用编排协作。循环依赖往往说明职责混杂，要追问是否缺少上层编排或真正共享的概念，而不是把全部代码搬到 shared。

```ts
// features/checkout/public.ts：教学接口，省略具体实现
export type CheckoutRequest = {
  cartId: string;
  expectedVersion: number;
};
export type CheckoutResult =
  | { kind: 'created'; orderId: string }
  | { kind: 'conflict'; message: string }
  | { kind: 'rejected'; message: string };
export interface CheckoutPort {
  submit(request: CheckoutRequest): Promise<CheckoutResult>;
}
```

此接口表达前端用例结果，而不是暴露数据库对象。expectedVersion 可帮助检测过期购物车，但必须服务端真正校验才有效；也不等于支付幂等键。网络异常可通过 Promise 拒绝进入系统错误路径，调用方应显示可恢复状态并确认结果，不能把所有异常映射成业务拒绝。

Lint 或依赖检查需要覆盖相对路径绕过、别名、测试代码和动态导入；只禁一个字符串前缀不充分。TypeScript Project References 可表达项目构建关系、支持分块类型检查与构建，但不是领域授权机制，也不替代所有导入规则。路径别名不会自动建立运行时包边界。

## 三、平台能力：标准化基础契约，不集中业务决策

Router 提供导航、路径生成和错误处理接入，领域定义自己拥有的路由及参数。深链接刷新应由服务端正确路由，路径参数需要校验；权限守卫用于体验，后端仍强制资源权限。路由冲突、未找到和异步加载失败要有一致页面。

Auth 提供身份状态、会话失效和登录入口，避免每个 Feature 独立刷新令牌。浏览器无法保守打包的秘密；BFF 会话可减少令牌暴露，但要配套 CSRF 防护和会话运维。退出应清理用户范围缓存，SSR 请求间不得共享用户会话状态。

API Client 统一请求超时、取消、错误分类和 trace 上下文，领域负责 DTO 到视图/领域模型的转换。不能让公共客户端对所有 POST 自动重试，因为超时可能发生在远端已经成功之后。遥测（Telemetry）统一事件格式和隐私控制，领域定义业务事件的含义。

Feature Flag 是行为开关，用于灰度、关闭问题功能和分阶段迁移。每个开关要有 Owner、默认值、过期时间及失败时策略；权限与价格仍由服务端决定。跨多个开关会形成组合爆炸，测试关键组合并及时清理，不能把临时迁移开关永远堆积。

平台 API 也要版本化和迁移承诺；如果业务团队每次变更都等平台审批，平台会成为瓶颈。让公共接口稳定、业务能力自治，并以提案及服务水平处理真正跨域的改变。

## 四、状态和数据：先确定真相归谁

### 4.1 五类状态分别放置

| 状态 | 存放方式 | 示例与失败风险 |
| --- | --- | --- |
| Local UI State | 最靠近使用位置的组件 | 弹窗、输入草稿；无故上移会扩大重渲染和耦合 |
| Server State | Query Cache 等请求缓存 | 商品和订单；不是永久事实，需失效、错误和权限范围 |
| URL State | 路径与查询参数 | 筛选、分页、排序；需解析、校验和向后兼容 |
| 跨 Feature Client State | 明确 Store Slice 或应用编排 | 多步骤客户端流程；必须定义唯一写入者 |
| 派生值 | 从已有状态计算 | 合计展示；避免保存两份长期不一致的副本 |

Query Cache 是服务端数据在客户端的副本，要定义查询键、身份/租户、过期、刷新和失效。筛选、分页或租户变化必须反映在键中，否则可能展示错误结果。服务器金额与权限不能由缓存展示值决定；提交时服务端再次校验。

URL 适合可分享、可后退的筛选，不适合令牌、敏感个人信息或未授权数据。表单草稿可以保留局部，确有跨页恢复需求再设计持久化、版本和身份清理。把全部状态都放全局 Store 会让团队依赖隐形扩散。

### 4.2 不共享后端内部 Entity

DTO（Data Transfer Object）是传输结构；前端模型表达当前交互需要的含义。后端可能将一个 Entity 拆表或增加内部字段，前端不应因此全站升级。各领域在边界适配必要字段，明确金额单位、时区、可空性和未知枚举处理；TypeScript 类型不等于运行时校验。

目录显示的商品价格只是报价视图，结账需请求服务器确认价格和库存。跨域不共享可变“大商品对象”，可传 productId/cartId 等身份和明确用例。代价是可能增加查询或映射代码，但换来独立演进和明确一致性边界。

### 4.3 并发、事务和失败体验

搜索 A 后搜索 B，若 A 晚返回，不能覆盖 B；可结合请求取消和请求身份判断。乐观更新适用于可恢复操作，但多个并发修改时不能用旧快照盲目回滚覆盖新成功状态。关键订单更适合确认后推进，并显示明确处理中状态。

结账调用超时表示结果未知，不等于失败；应按幂等键或业务状态查询确认。浏览器不提供跨 API 的数据库事务，库存、订单和支付协调必须由服务端负责。前端描述中间状态、恢复入口和人工支持信息，不能假装点击一次就获得 Exactly Once。

## 五、运行时边界、性能与体验

### 5.1 代码按路由加载，故障按业务任务隔离

初始入口只加载必需代码，目录和结账等路由可分块；重型编辑器按使用意图加载。切分减少首屏工作，也可能增加请求瀑布，因此需要结合数据预取、网络和设备测量，而不是把每个小组件都变成异步块。

```jsx
import { lazy, Suspense } from 'react';
const CheckoutPage = lazy(() => import('./CheckoutPage'));

export function CheckoutRoute() {
  return (
    <Suspense fallback={<p role="status">正在加载结账页面</p>}>
      <CheckoutPage />
    </Suspense>
  );
}
```

示例假设页面默认导出且构建器支持动态 import。Suspense 处理挂起的加载状态，加载 Promise 拒绝则由附近 Error Boundary 处理；示例尚未包含该边界。真实路由外层要配置错误边界、脱敏上报和回退导航。Error Boundary 也不会自动捕获所有事件处理器及任意异步回调异常，需要分别处理。

React lazy 缓存加载 Promise 及结果，简单重置错误边界不保证重新下载失败模块。发布后的旧页面可能请求已删除 chunk，应保留旧资源到合理期限，提供有限刷新和草稿保护，避免无限刷新。边界应让目录推荐失败不拖垮结账，但不要捕获错误后显示假成功。

### 5.2 预算与测量

Bundle Budget 是对初始及路由资源大小/执行成本的约束；Core Web Vitals 提供 LCP、INP、CLS 等用户体验信号。LCP 关注主要内容呈现，INP 关注交互响应，CLS 关注意外布局偏移。按设备、路由和版本看现场分布，并用实验室分析定位请求、长任务和布局问题。

共享库能减少重复，也可能扩大入口包和变更波及面；依赖“共享”不保证按需打包。将性能预算归到 Feature，公共包变化同时检查受影响路由。虚拟列表、memo 或 Worker 只有在瓶颈证据匹配时采用，不为架构图堆术语。

可访问性 Gate 应覆盖键盘、焦点、标签、对比度与错误恢复；自动扫描只检查部分规则。路由切换和弹窗需恢复合理焦点，国际化长文本和弱网 loading 要进入验收，否则组件库通过也无法保证完整旅程可用。

## 六、交付、质量与治理

### 6.1 主干开发与预览环境

Trunk-based Development 强调小批次、短生命周期分支和频繁集成，不等于未经检查直接推生产。未完成能力可用受治理开关隐藏，接口采用兼容演进，降低长分支冲突。Preview Environment 提供每次变更的可访问版本，便于产品、设计与跨团队验证，但需受控数据和凭证。

CI 根据依赖图运行受影响检查，公共平台变化应触发更广的消费者验证。缓存键须包含源码、依赖锁文件、编译配置等输入，错误缓存会让有缺陷制品被误判通过。固定工具链，测试将要晋级的同一制品，记录来源，避免测试后重新构建引入差异。

### 6.2 测试职责与审查

类型检查发现静态不匹配；Lint 发现约定违规；组件测试验证用户交互；契约测试核对真实提供者的结构和行为；少量 E2E 覆盖登录、结账与关键管理旅程。Mock 数据不能单独证明真实 API 兼容，要测试错误码、金额单位、null 和权限失败。

CODEOWNERS 表达路径所有者和审查候选；是否强制审批仍取决于仓库保护规则。风险型 Review 按影响选择审查者：局部文案不应召集所有团队，身份、支付、公共接口和依赖升级则需要相关责任人。技术意见冲突要记录依据与决策，不用“谁先合并谁说了算”。

建立架构决策记录（ADR）保存问题、候选、取舍、Owner 和复查条件。共享规范必须能自动执行且有例外流程；只写文档没有检查会腐化，所有例外永久存在也会失去边界。开发者体验（Developer Experience）用本地启动、反馈时间、故障定位及贡献门槛衡量，不只看工具是否新。

## 七、何时引入独立部署

### 7.1 先证明发布耦合，再选组合方式

当某领域发布频率、风险或团队节奏确实独立，且统一发布已成为可测量瓶颈时，可以按路由/领域引入微前端（Micro-frontend）。先排除慢 CI、审批串行或后端发布造成的等待；运行时拆分不会自动修复这些问题。

独立静态入口按路由组合通常较简单，但跨页面导航可能重载；Module Federation 可在运行时加载其他构建暴露的模块，但增加版本和共享依赖管理；iframe 可提供不同来源隔离，代价是导航、通信与可访问性整合。选择取决于实际自治与安全需求，不应仅因团队多就默认 Federation。

### 7.2 Shell、Remote 与版本契约

Shell 负责公共导航、身份接入、主题、遥测及集成规范；Remote 负责领域路由、数据、测试、发布和值班。契约包含入口、输入、事件、挂载/卸载、平台版本、错误与兼容窗口。不要共享一个所有团队可任意写入的全局 Store，否则部署独立而业务仍紧耦合。

webpack 5 Module Federation 的 Host 在运行时消费 Remote 容器，共享范围协调依赖。设置 singleton 或版本要求不是完整兼容保证，React、路由和上下文身份仍需集成测试。加载的同页远程脚本通常拥有页面权限，因此微前端不是天然安全沙箱。

使用不可变制品与版本清单，记录一次会话加载的 Shell/Remote 组合。灰度固定用户或会话，回滚切换到已知兼容组合并保留资源；不能只覆盖同一 remote URL 后指望 CDN 和已打开页面立即一致。降级时保留导航、明确功能暂不可用和支持入口，不能伪装订单完成。

卸载要清理监听器、订阅和计时器；加载过程中用户离开路由时应防止迟到结果再次挂载。故障演练要验证 Remote 404、超时、版本不兼容和共享服务失败。Error Boundary 限制部分 UI 错误扩散，但不能隔离全局脚本副作用。

## 八、统一可观测性，按责任定位问题

RUM（Real User Monitoring）采集真实设备体验；错误追踪关联异常与页面；Release Version 标记代码版本；Trace Correlation 将允许范围内的前后端请求关联；Business Funnel 记录从浏览商品到订单完成的转化路径。统一字段和事件含义才能跨团队比较。

建议事件包含应用/Feature、路由模板、发布版本、匿名关联标识、耗时与结果码，避免完整 URL 查询、令牌和个人正文。微前端需记录组合版本，否则“最新版本没有 Bug”无法解释旧会话。链路头由允许的来源和隐私政策控制，不应把内部上下文发给任意第三方。

Dashboard 按团队/Feature 分解，同时保留端到端任务视图。结账失败率上升可能是目录报价不兼容、平台身份过期或支付服务失败，不能只按组件 Owner 归罪。建立告警阈值、负责人和处置预案，观察错误率、体验和业务结果；埋点采样及失败上报也要监测，否则数据缺失会制造假改善。

## 九、渐进演进与可填写决策模板

演进顺序是先画出现有依赖和 Owner，再建立模块公共接口；从实际重复提取设计系统与 Platform API；自动化依赖规则并逐步清理例外；测量跨团队修改、发布等待和故障范围；最后只拆分确需独立交付的领域。迁移要有完成条件和适配层退出计划，不能同时长期维护两套入口。

可填写模板：业务目标为【】；领域及 Owner 为【】；关键任务和 NFR 为【】；渲染/数据/状态策略为【】；基线部署为【】；替代方案及放弃原因为【】；失败与回滚为【】；验证证据为【】；当【发布等待/兼容成本等条件】出现时重新评估。

虚构示例：目录先从遗留页面迁入统一路由，保留 API 适配器并测深链接；结账暂不拆分，优先补幂等和失败恢复。若目录长期因其他领域冻结而无法发布，再试点路由级独立制品，观察真实等待、运行故障及平台支持成本，再决定推广。这里没有预设微前端一定降低成本。

## 十、面试完整回答与深入追问

**问：请设计一个大型多团队 React 应用。**

答：我先澄清领域、团队责任、发布独立性、SEO、设备与 NFR。在没有明确独立发布要求时，用 Monorepo 管理模块化单应用，按目录、结账和账户划分 Feature，每个有 Owner、公共入口和自动依赖规则。平台提供 Router、身份、请求、遥测、开关与 CI，设计系统负责共享体验。局部状态留局部，服务端数据进查询缓存，筛选进入 URL，跨域流程由明确接口编排。路由按需加载并设加载和错误边界。主干小批次集成、预览验证、契约与关键 E2E、性能和可访问性预算共同把关。统一观测端到端任务，按 Feature 定位责任；只有发布耦合证据充分时才拆独立路由。

追问“为何不默认微前端？”答：多团队首先需要模块边界和治理，运行时拆分会增加兼容组合、共享依赖、故障及安全成本。没有独立发布价值时，这些成本可能超过收益。

**问：跨 Feature 数据怎样共享？**

答：先判断是服务端事实、局部交互还是跨域客户端流程。传递稳定身份和用例结果，通过公共接口或上层编排协作；不共享可变后端 Entity。查询缓存按身份和参数分区，写操作明确失效及冲突策略。

追问“统一 Store 是否简单？”答：初期调用方便，但任何团队都依赖同一内部状态会形成隐式契约和发布耦合。只给确需共享的客户端状态建立明确 Slice、写入者及变更规则。

**问：独立部署后如何防一个团队拖垮全站？**

答：按业务路由设置故障边界和 fallback，使用不可变制品及兼容清单，记录组合版本，验证旧新版本、超时与加载失败；保留回滚版本，卸载清理副作用。共享平台仍可能是公共故障点，需要单独观测和预案。

追问“Error Boundary 足够吗？”答：不够，它不能隔离任意全局脚本、事件或网络副作用；还需请求失败处理、生命周期清理，真正不可信代码要考虑独立来源隔离。

**问：如何避免规范让团队变慢？**

答：自动检查可机器执行的边界，常规变更按风险审查，共享接口变更提供兼容窗口和迁移工具；平台有支持责任与反馈指标。领域特例可以保留本地实现，但例外要有 Owner 和复查日期。

追问“如何证明架构有效？”答：比较发布等待、跨域修改比例、反馈耗时、缺陷逃逸、关键任务成功率和现场性能，同时记录需求与人员变化，不能把所有改善都归功于架构。

## 十一、扫雷自测与速记

1. **Monorepo 等于统一部署吗？** 不等于，仓库组织与制品/部署边界独立；可同仓多部署，也可多仓共同发布。
2. **公共 index 文件能阻止越界吗？** 不能，需要规则与依赖分析覆盖深导入、别名和相对路径。
3. **用户规模大就需要微前端吗？** 不成立，流量首先影响缓存与服务容量，微前端主要解决自治交付等组织需求。
4. **查询缓存是业务真相吗？** 不是，它是副本，提交价格、库存和权限必须由服务端重新确认。
5. **URL 能放全部状态吗？** 不能，敏感数据和令牌可能泄漏到历史、日志等；只放适合分享及导航的状态。
6. **Suspense 会处理所有错误吗？** 不会，加载与拒绝错误有不同处理路径，事件和任意异步错误还需显式处理。
7. **订单超时能立即重新创建吗？** 不应，远端可能已成功；应通过幂等重试或状态查询确认。
8. **独立 Remote 是安全沙箱吗？** 通常不是，同页脚本可访问页面能力，必须审查来源和权限。
9. **CODEOWNERS 存在就一定阻止未审批合并吗？** 不能推出，需结合分支保护和实际审批配置核验。
10. **所有规范都要统一实现吗？** 应统一必要契约与体验底线，领域细节保留自治；过度集中会形成平台瓶颈。

速记：先问约束，再定边界；仓库不等于部署；领域有 Owner 和公共 API；状态按真相分类；平台提供能力不包办业务；先自动治理模块，再用证据决定独立发布；故障、性能、安全和可观测性必须落到真实任务。
