# 04. 如何逐步迁移遗留前端而不中断业务

## 原则

避免 Big-bang Rewrite。使用 Strangler Fig 按 Route、Feature 或 Component 逐步替换，并让旧系统持续交付业务价值。

## 第一步：建立 Baseline

- 关键 User Journey 与业务指标。
- Error、Performance、Accessibility 和 Test Coverage。
- Dependency、Browser Support 和 Build 时间。
- Domain Boundary 与 Ownership。

没有 Baseline 就无法证明迁移改善了什么。

## 第二步：建立边界

选择集成方式：

- 新旧 Route 共存。
- Reverse Proxy 路由。
- Web Component/Custom Element。
- iframe（隔离强但体验成本高）。
- 临时 Adapter/Bridge。

先统一 Auth、Navigation、Design Token、Telemetry 和 API Contract。

## 第三步：选择迁移顺序

优先：高业务价值、变更频繁、边界清晰且风险可控的 Feature。不要一开始迁移最复杂 Checkout，也不要只挑无人使用页面制造虚假进度。

## 数据与 Contract

避免新 React 应用直接依赖遗留 Global Variable。建立 Versioned API/BFF 和 Anti-corruption Layer，逐步把业务规则从 UI 中抽出。

## 发布安全

- Feature Flag 和按用户/租户 Canary。
- 新旧实现并行对比。
- Contract/E2E Test 覆盖关键 Journey。
- 快速回退到旧 Route。
- RUM 比较 Version Cohort。

## 组织与技术债

定义旧代码停止新增的规则、Migration Owner 和删除里程碑。Bridge 必须有 Expiry，否则双栈成本会永久存在。

## 成功指标

除了迁移百分比，还看 Lead Time、Defect、Core Web Vitals、Bundle、Incident、Developer Satisfaction 和旧代码删除量。

## 面试亮点

说明如何保证业务连续性、如何选择 Slice、如何回滚、如何管理双运行成本，以及如何证明迁移价值。
