# 04 如何逐步迁移遗留前端而不中断业务

迁移的目标是降低业务交付与运行风险，而不是把旧框架名字全部换成 React。“不中断业务”应理解为持续提供关键能力、限制故障范围并能恢复，不能承诺任何变更绝对零故障。本题要说明迁移边界、数据一致性、发布回退和组织退出条件。

本文以**虚构的电商遗留站点迁移**举例，不代表用户经历或实测收益。React 挂载示例适用 18+ createRoot API；浏览器能力按目标版本验证。资料于 2026-11-27 核验。代码为教学片段，未实际运行新旧系统、浏览器或发布演练。

## 一、基本策略：逐步替换与持续交付

Big-bang Rewrite 是完成整个新系统后一次切换；它容易让业务需求和旧系统继续演变，而新系统始终追赶，直到切换时才暴露大量隐含规则。Strangler Fig（绞杀者模式）是在旧系统外围建立可控入口，按 Route、Feature 或 Component 将能力逐步替换，最终移除旧实现。

逐步迁移同样有成本：双框架、适配、测试矩阵和团队协调可能长期存在。若系统很小、已停止变更、替换范围清楚且停机窗口可接受，一次切换也可能更便宜。选择应比较交付期限、故障损失、兼容要求与双运行成本，不把渐进当成无条件正确。

切片（Slice）应交付一段端到端用户能力，例如商品收藏列表包含入口、查询、空态、权限与错误恢复，而不只是把按钮换成 React。旧系统仍需修复漏洞、支持必要业务变更，迁移期间不能以“反正要删”为理由停止维护。

## 二、先建立 Baseline 和行为清单

### 2.1 基线覆盖业务与工程

Baseline 是迁移前可比较的测量与行为证据。没有它，迁移后“更快、更稳定”只是印象。先列关键 User Journey：登录、商品筛选、加入购物车、结账、订单查询，并定义成功、失败、重试及人工恢复的含义。

| 基线维度 | 应记录的内容 | 常见误判 |
| --- | --- | --- |
| 业务 | 任务完成率、转化分母、放弃率、客服问题 | 流量结构变了却认为迁移提升转化 |
| 可靠性 | 错误分类、失败率、事故及恢复时间 | 新版不再上报异常被当成错误减少 |
| 性能 | 设备/网络/路由的现场指标与资源执行 | 只比较开发者电脑的加载速度 |
| 可访问性 | 键盘、焦点、标签、关键读屏任务 | 自动扫描全绿就认为整站可用 |
| 测试 | 关键规则及旅程是否有有效断言 | 只看覆盖率百分比 |
| 工具与依赖 | 浏览器支持、依赖版本、构建与反馈耗时 | 新构建更快却增加用户下载成本 |
| 边界与责任 | 领域、数据源、Owner、上线值班 | 只画技术目录，不知道故障谁处理 |

Core Web Vitals 是用户体验指标族，LCP 看主要内容呈现、INP 看交互响应、CLS 看意外布局移动；它们应与任务成功率共同评估。迁移不只是性能工程，不能以首屏快掩盖支付错误。

### 2.2 发现旧系统隐含规则

通过实际用户路径、代码、日志和领域专家找出未写入需求的规则：折扣舍入、权限差异、历史 URL、浏览器后退、导出、键盘快捷键和错误恢复。对当前行为建立特征测试（Characterization Test），用于暴露变化；但旧行为不必然正确，发现安全缺陷或明显 Bug 要由产品与技术确认目标语义。

保存请求/响应样例时脱敏，不能把真实客户凭据放测试仓库。对未覆盖行为标记风险和验证责任，不用“新页面截图一样”替代业务等价性。

## 三、选择共存边界和集成方式

### 3.1 先选最小稳定接缝

| 方式 | 适用情况 | 代价和边界 |
| --- | --- | --- |
| 新旧 Route 共存 | 路由职责清楚，能够整页替换 | 要处理深链接、后退、刷新与跨页状态 |
| Reverse Proxy 反向代理分流 | 可按路径将请求送不同站点 | 需正确转发路径、资源、身份与缓存头 |
| React 岛或 Component 替换 | 旧页面局部能力可独立挂载 | 必须严格约束 DOM 所有权与清理 |
| Web Component / Custom Element | 需要浏览器元素接口跨框架复用 | 属性、事件、样式和生命周期仍需契约 |
| iframe | 需要更强文档或来源隔离 | 导航、尺寸、焦点、登录和通信成本较高 |
| 临时 Adapter/Bridge | 两套接口无法同时改 | 容易变永久耦合，必须有 Owner 和退出条件 |

路由级通常更容易隔离，因为新旧系统不会同时管理同一个 DOM；但整页跳转可能失去未提交草稿。组件级可保持当前页面体验，但旧 jQuery 插件和 React 不能共同修改同一子树。iframe 的安全隔离依赖来源和 sandbox 配置，同源 iframe 不能自动当作不可信代码沙箱。

Custom Element 是浏览器自定义元素机制，可定义连接、断开及属性变化回调；Shadow DOM 可降低部分样式冲突，但不是完整安全边界。对象宜通过明确属性/方法传递，事件定义名称、结构与版本；跨 Shadow 边界传播还需按事件设置及目标浏览器验证。

### 3.2 挂载和卸载必须成对

```jsx
import { createRoot } from 'react-dom/client';
import { Favorites } from './Favorites';

export function mountFavorites(container, props) {
  const root = createRoot(container);
  root.render(<Favorites {...props} />);
  let mounted = true;
  return () => {
    if (!mounted) return;
    mounted = false;
    root.unmount();
  };
}
```

示例假设 container 是专用客户端容器，Favorites 和 JSX 构建已配置。旧路由卸载页面前调用返回的清理函数；React 组件内部 Effect 也需取消订阅、计时器及合适请求。若旧系统直接删除容器而不卸载，可能留下监听器、内存和迟到回调。

同一容器不能反复创建多个有效 Root；卸载后的 Root 不能继续 render，需要新 Root。已有 React SSR 内容应使用对应水合 API，而不是 createRoot 重建。隔离错误边界、重复进入、快速离开及异步加载迟到都需要测试，不能只测首次挂载。

### 3.3 统一跨边界底线

先统一 Auth、Navigation、Design Token、Telemetry 和 API Contract，不必先统一所有实现。Auth 明确会话范围、续期、退出与 CSRF；导航明确由谁改 history、处理路由和恢复焦点；Token 统一关键视觉语义；遥测统一版本、旅程和失败分类；API 明确请求响应及错误语义。

不要通过全局变量暴露令牌和全部 Store。跨文档 postMessage 应验证完整 origin、来源窗口和消息结构，发送时指定精确 targetOrigin；事件总线要能取消订阅，消息有版本及必要关联 ID。Bridge 只暴露任务能力，例如 navigate 或 cartChanged，不允许任意调用内部函数。

## 四、迁移顺序：价值、学习收益与风险一起评估

优先选择业务价值高、经常变更、边界清楚、可测量且可回退的 Feature。第一次既要证明集成与发布能力，也要控制损失：收藏列表或订单查询可能比支付更合适，但具体取决于权限与历史复杂度。

不要一开始迁移最复杂 Checkout，因为其支付、库存和会话规则隐含且回退困难；也不要只改无人使用的帮助页，然后以页面数量宣称接近完成。切片大小用能否独立上线、验收和删除旧代码判断，不靠文件数。

为候选记录价值、依赖、状态迁移、风险、观测和回退条件。先试点一个完整切片，复盘后再扩大。高风险模块最终仍要迁移，但应先建立契约、测试和数据兼容，不是永久回避。

虚构例子：先迁商品收藏读写，验证会话、设计 Token 和遥测；再迁账户编辑并解决草稿冲突；最后迁结账前先补服务端幂等与报价契约。每一步仍交付正常产品需求，迁移预算作为持续工作而非无限期平行项目。

## 五、数据、API 与业务规则迁移

### 5.1 防腐层避免新系统继承旧耦合

Anti-corruption Layer（防腐层）将遗留字段、状态码和调用方式转换为新领域可理解的模型。BFF 是服务浏览器用例的后端，可聚合旧接口并统一身份与错误；版本化 API 让新旧客户端在兼容窗口内同时工作。

例如旧接口用字符串金额和状态数字，新页面需要整数最小货币单位和明确状态；适配器应校验单位、null、未知枚举及溢出，不能随意 Number 转换后假装可靠。不要让 React 直接读取 window.legacyUser、全局购物车对象或旧页面 DOM 作为业务真相。

适配不是复制所有旧逻辑。将定价、权限和交易规则逐步移到可信服务端或明确领域服务；UI 保留输入及展示规则。迁移期间约定唯一写入者，避免新旧两个 Store 各自拥有已保存的同一事实，再靠事件同步碰运气。

### 5.2 兼容变更、草稿与并发

使用扩展—迁移—收缩（Expand–Migrate–Contract）：先增加兼容接口/字段，再迁消费者，确认旧版本退出后才删除旧字段。删除或改变语义不能只依靠新页面已发布，用户可能长期开着旧标签、Service Worker 或旧缓存。

持久化草稿需要 schemaVersion、身份范围、迁移和过期；新版写入后旧版是否读得懂，必须在回退计划里说明。可以在过渡期保留兼容写入，或禁止正在进行的编辑会话中途切换实现。跨页交接只传必要身份和可恢复草稿引用，不把敏感数据塞进 URL。

自动保存、购物车和支付写入需要版本检查及幂等。双写两套后端不等于原子事务：一边成功一边失败会分叉，必须有明确权威、操作 ID、补偿/对账和失败队列。能避免双写就优先避免，不为“对比”重复真实订单或发送两次邮件。

## 六、安全发布：灰度、比较和回退是不同能力

### 6.1 Feature Flag 与稳定分组

Feature Flag 决定启用哪个实现，Canary 将小部分用户/租户分配到新版本。分组应稳定，避免一个用户每次请求在新旧实现之间切换，导致草稿与流程不兼容。租户内协作需要一致时按租户分组，代价是样本与负载不均，需纳入观察。

开关有 Owner、默认值、故障策略和删除日期；认证、价格和资源授权仍由后端裁决。发布前验证关闭开关真实可回旧路由，并测试开关服务不可用。前端开关不是安全权限，也不能撤回已经执行的服务端副作用。

### 6.2 并行比较不等于重复执行

新旧实现可对只读请求或脱敏样例并行比较，检查字段、排序、金额、权限和错误映射。要区分预期差异与缺陷；时间、随机顺序、不同快照会产生噪声，需规范化并记录输入版本。

真实写操作不应为了影子验证执行两次。对写路径可比较构造出的命令、用隔离测试数据运行，或仅让一套执行并核验结果。影子读取也可能增加后端负载和敏感数据处理，应限流、采样并控制权限。

### 6.3 回退条件和操作步骤

回退应提前定义触发指标、负责人、执行路径和确认方式。例如关键旅程失败率超过预先批准阈值，停止扩大流量，切回旧路由，确认会话仍有效、已有交易可查询，再保留证据排查。阈值由业务基线和样本决定，不编造通用数字。

代码路由回退不等于数据回退。若新版改变了草稿格式、接口或交易状态，旧版可能无法接管。先判断兼容性；不可逆数据变更可能需要前向修复而非强行降级。旧资源和后端兼容接口在窗口内保留，回退演练要包含深链接、旧标签和 CDN 缓存。

运行时异常不能一律捕获后自动执行旧写流程，因为新流程可能已成功，自动重放会重复副作用。展示“结果待确认”，按操作 ID 查询，再决定恢复路径。

## 七、验证与观测：比较同类用户的任务结果

Contract Test 验证新旧消费者与真实提供者的约定；E2E 验证关键完整旅程，特别是新页到旧页、退出重登、后退、刷新和失败恢复。组件测试覆盖交互，视觉回归检查布局，人工键盘与读屏检查不能省略。测试应覆盖目标旧浏览器，不能把迁移理解为未经确认地取消支持。

RUM（Real User Monitoring）比较真实用户体验，按 Version Cohort（版本分组）、设备、网络、地区、租户和路由分析。分配方式和曝光记录必须可信；若新版只给高性能内部员工，不能用它证明全量用户更快。首跑错误、监控采样和事件缺失也要检查。

跨新旧系统统一旅程关联 ID 与发布版本，避免一次任务被重复计数。日志与埋点脱敏，不记录令牌和表单完整内容。迁移前后事件名称可以兼容演进，但不能悄悄改变“成功”的定义制造改善。

| 现象 | 首查边界 | 处理 |
| --- | --- | --- |
| 新版偶尔退出登录 | Cookie 域/路径、会话续期和代理 | 对齐会话协议，不通过暴露令牌绕过 |
| 往返页面越来越慢 | Root、监听器、订阅和定时器 | 成对卸载，测重复进入后的资源 |
| 新版有数据旧版没有 | 双写、缓存、版本和权限 | 明确权威与对账，避免继续复制状态 |
| 灰度结果很好全量却失败 | 用户分组、浏览器和流量形态 | 分层验证，重测容量和冷缓存 |
| 回退后白屏 | 旧资源删除、路径和接口收缩 | 保留兼容制品与接口，演练恢复 |

## 八、组织责任、双栈成本和删除里程碑

Migration Owner 负责切片计划、依赖协调和退出验收，领域团队负责业务语义与运行支持。明确哪些旧代码禁止新增、哪些安全修复与紧急业务需求例外；不能一刀切冻结导致业务绕开规范，也不能所有新需求继续加旧栈让迁移永不结束。

Bridge 必须登记使用者、版本、到期日、删除条件和负责人。到期未完成应显式重新评估，不能静默续期。双栈期间要预算依赖漏洞修补、浏览器测试、CI、重复公共资源、值班和培训，而不是只估重写开发时间。

删除里程碑应在流量和消费者证据之后：新功能达到验收、旧路由无正常流量、后台任务和外链确认、兼容窗口结束、回退替代预案批准，才删除旧入口、Bridge、依赖、构建和部署。零访问一小时不证明没有月末报表等低频用户，观察窗口要覆盖业务周期。

旧系统缩减后更新文档、Owner、监控和支持手册；不要留下无人负责的旧域名、API 密钥和部署权限。迁移完成意味着减少双运行责任，不仅是页面显示 React。

## 九、成功指标与决策模板

迁移百分比只在分母明确时有意义。按页面计数会把无人使用页面与关键结账等权；可按关键旅程、活跃流量或已退出能力分层报告，同时列剩余风险。

Lead Time 是变更从开始到交付的耗时，Defect/Incident 反映缺陷与运行事故；Core Web Vitals 和 Bundle 反映用户性能；Developer Satisfaction 需结合反馈周期、启动和定位成本；旧代码删除量显示退出进展，但删大量无用文件不等于用户价值。指标应比较同类变更与用户，注明同时发生的基础设施和团队变化。

可填写模板：迁移目标【】；试点切片与 Owner【】；当前行为及目标差异【】；集成边界【】；身份/导航/数据契约【】；灰度分组【】；验收与停止阈值【】；数据兼容及回退【】；Bridge 到期及删除证据【】。每完成切片就更新证据，再决定扩大或调整方式。

## 十、面试完整回答与深入追问

**问：怎样逐步迁移遗留前端而不中断业务？**

答：先建立关键旅程、错误性能可访问性、工具链和所有权基线，识别隐含业务规则。采用按路由或领域的绞杀者迁移，选择有业务价值、边界清楚且可回退的切片，旧系统继续必要交付。统一身份、导航、Token、遥测与 API 契约，通过适配或 BFF 隔离旧全局状态。新旧兼容接口先扩展再收缩，灰度固定用户/租户并比较同类任务结果。发布前演练路由回退及数据兼容；达标后逐步扩大，最后按消费者证据删除 Bridge 和旧部署。

追问“为什么不一次重写？”答：长期重写会与持续业务变化赛跑，集中切换也集中暴露风险；但小且冻结的系统可比较一次切换成本，不机械排斥。

**问：如何选择第一个模块？**

答：选择真实有价值、变更频繁且能独立验收的能力，既能验证身份、导航和观测集成，也控制失败损失。先避开隐含交易规则最复杂的结账，不只挑无人用页面充进度。

追问“复杂模块永远不迁吗？”答：不是，应先补契约、测试、幂等和数据恢复，再按更小子能力迁移，逐步降低它的风险。

**问：React 和旧 DOM 插件怎样共存？**

答：为 React 划定专用容器，旧系统不修改其内部 DOM，挂载返回明确卸载能力，离开时清理 Root、订阅和计时器；跨边界用版本化输入与事件。耦合太深时先路由级隔离比强行局部嵌入更稳。

追问“Shadow DOM 是否保证安全？”答：它主要隔离部分结构和样式，不是可信权限沙箱；需要安全隔离时评估不同来源 iframe 及严格通信。

**问：怎样快速回滚？**

答：准备稳定分组和开关、保留旧路由资源及兼容后端，事先定义触发条件并演练。发现异常先停止放量，判断新数据与旧版兼容，切回后验证关键任务；不可逆变更可能只能前向修复。

追问“新下单超时就交旧流程再下单？”答：不能，远端可能成功；应先按业务操作 ID 查询并去重，避免把回退变成重复交易。

**问：如何证明迁移值得？**

答：同时看交付时间、缺陷事故、用户体验、业务任务和旧系统退出成本，按版本用户分组及设备等控制差异。迁移比例只能说明覆盖，不自动说明改善；若双栈成本持续增加且收益不足，应调整范围。

追问“Bridge 到期没迁完怎么办？”答：让 Owner 公开复查剩余依赖、风险和新期限，选择继续、缩小范围或停止；不能把临时层无限保留而不计成本。

## 十一、扫雷自测与速记

1. **换完框架就算迁移成功吗？** 不算，还需业务行为、运行指标和旧栈责任退出的证据。
2. **旧行为必须全部照搬吗？** 不必，特征测试揭示差异，缺陷与安全问题应明确批准目标语义，不能悄悄改变。
3. **路由共存只需改导航链接吗？** 不够，深链接刷新、后退、身份、资源路径和服务器路由都要验证。
4. **React 容器直接删除就行吗？** 应先卸载并清理，避免监听器和在途回调泄漏。
5. **灰度每次随机分配可以吗？** 对有状态旅程通常不合适，会让同一流程跨实现；应稳定分组并管理状态兼容。
6. **并行对比能执行两次付款吗？** 不能，真实副作用只能按受控写入路径执行，对比应隔离或只比较命令。
7. **开关关闭能撤销已提交交易吗？** 不能，UI 选择与服务端事实不同，需幂等、查询和对账。
8. **回退一定比前向修复安全吗？** 不一定，新数据或接口可能不兼容旧版，必须提前分析并演练。
9. **零流量一天就能删旧系统吗？** 不一定，低频业务可能尚未发生，应覆盖实际周期及消费者清单。
10. **只看覆盖率与迁移百分比够吗？** 不够，它们不证明关键任务、断言强度或成本改善，需要多维证据。

速记：先基线，再边界和切片；旧系统继续交付；统一跨界契约，隔离遗留模型；灰度稳定，影子不重复副作用；回退先看数据兼容；Bridge 有到期日；成功要用户价值和旧栈退出。
