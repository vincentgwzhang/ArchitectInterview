# 05 如何定义前端平台的质量门禁和可观测性

质量门禁（Quality Gate）是在变更进入下一阶段前验证必要条件；可观测性（Observability）则让团队根据运行证据判断用户任务是否正常、异常在哪里以及如何恢复。二者应构成反馈闭环：生产发现风险，转成可重复检查，再验证改善。

目标是保护用户、安全和交付，不把所有团队送进中央审批队列。平台提供自动护栏（Guardrail）、风险分级和有期限的例外流程，领域团队对自己的生产结果负责。本文以虚构电商平台演示，不代表用户项目或行业强制指标；所有数值均为教学目标，须用业务需求、基线与样本校准。资料于 2026-11-27 核验，未实际部署 CI、SDK 或灰度系统。

## 一、从用户风险定义门禁，不从工具清单开始

先列关键任务及损失：商品页慢影响浏览，结账崩溃阻断购买，越权和敏感数据泄漏即使只影响少量用户也可能严重。对每类风险定义检查、证据、执行阶段、阻断条件、负责人和失败处理，避免“有扫描器”却不知道结果怎样影响发布。

风险分级应同时看变更范围、关键性、可逆性、数据副作用和兼容性。局部文案与支付重试、会话缓存、公共组件升级不能走同样流程。风险标签不能只由作者随意填，结合路径、依赖影响和评审确认；规则应透明可复查。

| 风险示例 | 自动证据 | 需要的补充判断 |
| --- | --- | --- |
| 类型或边界破坏 | 类型检查、导入依赖规则 | API 语义是否仍兼容 |
| 交互回归 | 单元/组件/关键旅程测试 | 断言是否覆盖真正业务风险 |
| 性能退化 | Bundle Diff、实验室预算、RUM | 用户设备、流量分布与业务取舍 |
| 安全与隐私 | 依赖/密钥扫描、安全头检查 | 授权、数据流和漏洞可达性 |
| 体验不一致 | 视觉差异、可访问性扫描 | 设计意图、键盘与读屏任务 |

门禁需要同时控制误报和漏报。误报太多会让团队习惯忽略；为了全绿无限放宽阈值则失去保护。先基线、观察模式和风险试点，再把稳定且可行动的检查升级为阻断，严重已知安全问题不能因基线不好而永久豁免。

## 二、PR 阶段：快速发现可定位的问题

### 2.1 必须明确每项检查证明什么

Type Check 验证静态类型关系，不证明运行时 JSON 合法；ESLint 检查代码约定，Import Boundary 防跨领域深导入；Accessibility Rule 能发现部分标签与语义问题，不证明完整流程可访问。规则应版本化，在 CI 统一执行，不能依赖每位开发者编辑器配置。

Unit Test 覆盖纯规则边界，Component Test 从用户行为验证输入、状态和失败恢复。不要以快照数量或行覆盖率替代断言强度。关键金额、权限和并发问题需要有明确反例；低风险样式修改不必重复运行所有后端依赖场景。

Dependency Scan 识别已知组件漏洞，需结合实际版本、部署和可达路径；Secret Scan 检查误提交凭据。发现真实密钥要撤销或轮换，删掉代码并不能使已泄漏密钥失效。安装脚本、锁文件和来源变更也进入审查，扫描零告警不等于供应链安全。

Bundle Diff 比较初始和受影响路由的资源变化，区分原始、压缩与执行成本；共享包小改可能影响所有入口。受影响 Package Build 根据依赖图验证消费者，不只构建改动目录。缓存键包含源码、锁文件、工具版本和配置，错误缓存可能误用旧通过结果。

### 2.2 反馈速度与正确性一起管理

把快速类型、Lint、组件测试并行运行，耗时检查按依赖和风险触发。小改动无需被全部慢 E2E 阻塞，但登录、结账、公共平台及接口变化应运行相关关键旅程，不能为了快永远移到合并后。

记录排队与执行时间，优先修复瓶颈；分片与缓存能加速，但不能省掉最终组合验证。合并队列可验证多个 PR 合并后的实际状态。必须检查的任务失败或执行失败应明确阻断；“没有结果”不应自动视为通过。

Flaky Test 是相同预期条件下时过时不过的测试。有限重试用于诊断，报告保留首跑失败；隔离要有 Owner、期限和替代风险覆盖，不能无限重试直到绿。修复等待、共享数据、选择器或产品竞态，别把所有超时简单扩大。

## 三、Preview 与预发布：验证真实组合和部署

Preview 是可访问的候选部署，Pre-production 是接近生产的验证环境。环境差异必须可见，包括 API、认证、CDN、CSP、配置和第三方沙箱；只运行开发服务器不能证明生产制品正确。

Contract Test 检查消费者与真实提供者的路径、Schema、错误码和行为，避免 Mock 自证。关键 E2E 验证登录到任务结果，用独立测试账户和数据，订单成功应有持久化证据，不只看绿色提示。并行用例不能共享可变购物车。

Visual Regression 需要固定字体、视口、数据和动画，评审者确认差异是否预期。可访问性自动扫描配合键盘、焦点和辅助技术检查，尤其弹窗、路由切换、表单错误与加载。组件可访问不等于完整页面通过。

Lighthouse 和实验室性能预算适合比较受控条件下的回归，不能把单次分数当所有真实用户体验。对同类环境多次测量并看波动，预算可包含初始 JS、关键图片、长任务和主要内容加载。CSP/安全头要检查实际部署响应与关键导航，不只是配置文件存在；Report-Only 不代表已经强制拦截。

预览默认使用沙箱及最小权限，不把生产密钥或真实个人资料暴露给不受信任 PR。验证制品应与晋级生产的制品一致，环境差异通过受控配置表达，避免测试后重新构建产生不同内容。

## 四、渐进交付：把生产信号接入放量决策

Artifact Immutable 指制品发布后内容不变，以哈希或版本识别；灰度只切换已验证的版本和配置。Canary 给一部分稳定用户/租户新版本，Feature Flag 控制能力启用，两者不等价：关功能不一定撤回坏制品，回滚制品也不会撤销已发生交易。

先明确对照组、新版曝光、关键路由和组合版本。用户分组需稳定，避免一次结账在新旧实现切换；版本、设备、地区及流量来源要可比较。内部员工样本不能直接代表移动弱网用户。

自动判定至少有三种结果：通过并继续、异常停止/回退、证据不足保持当前比例。没有最小样本或观察窗口就放量，会漏低频故障；无穷等待统计显著也会阻塞正常交付，应由风险策略定义最长观察和人工决策入口。先过滤已知遥测中断，但不能把缺数据当质量改善。

自动比较 Error Rate、API Failure、Core Web Vitals 与关键漏斗。错误率要统一分母；Vitals 按设备等分层；漏斗变化需考虑样本、促销和季节，不能看到短期转化抖动就反复回滚。可定义绝对底线加相对退化阈值，但数值必须来自业务而非通用模板。

确认严重用户影响后先停止放量，按预案关闭功能或切回已知兼容版本，验证关键旅程和监控恢复。后端 schema、持久草稿及交易若不兼容旧版，可能需要前向修复；禁止在超时后自动重放支付等不可逆操作。定期演练回滚、旧 chunk、CDN 和配置兼容，不能只相信控制台有按钮。

## 五、统一生产采集，保留领域语义

### 5.1 SDK 应采什么、怎样关联

统一 SDK 提供 Schema、脱敏、采样、批次、限流和发布上下文；领域团队定义任务、成功与失败事件。SDK 不是把所有页面内容全部录下来，而是提供可比较且有权限控制的最小证据。

| 信号 | 关键解释 | 定位价值和限制 |
| --- | --- | --- |
| RUM / Core Web Vitals | LCP、INP、CLS 与设备/版本 | 分别观察主要内容、交互、布局；没有交互的访问不应伪造 INP 为零 |
| JavaScript Error | 错误类型、栈、路由模板、版本 | 区分致命/可恢复及资源错误，非所有异常都代表任务失败 |
| Source Map | 制品对应的源码映射 | 必须按准确版本匹配，受控上传与访问，不上传秘密 |
| API Latency/Error | 方法、路由模板、耗时和结果类别 | 区分网络异常、超时、HTTP 错误与业务拒绝 |
| Release Version | 应用和必要的远程组合版本 | 将问题关联候选发布，不能只写 latest |
| Trace Correlation | 前后端关联上下文 | 需要客户端、网关和服务端正确传播与采样 |
| Domain Funnel Event | 进入、提交、确认等业务事件 | 定义操作/会话身份，去重并处理迟到 |

错误捕获结合全局错误、Promise rejection、框架边界及显式请求错误。Error Boundary 不会自动捕获所有事件与任意异步错误；捕获后也不能全部当“致命”。Fingerprint 将相似错误聚类，eventId 则用于同一事件重传去重，两者不能互换。

W3C Trace Context 的 traceparent/tracestate 为跨服务传播定义格式，不会自动创建完整链路。跨源还需相应 CORS 配置，且只向允许服务传播；浏览器上下文不可信，后端不能据此授权。端到端采样保持关联，不能每跳独立丢弃后仍期待完整 trace。

### 5.2 分解维度、隐私与成本

按 App、Route、Team、Version、Browser、Region 分解能发现局部退化；Route 应用模板而非带用户 ID 的完整 URL，控制高基数标签。Team 从维护的所有权映射得到，不让客户端任意填成别的团队逃避责任。

PII 是个人可识别信息。默认允许名单采集，避免 token、邮箱、地址、完整请求正文和敏感查询进入上报。假名 ID 仍可能与其他数据关联，不能等同完全匿名。定义同意机制、用途、保留、删除与访问权限，Session Replay 如采用需额外遮罩和验证，不能默认录所有输入。

Sampling 要明确单位：按会话采样有助于保留完整旅程，按事件采样适合高量独立计数，但会影响漏斗重建。错误提升采样有利于诊断，却不能直接拿“错误全量/成功采样”计算原始失败率。记录概率并用合适估计，或用独立一致计数源生成 SLI；不要平均各地区 p75 得到全局 p75，应使用可合并分布或原始样本。

### 5.3 SDK 本身也会失败

采用有界队列、批量和退避，限制体积、次数及 CPU/网络开销，防止遥测故障拖垮业务。sendBeacon 返回成功表示浏览器接受排队，不保证服务端已持久化；断网、进程终止或拦截插件都会造成数据缺失。

事件可携带 eventId、schemaVersion、发生时间、接收时间和发布标识，服务端去重并校验结构。设备时钟不可靠，跨设备不能直接比较客户端绝对时间推导严格先后。监控 SDK 初始化覆盖、拒收、队列丢弃、版本覆盖和服务端接收健康，配合独立合成探测发现“整页白屏连 SDK 都没运行”。

## 六、把 SLO 写成可计算契约

SLI（Service Level Indicator）是测量指标，SLO（Service Level Objective）是某个窗口内的目标，错误预算（Error Budget）是目标允许的坏事件比例/数量。不能只写“99.9% 稳定”而没有分母、好事件、时间窗口和数据来源。

下列数字是虚构教学目标，真实项目需协商：

| 候选目标 | 必须补全的定义 | 盲区 |
| --- | --- | --- |
| 99.9% Checkout Session 无致命 JS Error | 28 天窗口、会话起止、致命标准、唯一会话计数及观察截止 | 没有 JS 错误也可能无法下单，页面未启动可能没上报 |
| p75 LCP 达到目标 | 目标设备/路由、有效样本、窗口和明确毫秒值 | 整站汇总可能隐藏关键路由或弱设备 |
| 99.5% Order Submit 得明确结果 | 唯一提交意图、成功/合法拒绝的分类、结果期限 | 永久 Pending 或“任意 200”都不算明确 |
| 新版转化不显著下降 | 对照曝光、统计方法、样本、容忍区间和业务窗口 | 转化是业务信号，不宜单独当即时可靠性 SLI |

“明确结果”可以是订单已确认或可理解的业务拒绝，但系统错误不能通过改名为“业务拒绝”美化；Pending 要单独跟踪年龄，超过期限计坏事件。最终订单事实应由服务端核对，前端埋点只说明用户感知，二者结合防漏报。

虚构算例：某窗口 100,000 个有效结账会话，99.9% 目标允许 100 个坏会话；已出现 40 个，则消耗预算 40%，剩余 60 个。不能将一次请求失败直接当整个会话失败，也不能重复计数同一会话的十条异常。

预算燃烧率（Burn Rate）等于当前坏事件率除以允许坏事件率。例如允许 0.1%，当前 1%，燃烧率是 10，表示以十倍目标速度消耗预算。多窗口观察区分快速事故与持续慢退化；低流量需结合样本和实际影响，不把一例正常拒绝变成全站呼叫。

错误预算政策应预先协商：消耗异常时暂停高风险放量、优先恢复和可靠性修复，必要安全修复仍可按风险执行。预算不是每月必须花完的配额，也不是允许隐私泄漏的理由；安全底线可独立于可用性预算。

## 七、告警、Owner 与可行动的 Runbook

每个 Alert 都有 Team、Severity、处理时限和 Runbook。Runbook 是按证据执行的处置说明：看哪些图、怎样区分依赖与前端问题、停止放量/回退入口、验证恢复和升级联系人。仅写“联系开发”不够，失效链接也要定期演练。

Severity 按用户影响及紧急性分级，关键结账大面积失败应立即响应，低频可恢复错误可进入工作队列。基于症状和预算的告警通常比每个 CPU/单条 JS 错误都呼叫更有行动价值；底层指标作为定位证据。合并同因告警并抑制重复，避免一次上游故障通知所有团队几十次。

Platform 提供 Golden Path（默认推荐交付路径）：模板、SDK、测试能力、告警接入和例外工具；Domain Team 对业务语义、值班和修复负责。共享平台故障由平台牵头，跨域事故按事件负责人协调，不能简单按最先报错的组件归责。

处置后复盘触发条件、检测缺口和恢复成本，将可重现问题补为恰当层级测试，更新门禁与 Runbook。不是每次事故都增加一个全量 E2E，应该选择能稳定验证根因的最低有效层级。

## 八、例外、推广与交付流

Exception Process 让有正当理由的变更在已知风险下交付，不是免检按钮。记录原因、受影响范围、Risk Owner、补偿措施、批准人、到期日和复查条件；例如资源预算超出但业务必须上线，可缩小灰度、加强监控并设优化期限。严重越权或泄密不能只靠写“接受风险”随意绕过组织底线。

到期自动提醒或恢复阻断，未经复查不静默延期。区分新增退化与历史债务：可以先禁止继续恶化，再分期降低存量，但关键风险仍需专门修复。Warning 长期无人处理，应升级为明确任务、调整误报或删除无价值规则，不能无限堆积黄灯。

推广先选关键应用建立测量与责任，再逐步统一 Schema、风险模板和必需检查。兼容老应用 SDK 和事件版本，避免平台一次升级让所有产品停工。门禁成本要可见，包括 CI 分钟、存储、高基数查询和维护投入。

同时衡量 Quality 与 Delivery Flow：Change Failure Rate 是导致生产故障或需修复/回退的变更比例，分母与故障关联窗口须固定；Lead Time 是变更到生产的耗时，应明确起止。再看门禁排队、误报、首跑失败和例外存量。不能只优化发布速度而掩盖故障，也不能靠停止发布得到“零变更失败”。

## 九、面试完整回答与深入追问

**问：怎样定义前端平台质量门禁？**

答：先按关键任务与损失分级风险，定义每项检查的证据、阻断条件和 Owner。PR 运行快速类型、Lint、边界、组件测试、扫描和受影响构建；预览验证真实契约、关键 E2E、视觉、性能与可访问性；生产以同一不可变制品灰度，用错误、体验和业务结果决定继续、停止或回退。平台提供默认路径，领域负责结果，例外有风险责任人和期限。最后用事故、交付时间和误报反向改进门禁。

追问“所有 E2E 都阻塞吗？”答：不需要每个小改动全跑，但高风险路径及最终组合必须覆盖，按影响图和风险选择，不能简单全部放到上线后。

**问：可观测性怎样避免只是一堆 Dashboard？**

答：从用户任务定义 SLI，统一 SDK 的事件、发布和链路上下文，再按领域/路由定位。每个告警连接 Owner 与可执行 Runbook，处理后补测试和政策；同时监测采集健康，确保没数据不是被误当无故障。

追问“统一 SDK 就统一成功定义了吗？”答：不够，成功与业务拒绝由领域契约定义，Schema 只约束结构，需治理含义、版本和分母。

**问：怎样写结账 SLO？**

答：定义窗口内有效会话或提交意图，以去重的好事件/总事件计算，明确致命错误、结果期限、Pending 和数据缺失；再定目标与预算。前端感知和服务端订单事实交叉验证，按设备与版本看体验，不能只统计没有异常。

追问“99.9% 能通用于所有产品吗？”答：不能，需结合用户期待、后端能力、损失和成本；安全底线也不应简单折算成可用性预算。

**问：灰度转化下降就自动回滚吗？**

答：先保证对照和曝光可信，设置最小样本、时间窗口、绝对底线与容忍退化；证据不足保持当前比例，严重直接用户影响先停止。转化受促销和用户结构影响，结合错误和任务结果判断，并确认数据与旧版本兼容。

追问“回滚会撤销订单吗？”答：不会，代码和交易事实不同，支付等需按业务 ID 确认与对账，不能自动重放。

**问：怎么处理超预算但必须发布的 Feature？**

答：走有记录的例外，说明业务必要性、替代方案、风险责任人、补偿和到期，按组织权限审批。可以缩灰度、减少非关键资源并加强监控，到期复查；不可越过明确安全底线。

追问“门禁会变慢怎么办？”答：看排队、误报与维护成本，缓存分片和按影响运行，加速反馈同时保留关键验证，不把中央人工审批作为默认路径。

## 十、扫雷自测与速记

1. **类型检查通过等于接口正确吗？** 不等于，实际响应、金额单位与错误语义还需运行时与契约验证。
2. **自动可访问性扫描通过能替代人工吗？** 不能，键盘、焦点和读屏完成任务等仍需检查。
3. **重跑成功能忽略首次失败吗？** 不能，可能是真实竞态，保留首跑证据并治理 flaky。
4. **Beacon 返回 true 是送达证明吗？** 不是，只表示接受排队，需服务端接收健康与缺失监测。
5. **Source Map 任意版本都可定位吗？** 不行，必须对应准确制品，否则映射可能误导。
6. **平均各组 p75 等于全局 p75 吗？** 不等于，分位数不是可简单平均的量，需要分布或样本合并。
7. **只要错误数下降就是改善吗？** 不一定，流量、采样、SDK 覆盖和事件语义都可能改变。
8. **没有足够灰度样本算通过吗？** 不应，证据不足应保持或按明确定义的人工政策判断。
9. **每条异常都即时呼叫最好吗？** 不一定，噪声会削弱响应，应按用户影响与紧急性行动。
10. **例外写了到期日就够吗？** 不够，需风险 Owner、补偿、批准及到期执行机制，不能永久忽略。

速记：风险决定门禁；检查有证明边界；制品固定、灰度稳定、证据不足不冒充通过；SDK 统一结构、领域定义含义；SLO 有分母窗口和数据源；告警有处置人；例外有退出；质量与交付流同时测量。
