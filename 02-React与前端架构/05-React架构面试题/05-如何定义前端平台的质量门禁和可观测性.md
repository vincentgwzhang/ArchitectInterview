# 05. 如何定义前端平台的质量门禁和可观测性

## 目标

质量门禁应保护用户、安全和交付，不应变成所有团队的中央审批 Bottleneck。采用自动 Guardrail、风险分级和清晰 Exception Process。

## Pull Request 门禁

- Type Check。
- ESLint、Import Boundary、Accessibility Rule。
- Unit/Component Test。
- Dependency 和 Secret Scan。
- Bundle Diff。
- 受影响 Package Build。

保持反馈快速；慢 E2E 不应全部阻塞每个小改动。

## Preview/Pre-production

- Contract Test。
- 关键 E2E。
- Visual Regression。
- Lighthouse/性能 Budget。
- CSP/Security Header 检查。
- Accessibility 自动扫描。

## Progressive Delivery

Artifact Immutable，按 Canary/Feature Flag 发布。自动比较 Error Rate、Core Web Vitals、关键 Funnel 和 API Failure，异常时停止或 Rollback。

## 生产可观测性

统一 SDK 采集：

- RUM 和 Core Web Vitals。
- JavaScript Error 与 Source Map。
- API Latency/Error。
- Release Version。
- Trace Correlation。
- Domain Funnel Event。

按 App、Route、Team、Version、Browser 和 Region 分解，并控制 PII 与 Sampling。

## SLO

示例：

- 99.9% Checkout Session 无致命 JS Error。
- 75th Percentile LCP 达到目标。
- 99.5% Order Submit 得到明确结果。
- 新 Release 不得使 Conversion 显著下降。

## Ownership

每个 Alert 有 Team、Runbook 和 Severity。Platform 提供 Golden Path，Domain Team 对自己的生产质量负责。

## Exception

无法满足 Budget 的 Feature 必须记录原因、Risk Owner、补偿措施和到期时间。避免永久忽略 Warning。

## 面试亮点

强调门禁按风险分层，连接 CI 与 Production Feedback，并同时衡量 Quality 与 Delivery Flow，如 Change Failure Rate 和 Lead Time。
