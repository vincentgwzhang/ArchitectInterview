# 02 设计支持 SSR、SEO 和高并发的电商前端

本题的核心矛盾是：公开读取希望尽量缓存、搜索引擎希望获得完整可信内容，而价格、库存、身份和支付要求及时且正确。架构应按数据与用户任务分层，不能用“全站 SSR”或“全部缓存”回答所有约束。

本文使用虚构电商案例，不代表用户项目或测得的性能收益。SSR 是服务端渲染，SEO 是搜索引擎优化，CDN 是内容分发网络。React Streaming 基本能力按 18+ 讨论；ISR 是框架能力，本文以 Next.js App Router 的增量再生概念举例，不将其行为当作 React 标准。资料于 2026-11-26 核验；示例为策略与接口设计，未实际部署或压测。

## 一、澄清目标并划定正确性边界

### 1.1 需要问到什么

先问商品数量、热门与长尾比例、地区/语言/币种、登录比例、价格更新频率、峰值请求、活动持续时间、支持设备，以及商品下架和支付结果的处理要求。峰值要区分页面请求、API 请求、爬虫与真实下单，不能用日活直接推导服务器数量。

非功能需求应定义测量范围：移动弱网首屏、关键页面可用性、结账成功率、允许展示旧价格的最长时间、恢复时间与成本上限。先建立可填写目标，再通过压测和现场监控校准，而不是虚构“一台机器支持多少万并发”。

四个目标需要同时满足：商品和分类可发现与索引；首屏快且大促可承载；个性化不串用户、报价不被误当成交价；结账安全、失败后能确认结果。展示快照可以最终一致，但订单确认金额和库存扣减必须由服务端规则裁决。

### 1.2 页面读取和交易分开

公开商品读取通过 CDN 到可缓存页面，再到 SSR/再生服务及商品读模型；用户购物车和结账通过身份验证的应用接口到交易服务。读模型（Read Model）是为展示组织的数据副本，适合高读取与预计算，但可能落后于交易事实。

这个拆分避免每次商品访问都查询库存事务库。代价是数据有新鲜度窗口，所以页面需区分“展示价格/库存提示”和“最终确认”，并在提交时重新验证。不能让前端把展示价格作为可信金额传给支付系统。

## 二、按路由与数据选择渲染方式

| 页面 | 建议起点 | 为什么以及边界 |
| --- | --- | --- |
| Marketing、帮助、静态活动说明 | SSG，构建期生成 | CDN 可直接交付；紧急改动需可靠更新，活动状态不能靠旧页面裁决 |
| Category、Product | ISR 或可缓存 SSR | 兼顾内容更新和复用；必须约束缓存键与陈旧窗口 |
| Search | 有价值入口 SSR 首屏，后续客户端导航 | 首屏可读且交互连续；无限搜索组合不应全部开放索引 |
| Cart、Account、Checkout | 动态 SSR 或客户端渲染 | 用户私有数据；禁止进入共享响应缓存 |
| Recommendation | 延迟或独立加载 | 非关键，可超时降级，不能拖住商品与结账 |

SSG（Static Site Generation）在构建时生成页面，商品数量很大时全量构建可能过慢，可预生成热门内容、长尾按需生成。SSR 每次生成 HTML 或在缓存未命中时生成，计算与后端延迟更直接进入请求路径。ISR（Incremental Static Regeneration）允许在运行期间更新静态输出，但更新何时触发、是否先返回旧值、失败是否保留旧页、多副本如何共享，取决于框架版本和部署。

例如定时再验证通常不是“到点后台一定更新”，可能是后续请求触发。事件再验证也不能自动保证所有 CDN、数据缓存和浏览器同时更新。上线前要验证框架、托管层和自建缓存的实际组合，不能只看一个 revalidate 参数。

动态 SSR 有助于输出用户数据，但不保证比客户端渲染快；它增加服务端计算和身份隔离责任。私有后台若无收录需要，可优先关注交互与安全，不必为“统一技术”强制 SSR。

## 三、Streaming、Suspense 与水合的执行过程

Streaming SSR 允许先发送已准备好的页面 Shell，再陆续发送其他区域。Suspense 给尚未就绪的内容提供占位；水合（Hydration）则在客户端把 React 行为接到服务端 HTML。先看到文字不等于所有按钮已经能交互，监控不能只看 HTML 到达时间。

商品标题、主要图片、关键价格说明及能判断是否存在的商品信息应尽量在关键输出中；推荐、评价等可放在后续边界。若所有数据先被一个大 Promise 串行等待，再加 Suspense 也不会自动消除瀑布。应并行发起互不依赖请求，设置总预算，对非关键依赖超时后降级。

Node 环境可用 React renderToPipeableStream，Web Streams 环境用相应 API；多数生产项目应由支持这些机制的框架管理路由、资源和数据集成，不随意拼接协议。反向代理/CDN 若缓冲整个响应，会抵消流式收益，需通过真实链路检查首字节、分段和压缩行为。

HTTP 头一旦发出通常就不能改状态码。因此应在开始流之前解决关键路由是否存在、是否授权及必要重定向；Shell 发出后才发现商品不存在，不能假装还能变成正常 404。可选择等待关键内容，或者使用框架明确支持的流式错误语义并验证搜索引擎结果。等待所有内容适合某些静态生成或抓取场景，但会增加延迟，不能简单对任意自报爬虫无限等待。

客户端和服务端首次输出应一致。时间、随机数、地区和个性化条件不同会导致水合不匹配；用明确数据快照和环境输入，而非隐藏警告。中断连接要停止无意义渲染，取消可取消的请求；服务端取消不保证远端操作已经停止。

## 四、CDN 与缓存：提高命中率之前先保证不会串用户

### 4.1 缓存对象和键

静态资源使用内容哈希名称及长期 immutable 缓存，发布新内容产生新 URL；HTML 或清单保持可更新。回滚时保留旧资源，避免打开着的页面找不到旧 chunk。不能给经常覆盖的 main.js 同样设置长期 immutable 后期待立即更新。

公开商品键至少考虑 Product、Locale、Currency，并根据定价规则加入市场、渠道等真正影响输出的维度。不是所有币种都能代表税区；如果服务端根据 Cookie、会员等级或实验分组改变响应，却没反映在缓存边界中，就会泄漏或错价。

对随机跟踪参数先规范化，避免攻击者或广告参数造成无限碎片；对影响内容的参数不能随意忽略。整份 Cookie 进入缓存键通常导致低命中且仍难证明安全。更好的起点是公开页面完全不含私有字段，登录信息在独立私有请求中加载。

```http
# 教学策略，实际秒数由业务陈旧容忍与压测决定
# 公开商品 HTML，可供共享缓存短期复用
Cache-Control: public, max-age=0, s-maxage=60

# 账户、购物车、结账的私有响应
Cache-Control: private, no-store
```

上例是两类不同响应，不是同一个响应的两个并列头。private 禁止共享缓存，no-store 指示不存储；还需确保 CDN 规则没有覆盖、SSR 框架数据缓存没有跨用户复用，以及应用缓存按身份隔离。no-store 不能替代授权，也不能擦除已泄漏的数据。

### 4.2 失效、再生与竞态

商品更新事件可触发页面/标签失效、读模型更新和 CDN 清理，但事件可能延迟、重复、乱序或丢失。消费者需幂等，监控处理延迟，并用周期性修复或 TTL 提供兜底。下架、召回、重大价格错误等事件可能要求更严格的即时阻断，不能仅等待一般 TTL。

还要防止“旧请求在清理后重新填入缓存”：可将商品版本加入生成与发布校验，或按版本保存制品并原子切换指针。先更新数据再失效，并验证再生读取的是预期版本；多区域读模型延迟要进入设计。

缓存穿透是无效请求不断回源，可对不存在商品短期负缓存并限制异常输入，但新建商品需及时解除负缓存。热点失效时大量请求同时再生会产生击穿，可合并同键请求、限制生成并发、预热热门页并错开过期。允许时返回有界旧值保护源站，不能对支付和私人数据复用这一策略。

### 4.3 快照与成交正确性

商品页可显示某时点库存和价格，结账时服务端重新校验 SKU、数量、促销、税费、配送和权限，生成有有效期的报价或订单意图。价格变化应清楚提示并请用户确认，不能在付款后才解释。

库存数量是并发变化的事实，页面显示“有货”不等于预留成功。库存预留、超时释放和扣减由后端实现；前端展示处理中、缺货与替代选项。个性化推荐或会员价格若混入共享 HTML，要么单独加载，要么真正隔离缓存并评估命中率损失。

## 五、SEO：可抓取、可理解、状态正确

### 5.1 首屏内容和元数据

服务端应输出有意义的 Title、Description、Canonical、商品主体和可发现链接。Google 能处理很多 JavaScript 页面，但抓取与渲染有阶段和资源限制，其他搜索引擎及分享机器人也未必执行完整脚本。SSR 降低依赖，不保证一定收录或排名。

Canonical 表达重复页面的首选 URL，应与内链、站点地图和重定向策略一致；它不是强制删除其他 URL 的安全机制。Structured Data（结构化数据）用机器可理解结构描述商品、报价等，必须与可见内容一致，不能为了搜索展示编造评分、库存或价格，也不能保证获得富结果。

Sitemap 帮助发现重要 URL，更新时间应可信；站内导航仍需普通可抓取链接，不要只有点击事件。Robots 控制抓取，而不是隐私保护或授权；禁止抓取可能使爬虫看不到页面上的 noindex。私有账户必须身份保护，不能靠 robots 隐藏。

### 5.2 状态码与重复内容

不存在商品返回真实 404，永久移除可按业务选择 410；有稳定替代页面时使用合适重定向，不能把所有不存在商品都跳首页。错误内容却返回 200 可能形成软 404（Soft 404），既混淆爬虫也破坏监控。暂时缺货但仍有商品价值时可保留页面并准确标注，不等于必须删除。

分页应有稳定独立 URL、可抓取链接和对应内容。筛选、排序、颜色、价格区间组合会制造大量近似页面：只对有搜索价值且内容充足的组合开放索引，其他组合制定规范化与抓取策略。不能把内容不同的所有分页都无条件 canonical 到第一页，也不能靠无限滚动让后续商品永远没有可发现 URL。

通过抓取测试和搜索工具检查最终 HTML、渲染后内容、状态、Canonical、结构化数据及阻塞资源。机器人 User-Agent 可伪造，不应把仅对“爬虫”放行的数据当安全设计；用户与搜索引擎应获得一致的实质内容。

## 六、高并发：缓存命中之外的容量与保护

### 6.1 从回源模型推导容量

虚构算例：公开页面峰值 100,000 次/秒，若有效命中率 99%，仍有约 1,000 次/秒回源；若降为 90%，回源变成 10,000 次/秒。此为算术推演，不是 benchmark。真实容量还要算动态页面、API、再生、爬虫、重试、缓存冷启动及每次 SSR 的依赖扇出。

若每次 SSR 需三个 API，请求量不能只按一个页面计算。用压测估计 CPU、内存、依赖连接和尾延迟，控制每个实例并发、总渲染时间及等待队列。流式响应可能更久占用连接，低首字节不代表低资源成本。

Origin 多可用区（Multi-AZ）减少单区故障影响，自动扩容需考虑启动时间、冷缓存和共享后端上限；不能等故障已经过载才临时增加无限 SSR 实例。活动前预热、容量预留和限额核验通常比只依赖自动扩容更可靠。多区域还增加库存、身份和价格一致性成本，不必默认采用。

### 6.2 优先保护交易任务

推荐、评价和非关键埋点应有独立超时、并发和降级；推荐失败时隐藏或显示静态备选，不阻塞商品和结账。熔断器在持续失败时暂时停止调用，避免浪费资源；限流和有界队列限制过载扩散；重试必须有预算、退避和抖动，避免每层重试叠加成风暴。

热门商品可用缓存和预计算读模型，交易接口仍需要权限、幂等与库存控制。必要时使用等待室或准入控制平滑结账流量，但排队状态要可信、可恢复，并防机器人滥用。静态页面能扛流量不代表下单 API 也能扛。

成本同时来自 CDN 请求与流量、图片变体、SSR 计算、再生频率、数据库读取和监控。提高新鲜度可能增加回源，增加缓存维度可能降低命中率；给每类数据分配可接受的陈旧窗口比全站统一短 TTL 更可控。

## 七、性能：让关键内容快到达且能交互

Hero Image 是首屏主要展示图，常影响最大内容绘制 LCP。服务端早暴露正确资源，使用响应式尺寸与现代编码、保留宽高，避免给真正关键图片懒加载；高优先级只给少量关键资源，过多预加载会争抢带宽。

Route Code Splitting 按路由切分 JavaScript；重型评价、编辑器等延迟加载，避免主入口执行所有代码。第三方脚本按必要性、页面与同意状态加载，监测长任务和失败，不能让客服与分析初始化阻塞购买。

RSC（React Server Components）可让部分组件逻辑在服务端执行，减少对应客户端代码及数据准备工作，但仍需传输 HTML/RSC 数据；客户端边界下的依赖仍可能进入客户端包。它不等于自动缓存、安全授权或没有水合成本，需框架支持并测实际网络与执行量。

RUM（真实用户监控）按路由、地区、设备、版本观察 LCP、交互响应 INP 和布局偏移 CLS，以及商品可用率和结账漏斗。实验室分析定位原因，现场数据验证效果；只看桌面 Lighthouse 分数会遗漏弱机和真实第三方开销。优化前后保留可比较样本，不能把促销流量结构变化误当性能改进。

## 八、安全与失败体验

### 8.1 身份、支付与缓存隔离

HttpOnly 会话 Cookie 减少 JS 直接读取身份凭据，Secure 和适当 SameSite 控制传输及跨站发送，并配合 CSRF Token/来源校验。HttpOnly 不阻止恶意同源脚本发请求，因此继续防 XSS，使用 CSP 约束执行来源，对富文本清洗，后端独立校验资源归属。

支付 Tokenization 将卡信息交给支付提供者的受控组件处理，商户使用令牌发起流程，减少原始卡数据接触；令牌仍需保密、限制用途并验证订单归属，不能据此声称无需任何支付安全责任。支付成功由受信服务端结果确认，不能只信浏览器跳转参数。

SSR 的请求上下文、查询缓存和 HTML 必须区分公开与私有。不要把用户对象放模块全局变量；响应包含身份相关信息时禁止共享缓存。缓存泄漏属于正确性和安全事故，命中率再高也不能接受。

### 8.2 幂等、Pending 与局部错误

购物车“设置数量为 3”与“数量加 1”重试语义不同。前者可能按资源版本更新，后者需操作 ID 去重；幂等（Idempotency）意味着相同业务操作重试不产生额外副作用，必须由服务端实现，禁用按钮只防部分交互。

支付超时进入 Pending（结果待确认），显示“正在确认支付，请勿重复付款”，用订单/支付意图查询最终状态，采用有上限和退避的轮询，支持刷新后恢复。服务端根据支付通知、主动查询及对账推进状态；不能让客户端超时直接把订单改失败。

```text
created → awaiting_payment → processing → paid
                                  ↘ failed
                                  ↘ pending_reconciliation
```

这是概念状态，不是客户端自行裁决的状态机。重复或乱序支付通知需服务端幂等及合法迁移检查，已 paid 不应被迟到失败消息覆盖。长期未确认给出支持入口和业务标识，别无限转圈。

推荐和库存展示可独立加载、独立错误提示；Error Boundary 能限制部分 React 渲染故障，但 API 失败、事件和支付回调要显式处理。库存查询失败应说明“暂时无法确认”，不能伪装为有货；推荐失败不应导致整个购买页消失。

## 九、验证、监控和演进

先建立公开/私有数据清单和路由策略，再实现缓存键、再验证与交易正确性，随后补流式输出、性能和峰值保护。不要先大量缓存，再尝试辨认哪些字段含用户信息。

验证覆盖：两个身份/地区的缓存隔离；价格更新、下架和事件乱序；热门失效后的回源峰值；SSR 关键和非关键依赖失败；真实 HTML 与状态码；支付请求超时但远端成功；旧页面加载旧资源。单元测试验证键规范化和状态映射，契约测试验证金额/错误语义，E2E 验证关键旅程，压测验证容量与降级。

监控 CDN 命中及回源、数据与页面版本差距、再生失败、SSR 尾延迟、依赖超时、支付 Pending 年龄和重复支付告警。关联版本、路由模板及脱敏业务 ID，禁止把完整支付信息放日志。灰度发布并保留兼容制品；回滚代码不等于回滚价格、订单和支付事实，应分别处理。

## 十、面试完整回答与追问

**问：如何设计支持 SSR、SEO 和大促的电商前端？**

答：先澄清公开流量、商品更新、地区、个性化和交易目标。静态营销用 SSG，商品分类用 ISR 或可缓存 SSR，搜索首屏 SSR 加客户端导航，购物车账户结账动态处理且禁止共享私有缓存。CDN 缓存公开页面与哈希资源，键包含商品、语言、币种和市场，事件更新配 TTL 与版本兜底。关键商品信息先输出，推荐等流式或独立加载。SEO 保证真实正文、元数据、链接与正确状态。高峰时保护源站、缓存再生和交易接口，先降级推荐；价格库存和支付由后端最终确认。通过现场体验、回源容量和交易结果共同验收。

追问“为什么不全部动态 SSR？”答：公开内容重复计算浪费容量且放大依赖故障；缓存可显著减少重复工作，但必须限制陈旧窗口与私有数据混入。

**问：ISR 怎样保证库存实时？**

答：它本身不保证实时库存，只是在约定机制下更新页面。库存展示是快照，提交时服务端校验并按规则预留；事件失效、周期兜底和版本监控减少陈旧，用户需看到冲突与恢复选择。

追问“下架必须立即生效呢？”答：给下架设计高优先级阻断与失效流程，必要时在服务端交易和公开访问处明确拒绝，不能只依赖一般商品页 TTL。

**问：Streaming 会不会影响 SEO？**

答：取决于关键内容、元数据、HTTP 状态和抓取链路。先确认商品是否存在再发送关键响应，关键正文不只留在永远不触发的交互中；验证代理无不必要缓冲及搜索引擎实际渲染。不能在头发出后指望改 404。

追问“是否等所有内容再发？”答：某些生成和抓取场景可以，但会牺牲首字节并被慢推荐拖住，应按关键内容边界和客户端能力决定。

**问：大促命中率 99% 是否足够？**

答：还要乘峰值算回源，再加动态请求、再生、依赖扇出及冷缓存。命中率从 99% 到 90% 会让同样公开流量的回源增至十倍，所以必须模拟热点失效和故障容量，不只测正常缓存。

追问“加实例能解决吗？”答：有启动延迟和后端上限，可能把数据库压垮。需要预热、并发预算、请求合并、有限旧值及非关键降级。

**问：支付超时如何避免重复扣款？**

答：用同一支付意图/幂等键关联重试，浏览器显示 Pending 并查询服务端状态，服务端处理通知和对账。刷新后按业务 ID 恢复；绝不因客户端超时直接创建另一笔独立支付。

追问“按钮禁用够吗？”答：不够，多标签、刷新和网络重试仍会重复，正确性必须在服务端保证。

## 十一、扫雷自测与速记

1. **SSR 就一定收录吗？** 不保证，发现、抓取权限、状态、内容质量和规范化都影响结果；必须验证真实输出。
2. **ISR 到期一定立即生成吗？** 不一定，可能依赖后续请求或特定平台触发；核实实际版本与部署。
3. **商品键只含 productId 足够吗？** 若语言、币种、税区影响输出就不够；必须反映真实内容维度。
4. **Cookie 全部加到缓存键就安全且高效吗？** 不一定，命中率可能极低且仍可能漏其他维度，优先分离公开与私有响应。
5. **清理 CDN 后一定不会出现旧页吗？** 不一定，旧请求回填、读模型延迟及框架缓存都可能带回旧内容，需要版本与兜底。
6. **Shell 发出后还能正常改 404 吗？** HTTP 头已提交后通常不能；关键路由结果应在提交头前确定或明确处理流式语义。
7. **无库存就必须删除商品页吗？** 不一定，暂缺仍可保留有价值内容并标注；不存在或永久移除要使用符合事实的状态。
8. **RSC 能保证没有客户端 JS 吗？** 不能，客户端交互边界仍需要代码，传输与水合成本需实测。
9. **支付返回页说成功就能交付吗？** 不能，浏览器参数可不可信，服务端必须确认受信支付结果及订单归属。
10. **回滚前端就能回滚交易吗？** 不能，订单和支付事实需独立一致性处理，不能因代码回退丢掉已发生交易。

速记：公开读取可缓存，私有响应要隔离；展示是快照，成交由服务端确认；Streaming 先关键后非关键；SEO 看正文链接状态；容量算回源和扇出；峰值先降非关键；支付超时是未知，幂等与查询确认结果。
