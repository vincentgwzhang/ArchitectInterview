# 03 单元测试、组件测试、集成测试与 E2E 测试

测试的目标是用可承受的反馈时间和维护成本，发现会影响用户与业务的错误。测试数量、覆盖率和工具名称都只是手段。本章以 React Web 应用为例，解释如何组合测试、如何构造有证明力的断言，以及失败后如何定位。

版本边界：示例采用 React 函数组件、Vitest 的测试 API、Testing Library 的 DOM 查询与 user-event 14 风格异步调用、MSW 2 的 `http/HttpResponse` API、Playwright Test 的定位器与自动重试断言。项目应固定实际依赖和浏览器版本；MSW 1 的 `rest/res/ctx` 不能直接混用。文末提供官方核验入口。本文代码为教学示例，未在完整 React 项目中安装依赖或运行，业务路径和数据准备接口须按项目实现。

## 一、从风险选择测试层级

### 1.1 测试边界比工具名称更重要

单元测试（Unit Test）隔离一个规则或计算；组件测试（Component Test）验证一个 UI 单元的用户行为；集成测试（Integration Test）验证多个模块真实协作；端到端测试（End-to-End，E2E）验证跨系统的完整用户旅程。契约测试（Contract Test）专门验证服务交互约定。

同一个 Vitest 可以运行单元和组件测试；同一个 Playwright 可以测试孤立组件或完整系统。浏览器真实不代表后端真实，渲染了整页也不代表覆盖了真实登录和部署。报告必须声明“真实部分、替身部分、未覆盖边界”。

| 层级 | 具体对象与应验证行为 | 主要收益 | 无法单独证明的事情 |
| --- | --- | --- | --- |
| 单元 | 价格计算、Reducer、领域规则的输入输出和边界 | 快、失败定位直接，适合大量规则组合 | UI 是否接线正确、接口是否可用 |
| 组件 | 表单输入、校验、提交中状态、错误提示 | 从用户视角验证交互，重构内部实现较稳定 | 真实布局、浏览器兼容和服务端行为 |
| 集成 | Component、Router、Store、真实请求客户端加网络 Mock | 发现模块接线、缓存、路由与序列化问题 | Mock 是否等于真实服务 |
| 契约 | 请求路径、方法、身份要求、状态码、Schema 与关键行为 | 提前发现消费者与提供者不兼容 | 全旅程和生产配置正确性 |
| E2E | 浏览器、部署制品、真实受控后端的登录/结账/管理流程 | 跨边界信心高，发现部署接线问题 | 所有边界输入、所有设备和故障排列 |

DOM 模拟环境提供 JavaScript 可调用的 DOM，但不等于完整浏览器排版与绘制引擎。尺寸、滚动、字体、焦点细节等应按风险补真实浏览器测试。组件测试若把所有子组件和 Hook 都替换，虽然执行很快，却可能只证明替身互相配合。

### 1.2 金字塔不是固定比例

测试金字塔（Test Pyramid）提醒团队把大量可隔离规则放在低层，避免所有风险都用慢且难定位的 E2E 兜底。强调集成测试的策略则提醒：许多前端缺陷发生在组件、路由、状态和网络交界。两者都不能推导出通用的数量比例。

以结账为例：折扣、舍入与库存判断用单元测试覆盖组合；地址表单用组件测试覆盖输入和错误；订单页用集成测试覆盖请求及缓存；用契约测试核对金额单位与错误码；少量 E2E 验证从购物车到订单可查询。不要在每条 E2E 中穷举全部优惠规则。

评估优先级时同时考虑损失、发生可能、变更频率和发现难度。支付重复扣款、越权和订单丢失通常比装饰性图标更优先。对于浏览器编辑器、拖拽画布等高度依赖布局的产品，真实浏览器测试的比重可以更高。成本不仅是运行分钟数，还包括失败调查、测试数据维护和阻塞发布的时间。

## 二、断言可观察行为，而非实现结构

### 2.1 用业务结果组织 Arrange、Act、Assert

准备（Arrange）建立明确初始条件；操作（Act）执行用户或调用者动作；断言（Assert）检查业务约定。测试名称应表达条件和结果，例如“保存失败后显示错误并允许再次提交”，而不是“调用第二个 Hook”。

纯函数应覆盖正常值、边界值与非法输入；Reducer 是把旧状态和 Action 转为新状态的函数，应验证状态转换及旧状态不被意外修改。金额计算必须先明确整数最小货币单位或十进制定点策略，再断言舍入，不能拿与实现完全相同的算法计算“预期值”，否则同一个错误可能复制两遍。

UI 优先使用角色（Role）、可访问名称（Accessible Name）、Label 和用户可见文本。例如 `getByRole('button', { name: '提交' })` 表达用户可找到的控件。CSS 类名和内部 state 容易因重构变化；没有稳定语义的画布等场景可用明确约定的 test id，但它不能替代可访问性设计。多个同名按钮应缩小到表单或列表项内查询，不应依赖“第 3 个按钮”碰巧正确。

### 2.2 完整组件示例：失败可恢复

下面组件把持久化能力作为 `save` 参数注入，适合验证 UI 状态；它没有验证 HTTP 协议。代码假设 JSX 构建已配置。

```jsx
// SaveButton.jsx
import { useState } from 'react';

export function SaveButton({ save }) {
  const [busy, setBusy] = useState(false);
  const [message, setMessage] = useState('');
  async function submit() {
    if (busy) return;
    setBusy(true);
    setMessage('');
    try {
      await save();
      setMessage('保存成功');
    } catch {
      setMessage('保存失败，请重试');
    } finally {
      setBusy(false);
    }
  }
  return (
    <>
      <button disabled={busy} onClick={submit}>保存</button>
      <p role="status">{message}</p>
    </>
  );
}
```

以下测试需要 Vitest 配置 `environment: 'jsdom'`、安装 React Testing Library、user-event、jsdom 和 jest-dom；jest-dom 在这里仅为 Vitest 扩展 DOM 断言。显式 cleanup 避免依赖测试运行器的全局 Hook 配置。

```jsx
// SaveButton.test.jsx
import { afterEach, expect, test, vi } from 'vitest';
import { cleanup, render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import '@testing-library/jest-dom/vitest';
import { SaveButton } from './SaveButton';

afterEach(cleanup);

test('失败后可再次提交并显示成功结果', async () => {
  const save = vi.fn()
    .mockRejectedValueOnce(new Error('temporary'))
    .mockResolvedValueOnce(undefined);
  const user = userEvent.setup();
  render(<SaveButton save={save} />);
  const button = screen.getByRole('button', { name: '保存' });

  await user.click(button);
  expect(await screen.findByText('保存失败，请重试')).toBeVisible();
  expect(button).toBeEnabled();

  await user.click(button);
  expect(await screen.findByText('保存成功')).toBeVisible();
  expect(save).toHaveBeenCalledTimes(2);
});
```

断言调用次数是为了辅助证明用户动作没有重复提交，主断言仍是失败恢复和最终结果。另写一个受控 Promise 的测试可检查 pending 期间按钮禁用：先让 `save` 返回尚未完成的 Promise，点击后断言 disabled，再完成 Promise 并等待成功。不要靠“接口应该足够慢”制造 pending。

按钮禁用只保护当前 UI 的交互，不保证系统级恰好一次（Exactly Once）。超时后重试、页面刷新或多标签提交仍可能重复；订单 API 必须有幂等键和服务端去重，再用集成/契约测试验证同键重复请求的结果。

### 2.3 Snapshot 和覆盖率的正确位置

快照测试（Snapshot Test）保存某次结构或输出作为基线，适合小而稳定、评审者能理解的序列化结果。巨大 DOM 快照经常让人批量接受更新，既没说明用户行为，也可能漏掉事件未接线。关键行为应有显式断言，快照只作为补充。

行覆盖率表示执行过哪些行，分支覆盖率表示经过哪些判断分支；两者都不证明断言正确。例如函数永远返回 true，只要测试不检查结果，仍可达到高覆盖率。先列业务不变量和失败路径，再用覆盖率查遗漏；安全、金钱等关键规则可设更严格门槛。变异测试（Mutation Testing）故意改变运算符或条件，观察测试能否发现，可评估断言强度，但也有计算成本和等价变异，不必覆盖所有 UI。

## 三、异步、计时与竞态要可控制

### 3.1 按状态等待，不按猜测等待

Testing Library 中，`getBy*` 用于当前应存在的元素，缺失或匹配多个会报错；`queryBy*` 在缺失时返回 null，适合断言不存在；`findBy*` 返回 Promise，在期限内重试查找，适合等待异步出现。复数查询用于明确预期多个的情况。断言消失时要先确保元素曾出现，否则测试可能在请求尚未开始时提前通过。

user-event 模拟交互的 API 通常需要 await。需要等待断言满足时可用 `waitFor`，其回调可能多次执行，所以回调中应放断言，不能放重复点击、下单等副作用。固定 sleep 会同时产生“机器快时浪费、机器慢时失败”，应等待明确 UI、响应或业务状态；超时仍须有限。

Playwright 的 Locator 操作会做相关可操作性检查，`await expect(locator).toBeVisible()` 等 Web 断言会自动重试。但自动等待不知道“后台订单已经持久化”这一业务条件，也不能修复点击到了错误元素。不要用强制点击掩盖遮挡、加载层和真实交互缺陷。

### 3.2 时间控制与旧响应覆盖

防抖（Debounce）是等待一段安静期后才执行，节流（Throttle）限制单位时间内频率；测试时应控制时钟并明确边界：未到期限不触发，到期后只触发预期次数。伪计时器（Fake Timers）替换指定计时 API，不代表网络、浏览器所有异步源和服务端时钟都随之推进。与 user-event 联用时按版本配置推进计时器，测试结束恢复真实计时、Mock 和全局状态，避免下一个测试卡住。

搜索框的重要竞态：先发 A，再发 B，B 先返回，A 后返回。期望结果仍为 B。测试用两个可独立完成的请求控制返回顺序，断言最终内容且旧响应不会覆盖。实现可用 AbortController 取消旧请求，并用请求序号或当前查询身份校验结果；取消是资源与流程控制，不能假设服务端工作必然停止。仅测顺序返回的成功路径无法发现这类问题。

## 四、在网络边界 Mock，并持续核对契约

### 4.1 替身放在哪里

Mock 是可配置替身，Stub 提供预设返回，Spy 记录调用；术语在库中可能重叠，关键是说明替换边界。只测价格函数无需网络替身；验证订单页协作时，优先保留真实组件、路由、Store 和请求客户端，在 HTTP 边界使用 MSW 一类工具。

这样能发现错误路径、方法、JSON 处理和 UI 错误映射；直接 Mock 内部 Hook 为“成功”会绕过这些环节。MSW 在浏览器与 Node 环境的拦截机制不同：浏览器模式使用 Service Worker，Node 模式使用请求拦截层，并非真的启动一个后端服务器。它仍不能证明生产代理、TLS、CORS 或真实后端行为。

### 4.2 MSW 2 的生命周期和错误场景

下面是 Node 测试 setup 文件片段，需注册到 Vitest 的 `setupFiles`。使用绝对测试 URL，使 Node 请求目标明确；应用测试配置也须指向同一 origin。

```js
import { beforeAll, afterEach, afterAll } from 'vitest';
import { http, HttpResponse } from 'msw';
import { setupServer } from 'msw/node';

export const server = setupServer(
  http.get('https://api.example.test/orders/42', () =>
    HttpResponse.json({ id: '42', status: 'confirmed' }))
);
beforeAll(() => server.listen({ onUnhandledRequest: 'error' }));
afterEach(() => server.resetHandlers());
afterAll(() => server.close());
```

单条失败测试可通过 `server.use(http.get(...))` 覆盖响应为 403、409 或 500，随后 resetHandlers 恢复初始处理器。严格处理未匹配请求可暴露错 URL；如果需要放行静态资源，应精确允许，避免把所有请求放行而漏掉错误。处理器重置不等于业务数据重置：自定义内存数组、客户端缓存和数据库仍需单独隔离。

至少覆盖加载、成功、空结果、校验失败、权限失败、服务错误、网络拒绝/超时和重试后的结果，并按业务风险选择组合。HTTP 500 是收到错误响应，网络异常可能根本没有响应；`fetch` 不会仅因 HTTP 500 自动抛异常，客户端必须判断状态。测试要区分这两个路径，防止 UI 永远停在 loading。重试库默认行为可能拖慢测试，可在专测错误展示时关闭重试，再单独验证真实重试策略及次数上限。

### 4.3 契约防止“前后端各自全绿”

Schema 是数据结构约定，例如字段类型、必填、可空与枚举；契约还应包括方法、路径、认证、状态码、分页、金额单位和错误语义。TypeScript 类型在运行时通常被擦除，单靠前端编译无法证明实际 JSON 合法。

例如后端把金额从“分”改成“元”，字段依旧 number，结构检查可能通过，但展示和支付金额会错误。契约需明确单位，并以提供者验证或共享的受审查样例验证关键语义。消费者驱动契约可由前端声明需要的交互，再由真实服务实现验证；它不是只让前端用自己的 Mock 自测一遍。

可将 OpenAPI/JSON Schema 作为结构来源，生成或验证 Mock 数据，再在后端流水线验证提供者。还要测试未知枚举、null、缺失字段和向后兼容策略。增加可选字段通常比删除字段风险低，但严格消费者仍可能拒绝额外字段，应以实际契约为准。契约无法证明所有权限配置和部署路由，因此仍保留少量真实系统测试。

## 五、E2E：少量高价值旅程和真实业务证明

### 5.1 选择旅程与定义成功

登录、结账和管理后台的权限流程是典型候选。结账成功不能仅断言出现绿色提示，还要确认订单号、订单详情或通过独立后端读取确认持久化；支付应使用受控沙箱，不向真实用户或生产账户收费。管理测试既验证管理员可操作，也验证普通用户不能通过直接 API 绕过隐藏按钮。

下例仅演示真实浏览器流程。前置条件是独立测试环境已为该用例准备购物车、登录身份和充足库存，配置了 baseURL；订单详情页由后端查询返回。它不是可直接对任意项目运行的通用脚本。

```ts
import { test, expect } from '@playwright/test';

test('确认结账后可查看订单', async ({ page }) => {
  await page.goto('/checkout');
  await page.getByRole('button', { name: '确认下单', exact: true }).click();
  const link = page.getByRole('link', { name: '查看订单', exact: true });
  await expect(link).toBeVisible();
  await link.click();
  await expect(page.getByRole('heading', { name: '订单详情' })).toBeVisible();
  await expect(page.getByRole('status')).toHaveText('订单已确认');
});
```

若应用仅在本地缓存伪造详情，上例仍可能误通过。项目应补独立服务查询、刷新后读取或其他能排除该假象的证据，并核对订单归属和金额。等待整页“网络空闲”不一定代表业务完成，长连接还可能永不空闲。

### 5.2 数据与身份隔离

浏览器 Context 隔离 cookie 和存储，不隔离后端数据库。同一账户的两个并行用例仍会争抢购物车或余额。用测试运行 ID、worker ID 和用例 ID 划分租户、账户与资源；创建数据时记录资源 ID，清理按 ID 执行，避免按模糊名称删除其他人的数据。

测试必须能单独、乱序和并行运行，不依赖前一个测试注册的账户。登录流程本身保留专门测试；其他流程可使用受控 fixture 注入已认证状态以节约时间，但这会跳过登录边界。保存的认证状态含敏感凭证，不能提交到仓库或公开报告，权限与有效期应最小化。

数据库事务回滚只适合操作确实在同一受控事务内的测试；浏览器请求经过多个进程、异步任务与连接时不能假设外层测试事务能全部回滚。独立数据命名空间或环境重建往往更可靠。清理失败应留记录并有过期回收，不应无限累积数据增加成本。

## 六、Flaky Test：把不确定性转为可解释证据

偶发失败测试（Flaky Test）在相同预期条件下时过时不过。先区分产品竞态、测试错误与环境故障，不能看到重跑成功就认定是测试问题。

| 现象 | 优先假设 | 验证和修复 |
| --- | --- | --- |
| 本地过、CI 慢机失败 | 等待条件不足、资源争抢 | 查 trace 中事件顺序，等待真实状态，控制并发预算 |
| 并行失败、单跑通过 | 共享账户/缓存/数据库 | 给数据加独立命名空间，检查全局状态清理 |
| 偶尔点不到或点错 | 动画、遮挡、脆弱选择器 | 看截图与 DOM，改语义定位和加载状态 |
| 特定日期或时区失败 | 系统时间、夏令时、随机种子 | 固定输入/时区，记录 seed，显式测边界 |
| 重跑重复创建订单 | 清理或幂等缺失 | 每次尝试独立数据，检查后端去重 |

失败报告应包含提交、依赖锁定信息、浏览器/系统版本、首跑与重试结果、测试数据 ID、截图、trace 和必要网络日志。trace 是动作及页面状态等诊断记录，不应只留最终截图；记录和上传前清除 token、个人信息与请求敏感正文。

限制重试次数可帮助收集间歇问题证据，但要单独统计首跑通过率和 flaky 数量。Playwright 重试涉及 worker 重建，不能假设内存 fixture 或 beforeAll 只运行一次。对不稳定测试的隔离必须有负责人、修复期限和替代风险覆盖；核心支付测试不能长期隔离后宣称发布安全。禁止无限重试直到绿，也不能把所有超时直接放大。

## 七、可访问性与视觉回归是互补维度

### 7.1 自动扫描不能代替实际操作

可访问性（Accessibility，a11y）关注不同能力用户能否理解并完成操作。axe 等自动扫描能发现一部分标签、语义和对比度问题，但无法完整判断阅读顺序是否合理、提示是否好理解或整段旅程能否使用屏幕阅读器完成。

组件层检查输入有 Label、错误与字段关联、按钮有名称；真实浏览器用 Tab/Shift+Tab 检查焦点顺序，用 Enter/Space 操作控件。对话框打开后焦点应进入合理位置，关闭后返回触发处，并检查 Esc、背景不可误操作等约定。再用目标平台的屏幕阅读器人工检查关键旅程。角色查询成功只证明可找到相应语义，不等于已经通过完整可访问性验收。

### 7.2 视觉基线是被评审的产品约定

视觉回归（Visual Regression）比较当前截图与基线，适合设计系统组件、响应式布局和关键页面。它能发现文字遮挡、布局位移或颜色变化，但不能证明按钮确实下单成功。功能断言、可访问性和视觉比较各自保留。

固定浏览器、操作系统/容器、viewport、设备缩放、字体、语言、时区和数据；等字体与图片加载，关闭或稳定动画，控制时间与随机内容。Playwright 的 `toHaveScreenshot` 可执行截图比较，但像素差异仍受运行环境影响，不能拿开发者 Mac 的基线直接要求 Linux 像素一致。

遮罩只应用于本来不需比较的动态区域，不能遮掉价格、错误提示等关键内容。差异阈值用来容忍合理渲染噪声，不能无限加大。更新基线必须让评审者看到前后差异并明确确认是预期设计变化；批量接受所有变化等于丢掉测试价值。

## 八、把风险检查接入 CI 与发布

CI（Continuous Integration，持续集成）要让反馈尽早到达能修复问题的人。下面是起点，不是必须等合并后才运行集成测试的规定。

| 阶段 | 建议检查 | 失败处理与约束 |
| --- | --- | --- |
| PR | Lint、类型、受影响单元与组件，关键集成/契约 | 必需检查阻止合并；接口改动立即触发契约 |
| 合并队列/主干 | 完整集成、契约和关键回归 | 尽量在合并前验证最终组合；主干失败阻止制品晋级 |
| Preview/预发布 | 真实部署的关键 E2E、视觉、浏览器组合 | 独立数据与沙箱第三方；评审视觉差异 |
| 生产 | 只读 Smoke、受控 Synthetic Monitoring | 验证路由与关键读取，告警并按预案回滚 |

Smoke 是快速确认基本能力，Synthetic Monitoring 是定期执行受控用户路径。生产探测应默认只读；必须写入的合成交易要有专用身份、明确清理和业务授权，不能污染真实报表。生产探测不取代上线前验证。

应尽量测试将要部署的同一制品，避免“测试后重新构建”引入不同依赖或环境变量。外部支付、短信等不可控服务在普通 CI 用沙箱/替身，另设有限真实集成验证其边界。CI 密钥仅授予必要权限，尤其不能把生产凭证暴露给不受信任的 PR。

缓存和分片可加快反馈，但缓存键要包含依赖、配置及相关输入；不能复用不适用的通过结果。衡量首跑通过率、关键风险覆盖、缺陷逃逸和反馈耗时，用实际瓶颈调整测试组合，不虚构通用性能收益。

## 九、面试回答与深入追问

### 9.1 “你会怎样设计前端测试体系？”

完整回答：先识别资金、权限、数据一致性等关键风险，再按边界分层。纯规则在单元层穷举边界，组件层验证输入与状态，集成层保留 Router、Store、客户端并在网络边界 Mock，契约层核对真实提供者，少量 E2E 验证登录、结账和部署接线。视觉与可访问性补用户体验维度。PR 给快反馈，高风险集成提前运行，预发布测试实际制品。失败要能用 trace、数据 ID 和日志定位，并治理首跑失败率。

追问“为什么不全用 E2E？”答：真实边界多，信心高，但组合爆炸、数据难维护且失败定位成本高。把规则穷举下沉、把跨边界证明留在 E2E，既降低成本又保留真实旅程证据。

### 9.2 “Mock 很多，测试还有意义吗？”

完整回答：意义取决于替换边界。Mock HTTP 可验证前端请求和响应处理，却不能证明后端可用；Mock 所有 Hook 和子组件可能掩盖接线错误。我会明确报告边界，用提供者契约验证 Mock 的协议与关键语义，再用真实系统测试覆盖认证、部署和持久化。

追问“共享 TypeScript 类型够吗？”答：不够，运行时 JSON、状态码和金额单位仍可能违反约定。要验证实际响应结构及语义，尤其是 null、枚举和错误响应。

### 9.3 “E2E 经常偶发失败，怎么解决？”

完整回答：保存首跑 trace、截图、网络和数据标识，按单跑/并行、日期、浏览器和机器资源缩小范围。用状态等待替换 sleep，修复语义定位、共享数据、未清理缓存与产品竞态；限制重试并单独统计 flaky。确需隔离时指定负责人和期限，核心风险留替代覆盖。

追问“重跑成功能发布吗？”答：不能只看最终绿；必须判断首次失败是否真实产品竞态、当前风险是否有证据控制。重试是诊断手段，不是正确性证明。

### 9.4 “覆盖率 95% 为什么还会线上出错？”

完整回答：覆盖率只说明执行位置，不证明断言强度和风险覆盖。测试可能没有验证结果，Mock 可能错误，生产配置可能不同，异步返回顺序也可能没覆盖。我会从事故不变量构造能复现的测试，选择最低有效层级，再补必要契约或真实部署验证，而不是只追更高百分比。

追问“什么时候用快照？”答：小而稳定、容易人工评审的输出适合；关键行为必须显式断言，不能靠巨大 DOM 快照替代。

### 9.5 “如何验证前端不会重复支付？”

完整回答：组件测试验证提交中禁止重复操作，集成测试验证超时和重试不会生成不同业务请求身份，服务端契约验证同幂等键不产生第二笔支付，E2E 在沙箱验证最终订单与交易一致。前端无法独自保证跨进程和网络失败下恰好一次。

追问“超时就是失败吗？”答：超时只说明调用方没及时拿到结果，远端可能成功。应通过幂等重试或状态查询确认，不能直接再创建一笔独立交易。

## 十、扫雷自测：答案与推理

1. **findBy 比 getBy 更好吗？** 不总是。当前同步应存在用 getBy，异步出现用 await findBy，缺失检查用 queryBy。所有查询都等待会掩盖错误时序并增加成本。
2. **waitFor 中点击直到成功是否可靠？** 不可靠，回调可重复执行，可能提交多次。动作执行一次，等待回调只检查预期结果。
3. **Context 隔离后还会串数据吗？** 会，它隔离浏览器存储，不隔离后端账户、购物车和数据库；需要独立业务数据。
4. **MSW 返回 200 能证明接口正常吗？** 只能证明前端处理该预设响应。真实服务是否兼容要提供者验证，部署网络还需真实边界测试。
5. **接口字段类型没变就兼容吗？** 不一定，单位、枚举语义、可空性、权限和错误码都可能变化。契约必须含业务含义。
6. **按钮禁用能保证没有重复订单吗？** 不能，多标签、刷新、超时重试仍可能重复；服务端需要幂等和去重。
7. **把超时从 5 秒调到 60 秒能修复 flaky 吗？** 若只是正常环境确实需要更长预算，合理调整有用；共享状态、错选择器和竞态不会因此消失，应先看证据。
8. **axe 扫描无违规就可访问吗？** 不能推出。自动规则覆盖有限，还要键盘、焦点和屏幕阅读器检查关键任务。
9. **视觉基线变了直接更新好吗？** 不好，要确认变化符合产品意图。否则测试会把真实布局缺陷接受为正确。
10. **每条 UI 测试都应真实登录吗？** 不必，专门测试登录流程，其余可复用受控认证 fixture。但必须说明跳过边界，保护认证状态，避免共享业务账户造成冲突。

## 十一、面试前速记与来源

- 先列风险与不变量，再选测试层级；工具不决定层级。
- 单元验证规则，组件验证交互，集成验证接线，契约验证约定，E2E 验证关键真实旅程。
- 用户可观察行为优先；语义定位、正确异步等待、独立数据是稳定性的基础。
- Mock 网络要防漂移；覆盖率不等于正确性；重试通过不等于问题消失。
- 可访问性、视觉和功能互补；CI 验证同一制品，失败有证据、有负责人。
