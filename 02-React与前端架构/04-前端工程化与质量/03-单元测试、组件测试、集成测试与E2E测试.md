# 03. 单元测试、组件测试、集成测试与 E2E 测试

## 测试层次

- Unit Test：Pure Function、Reducer、Domain Rule。
- Component Test：从用户视角验证单个 UI 组件。
- Integration Test：多个 Component、Router、Store、API Mock 协作。
- Contract Test：Frontend 与 Backend Schema/行为兼容。
- E2E：在真实 Browser 和接近生产的系统验证关键 Journey。

## 测试原则

测试可观察行为，而不是 Implementation Detail。优先通过 Role、Label、Text 查找元素，不依赖脆弱 CSS Class 或内部 State。

```tsx
expect(screen.getByRole('button', { name: /submit/i })).toBeEnabled();
```

## API Mock

在 Network Boundary 使用 MSW 类工具 Mock HTTP，比 Mock 内部 Hook 更接近真实行为。Contract Test 或 Schema Validation 防止 Mock 与 Backend 长期漂移。

## E2E

覆盖少量高价值 Journey：Login、Checkout、关键 Admin 操作。E2E 应控制测试数据、隔离账户、保存 Screenshot/Trace，并治理 Flaky Test。

Flaky Test 不应无限 Retry 后忽略。需要识别时间、共享状态、动画、网络和不稳定 Selector 等根因。

## Accessibility Test

自动 Axe Check 可以发现部分问题，但 Keyboard、Focus、Screen Reader 仍需人工与 Component-level 验证。

## Visual Regression

适合 Design System 和关键页面。需要稳定 Font、Viewport、数据和动画，变更由 Reviewer 明确接受。

## CI 策略

- Pull Request：快 Unit/Component/Lint/Type Check。
- Merge/Main：Integration/Contract。
- Deploy Preview：关键 E2E 和 Visual。
- Production：Smoke/Synthetic Monitoring。

## 常见错误

- 大量 Snapshot Test，无明确行为价值。
- Mock 所有 Child，测试只剩实现结构。
- E2E 覆盖一切，Pipeline 又慢又不稳定。
- 只追求 Coverage 百分比，不看风险。
- 测试环境与真实 API Contract 不一致。

## 总结

测试组合应按风险提供快速反馈。多数逻辑在低层验证，关键跨系统 Journey 用少量高层测试，并持续消除 Flakiness。
