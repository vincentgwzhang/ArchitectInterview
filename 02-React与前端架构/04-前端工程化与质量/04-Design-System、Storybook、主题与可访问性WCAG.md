# 04 Design System、Storybook、主题与可访问性（WCAG）

设计系统（Design System）是把设计原则、视觉变量、交互约定、代码、文档和维护责任连接起来的共享产品。它的价值是让多个团队稳定交付一致且可用的体验，而不只是减少几段 CSS。本文以 React Web 产品为例；WCAG 采用 2.2，Storybook 示例采用 CSF 对象形式，实际框架包与插件应按项目锁定版本配置。代码均为教学示例，未实际运行浏览器、Storybook 或辅助技术测试。

## 一、设计系统包含什么，什么时候值得建设

组件库（Component Library）交付 Button、Input 等代码；设计系统还回答：什么时候使用危险操作、如何写错误消息、键盘怎样操作、谁可以增加新变体、旧接口如何迁移。没有这些规则，团队即使使用同一组件，也可能形成完全不同的体验。

| 组成 | 解决的问题 | 具体交付 |
| --- | --- | --- |
| Design Principle，设计原则 | 冲突时优先什么 | 例如“优先清楚表达风险，再追求紧凑布局”及应用案例 |
| Token，设计变量 | 多品牌、主题和尺寸如何统一变化 | 颜色、间距、字排、动效的有意义名称和映射 |
| Accessible Component，可访问组件 | 基础交互是否可靠 | 输入、弹窗、按钮的语义、焦点、状态契约 |
| Pattern 与 Content Guideline | 多组件流程及文案如何一致 | 表单校验、空状态、删除确认、错误恢复规则 |
| Documentation | 使用者如何选型 | 适用与禁用场景、代码、状态、迁移说明 |
| Governance 与 Contribution | 谁维护、怎样演进 | Owner、提案、评审、发布、弃用与支持周期 |

例如删除订单，组件库只提供红色按钮；完整系统还规定文案包含对象名称、不可逆操作是否二次确认、失败时是否保留上下文以及焦点返回哪里。业务权限和事务仍属于业务服务，不能靠“隐藏删除按钮”实现授权。

多个产品反复实现同一交互、跨团队品牌漂移或可访问性缺陷重复出现时，共享平台可能有价值。单个短期原型可先采用成熟组件库与少量规则，避免为尚未存在的复用付出平台成本。选自建、封装现有库或直接使用时，应评估支持浏览器、无障碍能力、定制深度、许可、维护人力及升级路径；不能只比较组件数量。

## 二、Token：从原始值到产品语义

### 2.1 三层关系与命名

原始 Token 表示数值，例如蓝色某一色阶；语义 Token 表达用途，例如主要文字；组件 Token 则用于确有独立调节需求的按钮背景。产品引用语义而不是颜色值，才可以在不修改每个页面的情况下切换品牌和主题。

`color.text.primary` 表示主要文字，不等于“永远黑色”；`color.surface.danger` 表示危险区域表面，不能假设它适合作为文字颜色；`space.component.md` 表示约定间距，仍需说明用于内部 padding 还是组件之间 gap。命名必须有语义说明和允许组合，不能仅把所有十六进制颜色改成模糊英文。

```css
:root {
  --color-text-primary: #172033;
  --color-surface-default: #ffffff;
  --color-surface-danger: #ffe8e8;
  --space-component-md: 1rem;
}
[data-theme="dark"] {
  --color-text-primary: #f4f5f7;
  --color-surface-default: #151a23;
  --color-surface-danger: #482020;
}
.panel {
  color: var(--color-text-primary);
  background: var(--color-surface-default);
  padding: var(--space-component-md);
}
```

此例只展示主题映射，不声称所有颜色组合均通过对比度验收。新增语义 Token 之前先找相同用途，避免每个页面生成一套“语义”名称。组件层过细会增加维护映射成本；层次太少又会让品牌调整必须修改通用 Token，波及不相关场景。

### 2.2 主题、多品牌与设计代码同步

主题（Theme）是一组语义映射，不只是反转颜色。需要覆盖边框、图标、禁用、悬浮、聚焦、阴影、图表和图片背景。深色主题的文字对比度通过，也不代表错误边框和焦点环可见。字号、行高与字体回退还会改变换行和布局，要测长内容和不同语言。

主题决策通常是“用户显式选择优先，否则跟随系统偏好”，并持久化允许的主题标识。服务端渲染应尽量在首屏使用正确主题，避免亮色闪烁及服务端与客户端输出不一致；读取存储失败要有默认值，不能阻断页面。CSS 变量随 DOM 祖先继承，React Portal 若挂到主题容器外，弹窗可能失去主题，需在合适根节点应用主题或显式传递。

跨 Figma 与代码同步必须指定唯一受治理来源。可以从受版本管理的数据生成 CSS、类型和设计资源，也可以采用设计工具导出后经代码评审；不能两边同时无约束编辑。生成时检查重复名称、缺失引用、循环别名和不支持的值，发布包含变更说明。改 Token 名称是消费者接口变化；即使只改数值，也可能导致文字溢出或视觉回归，所以需要评审而不是视为无风险补丁。

## 三、Component API：默认可靠，扩展有边界

### 3.1 有限变体与组合

变体（Variant）表达有限产品意图，例如 primary、secondary、danger。大量布尔参数如 primary、danger、quiet 同时为 true 会产生未定义组合，应改成互斥枚举。尺寸、状态和意图是不同维度，需说明哪些组合支持，而不是生成所有笛卡尔积。

组合（Composition）把标题、正文、操作区等组织成可复用部分，适合内容变化多但交互模型稳定的场景。它不是任意替换底层元素的理由：把按钮渲染成链接，键盘和导航语义就变了。导航用链接，执行动作用按钮；表单内非提交按钮应明确 type="button"，避免意外提交。

逃生口（Escape Hatch）可提供 className 或有限样式变量，但需约定不能移除可见焦点、覆盖可读颜色或破坏禁用行为。允许每个产品覆写内部 DOM 和任意 CSS，会把组件升级变成兼容所有历史覆盖的负担。真正不同的领域交互可保留业务组件，不必强塞入全局系统。

### 3.2 受控与非受控契约

受控（Controlled）组件由父级通过 value/open 决定状态，并通过 onChange/onOpenChange 请求变更；非受控（Uncontrolled）组件内部持有状态，defaultValue/defaultOpen 只定义初始状态。不要运行中切换模式，也不要让内外两份状态竞争。

例如受控弹窗点击关闭应通知父级，父级更新 open 后才关闭；若内部私自关闭但父级仍为 true，下次渲染可能再次打开。异步保存过程中是否允许关闭、关闭是否丢弃草稿，应由业务流程明确；通用弹窗只提供能力和可预测事件，不能默认替所有产品决定。

加载（Loading）和禁用（Disabled）也不同：加载表示正在处理，禁用表示当前不能操作。原生 disabled 通常使按钮不能聚焦；aria-disabled 只表达状态，不会自动阻止点击，使用者必须实现阻止逻辑。保留可感知的加载提示，不能只让图标旋转。前端禁止重复点击也不替代服务端幂等。

### 3.3 输入控件的最小语义示例

```html
<label for="email">电子邮箱</label>
<input id="email" name="email" type="email"
       aria-invalid="true" aria-describedby="email-help email-error">
<p id="email-help">用于接收订单通知。</p>
<p id="email-error">邮箱格式不正确，例如 name@example.com。</p>
```

Label 给输入提供名称；describedby 关联补充说明和错误；invalid 表达当前校验失败，但不会自动显示或朗读所有错误。动态提交错误还需设计状态通知及焦点策略，例如聚焦错误摘要并链接至字段，避免每次输入都打断读屏。多个实例必须生成不同 ID；复制示例而不改 ID 会把 Label 关联到错误控件。此例展示错误态，正常态应清除 invalid 和不存在的错误引用。

## 四、Storybook：把状态变成可评审的实例

Story 是某组输入和环境下的组件状态。Args 表达属性，Decorator 提供主题、路由等外部上下文，交互脚本执行用户操作并检查结果。隔离环境可以快速复现缺陷、讨论设计和运行视觉回归，但不会自动覆盖真实登录、权限、网络和生产 CSS。

以下为 CSF 对象示例，假设项目已经配置 React Storybook，Button 接受相应属性。不同构建适配器的类型导入不同，这里不省略项目依赖却假装可独立运行。

```js
import { Button } from './Button';

export default {
  title: 'Actions/Button',
  component: Button,
  args: { children: '保存', variant: 'primary' },
};

export const Default = {};
export const Loading = { args: { loading: true } };
export const LongContent = {
  args: { children: '保存并提交当前所有已验证的修改' },
};
```

只有故事存在不等于测试通过。交互测试应实际输入、点击并检查可见状态，视觉比较应有受评审基线，可访问性扫描应记录规则与结果。Storybook 的控制面板方便探索，却不能代替受版本管理的边界用例。

| 场景 | 要验证的风险 |
| --- | --- |
| Default 与不同 Variant | 意图、尺寸和语义一致 |
| Loading、Empty、Error | 布局稳定、错误可恢复、状态可感知 |
| Long Content 与不同语言 | 换行、按钮尺寸、截断后信息可得 |
| Keyboard 与 Focus | 顺序、操作键、可见焦点与退出 |
| 不同 Theme、缩放和窄视口 | 对比度、重排、弹层主题继承 |

不要穷举无意义组合；按风险选择代表状态，对复杂控件重点覆盖交互转换。隔离故事要声明替身和限制，并保留真实应用集成测试。例如 Story 中正常的弹窗，在生产被祖先 overflow、层叠上下文或主题 Portal 位置影响，仍可能不可用。

视觉比较固定字体、浏览器、操作系统、数据、视口与动画；差异须由评审者判断是否预期。CI 可以构建 Storybook 并运行组件交互、自动扫描与关键截图，但发布出去的 Storybook 不应含生产 token、客户数据或敏感内部链接。

## 五、WCAG：从原则到能完成的用户任务

### 5.1 POUR 与一致性等级

WCAG 是 Web 内容可访问性指南，成功准则按 A、AA、AAA 等级组织；达到 AA 需要满足适用的 A 和 AA 准则，而不是挑选几个 AA 检查。本文使用 2.2，不能把组件扫描通过表述为整站符合 WCAG。

POUR 是四个原则：可感知（Perceivable）要求信息不依赖单一感官，例如图片替代文本、视频字幕；可操作（Operable）要求键盘等方式能完成任务且不陷入操作死角；可理解（Understandable）要求标签、错误和流程可预测；健壮（Robust）要求语义能被浏览器和辅助技术可靠解释。原则必须落到完整用户旅程：按钮本身可访问，但提交后错误没有通知，任务仍可能失败。

优先使用原生 button、input、select 与合适的 dialog 能力，浏览器已提供很多语义和键盘行为。ARIA 是向可访问性树表达角色、状态和关系的属性，不会替 div 自动实现 Enter、Space、焦点管理或提交。错误 ARIA 反而可能覆盖正确原生语义。

### 5.2 键盘、焦点与弹窗

Tab/Shift+Tab 按合理顺序移动焦点，Enter/Space 按控件语义激活；复合控件如菜单或标签页可能使用方向键，不应把所有内部元素都塞进 Tab 序列。不要用正 tabindex 人工重排整页，否则 DOM 阅读顺序与视觉、键盘顺序容易分裂。焦点环不能简单 outline:none；固定顶部栏、浮层也不应让当前焦点完全被遮挡。

模态弹窗（Modal Dialog）打开后使背景不可交互，并将焦点放到弹窗内合理位置；Tab 在内部循环，Escape 通常关闭，关闭后返回触发控件或合理后继。长文本弹窗可先聚焦标题等静态位置，避免焦点跳到末尾导致开头内容不可见；危险确认可优先选择非破坏性操作。

原生 dialog 的 showModal 模式可提供背景隔离等浏览器能力，但仍需可访问名称、恰当初始焦点、明确关闭操作及目标浏览器验证。非原生实现还要管理背景 inert、滚动锁定、嵌套弹层和焦点恢复；只加 aria-modal="true" 不能实现模态行为。触发按钮被删除时，恢复焦点应选后继任务位置，不能盲目 focus 一个已卸载节点。

### 5.3 对比度、颜色与动效

颜色对比基于前景与背景相对亮度，不是设计者肉眼认为“够深”。WCAG 2.2 AA 中普通文本通常要求至少 4.5:1，大文本至少 3:1；大文本约为 18pt，或 14pt 粗体，不能把 CSS 18px 当成 18pt。必要的控件视觉边界和状态等非文本内容也有相应对比要求与例外，不能把文本阈值直接套给所有像素。

对每个实际主题和状态检查组合，特别是透明色叠加、渐变和图片背景。错误不能只靠红色，可同时给文字和图标；链接不能只靠难分辨颜色与正文区分。禁用控件存在准则例外，不代表产品可以故意让用户看不懂为什么不能操作。

Reduced Motion 表示用户偏好减少非必要动效。可通过 prefers-reduced-motion 调整动画，保留必要状态反馈而移除大幅位移和视差。不要全局设置极短动画却让依赖 animationend 的业务逻辑失效；交互状态应独立于视觉动画完成事件。尊重偏好只是部分工作，闪烁、自动播放和时间限制等仍需按具体内容审查。

### 5.4 验证方法与故障定位

自动检查适合捕获一部分缺少名称、错误属性和可计算对比问题；不能判断替代文本是否准确、焦点策略是否合理或真实用户能否完成订单。采用三层证据：组件自动扫描与交互测试、人工键盘/缩放/主题检查、目标浏览器加屏幕阅读器的关键任务测试。

排查“读屏没有正确读字段”时先检查 DOM 的 label/ID 和可访问名称，再检查隐藏、描述引用和动态更新，最后看目标辅助技术组合；不要先追加更多 role。排查“键盘卡住”时重现弹层开关与卸载，记录当前 activeElement，检查背景隔离及事件清理。报告应注明浏览器、辅助技术版本、步骤、预期和实际结果，避免只写“无障碍有问题”。

## 六、治理、版本与渐进演进

Owner 负责维护优先级和兼容性，不等于所有设计都由一人决定。贡献 RFC 是在新增能力前说明问题、使用场景、替代方案、API、可访问性及迁移成本的提案。先在真实产品验证，再提升为共享能力，避免把一次性业务需求泛化成复杂公共接口。

版本化需要把代码、Token、文档和设计资产对应起来。弃用（Deprecation）先说明替代项和支持期限，保留兼容窗口；迁移工具可处理属性改名或 import，但焦点、视觉和行为变化仍需人工验证。修复可访问性可能改变 DOM 或键盘行为，不能只因“修 Bug”就忽略消费者影响。

推广可先选高复用按钮、输入和反馈组件，再覆盖复杂模式。存量页面逐步迁移，不必一次重写；通过适配层保持短期兼容，但给适配层退出日期。Monorepo 可方便联动修改，独立包可支持不同升级节奏，两者都需要版本依赖、兼容测试和明确责任。

衡量价值时看真实采用率、重复实现减少、可访问性缺陷、升级滞后和交付反馈时间。下载数不等于生产使用；交付变快也可能来自人员或需求变化，不能全部归因设计系统。持续收集实际用户反馈，尤其是辅助技术使用者，防止只优化组件目录而没有改善任务成功率。

## 七、面试完整回答与追问

**问：设计系统和组件库有什么不同？**

答：组件库交付可复用代码，设计系统还交付设计原则、语义 Token、交互与文案模式、文档和治理。以删除确认举例，不仅是一个红按钮，还要明确风险文案、焦点、错误恢复与弃用升级。建设范围按重复成本和团队数量决定，原型可先用成熟库，避免平台投入超过收益。

追问“如何防止成为瓶颈？”答：中央 Owner 维护基础契约，产品团队通过有模板的提案贡献；常见需求优先，特殊领域保留本地组件，提供受约束扩展口，并用反馈时间与采用率调整流程。

**问：如何实现多品牌和深色模式？**

答：产品引用语义 Token，主题和品牌映射到实际值，组件只在必要时增加自身 Token。明确设计与代码来源和版本，验证全部交互状态、对比度与布局。首屏主题应与服务端输出一致，Portal 弹层也必须继承正确主题。

追问“换一套颜色为什么还会出问题？”答：字体与间距会改变换行，透明叠加改变对比度，弹窗可能位于主题外；需要真实组合测试，不能只看色板。

**问：怎样证明组件默认可访问？**

答：先选正确原生元素，定义名称、键盘、焦点、状态与错误契约；用自动扫描及交互测试验证，再在真实浏览器和辅助技术中完成关键任务。文档明确使用方责任，例如必须提供有意义的标签。组件合格并不保证整页流程符合 WCAG。

追问“ARIA 能修复 div 按钮吗？”答：role 只表达语义，还需要焦点与键盘激活等行为，因此通常直接用 button 更可靠且维护成本低。

**问：Storybook 能代替 E2E 吗？**

答：不能。Storybook 擅长隔离状态、文档、组件交互与视觉反馈，真实应用还存在路由、认证、CSS、后端和部署边界。应复用代表故事降低反馈成本，再用少量真实旅程验证集成。

追问“视觉变化怎样发布？”答：固定运行环境，评审差异确认符合产品意图，必要时提供迁移说明，不能批量更新基线直到流水线变绿。

## 八、扫雷自测与速记

1. **语义 Token 就是给色值起名字吗？** 不是。名称必须表达用途和允许组合，否则无法独立改变主题，且易产生同名不同义。
2. **defaultOpen 后续改变必须同步内部状态吗？** 通常不是，它定义初始值。需要父级持续控制时使用 open 和变更回调，避免双重真相。
3. **aria-disabled 能阻止点击吗？** 不能，它表达状态；仍需阻止动作。原生 disabled 与焦点行为不同，选择要结合可理解性。
4. **弹窗设 aria-modal 就能困住焦点吗？** 不能，需真实模态、背景隔离和焦点管理。ARIA 不执行这些行为。
5. **焦点总返回触发按钮吗？** 一般如此，但按钮已删除或流程进入下一步时应选择合理后继，不能返回无效节点。
6. **4.5:1 是否适用于全部 UI？** 不是，它主要是普通文本 AA 阈值；大文本和非文本有不同要求及例外，必须按准则与实际状态判断。
7. **Story 默认态通过足够吗？** 不够，loading、error、长内容、键盘和主题可能暴露完全不同的问题，需按风险覆盖。
8. **自动扫描全绿能宣布整站符合 WCAG 吗？** 不能，它只验证部分可自动化规则；完整页面和流程需要人工与辅助技术证据。
9. **Token 值变化没有 API 改动就无风险吗？** 有风险，可能改变对比、换行和布局，应评审并做关键视觉验证。
10. **Reduced Motion 就是删除全部状态反馈吗？** 不是，减少非必要运动仍要让用户知道操作进行中与完成，不能依赖动画结束驱动业务正确性。

速记：设计系统是共享产品；Token 表达意图；组件 API 控制组合和状态责任；Storybook 固化可评审状态；原生语义优先，ARIA 不执行行为；可访问性验证完整任务；版本、贡献、迁移与用户反馈决定长期价值。
