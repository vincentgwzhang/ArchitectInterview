# 03 缓存策略、CDN、资源压缩与图片优化

## 一、缓存首先是正确性与责任设计

缓存（Cache）保存先前计算或获取的结果，用空间与允许的陈旧时间换取延迟、吞吐和源站成本收益。必须先回答：谁能复用，最多旧多久，何时失效，由谁负责。命中率高但把甲用户账单返回给乙用户，是安全事故；库存显示很快但过旧，可能破坏交易体验。

浏览器HTTP缓存、CDN边缘缓存、反向代理、应用缓存和数据库可能依次参与请求，但实际不一定每次都穿过所有层。浏览器命中时不会到CDN；应用命中时不查数据库。每层需定义Owner、TTL（Time To Live，存活时间）、键、失效、隐私及观测。Service Worker或前端数据缓存还可能独立保存结果，不能认为修改HTTP头就自动清除所有客户端状态。

建议先按数据分类：内容哈希静态资源可长期复用；公共商品说明允许有限陈旧；个人账户只允许受控私有存储；支付授权、余额和敏感信息应优先正确性及明确禁止存储策略。缓存不是数据库的另一个权威副本，写入最终判断仍应在服务端权威系统执行。

本文HTTP语义依据RFC 9111及相关扩展，核验日期2026-11-24。CDN产品是否遵守或覆盖源站指令、如何归一化键、如何执行Purge必须以实际配置和测试为准，不能把厂商默认值当HTTP标准。

## 二、HTTP缓存：存储、新鲜和验证是三件事

### 2.1 先理解指令

| 响应指令 | 主要含义 | 适用与误区 |
| --- | --- | --- |
| max-age=N | 在相应年龄范围内可视为新鲜 | 不是从每次边缘命中重新计时；还需考虑Age等年龄信息 |
| s-maxage=N | 共享缓存的新鲜期，覆盖共享缓存的max-age等相应设置 | 不控制浏览器私有缓存；也不代表可安全缓存所有用户内容 |
| private | 不允许共享缓存存储该响应，私有缓存可以 | 不加密内容，也不代表禁止浏览器存储 |
| public | 显式允许共享缓存，仍受其他条件约束 | 不是安全认证，不能对个人页面盲目添加 |
| no-cache | 允许存储，但复用前需要成功验证 | 不是“不存储” |
| no-store | 不应存储这次请求或响应的相应内容 | 不是清除已经存下的所有副本的远程命令 |
| must-revalidate | 过期后不得无验证复用 | 不是每次新鲜命中都回源 |
| immutable | 在新鲜期内表示内容不会改变，减少不必要验证 | 只适合URL与内容不可变的约定，不能替代版本发布 |
| stale-while-revalidate=N | 在允许窗口内可先用过期内容，同时验证更新 | 不承诺持续后台定时刷新，也不是无限期陈旧许可 |

新鲜度与业务正确性不同。缓存里“新鲜”的商品价格可能在数据库中刚被修改，只是它仍处于协议允许的复用窗口。必须由业务接受这个窗口，而不是把max-age当作强一致承诺。

响应未明确禁止缓存时，部分响应可能被启发式缓存，因此敏感接口应明确发出策略。历史页面恢复、浏览器前进后退缓存与应用内状态也不完全等同于HTTP重新请求；退出登录后应同时处理私有界面状态，不能只依赖no-cache。

### 2.2 条件请求与304

验证器（Validator）用于确认缓存表示是否仍可用。ETag是源站给表示的标签；If-None-Match让客户端询问标签是否仍匹配。Last-Modified给出修改时间，If-Modified-Since用于基于时间验证，精度和生成方式会影响可靠性。两类条件同时出现时，按HTTP条件规则处理，不能让较粗的修改时间覆盖更准确的标签判断。

例如公开说明文档第一次返回200、ETag和正文。下次需要验证时带旧标签；未修改则返回304 Not Modified，无新正文，缓存继续使用已有正文并按响应更新元数据；已修改则返回200和新表示。304仍有网络往返与服务端验证成本，只省传输正文，不等于完全离线命中。

```http
GET /help/shipping HTTP/1.1
Host: example.com
If-None-Match: "shipping-v7"

HTTP/1.1 304 Not Modified
ETag: "shipping-v7"
Cache-Control: public, max-age=60
```

这是教学用请求/响应对，不是同一个HTTP报文。ETag可以是版本标识，不要求一定是文件MD5；强标签与弱标签的比较规则不同，涉及范围请求或写入条件时不能混用。带不同内容编码的表示需保持验证器与表示语义一致，压缩层不能随意照搬不再成立的强标签。

## 三、静态资源与HTML采用不同策略

内容哈希路径如app.a1b2c3.js应保证同一路径永不覆盖成另一份内容，适合：

```http
Cache-Control: public, max-age=31536000, immutable
```

这表示一年新鲜期，不是浏览器一定保存一年：容量淘汰、用户操作等仍可能移除它。前提是文件可以公开共享，且变更会产生新URL。没有版本的app.js若使用同样策略，修复后用户可能仍用旧代码，源站新增头无法主动召回尚未发请求的浏览器。

HTML通常更快验证或短期缓存，使用户发现新资源引用。公共站点可用no-cache配合ETag；允许短暂延迟时也可使用明确的短TTL。个性化HTML不能仅因它是HTML就进入公共CDN缓存，应采用private或更严格的no-store，并在边缘配置相应绕过规则。

发布顺序是先上传完整不可变资源，再切换HTML或清单。旧页面可能稍后请求旧懒加载Chunk，因此保留旧资源覆盖长会话、缓存和回滚窗口。回滚恢复旧HTML引用，不应要求覆盖已经发布的哈希文件。只Purge CDN不能清除用户的浏览器缓存，也不会撤销已经执行的JavaScript。

版本化URL把“修改同一对象”变成“引用新对象”，降低静态资源一致性难度，但存储与清理仍有成本。业务数据不断变化，不能总靠无限生成URL替代有界缓存设计。

## 四、API缓存键与隐私隔离

### 4.1 键决定谁会共享什么

缓存键（Cache Key）决定两个请求是否被视作同一个表示。通常涉及方法、目标URI及Vary选出的请求字段；CDN还可能按自定义规则纳入或忽略查询参数、Header、Cookie。源站Vary表达响应选择维度，不保证任意CDN自定义配置都会自动正确落实。

语言、租户、区域、实验组和权限可能改变响应。例如同一个/products地址按Accept-Language生成内容，可用相应Vary或显式语言路径区分。不能把所有Cookie原样放入键：会产生海量低复用变体，甚至在日志中暴露敏感信息。应把影响公共内容的有限维度映射为受控值，不影响内容的追踪参数可在确认语义一致后归一化。

键太粗会串数据；键太细会降低命中率并增加存储。归一化必须与源站语义一致，不能随意丢弃重复参数、大小写或排序信息。攻击者若能用未计入键的Header改变响应并使之缓存，就可能形成缓存投毒（Cache Poisoning）：后续正常用户命中攻击者影响的表示。防护重点是统一解析、验证输入和完整覆盖实际变体。

### 4.2 身份信息不是自动保护伞

带Authorization的请求在共享缓存中有特别限制，但某些显式响应指令可以允许共享复用。因此“有Token就绝不会缓存”不成立。Cookie或Set-Cookie也不能被当作所有缓存产品通用的禁止存储保证。对账户等私有响应，应明确private或no-store、边缘绕过，并测试两用户交叉请求。

把用户ID加入共享键并不自动安全：还要保证身份校验、键不可伪造、权限撤销及数据生命周期正确。多数个人数据没有必要用公共边缘缓存承担这些复杂性，浏览器私有缓存或服务端按用户隔离的应用缓存往往更容易治理。

缓存命中不能跳过资源授权。签名URL允许在限定时间与范围内访问资源，是一种持有即有访问能力的凭证；不能出现在公开日志或不受控分享中。若CDN在验签前直接命中返回，或忽略签名参数却没有独立授权步骤，就可能泄露资源。

### 4.3 示例：公共数据与私有数据

公共目录可以采用浏览器短TTL与共享缓存较长TTL，前提是所有命中用户应看到同一内容；例如max-age=30、s-maxage=120表达不同缓存层的预算。CDN已保存90秒后给浏览器的响应携带年龄信息，浏览器不能把它当成刚生成并再无条件使用完整30秒。

账户账单则可采用Cache-Control: no-store，不给它配置公共缓存覆盖。允许本机短暂复用的低敏感个人偏好可考虑private配合显式新鲜度；两者必须根据威胁模型和产品需求选择，而不是统一给所有API套一个头。

## 五、CDN：距离、回源与成本治理

CDN（Content Delivery Network）把内容放到靠近用户的边缘节点，命中可减少距离与源站工作；未命中仍需回源，还可能增加一段代理路径。低流量、极高变体的内容不一定取得高收益，因此要按区域和资源类别观察。

源站保护（Origin Protection）包括限制直接访问、校验边缘到源站的可信连接、速率与并发控制。源站屏蔽层或Origin Shield可合并多边缘回源；请求合并（Request Coalescing）让同一未命中对象的并发请求共享一次加载，防止热点到期时大量请求同时压数据库。缓存只是缓冲层，不等同源站容量规划或完整DDoS防护。

Purge/Invalidation用于主动移除或标记边缘副本，可能按URL、标签或范围执行。全球传播、速率限制和失败重试是产品相关行为，必须记录完成状态并验证多个区域，不能把API返回成功理解为所有节点瞬时一致。预热要有界，避免Purge之后集中回源。

签名URL适合单资源临时访问，签名Cookie可在产品支持时覆盖一组资源；过期、续签、撤销和密钥轮换需要单独设计。权限验证要发生在可返回缓存内容之前，不能只在首次回源时检查。私有对象是否可在边缘内部复用取决于产品能力和安全设计，不应照搬公共资源方案。

地区限制不仅关乎访问速度，还涉及数据存放、日志和处理位置，需按实际业务要求配置并核实服务能力。源站故障切换（Origin Failover）要检查备用站数据、身份和证书是否一致，明确哪些请求可以重试；GET故障切换不能被推导为支付POST可随意重放。

CDN费用包括流量出口（Egress）、请求、存储、图片转换、日志和Purge等。请求命中率与字节命中率不同：缓存很多小图可能请求命中高，但少数大视频仍占大部分出口。需要将成本与真实用户延迟、回源流量一起评估，而不是单看总命中百分比。

## 六、失效、陈旧窗口与并发失败

业务数据采用TTL、事件失效或重新验证，选择取决于可接受陈旧度和更新频率。TTL简单，代价是窗口内可能旧；事件失效更及时，却有消息延迟、漏发、重复与乱序；验证节省正文传输，但增加往返和验证负载。组合使用时仍需一个明确上限，不能让每层各自“短暂陈旧”叠出无法解释的结果。

stale-while-revalidate允许在规定的过期窗口内返回旧内容并触发验证，适合可容忍短暂旧数据的公共内容。它不是每隔N秒自动刷新的计划任务，也不适合余额授权等严格场景。支持与交互规则需验证，尤其不能把no-cache等更严格要求与其他扩展随意拼接后假定一定允许旧内容。

失效存在竞态：读请求先读取数据库旧值；写请求提交新值并删除缓存；旧读稍后又填回旧值。简单“写后删缓存”并不在所有并发情况下强一致。可用版本号约束回填、可靠事件及受控TTL限制影响；要求严格读写一致时，应在权威读取路径中实现，而不是宣称缓存失效具有事务原子性。

热点同时到期可造成缓存击穿或惊群。按键合并加载、TTL加入抖动、控制并发和有界重试可平滑流量；但合并等待也要有超时和失败传播，不能一个卡住的加载让所有请求永久等待。对不存在对象缓存短期“未找到”可减少穿透，但创建对象后应失效负缓存，且不应把临时鉴权失败当成所有用户共享的404。

错误时能否返回旧数据需按业务类别决定，并定义最大陈旧时间、用户提示和观测。无法获得可信状态时，订单可显示“暂无法确认，请稍后查询”，不能把旧状态当成最新支付结论。Purge是运维动作，业务一致性协议不能只依靠人工点击。

## 七、资源压缩：传输格式与CPU的平衡

文本HTML、CSS、JS和JSON通常适合Brotli（br）或Gzip。浏览器通过Accept-Encoding表达支持，服务端或CDN选择表示并通过Content-Encoding标明；协商产生的变体应正确区分，通常需要Vary: Accept-Encoding或经过验证的CDN等价机制，防止给不支持的客户端返回错误编码。

压缩有损与无损要区分：HTTP文本压缩通常无损，解压后相同；图片重新编码可能有损，需验证视觉质量。JPEG、AVIF和视频已经使用压缩，外层再Gzip往往收益有限甚至增加开销。不能把所有二进制统一套最高等级压缩。

预生成静态br/gzip产物可把CPU成本移到构建阶段，运行时按能力选择；动态JSON可在服务端或边缘按阈值与等级压缩。源站已经压缩时，下一层应理解Content-Encoding，避免重复处理或错误标记；若中间层解压再转换，要同步处理长度、验证器和缓存变体。

高压缩等级可能降低字节却增加首字节等待和服务器CPU，最佳选择需在目标负载下测量。不要给出脱离内容的固定节省比例。测试至少对比压缩大小、压缩耗时、用户TTFB、CPU及缓存命中，并验证不支持br的客户端能获得可解码表示。

## 八、图片：尺寸、格式与加载时机一起设计

### 8.1 响应式资源不是CSS缩小原图

把4000像素图片用CSS显示成300像素仍可能下载整张大图。srcset列候选宽度，sizes描述布局占用宽度，浏览器结合屏幕密度等条件选择资源；width/height给出固有比例，避免图片到达后推挤布局。sizes写错会让浏览器选择不合适的候选。

picture可提供格式回退或艺术裁剪（Art Direction），例如手机显示不同构图。AVIF/WebP的体积、编码与解码成本、透明度和视觉质量需按内容验证；不支持时应能选到普通img资源。下面假定所有候选比例2:1，桌面显示宽度不超过640像素：

```html
<picture>
  <source type="image/avif"
          srcset="/img/hero-640.avif 640w, /img/hero-1280.avif 1280w"
          sizes="(max-width: 640px) 100vw, 640px">
  <source type="image/webp"
          srcset="/img/hero-640.webp 640w, /img/hero-1280.webp 1280w"
          sizes="(max-width: 640px) 100vw, 640px">
  <img src="/img/hero-1280.jpg"
       srcset="/img/hero-640.jpg 640w, /img/hero-1280.jpg 1280w"
       sizes="(max-width: 640px) 100vw, 640px"
       width="1280" height="640"
       fetchpriority="high" alt="商品系列展示"
       style="width:100%;max-width:640px;height:auto">
</picture>
```

该例假设是首屏最大内容图片，因此不懒加载。非首屏图可使用loading="lazy"，并保留尺寸；所有图高优先级或所有图懒加载都会丧失按关键路径调度的意义。缓存命中也不代表解码和显示免费，应关注像素量、内存与实际绘制。

### 8.2 Image CDN与上传管线

图片CDN可以按受控参数Resize、裁剪、调质量和转换格式，再缓存变体。键应包含源图版本及有效转换参数；宽度应限制为有限档位，避免任意w参数造成几百万低命中变体和转换费用。格式自动协商时也要正确区分Accept相关变体。

上传入口应限制文件字节、像素、格式和处理时间，检查实际内容而不只信扩展名。很小的压缩文件也可能解码为巨大像素矩阵，造成内存耗尽。转换在隔离、有界资源的管线执行，生成缩略图与展示尺寸，记录失败并提供安全占位，不在每次页面请求中同步重算原图。

按需要移除EXIF等元数据，避免泄露拍摄位置，并正确处理方向与颜色。若支持从远程URL取图，要限制来源、跳转与可访问网络，防止服务端请求伪造（SSRF）访问内部系统。原图权限和派生图权限应一致，不能公开缩略图绕过私有相册访问控制。

## 九、监控、验证与排障场景

监控至少关联资源类型、路由模板、地区、版本和缓存状态。观察CDN请求/字节命中率、Origin RPS、TTFB、出口字节与费用、Purge错误及资源尺寸分布；不要把带Token或个人参数的完整URL直接写入日志。各层命中率的分母不同，浏览器命中的请求不会出现在CDN日志中。

虚构场景一：图片CDN命中率低。先检查是否跟踪参数或任意尺寸导致键爆炸，再检查TTL、格式与源图版本是否正确；不能先丢掉所有查询参数，因为裁剪与签名可能正依赖它们。归一化后对同一表示验证命中提升，并确认不同尺寸、身份和格式没有串用。

虚构场景二：发布后有人看不到新样式。检查HTML是否仍引用旧Hash，资源是否被同URL覆盖，浏览器、CDN、Service Worker和应用状态谁在复用。只清本机缓存能暂时恢复，不证明全体用户已恢复。修复应回到版本与更新协议，并验证旧标签页及回滚。

虚构场景三：缓存后出现用户信息串用。立即停止受影响共享缓存规则并阻止继续返回，识别响应与变体并执行受控失效，按事故流程调查暴露范围。修复后用两名用户交替请求、权限变化及不同Cookie/Authorization组合验证，不能只检查一个匿名请求的头。

验证可用浏览器Network查看状态、Age、验证请求与实际响应内容；命令行可比较Accept-Encoding和条件请求，但不等价于完整浏览器缓存生命周期测试。关闭浏览器缓存只适合冷请求诊断，不应拿它证明缓存策略没有效果。验收同时覆盖冷/热、过期/未过期、200/304、不同身份、失效失败和源站故障，最终看用户性能与成本是否同步改善。

## 十、面试完整回答与深入追问

### 1. 怎样设计网站缓存？

答：先按公开性、变化频率和最大陈旧度分类，再分别设计浏览器、CDN和应用层键、TTL与Owner。哈希静态资源长期缓存，HTML及时发现新版本，私有响应明确禁止共享，业务数据用有界TTL、验证或可靠失效。最后验证双用户隔离、旧会话、故障和成本，而不是给所有响应统一加一年缓存。

追问：no-cache和no-store有什么差别？答：前者允许存储但复用前须验证，后者是不应存储。二者都不是召回已经散落所有副本的万能命令，历史恢复和应用缓存还需独立处理。

### 2. 304是否比200一定快？

答：304不传新正文，适合表示没变时节省流量，但仍需网络与验证处理。新鲜缓存本地命中可能更快；如果每次验证都查昂贵数据库，服务端压力仍高。需要看验证器生成成本、往返与正文大小，不能只比较状态码。

追问：ETag必须是MD5吗？答：不需要，它是表示验证标签，可按版本生成；必须稳定反映相应表示变化，强弱标签与编码变体要正确处理。

### 3. 为什么有Cookie仍可能泄露缓存数据？

答：缓存行为由协议、响应头和产品配置共同决定，Cookie本身不是普遍禁止缓存保证。若响应随身份变化而键未区分，公共缓存可能复用给别人。我优先让个人响应private或no-store并在边缘绕过，对确需受控缓存的内容，在返回之前完成授权与隔离测试。

追问：把Token放键里就够了吗？答：不够，还涉及凭证暴露、权限撤销、TTL和高基数；身份键不是授权机制，也不应为了命中率接受泄漏风险。

### 4. 如何兼顾CDN性能、可靠性与成本？

答：按地区和资源看延迟、回源、请求及字节命中与出口费用，归一化不影响语义的键，限制图片变体，并保护源站。Purge和故障切换要演练，保留旧版本支撑会话与回滚。性能收益要与转换、存储、日志和运维费用一起计算。

追问：所有接口都故障返回旧值是否可用性最高？答：这取决于业务。商品描述可有限陈旧，支付授权不能用旧值伪装当前事实。应定义上限和失败体验，正确性也是可用性的组成部分。

## 十一、扫雷自测与推理答案

1. **一年max-age是否保证缓存保存一年？** 不保证。它规定新鲜度上限，缓存仍可能因容量或用户操作提前淘汰。
2. **no-cache是否禁止落盘？** 不是。它要求复用前验证，禁止存储应采用no-store并考虑其他应用存储。
3. **Purge CDN能清浏览器吗？** 不能。两者是不同层，版本化URL与HTML更新才使新请求引用新资源。
4. **s-maxage是否决定浏览器多久缓存？** 不决定，它针对共享缓存，浏览器仍按适用的私有缓存规则处理。
5. **带Authorization是否绝不会被共享？** 不可这样断言。显式响应许可等条件可改变共享规则，私有接口必须明确策略和实际验证。
6. **高命中率是否一定低出口费用？** 不一定。很多小对象命中而少数大对象不命中时，请求命中好看，字节出口仍高，且边缘向用户传输本身也可能计费。
7. **重复压缩JPEG通常值得吗？** 通常收益有限，因为内部已压缩，还会消耗CPU；需要实际比较而非一律启用。
8. **CSS缩小原图是否节省下载？** 不会自动节省，需提供匹配尺寸候选，并正确描述布局宽度。
9. **失效消息发出是否等于全层立即一致？** 不等于。传播、失败与旧请求回填都可能存在，应有版本、可靠传递和最大陈旧度约束。
10. **任意图片URL与尺寸转换是否只是性能问题？** 不是，还涉及SSRF、解码资源耗尽、权限绕过和费用放大，应限制来源、参数及资源。
