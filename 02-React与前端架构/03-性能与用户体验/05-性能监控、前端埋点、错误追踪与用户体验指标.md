# 05 性能监控、前端埋点、错误追踪与用户体验指标

## 一、从“收到了日志”走向可解释的用户失败

前端可观测性（Observability）把浏览器、网络、CDN、后端与真实用户旅程连接起来。目标是回答谁受影响、哪个版本开始、用户做到哪一步、失败发生在哪层、应该由谁修复。收集很多事件却无法回答这些问题，只增加费用和隐私暴露。

以结算为例，页面加载慢、点击无响应、请求超时、支付被拒、成功后界面未更新，是不同失败。技术信号需要与旅程事件关联，但不能把点击“付款”当成支付成功，也不能因HTTP 200就认为订单完成。前端监控是诊断视角，资金和订单事实仍以服务端权威记录为准。

一种可落地的链路是：浏览器采集并脱敏，按访问采样和有界队列批量上报，接收端校验去重，分别进入指标聚合、错误聚类与明细存储，再按版本、旅程和Trace关联分析。每层都需要失败与容量边界，监控链路故障不能拖垮业务页面。

下文浏览器API按2026-11-25核验的一手资料说明，Trace Context采用W3C Level 1规范语义；React错误边界按当前官方文档描述。浏览器、SDK与平台能力有差异，上线需固定版本和覆盖测试，不把某个厂商SDK默认行为视为标准保证。

## 二、先建立稳定的上下文与数据模型

上下文不是越多越好，而是让有限信息能够关联：

| 字段 | 作用 | 边界 |
| --- | --- | --- |
| release与build_id | 定位实际执行的构建 | 灰度、旧标签页、微前端需记录真实组合，而非只记录“最新版本” |
| page_view_id | 区分一次文档或明确约定的虚拟页面访问 | SPA切路由规则必须统一，不能与会话混用 |
| session_id | 在限定窗口内关联同一使用过程 | 尽量短期、随机，不等于用户真实身份 |
| route_template | 聚合如/orders/:id的页面类别 | 不记录完整含敏感参数的URL |
| event_id与schema_version | 去重与兼容演进 | 重试保持同一event_id，结构变更有版本 |
| trace_id或correlation_id | 跳转至对应请求诊断 | 不是授权凭证，也不应装入个人信息 |
| device/browser/region | 识别人群和兼容问题 | 能力与地区尽量粗粒度，未知值如实保留 |

指标标签要控制基数（Cardinality，即不同标签组合数量）。把每个用户ID、订单号或完整错误堆栈设成时间序列标签，会使序列爆炸、查询变慢且费用失控。高基数细节放受控明细，聚合只使用路由模板、版本、有限错误分类等维度。

浏览器时钟可被用户改变。事件可同时记录客户端发生时间和接收时间，同一页面的耗时优先用performance.now等单调时钟计算；不能用两个机器的墙上时间直接相减推导跨系统耗时。乱序到达是正常情况，分析按事件语义和标识重建，而不是按入库顺序猜流程。

## 三、RUM：测真实分布，也解释观测盲区

真实用户监控（RUM，Real User Monitoring）来自生产访问；实验室测量控制设备、网络与步骤，适合复现。二者互补：实验快不能证明所有真实用户快，生产平均好也不能证明弱设备没有长尾。

核心网页指标包括LCP（Largest Contentful Paint，主要内容呈现）、INP（Interaction to Next Paint，交互至下一帧响应）和CLS（Cumulative Layout Shift，非预期布局位移）。当前建议良好阈值分别为2.5秒、200毫秒、0.1，以移动/桌面分段的第75百分位评估。p75是分布位置，不是平均；各地区p75不能直接平均得到全站p75。

Navigation Timing帮助分解文档导航阶段；Resource Timing提供资源请求时序与大小；Long Task记录主线程长任务线索。它们是诊断材料而不是业务成功证明。主线程长任务常以超过50毫秒为诊断阈值，但连续多个较短任务仍会影响交互，不能把49毫秒当作安全线。

资源跨源时，部分时序受Timing-Allow-Origin等规则限制；CORS允许业务读取响应不等于自动开放所有性能细节。字段为0可能是缓存、限制或实现差异，不能直接判断网络耗时为零。PerformanceObserver与各entry类型需能力检测，及时消费并控制缓冲，避免无限保存资源事件。

标准指标有页面生命周期、后台切换、前进后退恢复等边界，应优先采用维护中的测量库。SPA路由切换不天然等于新文档导航；路由级自定义“内容就绪时间”可以很有价值，但须写清起止点，与标准Core Web Vitals分开展示。SDK升级也可能改变口径，报告中应记录采集版本。

无交互访问不能把INP填0；未上报的访问也不能算“没有错误”。广告拦截、离线、旧浏览器、同意状态和页面提前退出都会影响覆盖，需展示样本数与缺失率。按Route、Device、Browser、Region、Network、Version分段时，网络类别不可用就记unknown，不用推测补齐。

## 四、错误追踪：捕获、还原、聚类与影响面

### 4.1 捕获渠道各有范围

全局error可观察脚本执行错误；资源加载error常需要在捕获阶段观察并单独分类，不能把图片加载失败当成具有完整JavaScript堆栈的异常。unhandledrejection观察未处理Promise拒绝，但跨源脚本等情形存在限制；已经catch后吞掉的业务失败也不会自动成为未处理拒绝。

React Error Boundary可为子树渲染等受支持错误展示兜底并记录Component Stack；普通事件处理器、独立异步回调与服务端渲染等不能假定都由同一边界接住。边界自身失败需更外层处理。全局监听是最后诊断网，不是业务恢复逻辑，显示一个错误页也不会回滚已执行的服务端写入。

API层应区分网络不可达、超时、主动取消、HTTP错误和业务拒绝。fetch对HTTP 4xx/5xx不会仅因状态码自动reject，应检查响应状态及约定业务码。用户切路由主动Abort通常不应作为服务不可用告警；但超时后交易状态未知仍需查询服务端确认。

### 4.2 事件应记录什么

错误至少保留类型、脱敏后的Message与Stack、Release、路由、采集渠道及时间；React错误可附Component Stack；请求失败附接口模板、状态类别、请求关联ID，避免完整请求/响应体。Breadcrumb是错误前的有限操作摘要，例如“打开结算”“提交请求”“请求超时”，不是录下所有输入内容。

Source Map把压缩产物的位置映射回源码。必须与准确构建、文件及行列匹配，同名main.js对应不同版本时误配会指向错误代码。发布流水线应先上传可用映射并校验，再把Release关联到部署；可只上传错误平台，不必公开发布。映射访问、源码保留及第三方权限应受控，客户端包也不能包含密钥。

错误原因不一定是JavaScript Error对象，Promise可以拒绝任意值；序列化时需限制深度、长度和循环引用，防止上报器再次抛异常。Message与Stack可能含URL、查询参数或业务值，应在进入队列前脱敏，接收端再校验；仅靠展示页面隐藏字段不足以保护原始存储。

### 4.3 聚类不等于事件去重

Fingerprint是用于把相同根因聚成一个Issue的特征，常结合错误类型、稳定栈帧、操作和接口模板。原始Message里包含用户或订单号会造成海量Issue，应归一化动态值；只用“TypeError”又可能把不相关错误合并。规则需版本化，支持拆分与重新聚类，避免为了减少Issue数掩盖多个根因。

去重处理同一个事件被全局监听、框架边界或重试链重复提交，使用event_id或受控去重窗口；聚类处理多个真实发生但根因类似的事件。两者不能混用，否则会把真实发生次数去掉。

优先级看受影响Session数、关键旅程和版本，而不只看事件条数。一个会话循环抛错一万次，与一万用户各失败一次影响不同。对单会话错误风暴限额并记录丢弃计数，可减少费用，同时保留首条及关键样本。

## 五、业务埋点：从按钮动作到可解释的领域事件

领域事件（Domain Event）表达业务发生了什么，而不是页面实现细节。checkout_started、payment_submitted、order_confirmed、checkout_failed比button_clicked_2更稳定，但每个名字仍需精确定义触发条件。

| 事件 | 触发语义 | 不能混淆 |
| --- | --- | --- |
| checkout_started | 用户进入可操作结算流程，按约定去重 | 每次组件render不算新的开始 |
| payment_submitted | 一次有效提交尝试被发起 | 不代表服务端收到或扣款成功 |
| order_confirmed | 依据服务端权威结果确认完成 | 乐观UI、点击和请求发出都不算确认 |
| checkout_failed | 本次旅程进入定义的失败状态 | 可恢复警告、用户取消应另分类 |

Schema需包含Owner、版本、字段类型、单位、允许值、数据分类、触发时机和去重规则。破坏性变更建立新版本或兼容窗口，不悄悄把“耗时毫秒”改成“耗时秒”。使用schema registry或共享契约与接收端校验，未知字段策略需明确，避免一个新字段使全部旧事件被拒绝。

下面是虚构事件结构，标识仅作示意，不含支付凭证或真实用户信息：

```json
{
  "event_id": "demo-event-001",
  "schema_version": 1,
  "name": "payment_submitted",
  "release": "web-demo-17",
  "route_template": "/checkout",
  "page_view_id": "demo-view-001",
  "journey_id": "demo-journey-001",
  "attempt": 1,
  "sample_rate": 1,
  "properties": { "method_category": "card" }
}
```

journey_id关联一次流程，attempt区分重试；传输重试保留event_id，用户重新发起真实提交则生成新的事件。支付服务的幂等键是防重复业务执行的协议，与监控event_id用途不同，不能用分析系统的去重代替交易幂等。

接收端按事件ID去重，并处理乱序和有限迟到。客户端事件可被篡改、丢失或伪造，转化与收入分析需与服务端事实对账。统计监控不应反过来成为用户是否获得服务的唯一依据。

## 六、链路关联：Trace不是身份凭证

Trace把一次操作中的多个调用关联起来；Span描述其中一段工作。W3C traceparent包含版本、trace-id、parent-id和标志，tracestate用于供应商相关上下文。推荐用成熟追踪库创建与传播，不手拼随机字符串，也不在这些字段中放用户姓名、邮箱或Token。

浏览器对受控API请求传播Trace Context，后端校验后继续或按信任边界重新建立上下文；响应可以返回单独约定的关联ID。Trace Context标准并不要求所有服务把完整内部追踪信息返回给UI。用户界面若需要支持编号，应展示有限、不可用于授权的诊断ID，详细堆栈与服务拓扑留在受控平台。

跨源自定义Header可能触发CORS预检，后端需允许实际使用的请求头；前端若读取自定义响应关联头，还需适当Expose-Headers。CORS配置、Timing-Allow-Origin和Trace采样是不同机制，不能以“接口能调通”推断时序和链路关联必然完整。

只向明确允许的自有或合作域传播，避免给广告或任意第三方附加内部上下文。入站trace-id视作不可信输入，不用于权限、租户选择或计费。后端与前端采样策略可能不同，即便有相同trace-id，也可能查不到完整Span；诊断页应显示采样与缺失信息，而不是自动认定链路不存在。

## 七、采样、上报与容量：监控不能成为新的故障

### 7.1 采样要保住分母

会话或访问级采样让同一旅程的关键事件一起保留，方便漏斗和错误关联；逐事件独立抽样可能把一条完整旅程切碎。性能、错误和业务事件可以有不同策略，但必须保存采样率及决策版本，并明确哪些报表可以合并。

高严重度错误可提高保留率，但如果错误与正常访问抽样不同，直接拿采到的错误数除以采到的总访问数会有偏差。应使用一致采样的率指标或正确设计的加权估计。分位数需要原始分布或合适的分布摘要，不能简单平均各批p75或用一个采样率直接乘时间。

采样不是匿名化，少量敏感数据仍然敏感。错误风暴时先限额、聚合与保留代表样本，并监控丢弃量；不能让系统安静只是因为SDK把所有事件丢掉。新版本扩量前应验证正常与异常样本都能到达。

### 7.2 上报链路的失败语义

客户端队列应限制事件数、字节和存活时间，批量发送并有界重试。对暂时失败采用退避与抖动，对无效Schema等永久错误不要无限重试。离线持久化需要额外隐私和清理设计，不能默认把整个行为历史写入localStorage。

页面隐藏时可以尝试flush，visibilitychange通常比依赖unload更合适；浏览器崩溃、进程被杀和系统断网仍可能丢最后一批。sendBeacon适合少量异步POST，返回true只表示浏览器成功排队，不表示服务端已接收、校验或持久化。它也不能任意配置方法和请求头，需要这些能力或响应时可评估fetch keepalive，并验证额度和生命周期限制。

监控系统通常接受“尽力交付+事件去重”，不能声称端到端exactly-once。服务端需先校验大小、字段和速率，再入队或持久化；客户端公开的采集地址可能被滥用，应隔离业务接口，做容量、配额和异常来源治理。SDK自身报错不得再次递归上报造成风暴，SDK请求也应避免被自己的网络拦截器无限采集。

## 八、体验指标如何与业务结果连接

Crash-free Session可定义为1减去“出现指定致命前端故障的会话数/被可靠观测的有效会话数”。浏览器未必能报告真正进程崩溃，所以要明确这是平台对fatal事件的代理口径，而不是宣称监测到所有浏览器崩溃。发生普通可恢复接口错误是否计入，必须事先约定。

漏斗（Funnel）按规定顺序、时间窗与身份关联，比较started、submitted、confirmed等阶段。需要处理重试、回访、跨标签、重复事件和服务端延迟确认。Drop-off不自动等于Bug：用户犹豫、价格、身份验证和埋点丢失都可能导致离开。

Rage Click通常通过短时间相近区域的重复点击识别，Dead Click通过点击后没有预期响应识别，都是启发式线索。游戏连点、缩放、多选或非交互区域可能产生误判，应结合目标语义与后续行为验证，不能直接断言用户愤怒。采集位置或目标标签时避免读取敏感文本。

LCP与跳出率、INP与任务完成、API错误与结算转化可以关联分段分析，但相关不证明因果。弱网络用户既更慢也可能来自不同地区和设备，发布同时改价格也会影响转化。用随机A/B测试或明确控制变量验证，关注样本量与观察窗口，并保护错误率、收入正确性和可访问性等护栏；不为追逐一个分数隐藏错误或改变业务成功定义。

## 九、告警、SLO与排障闭环

服务水平指标（SLI）是被测量的可靠性指标，目标（SLO）规定一定窗口内应达到什么水平。例如“有效结算旅程中，能收到明确可操作结果的比例”，比“没有任何console.error”更贴近用户价值。目标数字应基于业务风险与基线制定，不给所有产品套统一阈值。

告警要看比例、绝对影响量、持续时间和分段。新Release错误率快速升高、关键漏斗确认明显下降、Crash-free Session持续退化或Core Web Vitals跨人群回归，可能需要响应；单个用户断网通常只聚合观察。低流量页面只按比例可能一例就100%，需最小样本与合适窗口；发布刚开始也不能等很长窗口才发现严重退化。

每条告警要有Owner、严重度、Runbook、版本对比和可回滚入口。对同一根因的多信号聚合，设置恢复条件和抑制，避免一场后端故障同时触发几百条前端通知。合成监控从受控浏览器定期验证关键流程，可在真实流量不足或SDK失效时补位，但不代表真实设备分布。

虚构排障案例：某版本checkout_failed增加。先确认采集量和Schema没有变化，再按浏览器、路由和Release识别集中人群；Source Map显示序列化异常，Breadcrumb表明发生在请求发送前，后端Trace缺失与该结论一致。修复后灰度验证事件、请求与服务端确认三者恢复，不能只看错误Issue变少。

另一个虚构案例：API超时增加但后端处理正常。利用请求关联与Resource Timing检查网络、预检、CDN及客户端超时预算，区分“没发出”“后端已完成但客户端没收到”和“前端展示失败”。支付状态未知时查询权威状态，不因用户看见超时就直接重新扣款。

监控链路本身也需心跳或合成事件、接收延迟、队列积压、Schema拒绝率、丢弃率、采样覆盖和SDK版本监控。业务事件突然归零可能是没有流量，也可能是采集失效；与后端请求或合成检查对照，才有解释力。

## 十、数据治理：采集前限制，生命周期内可控

治理包括同意（Consent）管理、数据最小化（Data Minimization）、保留期（Retention）、用户删除与访问控制。实际哪些处理需要何种依据应由适用政策与合规要求确认；技术上至少区分必要诊断与可选分析目的，支持配置、撤回和停止发送，不把“已经加载SDK”当作所有采集已获许可。

优先字段白名单和源头脱敏。不要收集输入值、密码、Token、Cookie、完整URL查询、病历或银行卡信息。哈希用户标识通常只是降低直接可读性，仍可能可关联，不能自动宣称匿名。IP、设备和会话关联也可能识别用户，应限制精度与用途。

保留期应覆盖明细、聚合、搜索索引、导出和备份策略，明确用户删除如何定位关联数据、何时生效及哪些聚合已不可逆。删除工作不能只删一个Dashboard记录。访问按最小权限分离，敏感明细和Session Replay尤其需要审计、遮罩及额外审批策略；Masking应在发送前完成，而不是只在回放界面盖住。

外部平台接收的数据、地区、子处理链和费用需纳入架构评估。低成本可以先用少量关键事件、错误与体验聚合，不必默认全量回放。扩大采集前先证明诊断价值，避免数据越存越多却无人负责。

## 十一、面试完整回答与追问

### 1. 如何设计前端监控？

答：我先定义关键旅程和故障口径，再把RUM、脚本/资源/API错误、领域事件、Release与后端Trace关联。客户端白名单脱敏、访问级采样、有界批量上报，接收端校验去重与错误聚类。Dashboard同时展示影响会话、分母、版本和覆盖盲区，告警有Owner与恢复步骤，最后验证监控自身故障不会影响业务。

追问：装一个SDK是否够？答：不够。SDK提供采集机制，不能替团队定义支付成功、去重、采样分母、隐私与回滚；必须通过正常和故障旅程验证整条链路。

### 2. 同一个错误很多次如何处理？

答：用event_id去除传输或多渠道重复，用Fingerprint把真实重复发生聚成Issue，同时保留发生次数与影响Session数。按稳定栈和操作归一化动态值，限制单会话风暴，优先关键旅程和新Release。

追问：只按Message聚合呢？答：动态ID会拆成很多Issue，过于通用消息又会误合并。需要脱敏、稳定栈帧与上下文组合，并可修订规则，不能为了少Issue而消灭影响数据。

### 3. 前端如何关联后端故障？

答：对允许的API传播合法Trace Context或约定关联ID，后端校验并继续追踪，错误记录同时带Release、请求模板和关联值。跨源处理预检与响应头暴露，注意两端采样和可信边界；ID不承载身份和权限。

追问：为什么有ID却查不到Trace？答：可能请求根本未到后端、采样丢弃、跨域传播失败、存储延迟或过期。需要结合请求证据和采样状态，不能把缺失Trace直接解释为后端正常。

### 4. 性能改善后转化上升，如何证明效果？

答：先对齐人群、时间与成功定义，排除版本、价格、渠道和采样变化，再用随机实验或控制变量估计。技术指标与漏斗相关只是线索，还要验证错误、可访问性与收入正确性，避免只让反馈动画变快而业务完成没改善。

追问：sendBeacon返回true能证明埋点不丢吗？答：不能，只说明排队。浏览器退出、网络和接收端仍可能失败，分析按尽力交付设计并与服务端事实对账，不承诺精确一次。

## 十二、扫雷自测与完整答案

1. **HTTP 200就是业务成功吗？** 不是。还需业务码与权威状态，客户端发出请求也不证明服务端已完成。
2. **错误条数等于受影响用户数吗？** 不等于。一个会话可循环报错，需事件去重、根因聚类与会话影响分开统计。
3. **未收到错误是否证明无错误？** 不证明。页面崩溃、拦截、断网、采样或SDK失败都可能阻断上报，应监测覆盖。
4. **各路由p75能直接平均吗？** 不能。分位数不是可直接相加平均的量，需整体分布或合适摘要。
5. **Source Map只要文件名一致就行吗？** 不行。需匹配实际构建与产物，否则源码位置会误导排障。
6. **Fingerprint与event_id一样吗？** 不一样。前者聚根因，后者标识一次发生及其传输重试，混用会丢失真实频次。
7. **Trace ID可以作为访问凭证吗？** 不可以。它来自跨系统上下文，应视作不可信诊断信息，鉴权必须独立完成。
8. **逐事件随机采样能自然保留完整漏斗吗？** 不能保证。旅程步骤可能被切碎，应按访问/会话一致采样或使用严谨估计。
9. **采样1%是否不需要脱敏？** 仍需脱敏。采样只减数量，不改变敏感性与可关联性。
10. **告警减少是否证明系统更好？** 不一定。也可能规则失效、采集停止或全被限额丢弃，需对照真实旅程和监控链路健康。
