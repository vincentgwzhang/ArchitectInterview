# 04 大列表虚拟化、防抖、节流与渲染优化

## 一、先识别成本，再决定减少什么

列表慢可能来自下载过多、排序过滤计算、React组件计算、DOM更新、浏览器样式布局或绘制。它们需要不同方案。虚拟化减少同时存在的行，防抖减少不必要执行次数，节流限制持续执行频率，记忆化复用结果，Worker迁移适合的计算；这些手段不能相互替代。

优化顺序是先减少总工作量，再减少执行频率，最后缓存值得复用的结果。例如十万条数据不必全下载时先分页；只显示几十条却每次键入都全量排序时先解决计算；DOM很多但每行很便宜时再考虑窗口化。只给所有组件套memo无法修复网络过大或布局抖动。

本章以React 18及以上常用Hooks语义说明；TanStack Virtual的机制核验使用v3文档，但正文不依赖其某个小版本API。React Compiler是否开启取决于项目工具链，不能把框架版本升级等同自动启用编译优化。所有效果都要在目标设备和实际旅程中验证，不提供虚构提速倍数。

## 二、虚拟列表怎样控制DOM规模

### 2.1 固定行高的窗口计算

虚拟化（Virtualization，也称Windowing）保留完整滚动范围，只挂载视口附近的行。假设有N条、每行高度h、容器高度H、滚动位置y，首个可见索引近似floor(y/h)，末尾排他索引为ceil((y+H)/h)，再向两侧多渲染o条。总占位高度N×h，当前行按其逻辑位置放置，因此滚动条仍代表整个数据集。

Overscan是视口外预渲染缓冲。太小会在快速滚动时出现空白，太大则恢复大量DOM和计算。应根据行复杂度、速度和目标设备调节，不把某个固定条数当作普遍最佳值。Overscan不是预取全部后端数据，也不是消除所有加载延迟。

下面是可单独理解的纯JavaScript范围函数，end为排他边界，要求行高为正、数量及overscan为非负整数：

```js
function fixedRange(count, rowHeight, viewportHeight, scrollTop, overscan) {
  if (!Number.isInteger(count) || count < 0 ||
      !Number.isInteger(overscan) || overscan < 0 ||
      !Number.isFinite(rowHeight) || rowHeight <= 0 ||
      !Number.isFinite(viewportHeight) || viewportHeight < 0 ||
      !Number.isFinite(scrollTop)) throw new Error("invalid geometry");
  if (count === 0) return { start: 0, end: 0, offset: 0, total: 0 };
  const total = count * rowHeight;
  const top = Math.min(Math.max(0, scrollTop), Math.max(0, total - viewportHeight));
  const start = Math.max(0, Math.floor(top / rowHeight) - overscan);
  const end = Math.min(count, Math.ceil((top + viewportHeight) / rowHeight) + overscan);
  return { start, end, offset: start * rowHeight, total };
}
```

例如N=1000、h=40、H=400、y=800、o=2，返回start=18、end=32、offset=720、total=40000，即显示逻辑第18至31行共14条。真实UI还需把滚动事件、容器测量、行定位和键盘行为接入；这个函数不是完整虚拟列表实现。空数据、数据变少导致旧scrollTop越界都必须处理，不能让窗口索引落在数组之外。

### 2.2 动态行高与测量

文字换行、图片、展开详情和不同语言会改变行高。动态虚拟列表维护每行估计或实测高度，以及前缀偏移；根据滚动位置定位对应行，再测量已渲染行并修正。若每次定位都从第一行扫描，数据大时会重新成为瓶颈，可采用前缀结构和二分等方式，或使用成熟库。

估计偏差会引起滚动位置漂移。测量上方行变高后，通常需要保持可见锚点及相对偏移，而不是单纯维持原始像素scrollTop。图片加载、容器宽度和字体变化后也需重新测量；测量后立即改尺寸再测量，可能形成反馈循环，应控制更新批次并避免无变化重复提交。

DOM键应使用业务稳定ID。若排序后仍把索引当身份，行内编辑状态和测量缓存可能关联到错误记录。测量缓存还应在宽度、字体、展开状态等几何条件变化时失效，不能因为ID不变就永久复用旧高度。

### 2.3 滚动恢复、表头与可访问性

返回列表时保存业务查询条件、排序、锚点ID与偏移，必要时再辅以像素位置。若数据已删除或排序变化，应明确回退到邻近记录或顶部；在数据与高度尚未准备时直接恢复旧像素，常会跳错位置。无限列表还需恢复相应页或游标上下文。

Sticky Header要相对正确滚动容器定位，注意祖先overflow、transform及层叠关系。表头、列宽和行内容需对齐，别为了绝对定位破坏原生表格语义。复杂交互表格可选成熟支持虚拟化与键盘模式的组件，而不是给普通div任意加role就宣称可访问。

未挂载行不在可访问性树中，浏览器查找、打印和Tab遍历也不能自动覆盖全部数据。键盘导航应先更新逻辑活动行，滚动使目标挂载，再把焦点移到存在的节点。不能让滚出窗口的聚焦节点被直接移除而使焦点丢失。按所选list或grid语义提供正确的位置与总数信息，并实测读屏、方向键、Tab及选择行为。

对需要全文查找、打印、导出或非常依赖原生语义的页面，分页或专门的完整展示模式可能更适合。小列表一般不值得付出虚拟化的测量、焦点与维护成本。

## 三、虚拟化与无限加载不是同一件事

虚拟化限制挂载节点数，不会自动减少已经下载的数据和客户端内存。无限加载（Infinite Loading）按用户接近末尾时继续请求，仍可能不断累积数据；需要结合分页、游标（Cursor）和有界缓存。游标表达从某个位置继续取，适合稳定顺序，排序条件变化应重置它，不能把旧游标用于新查询。

加载下一页应有hasNextPage和inFlight等约束，避免底部探测连续触发重复请求；返回后按实体ID处理重复，并明确失败重试和末页状态。列表滚动很快时可提前少量请求，但不要把每一行进入视口都变成独立API请求。

服务端排序过滤通常优于先把全部数据拉到浏览器，尤其数据规模大、权限敏感时。不能仅在已加载的三页上排序，却告诉用户这是全量排行榜。若服务端数据持续变化，页间重复或遗漏需要稳定排序、唯一排序键或快照策略；虚拟化不提供数据一致性。

缓存淘汰旧页时，要保留可解释的占位或恢复策略，否则上方内容消失会改变滚动范围。虚拟列表加载、失败与重试行也应计入几何计算，并有可操作提示，不应出现永远空白的底部区域。

## 四、防抖：延迟副作用，保持输入立即响应

防抖（Debounce）在事件持续到来时不断重新计时，等安静一段时间才执行，典型是输入建议。Trailing表示安静后执行；Leading表示第一下立即执行；持续输入时若要求最长等待时间，可采用带maxWait语义的成熟实现。纯尾部防抖可能在持续输入时一直不执行，这在自动保存中需要单独评估。

不要延迟受控输入本身的setState，否则光标与文字都显得卡顿。应立即更新输入值，只延迟查询等副作用。下面的教学Hook实现尾部延迟值，不包含leading或maxWait：

```tsx
import { useEffect, useState } from "react";

export function useDebouncedValue<T>(value: T, delayMs: number): T {
  const [settled, setSettled] = useState(value);
  useEffect(() => {
    const timer = setTimeout(() => setSettled(value), delayMs);
    return () => clearTimeout(timer);
  }, [value, delayMs]);
  return settled;
}
```

调用方应提供有限且非负的delayMs，并优先传字符串等稳定值。首次返回初始value；值或延迟变化会清理旧计时器，卸载也清理。若每次render创建新对象传入，会反复重置等待。React开发Strict Mode的额外setup/cleanup用来暴露清理问题，不应通过关闭检查掩盖重复计时器。

防抖不等于请求取消。旧请求可能已发出，新输入还在等待新计时器；仅延迟查询不能阻止旧结果回来。结果应关联查询键或请求代次，在展示时确认与当前输入及业务条件相符。AbortController可减少浪费，但取消可能来不及，也不意味着服务端已停止处理，所以仍需要结果有效性检查。

输入法组合（IME Composition）期间，用户尚未确认的文字不应盲目触发建议请求；结合composition事件和产品需求决定何时查询。清空输入、提交、失焦和卸载的行为也需定义。自动保存尤其要明确提交时flush还是等待，不能因尾部计时器被卸载清理而静默丢掉最后一次更改。

## 五、节流：持续事件下给出有界反馈

节流（Throttle）允许持续事件周期性执行，适合滚动进度和resize计算。原先“固定窗口最多一次”只是其中一种实现；固定时间桶在桶边界两侧可能很近地执行两次，基于上次执行时间的实现又有不同语义。必须说明间隔、leading、trailing与取消，而不只背“每N毫秒一次”。

Leading保留开始反馈，Trailing保留结束时最新状态。例如拖拽只leading可能停在过时位置，纯trailing又会让开始没反馈。某些实现两者都开时，孤立的一次调用只执行一次，避免重复动作；库之间细节要查文档。节流适合可合并状态，不适合随意丢弃每一笔交易或必须逐条处理的事件。

视觉更新可采用requestAnimationFrame合并一帧内的多次输入。以下不是固定毫秒节流，而是“最多保留一个待执行帧，并采用最新值”：

```js
function frameLatest(update) {
  let frame = null;
  let latest;
  function push(value) {
    latest = value;
    if (frame === null) {
      frame = requestAnimationFrame(() => {
        frame = null;
        update(latest);
      });
    }
  }
  push.cancel = () => {
    if (frame !== null) cancelAnimationFrame(frame);
    frame = null;
    latest = undefined;
  };
  return push;
}
```

注册滚动监听时调用push(scrollTop)，清理时同时removeEventListener和push.cancel。回调update应稳定，或显式读取最新业务上下文，避免闭包捕获旧状态。rAF在绘制前执行，通常随刷新率变化，后台标签页还可能暂停；它不是稳定60Hz计时器，不适合保证定时保存或业务截止时间。

防抖、节流都不提供服务端限流或可靠队列保证。它们仅控制当前客户端某段逻辑，多个标签页、恶意客户端和失败重试仍需后端独立治理。

## 六、React渲染优化：先画更新边界

### 6.1 测量与状态位置

React render阶段计算界面，commit阶段应用必要修改，随后浏览器还要样式、布局和绘制。一次重渲染不等于DOM一定变化；DOM没变化也不表示组件计算免费。先使用React DevTools Profiler或Profiler组件定位更新原因、次数与耗时，再用浏览器Performance面板看实际输入和绘制。

Profiler的actualDuration描述这次提交相关树的渲染工作，baseDuration是未优化整体渲染成本的估计，不是浏览器整帧耗时；Profiling自身有开销，普通生产构建默认不提供完整程序化profiling能力。不要把开发模式的额外调用次数直接当生产性能结论。

输入状态若放在页面Root，会使大量无关子树参与更新。把状态放到真正消费它的局部，拆分输入区与重型结果区，避免把局部hover、展开和草稿都广播到全局。若状态必须跨区共享，则通过小型稳定接口传递，保持单一权威状态，不能为减少render而复制多个容易失步的业务状态。

Context按值变化通知消费者；一个Context同时承载主题、用户与高频输入，会扩大更新范围。按职责与频率拆分，或通过受控选择器订阅具体片段。memo不能阻止组件自己state或所消费Context变化引起的更新。

### 6.2 memo、useMemo、useCallback的边界

memo默认逐个prop用Object.is比较；新对象、数组或函数即使内容看似相同，引用变化也可能导致重新计算。先减少不必要props和对象创建，再稳定确实影响昂贵子树的接口。useMemo缓存计算结果，useCallback缓存函数身份，两者都不是“让函数运行到后台”。

例如排序应避免在render中对props数组直接sort，因为sort原地修改输入，会破坏其他消费者与记忆化假设；可先复制再排序，或在服务端/数据层维护派生结果。useMemo只在依赖不变时复用，若每次键入都改变查询，对巨大数组过滤仍可能每次执行，应考虑索引、分页或Worker。

自定义比较器必须比较影响输出与行为的全部props，包括函数。忽略回调可能保留捕获旧数据的函数；深比较本身可能比render昂贵，且结构深度增长可能带来不可控成本。缓存应服务性能，正确性不能依赖“React永远不会重新算”。启用React Compiler的项目可减少手工记忆化需求，但仍需分析算法、Context和DOM成本。

### 6.3 延后更新与防抖的差别

useDeferredValue或Transition区分紧急与可延后的UI更新，适合输入立即响应、结果视图稍后跟上。它不是固定300毫秒等待，不会自动减少请求数量，也不会把同步大计算搬到另一线程。应明确显示旧结果状态，避免用户以为屏幕已反映最新查询。

若先在事件处理器同步扫描十万条，再把setState标为Transition，扫描仍阻塞输入。并发渲染允许React调度部分渲染工作，不代表任意JavaScript函数能在中途被安全打断。需要同时改变工作量或计算位置，而不只添加一个Hook。

## 七、浏览器主线程、布局与计算迁移

布局抖动（Layout Thrashing）常来自写样式后马上读几何值，导致浏览器为了回答读取而同步计算布局；循环交替读写会重复付费。应先批量读取，再批量写入；确需依赖新布局时，按明确批次和时机处理，不盲目把所有测量塞进useLayoutEffect，因为它会阻塞绘制。

动画优先评估transform和opacity，因为常有机会减少布局或重绘成本，但是否在合成层完成取决于具体页面与浏览器。大面积图层和过多will-change也消耗内存，不能把GPU加速当无限免费资源。动画时间应按时间戳推进，避免在高刷新率屏幕变快，并尊重减少动态效果的用户偏好。

长任务需要减少或真正让出主线程。把计算拆成多个片段可让输入与绘制获得机会，但连续Promise微任务不保证让出渲染；setTimeout也只提供调度机会，不保证准确时间或下一帧必然绘制。分片要记录进度、支持取消，并防止数据变化后把旧任务结果提交。

Web Worker适合独立CPU工作，如解析、索引或复杂计算，不直接访问页面DOM。传输数据的复制与序列化、Worker启动及协调都有成本，可转移对象还涉及所有权转移。为任务附版本和ID，返回时核对当前查询；即便无法停止旧任务，也能忽略旧结果。若瓶颈是巨大DOM布局，应减少节点而不是仅迁移纯计算。

性能优化不能减少必要安全与一致性检查。分页只返回有权限数据，导出和搜索结果不能依赖前端过滤隐藏敏感记录；Worker不构成与同页业务完全隔离的权限边界。

## 八、工程验证与场景推演

固定目标数据规模、行内容、设备、网络及发布版本，分别测试首次显示、连续输入、快速滚动、展开动态行、返回恢复和长时间使用。观察DOM节点、React渲染工作、长任务、交互响应、内存和请求数量。不能只看某次平均帧率；键盘、读屏与失败恢复是验收的一部分。

纯逻辑测试可以覆盖窗口上下界、空数据、末页、数据缩短；使用可控计时器验证防抖取消、尾部执行与卸载，使用乱序响应验证过期结果不覆盖新输入。浏览器层验证动态高度、焦点、sticky和背景切换。各类测试解决不同问题，数学范围正确不证明交互无障碍正确。

虚构场景：搜索输入卡顿。先确认受控输入立即setState，再查看点击或键入前是否有同步过滤。若请求太频繁，用防抖控制副作用；若结果render太大，用状态拆分与虚拟化；若独立索引计算耗时，用Worker或后端查询。改动后应同时验证请求减少、结果与查询匹配、输入法和取消正确，而不是只观察输入动画。

另一个虚构场景：虚拟表格滚动跳动。若图片和展开内容改变高度，应检查测量缓存、业务ID及锚点校正；若只是overscan小导致空白，适度增加缓冲。把overscan改得很大可能掩盖空白却恢复DOM成本，所以必须先区分原因。

## 九、面试完整回答与追问

### 1. 十万条列表怎么优化？

答：先判断是否必须全量下载与本地排序。能服务端分页就按稳定查询与游标取数据，再用虚拟化限制DOM；固定行高按位置算窗口，动态高度需要测量与锚点校正。把选择与编辑状态按业务ID保存，并验收滚动恢复、键盘读屏、失败和内存。虚拟化不自动减少后端传输或全部数据计算。

追问：为什么不用索引作key？答：排序、插入后索引对应实体改变，组件状态和测量可能附到错误记录；稳定业务ID能维持实体身份，但几何变化仍要使高度缓存失效。

### 2. 防抖和节流如何选择？

答：防抖等待事件安静后执行，适合输入建议；节流在持续事件中周期性执行，适合滚动进度。需明确leading/trailing、取消和最终状态。输入立即更新，延迟副作用；已发请求还需取消与结果版本检查，不能只清定时器。

追问：自动保存可直接尾部防抖吗？答：持续输入可能一直不保存，离开时还可能取消最后一次。应按风险加maxWait或显式提交/flush，并设计服务端版本与幂等，不能把UI定时器当持久保证。

### 3. 为什么加memo还是慢？

答：可能props每次都变、Context频繁更新、比较太贵，也可能主要成本根本不在React，而是算法、网络或布局。先Profiler定位，再缩小状态范围，稳定必要props，最后记忆化；巨大DOM用虚拟化，独立CPU用索引、Worker或后端。

追问：自定义比较时不比函数行吗？答：不安全，函数闭包可能包含新状态。不比它可能保留旧行为，即使视觉输出暂时相同也出错，应保证行为等价而不只是结构相似。

### 4. rAF能解决所有滚动性能问题吗？

答：它把视觉更新协调到绘制前，可合并最新状态，但回调本身太重仍会掉帧，也不减少所有事件派发。它随刷新率调度，后台可能暂停，不能代替业务定时器。还需减少布局读写和DOM工作，卸载取消回调与监听。

追问：把任务放rAF就一定能画一帧吗？答：不保证。回调在绘制前执行，长计算会推迟绘制；应减少工作或分片，不能只是换一个回调入口。

## 十、扫雷自测与完整答案

1. **虚拟化会减少所有网络数据吗？** 不会。它只限制挂载范围，网络需分页、游标与缓存另行设计。
2. **overscan越大越稳定吗？** 不一定。它降低边缘空白风险，但增加节点与计算，动态测量错误也不能靠缓冲根治。
3. **固定scrollTop能恢复所有动态列表吗？** 不能。高度和数据变化会改变位置，应用锚点ID与偏移并定义回退。
4. **取消防抖timer能取消旧请求吗？** 不能。请求已发出后需单独取消或忽略，且展示结果要关联当前查询。
5. **让输入setState也防抖是否最省？** 可能省频率却损害输入体验，应立即更新输入，延迟非紧急副作用。
6. **useDeferredValue是否固定间隔节流？** 不是。它是可延后UI更新机制，不保证时间间隔也不自动减少请求。
7. **memo能阻止Context更新吗？** 不能。组件消费的Context或自己的state变化仍可更新，应拆职责和订阅范围。
8. **useMemo内sort(props.rows)安全吗？** 不安全。sort原地修改props数组，缓存不消除副作用，应复制或使用合适数据层派生。
9. **Worker能直接修改DOM吗？** 不能。它需通过消息返回结果，由主线程更新界面，通信成本和结果版本都要治理。
10. **rAF永远60次每秒吗？** 不是。刷新率与页面可见性影响调度，必须用时间戳和取消协议，不当作可靠业务时钟。
