# 02 Code Splitting、Lazy Loading、Tree Shaking 与 Bundle 分析

## 一、先确定用户何时需要支付 JavaScript 成本

JavaScript 不仅需要下载，还要解压、解析（Parse）、编译（Compile）和执行（Execute）。网络缓存命中能省传输，却不能保证没有模块求值和页面初始化成本。低端移动设备可能在下载完成后仍长时间忙于主线程工作，所以“Brotli 后只有几十KB”不足以证明体验良好。

本章区分三个概念：代码切分（Code Splitting）决定构建产物如何分组；懒加载（Lazy Loading）决定何时请求或使用这些组；摇树优化（Tree Shaking）尝试从产物中移除无用代码。切分可能完全不减少总字节，只把成本推迟；摇树才可能减少实际保留代码。把一个大包拆成十个首屏立即请求的小包，不自动改善首屏。

架构决策应围绕用户旅程。例如普通用户从不打开管理员页面，将管理员代码放在独立路由块有意义；每个人一进入首页就要使用的导航和主内容，强制懒加载可能制造等待。需要同时考虑首屏、后续交互、缓存复用、发布可靠性和维护成本，而不是以Chunk数量证明优化成功。

下文React语义以当前官方lazy/Suspense接口为依据，webpack配置与行为以webpack 5为例。不同框架、构建器和小版本有差异，应锁定版本、检查生产输出；webpack注释和配置不是通用JavaScript标准。

## 二、如何选择切分边界

### 2.1 从依赖图到Chunk

构建器从入口追踪模块依赖。静态import一般形成当前构建可分析的依赖；动态import()提供异步边界，构建器可以把目标及相关依赖放入额外Chunk，并生成运行时代码加载它。Chunk是构建分组，不要求严格一模块一文件；共享提取、样式输出和框架策略都会影响最终文件。

动态import返回Promise，在模块可用后得到模块命名空间；下载成功后，模块求值仍可能抛异常。它不是“只获取文本绝不执行”的接口。因此主动调用import来预热代码，也可能执行模块顶层逻辑，不能把它等同于仅下载资源的提示。

运行时拼接路径可能使构建器生成包含一组候选文件的上下文，或者无法分析。对有限页面优先使用显式映射，既控制构建范围，也避免把不可信输入当作任意模块路径。能下载管理员Chunk不意味着拥有管理员权限，最终授权必须在服务端执行。

### 2.2 路由、功能和共享代码的取舍

| 边界 | 为什么值得切 | 不适合情况 | 验收重点 |
| --- | --- | --- | --- |
| 路由 | 访问不同页面的人不必下载全部页面逻辑 | 所有路由共享的核心能力仍需首屏 | 直接打开深链接、首跳与回跳 |
| 重型功能，如编辑器、图表、PDF查看器 | 使用概率低且代码成本高 | 功能就是当前页面主要内容 | 首次打开等待、取消、加载失败 |
| 第三方依赖 | 多路由复用并独立缓存 | 聚成巨大vendor导致所有路由都下载 | 实际复用率、变更频率、执行成本 |
| 很小的基础组件 | 通常收益有限 | 高复用、立即可见、切分开销大 | 避免请求和加载状态碎片化 |

优先粗粒度路由，再考虑成本显著的可选功能。每个按钮都Lazy会引入大量边界、占位和故障分支。HTTP/2或HTTP/3可降低部分连接成本，但不能消除请求调度、依赖瀑布和执行成本。

共享提取也有两面：重复打包会浪费下载和内存；过度提取会让罕用功能的依赖进入公共块，或让一次小改动扩大缓存失效。应按真实使用范围、模块大小与变化频率分组，而不是简单把node_modules全部塞进一个vendor文件。

## 三、React懒加载：等待、失败与状态身份

下面是教学用TSX片段，假定项目已配置React、TypeScript和支持动态import的构建器，AdminPage提供default导出的React组件，外层应用已有错误边界：

```tsx
import { lazy, Suspense } from "react";

const loadAdmin = () => import("./AdminPage");
const AdminPage = lazy(loadAdmin);

export default function AdminEntry() {
  return (
    <Suspense fallback={<p role="status">正在加载管理页面…</p>}>
      <AdminPage />
    </Suspense>
  );
}
```

lazy在第一次尝试渲染时调用加载函数，等待解析结果的default组件，并缓存加载Promise及结果。声明放在模块顶层，避免每次父组件渲染重新创建组件类型、造成状态重置。若只有命名导出，可显式映射成带default字段的对象，但要确认导出确实是组件，不要吞掉类型错误。

Suspense处理等待，不能充当下载失败兜底。lazy加载Promise拒绝时，React把错误交给最近的Error Boundary；错误边界应提供可理解的失败说明与恢复入口。加载失败可能是离线、Chunk被删除、CSP阻止、地址错误或模块自身异常，不能都提示用户“再点一次即可”。

仅重置错误边界不保证重新调用同一个lazy加载函数，因为其结果被缓存；动态模块加载失败的缓存和重试行为还受运行时及浏览器影响。恢复需由框架支持的重试机制或受控页面重载承担，并避免无限自动刷新。表单有未保存内容时，应先保护状态，不能为消除错误直接丢弃输入。

加载边界应按用户可理解的区域设置。例如报表图表单独等待时保留筛选栏与标题；页面级切换可展示布局稳定的占位。若新内容等待时整个应用消失、焦点丢失或屏幕阅读器没有提示，字节减少仍可能降低体验。已显示内容的过渡可结合框架导航与Transition策略，但不会让网络和CPU成本消失。

懒加载只推迟到“尝试渲染”的时刻；如果页面一开始就渲染AdminPage，它仍立即开始加载。真正按需的高级编辑器应在用户打开功能后才进入组件树，且关闭、离开后要防止迟到结果触发已过期的业务动作。

## 四、预取、预加载与瀑布

### 4.1 不同提示解决不同阶段

当前导航确定需要的关键资源应尽早可发现；预加载（Preload）适合已知当前会用、但浏览器不易及早发现的资源；预取（Prefetch）面向未来可能导航，在不影响当前关键资源的前提下准备。资源提示不是无条件执行保证，其调度与支持需按目标浏览器验证。

webpackPrefetch、webpackPreload是构建器识别的注释，用于生成相关提示；原生模块图还存在modulepreload等机制，不能把它们的处理方式和打包Chunk脚本完全混同。使用框架时先了解它已经做了什么，避免手写提示造成重复请求。

对高概率下一步，可以在链接进入视野、键盘聚焦或用户悬停等意图信号出现时准备；触摸设备没有可靠悬停，不能只设计鼠标路径。低概率、高体积的功能通常等明确打开再加载。弱网络、节流偏好和昂贵移动流量应减少投机加载，且不能把浏览器网络信息API可用性视为普遍保证。

显式调用import进行预热会加载并求值模块，若模块顶层打开连接、注册监听或发请求，会提前产生副作用。应把这些动作放在明确生命周期中并可清理。仅为了网络预取时，应优先使用框架或构建器提供、语义明确的机制。

### 4.2 代码和数据不要串行等待

一种反例是：用户点击报表，下载路由代码，组件挂载后才请求报表数据，数据返回再下载图表库。这条瀑布可能比一个稍大的首屏包更慢。

若路由已能确定参数和权限，可由路由加载器并行准备代码与数据，并让图表依赖按合理边界提前发现。数据预取仍需授权、取消和缓存策略，不能为了性能预取所有用户资料。代码预取成功也不代表业务数据仍新鲜，应按缓存新鲜度判断是否重新验证。

验证时在冷缓存和受限网络下查看请求发起者、开始时间和依赖链，而不只看总请求数量。减少瀑布比机械减少一个文件往往更有价值，但必须以实际用户旅程测量证明。

## 五、Tree Shaking：删除代码的前提是证明不影响行为

### 5.1 静态结构和副作用

ES Module（ESM）的import/export结构便于构建期分析哪些导出被使用。构建器先确定使用关系，再结合副作用分析和压缩优化删除可安全移除的部分。CommonJS的动态require、条件导出和运行时对象修改会增加难度，但“CommonJS绝对不能优化”过于绝对，具体能力取决于构建器版本和模块形式。

副作用（Side Effect）是模块求值会改变外部可观察状态，例如导入CSS、安装Polyfill、注册全局事件、初始化插件。一个导出没人引用，不代表执行整个模块没有价值；若删除它会让样式或初始化消失，就不能仅按导出使用情况删除。

webpack中的usedExports分析导出使用，sideEffects元数据帮助判断能否跳过整个模块及相关子树，生产压缩器再进行相应优化。开发包常保留更多调试代码，验收必须使用生产构建。转译若过早把ESM变成难分析形式，也会削弱优化，应检查整条转译流水线。

### 5.2 sideEffects不是性能开关

假设一个自有组件包明确知道只有CSS和初始化文件需要保留副作用，可在package.json写类似片段：

```json
{
  "sideEffects": ["**/*.css", "./dist/register.js"]
}
```

这些路径必须匹配实际发布产物，而不只是源代码。未列出的文件是在作“无副作用”承诺，不是要求工具猜测。若register.js通过一个被整体移除的入口子树才可达，也不能指望仅列出文件名就让它从任何地方自动执行；需要保证初始化入口被实际导入，并在生产产物测试。

错误地设置sideEffects:false可能把必要CSS、Polyfill或注册逻辑删掉，形成“开发正常、生产无样式”的故障。应逐个核查模块顶层行为，并在消费者样例中验证样式和初始化。纯函数注解也只是对某个调用可删除性的承诺，不能用于掩盖真实副作用。

### 5.3 导入方式和动态访问

命名导入不等于一定小包，命名空间导入也不等于一定整包。关键是工具能否证明哪些成员被使用。例如固定读取utils.format可能被分析，而utils[userSelectedName]需要保留更多候选。一个巨大库即便只写命名导入，也可能通过公共初始化拉入大量依赖。

优先使用库公开支持的按需入口或可摇树ESM版本，不应依赖未承诺的内部深路径。深路径短期可能减小包，却会在库升级或exports限制变化后失效。对大量Locale或数据文件，应明确只打包支持范围；运行时任意选择语言包的写法可能把所有候选纳入构建。

Tree Shaking与懒加载可同时使用：可选图表在异步块中，图表库未用部分仍可移除。若所有异步块最终都被全量预取，虽然构建分组还存在，却可能失去按需传输收益。

## 六、Bundle分析要回答哪些问题

Bundle Analyzer展示模块在产物中的分布；构建统计用于解释模块、Chunk和依赖关系；浏览器网络、Coverage与Performance记录则反映具体旅程的加载与执行。它们各有边界：某次Coverage未执行不代表该代码永远不用，交互、错误分支和其他路由可能需要它。

一次有效分析应同时保存生产构建版本、锁文件、构建配置及以下证据：

| 观察 | 如何解释 | 后续动作 |
| --- | --- | --- |
| Initial JS | 当前入口启动需要哪些块及其合计成本 | 查意外静态依赖、框架启动和公共块 |
| Route Chunk | 路由额外需要什么，是否又依赖多个块 | 检查首次导航瀑布和可选功能 |
| 重复依赖、多版本库 | 不同包或解析路径保留多个实例 | 查锁文件、依赖范围、别名和兼容性 |
| 巨大Locale或静态数据 | 代码之外的数据进入JS | 限制支持范围或独立资源加载 |
| 压缩与原始大小 | 前者接近传输成本，后者是代码量线索 | 结合解析求值记录，不能由大小推算固定执行毫秒数 |
| Source Map映射 | 压缩片段对应真实源模块 | 关联错误与执行热点，并控制映射文件访问 |

去重不能只强制所有库用同一版本。两个消费者若依赖不兼容API，强行覆盖可能减小字节却引入运行时错误，应升级消费者或接受受控重复。React等对实例身份敏感的依赖还需专门验证，不能只凭名称相同判断安全。

Source Map帮助定位而不自动代表浏览器下载了它；分析工具可能把映射文件纳入报告，需要区分发布资源与实际用户请求。映射可能暴露源码细节，应遵循发布策略，但前端代码本身仍不是秘密存储位置，任何客户端产物都不能包含密钥。

报告回归时比较同等配置和构建模式，按路由汇总实际必需资源，避免只比较某一个文件。共享提取后main.js可能缩小，新增vendor.js却更大，单文件比较会得出错误结论。

## 七、从依赖优化到服务端边界

替换重型库前先确认真正使用的能力。少量日期格式化可能由平台API或小工具满足，但时区、语言和边界行为必须验证；不能为省包随意替换金融或复杂日期逻辑。若库不可替换，可选按需入口、删无用语言数据或延后罕用功能。

Polyfill补齐目标环境缺少的能力。删除前要先定义支持浏览器，再核对构建目标、API使用与实际覆盖；语法转译不自动补齐所有运行时API。只按开发者最新浏览器删Polyfill，可能让部分用户整个应用无法启动。

第三方分析和营销脚本可按业务需求延后，但须协调归因、同意管理与关键事件可靠性。把脚本从首屏移到用户点击瞬间，可能改善加载却损害交互响应。第三方拥有页面执行能力，还需来源治理与权限最小化；延迟加载不等于安全隔离。

React Server Components在支持它的框架中，把服务器组件自身实现及仅服务端使用的依赖留在服务端，可能减少客户端JavaScript。它不等同SSR：SSR输出HTML后仍可能需要客户端组件代码与激活；服务器组件还涉及专门的构建、序列化与客户端边界。扩大客户端边界可能重新把依赖带回客户端；服务端结果载荷、服务器成本和延迟也要计入。不能在普通客户端项目里添加一个文件名就自动获得这种收益。

## 八、缓存、部署与加载可靠性

内容哈希（Content Hash）让资源URL随内容变化，使不可变Chunk可长期缓存。HTML和资源清单决定引用哪组文件，通常需要更及时更新；不能把可变HTML和不可变Chunk一概永久缓存。webpack的runtime、模块标识与共享提取策略会影响文件变化范围，应通过连续两次构建检查，避免无关业务改动使所有公共块重命名。

先上传完整新资源并验证可用，再切换HTML或清单。旧标签页持有旧运行时，可能数小时后才请求旧路由Chunk，因此发布新版本后不能立即删除旧资源。保留期结合长会话、缓存、回滚窗口与存储成本确定，清理必须有策略。

Chunk加载失败排障先看URL、状态码、内容类型、CDN发布顺序、缓存和CSP。服务器把缺失JS路径重写成HTML有时返回200，却在执行时报语法错误；单看HTTP成功不足以证明资源正确。离线应明确提示，地址错误应修发布配置，旧版本文件缺失应修保留策略，不能全部靠无限重试。

Service Worker如参与缓存，还需版本更新、旧客户端和资源清理协议。只更新CDN并不代表所有客户端立即使用新代码。受控重载应有上限和版本检测，避免每次启动都陷入重载循环，并保留用户未保存输入。

## 九、性能预算与持续验证

为关键旅程设置两类预算：资源预算限制初始JS、路由增量和可选功能体积；体验预算约束加载、交互等待和主线程工作。具体阈值由目标设备、真实基线与业务风险决定，不给所有项目套同一KB数。

CI可在锁定工具版本下生成统计，比较同一路由的资源合计与基线；超过预算则阻断或进入明确例外流程，记录Owner、理由和到期计划。不能只在PR里贴一张图而无人负责。生产RUM按路由、设备与发布版本看是否真的改善，实验室记录帮助定位，避免因流量变化误判收益。

虚构案例：后台首页引入PDF导出库后初始JS增长。依赖图发现顶层按钮文件静态导入导出模块，尽管只有少数人使用，所有用户仍需承担。改为按导出意图异步加载后，需验证首页不再请求该库、第一次导出有等待反馈、连续点击不重复执行、失败可恢复，并保留导出权限与数据校验。只有这些证据通过后才可声称体验改善，不能只报告main.js缩小。

另一个反例是把所有路由prefetch，首屏图因带宽竞争更晚出现。修复不是撤销所有切分，而是按概率和时机控制预取，在弱网络与冷缓存场景复测。优化有明确假设、证据和回滚，比“文件越多越先进”更可维护。

## 十、面试完整回答与深入追问

### 1. 如何减少首屏JavaScript？

答：先分析生产依赖图和实际请求，区分初始、路由增量、共享及可选功能，再看传输、解析和执行。优先移除无用依赖与语言数据，把罕用路由或编辑器异步化，核对ESM和副作用配置；最后验证真实设备与用户旅程，设CI及RUM预算。首屏减少不能以首次操作长时间无反馈或加载不可靠为代价。

追问：main.js变小是否足够？答：不够。新增公共块可能让初始总量更大，要比较实际启动必需块之和，以及网络瀑布和主线程记录。

### 2. lazy为什么还需要Suspense和Error Boundary？

答：lazy把组件代码加载推迟到尝试渲染，并缓存加载结果。Suspense为等待提供UI，失败由错误边界处理。要同时处理导出形状、模块顶层声明、稳定占位和恢复策略。加载成功与业务成功是不同状态。

追问：点击重试只清错误边界行吗？答：未必，同一个lazy对象可能仍缓存失败结果，运行时也可能缓存失败；应使用框架支持的恢复或有上限的受控重载，不能无限循环或丢弃表单。

### 3. Tree Shaking为什么没生效？

答：先确认分析的是生产构建，再检查ESM是否被转译破坏、实际导出如何使用、模块顶层副作用、包元数据和依赖入口。CommonJS和动态属性访问会增加分析难度，但不能绝对断言永远无法优化。最终以构建输出和行为测试确认。

追问：直接sideEffects:false是否最快？答：它是正确性承诺，不是优化许愿。错误声明可能删除CSS、Polyfill或注册逻辑，必须标记真实有副作用文件并验证消费者生产行为。

### 4. 如何平衡预取和缓存？

答：对当前确定需要的关键资源提前发现，对高概率后续旅程选择性预取，对低概率功能按需加载。共享块按复用范围和变更频率设计，用不可变哈希资源配受控HTML更新，保留旧Chunk支持旧会话和回滚。

追问：把所有依赖放vendor是否最好？答：不一定。可能强迫每条路由下载罕用库，也扩大变更失效范围；应对比冷缓存、复用和连续发布后的实际下载，不能只追求最大公共块。

## 十一、扫雷自测：答案与推理

1. **切分是否必然减少总字节？** 不是。它主要改变分组和加载时机，还可能引入运行时与重复开销；删除依赖和摇树才可能减少保留代码。
2. **动态import只下载不执行吗？** 不是。它使模块可用并涉及求值，因此顶层副作用可能在预热时发生，需明确生命周期。
3. **每个小组件都lazy是否更好？** 通常不是。额外边界、请求和占位成本可能大于节省，应优先路由与重型低频功能。
4. **Suspense能处理Chunk 404吗？** 不能作为失败边界。等待与错误是不同状态，lazy拒绝需要错误边界及恢复策略。
5. **命名导入是否保证只保留一个函数？** 不保证。导出结构、公共初始化、副作用和转译都会影响保留范围，必须查输出。
6. **CommonJS是否完全无法优化？** 不能绝对化。动态语义更难分析，但工具可优化部分形式，需结合版本与实际模块。
7. **Coverage没执行的代码都可删除吗？** 不能。它只代表当前录制旅程，其他路径、错误处理和路由仍可能使用。
8. **Brotli变小是否证明CPU更省？** 不证明。压缩主要影响传输，解析、求值、初始化需实测，没有通用字节到毫秒换算。
9. **发布后立即删旧Chunk是否节约合理？** 风险很大。旧标签页稍后仍会请求它，应按支持窗口保留并支持回滚。
10. **强制去重多个版本是否总安全？** 不是。消费者可能依赖不同API，必须先验证兼容，必要时接受隔离或重复，不能以体积牺牲正确性。
