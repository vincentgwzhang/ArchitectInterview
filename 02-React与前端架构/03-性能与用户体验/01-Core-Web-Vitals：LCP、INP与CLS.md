# 01 Core Web Vitals：LCP、INP 与 CLS

## 一、指标是用户体验结果，不是优化动作清单

核心网页指标（Core Web Vitals）分别观察主要内容可见、交互响应和布局稳定性。它们连接服务端、网络、资源、JavaScript 执行和页面渲染，不能仅由 React 团队或 CDN 团队单独负责。指标变好也不证明业务正确：付款按钮立即显示成功但交易失败，仍是严重问题。

截至 2026-11-24 核验的 Google 指标定义与建议阈值如下。浏览器实现、测量库和工具版本可能影响可用数据，应随报告保存版本，而不是把今天的实现当作永久标准。

| 指标 | 观察什么 | 良好 | 需要改善 | 差 |
| --- | --- | --- | --- | --- |
| LCP，Largest Contentful Paint | 视口内最大合格内容的呈现时刻 | ≤2.5秒 | >2.5且≤4秒 | >4秒 |
| INP，Interaction to Next Paint | 页面交互到下一次可呈现画面的响应延迟 | ≤200毫秒 | >200且≤500毫秒 | >500毫秒 |
| CLS，Cumulative Layout Shift | 最严重一组非预期布局移动的累积分数 | ≤0.1 | >0.1且≤0.25 | >0.25 |

评估使用真实访问的第75百分位（p75），并区分移动端与桌面端。p75 为2秒意味着约75%的观测不超过2秒，不是平均用户等待2秒。三个指标分别评估，不取三者平均，也不能平均各地区的p75得到全站p75。合并分位数需要原始分布或可合并的统计摘要。

除了设备类别，还应按路由模板、地区、设备能力、导航类型和发布版本分析。例如高端桌面流量占比上升可能改善全站数字，却掩盖移动端结算退化。分段过细又会导致样本不足，必须同时展示样本量、采样率、时间窗口和数据覆盖范围。

Core Web Vitals 不覆盖所有体验。搜索结果是否准确、网络请求何时完成、支付是否可恢复、键盘是否可操作，都需要业务和可访问性指标补充。它们是优化方向，不是产品质量的唯一分数。

## 二、先把浏览器执行过程讲清楚

浏览器收到 HTML 后解析结构，发现样式、脚本和图片；下载与解析可交叠，但样式计算、布局、绘制以及大量 JavaScript 工作需要协调。布局（Layout）决定元素几何位置；绘制（Paint）生成视觉内容；合成（Compositing）组合图层。下载结束不等于画面已经显示。

主线程正在执行一段不可中断的同步 JavaScript 时，输入处理和渲染可能排队。React 计算组件输出之后，浏览器仍需完成必要的样式、布局和绘制，因此“组件 render 很快”不能证明交互整体很快。

把链路分成三个问题更容易定位：主要内容什么时候能呈现，是 LCP 关注的加载路径；用户操作什么时候能得到下一帧反馈，是 INP 关注的响应路径；已经看到的内容是否突然移动，是 CLS 关注的稳定性。某个优化可能改善一个指标、损害另一个指标，例如过度预取抢占首屏带宽，或提前插入尺寸不确定的内容造成位移。

## 三、LCP：从最大内容反推关键路径

### 3.1 它如何形成

LCP 关注视口中符合条件的最大图片、文本块等内容的呈现时间，起点是页面导航，而不是图片请求开始。它不是整个页面全部资源加载完成，也不是第一次出现像素的 FCP（First Contentful Paint）。首屏先显示一个很小的 Logo，并不意味着主商品图已经出现。

候选元素可能随加载变化：先是标题，随后大图呈现并成为更大候选。因此先在浏览器性能记录中确认实际 LCP 元素，再决定优化哪一个资源。不要只优化团队认为的 Hero 图；不同屏幕尺寸可能让标题或另一张图片成为候选。页面交互等生命周期条件影响候选记录，应采用成熟测量工具处理边界。

对于作为 LCP 的网络图片，可以把主要等待近似分解为：

1. 首字节时间（TTFB，Time To First Byte）：请求文档到收到首字节，涉及连接、重定向、服务端与网络。
2. 资源加载延迟：文档开始响应后，直到浏览器开始加载关键图片。
3. 资源加载时长：图片下载所需时间。
4. 元素呈现延迟：资源到达后，等待解码、样式、脚本或显示条件满足。

这个分解适合资源型候选；文本没有对应图片下载阶段，不能机械套同一分解。真实导航还可能包含前一页面退出、连接和重定向成本，因此本地一次热缓存测试不代表用户访问。

### 3.2 怎样按主导阶段优化

TTFB 主导时，检查服务端查询、渲染、缓存命中、连接和地区距离。CDN 缓存公共内容可减少距离与源站工作；个性化页面不能用错误缓存键把甲用户内容返回给乙用户。缓存要同时设计失效和新鲜度，不能只追求命中率。

服务端渲染（SSR）可以让 HTML 早带内容与资源引用；静态生成（SSG）适合可提前生成的内容；流式响应（Streaming）可以尽早发送部分结果。但如果首屏内容仍藏在很晚的流片段里，或者服务端渲染本身很慢，LCP 仍会差。客户端激活（Hydration）是让服务端 HTML 接上客户端交互逻辑，过重的激活可能争用主线程，需要控制客户端包和组件工作量。

资源发现延迟主导时，把关键图片引用放在初始 HTML 的实际 img 中，避免等待 JavaScript 执行和第二次 API 请求才知道地址。CSS 背景图可能更晚被发现；确有需要时考虑精确预加载，但要避免预加载了与最终 srcset 选择不同的图片而重复下载。

下载主导时，使用适合显示尺寸的资源、响应式候选和合适压缩格式。现代格式也有编码、解码、兼容与内容质量取舍，不能只比较文件扩展名。首屏 LCP 图不要懒加载（Lazy Loading）；高优先级只是调度提示，不会绕过带宽和服务器延迟。把所有图片都设高优先级会丧失优先级区分。

呈现延迟主导时，检查阻塞样式、主线程长任务、字体等待、隐藏内容和动画。把图片从500KB压到200KB可能只是增加“下载完成后仍等脚本”的空档，若呈现仍被同一长任务卡住，最终 LCP 不一定改善。

### 3.3 图片示例与反例

以下是 HTML 教学片段，假设真实图片分别为640和1280像素宽，原始比例都是2:1：

```html
<img
  src="/assets/hero-1280.webp"
  srcset="/assets/hero-640.webp 640w, /assets/hero-1280.webp 1280w"
  sizes="(max-width: 640px) 100vw, 640px"
  width="1280"
  height="640"
  fetchpriority="high"
  alt="本季商品展示"
  style="width:100%;max-width:640px;height:auto"
/>
```

sizes 要表达实际布局宽度，浏览器再结合像素密度等条件选图；它不是强制下载某个文件。width/height 提供比例信息，同时帮助稳定布局。示例没有 loading="lazy"，因为假设它就是首屏关键图。若图片只是装饰，应按可访问性需求调整 alt；若它在页面下方，则应重新评估懒加载与优先级。

不要对所有路由都预加载同一张 Hero 图，也不要用过期预加载配置与新 HTML 引用不同资源。应在 Network 中核对请求发起者、优先级、缓存和实际下载数量，再看最终 LCP 是否改善。

## 四、INP：不是一次回调执行时间

### 4.1 三段延迟与两层统计

INP 观察点击、触摸和键盘交互的响应，不把所有滚动或鼠标移动都当作同类交互。单次逻辑交互可包含多个事件，测量关注从输入发生到下一次画面可呈现的时间：

- 输入延迟：事件发生了，主线程仍在忙，回调尚未开始。
- 处理时长：执行这一交互的处理逻辑。
- 呈现延迟：处理之后，等待下一帧所需的渲染和调度。

多数访问的 INP 接近最慢交互；交互很多时，定义会按每50次交互忽略一个最高延迟值，降低偶发异常影响。随后才在多次页面访问之间计算p75。不要把“页面内最慢或近最慢交互”与“全站第75百分位”混为同一种统计。没有发生合格交互的访问不能简单补成 INP=0，否则会美化报告。

INP 不是业务请求的端到端完成时间。点击后立即显示“处理中”，网络两秒后返回，第一帧响应可能很快，但业务完成仍慢。两者都要监控，不能靠展示加载动画掩盖业务失败。

### 4.2 先定位阻塞，再选择手段

录制真实慢交互，查看输入前的任务、处理调用栈和后续样式布局。常见错误是只看 click handler：真正阻塞它的可能是第三方统计脚本、激活或前一次无关计算。

长任务（Long Task）通常指主线程上超过50毫秒的任务。阈值是诊断线索，不表示49毫秒任务一定安全；多个任务和渲染成本仍会叠加。拆分工作要真正让浏览器获得处理输入和渲染的机会。连续 await Promise.resolve() 只排入微任务，微任务持续清空仍可能阻碍渲染，不能视为普遍让出主线程的方案。通过定时任务或受支持的调度 API 分片时，还要控制取消、顺序和总工作量。

例如本地对大量记录排序，分片期间用户修改了筛选条件，旧计算结果必须按请求序号或版本丢弃，不能覆盖新结果。优化响应能力不能引入错误状态。若总计算远超设备能力，应减少数据、索引、改算法或交给服务端，而不是无限拆小块。

### 4.3 React、列表与 Worker 的边界

减少一次更新触发的组件范围：把输入状态放在需要它的局部，避免在顶层每次键入都更新整页。先通过 React Profiler 确认重渲染来源，再用 memo 或 useMemo 处理有意义的重复计算；依赖变化每次都发生时，缓存可能没有收益，还增加比较与维护成本。

Transition 表达非紧急更新，让 React 有机会优先处理紧急交互，适合搜索框输入与较重结果视图分开。它不会把同步计算搬到后台线程：如果先同步扫描几十万记录，再在 Transition 中设置结果，扫描仍堵住主线程。输入受控值应及时更新，旧结果与等待状态也要明确，避免用户误以为筛选已经完成。

虚拟列表（Virtualization）只渲染窗口附近记录，减少 DOM、样式和 React 工作，适合大列表。但要处理动态行高、焦点、键盘操作、滚动定位和读屏体验。小列表不应为省几个节点引入复杂窗口管理。

Web Worker 在另一线程执行适合的 CPU 工作，如解析或索引，不直接操作页面 DOM。传输大对象的复制、序列化和协调也有成本；结果按版本校验并支持取消或忽略过期任务。若瓶颈是布局或 DOM 太大，移走纯计算不能自动解决它。

读写 DOM 交错可能导致布局抖动（Layout Thrashing）：修改样式后立刻读取几何信息，浏览器被迫同步计算布局，循环中反复发生。先批量读取、再批量写入，减少强制重排；如果读取必须依赖刚写的布局，则需重新设计批次与时机，而不是盲目套缓存。

## 五、CLS：移动的是谁，推动它的又是谁

### 5.1 分数与会话窗口

CLS 衡量非预期布局移动，分数没有时间单位。单次位移分数近似为“影响面积比例×移动距离比例”：影响面积包括元素移动前后的可见区域，距离按视口最大维度归一化。例如假设影响比例0.5、距离比例0.2，分数为0.1。它既考虑移动范围，也考虑位移，不是简单累计像素。

当前定义按会话窗口（Session Window）聚合：相邻位移间隔小于1秒，总窗口最长5秒，取累积分数最大的窗口；不是把整个长会话的全部位移无上限相加。与近期合格用户输入关联的某些位移会排除，常见判断涉及500毫秒窗口；这不是“用户点过按钮，此后所有变化都免责”。延迟响应超过窗口仍可能计入，滚动也不能被泛化为免计理由。

新元素出现或元素变大本身不一定计分，要看是否推动已有可见元素改变起始位置。诊断时记录显示的受影响节点可能是受害者，不是原因：标题向下移动，真正原因可能是它上方没有预留高度的广告。

### 5.2 工程治理

图片与视频设置正确宽高或 aspect-ratio，让内容到达前就能分配空间；比例错误会在加载后再次调整，因此不能随便填固定尺寸。自适应布局要同时验证各断点，不能以桌面稳定代表手机稳定。

广告、推荐和异步组件预留合理空间。Skeleton 是加载占位，应接近最终结构和高度，而不只是颜色相似。广告未填充时立刻折叠占位也可能推动内容；可以保留区域或在用户不受扰动的边界调整，代价是空白和展示效率，需要产品共同决策。

Banner 不应突然插到用户正在阅读内容上方。可采用预留区域或不会推挤正文的呈现方式，但覆盖式浮层又可能遮挡操作和损害可访问性，仍需验证。不要通过隐藏内容直到全部下载完才获得“零CLS”，那可能严重损害LCP和可用性。

Web Font 切换可能改变字宽、行高和换行。选择几何特征相近的回退字体、减少字体子集、控制加载策略并按需要调整回退字体度量。font-display: swap 让回退文字尽早出现，但字体切换仍可能移动；它不是零CLS开关。品牌一致性、首字可见和位移之间要按实际语言和字体测试。

## 六、Lab 与 Field：怎样把证据连起来

实验室数据（Lab）在受控设备、网络和操作脚本下测量，Lighthouse 与浏览器 Performance 面板适合定位和回归。它的优势是可重复，限制是脚本不一定覆盖真实用户的长会话、登录、广告和低端设备。一次导航型 Lighthouse 审计通常不能代表完整 INP；无真实交互时，主线程阻塞代理指标也不等于 INP。

现场数据（Field）来自实际访问。真实用户监控（RUM，Real User Monitoring）可关联自定义路由和版本；Chrome 用户体验报告（CrUX）是特定符合条件的 Chrome 用户群聚合结果，覆盖、窗口与归因粒度不同，不能直接当作所有用户的完整日志。

Lab好、Field差时，先检查人群与流程是否一致：弱设备、真实地区、冷缓存、页面停留时长、第三方内容、客户端导航、旧版本和后台恢复都可能改变结果。Field好、Lab差也要检查实验条件是否过度严苛或错误，而不是立刻否定实验。

SPA的客户端路由切换通常不等于传统新文档导航。不能每次路由变更都手动重置三个值，再称为标准Core Web Vitals。可以定义路由级自定义体验指标，但需明确起点和生命周期，并与标准文档级测量分开。支持软导航的实验机制须单独注明浏览器和工具版本。

RUM 应使用维护中的 web-vitals 等库处理生命周期，而不是手写几行 PerformanceObserver 就宣称完全复现所有标准边界。上报至少携带指标名、值、指标标识、页面访问标识、路由模板、设备类别、版本和导航类型。对同一指标多次更新应按库语义做更新或去重，不能把每条更新都当成新访问。

不要采集完整带查询参数URL、输入值或含个人数据的DOM文本；选择路由模板与受控元素标签。采样在访问层固定，避免只上报慢值或只上报成功访问。上报失败应有有界缓冲，不能阻塞业务，也不能无限重试产生新的性能负担。跨源iframe和浏览器API支持会限制页面脚本观测，因此RUM与浏览器聚合数据有差异时，要检查覆盖边界。

## 七、性能预算与故障排查闭环

性能预算（Performance Budget）是团队承诺的资源或体验上限，需有Owner、检测和超标动作。每个重要路由同时设置JS传输与执行、图片体积和LCP/INP/CLS目标；字节预算是可提前检查的原因指标，体验预算是结果，两者不能相互替代。

预算数值由真实用户基线、目标设备和业务风险确定。Google良好阈值可作外部参照，但不是所有团队都能立即达到的发布承诺。CI中固定构建、浏览器、节流和脚本，重复测量以区别噪声；资源明显超预算可阻断，接近边界的体验波动先检查稳定性。生产RUM按版本灰度观察，在足够样本下发现持续退化再扩大发布或回滚。

一个虚构排障案例：商品页移动端LCP退化。先排除流量结构改变，再发现新版本把图片地址放到客户端API结果中。Network显示入口脚本、API、图片串行，而图片下载本身没有明显变长。修复是在服务端已知图片时把引用提前放入HTML，并保持权限正确；验证资源发现阶段缩短，同时检查CLS占位和JS执行没有退化。这里不给虚构性能提升百分比，真实效果必须实测。

另一个虚构案例：点击筛选后INP差。若输入延迟高，先看点击前是谁占用主线程；若处理时长高，定位同步过滤；若呈现延迟高，检查巨量DOM和布局。三个原因需要不同修复，不能统一加useMemo。上线后比较相同设备和路由人群，继续观察业务完成时间，防止只改善反馈动画。

事故处理顺序是确定受影响人群与版本、保留记录、定位主导阶段、选择风险最小的修复、灰度验证并设回归检测。不要同时改缓存、图片、框架和字体再声称知道哪个动作有效；必要时分阶段实验，以便解释因果和回滚。

## 八、面试完整回答与追问

### 1. 如何优化 Core Web Vitals？

答：我先按移动和桌面、路由、地区、设备和版本查看RUM的p75及样本量，确定受影响人群。对LCP确认实际候选并拆TTFB、发现、下载和呈现等待；对INP拆输入、处理和呈现；对CLS找推动内容移动的原因。再用可重复实验验证假设，设置资源与体验预算，灰度观察同类人群，关联发布防回归。不会只背三个阈值或把Lighthouse分数当成全部用户体验。

追问：为什么不用平均值？答：平均可能掩盖慢用户，p75给出分布位置，但也不能覆盖所有长尾，所以同时看样本量、差体验占比与关键旅程失败。不同分段的p75不能直接平均。

### 2. 图片压缩了，LCP为何不变？

答：下载只是路径的一段。图片可能发现很晚，或者下载完仍被脚本、样式和隐藏状态阻塞。我会确认同一候选和同类访问的时间分解；若呈现等待主导，就减少关键路径脚本或调整显示条件，而不是继续牺牲画质压缩。

追问：SSR是否必然改善？答：不必然。服务端计算会影响TTFB，流式输出顺序和实际图片引用也很重要。必须看主内容是否更早到达并呈现，及客户端激活是否制造新的阻塞。

### 3. React Transition能解决所有INP问题吗？

答：不能。它帮助区分更新优先级，不会把同步计算移到Worker，也不能减少所有浏览器布局成本。先分清等待、计算和呈现，再考虑局部状态、减少重渲染、虚拟列表或CPU任务迁移，同时处理过期结果和取消。

追问：为什么await一个已完成Promise还卡？答：它继续安排微任务，不保证给浏览器一次渲染机会。需要真正让出调度机会或减少工作，且避免以分片为由让旧结果覆盖新输入。

### 4. CLS为零是否说明体验很好？

答：不说明。把内容一直藏起来可以避免位移却损害加载体验；覆盖式弹窗可能不推挤布局，却阻碍操作。我要保证空间预留、字体和异步内容稳定，同时看LCP、可访问性和业务旅程。

追问：用户点击后发生的移动都不计吗？答：不是。只有符合近期输入等排除规则的移动才可能排除，长延迟异步结果仍可能计入；无论分数是否计入，都应避免用户误点。

## 九、扫雷自测与完整答案

1. **p75达标意味着全部用户达标吗？** 不意味着。它描述约75%的观测所在边界，剩余用户仍可能很慢；要分段查看长尾和关键流程。
2. **DOMContentLoaded结束就是LCP吗？** 不是。它描述文档解析相关事件，最大内容可能稍后才下载和呈现，二者关注不同。
3. **关键图应懒加载以节流吗？** 首屏LCP图通常不应。延迟发起请求会拉长关键路径；页面下方非关键图才适合按需加载。
4. **给所有图片高优先级有帮助吗？** 不一定。资源仍竞争带宽与连接，全面提高无法表达真正重要性，还可能拖慢关键图。
5. **一个回调20毫秒能证明INP好吗？** 不能。输入可能先排队，回调后也有渲染延迟；应测完整交互到下一帧。
6. **Worker能修复巨量DOM布局吗？** 不能直接修复。Worker不能直接操作DOM，需减少节点与布局工作；它适合把独立CPU计算移走。
7. **图片宽高写错是否仍能防CLS？** 不能保证。预留比例与真实比例不符，加载后可能改变布局，应使用真实尺寸或正确比例。
8. **CLS是长会话所有位移之和吗？** 当前不是。取最大会话窗口累计分数，窗口受间隔和总时长限制，旧定义不能混用。
9. **RUM多次上报同一指标可当多个样本吗？** 不可。那会给变化多的访问更大权重，需按访问及指标标识更新或去重。
10. **实验变快可直接宣称生产提升吗？** 不可。实验只是受控证据，还要在相同生产人群、版本与窗口下验证，排除流量和缓存变化。
