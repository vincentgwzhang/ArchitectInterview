# 02. 索引、执行计划、锁、隔离级别与死锁

> 本章目标：面对慢查询与并发错误，能够沿“业务目标 → SQL 和访问路径 → 实际计划 → 等待与事务 → 验证”定位问题。索引优化不能破坏一致性，隔离级别也不能代替容量治理。
>
> 版本范围：主要以 PostgreSQL 17 为例；比较 InnoDB 时明确限定 MySQL 8.4。两者的默认隔离、存储布局与锁机制不同，不能将一种产品的实现当作 SQL 标准。本章场景和数据均为教学假设，不是用户项目经历或性能基准。

## 一、先确定慢在哪里、错在哪里

一次 Java 请求可能经历线程排队、等待数据库连接、发送 SQL、数据库锁等待、扫描与计算、结果传输、ORM 映射。数据库执行只占其中一部分。连接池等了两秒而 SQL 执行十毫秒，给查询加索引未必解决主因；一次 SQL 很快但请求调用了几百次，则可能是 N+1，即查一次主记录后逐项再查关联。

性能目标应写成可检验条件，例如“某租户最近 50 条订单，在规定并发与数据规模下达到目标尾延迟，同时写入吞吐与锁等待不退化”。p95/p99 表示 95%/99% 请求不超过的延迟；平均值会掩盖长尾。并发正确性目标则是“不超卖”“至少一位医生值班”“同一付款不能重复”，这些目标决定需要什么事务与约束。

先取得真实 SQL、绑定参数、调用次数、数据分布、事务时长和连接等待，再制定假设。排障记录中保存脱敏样本，不把令牌、患者资料或完整敏感参数写入公开日志。不能因为数据库 CPU 高，就先提高连接池上限；更多并发可能只是让同一资源上的竞争更严重。

## 二、索引如何减少工作量，又为什么有成本

### 2.1 B-tree 的工作方式与边界

B-tree 家族用多层有序页组织键值，内部页引导定位，叶层保存键及定位数据所需信息。高扇出让树较浅，等值查找可以沿路径定位，范围查询找到起点后继续扫描，有序遍历也可支撑排序。不要把 O(log n) 当作整个 SQL 的复杂度：命中后读取大量行、过滤、连接与排序仍可能很贵。

索引适合缩小候选集合，尤其是只需要少部分记录的查询。若报表读取表中绝大多数行，顺序扫描（Sequential Scan）可能比大量随机访问更合理；小表也可能直接扫描更便宜。“没有使用索引”是现象，不是错误结论。

写入必须维护相关索引，增加页修改、日志、缓存占用和磁盘空间。更新索引字段也可能放大维护；PostgreSQL 的部分更新可走 HOT 等优化，但不能据此假定索引没有写成本。删除索引前要考虑唯一性约束、低频重要查询和不同负载窗口，不可仅看一天使用计数。

### 2.2 复合索引：从排序顺序推导最左前缀

假设常用查询是：

~~~sql
SELECT order_id, created_at, total_amount
FROM orders
WHERE tenant_id = 7
  AND status = 'PAID'
  AND created_at >= TIMESTAMPTZ '2026-11-01T00:00:00Z'
ORDER BY created_at DESC, order_id DESC
LIMIT 50;
~~~

可评估 (tenant_id, status, created_at DESC, order_id DESC)。它先把一个租户的一个状态聚在一起，再在该区域按创建时间和 ID 排序，可快速从时间边界取 50 条。order_id 用来打破同时间戳的并列，使顺序确定。

若索引改为 (tenant_id, created_at, status)，created_at 的范围先决定一个较大的扫描区间，status 通常不能再像连续等值前缀那样缩小区间，可能需要扫描更多订单才能找到 50 条已支付记录。不过右侧列仍可能在索引层过滤，所以“范围之后所有列全部失效”过于绝对。

PostgreSQL 17 多列 B-tree 的扫描范围主要由左侧等值约束与首个非等值列的边界决定。缺少左侧条件时仍可能扫描索引，只是未必有效；其他访问方法、引擎与后续版本优化可能不同。“最左前缀”是理解有序访问的工具，不是 SQL 能否执行的语法规定。

列顺序也不是永远“区分度最高放第一”。如果查询必须先定位 tenant，且经常按 tenant 独立检索，把 tenant 放首位可能更符合查询族。若另一个高频查询不限制 status 却要按时间排序，上述索引跨多个状态的顺序未必直接满足它，应分别评估，避免一个超宽索引试图解决所有查询。

### 2.3 覆盖索引不等于绝不访问表

覆盖索引（Covering Index）包含查询需要的键和返回列，目标是减少读取主体记录。例如 PostgreSQL：

~~~sql
CREATE INDEX orders_paid_recent
ON orders (tenant_id, status, created_at DESC, order_id DESC)
INCLUDE (total_amount);
~~~

INCLUDE 的载荷列可用于返回，但不与键列一样参与有序搜索；加入大文本或频繁变化字段会使索引膨胀并增加写维护。在 PostgreSQL 中索引与堆表分离，即使列齐全，Index Only Scan 仍需判断 MVCC 可见性；页面的可见性映射不满足条件时仍访问堆，计划中可查看 Heap Fetches。频繁更新表不一定获得理想收益。

InnoDB 的聚簇索引把数据组织在主键树中，二级索引通常含主键定位信息，其“回表”路径与 PostgreSQL 不同。不能把 MySQL 主键覆盖逻辑直接套到 PostgreSQL，也不能把 Index Only Scan 的名称当作零 I/O 承诺。真正要验证的是总工作量、堆访问与实际延迟有没有降低。

### 2.4 可索引性、部分索引与索引上线

WHERE lower(email)=... 不一定使用普通 email 索引，可能需要匹配表达式的索引；隐式类型转换、排序规则和参数类型也会影响路径。LIKE '%term%' 通常不能指望普通 B-tree 高效定位，可评估适合子串检索的方案，但不应因此给所有搜索都换引擎。

部分索引（Partial Index）只收录满足谓词的行，例如只索引未完成订单，适合该集合小且相关查询重要的场景。规划器必须能够证明查询条件蕴含索引谓词；参数化或通用计划可能影响证明，不能只用常量 SQL 成功就保证线上同样使用。索引谓词变化也会增加迁移复杂度。

上线索引要评估构建时资源、锁等待、日志与复制延迟；PostgreSQL 的 CREATE INDEX CONCURRENTLY 可减少对正常写入的阻塞，但有更多扫描、等待、失败清理及事务块限制，不能承诺无影响。唯一索引还可能因既有重复数据失败。先在接近生产分布的环境验证，设资源与等待阈值，再灰度观察读收益与写代价。

## 三、执行计划：从估计树读到实际证据

### 3.1 EXPLAIN、ANALYZE 与安全边界

EXPLAIN 给规划器估计，不执行目标查询；EXPLAIN ANALYZE 会真的执行，并加入实际统计。常用读取分析：

~~~sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT order_id, created_at, total_amount
FROM orders
WHERE tenant_id = 7 AND status = 'PAID'
ORDER BY created_at DESC, order_id DESC
LIMIT 50;
~~~

不要在生产随意对 UPDATE/DELETE 加 ANALYZE，它会修改数据并加锁。即使 BEGIN 后 ROLLBACK，也可能产生负载、序列变化或不可回滚的外部副作用；对 SELECT 也要确认调用函数没有意外副作用。最好先在隔离环境，必要时以受控超时和权限执行。

计划是一棵执行树，从子节点供数给父节点理解。cost 是优化器成本单位，不是毫秒；rows 是估计输出数量，width 是估计行宽。actual time、rows 和 loops 则是执行观测，节点的时间不能简单全部相加，因为父节点往往包含子节点工作，且有并行与流水行为。

### 3.2 一段计划该怎样读

下面是刻意构造的讲解片段，不是实际测量输出：

~~~text
Nested Loop (... rows=100 ...)
  (... actual rows=5000 loops=1 ...)
  Index Scan (... rows=1 ...)
    (... actual rows=2 loops=5000 ...)
~~~

内侧实际 rows=2、loops=5000，意味着平均每次两行、共约一万行输出，而不是全查询只访问两行。若外侧原本估计 100 行却实际 5000 行，规划器可能低估嵌套循环次数。先找估计开始偏离的下层节点，而不是只看最顶层总耗时。

Index Cond 参与索引访问，Filter 表示取到候选后再筛；Rows Removed by Filter 很大意味着大量无效候选。Buffers 的 shared hit 表示从 PostgreSQL 共享缓冲命中，不等于没有 CPU、内存访问或整个请求都快；shared read 也不直接等于物理磁盘，因为操作系统还有缓存。必须结合时间、存储指标和负载解释。

Sort 关注排序行数、方法、内存及是否落盘；不能一看到排序就增大全局 work_mem，因为它按操作、连接和并行工作者叠加使用。每个请求多个排序，再乘高并发，可能造成内存超预算。

### 3.3 扫描和 Join 为什么会被选择

| 计划形态 | 怎样工作 | 适合与风险 |
|---|---|---|
| Seq Scan | 扫描表页并过滤 | 大比例读取、小表可能合理；大表筛出极少行时需查原因 |
| Index Scan | 按键找候选，再取主体记录 | 小集合常有利；大量随机读取可能变贵 |
| Bitmap 扫描 | 收集匹配位置，再按页访问 | 适合中等规模集合；可能丢失索引顺序并需重新排序 |
| Nested Loop | 对每个外侧行执行内侧访问 | 外侧小且内侧有高效索引时很好；外侧估错会放大 |
| Hash Join | 构建一侧哈希表，再匹配另一侧 | 常用于等值大集合；内存不足可能分批或落盘 |
| Merge Join | 按连接键顺序合并输入 | 有序输入有利；为得到排序可能额外付出成本 |

选择性（Selectivity）表示条件留下多大比例的数据，基数（Cardinality）通常指结果行数或集合规模。统计信息过旧、热点租户、列相关性都会让估计偏差。例如 tenant 和 status 独立分布的假设不成立：一个租户可能几乎全是未支付单。单纯提高单列统计不能总解决多列依赖，PostgreSQL 可评估扩展统计，但仍需检查具体条件是否受益。

参数化语句的通用计划与特定参数计划可能不同：小租户适合索引，大租户可能适合扫描。抓一个小租户计划不能证明全部流量已优化。更新统计、改查询、调整索引后，要保留典型与极端参数的前后对比；不要以关闭顺序扫描等强制设置当长期通用修复。

### 3.4 慢 SQL 之外的常见根因

返回百万行时网络、对象分配和序列化可能主导；索引只能减少找数据的成本，不能让无限结果免费。错误 Join 漏条件会产生结果膨胀，DISTINCT 虽能掩盖重复，却增加排序/哈希且可能掩盖逻辑错误。N+1 应批量或调整抓取，而不是只给每条小 SQL 加索引。

锁等待需要找阻塞者，连接等待需要查池与事务占用。计划在无竞争环境很快而线上很慢，应补充等待和并发证据。读副本滞后导致用户读不到刚写结果，也不能靠在副本上加同样索引解决一致性语义。

## 四、锁与 MVCC：读写能够并发不代表没有冲突

### 4.1 MVCC 保存多个版本，锁负责另一些问题

MVCC（Multi-Version Concurrency Control，多版本并发控制）让读取依据快照选择可见版本，减少普通读与写的直接互斥。它不是“数据库无锁”：两个写者修改同一行仍需协调，DDL 与读取可能在表级锁上冲突，外键与唯一性也有并发工作。

PostgreSQL 的 UPDATE/DELETE 创建或标记版本，旧版本在仍可能被快照需要时不能随便清理。长事务可能拖延清理并增加膨胀、索引与维护压力；长时间保持 idle in transaction 即应用不执行 SQL 却不结束事务，可能持续占连接和锁。VACUUM 是回收可清理版本等维护机制，不应把它当成随时强制清空所有历史版本的按钮。

在事务内等慢 HTTP 或用户输入，会无谓延长资源占用。需要外部支付时先设计状态与恢复边界，避免让一次远程超时把数据库锁住数十秒；但也不能简单把调用移出事务后忽略跨系统一致性。

### 4.2 行锁、表锁、意向锁不能混讲

行锁限制特定记录的并发修改；表级锁协调整表相关操作和结构变更。PostgreSQL 锁名中含 ROW 的表级锁仍然是表级锁模式，不能只按名字猜粒度。普通 SELECT 取得的 ACCESS SHARE 可与多数正常写入共存，但会与 ACCESS EXCLUSIVE 等不兼容模式冲突。

InnoDB 的意向锁（Intention Lock，例如 IS/IX）表示事务打算在表内取得某类行锁，方便与表级锁协调；它不是直接锁住所有行。InnoDB 的 record、gap 与 next-key 锁分别涉及索引记录、间隙以及二者结合，范围修改/锁定读的行为受隔离与访问路径影响。不要将这些机制称为 PostgreSQL 默认的间隙锁。

锁兼容关系要查具体产品；PostgreSQL 普通快照读、显式锁定读和 Serializable 的谓词依赖检测也不是同一种机制。面试先说明产品版本、SQL 类型、隔离与索引，才可能准确回答“锁了什么”。

### 4.3 锁住现有行不等于锁住不存在的业务对象

PostgreSQL 中 SELECT ... FOR UPDATE 锁查询取得的行，并不因为查不到一条业务号，就自动预留了这个不存在的业务号。防止同号创建应使用唯一约束；维护跨行不变量可锁一条稳定的父级/协调记录，或使用 Serializable 并正确重试。

锁库存通常更适合原子条件更新：

~~~sql
UPDATE inventory
SET available = available - 1
WHERE sku = 'sku-1' AND available >= 1
RETURNING available;
~~~

同一行上的竞争由数据库协调，条件在实际修改语义中保护不低于零；应用必须检查返回行数，零行可能是缺货或 SKU 不存在，需按业务区分。多个 SKU 一起扣减应在同事务并按稳定顺序处理，某项失败回滚全部。不要先查库存到 Java，再无条件写回旧数值减一。

FOR UPDATE NOWAIT 可用于不愿等待时快速失败，SKIP LOCKED 可用于竞争领取队列任务，但它会跳过被锁记录，不适合需要完整一致结果的普通业务查询。领取成功后任务仍可能崩溃，需任务状态、租约/恢复与幂等，不是加了 SKIP LOCKED 就获得可靠任务平台。

## 五、隔离级别：明确要防的异常，而不是盲目选最高

### 5.1 常见异常的具体含义

脏读（Dirty Read）读取未提交、随后可能回滚的数据；不可重复读（Non-repeatable Read）是同事务两次读取同一事实看到其他事务提交后的变化；幻读（Phantom Read）是重跑条件查询时匹配集合变化。丢失更新（Lost Update）则是两个操作者基于同一旧值计算，后写者覆盖前写者效果。

写偏差（Write Skew）更隐蔽：两个事务读取同一个跨行不变量，却修改不同的行，单行写冲突检查没有捕捉到联合结果。隔离的目标不是让每条读都“最新”，而是约定整个并发观察与执行允许什么结果。

### 5.2 PostgreSQL 17 的具体语义

| 级别 | 快照与保证 | 业务仍需承担什么 |
|---|---|---|
| Read Committed（读已提交） | 默认；每条语句取得自己的快照，不读未提交数据 | 同事务多次读可变化；跨行决策需额外保护 |
| Repeatable Read（可重复读） | 事务内一致快照，PostgreSQL 下也不发生传统幻读 | 可能发生写偏差；更新冲突可能导致事务失败 |
| Serializable（可串行化） | 成功事务的效果等价于某个串行顺序 | 可能因检测到危险依赖而失败，必须重试完整事务 |

PostgreSQL 的 Read Uncommitted 实际按 Read Committed 处理。SQL 标准规定最低隔离要求，产品可提供更强实现；因此“Repeatable Read 一定有幻读”不能不注明数据库。InnoDB 8.4 默认通常为 Repeatable Read，但一致读与锁定读等路径有不同语义，不能拿 PostgreSQL 的快照规则直接推导全部 MySQL 行为。

Serializable 不等于所有请求按真实时间顺序排队执行，更不涵盖数据库外部副作用。PostgreSQL 使用 SSI（Serializable Snapshot Isolation，可串行化快照隔离）追踪读写依赖等并发危险，在必要时拒绝事务，而非简单把每次 SELECT 都变成互斥表锁。应用无法重试时，仅把配置改最高可能导致错误率上升。

### 5.3 丢失更新：三种保护各有前提

余额 100，A 和 B 都读 100，各自减 10，再都执行 SET balance=90，最后只减一次。改成 SET balance=balance-10 是数据库内相对更新，能防这个单行旧值覆盖；余额非负还需把条件加进更新并检查行数。

乐观锁（Optimistic Lock）通过版本比较：

~~~sql
UPDATE account
SET balance = :new_balance, version = version + 1
WHERE id = :id AND version = :read_version;
~~~

零行意味着当前版本已改变或记录不存在，不能假装成功。重新读取后要重新作业务判断，而非重复发送旧 new_balance。它适合冲突相对少、愿意处理重试的场景。

悲观锁（Pessimistic Lock）先 FOR UPDATE，再在持锁事务内读取和修改，适合冲突明确且临界区短的场景，代价是等待与死锁风险。任何一种都不代替跨行规则：给每行 version 并不能自动保护“所有行合计必须满足某条件”。

### 5.4 写偏差：两位医生同时下班

初始 A、B 都值班，规定至少一位值班。T1 与 T2 都读到两人值班；T1 只将 A 设离岗，T2 只将 B 设离岗。修改不同行，两者若在允许此结果的快照隔离下提交，最终无人值班。它不是同一行丢失更新，却同样违反业务。

可选方案之一：所有下班事务先锁同一班次父记录，再读该班次最新值班情况并决定；在 PostgreSQL Read Committed 下锁定父记录之后的后续语句取得新快照，必须遵守所有写路径都先锁父记录的协议。若用固定事务快照，不能机械假设“等锁后所有普通读自动刷新”。

另一方案是 Serializable，让读取与写入都留在同事务，捕获序列化失败后从头读取、重新判断，某位医生的重试会发现仅剩自己，因而拒绝下班。也可改变模型，把可用名额建成受原子操作保护的协调状态，但要防计数与人员状态漂移。关键是保护整体不变量，而不是记一个隔离级别名称。

## 六、死锁：等待环、牺牲者与完整重试

### 6.1 与普通锁等待有什么区别

普通等待是 T2 等 T1，T1 能继续完成；死锁是形成闭环，例如 T1 持 A 等 B，T2 持 B 等 A。CPU 低但请求全部排队可能是锁等待，并不必然死锁。锁超时表示等待超过预算，也不能直接证明数据库发现了环。

PostgreSQL 检测到死锁后中止其中一个事务来破环；不要依赖某个固定事务必被选中。死锁错误与序列化失败不同，但都可能需要以完整事务为单位重试。错误后的事务不能当作正常事务继续提交，应回滚并按框架约定重新开启。

统一锁顺序能减少环：转账无论方向，都先锁较小 account_id，再锁较大 account_id，然后执行相应扣加。只把 UPDATE 的 WHERE 写成 id IN (...) 不一定承诺取得锁的顺序；要使用清晰可验证的协调方式。触发器、外键、其他表和升级锁也可能加入依赖，所以单一 SQL 表面顺序不是全部证据。

### 6.2 双会话实验：制造、观察、恢复

只在独立测试数据库运行：

~~~sql
CREATE TABLE lock_demo (
  id integer PRIMARY KEY,
  value integer NOT NULL
);
INSERT INTO lock_demo VALUES (1, 0), (2, 0);
~~~

按下面顺序在两个独立连接执行，保持事务不自动提交：

| 步骤 | 会话 A | 会话 B |
|---|---|---|
| 1 | BEGIN; | BEGIN; |
| 2 | UPDATE lock_demo SET value=value+1 WHERE id=1; | 暂停 |
| 3 | 暂停 | UPDATE lock_demo SET value=value+1 WHERE id=2; |
| 4 | UPDATE lock_demo SET value=value+1 WHERE id=2; 开始等待 | 暂停 |
| 5 | 仍在等待 | UPDATE lock_demo SET value=value+1 WHERE id=1; 形成环 |
| 6 | 若成功则 COMMIT；若失败则 ROLLBACK | 若成功则 COMMIT；若失败则 ROLLBACK |

预期只有一个事务作为这一轮胜者提交，其两行修改保留；牺牲者本轮修改全部撤销，因此先检查两行都为 1。再把失败者的完整两行递增作为新事务重新执行并提交，最终两行都为 2。若客户端有额外自动重试，观测可能不同，应先禁用或记录它。此处是实验预期，不是已执行结果。

修复时两个事务都先取得 id=1 再取得 id=2 的锁，短暂串行等待替代闭环。不要使用无限重试来掩盖持续死锁；记录错误、锁顺序和等待图，修正访问协议。

### 6.3 重试要保护业务效果，而不只是 SQL 成功

PostgreSQL 常见可重试信号包括 SQLSTATE 40P01（死锁）与 40001（序列化失败）。不是所有数据库错误都可重试：语法错误、权限拒绝和业务唯一性冲突需要分别处理，不能只按异常父类兜底。

一次重试应新建事务、重新读取、重新验证、执行完整修改并提交；对次数、总 Deadline、退避与抖动设置边界。调用栈多层都重试会放大负载，需统一责任。若第一次已经产生邮件、支付等外部副作用，数据库回滚不能撤销；用稳定业务操作 ID、外部幂等与 Outbox 等机制避免重复。Outbox 是同事务记录待发事实、再可靠转发的模式，转发仍可能重复，消费方也要去重。

提交响应丢失与明确被数据库回滚不同，不能把“结果未知”当 40001 随意重做。应按业务键查证已提交效果，必要时提供处理中状态。技术重试不保证业务可重入，幂等需要持久约束与恢复设计。

## 七、可操作的 PostgreSQL 17 实验与检查路径

### 7.1 一份查询实验的输入与预期

以下建立独立教学表，避免与仓库其他示例混用：

~~~sql
CREATE TABLE orders (
  order_id bigint PRIMARY KEY,
  tenant_id bigint NOT NULL,
  status text NOT NULL,
  created_at timestamptz NOT NULL,
  total_amount numeric(18,2) NOT NULL
);

INSERT INTO orders
SELECT g, (g % 100), CASE WHEN g % 3 = 0 THEN 'PAID' ELSE 'NEW' END,
       TIMESTAMPTZ '2026-01-01T00:00:00Z' + g * INTERVAL '1 minute',
       12.50
FROM generate_series(1, 100000) AS g;

ANALYZE orders;
~~~

先执行第三节的 EXPLAIN 查询，记录估计、实际行、排序与缓冲；再建立第二节的覆盖索引，重复相同查询。教学假设是该索引可能减少扫描和排序，但不预言固定计划或速度：优化器选择受统计、缓存和参数影响。这个均匀生成集不能代表热点租户，需再以大租户、小租户和高更新数据验证。

冷/热缓存、重复运行、并发与统计更新时间都要记录；不要把第二次自然变热的缓存收益全部归给索引。验收也要测 INSERT/UPDATE、索引大小和复制负载，不能只看 SELECT 变快。实验结束在测试环境清理，不向生产复制建表或批量插入命令。

### 7.2 查阻塞链与事务年龄

可先看等待类型和阻塞 PID：

~~~sql
SELECT pid, state, wait_event_type, wait_event,
       xact_start, query_start,
       pg_blocking_pids(pid) AS blockers
FROM pg_stat_activity
WHERE datname = current_database();
~~~

blockers 非空时沿 PID 找上游，不只杀最慢的等待者。结合 pg_locks、事务年龄和应用请求 ID 识别“长期不提交”的源头，查询文本与更多信息的可见性取决于权限。诊断帐号最小授权，不把系统视图里的 SQL 随意导出。

取消一条语句和终止连接不同；取消后应用可能仍留在失败事务里不回滚，阻塞未必立刻按预想恢复。处理生产阻塞前明确业务代价、回滚成本和责任人，先止住持续进入的同类工作，避免不断杀连接造成重试风暴。工具操作必须配合应用恢复逻辑。

### 7.3 监控要形成因果链

Slow Query 记录查询执行异常；调用次数揭示 N+1；扫描/返回比揭示无效工作；Buffer Hit 反映缓存路径但不保证低延迟；Lock Wait 与 Deadlock 反映竞争；Connection Wait 反映应用获取连接的排队；Replication Lag 反映副本追赶落后。后者既影响只读流量的新鲜度，也可能由重写、建索引或大事务放大。

按规范化 SQL 标识或受控标签聚合，避免原始参数作为高基数指标。用基线比较上线前后：读取 p99 改善，但写入锁等待和日志激增，就不是无条件成功。热点需要分租户或操作类型观察，同时防敏感信息暴露。告警应包含影响面、持续时间与行动入口，而非只有“命中率下降”。

## 八、Solution Architect 的取舍：效率、一致性与成本一起评估

索引使读更便宜却使写更贵；更强隔离减少允许的并发异常，却可能增加冲突与重试；短事务降低锁占用，但拆开强不变量会产生新的恢复问题。选择应围绕业务容错边界，而不是默认所有业务用一个隔离级别。

普通列表读可以用 Read Committed 与合理索引；库存单行扣减可用条件原子更新；跨行不变量需要共同锁协议或 Serializable；长报表可用一致快照，但需控制事务时长和对清理的影响。每种方案都先定义失败时用户看到什么、是否能安全重试、由谁对账。

扩容数据库之前先确认是否访问了不必要数据；增加缓存之前先定义陈旧容忍与权限隔离；分库之前确认强不变量是否跨分片。减少无效扫描、缩短事务和修复错误重试往往比新增组件更直接。若团队无法稳定执行死锁/序列化重试，再高的理论保证也无法变成可靠业务服务。

## 九、完整面试回答与追问

### 9.1 “一条订单查询很慢，你怎么优化？”

回答示例：“我先把连接等待、锁等待、SQL 执行和结果映射分开，再拿真实 SQL、参数分布与调用次数。检查返回量与 Join 正确性，用受控环境的 EXPLAIN ANALYZE 看基数偏差、扫描、过滤、循环和排序。按查询族设计复合索引，覆盖列只放有收益的字段，并测试写放大。最后用相同语义与负载比较尾延迟和资源，保留热点参数与回退方案。”

追问：“没用索引是不是一定错？”答：“不是。大比例读取或小表可能顺序扫描更便宜；先看代价和实际工作。反过来，走了索引却扫描很多候选再过滤，同样可能很慢。”

追问：“计划很快，接口仍慢？”答：“查连接池等待、长事务阻塞、一次请求的 SQL 次数、网络传输和 ORM 对象构建，不能把单条计划当完整链路。”

### 9.2 “Repeatable Read 能保证不超卖吗？”

回答示例：“必须说明数据库和 SQL。可重复读不自动替我保护每个业务规则。单行库存用条件更新并检查结果，可避免旧值覆盖和负数；多行组合扣减放同事务并统一锁顺序。对跨行不变量还要共同协调或可串行化与完整重试。PostgreSQL 的可重复读提供一致快照，仍允许写偏差，不能只背隔离名称。”

追问：“升 Serializable 就完了吗？”答：“成功事务可串行解释，但应用必须处理序列化失败，从头重新读与判断。外部支付、邮件和提交结果未知另有幂等与恢复责任，数据库隔离不涵盖它们。”

### 9.3 “死锁该如何处理与预防？”

回答示例：“我用等待图判断环而非只凭慢，捕获数据库确定的死锁回滚，限定次数地重试完整幂等事务。预防统一资源访问顺序、缩短临界区、检查触发器/外键参与的锁和索引扫描范围。记录死锁率与业务影响，持续发生时修协议，不靠无限重试。”

追问：“加索引就能消除死锁？”答：“不能。合适索引可缩短查找和部分引擎的扫描锁范围，降低冲突机会，但 A→B 与 B→A 的环仍可能存在。还需统一顺序，且不能保证所有隐式锁都消失。”

## 十、扫雷自测与完整推理

### 10.1 复合索引没写第一列条件，是否绝不可能使用？

**答案：不是。** 可能扫描索引或由其他优化路径使用，但未必能高效缩小搜索区域。要区分“能采用”与“收益足够”，并注明引擎与版本。PostgreSQL 17 B-tree 的左侧等值和首个非等值边界是分析扫描范围的主要依据。

### 10.2 Index Only Scan 的 Heap Fetches 为何不为零？

**答案：覆盖字段解决载荷来源，不自动解决版本可见性。** PostgreSQL 某些页仍需访问堆判断 MVCC 可见性；近期更新、清理与可见性映射状态会影响结果。需观察真实负载，不是索引名字含 Only 就保证不访问表。

### 10.3 内侧 actual rows=2、loops=5000，是只返回两行吗？

**答案：不是，表示每次循环平均两行，总量约一万。** 还需结合外侧实际行与估计，判断是否低估循环次数。节点时间包含关系与并行执行也需考虑，不能把所有时间盲目相加。

### 10.4 能对生产 DELETE 随便加 EXPLAIN ANALYZE 吗？

**答案：不能。** 它真的执行删除并取得锁；回滚也不代表无负载与无副作用。先用不执行的 EXPLAIN 或隔离环境，审查函数、触发器和外部效果，再决定受控验证方式。

### 10.5 MVCC 是否意味着写永远不等待读？

**答案：不能这样概括。** 普通快照读常不直接阻塞正常行修改，但显式锁定读、DDL 表锁、唯一性检查等会形成冲突；不同产品和语句规则不同。长快照还可能阻碍版本清理，即使没有直接行锁等待也会增加成本。

### 10.6 FOR UPDATE 查不到订单号，就能安全创建吗？

**答案：在 PostgreSQL 中不能靠锁住零行预留不存在的号码。** 用唯一约束仲裁重复，跨行决策另用协调记录或 Serializable。应用预检查可改善提示，但无法排除并发竞态。

### 10.7 两位医生修改不同行，为何还违反约束？

**答案：他们的决策共同依赖“至少一位值班”，但写集不相交。** 单行版本或写锁不必然发现写偏差。需串行协调共同父记录并正确读最新情况，或让完整 Serializable 事务失败重试后重新判断。

### 10.8 死锁后只重跑最后失败的 UPDATE 可以吗？

**答案：不可以把它当通用处理。** 事务可能已被中止，前面的修改已回滚，而且先前读取决定也可能过时。回滚、新事务、重新读取和验证，再执行整个业务操作；确保外部效果不会因重试重复。

### 10.9 加大连接池能解决连接等待吗？

**答案：先找持有连接的原因。** 若数据库已饱和或被长事务阻塞，更多连接只会增加排队和竞争。先缩短占用、修复泄漏与锁等待，依据数据库可承受并发配置上限，再验证总预算。

### 10.10 使用 SKIP LOCKED 是否得到完整一致的订单列表？

**答案：不是。** 被其他事务锁住的行会被跳过，适合竞争领取某些工作，不能当作完整业务查询。领取后崩溃仍需要状态、租约恢复与幂等；这种锁选项解决竞争获取，不保证任务最终完成。

## 十一、速记与执行边界

- 索引优化是减少工作量：定位、过滤、排序、主体访问都要算，也要算写维护。
- 读计划看估计与实际、rows×loops、过滤、缓冲和落盘；不把 cost 当毫秒。
- MVCC、锁、隔离与业务约束各有职责，说明产品和语句再下结论。
- 条件更新保护单行条件，版本比较识别旧值覆盖，共同协调/Serializable 保护适用的跨行决策。
- 死锁找等待环；重试新事务、重读与重新判断；提交结果未知先查证。
- 验证读收益时同时检查写延迟、锁、连接、日志与副本滞后。

本章 SQL、双会话与计划片段均为教学材料；计划数字刻意标为构造示意。未在 PostgreSQL/MySQL 实例运行建表、执行计划、死锁与隔离实验，不声称任何固定计划或性能提升已验证。完成了原主题覆盖、全部小节自足性、SQL字段一致性、事务时序及自测答案核对；独立逻辑检查不能替代真实引擎实验。实际落地须按指定版本以两个独立连接验证提交、回滚、等待、重试与最终不变量。
