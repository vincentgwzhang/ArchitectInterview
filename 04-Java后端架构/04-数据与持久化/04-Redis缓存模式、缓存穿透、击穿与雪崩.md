# 04. Redis 缓存模式、缓存穿透、击穿与雪崩

> 目标：能从业务允许的陈旧程度、流量与数据库容量推导缓存方案，解释正常命中、未命中重建和 Redis 整体不可用三条路径，避免把缓存变成数据库事故放大器。
>
> 适用范围：以数据库为权威数据源、Redis 保存可丢弃副本的 Java 后端。命令例子采用 Redis 7.x 常用能力，不依赖新版本专属解锁命令；官方 latest 文档用于核验通用语义，不表示所有模块、托管产品和客户端能力相同。Bloom Filter 是否由模块提供须核对实际部署。全部容量数字与案例为教学假设。

## 一、先确定缓存允许牺牲什么

### 1.1 缓存价值来自避免昂贵工作

缓存（Cache）保存可复用结果，减少数据库查询、计算或远程往返。是否有价值取决于结果能否复用、命中后省多少工作、失效与维护代价多大。例如公共商品说明复用高，按用户、时间、复杂过滤组合生成的查询结果则可能每次都不同，缓存占内存却很少命中。

先记录请求速率、热点分布、数据库单次成本和容量上限，再估计正常回源。假设请求 10000 次/秒、命中率 95%，理想普通未命中约 500 次/秒；缓存全部不可用则可能逼近 10000 次/秒。数据库若只承受 800 次/秒，不能直接让所有请求绕过缓存。

命中率（Hit Ratio）高不保证服务快：一个巨大结果虽然命中，仍可能消耗网络与反序列化；Redis 排队、应用 GC、连接等待也可主导尾延迟。优化目标应是业务延迟、可靠性与总成本，不是单独追求命中率。

### 1.2 陈旧预算与权威读取

陈旧预算（Staleness Budget）是业务允许看到旧值多久，以及在哪些场景允许。例如商品介绍允许短时旧值，支付余额和权限撤销不能机械套同一规则。TTL（Time To Live，存活时长）不是全部陈旧上界：若失效事件延迟、旧请求稍后回填或本地缓存另存一份，旧值可能比预想更久存在。

区分“用户浏览价格可缓存”和“下单必须重新验证权威报价”。不要用缓存库存直接决定扣减，写路径应在权威系统内验证版本、约束或预留状态。权限相关缓存也不能将可接受的商品陈旧时间直接用于撤权。

本章 Redis 不是 Source of Truth（权威事实来源），丢失后可重建。如果选择把 Redis 当唯一队列、余额或去重权威，就已改变问题，需要独立讨论持久化、复制故障、恢复与数据丢失承诺；不能沿用“缓存随时丢都没事”的假设。

## 二、缓存模式：谁负责读写，什么时候算成功

### 2.1 Cache Aside：应用协调数据库与缓存

Cache Aside（旁路缓存）的读路径是查缓存，未命中读数据库，再写缓存；写路径通常先提交数据库，再失效相关缓存。应用能控制业务查询、TTL和失败处理，适合已有数据库应用逐步引入缓存。

~~~text
读：
  认证并校验参数，构造包含数据范围的键
  GET 缓存
  若有效命中：返回
  若未命中：经合并/限流许可读取权威数据
  成功读到：有限TTL写入；回填失败不改变已成功的读取结果
  权威确认不存在：按规则写短期不存在标记

写：
  在数据库事务中校验并提交业务修改
  提交成功后删除/标记失效相关缓存
  失效失败：记录可恢复任务并监控，不假装已同步
~~~

Redis 网络故障不是普通“查不到键”，数据库超时也不是“不存在”。三种结果必须分开，否则会把故障写成负缓存，或在 Redis 故障时无边界放大回源。

先删缓存再写库容易让并发读在数据库尚未提交时读旧值并回填。先写库后删缓存减少这类窗口，但仍不消除全部竞态。不要把常见顺序当作强一致协议。

### 2.2 为什么“先写库后删缓存”仍会旧值回填

具体交错：缓存为空，读请求 R 从数据库取到版本 7；写请求 W 提交版本 8 并删除缓存；随后慢 R 才把版本 7 放回缓存。删除执行成功，却留下新鲜 TTL 的旧内容。若缓存正常 TTL 很长，陈旧可能持续很久。

“延迟双删”尝试在写后隔一段时间再删，能降低某些竞态概率，但延迟无法覆盖任意慢查询、暂停与故障，不能证明一致性。失效重试也必须持久记录，不能只在进程内 sleep 一下后假定一定执行。

更严格的做法可以使用源版本、失效水位与条件回填：新版本失效时先推进可靠的版本下限，回填仅接受不低于该下限的数据。但只把 version 放在值里不够，键不存在时旧值仍可能成为第一份值；水位与缓存写入需原子协调，其保留、淘汰、失效乱序与故障切换也要设计。

对于必须读到刚写结果的调用，可返回提交时已知结果、在指定路径读主库，或携最低版本要求验证缓存。查只读副本也可能遇到复制滞后，不能把“绕过 Redis”自动等同“读到最新”。架构应按业务承诺选择成本，而非给所有请求承诺强一致。

### 2.3 Read/Write Through：缓存层统一后端访问

Read Through（读穿透）由缓存抽象负责未命中加载，应用调用统一读取接口；Write Through（写穿透）由该层协调写后端与更新/失效缓存。好处是集中序列化、加载和策略，代价是抽象更复杂，也更容易让调用者误判保证。

Redis 普通 GET/SET 不会自动读写关系数据库；这是应用库、代理或产品方案实现的模式。必须核对“写返回成功”意味着数据库已提交、缓存已更新，还是只完成其中一项。若数据库成功但缓存失败，要按契约返回并安排修复；跨资源没有原子协议时，换一个模式名不会消除双写问题。

适合读写入口能统一治理的系统；若脚本、后台作业和其他服务直接写数据库，缓存层看不到变化，仍需事件/CDC等失效机制。通过抽象隐藏故障细节之前，必须把责任和恢复方式说明。

### 2.4 Write Behind：快确认换来持久与恢复责任

Write Behind/Write Back（异步回写）先接受缓存或缓冲更新，再异步写后端，可能合并多次修改以提升吞吐。但若先返回成功，随后缓存节点丢失、缓冲被淘汰或回写失败，就可能丢掉唯一新数据。

必须明确持久日志、重放、写入顺序、失败重试、背压、停机清空与回写积压监控。对于“最后状态”可合并的浏览计数，丢失容忍和重建可能可接受；对支付、订单成立、权限撤销，不能仅用可淘汰缓存承担可靠受理。

异步回写还可能在用户下一次读取数据库时看到旧值，或让旧回写晚于新回写落库。源版本与幂等条件更新可阻止回退，但需要后端配合。若无法清晰回答“接受后进程立刻死掉会怎样”，就不应为降低延迟贸然选该模式。

## 三、穿透：不存在的数据持续打到数据库

### 3.1 负缓存的对象必须是权威“不存在”

缓存穿透（Cache Penetration）常指大量不存在键绕过缓存反复查库，例如随机商品 ID。Negative Cache（负缓存）保存明确的 NOT_FOUND 标记，后续在短 TTL内直接回复不存在，避免同一无效键反复回源。

不要用空字符串同时代表不存在、有效空值与反序列化失败，建议带类型的封装，例如 kind=NOT_FOUND 或 kind=VALUE、schemaVersion和payload。只有数据库成功确认不存在才写负缓存；超时、断路器拒绝、权限不足都不能混成全局不存在。

负 TTL应短于通常正缓存，并在成功创建对象后失效相应负缓存。否则先查后建会导致对象已创建却仍看不到。短 TTL只是缩短窗口，创建后的失效仍可能失败，所以需要明确写后读路径与修复机制。

### 3.2 参数校验、Bloom Filter 与限流各管一层

参数校验在进入数据库前拒绝明显无效 ID、页大小、非法查询组合，成本低但不能知道一个格式正确 ID是否存在。按调用身份、租户与接口预算限流，可阻止攻击者用大量随机合法格式键击穿系统。不能只按 IP，代理共享与恶意分散都会影响效果。

Bloom Filter（布隆过滤器）用多个哈希映射到位图，查询对应位都已设置时表示“可能存在”，有一位未设置则在完整正确维护的模型下表示“不存在”。它有假阳性（不存在却判断可能存在），标准模型不产生假阴性；但实际系统漏加载、新增写入延迟或错误重建，会把真实存在对象挡掉。不能把数学模型保证当作运营链路保证。

它适合大量明确 ID集合且无效查询多的场景，不适合任意复杂查询或无法可靠同步的权限结果。新增对象需及时加入、重建需版本切换，普通 Bloom Filter 不能随便清位删除，否则可能影响其他键。过滤器不可用时也要有受限降级；不能让一次冷启动把所有存在对象判为不存在。

### 3.3 负缓存也可能造成容量攻击

攻击者生成无限随机 ID，每个写一个短 TTL负值仍可消耗大量内存。应限制可缓存的负结果、入口速率与负缓存容量，区分可重复热点无效键和只访问一次的随机垃圾。优先前置校验与身份预算，不能认为“写了空值”就已解决穿透。

监控负缓存命中、回源不存在比例和键增长速度；若正缓存被大量负键挤走，整体命中率可能下降，反而加重数据库负载。安全与容量治理需要一起看。

## 四、击穿：一个热点过期引发同键重建风暴

### 4.1 Single Flight 合并的是同一个工作

缓存击穿（Hot-key Breakdown/Stampede）是热点键缺失时，大批请求同时加载相同数据。Request Coalescing/Single Flight（请求合并）让一个加载者工作，其余等待同一结果，减少重复回源。

Java 进程内可用“键到共享 Future”的映射：第一个请求创建任务，其他请求复用；成功或失败后都清理映射，防永久泄漏。它只覆盖单进程，100 个实例仍可能有100次加载；还需全局回源预算。等待者必须有各自期限，不能一个请求取消就把所有等待者共用任务误取消。

加载者异常要通知所有等待者并释放状态；等待超时后不能让所有等待者同时重新回源。失败退避或短暂故障抑制能减少连锁风暴，但不能把故障伪装成不存在。共享任务执行器也要有界，避免不同键各起一个加载任务耗尽线程。

### 4.2 互斥重建的完整流程

Redis 互斥重建可降低多实例重复加载：

~~~text
GET 数据键；有效则返回
在本进程合并同键请求
尝试获取该键的短租约锁
  成功：
    再次 GET，避免前一个加载者刚完成而重复工作
    若仍缺失：取得数据库回源许可，加载
    在仍符合版本/所有权协议时回填，设置TTL
    在 finally 中按持有者身份释放锁
  失败：
    有允许陈旧的旧值则按规则返回
    否则有限等待并重新查缓存
    仍无结果则快速失败或进入受限回源，不无限自旋
~~~

再次检查缓存（Double Check）消除“看到 miss 后，真正拿锁前已有人填好”的重复。锁不是数据库容量配额：大量不同键各持一把锁，仍可能同时回源数万次，必须有总并发/速率限制。

进程暂停使租约到期后，其他实例可重建；旧持有者恢复时仍可能写入旧结果。防误删锁和防旧结果回填是两件事，后文分别说明。对可丢弃缓存允许少量重复加载可以简化，但不能让这把锁承担唯一扣款保护。

### 4.3 逻辑过期、后台刷新与陈旧返回

逻辑过期（Logical Expiration）把 softExpireAt 存在值中：超过软期限仍保留数据，在业务允许时返回旧值并异步刷新；物理 TTL作为 hardExpireAt 的最终保留边界。这样热点刷新期间不必让所有请求等数据库。

它必须限定最大陈旧时间、失败重试与无旧值路径。首次加载、物理淘汰、Redis 重启时仍是冷 miss；软过期不能处理这些情况。刷新失败不能无限延长旧权限或旧价格，超过硬预算应转权威读取、降级或拒绝。

后台刷新适合流量稳定的热点，不适合给所有键永久定时刷新，否则无人访问的数据也持续消耗数据库。热键判定、刷新频率与队列容量需受控；刷新任务饥饿时应告警，而不是只看前台仍有旧值可返回。

## 五、雪崩：大量键失效或整个缓存层故障

### 5.1 TTL Jitter 和预热只能解决部分问题

缓存雪崩（Cache Avalanche）包括大量键集中到期，也包括 Redis 整体不可用导致大规模回源。TTL Jitter（过期时间抖动）在基础期限周围加入随机偏移，分散同批写入的到期点。

例如正缓存采用 300 到360秒，而非全部300秒；如果业务最多允许300秒陈旧，就应改用240到300秒，不能为分散过期悄悄扩大承诺。抖动无法缓解一个超热点单键，也不能防止节点故障、FLUSH类误操作或集群网络中断。

分批预热可降低发布或冷启动冲击，但要限速、按实际热点优先，避免把全库扫进 Redis挤走已有热数据。预热失败不应阻止无关业务正常启动；必要数据的启动条件则需单独定义，不能把“预热完成”误当缓存永不会丢。

### 5.2 Redis 不可用时先保护数据库

Redis 超时必须短于总请求预算，设置有限重试和熔断。Circuit Breaker（熔断器）在持续故障时暂时停止调用，恢复时只放少量探测；避免每个请求都等待长超时后再查库。但熔断 Redis 不等于允许无限查询数据库。

回源 Bulkhead（隔离舱）限制并发工作，Rate Limit限制单位时间入口，Load Shedding（负载卸除）拒绝超出可承受预算的请求。可以优先核心读、给可容忍业务返回有界陈旧本地数据，关闭低价值报表；关键权限或金额不能随意返回旧值或默认零。

前述10000次/秒流量而数据库预算800次/秒时，必须让其余请求降级、排队到有限期限或拒绝。每实例配置800若有20实例，实际可能放出16000，不能把本地限制当全局限制。分配预算、实例扩缩容与共享限流器故障都需要设计。

### 5.3 多可用区与恢复不能替代容量计划

Multi-AZ（多可用区）部署与主从切换降低单点故障影响，但不能解决热键、坏命令、错误配置和应用同时回源。Redis 常见复制为异步，副本读可能滞后，故障切换也可能丢失部分已确认状态；缓存丢失可重建，锁或唯一业务状态丢失则有不同后果。

切换期间客户端拓扑、连接重建和重试会产生额外压力，恢复后别瞬间解除所有限制。逐步增加探测与回源，按热点受限重建，观察 Redis命中、数据库负载和错误率。不能通过全量失效或无界预热“修复缓存”，导致第二次雪崩。

重要系统应演练缓存整个不可用，而不只删除一个键。验收时同时验证拒绝是可预期、核心数据库未被拖垮、恢复时间和陈旧预算满足约定。

## 六、Hot Key、Big Key 与容量治理

### 6.1 热键：单个分片也可能先于集群饱和

Hot Key（热键）是请求高度集中于某个键，导致单分片 CPU、网络或排队饱和。增加分片数不会自动把一个键拆开；客户端重试还可能继续放大热点。

进程内 L1缓存可分担读取，但要限制容量、TTL和身份范围，承担多副本失效与内存成本。只读热点也可在业务允许时副本读取，但要接受滞后；复制多个独立缓存键可分散读，却增加更新失效和一致性治理。

可拆分的数据如按桶聚合计数，可让多个键承载工作；单一强约束库存不能任意拆成多个独立数字后承诺不会超卖。先确定数据语义能否分片，再谈技术拆键。热点检测应避免把所有原始键都作为指标标签，采样与受控诊断更可持续。

### 6.2 大键：元素多、值大和命令贵分别处理

Big Key（大键）可能是巨大字符串，也可能是拥有大量元素的 Hash/Set/List等。成本不只在内存，读取巨值占网络与客户端堆，复杂集合命令占执行时间，删除与过期也可能产生延迟。

对大集合使用 HSCAN/SSCAN 等增量遍历，对键空间用 SCAN，避免在繁忙生产路径用 KEYS 全扫。SCAN 的 COUNT是工作量提示，不是固定页大小；迭代可能重复，变化集合中的出现情况不等于一致快照，需要容忍重复并明确“扫描期间被改动”的语义。SCAN完整迭代仍有总成本，并非免费。

UNLINK可将键从键空间移除、让内存释放工作在后台进行，减少某些同步释放停顿，但不消除后台CPU和内存回收压力。它也不是一次读取巨大值的解法。根治通常是值大小上限、分页API、合理拆分和生命周期管理，不能只换删除命令。

### 6.3 TTL 与 Eviction 是两种离开缓存的原因

Expiration（过期）按时间使值不再有效；Eviction（淘汰）在内存压力下按策略移除键。即使 TTL没到，值也可能被淘汰；noeviction则可能拒绝需要更多内存的写入，不意味着内存无限。

LRU按近期使用、LFU按访问频率思路淘汰，Redis具体策略有近似采样与适用键范围；volatile类仅从带过期的候选集合中选择，allkeys类范围不同。选策略前要明确实例只存缓存还是还混放不可丢状态，最好避免让可淘汰缓存与可靠队列/锁/去重权威混在同一失效域。

maxmemory不是整个进程RSS硬上限，复制缓冲、客户端和持久化相关开销还需预算。评估内存应包含键名、数据结构、序列化、碎片、复制与峰值，而非只用业务JSON字节数。TTL过长与负缓存垃圾也会挤走真正热点。

## 七、正确性、安全与锁的失败语义

### 7.1 键命名、序列化与权限隔离

缓存键可采用 app:env:tenant:schema:entity:id，并对会影响结果的语言、权限主体或查询参数作明确规范化。不是所有响应都要把用户写入键：公共数据可共享，个性化字段必须按授权范围隔离。把用户Token放键名会泄密且难治理，不是正确的身份隔离办法。

版本号可用于序列化升级：新旧进程各读自己能解析的schema前缀，迁移窗口后清理旧键。反序列化失败应当作兼容/数据故障指标并走受限miss，不能反复返回500或无限回源。使用受控类型，不从缓存载荷任意恢复可执行对象。

缓存不可替代鉴权。即使命中，也要在正确边界校验访问权限；撤权要求高时不能只等一个长TTL。对象租户ID来自可信认证与数据库归属，不能相信客户端随便给tenant参数。日志与运维权限也要防止Redis成为敏感数据旁路。

### 7.2 租约锁：随机持有者标识防误删

Lease（租约）是有期限的占用权。常用获取方式：

~~~text
SET lock:product:42 unique-owner-token NX PX 3000
~~~

NX表示仅不存在时设置，PX为毫秒租期；unique-owner-token应每次获取生成足够独特的随机值。释放时必须原子比较持有者再删除，不能先GET再DEL，两命令间锁可能到期并被别人获取。

兼容常见Redis版本的教学Lua：

~~~lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
else
  return 0
end
~~~

脚本调用示意为 EVAL script 1 lock:product:42 token。返回0可能是锁不存在或不再属于自己，不应继续删除。获取超时也可能结果未知，仍不可无条件删锁。令牌比较只保护不误删新锁，不会阻止旧持有者继续写数据库或旧缓存。

### 7.3 Fencing Token：接收端必须能拒绝旧持有者

假设A取得租约后长GC暂停，锁过期；B取得新租约并完成刷新；A恢复后仍可能把旧数据写回。自动续约也不能证明永不暂停或永不丢网络。

Fencing Token（栅栏令牌）是单调递增的所有权代次，接收端保存已接受的最高代次，原子拒绝较旧代次。例如B持102，A持101，B写入后A的101必须被存储端拒绝。随机owner token不具备这个大小顺序，也不能只在应用内比较。

令牌生成与持久化本身要满足故障切换不倒退的要求，不能未经分析就拿一个可能丢更新的异步复制计数器证明全系统安全。接收端若没有条件写入/校验代次的能力，仅有令牌没有意义；代次还不等同源数据版本。对于缓存重建，可以选择接受可控重复工作并用源版本防回退；对于扣款与库存不变量，应依赖数据库约束/事务等权威机制，不能把缓存租约当最终保护。

## 八、一份带预算的读取策略

### 8.1 Java服务的控制流应包含所有出口

下面为算法伪代码，不绑定特定Redis客户端：

~~~text
readProduct(context, id, deadline):
  validate id; authorize access scope
  key = makeKey(context.tenant, schemaVersion, id)

  try short GET
    VALUE and within permitted age -> return
    NOT_FOUND and valid -> return not-found
  catch cache error:
    record error; do not classify as ordinary key-miss

  if a stale local value exists and policy permits:
    schedule bounded coalesced refresh if resources allow
    return stale value with appropriate business semantics

  join per-process single-flight(key):
    recheck shared cache if cache circuit permits
    optionally obtain bounded rebuild lease
    acquire backend bulkhead/rate permission before remaining deadline
      unavailable -> reject/degrade; do not bypass quota
    load from authoritative source with timeout
      found -> best-effort bounded cache write with TTL
      confirmed absent -> optional short negative cache
      timeout/error -> propagate dependency failure, never cache NOT_FOUND
    release permissions and owned lease in finally
    clear single-flight entry after all outcomes
~~~

伪代码中“尽力回填”仅表示读取已成功时缓存写失败不必将业务读改为失败，不表示写路径失效失败可以不追踪。重建lease失败时是否等待、返回旧值或受限回源必须按业务选定；不要让每个开发者自行决定导致行为失控。

正常命中无需数据库许可，所有miss、刷新、预热、穿透降级却必须共享可承受的后端预算。后台刷新使用单独上限但仍计入数据库总容量，防止“前台已限流、后台偷偷打满”。取消等待不应误取消其他等待者共享工作，失败完成必须清理状态。

### 8.2 写入失效要可靠衔接事务

数据库提交前就删除缓存可能让并发读旧库回填；提交后失效则存在进程崩溃窗口。对于需要可靠最终失效的系统，可在同数据库事务写业务和Outbox失效记录，后台按对象与版本处理。Outbox是待处理事件随业务一起提交的持久发件箱，不是内存回调。

处理重复失效通常可幂等；乱序事件不能把版本水位倒退。TTL作为兜底，但必须把事件积压与旧回填计入陈旧预算。列表查询、聚合页和L1副本也需有失效策略，不能只删详情键就认为所有展示已同步。复杂查询缓存若无法稳定管理依赖，可选择短TTL、版本化命名空间或不缓存。

## 九、故障推演与排障

### 9.1 发布后数据库突然满载

先比较Redis错误、miss、eviction和键空间变化。如果TTL集中到期，检查抖动与预热；如果Redis网络超时，检查重试与熔断；如果键schema前缀升级，全体实例可能冷启动同一批新键。立即限制回源和低价值功能，不先扩大数据库连接并发。

恢复时按热点逐步填充，观察Backend QPS、连接等待和错误率。一次miss数量并不能表示真实回源数量，single-flight后应另统计加载数，才能判断合并是否有效。

### 9.2 命中率很高但p99恶化

p99是99%请求不超过的延迟。检查热分片队列、巨值网络传输、集合命令耗时、客户端连接、反序列化及GC。总集群平均CPU不高，仍可能一个热键把单分片压满。

按请求链路将GET耗时、解码耗时、锁等待与回源分开，采样诊断大键与热点。不要为提高命中率不断拉长TTL，可能让数据更旧、容量更紧而延迟更差。

### 9.3 用户修改成功，却一直读旧值

检查是否数据库尚未提交、失效在提交前执行、旧读晚回填、L1未失效、负缓存遮挡新对象、读副本滞后或键构造遗漏身份/版本。按业务ID与源版本追踪，而不只看“DEL返回成功”。

先让关键写后读走权威结果或最低版本校验，再修复失效与回填协议。全量清缓存可能瞬间冲垮数据库，不能当作无风险常规排障手段。

### 9.4 最小监控面板与演练

同时监控命中/未命中/负命中、实际重建数与合并等待、eviction/expired、内存与RSS、命令尾延迟、热分片、连接与超时、复制滞后、数据库QPS及并发、回源拒绝、陈旧返回年龄、失效Outbox最老年龄。指标要有口径：GET异常不混入正常miss，负命中不混成成功业务命中。

演练至少覆盖同键大量并发、随机不存在键、全批到期、Redis断连、加载者暂停超过租约、旧读晚回填、大键删除及冷启动。验证不只是API还有响应，还要确认数据库未越预算、敏感数据不串用户、旧值不超预算、恢复能逐步收敛。真实成本需结合内存、网络、复制、L1多副本与运维计算。

## 十、面试回答与深入追问

### 10.1 “怎么区分穿透、击穿、雪崩？”

完整回答：“穿透是不存在对象持续回源，我先校验和限流，再对权威不存在做有界负缓存或维护可靠过滤器。击穿是同一热点缺失造成重复重建，用请求合并、短互斥与允许范围内旧值应对。雪崩是大批失效或缓存层故障，用到期抖动、分批预热和高可用降低概率，但最终还要回源预算、熔断与卸载保证数据库存活。三个问题都不能只用一把锁解决。”

追问：“Redis挂了都查库，功能不是更完整？”答：“只有数据库承受得住才可。缓存平时可能屏蔽绝大多数流量，直接放行会把降级变成全站故障。我会按预算保核心、对其他请求返回明确降级或拒绝，并渐进恢复。”

### 10.2 “Cache Aside怎样保证一致性？”

完整回答：“常见先提交库后失效缓存只能降低窗口，并非强一致。旧读可在失效后回填旧值，失效也可能丢。我先约定陈旧预算，用持久失效与TTL兜底；若要求更严格，需版本水位和条件回填等协调，关键写后读则返回已提交结果或查权威来源。所有L1、负缓存与副本滞后都应计入。”

追问：“延迟双删能保证吗？”答：“只能降低特定时序的概率，不能覆盖无界暂停和失败。若业务必须保证，应改变协议或读路径，而非挑一个看似足够长的睡眠时间。”

### 10.3 “Redis锁拿到了就能防重复扣款吗？”

完整回答：“不能。租约可在GC或网络暂停时过期，旧持有者恢复仍可能执行；异步故障切换也影响互斥。随机持有者标识和原子比较删除只防误删，fencing还需接收端可靠拒旧。扣款应有权威持久幂等键与事务约束，缓存锁最多减少竞争。”

追问：“自动续约呢？”答：“续约任务同样会暂停或失联，不能证明永不重叠。需要从业务存储最终写入点阻止旧操作者，或设计重复执行仍安全。”

## 十一、扫雷自测与完整答案

### 11.1 数据库超时可以缓存NOT_FOUND吗？

**不可以。** 超时是未知或依赖失败，不是权威不存在。缓存它会把短暂故障扩大为一段时间的假缺失。只有成功确认不存在才按短TTL缓存，并配创建后失效。

### 11.2 一百万个随机无效ID，用空值缓存就够吗？

**不够。** 每个键只访问一次时几乎无复用，还会消耗内存挤走正缓存。需参数与身份限流、受控负缓存容量，必要时用可靠维护的过滤器，所有放行仍受后端预算限制。

### 11.3 同进程single-flight是否保证全系统只查一次库？

**不保证。** 它仅合并本进程同键工作，多实例、不同键和后台刷新仍可并发回源。可加跨实例协调减少重复，但仍需总回源预算与失败路径。

### 11.4 逻辑过期是否完全消灭冷miss？

**不是。** 首次访问、物理淘汰、Redis重启仍没有旧值可返回。必须保留有界加载、等待与拒绝路径，并限制旧值最长使用时间。

### 11.5 为什么300秒TTL加60秒抖动可能违规？

**如果业务最大陈旧预算300秒，就可能被延长到360秒。** 应在不超上限的区间抖动，并把其他同步与副本延迟计入。抖动解决到期分散，不能修改业务承诺。

### 11.6 DEL成功为何仍读旧值？

**旧读可能更晚回填，或旧值来自L1/副本/负缓存。** 删除成功只证明那一时刻的键操作，不证明所有并发与副本都已同步。需按版本与时序定位，关键路径用权威读取或条件协议。

### 11.7 锁持有者A可否先GET确认再DEL？

**不能作为安全释放协议。** GET后锁可能到期并被B取得，DEL会删B的锁。应原子比较token再删除；即使安全释放，也不阻止A在租约失效后的旧写入。

### 11.8 随机token是否就是fencing token？

**不是。** 随机token用于区分持有者，fencing需要单调代次和接收端原子拒绝旧代次。生成器与接收端的故障持久性也须证明，不能只在锁库里存一个数字就宣布安全。

### 11.9 SCAN的COUNT=100是否每次恰好100条且无重复？

**不是。** COUNT是提示，可能返回不同数量，完整迭代也可能重复，变化集合不提供固定快照。调用方需处理重复与更新语义，并限制整体扫描成本。

### 11.10 多可用区是否意味着Redis故障无需DB保护？

**不是。** 网络、配置、热键、冷启动和共同失效仍可能发生，复制与切换也存在边界。必须演练整体不可用、限制回源，并验证渐进恢复，不能只检查有几个副本。

## 十二、速记、验证边界与一手来源

- Cache Aside写库后失效是常用模式，不是强一致证明。
- 不存在、未命中、依赖故障必须分开；穿透防御也要防负键容量攻击。
- 合并减少重复工作，锁减少竞争，总预算控制不同键与不同实例的总压力。
- 抖动防集中到期，逻辑过期换有限陈旧；整体故障仍靠熔断、隔离与卸载。
- 热键看单分片，大键看执行/网络/回收；TTL未到也可能被淘汰。
- owner token防误删，fencing防旧持有者写入，源版本防旧数据回退，三者不相同。

命令和伪代码为教学材料；未运行Redis实例、Java客户端集成、故障切换或负载实验，不宣称真实并发与性能目标已验证。正文逐节检查了原主题覆盖、策略边界、失败时序、命令参数及全部问答；独立状态/算术检查只能验证推理，不能代替真实服务测试。
