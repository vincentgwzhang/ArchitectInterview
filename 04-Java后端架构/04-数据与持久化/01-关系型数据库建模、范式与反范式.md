# 01. 关系型数据库建模、范式与反范式

## 建模起点

从 Domain Invariant、Transaction 和 Access Pattern 出发，而不是把 Java Object 机械映射成表。明确 Entity Identity、Cardinality、Lifecycle 与 Ownership。

## 范式

Normalization 减少重复与更新异常：

- 1NF：字段原子化。
- 2NF：非 Key 属性依赖完整 Key。
- 3NF：消除非 Key 的传递依赖。

交易系统通常以规范化模型保证一致性，再为经过证据确认的读取热点反范式化。

## 反范式

复制 Product Name/Price Snapshot 到 Order Item 可以保护历史语义；建立 Summary Table 或 Read Model 可以优化报表。代价是同步、重建和一致性窗口。

反范式数据需要明确 Source of Truth 和更新机制：Transaction、CDC、Event 或定期 Reconciliation。

## Key

选择自然 Key 或 Surrogate Key，并用 Unique Constraint 保护业务唯一性。UUID 便于分布式生成，但随机值可能影响 Index Locality；可考虑时间有序 ID。不要依赖 Application Check 替代数据库约束。

## 时间与金额

金额使用 Decimal + Currency，避免浮点。时间统一保存 UTC Instant，业务时区单独记录。审计字段应有清晰创建/修改主体。

## Schema 演进

使用 Expand-and-Contract：先添加兼容字段/表，双读写或 Backfill，再切换，最后删除旧结构。

## 总结

规范化保护写入一致性，反范式优化特定读取。每份重复数据都必须有 Ownership、同步和重建策略。
