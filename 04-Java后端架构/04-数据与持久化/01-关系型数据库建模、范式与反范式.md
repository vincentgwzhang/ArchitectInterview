# 01. 关系型数据库建模、范式与反范式

> 目标：面对一个业务需求，能解释“哪些事实应该存在哪里、哪些约束必须原子保证、哪些重复是错误而哪些是业务历史”，并把模型落成可约束、可查询、可演进的结构。本章示例是虚构的多租户订单系统，不代表用户项目经历。
>
> SQL 以 PostgreSQL 17 为说明基线；范式是逻辑模型理论，不依赖某个数据库。其他产品的空值唯一性、外键索引、DDL 锁与时间类型可能不同，不能直接照搬。本文不把任何版本视为最新版本。

## 一、建模从业务事实开始，而不是从 Java 类开始

### 1.1 先列不变量、事务与访问方式

领域不变量（Domain Invariant）是每次合法业务状态都必须满足的条件。例如订单属于一个租户、订单明细必须属于同租户的订单、数量必须为正、同租户外部订单号不能重复。“页面显示商品名称”则是查询需求，不是不变量。

事务（Transaction）把一组数据库操作作为一起提交或回滚的工作单元。如果订单头成功而明细失败不允许留下半张订单，就需要同一事务写入。一个 Java 方法或一个 ORM 对象图不会自动成为事务边界；异常是否回滚、连接是否共享、外部调用是否在事务范围都要明确。数据库事务也不会回滚已经发送的邮件或完成的支付。

访问模式（Access Pattern）描述实际怎么读写，例如“按租户和外部订单号查单”“每页按创建时间倒序查最近订单”“按订单读全部明细”。它指导索引和读取表示，但不能因此把全部事实放进一张大表。首先确保事实与约束正确，然后用测量优化热点。

教学需求可以写成：

| 业务条件 | 模型上的表达 | 应怎样验证 |
|---|---|---|
| 外部订单号在租户内唯一 | UNIQUE(tenant_id, external_no) | 并发插入同号，最多一个提交 |
| 明细不得跨租户挂单 | 包含 tenant_id 的组合外键 | 跨租户引用必须失败 |
| 下单价格不随商品调价变化 | 明细保存成交价快照 | 调商品价后旧单金额不变 |
| 已提交订单不可无声改价 | 状态迁移与修改权限 | 非法修改被拒绝，合法更正留记录 |
| 最近订单查询可控 | 明确排序及支持它的索引 | 真实分布下检查执行计划与尾延迟 |

前三项主要靠结构和事务保护；后两项还涉及业务操作与授权。不要把“有数据库约束”误解为所有业务规则都已实现。

### 1.2 实体身份、基数、生命周期与所有权

实体身份（Entity Identity）回答“信息变了还是同一件东西吗”。客户改名仍是同一客户，订单号改展示格式也不应变成新订单。因此名称通常不是稳定身份。值对象（Value Object）则按内容表达，例如一份地址值；客户当前地址与订单配送地址可能相同，但生命周期不同。

基数（Cardinality）区分一对一、一对多、多对多，还要包括可选性。订单有多条明细，明细恰好属于一个订单；“用户可以有零个配送地址”与“每个地址必须属于一个用户”是两端不同约束。多对多用关联表表达，例如 product_category(product_id, category_id)，组合唯一键防止同一关联重复；如果关联还含加入时间、角色等，它本身也有业务事实，不只是技术中间表。

生命周期（Lifecycle）决定删除与保留：商品下架不能删掉历史订单，订单取消也不等于物理删除。所有权（Ownership）说明谁能改变哪个事实：商品目录拥有当前名称与标价，订单模块拥有成交快照，报表模块拥有可重建的统计结果。多团队都写同一列且没有冲突规则，远比“表是否够规范”更危险。

不要机械把 Java 的继承层次映射为表。一个实体可能拆成主表和明细表，一个页面 DTO（数据传输对象）可能连接多表，数据库的集合关系也不需要等同于对象的双向引用。ORM 是映射工具，模型需先说明业务语义。

## 二、函数依赖与范式：用异常推导拆表理由

### 2.1 键与函数依赖先讲清

函数依赖（Functional Dependency）X → Y 意味着：在所有符合业务规则的合法数据中，只要两行 X 相同，Y 就必须相同。它由业务规则决定，不是因为当前样本中恰好没重复。商品编号决定当前商品名，但商品名一般不决定商品编号。

超键（Superkey）是能唯一确定一行的属性集合；候选键（Candidate Key）是去掉任一属性就不再具有这种能力的最小超键。主键（Primary Key）是选作主要标识的候选键；其他候选键仍要用唯一约束保护。出现在任一候选键中的属性叫主属性（Prime Attribute），不是简单指“主键列”。

设未经整理的订单行是：

~~~text
OrderLine(order_id, line_no, ordered_at,
          customer_id, customer_name,
          product_id, current_product_name,
          quantity, agreed_unit_price)
~~~

业务依赖包括：(order_id,line_no) 决定整行；order_id 决定 ordered_at、customer_id；customer_id 决定客户当前名称；product_id 决定商品当前名称；成交单价依赖具体订单行，不能假定由 product_id 单独决定，因为折扣与时间不同。

这里三种异常（Anomaly）很直观：客户改名必须更新很多订单行，漏改产生更新异常；还没有订单就无法单独录入客户，产生插入异常；删除客户唯一一笔订单时也丢掉客户资料，产生删除异常。规范化（Normalization）是按事实依赖重新组织关系，减少这种意外绑定，不是为了让 SQL 显得复杂。

### 2.2 第一范式：不要把集合藏在一个不可治理的字段中

第一范式（1NF）要求属性在所选关系模型中具有单值、可按定义处理的域，不存在重复组。把 product_ids 存成 "p1,p2,p3" 会让外键、逐项数量与检索变得困难；product1/product2/product3 列则把最多三个商品写死。应把每个订单项作为独立行，以 line_no 或行 ID 标识。

“原子”相对于建模需求：一个电话号码可作为整体值，不必拆成每位数字；如果需要按国家代码治理，则应显式建模。数据库允许 JSON、数组，不代表任何使用都违反或满足范式；要问其内部元素是否承载独立身份、关系与约束。原始第三方响应可保留 JSON 供审计，订单明细却通常不宜仅藏在 JSON 中而放弃关系约束。

SQL 表允许重复行和 NULL，与理想关系理论并不完全相同。面试中谈范式要说清讨论的是逻辑依赖；落地还需主键、非空、唯一性和明确的空值语义。

### 2.3 第二范式：非主属性依赖整个候选键

第二范式（2NF）在 1NF 基础上，禁止非主属性只依赖某个候选键的真子集。例子中主候选键为 (order_id,line_no)，ordered_at 只依赖 order_id，因此应拆出 Orders(order_id, ordered_at, customer_id)，明细保留整键相关的商品、数量和成交价。

如果不拆，同一订单不同明细可能写出不同下单时间。拆分后，只修改订单头的一行即可改变其唯一事实。查询整单需要连接，但写入事实不再被明细数量放大。

常见误区是“加一个自增 ID 就达到 2NF”。如果业务候选键仍是 (order_id,line_no)，其部分依赖并不会因为增加代理主键而消失。范式检查应看全部候选键与业务依赖，而不只看数据库 PRIMARY KEY 声明。反过来，若所有候选键都是单属性，才不存在非空真子集带来的这类部分依赖问题。

### 2.4 第三范式：事实不要通过非键属性绕行

拆出订单头后，order_id → customer_id → customer_name 仍让客户当前名重复在订单头中。第三范式（3NF）的严格判据是：每个非平凡依赖 X → A 中，X 是超键，或者 A 是主属性。常用的“非键属性不能传递依赖主键”是便于理解的简化，不足以覆盖有多个重叠候选键的全部情况。

把客户当前资料移入 Customer(customer_id, customer_name)，订单仅引用 customer_id，避免客户改名更新所有订单。商品当前资料同理；但订单行的 purchased_name 是“当时交易采用的名称”，与 current_product_name 不是同一个事实，下一节会解释为何不能盲目消除它。

分解还应无损连接（Lossless Join）：拆后连接能恢复原合法事实，不制造虚假组合。例如订单头与明细按 order_id 连接，头部 order_id 唯一，明细每行只对应一份头部事实。依赖保持（Dependency Preservation）则希望主要约束能在各表中直接检查，而不是每次跨表拼接才能验证。多拆几张表但无法有效维护约束，不等于更好的设计。

### 2.5 BCNF 与“规范化到几阶”的工程判断

BCNF（Boyce-Codd Normal Form）比 3NF 更严格：每个非平凡函数依赖的决定项都必须是超键，不再允许右侧为主属性这一例外。

例如 Teaching(student, course, teacher)，规则是每个师生课程组合中，一个教师只教一门课程，而同一学生同一课程只有一位教师。候选键为 (student,course) 与 (student,teacher)，teacher → course 的决定项 teacher 不是超键，但 course 是主属性，因此可能满足 3NF 而不满足 BCNF。拆成 TeacherCourse 与 StudentTeacher 可消除教师课程重复，但“一个学生同一课程只能有一个教师”不再能仅用各自简单唯一约束保证，需要额外协调。

这个例子说明更高范式也存在约束实现代价。普通交易模型先追求清晰的 3NF、业务约束和事务边界；发现独立多值事实再继续分析，不需要为了术语强拆全部业务。面试应先说明异常如何产生、拆分保住什么，再谈阶数，而不是宣布“所有表必须最高范式”。

## 三、从逻辑模型到可约束的订单结构

### 3.1 一份可阅读的 PostgreSQL 17 教学 DDL

下面限定为单数据库、订单与商品同租户，示例只允许 EUR/CNY 且以两位小数计价。它不是全球货币模型，也未实现订单状态机、全部审计与权限。

~~~sql
CREATE TABLE customer (
    tenant_id bigint NOT NULL,
    customer_id bigint NOT NULL,
    display_name text NOT NULL,
    PRIMARY KEY (tenant_id, customer_id)
);

CREATE TABLE product (
    tenant_id bigint NOT NULL,
    product_id bigint NOT NULL,
    current_name text NOT NULL,
    PRIMARY KEY (tenant_id, product_id)
);

CREATE TABLE sales_order (
    tenant_id bigint NOT NULL,
    order_id bigint NOT NULL,
    external_no text NOT NULL,
    customer_id bigint NOT NULL,
    currency char(3) NOT NULL CHECK (currency IN ('EUR', 'CNY')),
    ordered_at timestamptz NOT NULL,
    created_by text NOT NULL,
    PRIMARY KEY (tenant_id, order_id),
    UNIQUE (tenant_id, external_no),
    FOREIGN KEY (tenant_id, customer_id)
        REFERENCES customer (tenant_id, customer_id)
);

CREATE TABLE order_item (
    tenant_id bigint NOT NULL,
    order_id bigint NOT NULL,
    line_no integer NOT NULL CHECK (line_no > 0),
    product_id bigint NOT NULL,
    purchased_name text NOT NULL,
    quantity integer NOT NULL CHECK (quantity > 0),
    agreed_unit_price numeric(18,2) NOT NULL
        CHECK (agreed_unit_price >= 0 AND agreed_unit_price <> 'NaN'::numeric),
    PRIMARY KEY (tenant_id, order_id, line_no),
    FOREIGN KEY (tenant_id, order_id)
        REFERENCES sales_order (tenant_id, order_id),
    FOREIGN KEY (tenant_id, product_id)
        REFERENCES product (tenant_id, product_id)
);

CREATE INDEX sales_order_recent
    ON sales_order (tenant_id, ordered_at DESC, order_id DESC);
~~~

同租户外键同时比较两个字段，避免 tenant A 的订单引用 tenant B 的客户。仅在每张表放 tenant_id、外键却只引用全局 ID，不一定表达了租户一致性。即使组合约束正确，查询仍需身份范围过滤，数据库引用完整性不等于访问授权。

明细主键前缀支持按租户和订单取项；最近订单索引对应实际排序，order_id 用作时间相同的稳定次序。索引增加写入、存储与维护成本，不能对所有列自动加索引。此处未给 product 引用列建索引，因为是否频繁按商品查明细、删除/更新父记录需要额外证据；PostgreSQL 不自动给外键引用端建立所有所需索引。

外键默认的删除限制有意保留历史：商品应下架或归档，不能删除后使订单失去来源。若业务允许删除草稿订单，可在明确事务中删除明细再删头；不要不加区分地给财务历史设置级联删除。

### 3.2 约束能保护什么，不能保护什么

NOT NULL 阻止缺值，CHECK 限制单行合法范围，UNIQUE 仲裁并发业务重复，FOREIGN KEY 保证引用存在。PostgreSQL 的 CHECK 对结果为未知的 NULL 表达式不按 false 拒绝，所以 quantity > 0 必须配 NOT NULL。唯一约束的 NULL 语义也需按产品和定义确认，不能拿可空 external_no 实现严格业务唯一性。

“先 SELECT 无记录，再 INSERT”在并发下两个请求都能通过查询，最终应由唯一约束裁决；应用捕获确定的约束冲突，返回业务重复或查回原结果。不能把所有数据库异常都当作“订单已存在”，连接故障和其他约束失败必须区分。

订单至少一项、订单金额等于明细和、已提交后禁止改价，不能仅靠上面的单行 CHECK 完成。应通过受控业务事务、必要的锁/版本控制或审慎设计的触发器维护。PostgreSQL 不支持把任意跨行跨表条件当作可靠 CHECK；应用层规则也需防止其他写入口绕过。采用触发器时必须说明并发锁、批量导入和迁移行为，不能以“放数据库里”替代设计。

事务创建订单时，一并写入头、明细和需要的本地记录后提交，失败全部回滚。若提交时网络断开，结果可能未知；通过租户+外部单号或操作幂等键查证，不能重新生成业务号重建一单。结构建模因此直接影响失败恢复，而非只影响 ER 图外观。

## 四、反范式与历史快照：不要混淆三类重复

### 4.1 当前事实的副本、历史事实与派生值

| 数据 | 语义 | 正确更新策略 |
|---|---|---|
| 商品当前名称 | 目录的权威当前事实 | 目录模块修改 |
| 订单 purchased_name、成交价 | 成交时确定的交易事实 | 下单时冻结；更正通过受控流程留痕 |
| 搜索页商品名称副本 | 为读取复制的当前事实 | 追随目录更新，监控滞后并可重建 |
| 每日订单总额 | 从订单计算的派生结果 | 按既定口径增量或重算，对账 |

教材常把订单快照也称为反范式，工程上更重要的是识别其独立时间语义。商品改名不应“同步修复”旧单；订单成交价也不是商品现价的过期缓存。相同字符串存两处，不代表一定属于同一个函数依赖。

快照应说明冻结时机。若价格先读后写期间被修改，业务必须决定采用报价版本、重新报价还是锁住报价，不可让客户端任意提交一个低价。配送地址也是如此：修改个人资料不应改已经发货订单的地址；未发货订单改地址要有独立命令、权限、物流检查和审计。

历史事实也不是绝对永远不可更正。差错更正、退款、隐私处理有不同规则，但不能悄悄覆盖造成账实无法追溯。原交易事实、纠正记录和当前业务状态要区分，不能用“软删除”一列解决所有历史语义。

### 4.2 什么时候值得反范式

反范式（Denormalization）是有意把可从其他事实取得的信息复制或预先计算，以减少特定读取成本。先看慢查询证据：连接是否有索引、统计信息是否合理、返回是否过多、是否 ORM N+1，再考虑存副本。

例如每日经营看板反复扫描大批订单，可建立按 tenant、业务日期、currency 分组的汇总表，使看板读取固定范围。代价是写放大、更多存储、同步逻辑、迟到订单/退款处理和重建能力。若数据规模小、报表低频，直接查询或离线生成可能更便宜。少一次 JOIN 不自动等于快，复制宽字段也可能降低缓存命中。

决定前写明读延迟目标、读取次数、允许陈旧时间、源数据规模与更新率，并测量数据库 CPU、I/O、尾延迟与成本。不要编造“反范式快十倍”；性能收益属于具体执行计划与工作负载。

### 4.3 同步副本的四种方式与故障窗口

同库事务可以原子更新源表和汇总，但扩大锁范围，热门计数行可能串行化写入。事务越长，冲突与尾延迟越明显；不能为了所有报表实时而让下单依赖几十张投影表。

CDC（Change Data Capture，变更数据捕获）读取数据库变更构建投影，减少应用漏发风险；但必须处理快照起点、变更位置、结构变化、重放和重复。数据库行变化也未必携带完整业务意图，例如多行更新属于一次订单取消，需要正确归组而非简单数条数。

领域事件表达业务事实，适合模块间解耦；源写入与事件可靠发布可用 Outbox，即同事务写业务和待发送记录，再转发。发送确认丢失可能重复，因此消费端仍需幂等。不能先改库再“尽力发消息”却承诺绝不丢更新。

定期 Reconciliation（对账）按权威数据重算或比对，适合容许延迟的结果，也用于修复增量通道缺陷；代价是扫描成本和发现延迟。它不是用来掩盖没有正常同步机制。每份副本都应写清 Source of Truth（事实来源）、拥有者、正常同步路径、最大允许滞后和修复入口。

### 4.4 汇总更新与重建怎样避免重复和回退

假设一笔 EUR 订单总额为 30.00，按事件给每日总额加 30.00。事件重复会变成 60.00；只按订单 ID 去重又会挡住其后的退款。应设计事件唯一 ID、业务版本和“这条事件代表哪一种状态变化”，在同一事务中去重并应用变更。

完整状态投影可以只接受更高版本的快照；金额增量不能跳过缺失事件后假装正确。退款应归原交易日还是退款发生日是指标口径，不由消息框架决定。汇总还应按币种分组，EUR 和 CNY 数值不能直接相加。

重建用新表/新版本投影，在一致快照或明确水位上扫描，再接续其后的变更；没有水位会在扫描与消费交界处漏算或重复算。对比按租户、日期、币种的数量与金额，再切换读指针。后台重建也要限速，防止压垮交易库；保留旧投影到验证与回退窗口结束。不可重建、无人能解释来源的副本应视为数据债务。

## 五、自然键、代理键、UUID 与业务唯一性

### 5.1 自然键与代理键分别承担什么

自然键（Natural Key）来自业务，如国家代码或租户内订单号；优点是可解释，缺点是规则可能改变、值可能含隐私且可能很宽。电子邮件可修改、规范化规则复杂，通常不宜作为全系统外键身份。

代理键（Surrogate Key）是专为身份生成的值，如 bigint ID 或 UUID；稳定且便于引用，但它只证明技术身份不同，不能阻止同一业务订单被创建两次。示例用 order_id 做身份，同时以 (tenant_id, external_no) 保护业务唯一性。自然键变更时保持代理 ID，可减少引用更新；若业务编号规则变更，要考虑历史别名、重试请求和查询兼容。

复合键可以直接表达租户范围，代价是外键与索引变宽。也可选全局单列 ID 并额外建立组合唯一约束支持租户外键。两者都应基于隔离与访问模式选择，不能只用 ORM 写起来省事作为依据。

### 5.2 生成方式、局部性与安全

数据库序列便于集中生成，但回滚等情况可能留下间隙，不能当作连续无缺的财务编号；ID 大小也不等于事务提交顺序。分布式节点生成 UUID 减少生成时的集中协调，但仍需数据库唯一约束兜底。

随机 UUID 插入 B-tree 时可能降低写入局部性、增加页访问与拆分，实际影响取决于引擎、缓存与负载；PostgreSQL 堆组织与其他数据库聚簇主键布局也不同。时间有序 ID 可能改善局部性，却会暴露部分时间信息；基于时钟的自定义生成器还需处理时钟回退、节点号冲突与序号耗尽。PostgreSQL 17 不应被假设原生提供所有后续版本的 UUID 生成函数。

唯一 ID 不等于授权令牌。随机 ID 只是降低枚举便利性，读取仍必须检查租户与所有者；自增 ID 即使可猜，也不能因此绕过权限。身份、唯一性、排序与安全是四个独立问题。

## 六、金额、时间和审计：类型选择背后是业务语义

### 6.1 金额为什么用精确表示

二进制浮点不能精确表示许多十进制小数，持续求和与比较可能产生边界错误。金额通常选 decimal/numeric 加币种，Java 用 BigDecimal，从字符串或精确来源构造，并明确 scale（小数位）与舍入模式；不要先把 0.1 放进 double 再以为转成 BigDecimal 就恢复了原意。

也可用整数表示最小货币单位，但必须记录货币与单位，并控制乘法和求和溢出。不是所有货币都两位小数，也不应把精度设置当作全球业务规则。numeric(18,2) 表示总共 18 位、其中两位小数，写入超出 scale 时的舍入与范围行为需验证；金额必须有限，示例另排除了 PostgreSQL numeric 的 NaN 特值。

教学假设：三件单价 0.10、两件单价 0.20，总额应为 0.70。税费场景还要确定“每行先舍入再求和”还是“高精度求和后舍入”，两者可得到不同结果；规则必须在报价、支付和账单中一致。只把数据库改为 Decimal，却各服务用不同舍入规则，仍会发生对账差异。

多币种不能直接求和，换汇需保存汇率来源、适用时刻和舍入规则。若总金额冗余存订单头，须指定是受控成交事实还是可重算派生值，并以事务/校验防止与明细漂移。

### 6.2 Instant、业务时区和日期不是同一类数据

已发生事件适合存全球时间点（Instant），交换时采用带偏移的 ISO 8601。PostgreSQL timestamptz 按时间点处理并按会话时区显示，不保留最初输入的 Europe/Madrid 之类区域名称；需要原业务时区时另存 IANA 区域标识。

“每天当地上午九点”是未来日历规则，不能只存某次换算出的 UTC 值，因为夏令时会变化；应保存当地时间、区域与重复规则，在生成具体执行实例时解析。生日只需要 date，不应无故转成某个 UTC 午夜，否则展示时可能变成前一天。

统计“马德里 11 月 13 日订单”要先把该业务日的起止边界按 Europe/Madrid 转成时间点，用半开区间 [start,end) 查询。不能假设每天固定 24 小时，夏令时转换日可能不同。重复或不存在的当地时间须定义提前/延后/拒绝策略。

数据库时间也不是全局业务顺序：并发事务、时钟差异和重试会让时间戳不足以判定因果。需要状态演进顺序时增加业务版本，审计时间与事件序号分别使用。

### 6.3 审计字段与删除治理

created_at/created_by、updated_at/updated_by 要约定由谁写、代表接收时刻还是提交相关时刻。业务操作由后台代表用户执行时，可分别记录实际执行服务身份、发起用户和关联操作 ID，避免把所有修改都归为 system。仅有 updated_at 不足以回答“旧值是什么、为何改”。

关键业务更改记录不可随普通更新覆写的变更日志或专门审计存储，并限制访问；不要把令牌、完整敏感载荷无选择复制到日志。备份、投影、导出中的个人信息也需纳入保留与删除计划。

软删除（Soft Delete）用标记保留行，但所有读取、唯一性与引用都要考虑它。用户标记删除后是否允许重新使用业务号？引用旧用户的订单如何显示？查询漏加 deleted 条件会不会泄露？不能认为一个 deleted_at 列自动解决合规或历史保留。

## 七、Schema 演进：Expand-and-Contract 的并发正确性

### 7.1 为什么不能直接重命名或覆盖旧列

滚动发布期间旧程序和新程序同时运行，直接删旧列会使旧程序报错；一次性把所有历史记录大事务回填，会扩大锁、日志与复制延迟。Expand-and-Contract（扩展—迁移—收缩）让结构兼容窗口覆盖部署窗口，但不是自动零停机承诺。

例如旧系统把成交单价存在 price_text，新系统需要 amount 数值列和 currency。先明确旧值是否带币种、历史异常怎样处理；解析不出的数据必须隔离和修复，不能默认零。然后添加可空新列并部署兼容写入，保证新发生的修改同时正确写入两种表示；同库双写可放在同事务，跨存储双写则没有这份自动原子性。

### 7.2 回填必须防止旧快照覆盖新写入

回填程序读取 price_text 时，在线请求可能已经改价。若稍后无条件 UPDATE 新列，旧值就覆盖了新值。可采用行锁内读取并写入，或按读取时版本执行条件更新，版本不符重新读取；如果使用“仅填新列为空”的方式，必须证明在线写总会先保证新列非空，而且回填转换与更新不是脱离条件的陈旧快照。

按稳定主键分批，持久化检查点，限制批量大小和负载；失败从检查点重试且操作应幂等。检查点只代表扫描位置，不代表跳过的异常数据已修好。迁移期间记录未迁移数、解析失败数、版本冲突和读写差异，并分租户抽样和全量对账。

### 7.3 切换、约束、回滚和收缩

先让新读路径灰度读取新列，同时比对旧解释与新值；必要时只在明确安全的情况下回退旧列，不能无限回退把新列漏写掩盖掉。确认所有在线写入口、离线作业、消息消费者和回滚版本都兼容，再补齐约束并切换全部读取。

DDL 会持锁，是否扫描或重写与具体命令和版本有关；应在接近生产的数据量上观察，设置锁等待上限和中止策略，避开长事务。不能把“新增可空列往往较轻”扩张为“所有 ALTER TABLE 都无锁”。PostgreSQL 的分阶段约束验证、并发建索引等能力需分别按命令限制设计，不能与普通 ALTER 一样塞进一个大事务。

停止旧写后保留可验证的回滚窗口；新数据若已无法被旧版本理解，回滚程序也不再安全。最后删除旧列前确认调用量、作业、报表和历史重放都不再依赖。备份与恢复演练保护数据，不能代替兼容性设计；结构删除后再恢复全库通常不是可接受的快速回退。

## 八、从性能、可靠性和演进做选择

### 8.1 交易模型与报表模型不必相同

交易库强调不变量与短事务；看板强调聚合查询，搜索强调检索与排序。可以从规范化权威模型派生多个读模型，但必须由可重放事实或一致快照重建。把一个巨型宽表同时用于所有任务，会同时承受写放大、敏感字段扩散与模型变更耦合。

反过来，拆成多个数据库并不能自动获得扩展性。跨库外键与事务消失后，需要应用协作、异步恢复和对账；如果业务频繁要求原子修改，就应慎重拆分数据所有权。先模块化和限制写入口，往往比立即分库更容易控制风险。

### 8.2 如何排查“模型有问题”

发现重复订单先查唯一性范围、NULL、重试键和写入口，不要仅靠定时删重复。发现历史金额变化先追踪是否查询了商品现价、快照是否允许任意更新。发现汇总漂移则按事件 ID、版本、水位和对账追查重复或缺口，而不是直接手工改总额。

慢查询先看执行计划、过滤选择性、连接行数与实际返回量：正确逻辑模型可以通过索引、分页和受控聚合优化。若确需反范式，写出同步与恢复成本。上线后同时看读取收益和写延迟、锁等待、投影滞后，避免局部优化损害交易可靠性。

## 九、完整面试回答与追问

### 9.1 “订单库怎样建模？”

回答示例：“我先确认订单成立条件、身份和租户范围，把订单头与明细放在可原子提交的边界。客户和商品当前资料各自存权威记录，订单保存成交名称、价格与地址的历史快照。主键保护技术身份，租户内外部订单号再用唯一约束保护业务重复；组合外键阻止跨租户引用。最近订单索引对应实际访问模式。报表先查证瓶颈，必要时派生可重建的汇总，并定义滞后和对账。金额、业务时区和兼容迁移一起纳入模型，而不是最后再补。”

追问：“订单总额放不放？”答：“若它是成交确认事实，可以保存，但必须与明细定价、折扣、税费口径一致并由受控事务写入；若只是报表方便算出的值，则应作为派生结果治理。不能既允许明细任意修改，又默认头部总额永远正确。”

### 9.2 “规范化和性能冲突怎么办？”

回答示例：“我先确认是不是连接本身导致问题。缺索引、错误基数估算、扫描过多和 N+1 都可能比表拆分更重要。规范化让每个当前事实有稳定归属，减少更新异常；如果特定读路径确实高成本且允许陈旧，我为它建立投影，用成本换读取效率，并承担去重、同步、重建与对账。不把历史快照误认为需要追随现值的副本。”

追问：“要求强一致又要求汇总很快？”答：“可以在同库事务维护小规模汇总，但需测试热点行锁与写放大；也可实时查权威事实。若容量下两者都达不到，就必须讨论降低粒度、延迟或业务承诺，不能用异步投影口头保证实时。”

### 9.3 “有 ORM 和应用校验，还需要约束吗？”

回答示例：“需要。两个请求可能同时通过应用检查，其他作业也可能绕过 ORM。数据库唯一性和外键在实际写入点保护局部不变量，应用校验提供友好反馈，两者职责不同。跨行规则仍需事务和并发控制，数据库约束不是全业务验证器。”

追问：“拆成微服务后没有跨库外键？”答：“先避免把强不变量无理由拆开；确实需要拆时定义对方身份、允许的暂时状态、可靠事件、补偿和对账。失去外键后的责任要由可验证机制接手，不能只删掉约束。”

## 十、扫雷自测与推理答案

### 10.1 主键改成自增 ID，原表是否自动满足 3NF？

**不自动满足。** 其他候选键与函数依赖仍存在，例如 order_id 决定客户，而客户 ID 决定当前名称，重复当前名称仍产生更新异常。代理键解决身份表达，不消除事实之间的依赖。

### 10.2 customer_name 在订单中一定违规吗？

**先问语义。** 若它代表客户当前名，应跟随客户权威资料，不应每单随意复制；若代表成交时合同使用的名称，它是订单历史事实，应在成交冻结。字段同名容易掩盖差异，使用清晰命名和修改规则。

### 10.3 为什么一张订单不能用逗号分隔商品 ID？

**因为它把独立关系与约束藏进字符串。** 无法自然保护每项商品外键、数量和价格，也难以索引和更新单项。应建明细行。保留原始 JSON 作为审计证据是另一种需求，不能代替受约束的交易模型。

### 10.4 两请求都查不到外部订单号，为什么仍可能重复？

**查询与插入之间有竞态。** 数据库需 UNIQUE(tenant_id,external_no) 仲裁，应用识别冲突并查回原操作。外部编号若允许 NULL，要额外处理空值语义；仅有代理主键会允许两个不同 ID 表达同一业务订单。

### 10.5 每张表都有 tenant_id，就不会串租户吗？

**不会自动保证。** 外键必须表达所属租户一致性，查询还需按可信身份限制数据。数据库中能合法引用一条记录，不等于当前用户有权读取它；结构约束和授权分别测试。

### 10.6 商品改价后同步修改历史 order_item 是否是“修复冗余”？

**通常是破坏历史。** 成交价由当时报价与折扣决定，不是现价的副本。需要纠正错误时走明确更正流程，保留理由和可追溯事实，而非批量跟随商品现价。

### 10.7 有 CDC，汇总是不是就不可能错？

**仍可能错。** 重复、乱序、初始快照与增量交界、结构变更及业务口径都可能造成漂移。需要去重/版本、水位、重建和对账；CDC 提供数据变化通道，不提供全部业务语义。

### 10.8 保存 UTC 后是否可以不管业务时区？

**不可以。** 已发生时间点可统一存储，但当地营业日、未来重复任务和夏令时规则需要区域。timestamptz 不保存原区域名称。生日则是日期，不能无理由转换为某个时间点。

### 10.9 用 numeric 就无需讨论金额规则了吗？

**仍需单位、币种、精度和舍入时机。** 同样的税额，逐行舍入和最后舍入可能不同；不同币种不能直接相加。精确类型解决表示误差，不决定财务口径。

### 10.10 回填只要能断点继续，就是安全迁移吗？

**不够。** 检查点只保证扫描恢复；旧快照仍可能覆盖在线新写。还要版本条件或行锁、兼容写入、差异校验、异常修复和回滚窗口。迁移正确性包含并发语义与版本兼容，不只是跑完脚本。

## 十一、速记与验证范围

- 先事实与不变量，再表、事务和访问路径；对象图不是数据库模型。
- 函数依赖由业务决定；1NF 去重复组，2NF 检查完整候选键依赖，3NF 避免事实绕行，BCNF 更严格但考虑约束保持。
- 当前权威事实、历史快照、可重建投影是三种不同数据。
- 技术 ID 不代替业务唯一性；应用预检查不代替数据库并发约束。
- Decimal 不决定舍入规则，UTC 不代替业务时区，updated_at 不等于完整审计。
- 每份副本都要有来源、所有者、同步、滞后、重建与对账；每次迁移都要有并发保护与兼容窗口。

本章 DDL 和事务策略是教学实现。全部正文按原主题逐节核对；SQL 未在 PostgreSQL 实例执行，未声称数据库约束、并发迁移或负载实验已通过。金额、范式依赖与示例不变量可作独立逻辑验证，不能用其他数据库的通过结果替代 PostgreSQL 的实际验证。落地时至少覆盖正例插入、重复/NULL/跨租户/非法数量负例、并发唯一性、历史价不变、投影重放与迁移竞态。
