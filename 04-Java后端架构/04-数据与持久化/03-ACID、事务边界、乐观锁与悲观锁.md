# 03. ACID、事务边界、乐观锁与悲观锁

> 面试目标：先说明要保护的业务不变量，再解释本地事务覆盖哪些资源、如何处理并发与提交失败，最后选择锁和跨边界恢复策略。不能只背四个单词或认为一个注解等于业务正确。
>
> 版本范围：数据库例子以 PostgreSQL 17 为基线；Spring 事务说明限于 Framework 6.2 的常见代理模式；JPA 概念参考 Jakarta Persistence 3.2。它们是分别说明的语义基线，不表示 Spring 6.2 默认依赖 Persistence 3.2，也不声称是最新版本。所有业务场景均为虚构教学材料。

## 一、ACID 实际保证什么

### 1.1 Atomicity：在指定事务资源内一起提交或撤销

原子性（Atomicity）指一个事务的数据库修改不会以“只完成其中一部分”的已提交结果对外成立。假设转账先扣 A 再加 B，第二步失败时不能留下只扣款的结果。数据库通过事务状态、日志与版本管理等机制在回滚和崩溃恢复后保持事务边界；具体实现不应一概描述成“所有数据库都用相同 Undo”。

它不表示所有代码都可撤销。事务中打印日志、发邮件、调用支付或更新另一份未加入事务的数据库，不会因本地 ROLLBACK 自动逆转。原子性还不意味着其他事务在任意隔离级别都只能观察一个固定快照，那属于可见性与隔离问题。

保存点（Savepoint）允许回滚事务中一段数据库工作，但不是独立提交；外层事务最终失败时，保存点之前与之后尚属该事务的修改都不会变成已提交结果。只有确实允许部分业务继续时才用保存点，不能把“转账失败只回滚收款”当合理容错。

### 1.2 Consistency：正确规则经过正确事务得到保持

一致性（Consistency）表示事务在规则成立的状态之间迁移。哪些规则需要成立，必须由领域逻辑、约束和并发方案表达。数据库不知道“同币种两账户转账总余额应守恒”，更不知道“用户是否获准操作”。

NOT NULL、CHECK、UNIQUE、FOREIGN KEY 能保护适用的结构与局部条件；金额币种、权限、状态转换和跨行不变量还需业务设计。即使一条语句完全符合类型与约束，也可能把钱转给错误客户。ACID 中的一致性不能直接等同于分布式系统的线性一致性或“副本马上最新”，讨论时应说清所指对象。

以余额非负为例：先读余额 100，再由两个请求各扣 80，如果都基于旧值决定允许，就需要原子条件更新或锁来保护。只在 Java 中写 if(balance>=amount) 并没有把业务规则变成并发不变量。

### 1.3 Isolation：限制并发观察与交错结果

隔离性（Isolation）约定多个事务同时执行时允许看到什么。数据库默认隔离往往不是最高级别，不能把“用了事务”解读为“和完全串行没有区别”。

PostgreSQL 17 默认 Read Committed（读已提交），每条语句读取自己的快照，同事务重复读取可能看到其他事务的新提交；Repeatable Read（可重复读）提供事务一致快照，但仍可能出现跨行写偏差；Serializable（可串行化）使成功事务效果可等价于某个串行顺序，同时应用必须处理序列化失败并重试。

写偏差例如两人都读到“有两位值班医生”，各把自己设为离岗，修改不同行却使无人值班。每行都没有被覆盖，并不意味着整体规则安全。解决方式可以是协调同一稳定记录，或用可串行化事务从头重试，不能只给每行加 version 就宣布完成。

### 1.4 Durability：承诺取决于故障模型与配置

持久性（Durability）是事务被确认提交后，在约定故障范围内保留。PostgreSQL 的 WAL（Write-Ahead Log，预写日志）遵循先持久记录相关日志再写数据页的原则，恢复时可重做尚未落到数据页的已提交修改。因此提交不要求每个脏数据页都已写盘。

但“收到成功后任何灾难都不会丢”不成立。异步提交、存储配置、同步复制范围和故障切换选择影响已确认数据的承诺。主机本地日志持久与多地域灾难后零丢失是不同目标；异步副本提升时可能缺少最近提交。应明确 RPO（Recovery Point Objective，可容忍的数据丢失窗口）与 RTO（Recovery Time Objective，目标恢复时长），并做恢复演练。

备份保护误删、损坏与灾难恢复，复制提高可用性，两者都不是事务代码正确性的替代品。不能为缩短提交延迟随意关闭持久化保障，却仍对业务宣称支付绝不丢失。

## 二、事务生命周期与结果未知

### 2.1 语句成功、flush 与 commit 是不同阶段

一次本地事务可以理解为：建立事务上下文、读取与校验、执行 SQL、检查约束、提交并接收结果。JPA 的 flush 把待执行变更同步到数据库，可能暴露约束或版本冲突；它不等于 commit，也不保证此后不会失败。某些校验可能在提交阶段才完成。

因此不能在刚调用 repository.save 后就对外宣布“付款成功”，更不能认为方法体内没有异常就一定提交成功。Spring 代理通常在目标方法返回后完成提交，异常可能在退出代理时才传给调用方。日志和响应应区分准备、数据库已提交、下游已完成等状态。

数据库失败后连接与事务也需要恢复。在 PostgreSQL 中普通事务遇到错误后通常进入失败状态，应用应回滚，或仅在明确的保存点协议下恢复，不能吞掉异常继续当作成功提交。连接池复用前必须确保事务结束和连接状态正确，否则可能造成下一请求的污染。

### 2.2 明确失败与结果未知的处理不同

如果数据库明确返回死锁或序列化失败并回滚，应用可根据规则重试整个事务。如果 COMMIT 已送达，服务端已提交，但网络断开导致客户端没有收到确认，客户端只知道结果未知（Unknown Outcome），不能断言已回滚。

为写操作设计稳定操作 ID 或业务唯一键，并把操作结果与业务修改放在同一事务。重试携带同一 ID，数据库唯一约束使其查回原结果或安全继续；换一个 ID 就可能变成第二次扣款。幂等（Idempotency）保护同一逻辑操作重复提交的业务效果，不等于所有重试都返回相同网络状态。

操作 ID 必须限定主体/租户与操作类型，并校验请求指纹；相同 ID 携不同金额应拒绝，而非误返回另一请求结果。结果查询也需要授权，随机 ID 不是读取他人交易的凭证。去重记录保留期需覆盖实际重试与恢复窗口。

### 2.3 取消和超时不自动撤销已经提交的工作

客户端超时表示不再等待，不保证服务器已经停止。线程中断、HTTP 连接断开、任务取消和数据库语句取消都有各自传播与支持范围。若数据库已提交，取消不能让余额恢复，必须用新的受控业务操作退款或冲正。

应用设置总 Deadline（最晚完成期限）、连接获取超时、语句超时和锁等待预算，避免每一层重新得到完整等待时长。故障恢复要查实际业务状态，不可把“没有收到成功”当“没有发生”。这也是事务边界与 API 契约必须一起设计的原因。

## 三、事务边界：一个用例是起点，不是机械公式

### 3.1 从不变量决定哪些修改必须同生共死

应用用例（Application Use Case）例如“提交订单”或“同库转账”。通常把一次需要原子保证的状态迁移放入一个短本地事务，多个 Repository 可参与同一事务。关键是它们使用同一受管理资源和事务上下文，而不是代码恰好在同一个方法。

不能为了“一个请求一个事务”把上传文件、等待审批、发送邮件与整个数分钟流程包住。反过来，不能为了缩短事务把扣款与入账随意拆成两个独立提交。先明确允许哪些中间状态，再选择同步原子提交或有恢复机制的状态机。

长事务会延长锁和连接占用，增加冲突、日志与版本清理压力。热点下锁等待增长会拖住更多连接，进而影响无关请求。减少事务内无关计算、提前准备不改变正确性的输入，真正需要一致读取与修改的临界区则保留在事务内。

### 3.2 Spring 注解的覆盖范围与常见陷阱

Spring Framework 6.2 常见代理事务中，外部调用经过代理，拦截器选择事务管理器、开启或加入事务，目标方法返回后提交，符合规则的异常触发回滚。同对象 this 调用可能绕过代理，不能只看方法有没有 @Transactional。

默认通常对 RuntimeException 和 Error 回滚，对 checked exception 不自动回滚；可以通过显式规则或 6.2 提供的默认策略配置调整。必须核对项目实际规则，不要只背默认。捕获异常后返回成功会影响回滚决策，而已经被标为 rollback-only 的事务也不能靠 catch 恢复成可提交。

REQUIRED 通常加入已有事务；REQUIRES_NEW 使用独立事务，内层提交不会因外层随后回滚而撤销，且可能额外占连接。它适合真正独立的工作，不适合用来“确保转账一半总能成功”。readOnly 常是优化提示，不是跨数据库统一的写入安全沙箱。

常规命令式事务上下文与线程绑定，随手启动新线程或 CompletableFuture 不会自动继承数据库事务。响应式事务使用不同上下文机制，也不能照搬线程模型。JPA EntityManager 与连接也不应无协议地跨线程共享。

### 3.3 一个注解不会原子覆盖远程系统

使用本地事务管理器时，HTTP、Kafka 和第二个普通数据库不会因为出现在方法体中就一起回滚。JTA/XA 等分布式事务可以协调支持并实际加入的资源，但需要资源、事务管理与恢复协议共同配合，普通 HTTP 支付并不会自动成为可回滚参与者。

选择分布式原子协调前评估可用性、阻塞、运维与故障恢复成本；不能仅为避免解释最终一致性就承诺任何组合都强原子。大多数跨服务长流程需要显式业务状态与补偿，下文说明具体窗口。

## 四、乐观锁：比较预期版本，拒绝陈旧决策

### 4.1 版本条件与受影响行数

乐观锁（Optimistic Locking）假设冲突相对少，读取时获得版本，提交时比较预期。例子：

~~~sql
UPDATE orders
SET status = 'CANCELLED', version = version + 1
WHERE tenant_id = :tenant
  AND id = :id
  AND version = :expected_version
  AND status = 'DRAFT';
~~~

只有身份、版本与状态都匹配才修改。version 每次受保护修改递增，避免“值改了又改回去”仅比较状态无法发现的变化。受影响行数一行表示本次更新成立，但外层事务仍要成功提交；零行则可能是不存在、无权限范围、版本变化或状态已不允许，不应对所有零行统一宣称“版本冲突”。

先执行受租户约束的查询才能向有权用户解释具体原因；为不泄露对象存在性，无权请求可能统一返回未找到。版本号不是权限证明，猜中版本也不能操作他人订单。

### 4.2 冲突后重读、合并、拒绝分别何时适用

用户在页面读取版本 8，另一用户提交版本 9，旧页面保存应提示冲突并提供当前数据。若只改两个互不相关字段，可以在领域规则允许时做三方合并：比较原值、用户修改、新当前值，确认没有相互影响后再提交新版本。不能直接把旧 DTO 整体覆盖到新实体。

例如一人改送货备注、一人改联系电话可能可合并；一人更改币种、一人更改价格，字段不同却语义关联，不能自动合并。用户确认型操作通常应返回业务冲突而非后台无限重试，避免把用户未同意的新事实当作已授权。

HTTP 自定义版本冲突可按契约返回 409；如果用 ETag 与 If-Match 表达前置条件失败，则通常对应 412。协议码要匹配契约，不能说“乐观锁永远返回 409”。后台纯计算操作可在次数与总预算内重读后重算，但业务拒绝不应被伪装成瞬时故障。

### 4.3 JPA @Version 的能力与边界

实体有 @Version 字段时，持久化提供方在受保护更新/检查时比较版本，发现冲突抛 OptimisticLockException，时机可能在 flush 或 commit。应用不应手工随意篡改版本，而要让受控写路径维护。

批量 JPQL/原生 SQL 等路径不能假定自动遵守与普通托管实体相同的版本检查；直接 SQL 写入若不比较或递增版本，会破坏整个协议。批量更新后持久化上下文也可能仍持旧值，需明确刷新或清理策略。

乐观锁保护被比较的实体版本，关联集合与其他实体是否导致同一版本递增要核对具体映射与规则。若订单总额依赖多条明细，只给订单头加 @Version 却允许其他路径独立修改明细，未必能保护整体。可将所有相关修改统一经过聚合根并递增同一保护版本，或选择其他并发机制。

## 五、悲观锁：先取得协调权，再在短事务内决策

### 5.1 SELECT FOR UPDATE 的有效范围

悲观锁（Pessimistic Locking）在执行关键读改逻辑前锁住相关记录：

~~~sql
BEGIN;
SELECT balance, currency
FROM account
WHERE tenant_id = 7 AND id = 101
FOR UPDATE;
-- 在同一连接和事务中完成授权后的业务判断与修改
COMMIT;
~~~

锁通常保持到事务结束，其他不兼容修改等待；普通快照读不一定被阻塞，具体模式与产品有关。自动提交下 SELECT 结束事务后锁已释放，随后 UPDATE 不再受刚才的临界区保护。拿到锁后等用户输入，更会把整个系统资源留给一个慢操作。

PostgreSQL 查不到行时，不会因此锁住“未来可能插入的同一业务号”，创建唯一性需唯一约束。跨行范围不变量也不能只锁当前查出的少量行就保证没有新成员，需要稳定协调记录、合适隔离或其他设计。

### 5.2 等待、死锁与锁顺序

两个转账 A→B 与 B→A，若各先锁付款账户再锁收款账户，会形成循环等待。统一按账户 ID 从小到大锁，再按业务方向扣加，可减少这类死锁。数据库内部触发器、外键和其他资源也可能参与，顺序协议需覆盖实际写路径。

锁等待应有预算，超时快速失败或有限重试；NOWAIT 可在不愿等待时快速拒绝，不能一律把它改为无限等待。SKIP LOCKED 会跳过被锁行，适合部分队列领取，不适合“必须检查全部账户”的资金查询。

高冲突下悲观锁减少无效重算，却可能成为串行瓶颈；它不保证更高吞吐，也不保证永不失败。优化要缩短持锁时间，控制并发入口与热点，而不是仅扩大连接池。死锁或序列化失败应回滚后重试整个业务事务，不能只补跑最后一条 SQL。

## 六、完整本地转账：把一致性、锁和恢复连起来

### 6.1 最小模型与约束

本例限定同租户、同币种、同 PostgreSQL 数据库转账，金额用最小货币单位整数，不处理外部银行或汇率。生产需补权限、风控、审计、单位范围和账本治理。

~~~sql
CREATE TABLE account (
  tenant_id bigint NOT NULL,
  id bigint NOT NULL,
  currency char(3) NOT NULL,
  balance_minor bigint NOT NULL CHECK (balance_minor >= 0),
  PRIMARY KEY (tenant_id, id)
);

CREATE TABLE transfer_operation (
  tenant_id bigint NOT NULL,
  operation_id text NOT NULL,
  from_id bigint NOT NULL,
  to_id bigint NOT NULL,
  amount_minor bigint NOT NULL CHECK (amount_minor > 0),
  currency char(3) NOT NULL,
  state text NOT NULL CHECK (state IN ('APPLIED')),
  PRIMARY KEY (tenant_id, operation_id),
  CHECK (from_id <> to_id)
);
~~~

operation_id 只在该租户内代表一次逻辑转账，结果与余额一起提交。此简化表只保存成功操作，不承诺对失败响应也永久幂等；若产品要求同一 ID 连余额不足结果都固定，需要另设计拒绝结果记录和重试语义。账户余额不是完整财务账本，真实资金系统通常还需要不可随意改写的分录与对账，不应把此示例当可直接上线的银行实现。

### 6.2 按步骤执行与处理分支

下面是事务算法，冒号参数由应用绑定，条件分支由应用实现；不是可直接复制执行的 SQL 脚本。

~~~text
校验身份、租户、金额>0、源目标不同、币种与整数范围
BEGIN
  INSERT transfer_operation(..., state='APPLIED')
    ON CONFLICT (tenant_id, operation_id) DO NOTHING
    RETURNING operation_id

  若未插入：
    查询该租户的已有操作
    参数完全一致：返回已有成功结果，结束当前事务
    参数不一致：拒绝同一ID复用，回滚

  分别按较小ID、较大ID对两个账户 SELECT ... FOR UPDATE
  验证两账户存在、授权范围、币种一致
  验证源余额>=金额，目标余额+金额不会溢出
  UPDATE 源账户 SET balance_minor=balance_minor-金额
  UPDATE 目标账户 SET balance_minor=balance_minor+金额
COMMIT
提交确认后返回成功
~~~

APPLIED 在此事务未提交时对正常读者不可见；后续校验失败必须回滚连同操作记录，不能提交“已应用”但未转账的状态。遇到并发相同 ID，唯一性仲裁可能等待对方事务；PostgreSQL Read Committed 下冲突后另起一条查询可观察已提交结果。若实际隔离或错误状态不同，应按事务结果重试，而不是假定同一 SQL 快照永远能读到对方。

成功操作必须校验所有语义相关参数，不能只看 ID。先锁小 ID 再锁大 ID与资金方向无关；账户 202 给 101 转账，仍先锁 101。更新零行、溢出或任意约束失败都须回滚。账户跨租户查不到时不能退化为只按 id 再查。

### 6.3 五个故障点与恢复

| 故障时刻 | 数据库应有结果 | 调用方恢复 |
|---|---|---|
| 开事务前失败 | 没有本次转账 | 同 ID 可再次请求 |
| 只插入操作记录后失败 | 回滚后无成功记录与余额变化 | 重做完整用例 |
| 已扣款、未入账时失败 | 同事务全部回滚 | 不能只补入账，应完整重试 |
| COMMIT 被明确拒绝 | 没有本次已提交效果 | 按错误类型重试或拒绝 |
| 已提交但响应丢失 | 余额与操作结果都已提交 | 同 ID 查回结果，不能新 ID 再转 |

正常进程崩溃后未提交事务由数据库恢复处理，但本地持久化与灾难切换仍遵循前述故障模型。应用在结果未知时不能先给对端“保证已失败”，又稍后发现钱已到账；API 应提供可查证状态。

### 6.4 改成乐观锁是否更好

也可给两账户加 version，读取后分别条件更新，并与操作记录同事务，任何一项冲突回滚全部。低冲突时减少预先锁定的等待，但 UPDATE 本身仍有数据库并发协调，不是“完全无锁”。

若热点账户持续竞争，乐观失败导致两条账户逻辑不断重算，可能比短悲观临界区更贵；反之长时间持锁会拖垮系统。选择应看冲突率、临界区成本、等待预算与公平性，验证两种方案在相同业务约束下的成功吞吐与尾延迟，而非按读写比例单独决定。

## 七、库存、文档和高价值序列操作的不同选择

### 7.1 用户编辑文档：尊重用户意图

编辑持续几分钟时不能一直持数据库行锁。客户端带版本或 ETag，保存时乐观比较；冲突后展示差异，按领域规则合并或让用户确认。重试不是把旧全文覆盖到最新版本，尤其审批文件、合同和医疗记录不能静默“最后写入者胜”。

版本检查只在保存时短暂运行，读取可通过普通快照；若还要协同实时编辑，那是另一种变更合并协议，不能因为加了 version 就声称支持协作编辑。

### 7.2 库存热点：条件更新、排队与所有权

只需库存不低于零，可优先原子条件更新并检查行数，不一定先 SELECT FOR UPDATE：

~~~sql
UPDATE stock
SET available = available - :quantity
WHERE tenant_id = :tenant AND sku = :sku
  AND :quantity > 0 AND available >= :quantity;
~~~

单行正确性不等于整个订单正确性；多个 SKU 与订单创建仍需合适事务，扣了库存却没建单不能无恢复地遗留。预留模式可建预留 ID、数量和到期状态，确认/释放用条件状态迁移，避免重复释放把库存加多。

极热 SKU 仍可能串行竞争。队列或分区所有权把同一键交给一个处理通道，能控制并发和削峰，但增加等待、故障接管、重复消息与所有权 fencing（隔离旧持有者）责任。仅用一个租约锁而无法拒绝旧持有者的迟到写入，可能在接管后出现双写。无论哪种模式，不能以排队受理等同最终有货。

### 7.3 小范围高价值操作：短悲观协调可更直接

发放某个唯一名额或变更少量高度关联记录，若冲突高而判断很短，先锁稳定协调记录再执行，可能比重复乐观失败更清晰。需要有界等待、统一顺序、数据库约束和审计，避免锁粒度扩大成全租户串行。

若操作真正要求“序号连续无缺”，普通数据库序列不能自动满足，因为回滚等可能留空；应先澄清是否只是唯一且大致递增，还是法律/业务要求连续。更强的编号规则会增加串行化与恢复成本，不要把技术 ID 当业务承诺。

## 八、跨系统边界：可靠发布、补偿与对账

### 8.1 Outbox：避免数据库成功但事件丢失

数据库提交订单后直接发 Kafka，进程可能在二者之间崩溃；先发 Kafka 再提交又可能产生没有订单的事件。Outbox 在同一本地事务写订单与待发消息，转发器持续投递并记录进度。

若代理已收到消息但转发器尚未记成功时崩溃，会重发。因此消费者按稳定消息 ID 去重，并把去重记录与本地业务效果同事务提交。它缩小并可靠恢复发布窗口，不保证任意下游效果全局恰好一次。事务提交后的回调也不是持久 Outbox，进程可能在回调执行前消失。

### 8.2 Saga：补偿是新的业务动作

Saga 是把跨服务流程分成多个本地事务，每步成功推进状态，失败后按业务执行补偿。例如预留库存、授权支付、创建发货；支付失败可释放预留，已发货后则可能需要退货而不是简单删除订单。

补偿自身可能失败、重试或遇到并发，必须有操作 ID、持久步骤状态和人工处理入口。它不是数据库回滚，不保证中间状态从未被人看到。业务需要隔离这些状态，例如仅对已确认订单允许发货，并为重复与乱序的回调定义状态转换。

高价值流程要明确不可逆点：向外付款或发货后补偿可能有成本与时延，不能承诺“失败就恢复到从未发生”。选择最终一致前必须得到业务对中间状态与恢复时限的接受。

### 8.3 幂等与 Reconciliation：把遗漏和不确定收敛

幂等保护重复执行，对账（Reconciliation）比对权威记录并找出遗漏、漂移与结果未知。例如本地付款显示处理中，但支付机构已有成功流水，应按可信外部业务 ID查询并更新状态；不能仅凭客户端回调金额。

对账应有周期、差异分类、自动修复边界与审计。自动退款或补扣本身是新高风险写入，要有授权规则，不能把所有差异直接抹平。来源、重试、补偿和对账共同构成恢复闭环，而不只是列四个模式名。

## 九、工程验证与排障：验证不变量而非只测方法返回

### 9.1 本地并发实验应该看到什么

在独立测试环境创建第六节表，两账户初始 10000 与 5000。A 读取订单版本 8，B 也读版本 8；A 成功更新到 9 后，B 的 version=8 更新应零行，或 ORM 抛适用版本冲突。检查最终值不被旧请求覆盖，不要只断言异常类。

转账实验用两个独立连接并设置屏障：让两个请求同时带同 operation_id、同参数开始，最终只一笔效果，余额为 9000 与 6000；不同参数复用同 ID应拒绝。再在扣款后人为抛异常，确认两余额和操作记录一起回滚。不同 ID 的合法两笔转账则必须累计两次，不能误去重。

验证悲观锁时让 A 锁住较小账户，B 尝试取得同一锁，应等待或按预算失败；A 完成后 B 重新读实际状态。分别模拟反向访问制造死锁、统一顺序减少死锁。实验需要真实独立连接，单线程内顺序调用两个服务不能证明并发正确性。

### 9.2 故障注入与指标

还需在提交响应丢失、消费者提交后确认丢失、补偿服务超时、旧持有者恢复等故障点测试。单纯关闭应用不一定能准确制造 COMMIT 结果未知，测试必须记录注入位置与数据库真实结果。不能把其他数据库或内存模拟的通过结果视为 PostgreSQL 崩溃恢复证明。

监控事务时长、锁等待、版本冲突率、重试次数、连接获取等待、提交失败/未知数量、Outbox 最老未发年龄、Saga 卡住时长与对账差异。按业务操作 ID 串起日志，避免敏感载荷与高基数字段进入通用指标标签。

冲突率升高先看是否是热点、过长临界区或多层重试；“零版本冲突”也可能是某些 SQL 绕过 version。出现连接耗尽查长事务和远程等待，不能仅扩池。事务成功而业务仍不一致，则查写入口、跨资源副作用与状态机，不要只换隔离级别。

## 十、完整面试回答与深入追问

### 10.1 “一个 @Transactional 能保证订单、扣款和发消息原子吗？”

回答示例：“先确认事务管理器和参与资源。如果只是一个本地数据库，注解可以保护实际加入的数据库操作，但不自动覆盖远程支付和 Kafka。我会把本地订单状态与 Outbox 同事务提交，远程支付使用稳定操作 ID、结果查证和持久状态机；跨步骤失败按业务补偿并对账。只有支持且实际加入分布式事务的资源，才谈相应协调保证。”

追问：“提交后再发消息不是够了吗？”答：“进程可在提交后、发出前崩溃，回调不是持久任务。Outbox 把待发意图随订单提交；转发仍可能重复，消费端必须去重。”

### 10.2 “乐观锁和悲观锁怎样选择？”

回答示例：“我先确定不变量与冲突范围。编辑文档适合版本比较，冲突后让用户确认；短而高竞争的少量记录可悲观协调；单行库存条件可以直接原子更新。乐观锁也会在数据库更新时协调，悲观锁也可能死锁，两者都需处理提交失败。实际选择比较冲突率、重算成本、持锁时间、等待与吞吐，而非简单读多选乐观、写多选悲观。”

追问：“乐观锁失败直接重试原更新？”答：“不应盲目重放旧绝对值。必须重读后重算或返回冲突；若是用户意图关联新状态，应让用户确认。若是完整事务失败，则新事务重新执行整个决策。”

### 10.3 “事务成功返回后服务器断电，会丢钱吗？”

回答示例：“要区分应用进程崩溃、主机/磁盘损坏和跨区域切换。正常持久配置下数据库通过 WAL 等机制恢复本地已确认提交，但异步提交或异步副本切换会改变承诺。我会确认写持久化、复制确认范围、RPO 与恢复演练，不笼统承诺任何灾难都零丢失。若只是响应没送达，客户端也不能认定失败，要按操作 ID查证。”

追问：“ACID 不就是绝对可靠？”答：“它有资源与故障模型边界，而且不自动证明业务规则、授权或外部副作用正确。可靠性需要事务、配置、存储、复制、备份和应用恢复一起成立。”

## 十一、扫雷自测与推理答案

### 11.1 flush 成功是否代表事务已提交？

**不代表。** flush 只是把待处理变更同步到数据库，仍可能回滚，提交阶段也可能失败。应在实际提交结果确定后声明对应成功；代理外的调用方也要处理提交时异常。

### 11.2 version 更新零行一定是并发冲突吗？

**不一定。** 记录不存在、租户范围不符、状态条件失败也会零行。先防信息泄露，再对有权主体按实际状态分类。不能以一次零行证明某个特定原因，更不能把零行当成功。

### 11.3 同一记录所有写入口都要维护 version 吗？

**受该协议保护的写入都要遵守。** 一个批量 SQL 绕过比较或递增，就可能让旧客户端无法识别变化。JPA 注解不是对数据库所有入口自动生效的魔法；脚本、作业与关联修改都要审查。

### 11.4 悲观锁查完后结束事务，再更新是否仍受保护？

**不受先前锁保护。** 锁随事务结束释放，其他事务可在两步之间修改。读、判断、写应在同一受控事务，或改为版本条件/原子更新。

### 11.5 为两账户加独立版本是否自动保护所有跨行规则？

**不自动。** 本地转账可通过两次条件更新同事务、任一失败全部回滚保护；但跨行读取、分别修改的写偏差可能没有同一行冲突。需围绕具体不变量选共同协调或可串行化。

### 11.6 扣款成功后入账抛异常，重试只补入账可以吗？

**在同一已回滚本地事务的前提下不可以。** 扣款也已撤销，只补入账会凭空加钱，应完整重试。若本来跨两个已独立提交系统，则要按真实状态机恢复，不能套用本地回滚假设。

### 11.7 COMMIT 后断网是否等于可以换 ID重试？

**不能。** 可能已经提交，换 ID会成为新业务。保留原操作 ID，查证或在数据库幂等仲裁下恢复，区分明确回滚与结果未知。

### 11.8 Outbox 是否保证下游支付恰好一次？

**不保证。** 转发和消费都可能重复；本地消费事务不能回滚外部支付。需外部幂等键、操作状态与结果查询，再配合补偿和对账，明确每一份保证的覆盖范围。

### 11.9 有钱时先申请悲观锁，是否适合让用户几分钟后确认？

**不适合长时间持数据库事务。** 用业务预留状态、到期规则、确认/释放幂等和恢复机制表达等待，数据库事务只完成短暂状态迁移。业务预留与数据库锁是不同层次。

### 11.10 Saga 补偿成功是否证明流程从未发生？

**不能。** 中间状态可能已经可见，补偿是新事务，可能有费用、延迟或无法完全逆转的效果。需定义不可逆点、受限可见性、重试与人工处理，不把补偿包装成数据库回滚。

## 十二、速记、验证范围与来源

- ACID 先说明资源、约束、隔离与故障模型；本地正确不代表跨系统原子。
- flush、方法返回、commit 确认、业务最终完成不是同一时刻。
- 乐观锁比较预期版本，冲突需重读重算或提示；悲观锁在短事务内协调，并承担等待与死锁。
- 热点库存优先分析原子条件更新与状态模型，不机械先加锁或换队列。
- 重试明确回滚的完整事务；提交结果未知按稳定业务 ID查证。
- 跨边界用持久状态、可靠发布、幂等、补偿与对账形成闭环。

本章 SQL与算法是教学实现，转账算法包含应用分支，不是可直接执行的 SQL 脚本。未运行 PostgreSQL/JPA/Spring 集成、双连接并发、崩溃或外部支付实验；正文的预期结果不能视为测试通过。已检查原主题覆盖、全部小节自足性、参数/字段与事务失败时序、面试追问和自测答案。独立状态模型验证只能帮助检查算术与恢复推理，不能证明真实引擎行为。
