# 01. 性能基线、压测、Profiling 与瓶颈定位

> 本章目标：能够设计可重复的性能实验，判断测量是否可信，沿请求路径找到限制吞吐或尾延迟的因素，再用单一变更验证因果。性能结论必须带业务语义、负载与环境，不能只有“提升了多少倍”。
>
> 版本范围：诊断命令以 JDK 21 为基线，数据库计划参考 PostgreSQL 17；async-profiler 与 k6 必须按实际安装版本核对选项。示例负载、预算与结果均为教学假设，未表示真实生产容量或用户项目经历。

## 一、性能基线：让“优化了”成为可证实的命题

### 1.1 Baseline 不是一张平均响应时间截图

Baseline（基线）是对固定业务语义、环境和负载下系统行为的可重复描述。一次优化前后若数据、缓存、机器或查询语义变了，测量差异就不能全部归因给代码。

至少保存应用提交与构建版本、JDK/GC/启动参数、容器CPU与内存限制、实例数量、数据库与索引、连接池、依赖版本、测试数据生成方式、请求混合、并发/到达率和测试时段。环境噪声如共享主机、后台回填、自动扩缩容也要记录。配置文件“同名”不证明最终有效配置相同。

业务成功条件要一并固定。原请求完成订单落库，新请求只把任务入队就返回，两者延迟不可直接比较；必须分别测受理与最终完成。关闭鉴权、审计、持久化或约束获得更快结果，是改变服务，不应冒充同等可靠性下的性能优化。

### 1.2 指标应覆盖用户、应用与依赖

| 层次 | 应记录什么 | 能解释什么 |
|---|---|---|
| 用户与入口 | 到达/实际发送/完成RPS、p50/p95/p99、超时、业务错误 | 是否完成承诺、是否丢请求 |
| 应用 | CPU核时、分配率、堆/RSS、GC、线程、队列、连接等待 | 算力、内存与并发资源是否饱和 |
| 数据库 | 调用数、计划、锁等待、连接、I/O、复制滞后 | 查询成本与共享瓶颈 |
| 外部依赖 | 每请求扇出、耗时、错误、限流与重试 | 慢依赖和重试放大 |
| 压测端 | CPU/网络/连接、调度延迟、丢弃迭代 | 工具是否真正发出了目标负载 |

RPS（Requests Per Second）是请求速率，业务完成率另需定义；一次业务可能含多次HTTP调用，重试请求也不能算成额外成功业务。p99表示99%观测请求延迟不超过该值，不是最大值；平均值会隐藏少数很慢的请求。错误与超时不能被从延迟样本中静默移除，否则系统越拒绝慢请求，看起来反而越快。

多个实例的p99不能简单求平均，需汇总可合并的直方图/原始分布，再按同一口径计算。请求量太少时p99极不稳定，要说明样本数与观察窗口，不应拿几十个请求的小数位变化宣布收益。

### 1.3 Workload 必须反映数据与流量结构

Workload（工作负载）包括读写比例、接口组合、记录大小、查询选择性、热点与租户分布，以及身份和业务状态。全读测试不能代表带事务写入的服务；均匀随机键也不能代表一个SKU承担半数流量的促销场景。

数据库空表、每个请求永远命中同一缓存键、所有认证复用超长有效Token，可能只覆盖最容易路径。应按业务需要包含有效/无效请求、分页深度、不同响应大小、真实权限范围与状态转换，并避免测试重用相同幂等键导致所有写都成为廉价去重查询。

Cache Warm/Cold（热/冷缓存）分别测。冷不仅指Redis，还可能是数据库缓冲、操作系统页缓存、DNS/TLS/连接、类加载与JIT。说明暖机多久、何时进入测量窗口，也保留启动与冷恢复测试。只比较第一次冷运行和第二次热运行，会高估优化。

## 二、负载模型：工具发了什么，服务才承受了什么

### 2.1 闭环并发与开放到达率回答不同问题

Closed Model（闭环模型）固定一批虚拟用户，每人等上一次完成，再思考或发送下一次。服务变慢时，用户发下一次更迟，实际到达率下降。适合模拟确有等待行为的用户，不能直接拿固定100线程证明系统始终承受1000RPS。

Open Model（开放模型）按计划到达率发起请求，不以之前是否结束作为唯一条件，更适合模拟外部持续到来的请求。若压测端并发或资源不够，计划请求可能无法发送，应报告调度/丢弃，而不是把它们从统计里消失。

Coordinated Omission（协调遗漏）是服务停顿时，负载生成或测量同时减少了本应发生的请求/等待，从而低估用户会遇到的延迟。开放模型有助暴露这类问题，但不是自动免疫；仍要记录计划开始、实际开始与完成，确认工具和指标是否覆盖排队与未发送工作。

### 2.2 Little定律与饱和点

稳定系统在同一边界下满足平均在途数 L = 到达率 λ × 平均停留时间 W。假设500RPS、平均200ms，则平均在途约100。这里是平均关系，不能用p99代入当精确线程池大小，也不保证系统能承受该到达率。

如果固定100并发且无思考时间，平均耗时从100ms变为1秒，理想闭环完成率从约1000RPS降到100RPS。工具“没有更多失败”可能只是自动减小了负载。开放持续1000RPS时，若系统只能完成800RPS，积压约每秒增长200，持续一分钟约12000个工作。

Saturation Point（饱和点）是某个关键资源接近可用能力，使更多输入主要增加等待而非有效吞吐。资源可以是CPU、数据库锁、连接、网络或单热点分区。接近饱和时突发与服务时间变化会放大队列与尾延迟；不能把一小段低负载下的线性趋势无限外推。

### 2.3 排队预算、超时与重试应一并测量

请求总耗时由排队、连接获取、处理、依赖和返回组成。只有服务代码执行时间很短，不代表用户体验好。若总预算300ms，排队已花200ms，依赖不能再单独等完整300ms。

超时不保证后台工作已停止，重试可能与原请求重叠。三层各重试三次，最坏可扩为27次尝试；测试需区分入口业务操作与下游实际调用。写操作必须验证幂等和最终状态，不能只统计HTTP成功。

线程池/连接池队列应有界，压测达到上限时验证拒绝、降级与恢复。无界队列可能暂时没有错误，却把失败推迟为内存耗尽或等待超时。稳定容量应定义在满足延迟与错误目标时，而不是只报“最大能接收多少请求”。

## 三、五类测试各自解决什么

### 3.1 Load：验证目标峰值下的承诺

Load Test（负载测试）在预期常态与峰值下，验证目标延迟、成功率和资源余量。逐级升压并在每档停留，等系统达到可比较状态，再采集测量；不能几秒扫过全部档位便当稳态容量。

每一档检查请求混合、实际发送/完成速率、队列趋势和依赖。若队列持续增长，就不算稳定，即使短时间成功率仍高。目标峰值通过后还应保留故障与突发余量，不以CPU恰好100%作为可运行配置。

### 3.2 Stress：找极限，也找失败形态

Stress Test（压力极限测试）超过目标峰值，找饱和拐点和崩溃边界。价值不只是最大RPS，还包括是否有界拒绝、是否拖垮数据库、是否产生重复业务、降压后是否能自行恢复。

在隔离环境设置停止条件，例如错误、内存、数据库等待或积压超过上限。不要为了“测到底”对真实外部支付或生产共享服务无限施压。极限结果与负载、语义、环境绑定，不能直接成为另一环境容量承诺。

### 3.3 Spike：测试突发与扩容迟滞

Spike Test（突发测试）突然增加或恢复流量，检查冷连接、缓存击穿、线程创建、自动扩缩容和速率保护。即使最终实例数足够，扩容需检测、启动、预热和路由，期间可能已过载。

用相同总请求量但不同到达形态比较，才能看到平滑与尖峰的差异。恢复后也可能有重试和后台重建第二波流量，应观察到队列清空与指标回稳，不是尖峰结束就停止测试。

### 3.4 Soak：观察长期泄漏与退化

Soak Test（浸泡/耐久测试）在代表性负载下持续运行，观察堆/非堆、连接、线程、文件描述符、缓存键、磁盘、日志与延迟趋势。时长应覆盖要验证的周期，如连接轮换、缓存过期、定时任务、批处理与证书刷新，不靠机械统一“跑24小时”代替设计。

堆随分配上升后GC回落不一定泄漏，关注相似负载下存活集合是否持续增长；RSS增长也可能来自直接内存、线程栈或本地库。压测期间数据本来就不断新增时，需要把合法业务增长与无界保留区分。

### 3.5 Failover：故障后的容量与正确性

Failover Test（故障切换测试）在明确负载下移除实例、使缓存不可用或让依赖变慢，验证剩余系统能否保持核心服务、是否产生重试风暴，以及恢复时是否二次过载。数据库故障要在可控环境并定义数据恢复目标，不能仅看新主起来了。

三实例共处理1500RPS时，少一实例后如果平均分配，每个剩余实例负载从500变750，增加50%，不是33%。数据库仍可能是共享瓶颈，应用加实例并不增加其容量。故障测试必须检查最终业务不变量、结果未知和副本新鲜度，而不只看HTTP是否返回。

## 四、Profiling：根据问题选择证据

### 4.1 CPU Profile与Wall-clock Profile

Profiling（剖析）通过采样或事件了解资源花在哪里。CPU采样关注实际运行消耗CPU的调用栈，适合CPU高时定位计算、解析、压缩或序列化热点。Wall-clock（墙钟时间）关注经过的时间，能显示等待和阻塞，适合CPU不高却延迟大的情况。

Flame Graph（火焰图）宽度代表聚合采样权重，不是每条请求的时间线；纵向是调用关系，不表示先后顺序。一个函数很宽可能因为调用次数多，不一定单次慢；它也可能是框架包装，需沿业务调用与输入理解。采样有偏差和误差，栈解析、内联、运行时与权限都会影响结果。

不要只看一个“最宽方法”就替换实现。先判断它占端到端哪部分、是否可减少调用、是否属于必须工作。CPU火焰图里看不到慢网络的完整等待，并不说明网络不是瓶颈。

### 4.2 JFR与async-profiler怎样用

JFR（Java Flight Recorder）记录JVM事件，能关联执行采样、分配、锁、GC与部分I/O等信息；具体事件是否启用、阈值与采样配置会影响可见性。async-profiler支持多类采样，依赖操作系统、JDK与权限配置；CPU、分配、锁或wall等模式需按所用版本核对，不能假定一个默认文件包含所有证据。

JDK21诊断示意：

~~~bash
jcmd 12345 help JFR.start
jcmd 12345 JFR.start name=perf settings=profile duration=60s filename=/tmp/perf.jfr
jcmd 12345 JFR.check
jcmd 12345 Thread.print -l
~~~

12345需换成明确目标PID；同机、身份与容器命名空间权限要满足。先查help确认目标JVM能力，profile配置与时长按风险调整。文件可能含敏感路径、方法名和请求相关数据，限制访问与保留，不上传未审查的生产记录。

剖析本身有成本，短窗口和合适事件降低干扰，但不能承诺零开销。先在预演环境比较开启前后吞吐与延迟，线上采集时控制范围。文件落盘空间、采样频率与CPU权限都需检查，避免排障工具成为新负载。

### 4.3 Allocation、GC日志与Heap Dump分工

Allocation Profile（分配剖析）告诉你对象主要在哪里创建，适合“CPU与GC随流量上涨”的问题；Heap Dump（堆转储）展示某时刻保留对象及引用关系，适合查谁让对象不能释放。分配最多不等于泄漏最多，短命大流量和长期少量保留需分开。

GC日志看暂停、频率、分配/回收趋势和失败信号；不能只看到堆使用高就加Xmx。增加堆可能减少频率，也增加占用并改变暂停/回收行为，且容器还需要线程栈、直接内存、Metaspace等空间。

JDK21可在受控启动中记录：

~~~bash
java -Xlog:gc*:file=/tmp/gc.log:time,uptime,level,tags:filecount=5,filesize=20M -jar app.jar
~~~

日志路径、轮转与磁盘预算按部署调整，不能将此参数当通用调优方案。Heap Dump可能暂停或显著干扰进程且文件很大，需先评估堆规模、磁盘与安全；不要在最脆弱节点无准备地采集。转储中的密码、个人信息与业务载荷需严格保护。

### 4.4 Thread Dump解释阻塞与池耗尽

Thread Dump显示线程栈、状态和部分锁信息。连续多个时刻相同线程在相同锁/连接获取点等待，比单张快照更有诊断价值；一张图中WAITING多可能只是空闲工作线程，不直接证明故障。

BLOCKED常与监视器竞争相关，park/WAITING可能是队列、Future、连接或其他同步等待。Java RUNNABLE不保证正在占CPU，也可能处于某些本地I/O路径；应与CPU、系统调度和wall profile一起看。

线程池耗尽时区分任务在算、在等数据库、等远程、还是互相等待提交到同一池的子任务。增加线程对CPU饱和无益，反而增加调度与内存；对慢依赖也可能放大下游压力。虚拟线程降低某些线程占用成本，也不会创造更多数据库连接或CPU。

### 4.5 Trace与数据库证据连接请求关键路径

Trace（分布式链路）把一次请求拆成Span，寻找跨服务Critical Path（关键路径）。串行依赖可以相加，平行分支通常由较慢必要分支决定；不能把所有Span时长求和当请求总延迟，也不能把各组件p99相加当严格端到端p99。

采样可能漏掉故障，线程/异步上下文丢失会让Span不完整；数据库连接等待、线程排队若未埋点，可能只在“未解释时间”里。把Trace、指标和Profile对齐同一负载窗口，避免用不同时间的数据拼故事。

数据库慢查询与EXPLAIN用于确认扫描、基数、Join、排序与锁。EXPLAIN ANALYZE真的执行，写语句不可在生产随意尝试；锁等待和连接池等待也不一定由一份无竞争计划体现。先证明每个请求SQL次数与返回量，再讨论索引或ORM改造。

## 五、证据驱动的定位循环

### 5.1 Metric → Layer → Profile → Hypothesis

先用Metric（指标）判断影响与资源：延迟升高同时CPU是否高？完成率是否触顶？连接等待、队列、依赖耗时哪个先变化？再定位Layer（层次）：入口、应用、数据库、缓存、外部系统或压测端。

之后选合适Profile/Trace/Plan收集证据，提出可证伪Hypothesis（假设）。例如“每请求序列化多次大对象导致CPU与分配上升”应能预测减少重复序列化后每业务CPU核时、分配字节和GC下降，而不只是RPS短暂变高。

如果证据不支持，修改假设而不是继续增加JVM参数。CPU低且连接等待高，先查数据库持锁与连接占用；CPU高但容器受限，检查throttling（CPU配额限流）与实际核数，而不是只看宿主机平均CPU。

### 5.2 单一Change、重测与副作用检查

每次尽量只改一个可解释因素，保持其他基线一致；组合变更可以在实际交付中存在，但要承认无法单独归因。重复前后实验，交替或分批运行以减少环境漂移影响，记录波动，不以一次最好值代替典型结果。

检查吞吐、尾延迟、错误、CPU/业务、分配/业务、数据库调用与资源。某索引让读快但写和存储上涨，某缓存让p99好看但权限陈旧，某批处理吞吐增加却延迟超预算，都不是单指标无条件胜利。

灰度上线保留回退，观察真实请求形状与异常路径；配置改动的回退也要考虑已经增长的队列与状态。性能修复没有验证业务正确性，不能算完成。

### 5.3 Amdahl定律防止优化无关部分

Amdahl定律说明整体收益受未优化部分限制。假设串行总耗时中只有20%可被优化，即使这部分变成零，整体最大加速也只是1/(1-0.2)=1.25倍。优化只占少数时间的热点，不可能让端到端提升十倍。

它是简化模型，现实还可能有排队、缓存与瓶颈迁移，不能直接当性能预测器。价值是让人先估影响面，再投入复杂改造；优化后继续检查新瓶颈，而不是永久相信第一次定位。

## 六、一份可复用的压测方案与结果记录

### 6.1 虚构订单查询基线

假设目标：固定三个应用实例、每实例2vCPU，测试库一千万订单，读写80/20，最大租户占30%流量；在目标1500业务请求/秒下，p99不超过300ms，错误率不超过0.1%，写不重复。数字只是实验设计，不是本仓库验证成绩。

定义请求比例与输入生成：读取最近页、详情、创建订单及状态更新，创建使用唯一操作ID，另设重复ID验证幂等。认证与权限校验启用，载荷大小按分布覆盖，不把全部数据都压在一个测试用户。副本、缓存与真实依赖或模拟延迟分布需注明。

阶段可依次是预热、分档常态、目标峰值稳定段、短突发、降压恢复，再另跑耐久和故障。稳定段时长要足以采样并观察队列是否增长，耐久覆盖系统周期。每阶段保存输入、实际到达/完成、错误与业务校验，而非只留最终汇总一行。

### 6.2 压测工具必须独立自证

生成端与服务端尽量隔离，监控工具CPU、网络、端口/连接、TLS成本和调度。增加生成器后服务吞吐跟着上升，说明之前可能是工具瓶颈；但新增生成器也改变连接分布，仍需解释。

若目标1500RPS而实际仅1000，应报告未达到目标，不能拿1000的良好延迟宣称1500通过。工具丢弃迭代、超时、连接失败和客户端取消都要计入。分布式生成器的时钟、统计聚合与身份数据也需协调。

### 6.3 从测量到结论的记录模板

~~~text
业务与验收：
  操作成功含义、负载窗口、延迟/错误目标、正确性条件
可复现输入：
  commit、配置、实例/配额、数据/热点、缓存状态、依赖、工具版本
原始观测：
  计划/实际/完成速率、分位与样本数、错误、队列、资源和业务校验
假设与证据：
  同窗口Trace/Profile/Plan及其限制，预期变化指标
单一变更：
  改动、风险、回退条件
重测：
  多次运行分布、同负载对比、写/读/成本/正确性副作用
结论：
  已证实收益、未覆盖边界、容量余量与下一次触发复评条件
~~~

模板的意义是让另一位工程师能复现并质疑结论，不是填写一个“通过”状态。未执行的部分明确写未执行，预期结果与实际结果分开。生产高风险诊断应先有取证与回退准备，不为一张更漂亮图牺牲可用性。

## 七、常见症状怎样推理

### 7.1 CPU很高、GC也多

先检查同负载下CPU核时与分配/业务是否上升，用CPU与Allocation Profile定位重复解析、序列化、装箱、大集合复制。再看GC暂停和存活集合，判断主要是高分配还是保留增长。若调用量变多，只看总分配会误以为实现变差，应做每业务归一化。

减少不必要对象或重复工作后，验证语义与缓存失效，重测CPU、GC和延迟。盲目换收集器可能移动症状，却不消除昂贵分配。若CPU其实被容器限制，需要同时检查配额与调度等待。

### 7.2 CPU不高、p99却很差

查连接池等待、锁、依赖尾延迟、线程互等与队列。Wall Profile、连续Thread Dump与Trace比仅CPU图更有价值。假设少数数据库事务长时间持锁，其余线程大多等待，因此CPU低但用户很慢。

修复应缩短临界区、优化依赖与限流；直接扩大池可能让数据库更饱和。需要确认慢请求是哪个租户/操作，避免全局平均掩盖单热点。

### 7.3 单实例更快，全站却没有改善

可能瓶颈在共享数据库、外部API或网络，也可能入口负载分布不均。检查每实例请求、下游QPS与等待，测全系统而非将单实例吞吐乘实例数。

优化应用后可能把更多请求更快送到数据库，新瓶颈上移并增加失败。因此端到端验收要包括总容量、依赖预算与故障余量，不能只验一个方法的纳秒级基准。

### 7.4 微基准与宏观压测各有什么角色

Microbenchmark（微基准）隔离局部代码成本，Java可用JMH等专门框架处理暖机、重复、死代码消除与结果消费；手写循环计时容易测到编译器优化或常量折叠。宏观压测覆盖真实入口、并发和依赖，噪声更多却更接近业务。

局部算法快两倍不代表服务快两倍，仍受Amdahl与共享瓶颈限制。先用宏观证据证明局部重要，再用微基准比较实现，最后回到宏观验收。不能拿笔记本空库基准承诺生产容量。

## 八、完整面试回答与追问

### 8.1 “你怎么做性能优化？”

回答示例：“我先定义业务成功语义、目标负载和可重复环境，记录端到端分位、错误与资源。分层看CPU、排队、连接、依赖和数据库，选择CPU/wall/分配剖析、Trace或计划验证假设。一次改一个主要因素，按相同输入重复测，并检查正确性、写入、内存和成本副作用。最终灰度观察真实分布和回退，而不是先调JVM参数。”

追问：“为何不用经验直接加线程？”答：“如果CPU或数据库已经饱和，更多线程只是增加排队。要先证明等待来源和下游预算，再决定是否增加并发。”

### 8.2 “100并发压测无错误，能承诺1000RPS吗？”

回答示例：“不能。闭环并发会随服务变慢降低实际到达率，必须看真实发送与完成速率。若平均一秒，100并发大约只完成100RPS。目标持续到达率要用合适开放模型并验证生成端资源，报告未发送与丢弃，且以满足尾延迟和业务正确性的稳定段判定容量。”

追问：“开放模型就没有遗漏？”答：“也不自动保证。工具可能缺少并发资源或统计只覆盖实际发出的请求，需看计划与实际时间、调度和丢弃口径。”

### 8.3 “火焰图最宽函数就是根因吗？”

回答示例：“它是该采样事件下权重大，不是因果证明。CPU图可能漏掉等待，宽度也可能来自高调用次数或框架包装。我会关联同窗口请求链路和每业务资源，提出减少具体工作的假设，再用单一变更重测。不要把图形本身当最终解释。”

追问：“采集会不会影响结果？”答：“会有成本，取决于事件和频率。先验证开启前后差异，控制窗口和文件，不宣称零开销，也不在脆弱节点无准备采大转储。”

## 九、扫雷自测与推理答案

### 9.1 平均延迟不变而p99升高，是否没退化？

**不是。** 少数长请求可被大量快请求平均稀释。检查队列、热点、GC和慢依赖，并确认超时样本没有被排除。业务若看重尾延迟，就必须按相同窗口与样本量验证p99。

### 9.2 CPU图没有网络热点，是否网络一定正常？

**不是。** CPU采样主要观察运行消耗，不完整反映等待。应使用wall、Trace与网络/连接指标检查，不能用一个工具缺少证据推导资源无问题。

### 9.3 系统慢时固定线程工具发得更少，这有什么风险？

**可能低估真实持续流量下的等待与错误。** 闭环按完成节奏减少输入，出现协调遗漏类测量失真。要按场景选择模型，报告计划与实际到达及未发送工作。

### 9.4 只优化20%串行耗时，能提升十倍吗？

**在该简化前提下不能。** 即使20%完全消失，整体加速上限1.25倍。实际排队变化可能带来额外效应，但必须测量证明，不能用局部倍数代替端到端结论。

### 9.5 三实例少一个，每实例负载只增加三分之一吗？

**均匀分担且流量不变时增加50%。** 原来每个承担总量1/3，剩余每个承担1/2，比原来多(1/2)/(1/3)-1=50%。还需检查共享依赖与扩容迟滞，不能只算实例数。

### 9.6 堆上涨就证明内存泄漏吗？

**不证明。** 需区分正常分配、GC后存活集合、合法业务增长和无界引用。RSS还含非堆/本地内存。用时间趋势、分配剖析和保留路径解释，不能单张图下结论。

### 9.7 加大连接池为何可能更慢？

**数据库容量有限，更多连接可能增加锁与I/O竞争。** 先查持有连接时长、事务和SQL，再按整体预算验证。连接等待是症状，不自动等于池太小。

### 9.8 第二次测试快很多，是否代码优化有效？

**不能直接认定。** 可能是JIT、连接、数据库页缓存或Redis变热，也可能环境负载不同。保持暖机与缓存条件一致、重复前后测试，并保留原始资源证据。

### 9.9 Failover只检查HTTP成功率够吗？

**不够。** 还要核对最终业务状态、重复/遗漏、结果未知、数据新鲜度、剩余容量和恢复时间。只返回受理成功可能把失败藏到后台。

### 9.10 EXPLAIN ANALYZE对更新语句只是查看计划吗？

**不是，会实际执行。** 可能修改数据和加锁，即使回滚也有资源与潜在外部副作用。应先用安全环境和受控方法，不能当普通只读诊断随意跑生产。

## 十、速记、验证边界与一手来源

- 基线固定业务语义、版本、环境、数据、缓存与负载；结果保留分位、错误与样本量。
- 闭环固定用户，开放固定到达思路；实际发送、完成与丢弃分别记录。
- Load验证目标，Stress找边界，Spike看突发，Soak查长期，Failover验故障后容量与正确性。
- CPU查计算，wall查经过时间，分配查创建，dump查保留，Trace查关键路径，计划查数据层。
- 指标定位层次，证据形成假设，单一变更重测，最后检查正确性与成本副作用。
