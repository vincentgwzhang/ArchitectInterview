# 02. 连接池、线程池、批处理与背压

> 本章目标：面对“下游变慢、队列增长、扩容反而更差”的系统，能从业务时限推导资源上限，解释 Java 的执行与失败语义，并给出可验证的恢复方案。Java API 以 Java SE 21 为基线；HikariCP 配置说明以文末核验的项目文档为准，Kafka 参数示例限定为 4.0。所有数值都是教学假设，不是性能基准或推荐默认值。

## 1. 有界资源：先决定系统愿意承担多少工作

### 1.1 吞吐、并发和排队是三个不同维度

吞吐量（Throughput）是单位时间完成的工作，例如每秒成功处理 500 笔订单；并发量（Concurrency）是同时占用资源的工作数量；排队（Queueing）是已经接收、尚未得到执行资源的工作。提高接收速度不会自动提高完成速度，只会增加在途请求。

在统计口径一致、长期平均稳定的系统中，Little 定律为：

~~~text
平均在途数量 L = 平均到达率 λ × 平均停留时间 W
~~~

例如数据库阶段每秒处理 400 次操作，每次平均持有连接 25ms，平均正在使用的连接约为 400 × 0.025 = 10。这说明业务平均需求的数量级，不说明 10 条连接足以满足尾延迟，也不能把 P99 时间代入后声称算出了可靠容量。突发、慢查询、锁等待、连接建立、读写比例变化，都需要压测与余量验证。

如果入口持续进入 1,200 个任务/秒，而系统只能完成 1,000 个/秒，未拒绝时每秒积压 200 个。再大的有限队列也只是在推迟拒绝；无限队列则可能让请求先超过业务时限，再耗尽内存。队列不能修复持续的容量缺口。

### 1.2 资源上限必须覆盖“执行中”和“等待中”

线程（Thread）占用栈、调度和上下文切换成本；数据库连接（DB Connection）占用会话及执行资源；HTTP 连接（HTTP Connection）涉及套接字、文件描述符和服务端资源；队列保存任务引用及其关联对象；批次和响应体占用堆内存及缓冲区。只限制线程数、却允许每个任务携带巨大请求体排队，仍会发生内存不足（Out of Memory，OOM）。

一个任务表面只有几十字节的包装对象，却可能引用用户请求、解压后的文档、链路上下文和回调。假设每个排队任务实际保留约 64KiB 对象，容量 10,000 的队列就约占 625MiB，尚未计算执行中的任务、线程栈和其他业务对象。因此应同时限制任务数、单任务字节数、累计字节数和最大等待时间；对大文件应使用有界流式处理或落盘，而不是全部读入内存后再限流。

“有界”还要求越界行为明确：立即拒绝、限时等待、丢弃允许丢失的数据，或写入有容量与保留策略的持久队列。没有定义拒绝后的业务响应，只是把资源保护变成了随机错误。

### 1.3 从业务目标反推排队预算

假设订单 API 的端到端时限为 800ms，鉴权和序列化预留 80ms，下游处理预留 400ms，网络及收尾预留 120ms，那么入口排队最多只剩 200ms。若稳定处理速度为 1,000 个任务/秒，200 个等待任务对应约 200ms 的理想排空时间。这个计算只适合均匀任务、稳定服务速率下的初始估算；慢任务和突发会使实际等待更长。

可落地策略是：先取保守队列容量，再检查最老任务年龄（Oldest Age）和请求剩余时间；即使队列未满，已无法在截止时间前完成的请求也应尽早拒绝。对异步报表则可以接受更长等待，但必须返回任务标识和真实状态，定义取消、保留、结果过期和失败重试，不能把“接收成功”表达成“业务已完成”。

## 2. Pool 对齐：按共享瓶颈分配预算

### 2.1 数据库连接预算要乘以最大实例数

连接池（Connection Pool）复用已建立连接，避免每次调用都支付认证与连接建立成本。借出连接后，业务独占使用一段时间；调用池代理连接的 close 通常是归还池，而不是销毁物理连接。池的最大值限制本实例持有的连接，却不限制整个集群的总连接。

原场景中，50 个 Pod、每个池最大 30 条，潜在连接为 1,500 条。如果数据库在该业务负载下仅能安全承受 500 条，应用自动扩容就会放大竞争。500 应来自资源与负载验证，不能直接等同数据库允许建立连接的配置上限。

假设 500 的预算中，其他服务、运维及故障余量占 100，留给本服务 400；若滚动发布期间最多同时存在 60 个 Pod，每个 Pod 池上限至多 floor(400 / 60) = 6，总计 360，余下 40 保留弹性。要计入主从切换后落到同一节点的连接、批任务、定时任务和多数据源池，不能只按日常 50 个 Pod 计算。

这只是连接数量约束。即使不超过 500，增加活跃查询仍可能造成 CPU 争用、锁等待、缓存失效和磁盘排队，让持有时间上升，反过来进一步占满池。架构师需要同时管理“可建立连接数”和“数据库可持续执行的并发工作数”。

### 2.2 池满先分清借用等待和持有时间

连接获取时间（Acquire Time）是申请到拿到连接的时间；持有时间（Usage/Hold Time）是拿到连接到归还的时间。SQL 执行时间只是持有时间的一部分。

典型反例是：开启事务、读取订单并锁行，然后调用外部支付接口两秒，最后提交。即使 SQL 各只用几毫秒，连接和锁仍可能被持有两秒。扩大池会让更多事务同时等待支付，并加剧锁竞争。应检查能否把远程调用移出事务，通过短事务记录状态，再使用幂等操作与补偿处理跨系统失败；不能为了缩短事务而破坏业务一致性。

排查顺序是：看连接持有分布、长事务与锁等待，再看慢 SQL、未关闭资源、网络故障，最后评估池是否确实不足。连接泄漏（Leak）是某些路径未归还；长事务是最终会归还但时间过长。泄漏检测日志通常只是“借出太久”的线索，不能据此直接判定泄漏。

使用 try-with-resources 关闭 Connection、PreparedStatement、ResultSet；事务异常要回滚，并确保连接状态由明确的事务管理与池契约复原。不要把同一 JDBC Connection 任意共享给多个异步任务，否则事务边界与关闭时机难以推理。嵌套独立事务可能在外层仍持有连接时再次借用连接：所有工作线程都持有外层连接、又等待内层连接，会形成资源饥饿，必须重新设计事务边界或显式预算额外连接。

### 2.3 HikariCP 参数的作用不能混淆

HikariCP 项目文档中的 maximumPoolSize 包含空闲与在用连接；connectionTimeout 限制等待从池中借到连接的时长，不是 SQL 执行时限。maxLifetime 管理物理连接生命周期，不会把正在执行的业务当作查询超时强行终止；validationTimeout 管理连接有效性检查。参数单位和允许最小值须按实际版本核对。

因此，“设置 connectionTimeout=1 秒就不会有超过 1 秒的数据库调用”是错误的。还需要数据库/驱动支持的语句超时、锁等待超时、网络超时及整体请求截止时间，并实测其取消和资源回收行为。过期连接的生命周期、网络中间设备的空闲回收策略也要协调；否则借到已被网络断开的连接仍会失败。

连接代理（Proxy）可以复用后端连接，但不会增加数据库执行能力。事务级复用还可能限制会话级状态、临时表或其他依赖固定连接的功能；采用前应验证具体代理模式及驱动兼容性。不要用一个代理层把连接预算问题隐藏起来。

### 2.4 HTTP 池、线程池与数据库池不必机械相等

若一个线程的任务全程只做一次同步数据库操作，100 个工作线程配 10 条连接，会有大量线程等待借用，通常应在数据库调用前做并发准入。若任务包含 CPU 运算和不访问数据库的路径，两者也没有必须相等的关系。应按各阶段资源占用及访问比例建模，避免多个层级重复长时间排队。

HTTP/1.1 与 HTTP/2 的连接和请求并发关系不同：HTTP/2 可在单连接上多路复用流（Stream），所以“最多 10 条连接”不等于“最多 10 个请求”。仍需限制每个目标的在途调用、等待获取连接/流的时间，并及时消费或关闭响应体。池和连接复用提升效率，业务并发限制保护下游，两者各有职责。

## 3. 线程池：真正决定行为的是线程、队列与拒绝策略

### 3.1 Java ThreadPoolExecutor 的提交顺序

以 Java SE 21 的 ThreadPoolExecutor 为例，忽略并发关闭与线程创建失败等额外分支，execute 的关键顺序是：

1. 当前工作线程少于 corePoolSize，尝试创建线程执行任务。
2. 已达到核心线程数，优先尝试进入工作队列。
3. 队列不能接收时，尝试扩展线程至 maximumPoolSize。
4. 再无法接收时，执行拒绝策略；关闭中的线程池也可能拒绝任务。

所以 core=8、max=32、队列容量=1,000，并不是第 9 个任务就扩容到第 9 个线程。在前 8 个任务持续阻塞时，接下来先排队；队列满后才尝试新增线程。没有显式容量的 LinkedBlockingQueue 在实践中近似无界，通常使 maximumPoolSize 无法发挥期望作用。SynchronousQueue 不保存等待任务，而是直接交接给接收线程，接不住就触发扩线程或拒绝。

下面是限定平台线程与任务队列的配置片段，适用于 Java 21。它只展示准入与结果获取，业务方法、指标及 HTTP 错误映射需要由应用实现；本次未编译运行。

~~~java
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    8, 16, 30, TimeUnit.SECONDS,
    new ArrayBlockingQueue<Runnable>(64),
    Executors.defaultThreadFactory(),
    new ThreadPoolExecutor.AbortPolicy()
);

try {
    Future<Result> future = pool.submit(() -> processOrder(command));
    // 不要在事件循环上阻塞等待；此处假定普通请求工作线程。
    Result result = future.get(remainingMillis, TimeUnit.MILLISECONDS);
    // 返回业务结果
} catch (RejectedExecutionException busy) {
    // 映射为明确的过载响应，并计数；请求尚未进入执行队列。
}
~~~

生产代码还必须处理 TimeoutException、InterruptedException 和 ExecutionException。Future.get 超时只代表调用方停止等待，不会自动取消任务；需要保存 future 并按业务策略调用 cancel(true)，而中断仍是协作请求，不保证远程操作或数据库写入已停止。可取消读取与不可随意重试的支付写入，必须使用不同恢复逻辑。

### 3.2 拒绝策略就是业务语义

AbortPolicy 抛出拒绝异常，便于明确响应过载；CallerRunsPolicy 在池仍运行时让提交者自己执行，从而减慢提交速度，但可能阻塞请求线程、事件循环或持有锁的线程。它不保证整个应用并发仅等于 maximumPoolSize，因为多个提交者可同时在池外执行；线程池关闭时该策略会丢弃任务，也必须纳入关闭语义。

DiscardPolicy 静默丢任务；DiscardOldestPolicy 丢弃最老排队任务后尝试提交新任务。对允许丢失的观测数据可能有用途，对订单、扣款和等待 Future 结果的请求则危险：如果提交过程没有明确完成被丢弃任务对应的结果对象，调用方可能一直等不到完成。不能把“没有抛异常”解释为任务已可靠执行。

若用自定义拒绝策略阻塞提交者等待队列空间，必须限制等待时间并考虑调用线程持有的其他资源，否则只是增加一个不可见等待区。明确拒绝通常比无限阻塞更容易保证恢复能力。

### 3.3 线程多少取决于瓶颈而非固定公式

CPU 密集任务增加线程超过实际可用 CPU 后，通常只增加调度和缓存成本，应从容器可用 CPU、任务并行度和压测结果确定。阻塞 I/O 任务可能需要更多线程覆盖等待，但线程数上限仍受下游并发、内存和请求预算约束。“CPU 核数乘某常数”只能作为试验起点。

虚拟线程（Virtual Thread）让大量阻塞任务的线程成本降低，但不会制造更多数据库连接、下游配额或堆内存；需要独立的信号量或入口准入限制在途任务。不能把平台线程池换成每任务虚拟线程后就取消所有资源上限。

CPU 计算、慢报表和交互式订单宜采用分舱隔离（Bulkhead）：各自有限线程/并发、队列和预算，让慢报表无法占满订单资源。隔离不是无限拆池；过多池会造成资源闲置、配置与监控成本，仍须共享总预算。

### 3.4 线程饥饿与关闭恢复

若固定池的所有线程都在执行父任务，父任务向同一池提交子任务并同步等待，子任务只能排队，父任务又不释放线程，会形成线程饥饿死锁。解决方式是避免同步嵌套等待、在父线程内顺序执行简单子操作，或采用有界且资源预算明确的异步组合；新增一个无界池只会转移风险。

应用下线时应先停止接收新工作，再 shutdown 等待已接受任务在有限时间内结束，超时后按策略取消或持久化未完成任务。shutdownNow 返回尚未开始的任务，并尝试中断运行中的任务，不等于业务已回滚。必须能说明客户端何时得到结果、队列里任务是否可恢复、重复执行如何避免。

## 4. 批处理：摊薄固定成本，同时扩大失败单位

### 4.1 批量为什么提高吞吐，也会增加延迟

批处理（Batching）把多条记录合成一次交互，摊薄网络往返（Round Trip）、协议和提交的固定成本。假设一次调用固定成本 4ms，每条记录处理 0.2ms，串行且不考虑其他瓶颈时，单条调用处理 100 条约用 420ms；一次处理 100 条约用 24ms。这是成本模型，不是实际 benchmark；驱动可能拆包、服务器可能逐条执行，锁和日志也会改变结果。

批次大小 B 增加时，单条固定成本近似 4/B ms 下降，但第一条需要等待凑批，批次占用内存增加，事务持锁更久，超时和重试的影响范围更大。吞吐收益最终会被 CPU、日志、包大小、下游限制或热点锁截断，不能无限增大 B。

JDBC Batch 代表批量提交接口，不保证驱动将所有 SQL 合成一个网络包或一条 SQL；Kafka Producer 的批次常按分区聚合，也不是把所有分区的消息揉成一个业务原子事务；API Bulk 的原子性完全由接口契约决定。三个场景都能摊薄成本，但失败语义不能互相套用。

### 4.2 按条数、字节或时间触发 Flush

可靠聚合器应在“达到最大条数、达到最大字节数、第一条等待到达时限”任一条件满足时刷新（Flush），低流量时也不会永久等待。计时从当前批次第一条入队开始，不是每来一条就无限重置。还要定义单条超大数据如何拒绝或走独立路径。

下面是单一所有者事件循环的逻辑示意，非可直接运行代码：

~~~text
收到记录：
  校验记录字节数和业务标识
  若当前批次再加入会超字节限制，先封存旧批次
  空批次加入第一条时记录 firstEnqueueTime
  加入记录；达到条数上限则封存
周期触发：
  若批次非空且 now - firstEnqueueTime >= maxWait，则封存
封存：
  转移当前列表所有权，换一个空批次
  在有界发送槽位中提交；槽位满时减速或明确拒绝
  每条记录保留独立结果，成功/失败后完成对应结果
~~~

定时器与生产线程若直接共享可变列表，可能重复发送或漏记录；单线程所有权或锁内交换批次可避免这一类竞态。封存后也不能无限创建异步发送任务，必须限制在途批次数、累计字节和重试副本。停机需要处理尾批、失败结果及持久化，否则“批未满”会变成数据丢失。

Kafka 4.0 中 batch.size 与 linger.ms 分别影响批次规模和等待聚合的机会；4.0 的 linger.ms 默认值相对旧版本发生过变化，不能凭旧记忆推断。等待时间并不构成端到端发送延迟上限：缓冲区压力、重试、网络与服务端排队还会增加延迟。调参应观察实际批大小、压缩率、发送延迟和 buffer 等待，而不是只提高 batch.size。

### 4.3 JDBC 批次不是默认事务

调用 addBatch/executeBatch 只描述批量执行，不等同“全部成功或全部回滚”。需要全有全无时，应在支持事务的存储与语句范围内，关闭自动提交，执行批次，全部成功后 commit，异常时 rollback。不要在框架已管理的事务内再随意手工切换 autoCommit。

Java SE 21 的 BatchUpdateException 允许驱动在某条失败后停止或继续，因此 updateCounts 的长度与内容需要按规范和驱动行为解释：非负数是更新计数，SUCCESS_NO_INFO 表示成功但没有准确行数，EXECUTE_FAILED 表示失败。更新计数说明执行情况，不证明事务已经提交，也不能把 SUCCESS_NO_INFO 当作影响零行。

对于事务内整体回滚的批次，即使部分语句曾执行成功，也不应只重试报告失败的那几条；需要按事务恢复完整业务单元。反之，如果接口明确允许每条独立提交，就必须逐条返回结果，只重试确认未成功且可重试的记录。数据格式错误不应无限重试，超时后提交结果未知也不应直接假设失败。

提交时网络断开尤其重要：数据库可能已提交而响应丢失。此时 rollback 尝试不能证明原提交未发生。应凭稳定业务键查询结果或执行幂等重试，而不是重新生成业务标识再次写入。

### 4.4 幂等、毒数据和可恢复进度

幂等性（Idempotency）指同一业务操作重复执行不会产生额外业务效果。批次编号不足以替代记录级业务键，因为重试时可能重新分批。可用唯一业务键约束“订单导入记录只创建一次”，在同一事务内写业务变更和处理标记；并发重复由唯一约束或条件更新解决，不能先查询不存在再无保护地插入。

若一条格式错误让整批失败，可先区分暂态错误与永久错误：网络抖动采用有上限的退避；格式、权限或业务约束问题应进入可追踪的失败清单。允许记录间独立处理时，可以二分拆批定位毒数据（Poison Record），但若批次包含必须共同成功的转账等业务，拆分就破坏原子性，不适用。

进度检查点必须在结果可恢复后推进。先提交消息 offset 再写数据库会丢处理；写数据库后未提交 offset 就崩溃会重放，需要幂等。处理标记、重试次数、错误分类和原始记录索引要持久化并保护敏感信息，失败不能只留一条无人处理的日志。

## 5. Backpressure：把下游压力转换成上游行为

### 5.1 区分限速、限并发、缓冲和丢弃

背压（Backpressure）是接收方能力不足时，向上游反馈，使其减少产生或发送速度。限速（Rate Limiting）约束每秒进入多少，限并发（Concurrency Limiting）约束同时执行多少；缓冲吸收短暂波动；负载丢弃（Load Shedding）在无法完成时拒绝或丢弃工作。

它们不能互相替代。每秒 100 次调用、平均耗时从 20ms 上升到 2 秒，平均并发会从约 2 上升至约 200，固定速率仍会压垮下游。并发限制能限制在途数量，但若其前面等待者无限增长，内存仍失控。应组合入口配额、有限等待和下游并发限制，并让超限结果可被调用方理解。

对不可降速的外部推送源，真正的端到端背压可能无法建立。此时必须在边界选择有限缓冲、持久化接收、拒绝或允许的数据丢弃；不能声明用了响应式框架就保证永不丢数据。

### 5.2 信号量如何限制真实的工作

信号量（Semaphore）维护许可数量，成功获得许可才进入受保护操作，操作真正结束后归还。下面是 Java 21 同步调用的示意片段，本次未编译运行：

~~~java
if (!downstreamSlots.tryAcquire()) {
    throw new RejectedExecutionException("downstream overloaded");
}
try {
    return blockingCallWithDeadline(command, deadline);
} finally {
    downstreamSlots.release();
}
~~~

tryAcquire 不等待，便于快速失败；如果允许短暂等待，可使用带超时的形式，但要计算剩余预算并处理中断。release 只对应成功获取的许可，否则可能把许可数越放越多。许可应覆盖真实调用生命周期，而不是只覆盖“提交异步请求”这一步；异步场景要在完成回调释放，并处理提交失败，保证恰好释放一次。

本地信号量只保护单进程。如果 50 个实例各允许 20 个调用，集群潜在并发仍为 1,000。需要按最大实例数分配本地额度，或在下游/网关做共享准入；集中式控制会增加一致性、可用性和网络成本，也应避免把许可服务变成单点瓶颈。

### 5.3 Reactive Demand 的边界

Reactive Streams 的订阅者（Subscriber）通过 Subscription.request(n) 表达还可接收多少元素，发布者（Publisher）不能发送超出累计未消费需求数量的 onNext。需求是元素数，不是字节数，也不自动约束业务异步调用个数。若每个元素触发大文件下载，仍需要字节和并发边界。

例如一次请求 32 个元素，处理一个再补一个需求，可以控制交付窗口；但算子预取（Prefetch）、并行映射和缓冲策略可能引入额外在途元素，必须逐层检查。声明 Long.MAX_VALUE 需求通常意味着不再用需求量限制交付。取消订阅也不意味着已发起的数据库更新一定回滚。

该协议定义的是兼容参与者之间的异步非阻塞交付，不替外部 HTTP、JDBC 或不合作数据源创造相同保证。将阻塞 JDBC 放进事件循环会阻塞其他请求；应在有界隔离执行资源中执行，或选择适当的非阻塞驱动并验证事务和取消语义。

### 5.4 HTTP 拒绝与重试必须形成闭环

对某租户或调用者超过配额，可用 429 Too Many Requests；服务暂时因过载不可用时，可用 503 Service Unavailable。两者选择取决于拒绝原因，而不是随意互换。Retry-After 可给出 HTTP 日期或等待秒数，表达建议的重试时间；客户端不会因为存在此响应头就必然遵守。

调用方应只对适合重试的错误执行有限次数重试，使用指数退避和随机抖动（Jitter），并受总截止时间与重试预算约束。下游已经过载时立即重试，会把一次业务请求放大成多次工作。若三层各最多尝试三次，最坏可产生 3³ = 27 次末端调用；应明确哪一层拥有重试责任。

写操作必须带稳定幂等键，并能处理结果未知；已明确永久失败的请求不应重试。可选功能可以降级，例如订单详情暂不获取推荐，但不能把支付失败伪装为成功。优先级与租户配额还应避免某个大客户占满所有资源，并保留必要健康探测和运维入口。

### 5.5 消息积压扩容不是背压的替代物

Lag 是消费进度与生产进度的差距，通常按记录数度量；积压年龄说明用户实际等了多久。若生产 10,000 条/秒、消费 8,000 条/秒，积压以 2,000 条/秒增长。停止新生产也需要时间排空，更不能只看当前消费者 CPU 低就判断容量充足。

扩容消费者应确认分区并行度、热点 key、单条处理时间和下游余量。如果所有消费者都写同一已饱和数据库，扩容只会增加连接、锁等待与重试。必要时暂停拉取或降低处理并发，但仍要遵守客户端组成员活性与轮询要求；不能停止所有协议维护后期待消费组永远稳定。

持久消息系统把内存队列变成磁盘上的缓冲，仍受存储、保留时间和业务过期约束。定义最大积压年龄、积压增长告警、毒消息处理与恢复速率，才有可解释的异步服务承诺。

## 6. Timeout Budget：把等待和重试都放进同一截止时间

超时（Timeout）是某一阶段最多等待多久；截止时间（Deadline）是整个请求最迟何时结束。每层都各等 30 秒，会让总耗时远超用户预期，还会在用户已放弃后继续占用资源。

假设入口总预算 800ms，可初始分配排队 100ms、连接获取 100ms、下游执行 400ms、返回处理 100ms，剩余 100ms 为余量。这些是设计目标，具体客户端未必支持每个精确值；例如连接池可能有最小等待超时，必须检查实际配置范围并调整整体方案。

进入下一阶段时应重新计算 remaining = deadline - now，再取 min(该阶段上限, remaining - 必要收尾余量)。remaining 已不足就不再开始昂贵操作；重试与退避也消耗同一个 remaining。并行步骤按关键路径预算，顺序步骤按实际顺序预算，不应把并行耗时机械相加。

同进程测量间隔可用单调时钟，避免系统时间校正；跨服务传播剩余时限或采用有明确时钟误差约束的 deadline 协议，避免直接把一个进程的单调时钟数值发给另一个进程解释。任何客户端提供的超大超时都要受服务自身最大值约束。

取消是单独的语义：本地超时、线程中断、网络断开、数据库终止和事务回滚并不等价。系统要记录结果未知并提供幂等查询/恢复，而不是在 Future 超时后释放许可、同时让后台真实工作继续无限累积。若底层无法取消，许可应保护实际仍在进行的工作，并为失联操作设独立回收与隔离策略。

## 7. 一套端到端设计与故障恢复推演

### 7.1 从订单入口到数据库的设计

虚构场景：订单 API 需在 800ms 内响应，集群日常 50 个 Pod，发布峰值 60 个，共享数据库给本服务 400 条连接预算。每 Pod 最大 6 条连接只是数量约束的起点；通过压测确定每个实例安全在途数据库操作数，并保持集群汇总不越界。

入口先做认证、请求体上限和租户配额，再做有界准入；不要先解压 100MiB 请求体再发现无容量。交互式下单使用短事务和清晰的拒绝响应，后台导入则进入持久任务系统，使用独立并发份额与小批事务，避免导入占满下单容量。各阶段携带剩余时限，连接获取失败不进入无限重试。

扩容策略须同时约束 Pod 最大数和每 Pod 资源额度，发布峰值包含 surge 实例。扩容提高应用算力，但数据库并发总预算保持受控；若应用更多实例只是争抢相同数据库预算，应优先优化数据库阶段或业务访问模式，而不是继续扩容付费却没有吞吐收益。

### 7.2 数据库突然变慢十倍时会怎样

假设原连接持有 25ms，故障后变成 250ms；同样吞吐需求下所需平均在用连接增加十倍。先是池在用达到上限，随后连接借用等待变长，线程与入口队列增长。如果每层超时很长且不断重试，就会产生大量已经无法按时完成的工作，恢复后仍被旧请求拖住。

正确响应是保护瓶颈：降低数据库准入，拒绝过期新请求，暂停非关键批任务，限制重试并排查慢查询或锁阻塞。不能简单把连接池与线程池同时扩大十倍，这会把过载压入数据库。

下游恢复后仍需控制排空速度，先验证连接持有时间和完成吞吐恢复，再渐进放量。假设积压 120,000 条，新流量 800 条/秒，安全消费能力 1,000 条/秒，净排空能力只有 200 条/秒，理想排空需 600 秒。若恢复时把所有积压同时释放，会再次压垮系统。过期任务按业务规则终止或补偿，不能盲目全部执行。

## 8. 监控、排障与优化：观察资源为何被占住

### 8.1 指标需要成对解读

| 观察项 | 应一起看的指标 | 可解释的问题 |
| --- | --- | --- |
| 线程池 Active/Max | 完成吞吐、CPU、阻塞栈、Reject | 满池是 CPU 饱和还是在等下游 |
| Queue Depth | 最老年龄、入队/出队速率、超时前剩余时间 | 队列短也可能有一个极老任务；增长率反映容量缺口 |
| DB Active/Max | Acquire 分布、持有分布、锁等待、事务年龄 | 池小、慢 SQL、泄漏和长事务必须区分 |
| HTTP 在途请求 | 连接/流获取等待、目标延迟、响应体大小 | 连接够但流或下游并发不足 |
| Batch Size/Bytes | 第一条等待、Flush 原因、失败记录数、重试率 | 小批浪费固定成本，超大批扩大失败 |
| Consumer Lag | 积压年龄、分区倾斜、下游容量、净排空速度 | 扩容有无效果及恢复要多久 |

上述延迟看分布和尾部，不只看平均数；成功、失败、超时、拒绝分开计数。只看完成请求延迟会漏掉被拒绝或卡住的请求，可能误以为“延迟降低就是优化成功”。按依赖、池、业务类型与租户类别分组，但避免将用户 ID 等高基数和敏感值直接作为指标标签。

### 8.2 按证据选择动作

若 Acquire 高、持有时间正常、数据库仍有余量，可小步增加池容量或减少无效借用，并重新验证尾延迟；若持有时间与锁等待同时上升，应先定位长事务和热点锁。若线程 Active 高而 CPU 低，采集阻塞栈与下游耗时，不能直接判定线程不足。

若批次经常因时间触发且大小很小，增加最大条数没有帮助；可在业务时限内略增等待，或接受低流量时吞吐效率较低。若队列长度稳定但最老年龄不断上升，可能有任务饥饿、优先级不公平或单分区堵塞，应看最老任务及分区，而不是全局均值。

每次调整一个主要变量，使用同样流量模型、记录成功吞吐、P99、拒绝、资源占用和恢复时间。故障注入至少涵盖下游变慢、连接失效、批内单条失败、提交结果未知、停机尾批和重试风暴；“正常情况下吞吐更高”不足以证明可靠性。

## 9. 面试完整回答与深入追问

### 9.1 “线程池和连接池越大越好吗？”

完整回答：不是。池复用资源并限制竞争，容量应由业务时限、资源占用时间和共享下游能力共同决定。我会先估算平均并发，再在实际流量和故障场景验证尾延迟；数据库池预算必须乘最大实例数，并计入发布、故障和其他服务。线程池过大可能只是让更多线程等连接；连接池过大可能使数据库锁竞争更严重。队列只吸收短暂波动，必须有容量、年龄和拒绝策略。

追问：“连接获取已经超时，还不扩池？”答：先分开获取等待与持有时间。若慢 SQL、远程调用包在事务里或泄漏导致长期占用，扩池会掩盖甚至放大根因；只有数据库有余量且持有时间正常时，才把扩池作为受控试验。

### 9.2 “批量导入失败后怎么重试？”

完整回答：先说明原子性契约。整批要求原子时，用明确事务，失败回滚后按业务单元恢复；允许部分成功时，保存每条稳定标识和结果，只重试确认可重试的未成功项。JDBC 更新计数不是提交凭证，提交响应丢失会出现结果未知，需要凭业务键查询或幂等重试。格式错误进入可追踪失败清单，不能无限重试；与业务变更一致的检查点保证崩溃重放不会丢数据。

追问：“拆成两半找坏数据可以吗？”答：只适用于可独立处理的记录。转账双方、必须共同成立的业务约束不允许随意拆批。即使可拆，也要保留原始索引和幂等键，避免重新分批造成重复。

### 9.3 “用了响应式编程为什么仍然 OOM？”

完整回答：异步和非阻塞只改变等待方式，不等于资源无限。需求可能被设置为无限，算子预取或并行异步调用可能堆积，单元素也可能很大，外部源还可能不遵守需求。需要逐层核对元素数、字节数、真实在途调用与缓冲边界，慢端通过需求反馈或在协议边界明确拒绝。若把阻塞操作放在事件循环，还会阻塞整条共享处理链。

追问：“信号量不就够了吗？”答：它保护被许可覆盖的阶段；若许可前无限排队、异步提交后过早释放，或每个实例各自放大额度，都不能保护端到端资源。要把准入放到昂贵分配之前，并协调集群总量。

### 9.4 “队列积压时，为什么不马上扩容？”

完整回答：先判断瓶颈是否能通过更多消费者解决。CPU 饱和且分区可并行、下游有余量时扩容有效；热点分区、共享数据库饱和或外部限额导致的积压，扩容会增加竞争与成本。我会看积压增长率和最老年龄，给出净排空速度，暂停非关键工作，控制重试，在下游恢复后渐进放量。

追问：“业务要求一条也不能丢怎么办？”答：明确可靠接收边界，先持久化才确认接收，使用幂等和可恢复检查点；容量达到上限时拒绝尚未可靠接收的新工作，并让调用方按契约重试。有限资源系统不能对无限流量、无限故障时长同时承诺无拒绝、无丢失和有限延迟。

## 10. 扫雷自测：每题附答案与推理

### 10.1 core=4、max=12、队列容量=100，12 个长期阻塞任务会启用12个线程吗？

不会。在没有并发关闭、线程创建失败等额外因素时，先创建4个核心线程，其余8个排队；队列满后新提交才尝试扩至最大值。若希望少排队而允许扩线程，应调整队列与核心大小，并明确更早拒绝的取舍。不能只改 max 后认为生效。

### 10.2 50 个实例各30条连接，数据库安全容量500，改成60个实例会更稳吗？

不一定，连接潜在需求从1,500增至1,800，更偏离500。若本服务预算400且发布峰值60个实例，每池最多6才满足这一数量约束。还要验证活跃查询能力，连接数未超限不代表吞吐一定安全。

### 10.3 固定100请求/秒，响应从10ms变成1秒，限速为什么没挡住过载？

平均并发从约1增至约100，限速不直接限制在途数量。应加入有限并发和有限等待，拒绝超期请求，并定位下游变慢原因。Little定律描述稳定统计关系，不证明故障瞬间准确并发就是100。

### 10.4 executeBatch返回成功，是否说明所有数据已经持久提交？

不一定。若事务尚未commit，结果可被回滚；驱动与数据库也可能具有不同批次执行方式。必须先定义事务边界，确认commit及恢复语义。部分失败的updateCounts用于解释执行结果，不能替代提交证明。

### 10.5 Future.get等待超时后，能立刻重试扣款吗？

不能。原任务可能仍在运行且已扣款。先通过稳定幂等键查询状态或执行幂等恢复，取消尝试也不能证明远程回滚。重试必须受总时限和次数预算约束，并防止新旧操作并发产生重复效果。

### 10.6 有120,000条积压，新流量800/秒，安全处理1,000/秒，多久排空？

理想情况下120,000/(1,000-800)=600秒。用120,000/1,000得到120秒漏算了新流量；实际还要考虑重试、流量变化和分区倾斜。若新流量达到或超过安全处理能力，就无法在持续接收的同时排空。

### 10.7 每批最多100条是否足以保证内存有界？

不足。单条大小、在途批次数、重试副本以及待聚合队列都可能无界。需要同时限制条数与字节数，并限制发送槽位；第一条等待超时触发Flush，停机处理尾批。否则低流量尾批可能永远不发，高流量又可能堆积无数批。

### 10.8 “CallerRunsPolicy不会丢任务，还能保证并发上限”对吗？

不对。池关闭时它会丢弃任务；运行时多个提交者可在池外同时执行，使业务并发超过工作线程上限。它能在特定同步提交链路中减速，却可能阻塞事件循环或放大持锁时间，必须按调用上下文选择。

## 11. 速记：把原理压缩成决策链

先问业务多晚算失败，再计算入口和每个阶段的时间与资源预算；区分执行中、排队中以及结果未知。连接池乘最大实例数，发布与故障也算；线程池先核心、再队列、再最大、最后拒绝；池满先查资源为什么归还慢。

批处理摊薄固定成本，却增加凑批等待、内存、锁时间和失败范围；条数、字节、时间三条件刷新，事务与幂等决定重试方式。背压要让上游真实减速，协议不能传递时在边界有限缓冲并明确拒绝。扩容前确认瓶颈可扩，恢复时按净排空能力渐进放量。
