# 04. 幂等、去重、补偿与最终一致性

> 目标：面对重复请求、重复消息、乱序、部分提交和网络超时，能给出业务不变量、事务边界、恢复状态机与验证方法。SQL以PostgreSQL 17为例；消息语义分别注明Kafka 4.1与SQS Standard范围。场景和数字均为教学假设，不是用户经历或实测基准。

## 一、先回答“同一个操作”是什么

### 1.1 幂等不等于没有重复执行

幂等性（Idempotency）是同一业务操作重复执行，业务效果与执行一次等价。网络层仍可能发送十次、处理器仍可能被调用十次，但扣款、发货或余额增量不能重复生效。相同请求内容不一定代表同一操作：用户连续买两杯同样咖啡，应是两笔订单；同一笔订单因响应丢失重发，则应复用原操作号。

HTTP方法的幂等语义不能代替应用实现。PUT设置某资源为指定值可以自然接近幂等，而“余额加100”每执行一次就增加一次；DELETE重复调用的响应码可以不同，但删除效果仍可幂等。POST也能通过操作号提供业务幂等。因此面试回答应从操作身份和不变量出发，不能只说“换成PUT”。

先定义不变量（Invariant），例如“同一租户的同一支付操作最多产生一笔有效扣款”“累计退款不得超过已扣金额”。状态查询、唯一约束、状态转换和对账都围绕它设计。单纯保证消息ID不重复，不能证明资金不重复，因为同一业务操作可能被重新包装成不同消息。

### 1.2 三类身份要分开

请求标识（Request ID）用于追踪每一次调用，可以每次不同；业务操作号（Operation ID）标识同一次扣款或预留，重试必须稳定；消息事件号（Event ID）标识某一次已发生事实的发布与重投，重投通常保持不变。它们有关联，但用途不同。

例如支付操作pay-7经过三次HTTP尝试，各有不同traceId；成功后产生事件evt-9，发布器重投evt-9三次。HTTP入口按pay-7保护扣款，消费者按evt-9保护本订阅处理，同时资金表仍保留pay-7唯一性，防止有人用另一个事件号重述同一扣款。每层保护其拥有的业务边界，而不是期待一个全局ID解决所有问题。

## 二、请求幂等：Key、Fingerprint、状态与结果

### 2.1 Key的作用域与请求指纹

幂等键（Idempotency Key）应在发起业务操作前生成并持久保存，调用超时后继续使用同一个键。服务端作用域至少包含可信租户和操作类型，避免两个租户使用相同键互相冲突；不能直接相信请求体自报的tenant，应由认证上下文确定。

请求指纹（Request Fingerprint）用于发现“相同键却换了操作内容”。例如同键第一次支付10欧元、第二次100欧元，必须拒绝冲突，不能返回第一次成功而让调用方误以为100欧元已支付。指纹要覆盖金额、币种、收款对象、业务资源与语义版本等影响效果的字段；排除traceId、重试时间等非业务字段。

直接哈希原始JSON会因字段顺序、数值表示不同产生误判。应先校验并按明确规则规范化业务命令，再使用稳定编码计算指纹；金额可转为定义清楚的最小货币单位或精确十进制，不能用浮点近似。规范化规则演进也要有版本，否则同一旧请求可能在新版部署后产生不同指纹。哈希不是授权校验，日志与结果中仍要避免泄露敏感字段。

### 2.2 本地事务内的原子方案

以下DDL针对PostgreSQL 17，用于展示“同一数据库内创建本地业务结果”的边界，不是跨支付供应商的原子事务：

~~~sql
CREATE TABLE operation_result (
    tenant_id text NOT NULL,
    operation_type text NOT NULL,
    operation_key text NOT NULL,
    fingerprint text NOT NULL,
    status text NOT NULL CHECK (status IN ('SUCCEEDED', 'REJECTED')),
    result_json jsonb NOT NULL,
    completed_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (tenant_id, operation_type, operation_key)
);

CREATE TABLE local_order (
    tenant_id text NOT NULL,
    order_id text NOT NULL,
    operation_key text NOT NULL,
    amount_minor bigint NOT NULL CHECK (amount_minor > 0),
    currency text NOT NULL,
    PRIMARY KEY (tenant_id, order_id),
    UNIQUE (tenant_id, operation_key)
);
~~~

处理算法是：开启事务，尝试插入operation_result的最终结果占位记录，使用ON CONFLICT DO NOTHING RETURNING判断是否取得该键；取得后创建订单并将真实结果写回；然后一起提交。占位只在当前未提交事务内部存在，外部不能把它当作完成结果。业务验证拒绝可以按契约存为REJECTED，暂态基础设施故障则回滚整笔事务。

若未取得键，必须读取已提交记录、核对指纹，匹配则返回所存业务结果，不匹配则返回明确的冲突错误。PostgreSQL唯一约束会协调并发插入，等待可能受到锁等待或语句时限限制；ON CONFLICT不代表不会等待。Read Committed下冲突插入可能受另一事务影响，而当前语句快照看不到那一行，因此冲突后使用后续语句读取；若并发清理删除导致仍不存在，按受控恢复策略重新判断，不能直接当成功。

这套方案正确性的关键是取得唯一键、业务写入和最终结果在同一事务。若业务插入失败，占位也回滚，下一次可重新尝试。若提交成功但HTTP响应丢失，重试可返回已存结果。把幂等记录单独提前提交、再写订单，会产生“已占键但业务没完成”的窗口；此时必须升级为可恢复的异步状态机，不能套用这个简单方案。

结果重放不意味着原HTTP响应字节完全相同。应存稳定资源ID、业务状态和必要业务响应，明确是否重放原状态码、如何处理版本变化和授权撤销。每次读取仍需鉴权，不能凭知道Key取走其他人的结果。

### 2.3 并发重复与Processing状态

若操作涉及外部系统或执行很久，不能把本地事务和数据库锁跨网络长期持有。可在短事务中创建PENDING记录，返回操作ID，由工作者完成。重复请求读到处理中时，可返回202及查询位置，或返回契约定义的“处理中”错误；不要让无数重复请求无限阻塞等待同一锁。

记录至少包含操作身份、指纹、状态、当前版本、下次恢复时间、重试次数和最近错误类别。工作者租约（Lease）表示暂时处理权，租约过期允许接管，但旧工作者可能仍在执行。条件更新版本或栅栏令牌（Fencing Token）防止旧持有者覆盖新状态；外部副作用仍须由对端幂等键防重，单靠本地租约不能阻止旧请求在供应商那里生效。

PROCESSING也不是“失败后永久卡住”的合法终态。应有过期扫描、状态查询、重试及人工处理路径，并明确多个恢复者如何竞争。请求线程退出或进程重启不能让业务操作从系统里消失。

### 2.4 保留窗口与成本

保留期（Retention）决定去重承诺覆盖多久。若幂等记录只保留24小时，而客户端或灾难恢复会重放7天前的操作，过期后可能再次产生效果。保留窗口应综合客户端重试、消息保留、离线设备、备份恢复和人工重放时间，而不是随意设一个缓存TTL。

假设每天一千万操作、每条去重索引和结果平均占500字节，未计副本和维护开销就约5GB/天，30天约150GB。可分离短期完整响应与长期业务唯一键，归档冷数据，或让自然业务约束长期保证不重复。敏感结果需最小化、加密与受控访问；清理不能破坏尚未终结的处理中操作。

缓存可加速已完成结果读取，但不应作为唯一正确性依据：缓存丢失、淘汰、主从切换都可能让Key消失。最终防线应在拥有业务效果的持久存储或权威服务中。

## 三、消息去重：把处理标记与效果放在同一提交边界

### 3.1 至少一次交付为什么会重复

至少一次（At-least-once）强调在所配置的可靠交付和恢复条件下可能重复，不是无条件永不丢失。Kafka常见流程是消费、写数据库、再提交offset；写库成功但offset未提交就崩溃，会重放。SQS Standard也可能返回先前已接收甚至已删除消息的副本。错误确认顺序、超出保留期或配置不当仍会丢处理。

Kafka的事务与Exactly-once能力有明确范围，不能自动把外部数据库或支付HTTP副作用包进Kafka事务。对Kafka内部“读、处理、写回Kafka并提交消费进度”可采用相应事务机制；外部系统必须参与协调或自身提供幂等/事务接收。把“启用幂等Producer”等同“任何业务端到端只执行一次”是错误的。

### 3.2 Processed Event Table + Local Transaction

处理事件表（Processed Event Table，也常称Inbox）按“消费者逻辑身份+租户+事件ID”唯一。消费者身份很重要：库存和通知都应处理同一事件，不能共享一个全局“已处理”标记互相跳过。

~~~sql
CREATE TABLE processed_event (
    consumer_name text NOT NULL,
    tenant_id text NOT NULL,
    event_id text NOT NULL,
    payload_hash text NOT NULL,
    processed_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (consumer_name, tenant_id, event_id)
);
~~~

在本地事务内先尝试插入处理标记；取得处理权才更新业务表，二者一起提交；重复事件读取原hash确认同ID内容没有被篡改，匹配才跳过。业务更新失败则整笔回滚，不能留下已处理标记。提交后再确认消息。这样在“业务已提交、确认丢失”窗口重投会被跳过，而“事务回滚、尚未确认”窗口重投仍可重新执行。

如果在一个事务中消费事件并产生通知或下游命令，把它们写入Outbox，而不是事务内直接发网络消息。提交offset/删除消息之前，必须确认本地事务成功。Kafka分区并行处理时只能推进连续已完成位置，不能因为offset 102处理完成就提交越过仍未完成的101，否则101失败重启后可能被跳过。

数据库标记不能保护事务外已经发出的邮件或扣款。要么下游按相同操作号去重，要么把外部动作转换为独立可恢复任务，最终仍需明确外部副作用边界。

### 3.3 自然业务键、Entity Version与Upsert

自然业务键（Natural Business Key）例如“某订单的某个发货单号”，可在不同事件ID描述同一业务动作时仍阻止重复。对于余额增加等增量操作，必须有唯一流水号；仅比较最终余额不是可靠去重。

实体版本（Entity Version）适合防乱序，但要区分全量快照与增量事件。全量快照v=12可以在明确语义下覆盖v=10，随后到来的v=11应忽略；增量事件v=12若依赖v=11的增量，不能直接跳过去，需要等待缺口、回放或从权威状态重建。比较版本、更新内容必须原子执行，不能先查版本再无保护写入。

幂等Upsert指同一标识重复写入相同状态，不会重复增加效果。ON CONFLICT DO UPDATE SET amount = amount + incoming.amount仍然每次累加，不因使用Upsert就变成幂等。全量覆盖也要加版本条件，否则迟到旧事件会把新状态覆盖回去。版本应由权威实体生成，不应拿不同节点不可靠的墙上时间代替因果顺序。

## 四、Outbox：解决本地写库与发消息的双写窗口

双写（Dual Write）是一次业务操作既写数据库又发消息。先写库后发消息，进程可能在两者之间崩溃而漏发；先发消息再写库，消费者可能看到最终未提交的业务。常规本地事务无法同时原子提交两个不参与同一事务的系统。

事务发件箱（Transactional Outbox）在业务数据库同一事务中写业务表和待发布事件，提交后独立发布器轮询或通过变更数据捕获（Change Data Capture，CDC）读取已提交记录。业务回滚则事件也不存在，成功提交则有持久待发事实。

发布器发送成功后才标记已发；若发送成功、标记前崩溃，会重复发送，因此Outbox解决漏发窗口但不消除重复。事件ID必须稳定，消费者仍要幂等。多个发布器可通过有界批量认领、租约或数据库锁分工，按实体保持顺序需要额外设计，不能凭自增ID假设所有系统全局有序。

Outbox事件包含eventId、aggregateId、aggregateVersion、tenant、schemaVersion和必要业务数据。重试保留事件身份；重建全量投影要区分快照与增量。发布失败应有退避、最老未发布年龄告警和人工可追踪入口；不能把消息标记为失败后永久遗忘。

CDC降低轮询开销但增加日志保留、连接器位点和运维复杂度；轮询简单却可能增加数据库负载。两者都要考虑事件表清理、消费滞后、备份恢复及敏感数据复制。优先选团队能可靠运行的方案，而不是为了“事件驱动”叠加无人维护的组件。

## 五、Saga补偿：新的业务动作，而非历史回滚

### 5.1 为什么Refund不是Rollback

Saga将跨服务流程拆成若干本地事务，已完成步骤失败时执行补偿（Compensation）。例如先预留库存，再扣款，再创建发货；发货不可用时，可能退款并释放库存。数据库Rollback是在未提交事务内撤销修改；退款是新的资金流水，原扣款仍应保留审计历史，手续费、汇率、结算与退款时延都可能使它不能恢复到“从未发生过”的物理状态。

补偿也有业务前提：商品已出库不能简单释放库存，可能转为退货流程；付款尚UNKNOWN时不能确认退款已经完成。补偿不是对所有动作求一个技术逆运算，需要业务定义可撤销、不可撤销和可继续向前恢复的步骤。

优先把难以撤销的动作放在前置条件确认之后。库存使用预留、确认、释放，可降低售出后再“补偿”的复杂度；但预留占用容量并需过期与续租治理。若业务必须跨资源强原子且不能接受中间状态，应先考虑同一事务边界或合适的分布式事务能力，而不是机械套Saga。

### 5.2 编排与事件协作的选择

编排（Orchestration）由持久协调者记录当前步骤并发命令，适合流程较长、超时和人工介入复杂的场景，便于看全局状态；代价是协调服务及流程版本的维护。协调者不可只在内存保存“执行到第三步”，重启后必须能恢复。

事件协作（Choreography）让各服务响应事件并继续流程，局部自治强、简单流程易起步，但步骤多时依赖隐式、循环事件和排障困难。没有中央协调者不等于没有状态和治理，仍须有关联ID、可查询流程进度与失败处理责任。

二者都没有自动获得全局隔离性。一个Saga的中间结果可能被其他流程看到；需通过“预留中/待确认”状态、条件更新与业务规则限制其他操作。Saga不是ACID事务的同义词。

### 5.3 补偿任务如何做到可恢复

补偿命令使用稳定身份，例如“saga-7/step-2/refund”，重试保持不变，服务端按该操作号保护退款。记录原操作、目标金额、补偿状态、版本、已尝试次数、下次执行时间、错误类别和审计信息。暂态故障有限退避重试，永久业务冲突进入人工处置，人工操作也要使用相同业务身份和权限控制。

顺序通常与依赖相反，但不必机械全逆序：先释放一个资源会不会让另一个补偿失去必要信息，要按业务依赖判断；相互独立的步骤才可并行。一个补偿失败也不应把已经成功补偿的步骤重复产生副作用。

原命令可能迟到成功，必须防止“先取消、后成功”把流程重新推进。库存服务可保存取消墓碑或状态版本，使迟到预留被拒绝；支付无法取消时则查询是否扣款，确已扣款后启动稳定退款操作。补偿完成的终态必须与原操作实际结果一致，不能仅靠协调者本地超时猜测。

## 六、最终一致性：定义怎样收敛、多久收敛、失败怎么办

### 6.1 先明确Source of Truth与读语义

最终一致性（Eventual Consistency）的核心是在不再有新更新、传播机制持续有效等前提下，各副本最终收敛。它不自动给出时间上限，也不保证错误代码、丢失事件或冲突能自行修复。权威来源（Source of Truth）明确哪个系统负责判定业务事实，例如支付账本负责资金事实，搜索索引只是可重建投影。

可接受陈旧度（Staleness）必须按场景设定。搜索结果落后30秒可能可接受，结算价格和权限撤销可能不可接受。读己之写（Read Your Writes）可通过提交后读取权威存储、携带版本等待投影追上，或暂时在界面合并刚提交结果实现；等待也须有时限，不能无限卡住查询。

用户可见中间状态应具体，例如“订单已接收，付款确认中”“支付已确认，库存确认中”“退款处理中”。HTTP 202只表示接受处理，不表示业务成功。UI、客服和运维对同一状态要有一致解释，避免用户因看不到进度反复创建新操作。

### 6.2 收敛机制与冲突策略

正常路径可由Outbox、可靠事件消费和版本检查传播；缺口通过重放、权威查询、快照重建修复。对同一事实指定单一写入者最容易推理；若允许多主写入，必须明确冲突规则，例如版本冲突人工合并或领域特定的可交换操作。

Last Write Wins按时间选最后值，简单但可能丢更新，时钟偏差还会使旧值覆盖新值；不能用于要求保留每笔资金流水的账本。对于可交换计数等特定数据，可考虑相应合并模型，但不能把任意业务都假设成可交换。选择冲突策略要以信息丢失风险和业务不变量为依据。

反熵修复（Anti-entropy）是周期比较副本或投影与权威状态，发现差异后修复。它不是随便把目标表清空重建：必须考虑并发新事件、水位、删除记录与权限，重建后不能被旧事件回填污染。

### 6.3 给“最终”一个可测的SLO

例如“99.9%已提交订单事件在30秒内反映到查询投影”，应定义起点为权威提交时间，终点为相应版本在读路径可见，而不是仅消费者收到消息。跨机计时考虑时钟误差；用业务关联ID连接提交、发布、消费、投影可见各阶段。

假设窗口内10万事件，其中120条超过30秒，则及时比例99.88%，未达到99.9%。失败、毒消息与永久卡住事件不能从分母删掉来美化结果。百分位SLO也不覆盖剩余长尾，因此还需最老未完成年龄、绝对超时升级和对账告警。

处理积压要看净排空能力：积压60,000条，新流量900条/秒，安全处理1,000条/秒，理想排空至少600秒。若为了追进度无限扩消费者，而共享数据库已饱和，可能让收敛更慢。按关键业务优先级分配恢复容量，限制重试与重放速率。

## 七、Unknown Outcome与Reconciliation

### 7.1 状态机必须承认不知道

未知结果（Unknown Outcome）表示缺乏足够证据确定成功或失败，不是新的业务事实。支付请求超时后可以标记UNKNOWN或PENDING，保存原供应商操作号，等待查询、回调或对账；不能将网络错误直接转换为“未扣款”。

查询“暂未找到”也未必证明未发生：供应商查询可能最终一致、请求可能仍在处理。需要明确其查询一致性、最终失败条件与幂等保留契约。只有获得足够证据，才能决定重发同一操作、继续等待、退款或人工处理。

回调可能重复、乱序甚至伪造，需要签名验证、租户/供应商身份匹配和事件去重。以状态转换条件和版本控制防止迟到PENDING覆盖SUCCEEDED；但真实退款是后续新事实，不应被“成功状态不再修改”的简单规则丢掉，应建立独立退款对象和关联账本。

### 7.2 对账如何发现并修复差异

对账（Reconciliation）比较本地业务记录与外部权威流水或读模型。按稳定操作号、币种、金额和状态匹配，区分本地缺失、外部缺失、金额冲突、重复流水和长期未知。对账任务保留扫描范围与检查点，允许重复扫描并使用幂等修复。

扫描窗口应有重叠，覆盖晚到数据；不能仅按“上次运行时间之后”查询而漏掉延迟入账记录。分页要有稳定排序或供应商游标，进度只有在结果已持久记录后推进。遇到金额不符不能自动覆盖本地账本，而应冻结相关自动动作、保存证据并人工处理。

修复也通过正常领域命令和审计流程，例如“确认支付”“发起退款”，不能直接在生产库把status改成成功。这样能重新执行不变量检查、生成必要事件，并避免投影与权威数据再次脱节。需要限制重放范围、权限、速率和干跑预览，防止一次“修复”批量制造重复扣款。

## 八、完整订单案例与崩溃窗口

虚构流程：创建订单、预留库存、扣款、确认订单。订单服务短事务写PENDING订单和Outbox；库存以订单预留号幂等预留；支付以支付操作号幂等扣款；协调者持久记录每步结果后决定确认或补偿。

| 故障窗口 | 可能事实 | 恢复方式 |
| --- | --- | --- |
| 本地事务提交前崩溃 | 订单与Outbox都未提交 | 同键重试，重新执行 |
| 提交后响应丢失 | 本地订单已存在 | 核对指纹，返回原订单 |
| 消息发送后未标记已发 | 消息可能已到达 | 保留eventId重发，消费者去重 |
| 消费者写库后未确认消息 | 本地效果已提交 | 重投后同事务处理标记阻止重复效果 |
| 扣款后响应丢失 | 外部可能已扣款 | 保留UNKNOWN，查询/回调/对账 |
| 退款成功但响应丢失 | 外部已退款可能性存在 | 同退款操作号查询或幂等重试 |
| 取消后原命令迟到 | 旧工作可能继续 | 墓碑/版本/权威查询防止错误推进 |

所有“最多一次效果”承诺都有范围：本地唯一约束保护本地效果，供应商幂等保护外部效果，备份恢复和保留期必须一起设计。消费者重放、协调者恢复与人工修复也走同一身份规则，不能在每次恢复时重新生成操作号。

正确性优先于表面成功率。若库存已释放但扣款后来确认成功，应根据业务策略重新尝试履约或退款，不能让订单标记取消就忘记资金。若退款长期失败，流程保留COMPENSATION_PENDING并升级处理，不应标记整个Saga已完成。

## 九、验证、排障与演进

### 9.1 如何验证不只是正常路径能跑通

建立故障矩阵：同键同内容并发、同键不同内容、事务写入后回滚、提交后响应丢失、事件重复/乱序/缺口、消费完成前崩溃、补偿响应丢失、过期重放、权限撤销、旧工作者迟到。每个测试断言业务不变量和可恢复状态，而不只是HTTP状态码。

本地模型可验证状态转换和去重思路，但数据库真实并发还需双会话实验：会话A占唯一键未提交，会话B同键等待；A提交后B应走结果重放，A回滚后B可取得处理权。注入锁超时与进程终止，确认没有永久占位或重复业务效果。

对消息系统验证真实offset/确认行为、分区并行进度与重新均衡；对供应商使用沙箱验证同键保留、查询一致性和退款幂等。未得到对端契约与故障证据前，不能宣称端到端Exactly-once。

### 9.2 监控与安全运维

监控重复命中率、指纹冲突、处理中最老年龄、Outbox未发布年龄、消费去重冲突、版本缺口、补偿重试与失败、UNKNOWN数量和对账差异。重复率突升可能来自客户端超时或确认丢失，不能仅把“去重挡住了”当作系统健康。

按业务操作号串起请求、事件、Saga步骤和供应商流水，但对外查询仍需鉴权。审计记录谁触发重放、为何修复、前后业务状态及证据，敏感请求体不应无限复制到日志。操作号不是访问凭证，错误响应也不能泄露别的租户结果。

Schema演进使用明确版本，先让消费者兼容新旧数据，再发布新字段或事件。重放历史消息时使用当时语义还是新语义，必须明确；不能让新代码把旧订单重新计算为新的价格。可重建投影与不可重复执行的业务副作用应分离处理入口。

## 十、面试完整回答与追问

### 10.1 “Redis SETNX能实现支付幂等吗？”

完整回答：它可以减少并发重复进入，但不能单独保证业务幂等。锁过期、缓存丢失、进程暂停后旧请求继续执行，都会打破“一个持有者”的假设。我会用可信租户和稳定支付操作号建立持久唯一约束或操作记录，本地效果与结果同事务；外部支付使用供应商幂等操作号，并处理结果未知与对账。Redis只作为优化或受限租约，不能代替外部副作用保护。

追问“加长锁TTL是否就安全？”答：只能改变重叠概率，无法覆盖无限网络延迟或进程暂停，还会延迟故障接管。需要版本/栅栏和权威端幂等，不能靠一个时间参数证明正确性。

### 10.2 “消息保证Exactly-once为什么还要消费者去重？”

完整回答：先问保证范围。Kafka内部事务可以协调相应消费进度和Kafka输出，外部数据库或HTTP扣款不自动参与。同一数据库内我会把消费者处理标记与业务效果放同一事务，提交后确认消息；对外部副作用再用稳定业务身份和恢复机制。消息投递次数与业务效果次数是两个不同层次。

追问“有Event ID唯一约束就够吗？”答：同一业务操作可能有不同Event ID，还需自然业务键；事件乱序需要版本语义，增量缺口不能靠去重解决。

### 10.3 “Saga失败后逆序调用补偿，就等于分布式回滚吗？”

完整回答：不等于。补偿是新的业务操作，可能有手续费、时延和失败，原历史必须保留。我要先设计可补偿步骤、不可逆边界、中间状态与业务不变量，再持久化步骤和补偿任务；补偿幂等、可重试、可审计，永久冲突可人工处理。Saga也不提供全局隔离，其他流程可能看见中间结果。

追问“取消后扣款才成功怎么办？”答：先承认结果未知，通过原操作号确认资金事实，再决定履约或稳定退款；不能仅因本地订单取消就丢弃迟到成功。

### 10.4 “最终一致性如何证明真的会最终一致？”

完整回答：明确权威来源、可接受陈旧度、正常传播、去重乱序规则、缺口修复和对账。以权威提交到读路径可见定义SLO，同时告警最老未完成记录，覆盖长尾。若系统没有持续恢复、冲突策略和人工兜底，“最终”只是愿望。

追问“30秒SLO内有少数永远不完成也算达标吗？”答：百分位指标可能掩盖极少数永久卡住，所以还需绝对年龄阈值、逐项恢复和业务差异对账；不能仅满足百分位就宣称所有操作收敛。

## 十一、扫雷自测与完整答案

### 11.1 同一用户连续两次支付相同金额，是否用请求体哈希去重？

不应只按内容去重。它们可能是两个独立操作，应使用各自稳定操作号；同一操作重试复用同一号。指纹用于检查同键内容一致，不负责猜测用户是否真的想再次支付。

### 11.2 先写“已处理事件”，再单独写余额，哪里会丢处理？

两次提交间崩溃时标记已存在而余额没增加，重投被错误跳过。二者必须在同一事务，失败一起回滚。若余额在远程系统，则本地事务无法解决，需远程幂等及可恢复任务。

### 11.3 消费写库成功后尚未提交offset就崩溃，为什么不能先提交offset？

先提交会在后续写库失败时永久跳过消息。正确选择是提交业务后再确认，接受可能重复，并用本地事务去重消除重复效果。并行分区处理还要保证不越过未完成位置。

### 11.4 Upsert中使用balance=balance+100，重复两次会怎样？

会增加200，而不是100。Upsert只是冲突写入语法，不自动提供业务幂等。需唯一流水号与余额变更同事务，或者按具有版本保护的权威全量状态更新。

### 11.5 收到v=12后又收到v=11，能否一律丢弃v=11？

全量快照且v=12覆盖完整状态时通常可忽略旧版本；增量事件则可能依赖v=11，跳过会丢效果。要先定义事件语义，再决定缓冲、补拉、重放或权威重建。

### 11.6 退款接口超时，能否生成新退款号再试？

不能直接这样做，第一次可能已成功。保持稳定退款操作号查询或幂等重试，并受累计退款不超过扣款金额等不变量约束。生成新号可能绕过去重造成重复退款。

### 11.7 去重记录24小时后删除，但备份恢复重放7天消息，有什么后果？

旧事件可能被重新当成首次处理，重复产生效果。应延长保护范围、保留长期业务唯一性、恢复时协调快照与位点，或仅重建无副作用投影；不能只依赖短TTL标记。

### 11.8 10万事件中120条超过30秒，是否满足99.9%在30秒内？

不满足，及时比例为(100000-120)/100000=99.88%。不能删除失败记录美化分母，还需最老年龄与对账处理永久卡住长尾。

### 11.9 积压60,000，新流量900/秒，安全处理1,000/秒，多久排空？

理想净处理速度100/秒，至少600秒。直接用60,000/1,000=60秒漏算新流量；若处理能力不高于新流量，持续接收时无法排空。实际还要考虑重试、倾斜和下游故障。

### 11.10 对账发现本地UNKNOWN而供应商已扣款，直接改status够吗？

不够。应通过幂等领域命令确认资金事实、检查订单履约状态，生成必要事件与审计，必要时发起退款。直接改表可能跳过不变量和下游通知，使另一部分数据继续不一致。

## 十二、速记、来源与验证边界

先给操作稳定身份，再用指纹防同键异义；本地效果与防重标记同事务，外部效果由权威端幂等与状态恢复保护。Outbox防漏发但仍可重复；Inbox防本地重复效果但不自动保护外部调用。版本解决乱序必须先区分快照与增量，补偿是新业务动作，UNKNOWN必须靠证据收敛。
