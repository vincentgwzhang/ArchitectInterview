# 05. 日志、指标、链路追踪与线上问题诊断

> 本章目标：从用户症状出发，设计能回答问题的遥测数据，并通过证据逐步定位和缓解故障。示例使用OpenTelemetry Java API 1.x的稳定基础接口与Prometheus经典Histogram语法；实际SDK、Agent、语义约定和后端须锁定兼容版本。所有事故与数值均为虚构教学示例，不是用户经历或实测基准。

## 一、三类Telemetry怎样配合

### 1.1 Metrics、Logs、Traces分别回答什么

遥测（Telemetry）是系统向外输出的运行证据。指标（Metrics）把同类事件聚合成时间序列，适合看流量、错误率、资源和趋势；日志（Logs）记录离散事件及上下文，适合解释一次失败发生了什么；链路（Trace）通过跨度（Span）描述一次分布式执行的因果关系和耗时，适合寻找跨服务慢点。

例如订单失败率从0.1%升到5%，指标告诉我们故障范围和起点；一条失败Trace表明支付调用等待了600ms；关联日志给出连接获取超时错误与服务版本；数据库或JFR进一步验证连接被长事务占用。指标不能替代单次错误细节，日志没有因果关系时也难以解释并行调用，Trace又可能被采样遗漏。三者相互验证，不能要求任一信号独自证明全部根因。

可观测性（Observability）不是多装三个产品，而是让输出足以检验假设。发现慢请求后，能否区分排队、锁等待、网络和CPU？发布后错误上升，能否按版本与区域比较？回答不了时，应补充缺失测量，而不是持续堆日志。

### 1.2 关联字段需要一致语义

Trace ID标识同一链路，Span ID定位其中一次工作；Business ID如订单号跨越重试、后台任务及多条Trace关联业务生命周期。Request ID可以标识一次入口尝试，不能假设一个订单永远只有一个Trace。还应记录service.name、service.version、部署环境、Region和Availability Zone（AZ，可用区），以区分代码、配置及基础设施差异。

业务ID适合受控日志与查询字段，通常不适合指标标签。服务版本是必要部署维度，但版本持续增加也有保留和基数成本。时间统一输出带时区的时间戳，测持续时间使用单调时钟；跨机时间线考虑时钟偏差，不能用两个主机墙上时钟简单相减就认定网络耗时。

Trace ID和客户端传来的Correlation ID不是授权凭证；不允许凭ID读取其他租户的诊断记录。外部字段要校验长度、格式并结构化编码，避免日志注入或存储膨胀。

## 二、Structured Log：可搜索、可解释、不过量

### 2.1 设计稳定事件，而非拼接人类句子

结构化日志（Structured Log）将事件名与字段分别保存，JSON是一种常见编码。例如：

~~~json
{
  "timestamp": "2026-11-16T00:00:00Z",
  "severity": "ERROR",
  "event_name": "payment.confirmation.failed",
  "service_name": "order-service",
  "service_version": "2026.11.16-1",
  "region": "eu-west",
  "availability_zone": "zone-a",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "order_id": "demo-order-7",
  "error_code": "PAYMENT_RESULT_UNKNOWN",
  "dependency": "payment-provider",
  "attempt": 1,
  "duration_ms": 601
}
~~~

event_name描述稳定事件类别，order_id是可搜索值；不要把订单号拼进事件名。error_code供机器聚合，message可补充可读上下文；同一字段类型保持稳定，避免某版本duration_ms是数字、另一版本是字符串导致索引或查询失效。

日志还应说明结果和恢复语义：连接失败、明确业务拒绝、超时结果未知是不同事件。不能把“调用已发出”写成“支付成功”，也不能只记录“something failed”而无依赖和错误分类。日志字段不是越多越好，应围绕可检验的诊断问题选择。

### 2.2 日志级别、异常归属与重复堆栈

DEBUG用于临时或低成本细节，INFO记录有价值的业务/生命周期事件，WARN表示需关注但已恢复或可降级的异常条件，ERROR表示操作失败或需要处理的错误。具体规则需团队统一；正常参数校验失败不应每次都打印完整ERROR堆栈，重试的每次暂态失败也不必被当作独立事故。

异常在拥有足够处理上下文的边界记录一次完整堆栈，下层保留Cause并向上传递；确有不同诊断价值时可在下层记录独立事件，但不要五层都打印同一个异常。日志中的“同一错误很多条”可能是重复记录，不等于很多次业务失败。

保留异常类型、稳定错误码、Cause和必要上下文；不要把密码、Token、卡号、不必要个人信息（Personally Identifiable Information，PII）放进异常message。参数化日志减少字符串拼接且利于结构化，但不会自动脱敏；请求体、URL查询参数、SQL绑定值和HTTP头都是常见泄露点。

### 2.3 日志管道也会失败

同步写远端日志会把遥测后端故障传播到业务；异步缓冲减少请求阻塞，却可能在队列满或进程崩溃时丢数据。必须定义缓冲上限、丢弃策略、采样、磁盘配额与失败计数。不能为“保证日志不丢”在内存无限堆积，最终导致业务OOM。

诊断日志与强审计记录的可靠性契约不同。资金审计需要持久、权限与防篡改设计，不能仅依赖可丢弃的异步控制台日志；但也不应把所有DEBUG提升成审计级同步持久化。按用途选择保留、索引与存储层级，控制采集、传输、索引和查询成本。

出现日志空白时先检查采集延迟、Agent丢弃、磁盘满、索引失败与访问权限，再推断“服务没有执行”。事故中临时提高日志级别应限定服务、时间、字段和采样，设置自动恢复，避免日志风暴及敏感数据外泄。

## 三、Metrics：用低基数聚合衡量用户与资源

### 3.1 RED与USE要连接起来

RED针对请求：Rate是每秒请求/完成量，Errors是失败数量及比例，Duration是耗时分布。应区分入口请求、下游尝试、重试、拒绝和最终业务结果；HTTP 200可能包含业务失败，HTTP 503快速返回也不是成功。异步订单还要看从接收到业务终态的时延和长期处理中数量。

USE针对资源：Utilization是使用程度，例如CPU忙碌比例；Saturation是需求超过即时服务能力的迹象，例如运行队列、连接等待和最老任务年龄；Errors是资源相关失败。CPU利用率高但无排队和用户影响，不一定需要立即叫醒值班；CPU低却连接池等待高，也可能已经严重故障。

四个Golden Signals通常指延迟、流量、错误、饱和度。将用户侧RED与资源侧USE连接，才能回答“用户失败是否由资源争用造成”。CPU、内存和线程数只能作为假设证据，不能见到一个高值就认定根因。

### 3.2 Counter、Gauge、Histogram的使用边界

Counter是累计计数，进程重启可归零；查询每秒速率时使用rate等理解重置的函数。Gauge是当前值，可增可减，适合队列长度、在用连接；不要对温度或当前队列长度机械使用Counter速率。Histogram把观察值放入桶，适合延迟和大小分布。

平均延迟会掩盖尾部：90次10ms、10次1,000ms，平均109ms，但十分之一请求等待1秒。P99是使约99%观测值落在其下的分位点，其精度取决于采样、桶和算法；不应把不同实例P99求平均当作全集群P99。若需要跨实例聚合，应合并兼容的Histogram分布后计算。

经典Histogram的桶是累计计数，le表示小于等于该上界。例如le=0.3桶包含所有不超过300ms的观察。桶边界应覆盖业务SLO及实际分布；若阈值在很宽桶中，分位估计可能不够精确。客户端Summary的预计算分位通常不能直接跨实例合并。Native Histogram的配置、支持和查询细节需按部署版本确认，本章查询限定经典桶。

### 3.3 可解释的PromQL示例

假设应用自定义order_requests_total Counter，标签为service、route、outcome、version、region；outcome在受控枚举success/failure中取值，所有计入的请求最终都恰好增加一次，未知结果由业务契约明确归类。以下为教学查询，未连接真实Prometheus运行：

~~~promql
sum(rate(order_requests_total{service="order-service",outcome="failure"}[5m]))
/
sum(rate(order_requests_total{service="order-service"}[5m]))
~~~

先对每条Counter计算rate，再求和，使各实例重启的归零可分别处理。分母为零时不要把NaN或缺失值无条件当0%健康；低流量或无数据需要单独策略。按版本比较时分子分母使用相同分组，不能拿新版失败除以全站请求稀释问题。

若应用记录order_request_duration_seconds经典Histogram，按路由聚合P99：

~~~promql
histogram_quantile(
  0.99,
  sum by (le, route) (
    rate(order_request_duration_seconds_bucket{service="order-service"}[5m])
  )
)
~~~

必须保留le维度并确保桶定义兼容。若目标是“300ms内成功比例”，最好直接使用成功且le=0.3的桶与定义一致的总数计算，而不是先计算一个近似P99再猜SLO。只记录已完成任务会遗漏永远卡住的任务，因此还要有在途数、最老年龄和入口端超时统计。

### 3.4 Cardinality为何会成为事故

基数（Cardinality）指标签组合产生的不同时间序列数量。若100条路由、5种状态、10个版本、3个区域、20个实例全部组合，单指标就可能有300,000条序列；Histogram每个桶及count/sum还会继续放大。实际组合未必全出现，但设计必须评估最坏规模和持续 churn。

User ID、Order ID、Trace ID、原始URL与任意异常message通常不能作为指标标签。把/orders/123规范成/orders/{id}，错误归为有限error_code；业务ID放日志或Trace，必要时用Exemplar把分布中的样本关联到Trace，而不是为每个Trace建序列。

按Tenant诊断有价值，但所有租户永久作为标签可能不可承受且泄露业务信息。可用受控租户等级/类别做常规指标，事故中通过受限日志或临时有界分析定位具体租户。维度精细度、保留时长、查询成本和隐私要共同设计。

## 四、Tracing：因果关系、时间和上下文传播

### 4.1 Span不是一条普通日志

Span描述一次有开始和结束的操作，包含traceId、spanId、父关系、名称、属性、事件和状态。入口HTTP Server Span可包含数据库Client Span、下游HTTP Client Span与关键领域步骤；名称应稳定，例如payment.confirm，而非payment.confirm.order-123。

自动埋点擅长HTTP、数据库等通用边界，手动Span补充“库存校验”“支付确认”等领域意义。不要给每个getter建Span，过细会增加CPU、分配、导出成本，且淹没真正慢点。避免Agent和手工代码重复生成同一HTTP边界，重复Span会使请求数和时序解读混乱。

Span时长是墙上经过时间，可能包含排队、阻塞和远程等待，不等于CPU时间。父Span中的子Span并行时，不能将所有时长直接相加；找延迟贡献要沿关键路径（Critical Path），并考虑未被埋点的空白区间。

### 4.2 W3C Context与异步边界

W3C Trace Context通过traceparent等字段传播追踪身份。其版本00示例包含版本、32位十六进制traceId、16位父spanId和flags。调用方注入、接收方提取并创建子Span，SDK与传播器应负责校验，不应业务代码自己随意拼接。

线程本地上下文不会天然跟随所有线程池、CompletableFuture或响应式调度。下面是OpenTelemetry Java API 1.x的示意片段，依赖正确配置的Tracer/SDK与应用executor，本次未编译运行：

~~~java
Context captured = Context.current();
executor.execute(captured.wrap(() -> {
    Span span = tracer.spanBuilder("inventory.reserve").startSpan();
    try (Scope scope = span.makeCurrent()) {
        reserveInventory();
    } catch (RuntimeException ex) {
        span.recordException(ex);
        span.setStatus(StatusCode.ERROR);
        throw ex;
    } finally {
        span.end();
    }
}));
~~~

captured.wrap使任务执行时恢复提交处Context，makeCurrent让任务内调用关联当前Span，Scope关闭后恢复原上下文，finally保证Span结束。recordException记录异常事件，不应假设它总会自动设置错误状态，示例显式设置StatusCode。InterruptedException、取消和业务拒绝的分类应由具体操作补充；示例的reserveInventory未实现，不代表完整库存服务。

MDC（Mapped Diagnostic Context）是日志框架常见线程关联字段机制，不等于OpenTelemetry Context。线程复用若不恢复或清理MDC，会把前一个用户的traceId带到下一个请求，造成错误关联甚至泄露；必须用作用域恢复而非永久写入。响应式流程应使用对应上下文传播支持，不能简单把ThreadLocal当跨订阅状态。

### 4.3 HTTP、DB、Kafka与领域步骤的区别

数据库Span应说明操作类型、目标和耗时，SQL文本与绑定值要脱敏，不能把敏感条件全部写入遥测。Span显示数据库调用500ms，仍需区分借连接、驱动、网络、锁与执行；必要时增加池等待测量并关联数据库会话证据。

消息生产与消费分离于时间和线程。应通过消息头传播Context，但长生命周期任务、批消费或一条消息关联多个来源时，Span Link可表达关联，而不是强行给所有消息一个父Span。保留eventId与业务操作号便于重放诊断，重投/重试的Span也要说明attempt，避免把重复工作误判为更多用户请求。

外部traceparent和Baggage均应视为不可信输入。Baggage是随Context传播的业务元数据，不应携带Token或PII，也不能直接作为授权依据；过多字段还增加每跳网络开销。跨信任边界限制可传播字段、长度与目标，必要时建立新Trace并安全关联，不能让外部调用者无限控制采样成本。

## 五、Sampling：保留诊断价值，但承认盲区

头部采样（Head Sampling）在链路早期决定是否记录/导出，成本较低，但此时通常不知道最终是否慢或失败。尾部采样（Tail Sampling）在收集若干Span、等待链路结果后按错误、慢请求等规则选择，诊断针对性更强，却需要缓存、决策等待及相关Span路由到同一决策节点。

因此“采样应保留错误与慢Trace”应理解为策略目标，而不是100%无条件保证。若头部已经丢弃Span，尾部无法凭空恢复；超长Trace、Span晚到、Collector过载、网络丢失也可能让错误Trace不完整。应定义错误/慢请求优先、正常流量基线随机样本以及每服务/租户成本上限，并监控实际保留率。

尾部策略会偏向错误，不能直接用采样后的Trace数推导全流量错误率。业务SLI通常由覆盖范围清晰的指标或权威事件计算；若确需从样本估计，必须考虑抽样概率与选择偏差。没有找到某条Trace不是该请求未发生的证明，日志与业务状态仍是补充证据。

例如1,000请求/秒，每Trace平均20个Span、每Span导出体积假设1KiB，全量约20,000KiB/秒，未计协议、索引、副本和压缩；长期存储成本不小。采样之外还可以减少无价值属性、缩短普通Trace保留、对关键事故有界提高采样，不能只降低百分比而丢失所有罕见故障。

## 六、遥测管道的架构与可靠性

应用中的API产生信号，SDK负责聚合、批量和导出，Collector可做接收、处理、采样、脱敏和转发，后端负责存储与查询。OpenTelemetry本身不是一个自动提供全部存储和查询能力的数据库。各组件版本、语义约定与资源属性应统一治理，避免HTTP属性名升级后同一看板漏掉半数服务。

业务优先于普通诊断数据：导出需有界队列、批量和超时；Collector宕机不能让每个请求无限等待。异步导出存在丢失窗口，持久队列可改善恢复但增加磁盘和运维成本；对审计用途需要另外满足可靠性要求。监控SDK/Collector接收、拒绝、丢弃、队列、发送失败和导出延迟，遥测系统也需要自身可观测性。

所有数据通道使用适当认证与传输保护，按环境/租户隔离读取权限，敏感字段尽量在源头不采集，Collector脱敏作为额外防线。不同信号的删除、保留与访问审计要协调，不能日志已删除而Trace属性里继续存完整个人信息。

## 七、线上诊断：从影响到可验证假设

### 7.1 确认范围并建立时间线

先确认谁受影响、哪个操作、何时开始、成功率/时延变化、是否有结果未知或数据损坏。记录时区、观察窗口、发布和配置变化。使用用户侧SLI或独立探测验证，而非仅凭一个Pod日志判断全站不可用。

比较版本、Region/AZ、路由和受控租户类别。总错误率可能看似1%，但某区域已全部失败；反之一个大流量租户可使全站聚合变化，未必所有客户都受影响。分段时检查分母和样本量，避免把低流量随机波动当成确定版本回归。

相关不等于因果。发布时间与故障相近是强线索，但依赖变更、流量倾斜、定时任务和容量边界也可能同时发生。优先提出能被证据推翻的假设，例如“新版使连接持有时间上升”，再查相应指标、Trace和数据库事务，而不是先确定责任归属。

### 7.2 Trace找路径，Logs/DB/JFR找机制

从失败/慢样本检查根Span、关键子调用、重试、空白区间与采样完整性。HTTP父Span耗800ms、DB Span只20ms，不代表CPU计算780ms，空白可能是线程排队、借连接或漏埋点；需补充线程池等待、线程栈或JFR证据。

CPU高时用Java Flight Recorder（JFR）或采样Profiler定位热点与分配；CPU低却请求卡住时检查锁、I/O、连接池和线程阻塞。数据库看活跃会话、阻塞链、长事务和执行计划；EXPLAIN ANALYZE会实际执行语句，不能对生产写SQL随意运行。Heap Dump可能暂停并包含敏感数据，需要容量、权限与处置计划。

重复时间点线程栈可区分瞬时等待与持续堵塞；单张栈只是一瞬间证据。工具会增加CPU、磁盘与暂停风险，应优先低影响观测、限定时间和目标。禁止在事故中无约束打开全量SQL/请求体日志或对所有实例同时dump。

### 7.3 先Mitigate，再验证，最后Root Cause

缓解（Mitigation）是减小用户损失，例如回滚已证实有风险的版本、关闭非关键功能、限制异常流量或暂停后台任务。执行前核对回滚是否兼容数据库Schema和已产生数据；扩容也需确认下游余量，不能把数据库过载放大。

每个动作记录假设、预期指标与观察时间。若回滚后错误率下降，但UNKNOWN支付仍未收敛，事故业务恢复尚未完成；需确认成功吞吐、尾延迟、队列、未知操作与数据对账。恢复流量时渐进放量，避免积压、重试与缓存回源同时触发。

根因分析（Root Cause Analysis）应解释触发条件、机制、为何保护和监测未阻止影响，以及哪些证据支持。修复行动落到负责人、验收和期限，例如“连接获取和事务持有分别埋点、故障压测验证上限”，而不是空泛“加强监控”。保留事实与不确定性，不把一次相关性当作最终结论。

## 八、可执行告警：Page、Ticket与Runbook

### 8.1 Error Budget燃烧率

服务等级指标（SLI）衡量实际表现，SLO是目标；错误预算（Error Budget）是允许的不良事件比例。若目标99.9%成功，允许失败比例0.1%。当前失败率1%，燃烧率Burn Rate=1%/0.1%=10，表示按相同流量统计口径以允许速度的10倍消耗预算。

假设30天窗口且流量均匀，持续1小时燃烧率10，约消耗月预算的10×1/720=1.39%。这是预测模型，真实请求型预算受流量分布影响，不能把时间比例当精确账本。成功定义、分母和排除规则必须固定，拒绝、超时及降级不能随意移出统计。

快速预算消耗且需要立即行动时发Page；慢趋势、容量规划和可稍后处理的问题发Ticket。CPU高但无用户影响通常是诊断或趋势信号，不过即将耗尽磁盘、证书将过期等明确迫近风险也可以在用户受损前告警，不能机械坚持“出事后才通知”。

### 8.2 多窗口、低流量与缺失数据

长窗口降低噪声，短窗口确认问题仍在持续。例如同一服务同时满足过去1小时和5分钟的高燃烧条件才Page；另设较慢燃烧的长窗口Ticket。阈值和窗口来自能容忍的预算损失、检测速度和响应能力，不是抄一个固定失败率。

低流量时一次失败可产生很高比例，需要绝对事件数、关键操作特殊规则或独立探测辅助判断；但不能因样本少就忽略唯一一笔高价值支付。无流量、采集断开和服务真的不可用必须区分，必要时对缺失序列与黑盒探测分别告警。

对依赖故障可分组、去重和抑制下游重复Page，但保留关键用户影响可见性。维护静默应限定时间与范围；告警状态、恢复通知和事故关联可追踪，避免同一根因叫醒十个团队却没人负责协调。

### 8.3 Runbook必须让值班者能执行

运行手册（Runbook）至少说明用户影响、所属服务和负责人、指标口径、看板/查询、先检查什么、可执行缓解及回滚条件、何时升级、怎样确认恢复。链接只是入口，关键判断规则应写清，例如“新版本失败率显著更高且旧版本健康，核对Schema兼容后停止新版本流量”。

对危险操作注明权限、影响和证据保留要求；不要把“重启所有Pod”当通用答案。定期演练告警是否真的触发、通知能否到达、查询是否仍有效、手册操作能否恢复业务。没人能够依据告警做动作时，应补手册或调整告警，而不是继续增加噪声。

## 九、完整教学事故：新版本订单变慢

假设发布新版后，zone-a的订单P99从200ms升到1秒，失败率达2%，CPU仅30%。先确认入口订单SLI和影响时间，分版本/区域比较，发现新版实例失败明显，而旧版和其他区域较正常。该事实支持发布相关假设，但尚不能证明代码就是根因。

Trace显示慢请求在“支付前”的空白区间长，HTTP支付Span只有40ms；连接池Acquire P99升到600ms，在用连接满，Usage也上升。关联日志显示连接获取超时，数据库活跃事务记录表明新版在事务内等待一个外部查询。这里证据链是“事务跨远程等待→连接持有变长→借连接排队→入口超时”，而不是“CPU低所以线程不够”。

先停止新版扩量并暂停非关键批处理，核对迁移兼容后回滚；验证错误率和时延恢复，队列排空，UNKNOWN操作经查询/对账收敛。不要直接扩大连接池，可能将更多并发压向数据库。永久修复是重设事务边界、分别测量Acquire和Usage，并增加依赖慢时的隔离测试。

若没有Trace，仍可通过版本指标、池等待、重复线程栈与数据库事务验证；若没有业务ID，超时后的资金恢复则会非常困难。该案例说明信号缺失可被部分补偿，但业务正确性与追踪关联应在设计时建立。

## 十、面试完整回答与追问

### 10.1 “日志、指标、Trace怎么选？”

回答：指标用于全量趋势、SLI和告警，日志用于离散事件与错误细节，Trace用于单次分布式因果和耗时。以traceId、业务操作号、版本和区域关联，从用户症状用指标缩小范围，再用Trace找路径，日志和Profiler/数据库验证机制。不能只堆数据，字段、成本、采样和安全边界要一起设计。

追问“为什么不全部写日志后再聚合？”答：高流量原始事件采集、索引成本高，丢弃和采样可能影响精确SLI，查询时聚合也更重；专用低基数指标更适合常规监控，关键业务账本另有持久要求。

### 10.2 “如何保留所有错误Trace而降低成本？”

回答：头部采样早期不知道最终结果，无法保证所有错误被保留；可采用尾部错误/慢请求策略，加正常基线随机样本与成本上限。但前端丢弃、Span晚到、Collector缓存和路由失败仍可能导致缺失，应监控采样管道，并用指标计算真实错误率，不把偏向错误的样本当全量。

追问“错误样本占比50%说明全站错误率50%吗？”答：不说明，尾部策略本来就优先保留错误；需使用完整覆盖的SLI或明确抽样概率的估计。

### 10.3 “CPU不高但接口超时，怎样查？”

回答：先确认用户影响和版本/区域范围，再查饱和度而不只看利用率。线程池排队、连接获取、锁与下游I/O都可能在CPU低时阻塞。我会用Trace关键路径及空白区间定位阶段，再用重复线程栈、JFR和数据库阻塞链验证。缓解先减少非关键争用，扩线程或连接前确认瓶颈与下游余量。

追问“Trace中没有慢Span是否证明服务没问题？”答：不证明，可能漏测排队或Context断裂，也可能样本不完整；需要补充阶段计时和其他证据。

### 10.4 “怎样设计不会扰民的告警？”

回答：以用户影响和预算消耗决定Page，趋势与容量问题进入Ticket；用长短窗口确认持续燃烧，结合低流量与缺失数据规则。告警包含负责人、口径、Runbook和恢复标准，并分组抑制同根因噪声。也保留磁盘将满等明确迫近风险，不等用户受损才行动。

追问“错误率降低就能关闭事故吗？”答：还要验证成功吞吐、尾延迟、积压、数据正确性和未知业务结果；只因限流让错误流量消失不代表业务已恢复。

## 十一、扫雷自测与推理答案

### 11.1 能否平均20个Pod的P99得到全站P99？

不能，分位数不是线性可加统计。应聚合兼容Histogram桶再求分位，或用其他可合并分布算法；还要确认样本口径和桶精度。

### 11.2 用户ID放指标标签，方便定位，有何问题？

它会让时间序列随用户数不断增加，叠加其他标签和桶迅速放大存储、内存与查询成本，也可能暴露身份。使用有限分类指标，具体ID通过受控日志/Trace查询。

### 11.3 ERROR日志打印了五次，是否五个请求失败？

不一定，可能同一异常被五层重复打印。通过业务/请求ID和事件语义去重判断，最终业务失败计数应在清晰边界恰好记录一次，不能靠堆栈条数计算错误率。

### 11.4 Head采样丢掉99%后，Tail能找回全部慢请求吗？

不能，已未记录/未导出的数据不能被尾部凭空恢复。需要协调采样链路并承认完整性与成本取舍，额外指标和关键日志保留诊断证据。

### 11.5 99.9%SLO、当前失败率1%，燃烧率是多少？

10，因为允许失败0.1%，1%/0.1%=10。若均匀流量30天窗口持续1小时，约耗1.39%总预算；真实请求分布不均时按实际事件计算。

### 11.6 父Span800ms，两个并行子Span各500ms，是否说明Trace错了？

不一定，两个子操作可能重叠，不能相加成1,000ms再与父比较。检查开始结束、关键路径和跨机时钟误差；父还可能包含排队或其他工作。

### 11.7 Collector没有新数据，是否可以断言业务无请求？

不能，采集、网络、导出、队列、权限或后端都可能异常。结合独立入口指标、黑盒探测和管道自身监控区分无流量与观测失明。

### 11.8 一个租户的支付全部失败，全站失败率很低，是否无需行动？

不能仅看总体。需按业务重要性、影响范围与契约判断，检查有限租户分类及业务日志，避免大流量健康请求稀释局部严重故障，同时控制指标基数。

### 11.9 返回HTTP 200的fallback是否都算成功？

取决于业务SLI。推荐省略可能属于允许体验，支付不可用却返回默认成功不能算支付成功。必须把主路径、降级与最终业务结果分开统计。

### 11.10 外部traceparent能否证明请求来自可信服务？

不能，它只是上下文输入，攻击者可以构造。使用独立认证授权，校验传播字段并限制成本，Baggage也不承载未经校验的权限结论。

## 十二、速记、来源与验证边界
