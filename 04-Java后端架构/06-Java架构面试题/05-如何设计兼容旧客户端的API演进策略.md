# 05. 如何设计兼容旧客户端的 API 演进策略

## 一、问题基线：兼容的是已部署的行为，而不只是 JSON

API（Application Programming Interface，应用编程接口）是服务端与调用者之间的契约（Contract）。契约包括路径、字段、类型，也包括金额单位、默认值、权限、错误码、分页顺序、超时以及一次请求会产生什么副作用。只比较字段名，会漏掉最危险的语义变化：把同一个 amount 从“分”改成“元”，JSON 仍是数字，付款金额却可能放大一百倍。

后向兼容（Backward Compatibility）在本章指新服务端仍能正确服务已部署的旧客户端；前向兼容（Forward Compatibility）指客户端能在约定范围内容忍未来服务端扩展。两者有方向性，不能凭“接口没报错”判断成功。旧客户端把新订单状态显示成“已完成”，即使返回 HTTP 200，也已经不兼容。

移动应用受应用商店审核、用户升级意愿、离线设备限制；外部集成还受合作伙伴发布周期与合同约束。服务端不能假设发布新 SDK 后所有调用者立即升级。SDK（Software Development Kit，软件开发工具包）只是帮助调用接口的代码，服务端升级不会替换用户设备里的旧 SDK。

本章使用一个**虚构订单 API**贯穿说明：V1 只支持人民币，金额为整数分，状态只有 PENDING、PAID、CANCELLED；V2 希望支持显式币种、字符串小数金额及新履约状态。目标是引入新能力，同时避免旧客户端错付、误展示和重复下单。这里的版本与数据均为教学设计，不代表用户项目。

### 1.1 先明确业务承诺与成本边界

设计前必须回答：哪些调用者承诺长期支持，哪些操作涉及资金或安全，允许多长迁移期，谁负责通知合作伙伴，维护多版本的人力与基础设施预算是多少。读订单可以降级为只读摘要，支付授权却不能靠猜测默认值继续执行。兼容性是受约束的服务承诺，不是永久保存漏洞或无期限维护所有历史行为。

若公司控制所有内部客户端，能协调发布且有回滚窗口，可以用短期兼容桥接；若设备多年不升级，通常要维护稳定旧契约、在边界翻译并限制旧版本可访问的业务范围。选择受支持窗口时，需同时考虑活跃消费者、历史回流、合同与安全，不把“低于某个流量比例”当作通用下线标准。

### 1.2 建立真实消费者画像

版本分布（Version Distribution）至少分 API 契约版本、应用版本、SDK 版本和操作系统版本。应用 3.0 可能仍调用 V1，某 SDK 的用户也可能自写 HTTP 请求，所以 User-Agent 不能替代契约版本。网关记录规范化后的契约版本、受认证的客户端标识、路由、状态码、错误业务码和延迟；保留未声明版本这一类，不能把它悄悄归到最新版本。

契约使用情况还包括哪些字段真的被消费、哪些错误分支影响业务。服务端能观察请求字段，却通常无法仅凭访问日志知道响应字段是否被读取，应结合消费者登记、旧安装包测试、集成反馈。按活跃消费者数、成功交易量与关键业务收入共同评估，比只数请求更可靠；一个每月结算一次的客户可能流量很小而价值很高。

日志不保存令牌、完整付款信息或个人敏感数据。客户端标识进入明细审计可控，监控指标标签则应保持低基数，例如按版本和路由聚合，避免为每个用户建立时间序列造成成本失控。

## 二、判断兼容变化：请求和响应必须分别推理

把服务端看成函数：接收合法请求，产生业务效果及响应。升级后，旧请求仍应被接受，产生原来承诺的效果，响应也应仍在旧客户端能处理的范围内。这比“Schema 能通过”更严格。

| 变化 | 旧客户端发请求给新服务端 | 新服务端返回给旧客户端 |
| --- | --- | --- |
| 新增可选字段 | 旧请求不传，服务端须执行已定义的默认行为 | 只有旧解析器容忍未知字段才安全 |
| 新增必填字段 | 通常破坏兼容，旧请求缺字段 | 新字段存在本身未必破坏，但仍受未知字段处理影响 |
| 放宽枚举集合 | 可接受更多输入，通常不影响旧输入 | 可能返回旧客户端不认识的值，风险很高 |
| 缩窄取值范围 | 旧请求可能被拒绝 | 若仍满足原语义，输出范围变小未必破坏解析 |
| 删除或改名字段 | 旧请求可能无效 | 旧客户端取值、展示或计算可能失败 |
| 改单位、排序、错误码 | 即使类型不变也可能改变业务效果 | 可能破坏计算、翻页、重试和用户决策 |

“通常”必须通过实际消费者行为验证。例如请求端允许额外字段但忽略拼错的 currency，可能以默认币种付款；在资金命令中明确拒绝未知字段，反而比宽松接收更安全。响应可扩展性与请求严格校验可以同时成立，不能用一条“宽容接收”规则替代风险分析。

### 2.1 新增 Optional Field 的四个前提

可选（Optional）只表示允许缺席，不等于允许 null、空字符串或错误类型。给创建订单增加 deliveryMode 时，旧请求不传应沿用原配送行为；不能默认变成更贵的加急配送。还必须确认旧服务端滚动实例遇到新客户端传这个字段时如何处理：如果忽略了新要求，客户端却认为已选择加急，会形成静默错误。

安全步骤是先让所有服务端理解字段，确认缺省行为稳定，再允许客户端发送新值；响应增加字段则先用真实旧解析器测试。某些生成式客户端或严格反序列化配置会拒绝未知字段，“JSON 天生兼容新增字段”不是标准保证。

新增 Endpoint（端点，即路径与 HTTP 方法组合）通常不会影响旧调用，但仍可能占用已有路由匹配、改变共享限流池或引起权限配置错误。新增接口也要做路由冲突、资源配额与鉴权检查。

### 2.2 缺失、null 与默认值必须分开

更新用户资料时，字段缺失可以表示“不修改”，null 表示“清空”，字符串表示“设置”。如果把三种情况都映射成 Java 的一个 null，边界信息就丢失了。可使用带 presence 标记的 DTO（Data Transfer Object，数据传输对象），或显式操作类型表达区别，再映射成内部命令。

对创建订单的 currency，本例约定 V1 根本没有该字段且固定 CNY；V2 必须显式传入支持的币种。不能让 V2 的 null 也自动变成 CNY，因为这会掩盖调用者数据错误。默认值是契约的一部分，变更默认值可能是破坏性变化，即使字段仍可选。

OpenAPI Schema 的 default 描述接收方行为，不会自动把缺失值写入请求或实现服务端逻辑。必须在代码和测试中实现默认值。OpenAPI 3.1.1 的 Schema 可用 type: [string, 'null'] 表达可空，再由 required 决定必须出现；不要把 OpenAPI 3.0 的 nullable 写法不加区分地搬进 3.1。具体生成器的支持还要单独验证。

### 2.3 未知 Enum 不能一律忽略

Enum（枚举）是预先列出的值集合。旧客户端通过穷尽 switch 处理三个状态，服务端新增 REFUNDING 可能触发异常，或落入错误默认分支。已有客户端没有未知值兜底时，服务端不能通过一次发布“让它学会忽略”。

展示场景可以定义 UNKNOWN 并保留原始值，显示“状态更新中，请刷新或升级”，同时关闭依赖未知状态的操作。付款和授权场景应失败关闭（Fail Closed）：无法证明允许时拒绝动作，而不是把未知状态当成 PAID。若客户端需要完整状态机，新状态应通过新契约或明确能力协商提供。

V1 投影也不能把所有新状态硬映射为 PENDING。若 V1 文档承诺 PENDING 可以取消，而新内部状态已进入不可取消履约阶段，该映射会撒谎。应提前设计旧契约能准确表达的粗粒度状态与独立操作权限；无法表达时限制旧版本进入该新流程，提供安全的升级入口。字段类型相同不代表状态机兼容。

### 2.4 错误、分页与时间也是契约

HTTP 状态决定基础设施和 SDK 的默认处理，业务码决定应用行为。把原来的余额不足业务码改成临时不可用，可能使客户端自动重试。错误响应应保留稳定机器码与可供关联的 traceId，人类消息可以改善但不应成为客户端分支条件。不要为了兼容而把所有失败改成 200。

分页从页码改游标时，应提供新参数或新接口。游标（Cursor）是服务端给出的续读位置，通常包含排序边界并防篡改；它不能被当作可计算页码。改变默认排序会造成重复或漏项，即使返回数组形状完全相同。契约应明确稳定排序的第二键、数据变动时的一致性范围和令牌失效处理。

时间字段要写清时区、精度与格式；把秒变毫秒，或者把带偏移时间变成本地时间，都会产生语义破坏。金额、时间、状态和错误这四类字段，应优先进入评审用的兼容性清单。

## 三、版本与能力协商：显式选择，不猜客户端

### 3.1 何时保留同版本，何时创建新契约

若新增字段在旧解析器中安全、缺省行为未变且旧语义仍成立，可以留在同一版本。若需要改金额单位、删除字段、改变资源含义或使旧状态机无法成立，应通过显式新契约隔离，如 /v2/orders。团队也可以用媒体类型或版本请求头；HTTP 并不规定所有 API 必须采用某一种 Major Version 方案，仓库原文“必须新 Major 或 Endpoint”应理解为不能在旧契约下静默破坏。

版本号用于标识外部契约，不应跟随每次内部部署递增。拆成微服务或换数据库不要求客户端升级。反过来，发布 /v2 也不会自动兼容 /v1；必须保留路由、适配器、数据表达能力和维护责任。每版本复制整套业务会让修复逐渐分叉，应共享稳定业务能力，在边界保留差异。

| 选择 | 好处 | 代价与使用边界 |
| --- | --- | --- |
| 路径 /v1、/v2 | 日志、网关和人工排障直观，URI 天然区分 | 链接和路由需维护，多版本仍有治理成本 |
| 媒体类型或版本头 | 同一资源 URI 可选择表示 | 缓存、网关、SDK 必须传播并正确分区 |
| 可选字段与局部能力 | 避免为小扩展整体分版 | 组合数可能膨胀，必须定义依赖与默认行为 |

### 3.2 Capability Negotiation 的执行流程

Capability（能力）是明确命名的行为支持，例如 money-decimal-v2，而不是“客户端版本大于 5 就大概支持”。客户端声明它理解的能力，服务端校验当前可用且该身份有权使用，返回本次选定能力；双方只按选定集合执行。没有声明时沿用旧行为。若请求明确要求某能力才能完成操作而服务端不支持，应返回文档规定的失败，不能悄悄降级为另一种付款语义。

功能开关（Feature Flag）控制服务端向哪些人开放已实现能力；协商决定双方是否理解契约；鉴权决定该身份是否允许执行。三者职责不同。客户端伪造能力头不应获得权限，回滚开关也不能撤销已经创建的订单事实。

能力组合应控制在有测试覆盖的集合。例如 decimal-money 依赖 explicit-currency，服务端拒绝缺依赖的组合，而不是测试所有任意布尔组合。对于完全不同的工作流，单独版本通常比十几个相互作用的开关更可维护。

### 3.3 缓存与灰度不能串版本

若同一个 URI 由 Accept 或自定义版本头决定响应，缓存必须把相关请求头纳入正确的匹配维度，响应按实际选择设置 Vary，CDN 配置也要验证。否则首个 V2 请求填入共享缓存，旧客户端可能拿到 V2 金额格式。Vary 不能替代敏感响应的 Cache-Control 策略；包含用户订单的响应还需适当 private 或 no-store 等策略和真实缓存链路测试。

灰度应按稳定消费者或租户分组，避免同一交易过程中在旧新语义之间随机跳转。记录选定版本并贯穿异步任务和审计，后续重试继续按原业务语义处理。客户端声明版本缺失或未知时，按已公布规则使用固定旧默认值或明确拒绝，绝不默认“最新”。

## 四、边界 Adapter：外部稳定，内部可演进

### 4.1 分层职责与共享领域服务

Adapter（适配器）把外部协议转换为内部命令，再把内部结果投影回该版本响应。请求 DTO 不直接传入持久化实体；否则旧字段名、权限漏洞和数据库结构会相互绑死。领域服务（Domain Service）负责金额规则、订单状态转换与业务不变量，应用服务组织事务、调用和幂等，版本适配器负责格式与历史语义。

V1 的 amountMinor=1234 转成内部 amountMinor=1234、currency=CNY；V2 的 amount="12.34"、currency="CNY" 也转成相同内部命令。内部以整数最小货币单位存储只是本例选择，不是所有币种都有两位小数。扩展币种时必须使用受控的币种精度表和金额上限，不能硬编码所有金额乘 100。

共享业务不等于强行统一所有规则。如果 V1 合同承诺某定价方式，V2 使用新定价策略，可把版本选择转成显式 policyId，并维护受支持策略的测试；不要在核心代码各处读取 HTTP 版本头。这样业务差异可审计，也能避免一改共享服务就悄悄改变旧合同。

### 4.2 可执行的金额适配模型

下面是 Python 标准库教学模型，模拟真实 Java 服务边界需要实现的验证；限定 CNY、正金额、最大一亿元，**不是生产服务**。使用十进制 Decimal 避免二进制浮点误差，先检查分的整数性再转整数，拒绝静默四舍五入。Java 实现可对应使用 BigDecimal 精确换算和显式范围检查，而不是 double。

~~~python
from decimal import Decimal, InvalidOperation

MAX_MINOR = 10_000_000_000

def to_command(version, dto):
    if version == "v1":
        if set(dto) - {"amountMinor"}:
            raise ValueError("unknown field")
        n = dto.get("amountMinor")
        # bool 在 Python 中属于 int 子类，必须明确排除
        if type(n) is not int:
            raise ValueError("integer amountMinor required")
    elif version == "v2":
        if set(dto) - {"amount", "currency"}:
            raise ValueError("unknown field")
        if dto.get("currency") != "CNY":
            raise ValueError("unsupported currency")
        raw = dto.get("amount")
        if not isinstance(raw, str):
            raise ValueError("decimal string required")
        # 此契约只接受普通十进制写法，不接受指数、空白或符号
        parts = raw.split(".")
        if (len(parts) not in (1, 2)
            or any(not p or not p.isascii() or not p.isdigit()
                   for p in parts)
            or (len(parts) == 2 and len(parts[1]) > 2)):
            raise ValueError("invalid money format")
        try:
            scaled = Decimal(raw) * 100
            if not scaled.is_finite() or scaled != scaled.to_integral_value():
                raise ValueError("fractional minor unit")
            n = int(scaled)
        except InvalidOperation as exc:
            raise ValueError("invalid money") from exc
    else:
        raise ValueError("unsupported version")
    if not 0 < n <= MAX_MINOR:
        raise ValueError("amount out of range")
    return {"amountMinor": n, "currency": "CNY"}

def to_response(version, order):
    # 旧响应只能输出旧状态；无法忠实表达时阻止错误投影
    if order["status"] not in {"PENDING", "PAID", "CANCELLED"}:
        raise ValueError("state not representable in this model")
    common = {"id": order["id"], "status": order["status"]}
    if version == "v1":
        return dict(common, amountMinor=order["amountMinor"])
    if version == "v2":
        n = order["amountMinor"]
        return dict(common, amount=f"{n // 100}.{n % 100:02d}",
                    currency=order["currency"])
    raise ValueError("unsupported version")
~~~

本例 V1 请求拒绝额外字段是明确的教学契约，不是建议突然收紧已有宽松接口。历史客户端如果一直发送额外字段，改成拒绝也是兼容性变化。生产还需要请求体长度上限、字符串长度限制、认证授权、结构校验与稳定错误映射；模型中的 ValueError 不能直接变成含堆栈的对外错误。

响应函数拒绝无法表示的新状态，目的是暴露设计缺口；生产应在业务能力入口就阻止 V1 创建不能表示的流程，或设计准确投影，而不是等查询时大量返回异常。测试发现无法投影，是要求重新审查契约，不是鼓励用 500 代替兼容方案。

### 4.3 幂等和事务必须跨版本一致

幂等（Idempotency）表示同一业务请求重试不会重复产生效果。V1 创建订单超时，调用者升级后用 V2 重试，若幂等空间按版本完全隔离，可能下两张订单。对于允许跨版本续试的同一业务命令，使用受认证消费者、操作类型和幂等键确定身份，并以规范化内部命令计算请求指纹。12.34 元与 1234 分是同一金额；同键换金额必须拒绝冲突。

去重记录与订单写入需要同一数据库事务或等效原子保障，不能先查“键不存在”再无约束插入。并发请求由唯一约束决定唯一胜者，失败者读已有结果。响应可以按请求版本重新投影，但业务订单身份保持不变。若新版本改变了业务操作含义，先定义是否仍是同一操作，不能为了去重把不同命令错误合并。

## 五、数据迁移：Expand-and-Contract 的完整时序

Expand-and-Contract（扩展后收缩）是先加入兼容结构，让新旧程序共存，验证迁移后再删除旧结构的发布方法。它同时约束代码、数据库、客户端及后台任务，不能只给表加列就称为迁移完成。

### 5.1 扩展与建立唯一权威

假设旧表只有 amount_minor，新表要加 currency。先增加可兼容的列和必要索引；具体 DDL 是否锁表、是否在线，需要按所用数据库与版本验证，本章不假设无锁。新服务读取旧记录时按已知 V1 合同解释为 CNY，新写入同时保存币种；在旧实例仍运行时，读逻辑还必须容忍它写出的缺币种记录。

“兼容读”应记录命中次数，防止兜底掩盖回填遗漏。不能在多币种已经开放后对任意缺币种记录猜 CNY：旧记录可推断的依据是它产生于只支持 CNY 的受控时期。对无法证明来源的数据隔离审计。

### 5.2 回填与并发更新

回填（Backfill）以稳定主键分批扫描，每批提交，保存检查点，限制速率，避开大事务占满日志和复制带宽。更新使用条件保护，例如只对 currency 仍缺失且确认属于旧合同的记录赋 CNY；业务请求已写入的值不能被回填覆盖。对需要由多个可变字段计算的新列，使用版本号比较或锁等并发策略，遇冲突重读重算。

回填完成要验证记录数、空值、金额和币种的一致性，并抽查关键业务结果。只比较总行数无法发现一部分记录重复处理、另一部分漏掉。长尾写入来自旧实例、补偿任务和消息重放，均需纳入写入者清单。

如果新旧结构分属两个系统，普通数据库事务不再保护双写。应指定一个权威源，通过可重试变更事件或变更捕获同步，并以版本号、去重与对账处理延迟和乱序。两个方向都随意写入会产生冲突，不能把“双方都写”当作一致性方案。

### 5.3 切换、观察与收缩

先上线兼容服务端，再完成回填和校验，最后才开放新客户端能力。观察新读路径是否还有兼容兜底、旧写入者是否已消失、错误与延迟是否达标，达到明确门槛后切读。保留旧结构和可逆代码经过约定观察窗口，再停止旧写并删除旧列、适配代码及权限配置。

回滚不是一个开关：只增加字段阶段通常易回退；新币种数据产生后，旧程序无法解释便不可直接恢复旧二进制；删除旧列后更不能靠重发旧包恢复。应优先关闭新入口、让兼容新数据的版本继续服务，再修复向前推进。迁移评审必须写清每阶段可回滚的程序版本、数据条件和恢复动作。

## 六、弃用：有证据的生命周期管理

### 6.1 Deprecation 与 Sunset 不相同

Deprecation（弃用）表示不建议新增依赖并要求准备迁移，Sunset（停止服务预告）表示资源预计何时不再响应。RFC 9745 定义 Deprecation 为结构化日期，RFC 8594 的 Sunset 使用 HTTP-date；不要把两者都输出成布尔值或都当 ISO 字符串。

以下仅演示语法，日期是固定教学日期，不是本仓库服务计划：

~~~http
Deprecation: @1688169599
Sunset: Sun, 30 Jun 2030 23:59:59 GMT
Link: <https://developer.example.com/migrations/orders-v2>; rel="deprecation"; type="text/html"
~~~

弃用头本身不改变现有业务语义，也不会强制客户端弹窗或升级。日期与弃用范围必须在政策中说明，Sunset 不应早于 Deprecation。原文的 Header Warning 应具体化为这些生命周期信号；历史 HTTP Warning 字段已被 RFC 9111 废止，不应新建依赖。对于浏览器脚本读取非默认可见响应头的场景，还需正确配置跨域响应头暴露规则并做实际验证。

### 6.2 通知与迁移指南应让消费者能行动

迁移指南要给出旧新请求响应、字段映射、金额及状态差异、错误处理变化、SDK 升级步骤、沙箱和回退限制，而不是一句“请升级到 V2”。提供最小可运行调用示例和验证清单，允许消费者先测试，再预约灰度。SDK 默认版本不能自动跳到最新，否则仅升级依赖也可能改变业务语义。

时间线包括宣布弃用、禁止新接入、迁移验证、停止服务与清理；每个阶段有负责人和延期决策机制。通过开发者门户、合同约定渠道及负责人联系通知活跃消费者，并跟踪已送达、已确认、已验证三种不同状态。文档发布与头部提示只能辅助，不能替代关键客户迁移沟通。

### 6.3 下线门槛与安全例外

使用仪表盘（Usage Dashboard）按消费者和版本观察最后成功时间、关键操作、流量与错误；观察窗口覆盖结算周期、季节性客户端和休眠设备回流。停止服务前做受控演练，例如仅对确认已迁移的租户停止旧写操作，并确保能迅速恢复，不能无通知随机制造生产失败。

当旧版本存在严重授权漏洞，安全优先级可能要求提前限制高风险写入，而保留受控只读能力或提供升级拦截页。决策要有安全负责人、业务负责人和合同评估，明确残余风险；“兼容旧客户端”不意味着继续允许越权。下线后返回可理解、符合既定政策的错误，清理旧路由、文档和凭证范围，同时保留必要审计与迁移记录。

## 七、验证与发布：证明旧客户端仍能完成原业务

### 7.1 四类测试覆盖不同盲区

OpenAPI 兼容性检查比较接口描述，能发现必填字段、类型、路径等结构变化，但发现不了“分变元”这种同类型语义变化。Consumer Contract（消费者契约）测试保存真实消费者依赖的交互及断言，例如旧应用要求 amountMinor 为整数、状态在旧集合内；提供者构建时验证这些交互。它只保护已经写入的断言，不能代替全部业务测试。

旧 Client E2E（End-to-End，端到端）应使用保留的旧安装包或真实旧 SDK 二进制，走登录、下单、查询、失败和重试，而不是用新代码模拟旧版本。序列化配置、错误分支和升级后的本地缓存都可能与新客户端不同。

生产请求回放（Replay）发现真实字段组合与边缘输入，但不能在生产直接回放支付、发货等写操作。先脱敏，在隔离数据和隔离外部依赖中回放，或只计算无副作用的差异。只回放请求还不够：比较响应语义与副作用计划，并验证旧客户端消费新响应；生产录制中没出现的极端输入仍需人工构造。

### 7.2 最小验证矩阵与失败判定

| 组合或故障 | 断言与原因 |
| --- | --- |
| 旧客户端→新服务端 | 旧字段、默认行为、错误及副作用保持承诺 |
| 新客户端→滚动中的旧实例 | 新能力在全量支持前不开放，不能被忽略后伪成功 |
| 新响应→严格旧解析器 | 新字段、枚举、null 和数值范围不导致崩溃 |
| 同键 V1/V2 并发重试 | 一个业务订单；同键不同内容返回冲突 |
| 回填与在线写并发 | 条件更新不覆盖新值，重试仍收敛 |
| 版本头经网关和缓存 | 响应不会串版本，敏感数据不会串用户 |
| 关闭开关或回滚 | 已有新数据仍可读，未完成业务不会丢失 |

契约样本应来自受支持版本清单并持续更新，不能只保留一个“最老”和一个“最新”就忽略中间版本已知缺陷。每次故障修复增加对应回归样本，形成维护成本可见的支持集合。

### 7.3 Canary 指标与停止条件

Canary（小流量灰度）逐步向稳定消费者组开放新版本。按契约版本看成功率、反序列化失败、业务拒绝、延迟与重复订单，再看全局指标；新版本占比很小时，全局平均值会掩盖问题。客户端崩溃和错误展示需要客户端遥测或受控测试辅助，服务端 200 率看不出来。

发布前写下停止条件，例如出现无法解释的金额差异或重复业务效果立即关闭新入口并调查；具体阈值来自服务目标和风险预算，不能照搬固定百分比。纯读操作可影子执行并比较，写操作只执行一次，另一实现只能计算计划或在隔离环境运行。回滚后对已产生事实做对账，不能认为路由切回就已修复错误订单。

### 7.4 本章验证范围

本章金额适配函数已在本次编写中用 Python 标准库执行正常、错误与跨版本等价测试，检查结果见任务进度。该模型只证明列出的确定性规则，不证明真实 Java 序列化、HTTP 网关、CDN、数据库事务或移动应用兼容。生产验收必须补上上述矩阵中的集成与故障测试；文中的发布和迁移步骤是待工程实现的方案，不是已完成的线上实验。

## 八、完整面试回答与深入追问

### 8.1 主问题：多年不升级的客户端，API 如何演进？

**示例回答：**“我先建立受支持消费者清单，区分应用版本与 API 契约版本，并用请求日志、真实旧客户端测试和消费者确认识别实际依赖。兼容性不只看字段，还看金额单位、默认值、状态机、错误与重试。能证明安全的可选扩展留在原版本；金额表示或业务语义不兼容时提供显式新契约，旧新边界适配到共享领域能力，避免复制整套业务。服务端先支持新旧格式，再回填和验证数据，最后开放客户端能力。发布按消费者灰度，按版本观察错误和副作用；弃用有迁移指南、SDK、负责人、使用证据和停止服务门槛。我的回滚设计会保留解释新数据的能力，不把关开关当作撤销已发生交易。”

这段回答的推理顺序是消费者约束决定兼容承诺，语义判断决定是否分版，边界与迁移保证共存，验证与下线控制长期成本。它给出可执行决策，不依赖报出一串工具名称。

**追问：为什么不永远保留 V1？** 保留有适配测试、漏洞修复、运维和认知成本，也可能阻碍新业务表达；但成本高不是随意违约的理由。应明确支持政策、禁止新接入旧版、投入迁移支持，并用活跃消费者及业务风险决定收缩时机。

### 8.2 追问：新增字段为什么也会破坏？

**回答：**“请求新增可选字段只有在缺席时旧语义保持才兼容；响应新增字段还要确认旧解析器不拒绝未知字段。滚动发布中，旧服务端可能忽略新字段造成伪成功，所以我会先全量升级服务端，再开放发送该字段的客户端。金额和授权字段尤其不能依赖默默忽略。”

**再追问：服务器能否忽略所有未知请求字段？** 不能统一决定。查询扩展可能可容忍，资金命令的拼写错误应暴露；策略必须事先写入契约并验证真实旧请求，不能突然收紧历史接口。

### 8.3 追问：V1 无法表达新内部状态怎么办？

**回答：**“先判断是否存在语义准确的旧状态投影。若旧 PENDING 承诺可取消，而新状态不可取消，映射就不成立。我会让旧客户端继续使用它能表达的业务子集，在入口阻止进入新流程，或通过新契约呈现新能力。UNKNOWN 只适用于提前支持该兜底的客户端，不能修复已经部署的穷尽枚举解析器。”

**再追问：这样会不会损失业务？** 会，所以要比较保留旧流程、提示升级、人工处理或延迟新功能的成本。正确边界是避免误导性成功和错误资金动作，而不是保证任何旧客户端都能使用未来全部功能。

### 8.4 追问：OpenAPI 检查通过可以直接发布吗？

**回答：**“不可以。它检查声明结构，无法证明客户端实际解析行为、金额单位或重试副作用。我会加入消费者契约、真实旧客户端 E2E、脱敏隔离回放和版本灰度。特别测试混合服务实例、未知枚举、默认值、跨版本幂等和缓存分区。”

**再追问：没有全部消费者契约怎么办？** 先登记关键消费者、保留可获得的旧 SDK 和样本，限制高风险变化，逐步补齐覆盖并承认残余风险。没有观测证据时不能把零投诉当作兼容证明。

## 九、扫雷自测：完整答案与推理

### 9.1 amount 从整数分改成整数元，字段名和类型不变，兼容吗？

不兼容。调用者依据旧单位解释数值，类型检查不会发现一百倍偏差。应保留旧字段单位，通过新字段或新版本引入新表示，并在边界精确转换。不能只改文档后继续使用同名同类型字段。

### 9.2 可选 currency 的默认值从 CNY 改成 USD，旧请求不传，有问题吗？

有。旧请求仍通过校验但业务效果变了，可能造成错误计价和结算。应冻结旧版本缺省语义，新能力要求显式币种；null 与缺失分别规定，避免“默认值”掩盖上游缺陷。

### 9.3 客户端不认识退款中状态，统一按已支付展示可以吗？

只有旧“已支付”的完整语义仍准确才可能成立；如果它还暗示可立即发货或不在退款中，映射会误导操作。应审查状态对应的动作和承诺，必要时限制旧客户端参与新流程。未知展示兜底也不能自动授予操作权限。

### 9.4 V1 超时后用户升级，用同幂等键调用 V2，为什么仍重复下单？

可能去重键按版本分区，或者请求指纹直接比较外部 JSON，把 1234 分与 12.34 元当成不同业务。若产品允许跨版本续试，应在消费者和业务操作范围内共用幂等身份，先规范化命令再比较，并用事务与唯一约束保证并发唯一性。

### 9.5 回填时直接覆盖 currency=CNY，为什么危险？

在线写入可能已经保存合法的新币种或更新数据；无条件回填会覆盖事实。只处理可证明属于旧 CNY 合同且仍缺币种的记录，使用条件更新或版本保护，冲突后重读。完成还需检查旧写入者是否继续制造缺值。

### 9.6 文档写了 default，为什么服务端仍拒绝缺字段？

Schema 注解不自动实现接收行为；校验器、生成器与实际业务代码可能不一致。应同时检查 required、可空性、代码缺省路径和测试样本，让声明与运行行为一致，不能靠文档弥补缺失逻辑。

### 9.7 同 URI 用版本请求头，灰度少量用户就安全了吗？

不一定。共享缓存若没按选择头分区，会把少量新响应传播给其他客户端。必须验证 Vary、CDN 缓存键、头部透传和敏感响应策略；灰度分流与缓存正确性是两个不同问题。

### 9.8 旧版一周没有流量，可以删除吗？

不能只凭一周判断。检查日志是否完整、是否有月度结算、休眠回流、离线设备及合同承诺，再确认通知和迁移结果。下线门槛应覆盖实际业务周期，并有可执行恢复方案；不是永远不能删，而是删除必须有证据。

### 9.9 关闭新版本开关，就能回滚数据库和已发订单吗？

不能。开关只控制未来入口，已经写入的新格式、任务与订单仍存在。回滚程序必须能解释这些数据，否则只能保持兼容版本并向前修复。业务副作用要逐项对账、补偿或人工处理，不可用旧包发布替代。

### 9.10 生产请求回放没有差异，为什么还需要旧客户端测试？

回放验证的通常是服务端接收与生成结果，未证明旧客户端能反序列化、展示或正确响应错误；录制样本也不覆盖未发生输入。真实旧客户端测试与构造边界样本弥补这些盲区，写请求还必须隔离副作用，防止验证过程产生真实交易。

## 十、速记与来源

速记顺序：**先识别消费者与承诺 → 分请求/响应判断结构和语义 → 决定局部兼容、能力协商或显式新契约 → 边界适配共享业务 → 先服务端后客户端、先扩展后收缩 → 按版本验证 → 有证据弃用。**

面试最关键的四个反例是：新增枚举不一定安全，default 不自动执行，版本号不解决数据与幂等，关闭开关不撤销业务事实。能解释这些失败路径，比单纯回答“新增 /v2”更能体现架构判断。

以下来源用于核验，不替代正文。规范事实以所列版本为边界；具体客户端生成器、数据库和缓存产品仍需验证自身配置：

- [OpenAPI Specification 3.1.1](https://spec.openapis.org/oas/v3.1.1.html)：Schema、required、类型与 default；与 3.0 的可空表达需区别。
- [RFC 9745：Deprecation HTTP Response Header（2025）](https://www.rfc-editor.org/rfc/rfc9745.html)：弃用日期、作用范围、deprecation 链接及与 Sunset 的关系。
- [RFC 8594：Sunset HTTP Header（2019，Informational）](https://www.rfc-editor.org/rfc/rfc8594.html)：预计停止响应的时间与 HTTP-date 语法。
- [RFC 9111：HTTP Caching（2022）](https://www.rfc-editor.org/rfc/rfc9111.html)：缓存匹配、Vary 与旧 Warning 字段的废止。
