# 01. 设计一个高并发订单服务

> 本章是一份可以直接用于系统设计面试的完整推演。场景、规模、时限和成本均为虚构教学假设，不代表用户经历或性能基准。SQL按PostgreSQL 17解释，消息边界按Kafka 4.1核验；支付授权、扣款及退款能力必须以实际供应商和支付方式契约为准。

## 一、需求澄清：先定义订单成功，再讨论QPS

### 1.1 面试开始应该问什么

订单服务并非仅把购物车存入数据库。先确认是普通电商、限量抢购、订阅还是高价值采购；是否允许部分商品成功、何时锁定价格、库存是否跨仓、支付是先授权后扣款还是直接扣款、未付款多久取消。每个答案都会改变事务和状态机。

峰值每秒请求数（Peak QPS）应分清商品浏览、创建订单、查询、支付回调和重复重试。商品数与分布也重要：一百万商品均匀写入，与十万请求争抢一个SKU是不同瓶颈。还要问服务等级协议（SLA）、内部目标（SLO）、Region范围、数据保留、隐私要求、故障恢复目标，以及是否允许超卖。

本章选择：单Region、多可用区（Multi-AZ）；普通商品与热点商品并存；不允许库存为负；创建订单可先返回“已接收”，支付和库存确认异步收敛；不允许伪造支付成功；通知与推荐不决定订单成功。跨Region主动多写作为后续演进，不能在不讨论一致性成本时默认提供。

### 1.2 四个不变量及其验证位置

不变量（Invariant）是在并发、重试和恢复后仍必须成立的业务规则：

| 不变量 | 本章的具体含义 | 主要保证位置 |
| --- | --- | --- |
| 订单唯一 | 同一租户同一创建操作只对应一个订单 | 持久唯一键与本地事务 |
| 金额可追溯 | 金额来自服务端规则，保留报价/税费/优惠与币种快照 | 订单明细、金额校验和审计 |
| 库存不为负 | 可分配库存不能被并发扣成负数 | 库存权威端条件更新与预留事务 |
| 支付不重复 | 同一支付业务操作不得产生重复扣款效果 | 支付操作号、供应商幂等与对账 |

“同一创建操作”不等于“相同商品内容”：用户真的购买两次应创建两单；同一次操作因响应丢失重试则复用同一幂等键。HTTP方法、Redis锁或Kafka去重都不能单独证明四个不变量全部成立。

## 二、容量估算：把应用并发与热点串行分开

### 2.1 一组可检验的教学假设

假设每日100万订单，平均创建约1,000,000/86,400=11.6单/秒；活动峰值创建2,000单/秒、订单查询10,000次/秒、商品浏览50,000次/秒。峰值不是从平均值凭空保证出来，而是需求输入，必须确认持续时间及热点比例。

若创建入口平均停留100ms、稳定接收2,000次/秒，Little定律估算平均在途约200；若改为同步等待支付2秒，同样流量下平均在途约4,000。这是稳定统计的平均数量级，不是线程数或P99容量的直接配置。异步状态机能减少入口等待，但后台工作和持久积压仍需有界治理。

假设订单头与明细平均逻辑数据4KiB，每天约3.81GiB，30天约114.4GiB；索引、WAL、Outbox、审计、备份、副本和存储碎片另计。不能只算JSON大小就声称数据库容量足够，也不能把每天平均IO当作活动峰值写入能力。

### 2.2 从资源预算反推扩容边界

如果数据库给订单应用的连接预算240条，发布时最大40个Pod，每池最多6条才满足连接数量约束；还要为批处理、维护、其他服务及故障切换预留额外预算。应用扩容不会自动增加数据库CPU、日志带宽或热点行并行度。

压测要覆盖真实商品倾斜、支付慢、重复操作和连接持有时间，不能只用随机订单ID制造无冲突吞吐。安全容量以成功吞吐、尾延迟、拒绝和恢复能力共同决定，并用失去一个可用区后的容量验证Multi-AZ是否真正有余量。

## 三、架构：明确谁拥有数据和事务

~~~mermaid
flowchart TD
  C["客户端"] --> G["网关与准入"]
  G --> O["订单应用"]
  O --> D["订单库与Outbox"]
  O --> I["库存权威端"]
  O --> P["支付适配层"]
  D --> R["发布器"]
  R --> K["Kafka"]
  K --> F["履约与通知"]
~~~

### 3.1 各组件职责和同步边界

网关负责认证、请求大小、租户/用户配额及流量治理，但领域授权仍在应用完成。订单应用无状态，实例不保存唯一流程进度；持久订单、操作结果、Saga步骤和待发送事件存在数据库，因此任一实例都能恢复处理。

库存权威端（Source of Truth）负责可用数量和预留生命周期；支付适配层负责把内部稳定操作号映射到供应商请求、查询、回调与退款。订单数据库只拥有订单本地事务，不声称与远程库存、支付和Kafka一次原子提交。

初期可以采用模块化单体，让订单与库存模块在同一数据库事务内维护，减少分布式复杂度。只有独立扩展、团队边界或库存多渠道共享等需求充分时才拆服务。本图按已分离权威服务推演，不能把“高并发”当成必须微服务的理由。

### 3.2 Multi-AZ和Region的含义

应用跨AZ部署，负载均衡避开故障实例，数据库与消息系统选择适当的跨区复制和故障切换方案。同步复制提高某些故障下的持久性，却增加提交延迟和成本；异步副本可能落后，切换后能否丢失已确认订单取决于实际复制与确认策略。

单Region多AZ不等于跨Region灾备。明确恢复时间目标（RTO）和可接受数据丢失目标（RPO），定期演练恢复、DNS/路由切换、密钥与供应商可用性。若跨Region同时写同一SKU，需要一个权威主区域、库存配额划分或可满足业务要求的协调存储；不应依赖最终一致的两个计数器各自承诺不超卖。

## 四、API、价格和订单数据模型

### 4.1 创建与查询契约

创建入口接收商品ID、数量、配送选项和必要的报价/优惠凭证，金额由服务端重新验证计算。客户端显示价格可能过期，服务端应按业务契约返回新的报价并让用户确认，不能悄悄提高已授权付款金额。

~~~http
POST /orders
Idempotency-Key: demo-create-7
Content-Type: application/json

{"items":[{"sku":"demo-sku-1","quantity":2}],"quote_id":"demo-quote-3"}
~~~

应用先做认证、对象/租户授权、数量上限与数据校验，再校验报价和幂等指纹，最终短事务提交订单与Outbox。异步接收可返回：

~~~http
HTTP/1.1 202 Accepted
Location: /orders/demo-order-7

{"order_id":"demo-order-7","status":"PENDING","status_url":"/orders/demo-order-7"}
~~~

202不表示已付款或已保证库存，只表示可靠接受处理。若契约是创建订单资源本身已完成，也可返回201并明确其PENDING业务状态，二者选择要一致。客户端超时后用同键恢复或查询，不重新生成键创建重复订单。

查询必须检查用户对订单的权限；分页使用稳定排序与游标，不能把订单ID难以猜测当作授权。读模型有延迟时，刚创建的订单应从权威库读或携带版本等待投影追上，等待超时则显示处理中，而不是误报订单不存在。

### 4.2 金额快照和业务状态

订单明细保存SKU、名称/规格、单价、数量、折扣、税费、币种及规则/报价版本快照，使后续商品改价不会改变历史订单。金额使用定义明确的最小货币单位整数或精确十进制；币种的小数位和舍入规则需要显式配置，不能假设所有货币都两位小数。

订单状态与支付、库存状态分开。例如订单PENDING/CONFIRMED/CANCEL_PENDING/CANCELLED，支付NONE/AUTHORIZED/CAPTURE_PENDING/CAPTURED/UNKNOWN/REFUND_PENDING/REFUNDED，库存NONE/RESERVED/COMMITTED/RELEASED。避免一个status字段试图表达所有组合，导致“已取消但退款未完成”无法表示。

状态转换需有前置条件和版本。订单CONFIRMED至少满足本章选定的库存已承诺、支付已扣款事实；取消请求不立即等于资金已退。事件携带订单版本，消费者不能用迟到PENDING覆盖CONFIRMED；退款作为后续独立事实不能因“已成功终态不可改”而被忽略。

### 4.3 本地核心DDL与索引起点

以下是PostgreSQL 17教学DDL的最小核心，不含所有金额明细、Outbox与Saga表实现；实际系统需补外键、权限、审计和保留设计。

~~~sql
CREATE TABLE orders (
    tenant_id text NOT NULL,
    order_id text NOT NULL,
    buyer_id text NOT NULL,
    create_key text NOT NULL,
    request_fingerprint text NOT NULL,
    status text NOT NULL,
    amount_minor bigint NOT NULL CHECK (amount_minor >= 0),
    currency text NOT NULL,
    version bigint NOT NULL DEFAULT 0,
    created_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (tenant_id, order_id),
    UNIQUE (tenant_id, create_key)
);
CREATE INDEX orders_buyer_created
ON orders (tenant_id, buyer_id, created_at DESC, order_id DESC);
~~~

唯一键由数据库协调并发创建，不能用“先查不存在再插入”代替。相同键读取原指纹，相同命令返回原订单，不同命令拒绝冲突。更完整的操作结果表可保存处理状态与响应，保留期须覆盖客户端和灾备重放；删除短期缓存后仍由业务唯一约束保护。

买家订单列表索引匹配租户、买家和时间排序。其他索引根据真实查询与执行计划添加；每个索引都增加写放大与存储。按时间分区/归档可降低历史维护成本，但PostgreSQL分区表的唯一约束受分区键限制，不能为了归档破坏全局创建键唯一性；可保留独立未按时间分区的幂等登记表或重新设计路由和键约束。

## 五、库存预留：并发正确性与生命周期

### 5.1 条件更新为什么能阻止超卖

库存保存available可分配量，预留时在同一事务内创建唯一reservation并扣减可用量：

~~~sql
UPDATE inventory
SET available = available - :quantity
WHERE tenant_id = :tenant
  AND sku = :sku
  AND available >= :quantity
RETURNING available;
~~~

quantity必须先验证为正，inventory也应有available>=0约束和租户SKU唯一键。PostgreSQL Read Committed下同一行并发更新会协调锁和重新检查更新条件；若最后一件已被其他事务扣走，后续更新条件不成立返回零行。不能在应用读取available=1后无条件写回0，因为多个请求都可能认为自己买到了最后一件。

业务算法必须把reservation唯一插入、条件扣减和状态一起提交，重复reservation返回原结果，不再次扣库存；扣减失败时回滚新预留记录。多SKU若要求整单预留，在同一库存事务按稳定SKU顺序操作，任一不足则整体回滚；稳定顺序减少死锁但不保证所有死锁消失，死锁受害者需重试整个幂等事务。

### 5.2 Confirm、Release和超时竞争

预留有reservationId、数量、状态、expiresAt和版本。确认时仅把RESERVED转为COMMITTED，可用量已在预留时减少，不重复扣；释放时仅允许RESERVED转RELEASED，且同一事务把数量加回。条件状态转换保证重复释放不会增加两次库存。

过期扫描与支付成功确认可能并发，双方在库存权威端竞争同一状态转换。若过期释放先成功，迟到确认必须失败，订单不能当作仍有库存；此时根据业务尝试重新预留或取消授权/退款。若确认先成功，过期任务不得释放已承诺库存。不能仅在订单服务比较本地时间就决定库存事实。

取消消息可能先于预留消息到达，可保存取消墓碑或操作状态，使迟到预留被拒绝，避免取消后重新占库存。墓碑保留需覆盖重放范围。租约接管也需要版本保护，本地分布式锁过期不能自动阻止旧工作者继续写入。

### 5.3 热点SKU不是多加分区就能并行

普通商品可以使用数据库条件更新；单个热点SKU仍会在权威计数或状态上串行争用。按商品分区的队列可把同一SKU的处理顺序化、减少数据库锁竞争，但不能增加一个串行分区本身的处理能力，还会产生排队与接受但未成功的用户体验。

可用准入、等待室、分批放行或把库存预算分成互不重叠的桶提高并行，每桶独立不为负；代价是桶间余量不均、回收与转移复杂、可能“总库存还有但当前桶售罄”。转移配额也要原子或可恢复，不能复制同一库存到多个桶重复售出。

Redis可缓存展示库存或承担明确定义的配额预分配，但若数据库是最终权威，不能让可丢失缓存计数单独证明不超卖。必须解释故障切换丢写、回滚、对账和恢复规则。业务接受少量超卖时可选择更宽松方案，但本章明确不接受，不能偷偷改变前提。

## 六、支付与Saga：把Authorize、Capture、Confirm讲完整

### 6.1 授权不是扣款，取消不是退款

授权（Authorize）为支持的支付方式暂时保留支付能力，扣款（Capture）才发起实际资金获取；授权可能过期，未扣款授权通常走取消/撤销，已扣款则走退款（Refund）。不同支付方式与供应商能力不同，不应把卡授权流程套到所有支付渠道。

本章明确一条主流程：预留库存→授权支付→承诺库存→扣款→确认订单。原来的Reserve→Authorize→Confirm应展开说明“Confirm”到底确认什么，不能在只有授权时就声称已付款。若业务允许下单成功后发货时扣款，也可在授权后进入另一种“已接受但未扣款”状态，但SLO与用户文案要相应改变。

承诺库存后扣款明确失败，可按库存业务支持撤销承诺或取消分配，并取消未扣授权；若扣款已成功却后续流程无法继续，则退款并恢复相应库存。不能将“已承诺库存的撤销”与“释放未确认预留”混为同一无条件操作。

### 6.2 Saga的持久编排和独立幂等

Saga是把跨系统业务拆成各自本地事务，再通过前向恢复或补偿收敛。协调者持久记录每一步命令、状态、版本、deadline和下次恢复时间；进程重启后可接管。每步有稳定操作号，例如order-7/reserve、order-7/authorize、order-7/capture、order-7/refund，重试复用，不把每次HTTP requestId当业务号。

支付服务内部记录金额、币种、供应商操作ID、尝试与结果。供应商幂等保留范围、参数冲突和查询一致性必须确认；本地唯一约束只能保护本地记录，不能让供应商外部效果自动原子化。协调者发送命令后超时，先查询原操作，不能立即换新操作号重扣。

补偿是新的业务动作，退款可能失败且耗时，必须可重试、可审计和人工处理。Saga不提供全局隔离性，其他流程可看到中间状态，应通过状态规则限制发货/取消，而不是只期待一个最终成功事件。

### 6.3 Unknown Outcome、回调与对账

支付超时属于结果未知（Unknown Outcome），可标记UNKNOWN或CAPTURE_PENDING并展示“支付确认中”。查询暂未找到也可能因为供应商最终一致或请求仍在处理，不能立刻证明未扣款。

回调需验证签名、供应商账号、租户映射、金额币种及操作身份；按事件ID去重，按状态版本防乱序。回调可能在同步响应前到达，也可能重复或永久丢失，所以状态查询与周期对账仍必要。不能仅靠客户端跳转页面决定支付成功。

对账比较权威支付流水与本地操作，覆盖晚到数据的重叠窗口；本地UNKNOWN而供应商已扣款时，通过幂等领域命令推进履约或退款，不直接改status绕过事件和不变量。长期卡住的Saga有最老年龄告警和人工队列，不能无限“最终会一致”。

## 七、本地Order + Outbox与消息消费

订单创建短事务同时写Order与Outbox事件；事务提交后发布器轮询或通过CDC读取已提交事件并发Kafka。这样本地成功提交会留下待发事实，避免写库后发消息前崩溃漏发。

发布成功后标记前崩溃仍会重复，所以事件ID稳定，消费者用Processed Event表与业务效果同一本地事务去重，提交后才推进offset。Kafka内部事务能力不自动覆盖外部数据库或发货HTTP调用；外部发货服务还需按稳定发货操作号防重复。

履约与通知异步解耦，通知失败不撤销已成功订单，履约失败则有独立业务状态和恢复策略。事件按订单ID分区可帮助保持单订单顺序，但不提供跨所有订单全局顺序；重试、并行处理与版本缺口仍需判断。消费者并行完成高offset不能越过尚未完成的低offset提交进度。

Outbox、消息与幂等表都要定义保留、重放和清理。无限存储成本高，过早删除又会让灾难恢复重放产生重复副作用。重建搜索/查询投影与重新执行发货命令应分不同入口，避免历史重放再次发货。

## 八、高并发与过载保护：减少关键路径工作

商品详情和非权威展示价格可以缓存，支持TTL、抖动和回源合并，避免热点失效时同时压库；但结算重新校验价格。用户购物车/订单数据缓存需隔离租户与授权，不能因缓存命中绕过权限。缓存不可用时限制回源，不能全量流量直击数据库。

创建、支付、库存和查询分别设置合理并发/池与队列边界，关键交易与批处理分舱隔离。线程池大于数据库池不一定有用，多余线程可能只是等待连接；虚拟线程降低等待线程成本，但不能增加数据库和供应商配额。

入口限速与限并发共同使用：相同QPS在下游从20ms变成2秒后，所需在途量约放大100倍。队列有条数、字节和最老年龄上限；超出业务deadline的请求尽早拒绝，以429或503表达真实原因。已接收持久任务与尚未接收请求不能使用同样成功承诺。

所有重试受单次时限、总deadline和额外流量预算限制；永久参数错误和本地熔断拒绝不立即重试。推荐故障可省略或返回允许旧值，不阻断Checkout；支付不能降级为伪成功。数据库索引、分区、分片及归档按执行计划、热点和维护证据演进，不把Kafka+Redis当作吞吐保证。

## 九、故障与恢复矩阵

| 故障 | 用户可见结果 | 系统恢复与边界 |
| --- | --- | --- |
| 创建提交成功但响应丢失 | 客户端暂时不确定 | 同键查询/重试返回原订单 |
| 库存不足 | 明确拒绝或订单失败 | 回滚本地预留，未扣款不退款 |
| 支付授权超时 | 支付确认中 | 查询原授权，不能新号重授权 |
| 库存过期后迟到支付结果 | 中间状态待确认 | 权威确认库存是否仍可承诺，必要时撤销授权/退款 |
| 扣款成功后协调者崩溃 | 订单暂未确认 | 稳定操作号查询，恢复步骤，不再扣款 |
| 消息重复/确认丢失 | 通常不新增业务效果 | Inbox+业务事务，外部服务独立幂等 |
| 通知/推荐失败 | 已成功订单仍有效 | 独立有限重试或降级 |
| Saga补偿永久失败 | 取消/退款处理中 | 持久任务、审计、告警与人工处理 |
| AZ或数据库主节点故障 | 按契约短暂降级 | 路由切换、连接重建、验证已确认数据与UNKNOWN |

恢复也有容量限制。假设积压120,000个任务，新流量800/秒，安全处理1,000/秒，净排空仅200/秒，理想至少600秒。恢复时渐进放量，给新交易、对账和积压明确份额，防止重试、缓存回源、消费者同时恢复再次压垮数据库。

回滚应用前检查Schema和事件兼容性。数据库恢复备份后，订单表、幂等表、Outbox和消费位点必须共同核对；只恢复订单却保留较新offset可能漏处理，恢复旧幂等表却重放历史扣款也可能重复。业务对账是灾备验收的一部分。

## 十、观测、安全、成本与交付演进

订单成功率与P99需定义清楚：入口可靠接受时延和最终确认时延分开统计，失败、拒绝、支付UNKNOWN不能被HTTP 202掩盖。监控库存冲突/预留年龄、支付Pending/Unknown、Outbox最老年龄与Lag、Saga年龄、补偿次数、数据库连接等待、锁等待和Cost/order。

每单成本（Cost/order）应说明分母是创建、确认还是履约完成订单；计算资源、数据库IO存储、消息、遥测和供应商费用分项核算。假设日基础设施成本500欧元、确认10万单，每确认单分摊0.005欧元，不代表含支付手续费或真实采购报价。提高采样、复制和保留都影响成本，不能只看Pod数量。

Trace串起请求、库存、支付和事件，业务操作号连接不同重试/异步Trace。指标标签不放订单ID，日志不输出Token、卡号和不必要个人信息。付款通过合适的供应商令牌化接口处理，订单服务避免保存原始卡数据；回调验签、重放保护和租户对象授权同样是架构核心。

初期用模块化单体、关系数据库、短事务和必要异步即可起步；当数据库写、热点或团队耦合被证据确认后，依次考虑读模型、归档/分区、按租户/订单路由分片、库存配额等。分片后跨订单查询、全局幂等键、跨分片事务和迁移复杂度上升，应给出双读验证、回填和回滚计划，而不是一次重写上线。

## 十一、怎样验证这套设计

测试应断言不变量及恢复，而不仅是返回200。最后一件库存并发抢购，只能有一个成功预留；同创建键并发请求仅一单，同键不同内容拒绝；同reservation重复释放不增库存；过期与确认竞争只能一个合法终态；支付成功但响应丢失不能二次扣款；消息重复、乱序和协调者重启仍能收敛。

压测采用接近真实的商品倾斜和开放到达率，区分发出量、接收量、完成量与拒绝，覆盖冷缓存、数据库慢、供应商限流和失去AZ。持续过载时队列和内存应有界，停止故障后可在预算内恢复。不能用客户端自身阻塞导致实际发压下降的结果声称服务能承受目标峰值。

容量实验记录环境、版本、数据规模、索引、事务时长与分布；SQL需在PostgreSQL实际并发会话验证，供应商语义需沙箱故障实验。本章本地模型仅验证逻辑状态与算术，不代替真实数据库锁、网络、Kafka交付或支付证明。

## 十二、完整面试回答与深入追问

### 12.1 五分钟架构回答示例

“我会先确认峰值创建和查询、热点商品、库存与支付语义、成功时限和Region。本题假设不超卖、单Region多AZ，可靠接受订单与最终付款确认分开。四个不变量是创建操作唯一、金额可追溯、库存不负、支付不重复。

订单服务无状态，创建用可信租户下稳定幂等键，服务端重算报价并保存快照，短事务写Order与Outbox。库存权威端使用唯一预留号与条件扣减，确认和释放竞争状态转换。支付区分授权与扣款，各步独立幂等；持久Saga推进预留、授权、库存承诺、扣款、订单确认，失败走可恢复补偿，超时先查询原操作。

Outbox异步发布，消费者以本地事务去重，外部履约另有操作号。商品读取缓存，热点库存按实际争用选择顺序队列或不重叠配额；所有池、并发、重试和队列有上限，推荐不影响结算。监控接受和最终成功、P99、Pending、Outbox及Saga年龄，用重复、乱序、响应丢失和AZ故障验证恢复。扩分片和跨Region多写要有容量与业务证据，而不是先堆组件。”

追问“哪里是事务边界？”答：Order+Outbox在订单库事务，reservation+库存变化在库存库事务，支付操作记录在支付本地边界；外部支付不在前两者本地事务中，依赖供应商幂等与对账，Saga仅提供业务收敛。

### 12.2 “如何保证最后一件不卖给两个人？”

回答：库存权威端用available>=quantity的原子条件更新和非负约束，同一预留号唯一，扣减与预留状态同事务。不能先查再写或仅看缓存。确认、过期与释放也按状态条件原子竞争，重复释放不重复加库存。

追问“单行写锁成为瓶颈？”答：先做热点准入与有限队列，必要时把可售额度分成不重叠桶提高并行，接受余量不均与转移治理成本。按商品分区的队列可减竞争，但单商品仍串行，不能只增加分区数就声称解决。

### 12.3 “支付超时，订单能否直接取消？”

回答：可以发起取消意图，但不能把超时当未付款。持久记录UNKNOWN并查询原操作，结合验签回调和对账确定资金事实；库存可能已过期，要权威确认能否继续履约。若已经扣款却无法履约，发起稳定退款操作，退款失败留待恢复与人工处理。

追问“换供应商扣款能提高成功率吗？”答：原供应商结果未知时可能两边都成功，不能直接切换写副作用。先恢复原状态或有明确跨供应商业务去重与资金处置契约。

### 12.4 “为什么不把所有步骤放一个事务？”

回答：同库短事务能提供原子性，应能用则用；但独立库存库、支付HTTP和Kafka不自动参加同一本地事务。跨网络持锁会耗尽连接并放大故障，且无法凭注解原子回滚供应商扣款。要么选择业务可接受的持久流程与补偿，要么在确有支持且代价可接受时采用合适的协调事务能力，不能宣称Saga与ACID相同。

追问“SAGA成功后就没有中间态泄露？”答：不是，过程没有全局隔离，查询、发货与取消必须显式理解中间状态并校验前置条件。

## 十三、扫雷自测与推理答案

### 13.1 每日100万订单平均只有约11.6QPS，能按12QPS配置吗？

不能，活动峰值、持续时间、重试和热点分布决定容量。本章2,000峰值是额外需求输入，平均值仅用于数量级和存储估算；还要测试故障余量与尾延迟。

### 13.2 两个请求同SKU同数量，应该自动合并成一个订单吗？

不应按内容猜用户意图。两个独立购买操作用不同键，同一操作重试用相同键；指纹负责防同键异义，数据库唯一约束负责并发防重。

### 13.3 已授权支付，是否订单已付款？

不一定。授权与Capture不同，授权会过期且能力依支付方式而异。本章CONFIRMED要求扣款事实，若产品选择授权后接受订单，需明确状态与后续扣款策略。

### 13.4 预留已扣available，确认时是否再扣一次？

不能再扣。确认只是将预留转为承诺；释放只对仍RESERVED状态加回一次。库存模型要区分可用、预留与已承诺，避免双扣或双加。

### 13.5 过期释放先成功，支付稍后成功回调能直接确认订单吗？

不能，库存已不属于该预留。查询资金事实并尝试重新获得库存或按业务取消/退款；迟到回调不能绕过库存前置条件。

### 13.6 Outbox能保证消息从不重复吗？

不能。发送成功但标记前崩溃会重复发送。Outbox解决本地提交和待发事实原子性，稳定事件ID、消费者本地事务去重和外部操作幂等仍必要。

### 13.7 40Pod各池20，数据库只给240连接预算，扩容有何风险？

潜在800连接超预算，会增加数据库竞争。每池6才满足该数量上限，且还要验证实际查询能力、发布峰值和其他连接；数量合规不自动等于性能达标。

### 13.8 队列分区从10增到100，单一热SKU吞吐是否必增10倍？

不是，同SKU若仍路由同一权威串行路径，瓶颈没变。需减少进入热点的请求、优化事务，或采用不重叠配额并承担库存利用率与治理代价。

### 13.9 积压120,000，新流量800/s，处理1,000/s，为什么不是120秒排完？

新流量消耗800/s，净排空仅200/s，理想600秒；重试和故障会更久。恢复放量必须看净余量，不能无限加消费者。

### 13.10 查询缓存显示有货，结算权威更新零行，是系统错误吗？

不必然。展示允许陈旧，权威扣减才作承诺。应返回明确库存不足并更新体验，不能为了维持展示结果绕过条件扣减。

## 十四、速记、来源与验证边界

面试重点是把容量、业务语义与故障恢复连接起来：创建唯一靠持久身份，金额追溯靠服务端快照，库存不负靠权威端事务，支付不重靠稳定操作与外部恢复；异步解耦减少等待，却增加中间态、重放和对账责任。

本次SQL/HTTP为教学示例，未运行真实数据库、Java服务、Kafka或支付沙箱；Python本地模型验证了预留/释放/确认幂等与竞争终态及容量算术，不代表数据库并发或实测吞吐。来源核验于2026-11-16，支付供应商示例只用于核对授权与扣款区别，不假设所有渠道窗口相同。

- [PostgreSQL 17事务隔离](https://www.postgresql.org/docs/17/transaction-iso.html)：条件更新与Read Committed并发行为。
- [PostgreSQL 17 INSERT](https://www.postgresql.org/docs/17/sql-insert.html)：唯一冲突与ON CONFLICT边界。
- [PostgreSQL 17分区限制](https://www.postgresql.org/docs/17/ddl-partitioning.html#DDL-PARTITIONING-DECLARATIVE-LIMITATIONS)：分区与唯一性设计。
- [Kafka 4.1设计](https://kafka.apache.org/41/design/design/)：消息交付和事务保证范围。
- [Stripe：分别授权与Capture](https://docs.stripe.com/payments/place-a-hold-on-a-payment-method)：支付方式支持、授权有效期与扣款区别，实际集成以供应商版本契约为准。
