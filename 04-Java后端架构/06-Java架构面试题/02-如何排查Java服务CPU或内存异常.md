# 02. 如何排查 Java 服务 CPU 或内存异常

> 本章按“用户影响→资源分类→低影响证据→验证假设→缓解与复测”推演。命令以Linux、HotSpot JDK 21为基线，cgroup文件限定v2；实际JDK发行版、容器命名空间、权限和Profiler版本要先核对。案例及数值均为虚构教学假设，不是用户经历或实测结论。

## 一、先确认影响：异常数值不是根因

### 1.1 建立症状与变更时间线

先确认服务等级目标（SLO）、延迟（Latency）、错误（Error）、流量（Traffic）和成功吞吐，按Version、Region/AZ、路由与实例分段。CPU从30%到80%同时吞吐增长三倍可能是正常利用；CPU下降但请求大量超时可能是被限额或等待依赖。内存涨到较高水平也可能是JVM正常利用已提交堆，不能直接判泄漏。

记录开始时间、发布/配置、请求大小、缓存冷暖、定时任务与依赖变化。对比相同负载下旧版与新版、健康与异常实例；若只影响一台，还需检查宿主机噪声（Host Noise）、磁盘、网络和容器限制，而不是立刻修改全站JVM参数。

先明确故障风险：是否濒临容器OOM、是否有持续数据损坏、是否影响支付结果。可先限流、暂停非关键任务、隔离或逐实例回滚，让剩余实例承载安全流量，再采集证据。重启可以止损，但会销毁现场，不能作为最终解释。

### 1.2 CPU、Load与配额的口径

CPU占用表示某段时间消耗的处理器时间，可能按单核100%或整机总容量归一化。假设进程10秒内累计消耗18秒CPU，平均使用1.8核；在2核配额下约90%，在8核整机视角只有22.5%。没有分母就无法比较看板和top。

Linux Load Average不等于CPU百分比，包含可运行及某些不可中断等待任务的平均数量；I/O堵塞时Load高也可能CPU不高。线程数同样不等于可运行线程数，几千个等待线程与几千个忙循环线程的影响不同。

容器CPU带宽限制（Throttling）意味着有可运行工作却暂时不能被调度。cgroup v2的cpu.max若为200000 100000，表示每100ms最多可用200ms CPU时间，约等于2核带宽；并不是固定绑在两颗物理核。检查cpu.stat在相同窗口的usage、nr_periods、nr_throttled与throttled_usec增量，并看祖先限制、CPU压力和尾延迟；节流周期比例不能直接等同“损失的CPU百分比”。

## 二、先用什么证据：由低影响到高影响

### 2.1 建立最小现场包

保留实例/容器ID、部署版本、JDK版本、GC类型、堆设置、资源request/limit、进程启动时间、负载与错误窗口。随后收集CPU/内存/GC/线程/队列的同时间曲线、一段有时限JFR、必要的重复线程栈，以及脱敏的请求/错误类别。

命令中的4242只是示例PID，执行前必须替换并确认目标，避免对错误实例操作。容器内PID与宿主机PID可能不同；jcmd通常要求同机及匹配的有效用户/组，Attach机制、PID命名空间或精简镜像也可能使其不可用。先看help，不在事故中盲目下载不明二进制或修改全局权限。

~~~bash
jcmd 4242 help
jcmd 4242 VM.version
jcmd 4242 VM.flags
jcmd 4242 GC.heap_info
jcmd 4242 JFR.check
~~~

这些命令并非全部零成本，输出也可能含配置和内部信息，须受控保存。GC.heap_info只提供堆概况，不解释对象为何被持有。记录采集时刻和采集本身带来的负载，才能与事故指标对齐。

### 2.2 选择正确的Profiler事件

CPU采样回答“线程实际在CPU上运行时主要执行什么”；Wall-clock采样覆盖经过时间，更适合等待、阻塞与排队；Allocation采样找对象分配来源；Lock/阻塞事件帮助定位竞争；GC事件说明回收节奏与暂停。CPU火焰图不能单独证明网络等待在哪里，分配火焰图也不能证明对象长期存活。

JFR（Java Flight Recorder）结合多类事件、栈与时间，可在JDK Mission Control等工具分析；async-profiler可采集不同事件及原生栈，但权限、内核perf限制、平台和版本会影响可用事件。先使用已验证版本及有限时长/文件大小，不能宣称“Profiler永远无停顿且开销固定1%”。

## 三、CPU排查：把高占用分成可推翻的假设

### 3.1 从进程到高CPU线程

Linux可使用以下示例查看线程，1秒一次共5次，避免只看瞬时值：

~~~bash
pidstat -t -p 4242 1 5
top -H -p 4242
jcmd 4242 Thread.print -l
~~~

pidstat来自相应系统工具包，镜像未安装时不应误认为服务异常。将同一PID命名空间中的高CPU线程TID转换十六进制，与传统平台线程dump里的nid匹配。例如十进制2671对应0xa6f。重复采集有限次数，观察是否同一调用链持续出现。

nid映射适用于相关HotSpot平台线程表示，不是所有线程模型的通用身份。虚拟线程会在载体线程上调度，不能把高CPU载体与某一个固定虚拟线程永久绑定；传统线程dump也未必提供需要的完整虚拟线程视图。JDK 21可先查Thread.dump_to_file帮助，再选择其支持的格式与工具，不跨版本照抄。

RUNNABLE不等于正在吃CPU，Java线程处在本地socket读取等情况也可能显示RUNNABLE。必须结合线程CPU增量、采样栈与依赖耗时判断。线程dump只是某一时刻状态，一张图不足以证明循环或死锁持续存在。

### 3.2 采集JFR并正确读火焰图

在已确认存在且有空间、权限的目标目录中，示例命令为：

~~~bash
jcmd 4242 JFR.start name=incident settings=profile duration=60s filename=/secure-diagnostics/incident.jfr
~~~

profile设置通常提供较丰富事件，但比轻量持续记录可能有更多成本。文件路径在目标JVM所在文件系统解释，不能假设是操作终端本地；文件可能包含方法、路径和业务信息。若已有持续记录，先检查再导出合适区间，避免重复启动多份记录增加成本。

火焰图（Flame Graph）的宽度通常代表所选事件的样本权重，纵向代表栈深，横向排列通常不是请求时间线。最宽的上层框可能只是汇总入口，需展开到具体耗时叶子及其调用者，区分自身时间与包含子调用的时间。仅看到某方法宽，不代表优化它必然带来同比端到端收益。

采样有窗口与偏差，稀短事件或缺失原生符号可能看不到，须与请求、GC和系统指标交叉验证。CPU热点集中于日志格式化时，应检查日志量与错误风暴；不能只优化格式化却忽略真正导致错误的下游故障。

### 3.3 常见CPU热点与针对性修复

| 证据模式 | 可能机制 | 如何验证与修复 |
| --- | --- | --- |
| 业务计算栈宽且CPU随输入增长 | 算法复杂度、重复计算 | 用真实规模复现，减少重复工作或更换算法，核对输出一致性 |
| JSON/压缩/编码占比高 | 大响应、重复序列化 | 看载荷大小和分配，减少字段/重复编码，评估压缩率与CPU取舍 |
| Regex栈随特定输入飙升 | 回溯爆炸 | 限制输入长度、重写表达式或选合适算法，加入恶意输入测试 |
| 自旋/CAS循环持续占用 | 竞争、忙等待 | 看争用与重试次数，退避/阻塞协调或减少共享热点 |
| GC线程消耗高 | 分配压力、存活集过大或回收赶不上 | 联合分配率、回收后存活与GC日志，不先乱改收集器 |
| 日志/异常堆栈热点 | 错误风暴、重复打印 | 先修错误来源与重试放大，再限制日志量与重复堆栈 |
| 流量不增而循环次数异常 | 空轮询、错误重试无退避 | 检查失败路径退出条件、阻塞等待和取消处理 |

锁竞争有两种表现：阻塞等待可能CPU低，忙自旋可能CPU高。GC、JIT编译、启动预热也会消耗CPU，不应把所有CPU归到请求业务线程。编译热点若只在启动期出现，要确认是否过度频繁重启或扩缩容造成持续预热。

依赖变慢本来应让调用等待，但错误处理代码可能立即重试、空轮询状态或不断生成异常，形成Busy Loop。限制单次/总体时限、重试次数与额外流量预算，退出取消状态并释放资源。单纯扩容会把更多重试压给依赖。

### 3.4 Throttling与Host Noise如何区分

若服务CPU接近配额、节流增量高、尾延迟同步上升，可能是配额不足或短时突发；先确认应用是否无效耗CPU，再按成本与集群容量调整配额/并发。即使一分钟平均CPU不高，短周期内突发也可能触发带宽限额，需查看更细时间与节流数据。

若同版同流量只有某宿主实例异常，且CPU调度压力、I/O等待或虚拟化steal等宿主指标异常，考虑邻居负载与节点问题。可受控迁移单实例验证，但迁移后好转只是支持该假设，仍应保存节点证据。不要用Host Noise一词替代具体调度或资源争用机制。

## 四、Memory分类：Heap、RSS和容器内存不是同一个数

### 4.1 内存地图与预算

Heap用于Java对象；Metaspace存放类元数据；Direct Buffer和其他native分配在堆外；平台线程栈、JIT Code Cache、GC/JVM内部结构、共享库及映射也占地址空间或物理内存。进程RSS是驻留物理页近似口径，容器memory.current则按cgroup计费，可能还包含其他进程和文件缓存等，不能简单把它们等同。

Reserved是保留虚拟地址空间，Committed是已承诺可用的区域，两者都不必等于RSS实际驻留。看到NMT保留很大地址空间不等于物理内存已经用光；但Heap Used低也不证明容器安全。

容器limit=2GiB、Xmx=1.5GiB，只剩约512MiB留给所有其他计费来源与余量。若Direct峰值256MiB、Metaspace160MiB、线程实际驻留等又增加，就可能在堆未满时被杀。这是教学预算，不是简单相加就能精确预测RSS，应结合实际峰值、共享页和计费口径验证。

### 4.2 Heap Leak与Allocation Pressure

堆泄漏（Heap Leak）指本不应继续存活的对象仍从GC Root可达，回收器不能释放。稳定可比负载下，经过有效回收周期后的存活基线持续上涨，是强线索；但业务缓存预热或数据规模增长也会抬高基线，需要证明对象生命周期不合理。

分配压力（Allocation Pressure）是单位时间大量创建短命对象，Young GC频繁但回收后基线可恢复。大量临时byte[]、字符串拼接、JSON中间树都可能造成此模式。优化应减少不必要分配、控制载荷和复用合适缓冲，而不是把所有对象塞进永久池增加存活集。

“Full GC后仍上涨”是传统诊断表述，不应要求所有收集器都先做手工Full GC。不同GC的并发周期、代际和统计不同，应以实际收集器的有效回收后存活数据比较；强制GC本身可能长停顿并改变现场。高GC CPU既可能是压力，也可能是存活集接近容量，必须看趋势和机制。

### 4.3 Native、Direct、Metaspace和线程栈

Heap稳定而RSS增长时，检查Direct Buffer池、线程数量、类加载与卸载、JNI库、内存映射及分配器行为。Direct Buffer Java包装对象虽在Heap，实际大块数据在堆外，单看byte[]直方图可能漏掉。Cleaner回收时机和库自己的引用计数也会影响释放，不能把“调用System.gc”当生产修复。

Metaspace增长可能来自正常动态类加载，也可能是ClassLoader被旧线程、静态注册表、ThreadLocal或缓存引用而无法卸载。看类/加载器数量、部署周期和保留路径；仅提高MaxMetaspaceSize会延迟复发，限制过低又可能制造新的OOM。

大量平台线程会占用栈地址空间和实际驻留页，线程创建还受进程/系统限制。线程数乘Xss可作为栈保留量数量级，不能直接当实际RSS；虚拟线程栈存储方式不同，不能按每个虚拟线程固定Xss套用。修复无界线程创建、未关闭执行器和过高并发比单改栈大小更可靠。

## 五、Memory排查流程与Heap证据解释

### 5.1 先对齐Heap、GC、RSS和容器事件

在相同时间窗口对比Heap Used/Committed/Max、回收后存活、分配率、GC频次/暂停、RSS、Direct Buffer、Metaspace、平台线程数、容器memory.current/limit/events与重启原因。看趋势和增长斜率，不把一次尖峰当长期泄漏。

先识别错误类型：Java heap space说明堆分配失败，Direct buffer memory指向相关堆外限制，Metaspace说明元数据空间问题，unable to create native thread还可能是线程或系统资源限制。Container OOMKill是外部内存治理终止，JVM可能来不及抛Java OOM和生成dump。exit code 137仅表明常见SIGKILL退出编码，不能单凭它证明内存超限，还需容器终止原因及cgroup/节点证据。

cgroup v2的memory.events可提供oom、oom_kill等计数，memory.stat帮助分解匿名页、文件页等。先定位该进程真实cgroup路径，不假设所有环境固定挂载位置；v1文件名和统计不同，不能混用。应用重启会使某些指标归零，容器/Pod生命周期也影响计数，要保存前后事件。

### 5.2 安全生成Heap Dump

Heap Dump是对象图快照，通常比类直方图更适合分析引用关系，但采集可能高影响、触发回收并产生大型文件。先确认有可替代实例、流量处理能力、磁盘空间、路径权限、输出保留和敏感信息策略，再对一个目标实例操作；不对所有Pod同时dump。

~~~bash
jcmd 4242 help GC.heap_dump
jcmd 4242 GC.heap_dump /secure-diagnostics/heap-incident.hprof
~~~

HotSpot JDK21该命令默认会请求Full GC，除非使用-all等相应选项；-all包含不可达对象，但不等于采集无停顿或低成本。磁盘空间不足可能使采集失败甚至加重事故。GC.class_histogram也可能高影响，不能把它当完全免费的替代方案。

可在启动配置中预先设计受控的OOM dump路径与轮转/传输方案，但外部OOMKill未必触发；目录需在容器重启后仍可取到且不落入公开位置。Dump可能包含密码、Token、个人信息和业务载荷，限制读取、加密传输、记录访问与及时删除。

### 5.3 Shallow、Retained、Dominator与Retainer Path

Shallow Size是对象自身占用，不包含其引用的其他对象；Retained Size近似表示该对象不可达后可一并释放的对象总量。一个很小Map本身不大，却能间接保留大量请求体。不能按最大Shallow对象就断言它是根因。

支配（Dominator）关系表示从GC Roots到对象Y的所有路径都经过X，X支配Y；Dominator Tree帮助找到“谁控制着大块存活集”。Retainer Path或Path to GC Roots则解释对象为什么仍可达，例如静态Map→Entry→订单DTO→大byte[]。两者结合才能从“占用很多”追到“不该持有的生命周期”。

大Retained对象可能是合理缓存，根因需要与容量上限、业务规模和时间比较；共享对象的Retained Size也不能任意相加。分析软/弱引用时说明工具是否排除这些路径，不应把所有可达路径都等价视为强保留。比较两份dump也要考虑负载和采集GC行为差异。

### 5.4 五类高频保留源及工程修复

缓存没有条数/权重/TTL边界，会随唯一Key增长；修复需同时定义淘汰、加载并发和失效，不是只把HashMap换成ConcurrentHashMap。监听器注册后未注销，会使长寿命事件总线保留本应结束的对象；使用明确注册句柄和生命周期关闭。

线程池中的ThreadLocal值若不清理，会被长期线程保留；弱Key不保证值立即释放。应在请求作用域try/finally中remove或恢复原值，并避免将大请求体放入长寿命上下文。ClassLoader泄漏常与重复部署、插件和动态代理类缓存相关，要释放线程、定时器和跨加载器静态注册。

无界Queue保留的是待处理工作及全部关联上下文；下游变慢时队列增长不是传统永久泄漏，却同样能OOM。设置任务数、字节数和等待年龄上限，限流、背压或持久化排队，并验证恢复后能排空。不要只扩大Heap掩盖持续吞吐缺口。

## 六、Native Memory Tracking与堆外盲区

NMT（Native Memory Tracking）追踪HotSpot相关原生内存类别，可按启动参数启用summary或detail。它有开销，通常需启动时开启；未启用时不能期待事故中无重启就补回历史明细。具体命令和可用选项先查目标JDK帮助。

~~~text
启动配置示例（不是对运行中进程直接执行）：
-XX:NativeMemoryTracking=summary
~~~

~~~bash
jcmd 4242 VM.native_memory summary scale=MB
jcmd 4242 VM.native_memory baseline
jcmd 4242 VM.native_memory summary.diff scale=MB
~~~

先保存基线，隔相同负载窗口再看diff，定位Thread、Class、Code、GC或其他类别增长。只看一次总数难以区分启动预热和持续增长。summary不足且需要调用点时，后续受控部署评估detail模式，而非在全量实例盲目增加追踪。

NMT不覆盖所有第三方native库分配，也不等于进程RSS或容器完整计费。若RSS涨而NMT无明显增长，检查本地库、映射、文件缓存、分配器保留/碎片以及统计口径，结合/proc中映射和系统工具；不能直接宣称“肯定是JVM bug”。Direct、JNI和库资源要用对应指标和释放契约验证。

## 七、两个完整事故推演

### 7.1 CPU高：错误路径忙重试

虚构场景：新版本发布后支付依赖间歇失败，QPS未增，CPU从40%升到配额上限，P99和错误率上升。先按版本/区域确认影响，保存短JFR与线程CPU样本；发现业务CPU热点是重试循环、异常构造与日志序列化，GC也增加但回收后Heap稳定。

证据支持“失败后立即循环重试→异常与日志分配→CPU和GC争用”，不是单纯“GC参数错误”。先停止新版扩量、限制重试和非关键任务，核对兼容后回滚；验证真实下游尝试数、CPU、GC与用户成功率恢复。永久修复加入可重试错误分类、deadline、次数/预算、退避抖动、取消退出与日志限量，并做依赖失败测试。

扩容可能暂时分摊CPU，却将更多尝试压到支付端，甚至扩大费用和故障。应把依赖总尝试和成功业务请求分开计量，防止表面吞吐提升来自重复工作。

### 7.2 内存高：慢下游与无界队列

虚构场景：订单Heap回收后基线由600MiB逐步到1.4GiB，队列从几百涨到两万，入队率1,000/s、完成800/s。Dump显示Queue支配大量请求上下文，每个约32KiB；两万项仅载荷就约625MiB，额外包装和执行中任务另计。

这是持续积压导致保留，不必先假设集合库泄漏。每秒净增200项，空队列约100秒就可增长到两万；扩大内存只能延迟失败。先限流、暂停非关键生产、恢复下游，避免把所有积压同时释放；再给队列任务数/字节/年龄设上限和拒绝契约，业务必须可靠接受时改用有容量治理的持久任务系统。

若CPU和Heap恢复但容器仍接近limit，继续检查Direct和线程，而不是把第一个发现当作全部根因。最终验收包括业务恢复、积压排空、回收后基线稳定、堆外余量及再次故障时资源有界。

## 八、缓解、复测与架构演进

回滚适合有明确版本差异且Schema/事件兼容的情况；限流保护关键资源，但拒绝不是业务成功；扩容需确认瓶颈可水平扩展及下游余量；加内存可能适合正常存活集确实增长，但必须保留堆外和容器余量。重启只是有代价的现场清理，可能触发缓存冷启动和重试风暴，应逐实例、渐进恢复。

复测采用相同JDK、资源限制、数据规模、负载和依赖延迟，对比成功吞吐、P99、CPU/请求、分配/请求、回收后存活、RSS、节流、队列和成本。优化CPU却增加无限缓存会把问题转成内存；减小Heap可能减少容器风险却提高GC压力；结论必须包含副作用。

把检查前移：版本基线、有限资源、慢依赖/大输入/长时间Soak测试、持续轻量记录、受控dump路径和可执行Runbook。线上诊断权限按最小范围配置，不暴露未认证JMX等管理入口。采样与数据保留也有成本，选择能稳定运行的方案而不是长期全量采集一切。

## 九、面试完整回答与追问

### 9.1 “CPU 100%怎么查？”

回答：我先确认100%的分母和用户影响，按版本、实例和区域比较，区分实际CPU、GC、cgroup节流与宿主争用。查看流量、线程和GC后，用有限时长JFR或CPU采样定位热点，并以高CPU线程增量和重复dump对应调用链。再判断业务计算、序列化、正则、忙自旋、GC还是日志错误风暴。先做可回滚缓解，随后以相同负载验证根因修复，而不是只扩容。

追问“dump都是RUNNABLE是否就是死循环？”答：不是，RUNNABLE可能包括某些本地等待，需要线程CPU增量和采样证明持续执行；虚拟线程还需考虑载体与任务映射。

### 9.2 “Heap不高却OOMKill，为什么？”

回答：Heap只是容器计费的一部分，还可能有Direct、Metaspace、平台线程栈、JVM/native库、映射和文件页，容器内其他进程也可能计费。先核对OOMKill事件而非只看137，再对齐RSS、memory.current/stat、Direct、线程和NMT差分。Xmx不能顶满容器limit，且NMT不能覆盖所有native分配。

追问“没有Heap Dump是否说明不是内存问题？”答：不能，外部SIGKILL可能来不及让JVM抛OOM和写dump，应依赖容器/节点事件、历史曲线和预先配置的诊断。

### 9.3 “怎么区分泄漏与分配太快？”

回答：在可比负载下看有效回收后的存活基线与分配率。基线稳定但Young GC频繁偏向短命分配压力，基线持续增长需要检查缓存预热、队列和异常保留。用Allocation样本找创建来源，用Dump的Dominator和GC Root路径找谁长期持有，二者不能互相替代。

追问“最大的byte[]就是根因？”答：未必，byte[]可能是合理载荷，关键是被谁持有、多久、是否有上限。一个小静态Map或Queue可能支配大量数组，应修生命周期和容量。

### 9.4 “为什么不先加内存再说？”

回答：若业务正常存活集增长，扩容可以是合理容量调整；但泄漏、无界队列或Direct资源未释放只会延迟复发，并增加GC、成本和dump难度。我会先保留最小证据和限制影响，确认增长来源，再选择加内存、减少保留或修队列等方案，并验证容器总余量和长期稳定性。

追问“必须先找到根因才能重启吗？”答：不必，用户损失严重时先按Runbook止损，尽量保留轻量证据并逐实例恢复；重启是缓解，不代表诊断已经完成。

## 十、扫雷自测与推理答案

### 10.1 10秒消耗18秒CPU、配额2核，占用多少？

平均1.8核，配额口径90%；按8核整机则22.5%。看板口径不同可能同时成立，必须确认分母、窗口和是否包含整个容器多个进程。

### 10.2 Load很高是否一定CPU耗尽？

不是，Linux Load包含某些不可中断等待，I/O等问题也可能抬高。检查CPU用户/系统时间、调度压力、节流与I/O，不用Load替代全部资源判断。

### 10.3 2671如何对应平台线程dump？

十六进制为0xa6f，在同PID命名空间和相关HotSpot平台线程表示中匹配nid。不能把这一技巧直接套到固定虚拟线程身份，也要注意采样时间中线程可能退出和ID复用。

### 10.4 CPU火焰图没有数据库等待，能证明数据库不慢吗？

不能，CPU采样主要看在CPU上执行的栈，等待可能被排除。用Wall-clock、Trace、池等待和数据库指标验证，且检查事件设置与采样完整性。

### 10.5 Full GC后Heap高是否足以证明泄漏？

不足，可能是合理缓存、业务存活集或积压。要看长期趋势、生命周期和GC Root路径；不同收集器不应机械要求手工Full GC，强制回收还可能破坏现场。

### 10.6 队列两万项、每项32KiB，载荷多少？

约625MiB：20,000×32KiB/1,024。还未算包装、引用、执行中任务和线程栈。以条数限制但不限制单项大小仍可能失控。

### 10.7 入队1,000/s、完成800/s，多大队列能永久承受？

没有有限队列能永久承受持续差额，每秒净增200项。需要减少到达、提高安全处理能力或拒绝/转持久化，并定义等待时限与容量。

### 10.8 NMT reserved很大是否物理内存已用满？

不一定，reserved是虚拟地址空间，committed与RSS也不同。结合实际驻留和cgroup计费，NMT还不覆盖所有外部分配，不可单看一个总数。

### 10.9 exit 137就等于Java Heap OOM吗？

不是，137常见对应SIGKILL，可能OOMKill也可能其他终止。需要容器终止原因、内核/cgroup事件与堆曲线；Java Heap OOM只是可能的不同故障路径。

### 10.10 Heap Dump使用-all就安全且不暂停吗？

不是，-all改变是否包括不可达对象及默认请求Full GC等行为，不保证无停顿或低成本。采集仍可能高影响、耗大量磁盘并包含敏感数据，要先按目标JDK帮助和运维条件评估。

## 十一、速记、来源与验证边界

CPU先问分母，再分业务/GC/节流/宿主；用正确事件找热点，线程栈只是瞬时证据。内存先分Heap与进程/容器口径，再用分配看创建、对象图看保留、NMT看HotSpot原生类别。先恢复服务，证据验证机制，最后以长期和故障负载复测，避免“重启”“加Heap”成为最终答案。
