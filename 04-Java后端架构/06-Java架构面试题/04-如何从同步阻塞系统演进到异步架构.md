# 04. 如何从同步阻塞系统演进到异步架构

## 不先换技术

建立 Trace，识别同步 Critical Path、慢依赖、峰值与可异步 Side Effect。不是所有调用都适合异步；用户立即需要的授权结果仍需同步。

## 迁移步骤

1. 将通知、Analytics 等非关键动作从 Transaction 中分离。
2. 引入 Outbox，避免 DB/Event Dual Write。
3. 定义 Event Contract、Version 和 Ownership。
4. Consumer 实现 Idempotency、Retry、DLQ。
5. UI/API 显式展示 PENDING/PROCESSING 状态。
6. 建立 Queue Lag、Age、失败与 Reconciliation。

## Contract

Event 表达已发生事实，如 `OrderCreated`，包含稳定 ID、Version、Timestamp 和最小必要数据。不要发布内部 Entity Dump。

## Backpressure

Queue 吸收峰值但不是无限容量。设置 Retention、Producer Limit、Consumer Auto Scaling、Max Retry 和 Poison Message 隔离。

## 双运行

可 Shadow Consumer、比较新旧结果，按 Feature Flag 切流。避免同一 Side Effect 被新旧路径同时执行。

## 代价

Eventual Consistency、乱序、重复、Debug 和运营复杂度。只有当 Decoupling、Peak Absorption 或 Latency 收益明确时才值得。

## 面试亮点

强调渐进式迁移、Outbox、状态变化、幂等和可观测性，而不是简单“加 Kafka”。
