# 04. 如何从同步阻塞系统演进到异步架构

> 本章给出从诊断、契约、可靠接收、消费者到灰度回滚的完整迁移方案。虚构订单通知与报表场景仅用于推演，不是用户经历。Java机制以JDK 21为基线，Spring代理说明限定6.2常见模式，Kafka语义按4.1核验；队列和SDK实际版本需在项目中锁定验证。

## 一、不先换技术：找出用户真正等待的东西

### 1.1 同步、阻塞、异步和持久化是不同维度

同步（Synchronous）指调用者的流程依赖当前操作结果，阻塞（Blocking）指等待期间占住执行线程；异步（Asynchronous）指发起与完成分离，结果通过Future、回调、消息或查询取得。异步不自动表示非阻塞，也不表示可靠持久化。

把同步HTTP调用放到线程池，工作线程仍可能阻塞；返回Future后马上join，入口仍在等待结果；把任务放进进程内Queue后返回成功，进程崩溃可能丢任务。消息队列能跨进程保存工作，但需要持久性、确认、保留和恢复契约，不是换一个方法签名就获得。

非阻塞I/O、响应式编程或虚拟线程可以改善等待资源使用，未必改变业务完成语义。反之，采用持久任务与202状态API，即使工作者内部使用阻塞JDBC，也已经是业务异步流程。先说要解决线程成本、用户时延、削峰还是故障解耦，才能选择正确层次。

### 1.2 用Trace识别Critical Path

关键路径（Critical Path）是决定端到端完成时间的依赖路径。采集入口、数据库、远程调用、队列等待和业务步骤的耗时，区分排队、计算与I/O；并行子调用不能简单相加。按峰值、P99、请求大小、依赖慢和版本分布观察，不只看平均值。

虚构下单流程串行耗时：鉴权20ms、价格/库存校验80ms、本地事务40ms、通知600ms、Analytics60ms，总计800ms。若通知和分析不决定下单成功，可以移出用户等待路径，使关键路径的教学模型降到约140ms；这不是生产性能保证，Outbox写入、网络和实际分布仍有成本。

若真正慢的是必须实时完成的库存决策，异步通知不会修复库存瓶颈。若CPU已饱和，增加线程或消息也不会凭空增加算力。先用证据找到主要贡献，再确定可迁移的副作用（Side Effect）。

### 1.3 哪些事情必须立即决策

认证、授权、租户隔离、请求基本校验及“是否有资格接受此操作”通常必须在可靠接收前完成，不能先接收越权付款，再指望消费者将来拒绝。用户立即需要的风险判断、额度或库存承诺，也不能未经产品契约调整就变成“稍后再说”。

通知、分析、搜索投影等常可延后，但仍需定义重要性：安全通知可能有时限，分析可能不允许重复计费。长报表和导入更适合显式任务API；支付可采用处理中状态，但不是把未知结果伪装为成功。可以异步的是完成时间，不是业务正确性责任。

## 二、选择迁移粒度：先切开非关键副作用

### 2.1 四种方案及其代价

| 方案 | 解决什么 | 主要限制 |
| --- | --- | --- |
| 有界线程池/Future | 同进程并行、隔离阻塞工作 | 重启丢内存任务，线程/队列仍要限额 |
| 虚拟线程或非阻塞I/O | 降低部分等待成本 | 不增加数据库和供应商容量，不自动持久 |
| 数据库持久任务/Outbox工作者 | 可靠接收、可恢复异步流程 | 扫描、认领、重试与表维护责任 |
| Broker消息驱动 | 多消费者解耦、积压与重放 | 事件契约、重复乱序、运维与容量成本 |

简单低吞吐后台任务可以从同库任务表开始，不一定立即部署Kafka。多订阅者、跨团队独立消费和重放需求明确后，Broker更有价值。不要为“异步化”同时重写Web框架、数据库、消息和领域模型，使失败时无法定位或回滚。

### 2.2 第一步：先缩短事务，再移动执行位置

识别事务内的通知、日志外部发送、分析和其他远程副作用。事务持有连接与锁时等邮件服务600ms，会放大连接等待和锁竞争。将它们转为本地待执行事实，与业务一起短事务提交，再由工作者调用外部系统。

不能只是把发送语句移到COMMIT后：进程可能提交后、发送前崩溃。也不能在事务未提交时启动异步线程读同一订单，它可能看不到订单或处理最终回滚的数据。迁移要同时修复提交边界，而非只换线程。

## 三、Outbox：可靠迁移的第一道持久检查点

### 3.1 为什么DB/Event Dual Write会出错

双写（Dual Write）是一次操作写数据库又写消息系统。先写库后发消息存在漏发窗口；先发消息后写库存在“消息已处理但业务回滚”窗口。普通本地事务不自动跨两个独立资源原子提交。

事务发件箱（Transactional Outbox）将业务行和事件行写在同一数据库事务。提交后发布器轮询或用变更数据捕获（CDC）读取已提交事件，发送成功后标记。发送成功但标记前崩溃会重复发送，因此它保证可恢复的待发事实，不保证从不重复。

以下是PostgreSQL风格的概念表，DDL仅示意字段，不是完整发布器实现：

~~~sql
CREATE TABLE outbox_event (
    event_id text PRIMARY KEY,
    aggregate_id text NOT NULL,
    aggregate_version bigint NOT NULL,
    event_type text NOT NULL,
    schema_version integer NOT NULL,
    payload jsonb NOT NULL,
    occurred_at timestamptz NOT NULL,
    published_at timestamptz
);
~~~

实际多租户系统需包含可信tenant字段及访问控制，发布状态、重试与认领信息可单列。主业务与Outbox同事务；eventId生成一次，重发保持不变。发布器不能因为异常就删除待发记录或写“已成功”掩盖故障。

### 3.2 认领、顺序、清理与监控

多个发布器可短事务认领有限批次，再发送；使用租约时旧持有者可能迟到，状态更新要有认领版本保护。不要持有数据库长事务等待Broker网络，具体实现要处理认领到发送间的崩溃与重复。并发分工还可能打乱同一实体顺序，按aggregateId路由并使用版本检查，不能把表自增顺序当全局提交顺序。

轮询易理解但可能增加扫描与数据库负载；CDC可从提交日志读取，却增加位点、连接器和日志保留治理。先验证团队运行能力。清理以已发布、重放需求和审计保留为依据；未发布事件即使很老也不能自动静默删除，应告警并修复。

监控Outbox数量、最老未发布年龄、发布失败、重试与发布吞吐。Broker恢复后有限速排空，避免同时释放全部历史事件压垮消费者。数据库备份恢复与发布位点也要协调，避免漏发或重发不可幂等副作用。

## 四、Event Contract：发布业务事实，不泄露内部实体

### 4.1 Command与Event及最小必要数据

命令（Command）表达希望某个所有者做什么，例如SendOrderConfirmation；事件（Event）表达已发生事实，例如OrderCreated。事件不能在订单事务尚未提交前就宣称已创建，消费者也不能把事件当作任意调用内部方法的授权。

~~~json
{
  "event_id": "demo-event-7",
  "event_type": "OrderCreated",
  "schema_version": 1,
  "aggregate_id": "demo-order-7",
  "aggregate_version": 1,
  "tenant_id": "demo-tenant",
  "occurred_at": "2026-11-17T00:00:00Z",
  "data": {
    "order_id": "demo-order-7",
    "confirmation_destination_ref": "demo-contact-ref"
  }
}
~~~

event_id用于同一次事实重投去重，aggregate_version用于实体顺序，schema_version用于消息结构，三者不是同一个版本。occurred_at有时钟和语义边界，不能直接代替因果版本；若需要测提交到可见延迟，应补充可追踪提交时间口径。

不发布ORM Entity Dump：内部字段、懒加载代理、密码和数据库Schema会意外变成外部契约。只发必要业务数据或受控引用；引用可减少敏感复制，但消费者处理时源数据可能已变化或不可用，历史通知内容若必须反映下单当时事实，应保存足够快照与模板版本。

### 4.2 Version和Ownership如何落地

明确事件生产者负责业务含义与发布契约，消费者负责自身效果与幂等；Schema变更有评审、兼容检查和责任人。增加可选字段通常更容易兼容，但枚举新增、默认值、金额单位或字段语义变化仍可能破坏旧消费者。

先让消费者兼容新旧结构，再发布新事件；破坏性语义可用新事件类型/版本并明确迁移期限。重放历史事件时，决定按原规则还是新规则解释；不能用当前价格和模板无意改写历史事实。

契约测试验证必需字段、类型、未知字段、版本与领域规则；Schema通过不代表业务行为兼容。记录各消费者是否完成迁移，避免生产者删除字段后才发现一个低频月结任务仍依赖它。

## 五、Consumer：幂等、确认、重试与DLQ

### 5.1 本地效果与处理标记一起提交

至少一次交付（At-least-once）允许重复。消费者收到事件后，在本地事务中插入按consumerName/tenant/eventId唯一的处理标记，再更新本地业务，提交后确认消息。失败一起回滚；提交后确认丢失再投递时跳过已完成效果。

Kafka消费进度与Kafka输出可利用其特定事务机制，但外部数据库、邮件或支付HTTP不自动加入Kafka事务。通知发送成功但本地标记前崩溃仍有重复窗口，需供应商支持稳定发送操作号、领域自然幂等，或明确接受有限重复。不能声称Inbox能自动让任意外部邮件恰好发送一次。

Kafka分区并行处理时，只能推进连续已完成位置，不能让完成的offset102越过未完成101提交。实体全量快照可按版本忽略旧值，增量事件存在缺口则需等待、补拉或重建，不能只保留最大版本就丢掉必要增量。

### 5.2 Retry和Poison Message

暂态网络故障可有限重试，指数退避与随机抖动降低同步重试风暴；参数格式、未知必需Schema或永久权限问题不应无限重试。记录尝试次数、错误类别、原eventId和下次时间，重试不生成新业务身份。

毒消息（Poison Message）是持续无法处理、可能阻塞整个分区的记录。达到分类规则与重试上限后进入死信队列（Dead Letter Queue，DLQ）或持久失败表，保留原身份、错误、Schema与必要脱敏载荷，指派负责人和处理时限。DLQ不是垃圾桶，若没人查看、修复和重放，系统并没有最终收敛。

跳过毒消息可能破坏同实体后续顺序与业务依赖：可以隔离该实体、阻止其后续增量，或在明确语义下继续其他独立实体。重放需预览范围、限速、鉴权、保留原操作号并审计；不是修好代码后把所有DLQ一次性灌回。

### 5.3 Reconciliation补充恢复

对账（Reconciliation）比较权威订单与通知/投影/任务结果，发现缺失、重复和长期处理中。使用稳定操作号、可恢复分页检查点与重叠窗口覆盖晚到数据，通过正常领域命令幂等修复。

若一个消费者永久停机，消息保留结束后再启动可能已经无法重放，需从权威数据重建或对账补发。因此“最终一致”依赖传播、保留和恢复机制持续有效，不能只写一句“队列会重试”。

## 六、UI/API显式表达PENDING与PROCESSING

### 6.1 接受成功不等于业务完成

如果只是通知异步，原订单API仍可在订单提交后返回创建成功，不必把整笔订单改成PENDING。若报表、导入或支付确认本身异步，则API明确返回202 Accepted与Operation资源：

~~~http
HTTP/1.1 202 Accepted
Location: /operations/demo-job-7

{"operation_id":"demo-job-7","status":"PENDING","status_url":"/operations/demo-job-7"}
~~~

Operation定义PENDING、PROCESSING、SUCCEEDED、FAILED、CANCEL_REQUESTED等状态，并提供创建时间、进度口径、稳定错误码和结果位置。CANCEL_REQUESTED不等于已取消，正在执行或已提交的副作用可能不能撤销；只有有权威证据才进入相应终态。

客户端重试创建使用同一幂等键，避免超时后创建两份任务。状态查询要鉴权，任务ID不是凭证；响应中不暴露其他租户任务是否存在。任务提交、状态和待执行事实应在可靠边界内持久，不把内存入队当可靠接受。

### 6.2 Polling、推送与用户预期

轮询（Polling）最简单，但应有建议间隔、退避、停止条件与页面离开策略，避免每个用户每100ms查询形成新峰值。SSE/WebSocket可改善即时通知体验，却增加连接、重连与消息恢复复杂度，状态API仍是权威查询入口，断线重连不能制造重复执行。

用户看到处理中时，应知道结果预计时限、是否可离开、失败如何重试和取消是否可能。不要将后台失败吞掉后永远显示转圈。若查询读副本有延迟，刚提交任务可从主存储读取或返回足够状态，不能用户刚收到202就立刻查到404。

授权也有时间语义：任务接收时通过权限，不代表几天后下载敏感结果时无需再次鉴权。长任务执行是否受权限撤销影响由业务定义，不能把用户Token原样放入消息等待过期后继续使用。

## 七、Backpressure：队列只是有限缓冲

### 7.1 用增长率和年龄计算可承诺的恢复

背压（Backpressure）让下游能力不足反馈到上游生产。Broker可吸收短时峰值，但不增加下游长期处理能力。假设峰值生产2,000条/秒、消费1,200条/秒、持续300秒，新增积压240,000条；峰值后生产降到800条/秒，净排空400条/秒，理想还需600秒。

每条平均2KiB，240,000条仅原始载荷约468.75MiB，副本、索引、日志和协议开销另计。保留（Retention）应覆盖最长故障与排空窗口及重放需求，同时设存储容量、最大任务年龄和生产者限制。消息数不等于等待时间，快慢任务混合和热点分区需看最老年龄。

本章采用“99.9%通知在订单提交后30秒内完成”的教学SLO；上面的活动积压可能明显超标，所以不能一边宣称30秒，一边把15分钟排空当正常。应提前扩安全消费能力、限制接收、分配优先级或与业务调整承诺。

### 7.2 Producer Limit与Consumer Auto Scaling

生产者按租户、操作成本、请求体字节和在途量限制，超出可靠接收能力时明确拒绝尚未接受任务。已持久接受的工作不应被静默丢弃；若允许过期丢弃分析事件，需在业务契约和指标中明确。

消费者自动扩容参考Lag增长、最老年龄、处理速率与下游余量，不能只看CPU。Kafka可消费并行度受分区及热点限制；多个消费者写同一个饱和数据库，扩容会增加连接和锁等待，反而降低吞吐。线程池、连接池、预取、在途批次和重试都有上限，不能把Broker有界换成消费者内存无界。

恢复后渐进放量，给新流量、历史积压和DLQ重放分配份额。重试和备用路径也占容量，需总预算；库、供应商和网络的配额不因更多Pod而扩大。

## 八、渐进迁移与双运行：一次只让一个路径产生真实效果

### 8.1 分阶段迁移计划

第一阶段建立基线：Trace明确关键路径、入口和最终业务SLI，统计旧路径效果数和依赖时延，补稳定业务操作号。先具备对比证据，否则迁移后只知道“HTTP快了”，不知道通知漏了。

第二阶段在原业务事务增加Outbox，但新消费者只做Shadow：读取事件、生成拟执行结果，写隔离的影子结果表，不发邮件、不扣款、不发货，也不修改权威库存。旧同步路径继续唯一产生真实效果；可比较收件引用、模板版本、金额或投影内容的规范化差异。

第三阶段按租户/订单的稳定分桶与Feature Flag切小流量，决定每个业务操作的执行路径，并把routeVersion/owner持久化。旧路径只处理OLD归属，新消费者只处理NEW归属；进程内实时开关不足以保护正在执行和重试中的任务。

第四阶段逐步扩大，观察入口与最终完成、重复、差异、Age、下游资源及成本；达到验收后，等待旧路径在途处理结束，确认补偿/失败任务有负责人，再停止旧代码。事件兼容与重放支持保留到约定窗口结束，不是新路径上线就立刻删除所有旧字段。

### 8.2 Side Effect Ownership如何防双发

执行权（Ownership）必须跨重试与回滚稳定。对于可在本地事务保护的效果，可在同一个权威登记中按businessOperationId记录处理所有者与结果；OLD和NEW竞争同一业务防重约束，而不是各自独立一张去重表。

外部副作用仍需要对端稳定操作号或可接受重复的契约。本地写“我要发邮件”后崩溃、或邮件成功后未写结果，都存在未知窗口。旧新路径切换不能生成新的外部业务号，否则绕过共同去重。迁移正确性靠身份、所有权与恢复共同保证，不靠Feature Flag出现在哪里。

Shadow不能无意经过生产适配器：测试凭证、独立Topic/表、网络策略和运行时禁止真实副作用共同限制。仅约定“大家别调用发送方法”不够，错误配置或依赖注入仍可能触发真实动作。

### 8.3 回滚不是把开关切回去就结束

新路径接受但尚未执行的任务仍在队列，切回旧路径不能又同步执行一次。回滚通常先停止新的NEW分配，保留已归属NEW任务由新路径排空或按受控交接协议转移；交接需处理在途结果未知、共同幂等及版本，不能直接重置成未处理。

若新消费者有严重错误，暂停相关消费并保存位点与状态，修复后限速恢复；已产生错误外部效果按业务补偿，不是回滚代码就抹掉。数据库Schema和事件版本必须对旧代码仍兼容，采用先扩展、迁移、再收缩的节奏。

迁移验收覆盖功能等价、失败/重试、数据正确性、最终SLO、资源/成本和运维可操作性。不能为了回滚方便永久双发真实效果，也不能把长期双运行和两套状态维护成本忽略掉。

## 九、Java工程落地与并发陷阱

JDK21 CompletableFuture不带显式Executor的常见Async方法默认使用commonPool；阻塞远程调用堆在公共池会争用其他任务。为阻塞依赖选择明确有界执行资源和拒绝策略，并观察排队与上下文。thenApply等非Async回调也可能由完成线程执行，不要在其上无意放重CPU或阻塞工作。

Future超时、cancel或客户端断开不证明远程副作用已回滚。CompletableFuture的取消主要是异常完成语义，不应把mayInterruptIfRunning当作保证底层任务停止。操作幂等、真实完成跟踪与恢复任务仍不可缺少。

Spring6.2常见代理模式下，@Async同对象内部调用可能绕过代理，异常和执行器配置也需要明确。即使外部调用确实异步，也只是进程内调度，不自动持久化，不会把原线程事务跨到新线程。在线程里传ORM实体还可能触发已关闭上下文的懒加载或并发访问，应传不可变命令/ID并在工作者建立自己的短事务。

Trace Context、日志MDC、租户和安全上下文需要显式或框架支持的传播与作用域恢复；不能线程复用后串到其他请求。数据库连接、Session和用户Token不应作为可跨进程任务上下文直接序列化，任务只携带最小必要身份和业务数据。

## 十、故障推演与诊断

虚构通知迁移后入口P99从约800ms降到约150ms，表面成功，但通知完成P99升到5分钟。先看提交到Outbox、发布到Broker、消费者等待、供应商调用四段时间；若Outbox快而队列年龄涨，说明瓶颈在消费/下游，不能以入口优化宣布迁移成功。

若重复通知增加，核对旧新路径是否共同产生效果、是否使用同一操作号、消费者提交与确认顺序、供应商结果未知处理。若只有一个租户堵塞，查热点分区、毒消息与租户公平性；若全部恢复同时再次过载，检查自动扩容和重放是否越过供应商配额。

建立Queue Lag、Oldest Age、Outbox年龄、处理失败/重试/DLQ、最终完成率、重复效果和对账差异监控。订单/业务号连接请求与不同消费Trace，指标不放高基数订单ID；事件载荷、日志和DLQ统一脱敏、权限和保留。Page对应用户承诺或明确迫近风险，并附暂停、限流、回滚及恢复手册。

## 十一、测试、取舍与何时不迁移

### 11.1 有意义的验证矩阵

至少验证：事务回滚无事件；提交后崩溃仍有待发布记录；发送成功未标记重发不重复效果；消费提交后确认丢失可重投；毒消息隔离不悄悄破坏依赖顺序；客户端超时后原键只一任务；Feature Flag切换时同一业务只一所有者；回滚后旧NEW任务不被再次同步执行。

压测采用真实载荷与倾斜，区分提交、可靠接受、真实完成与失败；注入Broker/消费者/供应商长故障、重启和恢复积压，验证内存有界、存储保留和最终SLO。用可注入时钟测试超时重试，测试Schema新旧交错与历史重放。

本地模拟可以证明流程模型中预期规则，但不证明数据库锁、Kafka真实确认、供应商幂等或部署竞态；这些需集成和故障实验。没有运行的实验必须列为限制，不能把架构图当验证报告。

### 11.2 明确收益与代价

异步可减少非关键依赖进入用户关键路径，允许生产消费独立扩展并吸收短峰值，但代价是最终一致、中间态、重复乱序、持久积压、调试与值班复杂度。后台总耗时可能更长，消息和遥测成本也会上升。

若用户必须立即取得最终授权结果、吞吐很低且依赖稳定、团队没有消息运维能力，优化短事务、依赖时限、并行只读查询或有界线程模型可能更合适。若持久任务表已满足需求，不必为了流行技术引入复杂事件平台。架构决策应记录目标、约束、备选方案、验收和回滚条件。

## 十二、面试完整回答与追问

### 12.1 三分钟完整迁移回答

“我先用Trace和SLI确认同步关键路径、峰值与慢依赖，不先换框架。把通知和分析这类不决定当前业务成功的副作用移出事务，用本地业务加Outbox同事务保留待执行事实；若是长任务，API改为可靠接收加Operation状态，202不等于完成。

定义已发生事件的稳定ID、实体版本、Schema版本和责任人，避免发布内部实体。消费者去重和本地效果同事务、提交后确认，外部副作用有独立幂等与未知结果恢复；重试有上限，毒消息进可运营DLQ，对账修长期偏差。队列按存储、年龄、保留和净排空能力治理，扩消费者前确认下游余量。

迁移先Shadow只算结果不产生真实效果，再按稳定分桶持久化执行所有权，小流量切换并比较最终业务结果。回滚停止新分配，已归属新路径的任务受控排空或交接，避免旧新双发。最终验收不只入口变快，还看完成SLO、数据正确性、恢复、成本和团队运维能力。”

追问“直接@Async可不可以？”答：仅适合允许丢失或另有恢复依据的进程内任务；它不提供跨重启持久保证、事务原子发布和消息恢复，不能用来替代上述可靠接收边界。

### 12.2 “用户立即需要的结果为什么不能都异步？”

回答：技术上可以改变交互，但那是产品契约变化。认证授权必须先保护接受入口，库存/额度承诺若必须实时成立就要在权威端同步决策；把它返回PENDING必须得到业务允许，并定义失败后体验与恢复。异步不能把尚未成功的业务伪装成成功。

追问“订单创建后通知没发是否下单失败？”答：取决于契约，本章通知不决定订单成功，单独追踪通知SLO和恢复，不撤销已成功订单。

### 12.3 “队列能否解决消费能力不足？”

回答：只能缓冲短暂缺口。长期生产率大于消费率，有限存储最终耗尽；需要降低接收、提高安全处理能力或调整业务承诺。看增长率和最老年龄，扩容还受分区热点和共享下游限制，不把Lag变大机械等同加Pod。

追问“为什么恢复要渐进？”答：历史积压、新流量、重试和DLQ都会争同一下游，瞬间全放会重复过载。按净余量分配份额才可稳定排空。

### 12.4 “双运行怎么保证不双发？”

回答：Shadow必须不产生真实副作用，切流把每个业务操作的执行归属持久化，旧新路径共用稳定外部操作号和权威去重。回滚只改变新接收操作的路由，已在途操作按状态恢复，不能直接由旧路径重新执行。必要时暂停、查询未知结果再交接。

追问“两个路径各有自己的去重表行不行？”答：它们可能都认为首次处理，无法互相保护。必须有共同业务身份与可协调执行权，外部副作用还需对端支持或明确接受重复的范围。

## 十三、扫雷自测与答案

### 13.1 把HTTP调用放线程池再join，是否减少用户等待？

未必，入口仍等结果，只是执行线程改变，还增加调度和排队。并行独立操作可缩短部分关键路径，但持久解耦和业务异步需另外设计。

### 13.2 DB提交后调用异步发送，为什么仍会漏通知？

提交后、提交异步任务前或内存任务运行前崩溃均可能丢失。业务与Outbox同事务持久化，恢复者才能发现待做工作；单靠线程池不够。

### 13.3 Outbox是否从此不再重复？

不是，发送成功后标记前崩溃会重发。保持eventId，消费者本地事务去重，外部发送以稳定业务操作号保护，不能把消息确认当外部效果原子证明。

### 13.4 schema_version和aggregate_version能否共用？

不应混淆。前者说明事件结构，后者说明某实体状态顺序；结构升级不表示订单多了一次业务变化，实体版本推进也不代表Schema变更。

### 13.5 2,000/s生产、1,200/s消费持续300秒，积压多少？

差额800/s，新增240,000。之后生产800/s、消费1,200/s，净排空400/s，理想600秒；不是用240,000/1,200=200秒，后者漏算新流量。

### 13.6 240,000条各2KiB是多少容量？

载荷约468.75MiB，副本与日志等另算。平均大小也不能替代单消息最大值和总容量限制，Broker有空间不表示消费者内存可以无限预取。

### 13.7 202 Accepted能否在界面显示任务成功完成？

不能，它只说明请求被接受处理。应显示PENDING/PROCESSING并提供结果查询，失败有稳定错误与恢复，取消请求也不自动代表副作用已撤销。

### 13.8 Shadow消费者能否发真实邮件后再比较？

不能把这当无副作用Shadow，会造成双发。影子路径只产生隔离拟结果，真实效果有唯一所有者；若需要真实试验，应作为受控灰度而非影子。

### 13.9 回滚开关后，队列里新路径任务怎么处理？

保留原所有权，排空或按有界、可审计、共同幂等的协议交接。不能旧路径立刻补做全部任务，原消费者和失联请求可能仍在执行。

### 13.10 DLQ清空就代表最终一致了吗？

不是，丢弃或错误重放都能让DLQ变空。需要逐项确认业务效果、失败处置与对账差异收敛；保留来源、操作号和审计证据。

## 十四、速记、来源与验证边界

先识别关键路径与业务承诺，再移出非关键副作用；可靠接受靠持久事务边界，独立消费靠契约与恢复，切流靠所有权。异步减少等待和耦合，却增加中间态与运营责任，只有收益可测、失败可恢复、回滚可执行时才值得迁移。

本次DDL、HTTP与流程为教学示例，未执行Java/Spring/Kafka或真实数据库、供应商与灰度故障实验；本地Python仅验证路由所有权模型、去重与容量算术，不代替真实并发保证。来源核验于2026-11-17，实际组件版本须锁定并做集成验证。

- [JDK21 CompletableFuture](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/CompletableFuture.html)：默认执行器、完成与取消边界。
- [Spring Framework 6.2任务执行与调度](https://docs.spring.io/spring-framework/reference/6.2/integration/scheduling.html)：@Async代理与执行器；说明限定6.2模式，不把当前其他版本默认值套入。
- [Kafka 4.1设计](https://kafka.apache.org/41/design/design/)：投递、顺序和事务范围。
- [RFC 9110 §15.3.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3)：202 Accepted语义。
