# 03. 如何保证接口幂等与数据一致性

> 这是一道设计推理题：先划分问题与不变量，再给事务、并发和跨系统恢复方案，而不是只回答“加Redis锁”。SQL限定PostgreSQL 17，HTTP条件请求按RFC 9110，消息边界参考Kafka 4.1。案例为虚构教学示例，不是用户项目经历；正文不依赖外链才能理解。

## 一、先定义语义：四种问题不能用同一种锁解决

幂等（Idempotency）表示同一业务操作执行多次，业务效果等价于一次。它处理的是重发、重试和重复投递，不自动处理两个不同合法操作之间的竞争。并发控制防止不同操作互相覆盖；本地事务保证一个提交边界内的修改一起成功或回滚；跨服务一致性还要应对局部提交后其他步骤失败。

| 问题 | 例子 | 首要机制 |
| --- | --- | --- |
| 重复请求 | 同一次付款响应丢失，客户端再发 | 稳定操作号、幂等结果与唯一约束 |
| 并发更新 | 两人读取v7后分别修改地址 | Version/ETag与原子条件更新 |
| 跨服务部分失败 | 库存预留成功，支付失败 | 持久流程、补偿与对账 |
| 消息重复/乱序 | 同一扣款事件重投、旧状态迟到 | 消费去重、版本语义与缺口恢复 |

例如余额100，两笔独立提现各80：即使每笔都只执行一次，若都先读100再无条件写20，仍然可能两笔都被接受。幂等没有阻止超额提现，需要在权威账本事务内检查和扣减。反过来，仅给余额加行锁，也不能阻止同一提现在锁释放后被重发再扣一次。

面试先问：谁定义同一操作、重复承诺保留多久、哪些结果允许陈旧、跨系统失败能否补偿、何时必须明确成功。再定义不变量（Invariant），例如同一提现号最多一笔借记、余额不负、转账借贷守恒，以及最终到账允许的时间。机制的选择要能逐项保护这些规则。

## 二、操作身份与Fingerprint：正确区分重试和新意图

客户端在第一次执行前生成并持久保存Idempotency Key，网络失败继续用原键。Request ID和Trace ID可以每次尝试不同，业务操作号必须稳定；同一用户真的再次购买相同商品则用新操作号。不能只用请求内容Hash把两次真实购买合成一笔。

Key作用域包含可信租户、操作类型，必要时包含主体或资源范围，防止租户之间相同键冲突。Key不是访问凭证，读取原结果仍需授权。长度、格式与创建速率要有限制，防止恶意填满幂等表。

请求指纹（Request Fingerprint）检查同键是否对应同一命令。将影响业务的字段校验并规范化，例如币种、精确金额、账户、商品数量和语义版本，再以稳定编码计算摘要。traceId、客户端重试时间不参与；JSON字段顺序和等价数字表示不应导致意外不一致。原始敏感数据不能因“为了指纹”就无限留存。

相同Key但金额从10变100必须返回契约定义的冲突，例如409与稳定业务码；不能悄悄执行新金额，也不能返回旧结果却让调用方以为100已执行。指纹算法演进要兼容旧记录或保留规范化版本，否则发布本身会制造大量假冲突。

## 三、创建接口：一份完整的本地事务设计

### 3.1 表与持久化边界

下面用“创建业务单据”演示本地事务，不在事务中调用外部付款。PostgreSQL 17教学DDL如下：

~~~sql
CREATE TABLE api_operation (
    tenant_id text NOT NULL,
    operation_type text NOT NULL,
    operation_key text NOT NULL,
    fingerprint text NOT NULL,
    response_status integer NOT NULL,
    response_body jsonb NOT NULL,
    completed_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (tenant_id, operation_type, operation_key)
);

CREATE TABLE business_document (
    tenant_id text NOT NULL,
    document_id text NOT NULL,
    operation_key text NOT NULL,
    amount_minor bigint NOT NULL CHECK (amount_minor > 0),
    currency text NOT NULL,
    PRIMARY KEY (tenant_id, document_id),
    UNIQUE (tenant_id, operation_key)
);
~~~

api_operation用于保存已提交结果，business_document的自然业务唯一性提供额外防线。若实际一个operation_type可创建多个资源，唯一键设计必须与该业务语义一致，不能机械复用这个简化DDL。

算法关键是先通过唯一键竞争取得执行资格，而不是先SELECT不存在再INSERT。伪代码说明完整控制流：

~~~text
校验认证/授权/请求大小和命令字段
生成规范化指纹与候选documentId
BEGIN
  INSERT api_operation(键、指纹、最终响应占位)
    ON CONFLICT DO NOTHING RETURNING operation_key
  若插入成功：
    写business_document
    写同库Outbox（若需要事件）
    把api_operation更新成真实最终响应
    COMMIT
    返回真实响应
  若未插入：
    用后续语句读已提交api_operation
    若指纹不同：结束事务，返回同键异义冲突
    若指纹相同：结束事务，按授权重放原结果
    若记录不存在：结束并按受控策略重新判断
任意事务错误：
  ROLLBACK
  分类处理；不宣称完成
~~~

占位只在同一未提交事务内部存在，不能提前提交或对外当作成功；任一业务写入失败，操作记录也回滚。业务永久拒绝是否存结果是接口契约选择，暂态基础设施失败通常不应被永久缓存成不可恢复结果。

### 3.2 并发重复实际发生什么

会话A插入某Key未提交，会话B同Key插入可能等待唯一索引竞争。若A提交，B不能再取得该键，读取A的结果；若A回滚，B可有机会插入并执行。必须为等待设置预算，不能让大量重复调用无限占用连接。

PostgreSQL Read Committed下，ON CONFLICT DO NOTHING可能因另一个并发事务的结果不插入，但该语句快照不一定能SELECT到冲突行，所以使用后续语句读取。并发清理仍可能让读不到，需要明确重试/查状态策略；不应写一个单语句CTE后假设必定返回已有结果。Serializable或其他数据库的异常和可见性规则不同，按实际隔离级别重试整个事务。

唯一约束异常在某些数据库会使当前事务进入失败状态；不能捕获异常后继续当作正常事务随意查询。ON CONFLICT是PostgreSQL方案之一，其他产品可用其冲突语法或回滚后重读，但必须清楚错误和提交边界。

### 3.3 四个崩溃窗口的结论

| 崩溃位置 | 持久事实 | 恢复 |
| --- | --- | --- |
| 事务提交前 | 操作记录和业务都未提交 | 原键重试重新执行 |
| 业务SQL成功但事务回滚 | 业务效果未提交 | 原键重试，不能单凭SQL返回宣称成功 |
| 提交成功但响应丢失 | 结果与业务都存在 | 原键读取并重放，不创建第二份 |
| 提交响应本身丢失 | 调用方不知道是否提交 | 新事务/重连查原键，不猜测失败 |

重放可保存稳定资源ID、业务结果、必要状态码和响应字段，不必无限保存全部HTTP字节。响应要明确是原操作结果还是当前资源状态，避免历史创建成功结果被当作资源此刻仍处原状态。授权撤销后不能仅因有Key而继续泄露历史数据。

## 四、长任务与外部调用：从同步结果表升级为Operation状态机

如果操作需要几秒或涉及远程支付，不应持有数据库事务和锁等待网络。先短事务保存PENDING操作、命令及Outbox，再返回202和Operation查询地址；后台工作者处理后保存结果。状态至少区分PENDING、RUNNING、SUCCEEDED、FAILED与需要恢复的UNKNOWN，含版本、重试次数、下次执行时间和错误类别。

重复调用读到处理中，可以返回同一Operation和当前状态，或契约定义的处理中响应。不要开第二个工作者无保护地重做；租约（Lease）可用于短期认领，但租约到期旧工作者可能仍运行，因此状态写入用版本条件或栅栏令牌（Fencing Token）阻止旧工作者覆盖新结果。

本地租约不能让供应商副作用自动停止。外部调用仍用稳定操作号，超时后查询原操作，只有对端能提供的幂等与状态契约才保护对端效果。若对端完全不支持安全去重和查询，就不能对业务承诺“任何故障下绝不重复”，需改变流程、增加人工确认或选择更合适的服务。

客户端总deadline、本次网络timeout和业务任务有效期是不同概念。客户端断开不应使已可靠接收的付款任务消失；任务过期也不证明外部未成功。后台恢复器扫描长期RUNNING/UNKNOWN，依据权威查询推进，有限退避并升级人工，而不是无限循环。

## 五、更新接口：Version/ETag与If-Match防Lost Update

### 5.1 一个完整的HTTP条件更新

丢失更新（Lost Update）是后提交操作覆盖了基于旧快照看不到的新修改。假设两个客户端都读取地址版本7，A更新成版本8后，B不能继续用版本7覆盖。

~~~http
GET /documents/demo-7

HTTP/1.1 200 OK
ETag: "doc-demo-7-v7-json"

{"id":"demo-7","shipping_address":"old","version":7}
~~~

~~~http
PATCH /documents/demo-7
If-Match: "doc-demo-7-v7-json"
Content-Type: application/merge-patch+json

{"shipping_address":"new"}
~~~

服务端先鉴权和校验字段，再把条件绑定到真实数据库更新：

~~~sql
UPDATE document_state
SET shipping_address = :address,
    version = version + 1
WHERE tenant_id = :tenant
  AND document_id = :document
  AND version = :expected_version
RETURNING version;
~~~

document_state需有租户/文档主键、非空版本和相应地址字段；此SQL是条件更新片段，不是上节business_document的完整DDL。RETURNING一行才表示该条件下成功；零行可能是不存在、无权限范围或版本冲突，按既定授权和查询策略映射，不能全当更新成功。

ETag是表示的验证器（Validator），不是任意版本号标签。只有所有影响该表示的更新都会推进相应版本、并考虑表示变体时，才能将行版本映射为强ETag；If-Match使用强比较，弱标签W/不能用来代替。服务端应解析自己签发的验证器并做原子条件检查，不能先内存比较ETag再无条件UPDATE。

### 5.2 冲突处理与重试边界

If-Match不成立按HTTP语义通常返回412 Precondition Failed，业务状态冲突可用409，要求客户端必须提供条件时可按契约返回428。不要把所有失败都200，也不要把版本冲突统一归为可自动重试的网络错误。

客户端收到412后读取新状态，展示冲突或由业务规则合并，再以新版本提交。库存已从10变3时，不能自动把旧表单“设置为8”强行重试；合并是业务决策，不是简单换ETag。对增量“扣1”要用稳定操作ID和原子扣减，两个独立扣1都应生效。

幂等键和版本条件解决不同问题。若A用v7更新成功为v8但响应丢失，原样重发的If-Match v7会失败；如果还承诺原操作可重放，应先在独立的操作身份逻辑中识别已完成同命令，再返回原操作结果，不把它重新当新修改。这个恢复契约必须保留完整指纹和授权，不能用“版本过期所以失败”掩盖第一次已成功。

## 六、余额、库存与跨行不变量：强控制放在权威边界

对“库存不负”可用quantity>0校验与available>=quantity条件扣减，并添加数据库约束。对余额同理，还要考虑币种、冻结额度和流水唯一性。CHECK约束保护单行规则，但“借贷守恒”“两个账户合计限制”等跨行规则不能只靠一个版本字段。

同库转账可在短事务内按稳定顺序锁定双方账户，校验币种、权限和余额，写唯一转账流水与借贷更新，一起提交。稳定锁顺序减少死锁，死锁或序列化失败需重试整个事务并保留原操作号。不要在持锁事务内远程调用或睡眠退避。

乐观锁适合冲突低且冲突后能合理重读的操作；悲观锁适合短事务、高价值资源协调，但等待、死锁和连接占用有成本。Serializable可发现某些无法串行化的并发，需要完整事务重试；不是“设置最高隔离级别后不再处理异常”。

单服务也可能写多个数据库或远程系统，不能仅凭“同一个Service”就声称本地ACID保护所有数据。本地事务只覆盖实际参与的存储资源；如果可以将强不变量放入同一权威边界，通常比后续补偿更容易证明正确。

## 七、跨服务：Outbox、消费者、Saga与对账各司其职

### 7.1 Outbox补上双写窗口

本地业务提交后直接发消息，可能在两者之间崩溃漏发；先发消息再提交业务，可能让外界看见最终回滚的事实。事务发件箱（Transactional Outbox）把业务数据和待发事件写在同一数据库事务，发布器只处理已提交记录。

发送成功但标记已发前崩溃会重复发布，所以Outbox不是从不重复的魔法。事件ID稳定，含实体ID、版本、租户和Schema版本；发布器有有限批次、退避、最老待发年龄和重放入口。轮询较简单但增加数据库扫描，CDC从提交日志读取可降低轮询却增加连接器位点与运维复杂度。

Outbox保证的是在持久性、发布器持续恢复和保留条件下“可重试发布”，不保证任意故障时无限期必达。清理必须与恢复范围协调，发布器长期停止仍须告警。

### 7.2 Consumer去重、自然幂等与乱序

消费者用Processed Event表按consumerName、tenant、eventId唯一，在同一本地事务内插入标记并更新业务，提交后再确认消息。事务回滚时标记也回滚；提交后确认丢失，重投被跳过。不同订阅者应分别处理同一事件，不能共享一个全局已处理标记。

自然幂等是重复写同一资源状态不增加额外效果；例如按订单ID写相同投影。Upsert中balance=balance+amount仍会每次累加，不自动幂等；资金增量要有唯一流水号。若同一业务动作有不同eventId，还需业务自然键约束，不能仅依赖投递身份。

实体版本能防旧快照覆盖新快照，但增量事件v12若依赖v11，不能直接跳过缺口；要缓冲、补拉或重建权威快照。Kafka的内部Exactly-once范围不自动包含外部数据库/支付HTTP。外部副作用需要对端幂等或可恢复协调，不能在本地标记提交前后随意调用邮件或扣款再声称原子。

### 7.3 Saga与Compensation不是数据库Rollback

Saga把跨服务流程拆成本地事务，用持久步骤推进；后续失败时执行补偿（Compensation），例如释放未确认库存或对已扣款发起退款。退款是新流水，可能收费、延迟和失败，不能擦掉原支付历史。授权未扣款可能需要撤销授权，与退款不同。

协调者记录每步稳定命令号、状态、版本、重试与补偿结果；进程重启从记录恢复。补偿本身也幂等、可重试、可审计，永久业务冲突进入人工队列。旧命令可能在取消后迟到，应由目标端状态/墓碑/版本规则拒绝不合法推进。

Saga不提供全局隔离：库存预留中、支付UNKNOWN等状态可能被其他请求看到，查询和发货规则必须理解它们。若业务完全不能接受中间态且参与资源支持适当协调，应评估同库事务或分布式事务能力；不要机械把所有一致性都改成最终一致。

### 7.4 Reconciliation修长期偏差

对账（Reconciliation）按稳定操作号比较本地与权威系统状态、金额、币种与流水，分类为缺失、重复、金额不符和长期未知。扫描保留检查点和重叠时间窗口，覆盖晚到记录；进度只有在差异和处理结果可靠保存后推进。

修复通过幂等领域命令和审计执行，不能直接改表跳过不变量和事件。金额不符需保存证据并人工介入，不能自动选一边覆盖。对账不是正常流程不设计正确性的借口，而是应对消息缺口、外部延迟、历史错误与灾备重放的最后恢复层。

## 八、Timeout：Unknown Outcome的完整处理

网络超时只表示当前调用方未及时得到结果。可能服务端未执行，也可能已提交而响应丢失；取消Future或关闭socket不证明远端回滚。客户端继续原Idempotency Key重试或查询Operation Status，不能创建新Key盲目再次扣款。

服务端提交结果未知时先重连查询原操作身份；支付对端需查询原供应商操作。查询“暂未找到”也未必是最终失败，需了解查询一致性和在途处理契约。回调可重复、乱序或伪造，应验签、核对账号/租户/金额/身份并幂等处理；回调与主动查询并发时按状态和版本协调。

重试只对安全且暂态的错误，受单次超时、总deadline、次数、退避抖动和额外流量预算约束。UNKNOWN记录需最老年龄与恢复责任，用户显示“处理中/待确认”，而不是伪造成功或明确宣称未扣款。

## 九、一致性选择、保留、安全与成本

### 9.1 按不变量决定强弱

余额、库存和唯一业务流水在权威端采用强约束，通知、分析和可重建查询投影可接受最终一致性（Eventual Consistency）。即使是分析数据，也要定义业务是否允许重复计数、晚到和更正，不能随便丢事件。

定义权威来源（Source of Truth）、允许陈旧度（Staleness）、冲突规则和收敛机制。比如“99.9%已提交订单在30秒内反映到查询投影”，起点是权威提交，终点是指定版本可读，失败事件不从分母移除。还需最老未完成年龄告警，防少量永久卡住被百分位掩盖。

刚写后读取旧副本可能误报失败，读己之写可暂时读主存储、携带版本等待投影追上或在客户端合并已确认结果；等待有界。不能通过放宽查询一致性改变资金写入不变量。

### 9.2 Retention与灾备必须共同设计

幂等记录保留24小时但消息可重放7天，就无法仅靠该记录承诺历史重放不重复。长效自然业务键、长期流水、短期完整响应与归档可组合，保留期限覆盖离线客户端、人工重放和备份恢复。

假设每天100万操作、每条结果与索引平均1KiB，30天逻辑量约28.6GiB，副本、WAL、备份另算。无限保存完整响应成本高且增加隐私暴露；过早删键会破坏正确性。分区/清理还要注意唯一约束的实际范围，不可为方便删除而让同一业务键跨分区重复。

恢复旧备份时，业务、幂等、Outbox和消费进度不能互不协调。新offset配旧业务数据会漏处理，旧去重记录配历史外部副作用可能重扣；恢复后以权威账本和对账确认，不靠“服务启动成功”验收。

## 十、验证与Observability：用故障矩阵证明边界

验证同键同内容并发只一份效果，同键不同内容冲突；事务失败无残留占位；提交后断连原键可恢复；版本并发只有一个旧版本更新成功；消息重投不重复增量；增量缺口不会被误丢；补偿响应丢失不重复退款；过期重放与备份恢复仍符合承诺。

真实数据库双会话测试要覆盖A占唯一键、B等待，A分别提交和回滚；还要注入锁超时、死锁和序列化失败，检查整个事务正确回滚。外部支付沙箱验证同键范围、查询延迟和回调乱序，本地内存模型无法证明这些实际行为。

监控Duplicate命中、Fingerprint Conflict、412/业务冲突、Outbox最老年龄与Lag、消费者去重与版本缺口、Failed Compensation、UNKNOWN和Reconciliation Difference。重复突升可能来自客户端或代理重试，冲突突升可能是Key生成或规范化版本错误；不要只把被挡住的重复当作成功治理。

指标使用有限维度，操作ID放受控日志/Trace，日志不记Token或完整敏感请求。人工重放、补偿与修复必须鉴权、限速、审计，支持预览范围与结果确认，防止一次修复批量制造新副作用。

## 十一、面试完整回答与深入追问

### 11.1 三分钟完整回答示例

“我会先区分重复操作、不同操作并发、跨服务部分失败和消息重复。创建接口用客户端稳定操作号，服务端以可信租户和操作类型限定Key，保存规范化指纹和结果，通过数据库唯一约束取得执行权；本地业务、操作结果和Outbox同事务提交。相同Key重放原结果，不同内容拒绝冲突。

更新接口用表示版本签发强ETag，If-Match绑定数据库版本条件更新，检查影响行数，冲突让客户端重读并按业务合并。它防丢失更新，不能代替支付操作防重。

跨系统用持久Saga推进，本地Outbox保证待发事实，消费者把去重和业务效果同事务，外部副作用仍需对端幂等。超时是结果未知，原Key查询或重试，补偿与对账让中间状态收敛。余额库存强约束，通知和分析允许有SLO的陈旧；用并发、断连、重复、乱序、补偿失败和灾备恢复验证边界。没有一个Exactly-once配置能自动覆盖所有外部效果。”

追问“你的保证期限是什么？”答：明确客户端和消息重放窗口，操作结果与长期业务唯一键各自保留；超出窗口不能继续无条件承诺去重，灾备也需协调位点和权威流水。

### 11.2 “Redis锁就能保证幂等吗？”

回答：不能单独保证。锁过期、进程暂停、缓存丢失或主从切换可能让旧新工作者重叠；即使没有重叠，锁释放后重复请求还能再次执行。正确性放在持久操作身份、唯一约束和事务结果，远程效果由权威端幂等与查询恢复保护，Redis可作为优化或有限租约。

追问“锁永不过期？”答：进程崩溃后可能永久卡住，还不解决提交成功后重试和外部结果未知。无限占锁以可用性换来一个不完整保证，不是完整方案。

### 11.3 “If-Match和幂等键冲突时先看哪个？”

回答：先明确接口是否提供已完成操作的重放契约。已成功的相同操作响应丢失，原版本过期是正常结果，服务端应识别同Key同命令并返回原操作结果；新操作才检查当前If-Match并执行原子更新。每次都鉴权，指纹包含命令与必要前置条件，不能用Key绕过授权或修改内容。

追问“客户端自动刷新版本再试可以吗？”答：不应通用自动做，刷新意味着在新数据基础上重新决定业务意图，可能覆盖他人修改；要重读并按领域规则合并。

### 11.4 “Outbox、去重都做了还要对账吗？”

回答：需要。外部查询延迟、消息保留/位点错误、历史代码bug、补偿失败和灾难恢复都可能产生长期差异。Outbox不保证不重复，Inbox只保护本地事务，对账提供跨边界的事实核验与恢复。修复也走稳定业务号和领域命令，不能手工改status就结束。

追问“对账能代替强事务吗？”答：不能。对账是恢复层，不能把本应同步保证的余额不负和借贷守恒先破坏再等待修复。

## 十二、扫雷自测与答案

### 12.1 相同内容是否必须使用同一Key？

不是，同内容可能是两次真实购买。Key标识用户操作意图，Fingerprint只检查同一Key的内容是否被更改；二者职责不同。

### 12.2 幂等Key先单独提交，业务后提交，有什么风险？

两者间崩溃会留下“占键但无业务”的残留。简单同步方案应同事务；若确需先提交，则记录真实PENDING并有持久工作者/恢复状态机，不能当作完成。

### 12.3 两个不同提现号各提现80、余额100，幂等为何不够？

它们不是重复操作，各执行一次也可能超额。需权威端事务内条件扣减、锁或合适隔离与约束，同时各流水号防重，不能用无保护的先读后写。

### 12.4 If-Match过期应返回什么？

通常412，表示请求前置条件不满足；业务状态冲突可409，强制要求条件却缺失可按契约428。区分错误有助于客户端选择重读、合并或修正，而不是盲目重试。

### 12.5 更新SQL影响零行能否返回成功？

不能默认成功。可能版本冲突、资源不存在或租户范围不匹配，要按授权策略判断，不泄露他人存在性。执行前比对版本后无条件写入也不能防并发竞态。

### 12.6 消费标记成功、业务写入失败，重投会怎样？

若标记被单独提交，重投错误跳过，业务丢处理。标记与本地效果同事务，失败一起回滚；事务外副作用还需独立幂等和恢复。

### 12.7 Upsert做balance=balance+10重复两次是否幂等？

不是，会增加20。语法不代表业务语义，应以唯一增量操作号和业务变更同事务，或采用版本保护的完整快照。

### 12.8 超时后换新Key为何危险？

原操作可能已成功，新Key会被视为新意图，绕过原去重造成重复扣款。保持原Key并查询，承认UNKNOWN，通过回调和对账确认。

### 12.9 10万事件中120条超过30秒，满足99.9%收敛吗？

不满足，及时比例99.88%。失败和长期卡住也计入，且要有绝对年龄告警，不让百分位掩盖少数永久偏差。

### 12.10 24小时去重保留能保护7天历史重放吗？

不能仅凭短期表。需要长效自然业务键、流水和恢复位点设计，或者明确限制可重放范围；超出保护期不能继续承诺无重复效果。

## 十三、速记、来源与验证边界

重复操作靠稳定身份，竞争更新靠版本/锁，跨系统靠真实事务边界与持久恢复。At-least-once交付配合幂等处理、约束与对账，可以在明确期限、权限和故障模型内实现目标业务效果；不是任意系统无条件“恰好一次”。先说明范围和反例，再给实现与测试，才是完整架构回答。

本次SQL/HTTP为教学片段，未在真实PostgreSQL、Java服务、Kafka或支付沙箱执行；本地Python只验证事务模型、重复冲突、版本条件和算术，不替代数据库并发证明。来源核验于2026-11-16；实际驱动、隔离级别和供应商幂等契约必须另做集成验证。
