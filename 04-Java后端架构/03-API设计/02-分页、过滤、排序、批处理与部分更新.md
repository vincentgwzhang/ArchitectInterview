# 02. 分页、过滤、排序、批处理与部分更新

> 范围：面向多租户订单 API 的集合读取与批量写入。SQL 以 PostgreSQL 17 语义为例，命名参数是应用绑定占位符，并非可直接粘贴到 psql 的语法。HTTP 条件请求依据 RFC 9110；部分更新依据 RFC 5789、7396、6902。数字均为教学限制，不是通用生产参数。

## 1. 集合接口的设计目标与承诺

一个“查询订单列表”接口要同时约束结果语义和资源消耗：哪些订单可见、按什么顺序、翻页时数据变化会怎样、一次最多读多少，以及客户端如何继续。仅有 page 和 size 两个参数，无法回答稳定性与性能问题。

贯穿场景：客服查询本租户近一个月订单，滚动浏览；财务要导出某时刻的结算清单；运营要批量修改订单备注。客服能容忍列表随新订单变化，财务要求结果集合可重现，批量编辑要求逐项知道成功与否。这三种需求不能用同一个“Cursor 很快”的结论覆盖。

先明确一致性契约：实时列表通常每次读取当前状态；快照列表针对固定数据视图；导出任务把选中集合或快照及结果持久化。分页方式控制访问路径，不自动定义跨请求一致性。批量接口减少网络往返，也不自动提供一笔全局事务。

## 2. Offset Pagination：简单在哪里，代价在哪里

### 2.1 查询方式与稳定顺序

Offset Pagination（偏移分页）先跳过 offset 条匹配记录，再返回 limit 条。典型查询：

~~~sql
SELECT id, created_at, state
FROM orders
WHERE tenant_id = :tenant
ORDER BY created_at DESC, id DESC
LIMIT :limit OFFSET :offset;
~~~

offset=100、limit=50 表示跳过前 100 条取后续最多 50 条。页号从 0 还是 1 开始是 API 约定，必须明示；将页号换算 offset 时还要检查整数溢出、负数和最大深度，不让巨大参数穿到数据库。

必须有确定的唯一顺序。仅 created_at DESC 不够，因为同一时间可以创建多条订单；追加唯一 id 才能打破平局。数据库没有显式 ORDER BY 时不承诺默认顺序，索引或执行计划变化都可能让分页结果变化。

### 2.2 为什么深分页慢

即使有匹配索引，数据库仍可能需要扫描/计算并跳过前面大量行，不能把 OFFSET 当作数组随机下标。第 10000 页只显示 50 行，并不意味数据库只处理 50 行；过滤选择性、排序、关联与执行计划会影响成本。

Offset 的优势是实现简单、支持随机跳页，适合数据量有限的管理页面。缺点是偏移越深通常越贵，且总页数需要额外计数。可以限制最大 offset、要求更窄时间范围，或为历史数据提供导出任务，避免无限跳到最后一页。

不能以“索引存在”证明性能已达标。要检查过滤后扫描行数、排序是否落盘、缓冲读取和返回字节，使用代表性深度与大租户数据测试。缓存前几页可减轻常见读取，但不会修复深页和授权隔离问题。

### 2.3 插入删除怎样造成重复与遗漏

原顺序为 A、B、C、D，每页两条。第一次返回 A、B；此时新增 X 到最前，列表变成 X、A、B、C、D。第二次 OFFSET 2 得到 B、C，B 重复。若第一次后删除 A，列表变成 B、C、D，OFFSET 2 从 D 开始，C 就漏了。

这不是排序没写好，而是每次请求读取的集合不同，按位置计数随变化移动。确定排序只消除同一结果集内的歧义，不冻结列表。若要求精确遍历某时刻集合，需要快照或物化结果，不是继续增加排序字段。

## 3. Keyset/Cursor Pagination：从最后一个值继续

### 3.1 Cursor 与 Keyset 不是完全同义词

Cursor 是客户端用于继续查询的不透明标识；它可以编码键集位置，也可以引用服务端保存的快照或查询句柄。Keyset Pagination（键集分页）具体指按上一页边界值继续范围查询。一个 Base64 编码的 offset 仍然是偏移分页，不会因为叫 cursor 变成索引范围访问。

本例采用 created_at DESC, id DESC，假设两列均 NOT NULL，created_at 创建后不可修改，id 有稳定排序。首屏无边界，后续查询：

~~~sql
SELECT id, created_at, state
FROM orders
WHERE tenant_id = :tenant
  AND state = :state
  AND (
      created_at < :last_created_at
      OR (created_at = :last_created_at AND id < :last_id)
  )
ORDER BY created_at DESC, id DESC
LIMIT :fetch_limit;
~~~

fetch_limit=pageSize+1。对同方向且非空键，PostgreSQL 也可用 (created_at, id) < (:last_created_at, :last_id) 表达字典序比较。上式展开写法更便于看清边界：先比较时间，同时间再比较 id，不是两列都必须小于。

### 3.2 正反向、混合方向与空值

按 DESC 向后读，用小于边界；若读取上一页，可取大于边界、临时按 ASC 取最近若干条，再将结果反转为对外 DESC。上一页 Cursor 应由当前页第一条记录产生，下一页由最后一条产生，不能直接复用同一个端点值。

若排序是 priority DESC, id ASC，范围条件变为 priority < lastPriority，或 priority 相等且 id > lastId；不能把所有字段统一塞进一个小于比较。实现需让排序定义和边界谓词共用同一受控模型，否则某种排序方向会漏数据。

空值也必须单独定义。SQL 比较 NULL 不是普通真/假大小关系，NULLS FIRST/LAST 与谓词需一致。最简单的契约可以禁止分页主键为空；若业务允许排序字段为空，要有显式空值分组和后续边界分支。字符排序规则、大小写归一和时间精度也必须与数据库一致；Cursor 中截断微秒可能改变同时间分组。

### 3.3 多取一条与 nextCursor 的正确位置

若 pageSize=2，数据库返回 A、B、C，只交付 A、B，hasNext=true，nextCursor 用 B 的排序键。不能用额外探测的 C，否则下一页从 C 之后开始，C 永远被跳过。若只返回两条就断言“没有下一页”，也可能误判。

响应可以是：

~~~json
{
  "items": [
    {"id":"ord-9","state":"PAID"},
    {"id":"ord-8","state":"PAID"}
  ],
  "page": {
    "limit": 2,
    "hasNext": true,
    "nextCursor": "<opaque-token>"
  }
}
~~~

这些字段是本 API 契约，不是 HTTP 标准规定。到达结尾 nextCursor=null，客户端不应根据解码内容自行构造下一页。没有结果的列表通常返回 200 和空 items，不用 404 表示“这个过滤没有匹配”。

## 4. Keyset 没有消灭并发：快照与排序字段的边界

### 4.1 不可变排序键解决哪些问题

继续 A、B 后的读取时，若新行 X 排在最前，Keyset 从 B 的值往后走，不会因 X 插入而再次看到 B。这避免了偏移位置移动造成的一类重复。删除边界记录 B 也不一定使 Cursor 失效，因为范围条件只需 B 的键值，不一定要重新找到这条行。

但若按 updated_at 排序，某条未读记录更新后移到边界之前，就可能漏读；已读记录移到边界之后可能再次出现。唯一 id 只保证同一时刻总顺序，不保证所有排序键不可变。应优先为连续扫描选择不可变键，或明确实时列表允许哪些漂移。

过滤字段也会变：订单 state 从 PENDING 变为 PAID 后可能加入当前过滤集合，从 PAID 变为 CANCELLED 又会离开。即使 created_at 不变，Keyset 仍不是最初集合快照。客户端按 ID 去重只能去掉部分重复，无法恢复从未见到的行。

### 4.2 高水位不等于数据库快照

首屏记录一个时间上界 asOfCreatedAt，后续始终加 created_at <= 上界，可以排除较新的创建时间。但延迟写入、回填旧时间和状态更新仍能改变集合；主键分配顺序也不必等于提交顺序。因此仅有时间戳上界不能宣称“严格截至某时刻”。

精确导出可使用数据库一致性快照或物化满足条件的记录/版本，再分页读取。跨请求持有长事务会占连接、保留旧版本并影响回收，通常不适合让用户慢慢点下一页。可在后台短时建立可重放结果、写入对象存储并分页/下载，明确生成时点、权限与保留期限。

物化 ID 只能冻结成员集合；若之后按 ID 查最新字段，字段值仍会变化。财务导出若要求当时值，也要冻结内容或保留可重建版本。准确承诺需要区分“固定哪些记录”和“固定每条记录哪一版”。

## 5. Cursor 是受控协议：不透明、完整性、授权分别设计

对客户端不透明意味着实现可演进，客户端只传回 Token。Base64 只编码，不提供完整性或保密性。可用带认证的 Token，或服务端随机句柄引用状态；需要保密排序键/条件时还要加密或不把内容暴露给客户端。

教学载荷可包含 schemaVersion、方向、末尾排序键、规范化过滤与排序的摘要、可信租户/主体范围绑定、签发与过期时间，以及必要的快照引用。签名密钥要有轮换策略和长度上限，解析前先限制输入大小；使用成熟密码库并固定算法，不自己拼一个容易误用的“hash”。

收到 Cursor 后，验证完整性、版本、过期、方向和当前查询条件是否一致，再从认证上下文重新计算授权范围。用户换 tenant、改过滤或改变排序时，应拒绝不匹配 Token 或要求重新开始，不能拿旧边界套进新查询。可明确允许调整 limit，但要验证上限及与快照的兼容性。

签名 Cursor 不是访问许可：用户权限在翻页间被撤销，仍要按当前政策判断。共享 Cursor 也不能绕过用户/租户授权。Token 错误、过期、快照消失的恢复指引要稳定，例如分别返回约定的 CURSOR_INVALID、CURSOR_EXPIRED 并让客户端重新开始，不泄露原始载荷和内部 SQL。

## 6. Filter 与 Sort：把查询能力约束成可承载的产品

### 6.1 白名单不是只校验字段名

客户端可以请求 state in (...)、createdAfter、customerId 等受支持条件；服务端将逻辑字段映射到固定数据库表达式，值用参数绑定。字段名、排序方向和 Operator 通常不能像值一样简单绑定，所以必须从枚举/白名单生成，不能把传入字符串拼成 SQL。

每个字段定义类型、允许运算符、空值、时区、大小写和边界含义。例如 createdAfter 是严格大于还是包含端点，时间采用 UTC 还是含时区时间，金额最小单位是什么，都影响重复、遗漏与索引使用。

~~~http
GET /orders?state=PAID&createdFrom=2026-11-01T00%3A00%3A00Z&limit=50&sort=-createdAt,-id HTTP/1.1
~~~

这里 - 表示降序是应用约定，createdFrom 本例定义包含端点。相同字段重复出现、互相矛盾区间、未知状态应明确拒绝或按规范化规则处理，不随意忽略错误条件导致用户以为过滤已生效。

查询复杂度还需限制 IN 元素数量、OR 分支、关系跳数、文本长度、时间跨度与通配符。参数化能防注入，却不能防代价巨大的合法查询。对隐私字段的过滤和计数还可能成为数据探测通道，应单独授权而不是只看返回字段。

### 6.2 索引与排序共同决定能否高效继续

对 tenant_id、state 等值过滤，加 created_at DESC、id DESC 的键集扫描，可以评估：

~~~sql
CREATE INDEX orders_tenant_state_time_id
ON orders (tenant_id, state, created_at DESC, id DESC);
~~~

这是 PostgreSQL 17 的候选索引，不是看到四个字段就保证最优。若查询不限制 state，中间列可能妨碍按跨状态时间顺序直接读取；若时间范围/租户规模差异很大，执行计划也可能变化。排序选项越多，需要支持的访问路径越多，索引增加写入、存储和维护成本。

常见做法是提供少数有业务价值的排序组合，而不是承诺任何字段任意组合。对统计/全文检索等查询可使用单独读模型或搜索引擎，但搜索结果的一致性、排序键和快照能力也需重新设计，不能假定迁移后自动精确。

分页查询还应避免关联 JOIN 放大父记录。一笔订单多条明细，LIMIT 50 个 JOIN 行不等于 50 个订单；可先查符合条件的订单 ID 页，再批量加载投影所需字段并恢复顺序。每步仍需正确租户约束，不能第二步只按任意 ID 取数据。

## 7. Metadata、totalCount 与运行成本

items、nextCursor 和必要元数据通常足够驱动滚动列表。hasNext 可通过多取一条得到，但在实时变化中它只描述这次读取观察到的情况，不保证下一次请求一定非空，也不保证此后永远无新数据。

精确 totalCount 可能需要扫描大量匹配记录，即使当前页只返回 50 条。它不一定总是“全表 Count”，成本取决于过滤、索引与计划；不能在每页默认执行后才抱怨分页慢。若客户只需知道能否继续，去掉精确计数往往更划算。

若业务必须计数，应明确是当前精确值、同快照精确值还是近似值。近似结果可返回 countKind=ESTIMATED 与 asOf 等元数据；单独异步计算也可以。不能把缓存旧数或估算值伪装为精确总数，尤其用于财务与合规报告。

运行监控记录规范化查询类型、pageSize、扫描/返回比、数据库耗时、超时、Cursor 失效率与返回字节。不要把每个 Cursor、用户 ID 或完整过滤 JSON 当指标标签。对大租户/冷缓存/深页分别观察，按租户限流和总并发预算避免一个导出拖垮在线查询。

## 8. Batch API：减少往返，明确失败单位

### 8.1 All-or-nothing 与 Partial Success

批量减少网络往返和部分解析开销，但同时放大单请求的数据库、内存和下游需求。必须限制 item 数、总字节、单项大小、执行时间、并行度和最大响应大小；仅限制 100 项而允许每项 20 MiB，仍可能无法承载。

All-or-nothing（全有或全无）表示这批业务效果共同提交/回滚，适合同一数据库内可短事务完成的相关变更。必须先定义校验失败、授权失败、版本冲突时的整体结果。跨多个远端系统时，单个 HTTP 请求不能凭空实现原子性，可能需要 Saga 等补偿流程，并说明不可逆副作用。

Partial Success（部分成功）表示各项可独立完成，返回每项结果并允许针对失败项恢复。它更利于大批量继续处理，但调用方要理解整批响应成功不等于每项业务成功。不能在 API 文档承诺整体原子，内部却循环单独提交。

### 8.2 一份部分成功契约

~~~json
{
  "requestId": "batch-7",
  "mode": "PARTIAL",
  "items": [
    {"itemId":"a","orderId":"ord-1","expectedVersion":7,"note":"call before delivery"},
    {"itemId":"b","orderId":"ord-2","expectedVersion":3,"note":"leave at reception"}
  ]
}
~~~

~~~json
{
  "requestId": "batch-7",
  "results": [
    {"itemId":"a","outcome":"SUCCEEDED","version":8},
    {"itemId":"b","outcome":"FAILED","code":"VERSION_CONFLICT","retryable":false}
  ]
}
~~~

这份应用契约可选外层 200 表示批次已处理且结果完整可读，每项 outcome 表达业务结果；不要因此让监控只按外层 2xx 统计全部成功。整批 JSON 无效、超限或无资格调用端点时，应使用适当请求级错误，而不是伪造“每项失败”掩盖结构错误。

itemId 用于结果关联，不应依赖响应数组顺序，尤其服务端并行执行时。每项要做对象授权和版本检查，不能因为第一项有权就放开整批。同一资源在一批中出现多次，要拒绝或明确顺序语义；并行执行相互依赖项会让结果不可预测。

207 Multi-Status 源自 WebDAV，不能假设普通 JSON API 客户端都理解它的每项语义。选择自定义 JSON envelope 时，明确外层状态、部分失败结构和 SDK 行为，比仅换一个状态码更关键。

### 8.3 批次键、每项键与超时后的恢复

批次幂等键标识一份批次意图，每项也可能需要独立稳定业务键。网络超时后重发整个批次时，已成功项不应再次执行；重试失败子集也不能因新的批次键丢掉每项去重依据。服务端记录 item 状态与结果，保证业务写入和去重状态协调提交。

同键不同输入应拒绝；处理中同键并发请求应返回明确状态或受控等待；保留期过后不再保证去重，客户端需知道恢复窗口。请求 ID、traceId 和幂等键目标不同，不要用每次尝试随机生成的新 traceId 作为同一业务意图的去重标识。

如果数据库提交后结果写入另一个缓存失败，客户端仍可能看到未知结果。应优先将业务效果和持久结果放入同一事务边界，或设计可恢复状态机。不要声称“加 Redis 键”就提供 exactly-once，更不能对有副作用操作无条件全批自动重试。

## 9. 超大批量与导出：转为有状态 Job

当处理超过同步请求预算，或需要结果持久化/断点恢复，就应提供异步 Job。阈值不只由 item 数决定，还包括预估 SQL 工作、外部调用、数据量、尾延迟和租户配额。所谓“超大批量返回 202”是合理的接口设计，不是每种大小都由 HTTP 标准规定。

~~~http
HTTP/1.1 202 Accepted
Content-Type: application/json
Location: /jobs/job-42
Retry-After: 5

{"jobId":"job-42","state":"QUEUED","statusUrl":"/jobs/job-42"}
~~~

202 只表示接受处理，不保证已完成；接口应在可靠接受边界之后返回，比如任务元数据和待执行记录已持久化。后台 worker 通过有界并发按块处理，记录每项/每块检查点；崩溃后恢复不能重复副作用。提交任务、查状态、取结果和取消都要授权，下载地址也要有访问期限和策略。

状态可以有 QUEUED、RUNNING、SUCCEEDED、PARTIALLY_SUCCEEDED、FAILED、CANCEL_REQUESTED、CANCELLED。取消请求不等于立即撤销已经提交的项，任务状态应记录已完成和未开始部分；若必须补偿，另有补偿状态与失败处理，不能把 CANCELLED 描述为“历史效果全部消失”。

大任务通常分批提交，避免长事务长期持连接和锁。这会牺牲全批原子性，必须与业务接受的失败单位一致。财务导出还要考虑固定集合和固定字段值；只把普通分页循环搬进后台，并没有获得准确快照。

## 10. 部分更新：缺失、null、删除、只读字段

### 10.1 先区分数据模型，再选格式

字段没出现可能表示保持原值；显式 null 可能表示清空业务值，也可能在某种补丁格式中表示删除成员。一个普通 Java DTO 的 null 往往无法区分这几种输入，简单 Bean 拷贝可能把未提交字段清空。需要保留字段存在性，例如专用补丁模型或受控 JSON 树，按字段白名单映射。

创建 DTO、读取 DTO 与更新 DTO 可以不同。ownerId、tenantId、计算价格、审批状态等只读或高权限字段不能因为客户端传了就接受。修改地址必须校验整体地址规则；只更新邮编也可能让地址跨字段不一致，所以应用补丁后还要验证最终候选状态。

### 10.2 Merge Patch 的完整例子

原表述：

~~~json
{"note":"call first","delivery":{"city":"Madrid","floor":"2"},"tags":["gift","priority"]}
~~~

补丁使用 Content-Type: application/merge-patch+json：

~~~json
{"note":null,"delivery":{"floor":"3"},"tags":["gift"]}
~~~

结果是 note 成员被移除，city 保留为 Madrid，floor 改成 3，tags 数组整体变为 ["gift"]。没有提交 delivery.city 表示不改，不等于设 null。若字段必须保留并允许 JSON null，Merge Patch 的删除含义就不够自然，可选明确更新模型或 JSON Patch。

数组不按元素自动合并，重复应用同样的整体替换通常不会继续追加。服务端仍要禁止不支持的根级类型变换和非法字段，而不是把任何合乎 JSON 的补丁都直接写库。

### 10.3 JSON Patch 的操作序列与原子应用

~~~json
[
  {"op":"test","path":"/delivery/city","value":"Madrid"},
  {"op":"replace","path":"/delivery/floor","value":"3"},
  {"op":"add","path":"/tags/-","value":"fragile"}
]
~~~

Content-Type 是 application/json-patch+json。test 检查当前指定值；replace 要求目标按格式规则存在；add 到数组末尾会追加。重复最后一步可能出现多个 fragile，所以 JSON Patch 不默认幂等。数组下标在并发修改中尤其脆弱，应结合版本条件或改用稳定子资源身份。

JSON Pointer 路径中的 ~ 与 / 有转义规则，不能只做字符串 startsWith 白名单就宣称字段授权安全。要用正确解析器，规范化后检查可修改目标，并限制操作数量、深度和复制展开大小。test 也可能成为敏感字段探测渠道，读取权限与写权限都要考虑。

PATCH 的这份修改文档应整体原子应用：某步失败，不让前几步悄悄生效。可在隔离副本上应用并验证最终状态，再通过事务/版本条件提交。把“文档内原子”与“大批多个独立 PATCH 的全批原子”分开；后者只有接口明确承诺并实现才成立。

## 11. ETag/Version 与 If-Match：将条件落实到数据库

读取可返回 ETag: "order-42-json-v7"，客户端 PATCH 时带 If-Match: "order-42-json-v7"。服务端要求当前选定表述版本仍匹配，失败返回 412 Precondition Failed。原文将这里写成“412 或 409”过于含糊：HTTP If-Match 条件失败应按 412；若不是 Header 条件失败，而是订单已发货等业务状态冲突，可用 409。仅在 Body 里约定 expectedVersion 的批量 item，其错误结构是应用契约，应单独定义。

缺少接口要求的条件，可按政策返回 428 Precondition Required。If-Match 使用强比较，弱 ETag 不适合作为该写入保护。ETag 代表选定表述，生成要覆盖与其强语义有关的变化；不能因为数据库某列没变就让实际响应变化仍使用相同强标签。

服务端不能“先读版本验证，隔一会再无条件写”。比较和写入必须原子协调，例如概念 SQL：

~~~sql
UPDATE orders
SET note = :new_note, version = version + 1
WHERE id = :id
  AND tenant_id = :trusted_tenant
  AND version = :expected_version;
~~~

检查受影响行数并结合受保护查询区分目标不可见、版本冲突和业务拒绝，避免越权信息泄露。涉及多字段规则或关联状态仍需合适事务/锁。补丁后的校验失败也不能部分落库。

条件请求不保证业务副作用去重。两个不同请求基于不同版本都可能成功追加一项；相同业务重试还需幂等协议。版本过期后 SDK 不能自动去掉 If-Match 重发，那会主动放弃并发保护，应重新读取、按业务合并或让用户确认。

## 12. 端到端选型与故障推演

教学场景：客服接口改成 Cursor 后仍有遗漏，导出任务又重复修改了部分订单。调查发现 Cursor 按 updated_at 排序，订单变更后跨过边界；批量 worker 在业务提交后、记录内存进度前崩溃，恢复时重新执行。

分页修复先明确目标：实时客服列表使用不可变创建键与 ID，并在界面说明实时变化；精确导出冻结成员和必要字段版本。签名 Cursor 解决篡改，不解决排序键移动，不能通过加密 Token 修复这个问题。

批量修复把每项业务结果和持久检查点放进可协调事务或幂等状态机，恢复读取已有结果，不依赖进程内 index。控制每租户并发与块大小，避免一个大任务占满数据库连接；记录每项终态、可重试失败与结果未知，不把网络超时直接标为未执行。

最终验证要重放排序变化、回填数据、撤权、并发更新、任务崩溃和慢数据库，而不是只测正常首屏。指标分别覆盖在线延迟、扫描成本、任务完成时间、部分失败率和去重命中，避免通过“返回更快的 202”掩盖后台从未完成。

## 13. 面试完整回答与深入追问

### 13.1 “Offset 和 Cursor 怎么选？”

可表达回答：“小数据管理页需要随机跳页时，Offset 简单，但要稳定唯一排序和深度上限。连续滚动的大列表倾向按不可变排序键做 Keyset，Cursor 绑定过滤、排序和授权范围，并限制大小与有效期。它减少位置移动问题，但不自动得到快照；精确导出需冻结集合及字段版本，承担存储和生命周期成本。”

追问：“created_at 加 id 就保证不漏吗？”答案：只在符合相应不变性与集合变化假设下减少特定重复/遗漏。过滤字段变化、回填记录和跨请求新快照仍会改变成员，严格遍历需要额外一致性机制。

### 13.2 “怎样防止用户构造昂贵查询？”

可表达回答：“我白名单字段、运算符和排序组合，类型化绑定值，限制 IN/OR/时间范围/关联深度、pageSize 与响应大小。常用组合有测量后的索引，数据库有执行预算，租户有并发配额。参数绑定防注入，但合法的无界查询仍可能拖垮数据库，所以需要复杂度和成本治理。”

追问：“给所有字段加索引呢？”答案：索引增加写放大、存储和维护，任意组合也不一定复用索引顺序。应围绕实际用例收敛查询能力，复杂分析可用独立读模型。

### 13.3 “批量接口失败怎样让客户端恢复？”

可表达回答：“先约定全批原子还是逐项提交。部分成功返回稳定 itemId、每项结果与错误码，定义批次和每项幂等键，超时后可查询已有结果，只恢复未完成项。超出同步预算转成持久 Job，分块检查点和取消语义明确；202 只表示接受，不表示后台成功。”

追问：“返回外层 200 会不会掩盖失败？”答案：若契约明确是处理批次并返回结果，可以使用，但 SDK 和监控必须检查每项 outcome。整批结构非法仍是请求级错误，不能混为部分业务拒绝。

### 13.4 “Merge Patch 和 JSON Patch 怎么选？”

可表达回答：“简单对象字段修改可用 Merge Patch，但 null 是删除、数组整体替换；需要精确操作序列可用 JSON Patch，但路径授权、数组索引与幂等更复杂。两者都要验证最终领域状态、禁止只读字段，并用 If-Match 将并发条件落实到原子写入。”

追问：“有 test 操作就不需要 If-Match？”答案：test 只验证指定路径，可能未覆盖其他相关变化；是否足够取决于完整不变量，而且必须与提交原子协调。统一版本条件更容易表达基于哪一版编辑，不能把局部比较当全资源保护。

## 14. 扫雷自测与完整答案

### 14.1 一页多取一条，下一页 Cursor 应放在哪条？

放在实际交付页的最后一条，而不是额外探测行。探测行只用于判断后面仍有数据，若用它作严格边界会把它跳过，造成静态数据下也遗漏。

### 14.2 Cursor 内容用 Base64 编码是否防篡改？

不能。编码可逆且可自行构造，需要认证完整性或服务端随机句柄；若含敏感数据还需保密。即使签名正确也要重新检查当前授权范围。

### 14.3 优先级降序、ID 升序，是否两列都用小于？

不对。同优先级时后续 ID 应更大。边界要按每一排序方向展开，且与 NULL、字符排序规则和数据库比较一致，否则分页会漏/重。

### 14.4 物化 ID 后是不是财务快照完成了？

只固定成员，不固定字段值。后续按 ID 读取最新金额会使同一导出数据变化。要冻结值或保留明确可重建版本，并说明时点、权限和保留期。

### 14.5 每页返回 totalCount 为何可能比查 items 更贵？

页面查询可以借索引早停，精确计数通常要处理全部匹配范围。若前端只需 nextCursor，就不必付这个成本；需要计数时区分精确、估算与计算时点，不能伪装精度。

### 14.6 一百项内第八十项失败，前面成功算不算 Bug？

取决于契约。全批原子必须回滚且无不可逆副作用；部分成功应保留前面提交并逐项报告。实现与承诺不一致才是问题，不能仅凭“Batch”一词推断事务范围。

### 14.7 Merge Patch 中 note 缺失和 note:null 是否相同？

不相同。缺失通常保持成员，null 按格式用于移除成员；数组也不是自动逐元素合并。应用若需要显式 null 值，应选择能准确表达该需求的更新模型。

### 14.8 If-Match 失败返回 409 还是 412？

HTTP 前置条件不成立应使用 412；业务状态冲突用 409。Body 内自定义 expectedVersion 和批量每项错误则按明确应用契约处理，不能把几种机制混说。

### 14.9 worker 已提交但未回复，重试能否整批重新执行？

不能无条件重做。需持久每项标识、业务效果和结果，恢复时识别已完成项；外部副作用也需幂等/查询协议。否则网络与进程故障窗口会导致重复修改。

## 15. 验证方案与本次执行边界

静态分页测试构造相同时间不同 ID、多页、恰好整页、少于整页与空集合，遍历后断言无重复无遗漏；正反向和混合排序单独验证，特别检查额外探测行不会被跳过。动态测试插入头部、删除边界、移动排序字段和改变过滤状态，结果应符合公开一致性契约，而不是假定永远快照。

安全测试覆盖篡改/超长/过期 Cursor、跨租户复用、换过滤与排序、权限撤销、未知字段和复杂查询；SQL 性能测试比较小/大租户、深 Offset、不同索引组合、Count 与无 Count，并记录实际计划。索引建议需要目标数据分布验证，不以单次快查询证明规模化。

批量测试覆盖同资源重复、部分授权失败、版本冲突、全批回滚、逐项恢复、并发同键、提交后崩溃与取消时在途项。PATCH 测试覆盖缺失/null/删除、数组、非法路径、只读字段、某步失败原子性、并发旧版本和领域跨字段校验。

本次用 Python 对 12 条含相同主排序值的记录、每页 3 条的键集遍历做了实际检查，降序与混合方向均完整覆盖且没有重复，额外探测行未丢失。该实验只验证内存比较与取页逻辑，不证明索引计划、授权或数据库并发行为。SQL、HTTP 与 JSON 示例**未在真实数据库或端到端服务运行**；已人工核对比较谓词、Cursor 位置、格式语义、原主题覆盖和所有正文小节自足性。上面的验证矩阵是落地要求，不是已通过的运行结果；不得把 PostgreSQL 17 的计划与隔离细节当作所有数据库保证。

## 16. 面试前速记

- 唯一排序解决平局，不自动冻结集合；Offset 是位置，Keyset 是值边界。
- DESC 向后常用小于，混合方向逐字段展开，NULL 和时间精度须对齐。
- 多取一条只用于探测，Cursor 来自最后交付项。
- 签名防篡改，授权防越权，快照防跨页漂移，三者不同。
- Filter 白名单还要限制运算符、结构与成本；索引按实际查询组合设计。
- totalCount 不免费，精确/估算/时点明确，在线与导出采用不同预算。
- Batch 先定义提交单位，每项结果与幂等可恢复，Job 的 202 不等于完成。
- Merge Patch 的 null 删除、数组替换；JSON Patch 有路径与操作序列成本。
- If-Match 失败 412，业务状态冲突 409；版本检查必须与写入原子协调。
