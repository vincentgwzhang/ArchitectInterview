# 05. REST、GraphQL、gRPC 与异步 API 的选择

> 本章要解决的是“谁需要什么结果、何时需要、失败后如何恢复”，然后才是选通信技术。阅读后应能从业务约束推导方案，解释执行机制，识别看似成功但业务未完成的情况，并给出迁移与验证办法。
>
> 版本范围：HTTP 语义与缓存按 RFC 9110/9111；GraphQL 核心语法与执行示例以 October 2021 规范为基线，不假设后续增量传输扩展；Protobuf 示例使用 proto3（含 optional），gRPC 行为按官方通用文档，具体库与代理能力需在项目锁定版本后验证；Kafka 语义参考 4.1 文档；AsyncAPI 使用 3.0.0 概念。本章不声称这些是所有技术的最新版本。教学场景、预算和指标均为假设，不是用户项目经历或性能基准。

## 一、先区分四种技术实际解决的层次

### 1.1 它们不是四个完全互斥的网络协议

REST（Representational State Transfer，表述性状态转移）是一种架构风格，强调资源标识、统一接口、无状态交互和缓存等约束；工程里常说的“REST API”通常是面向资源的 HTTP API。JSON 只是常见表示格式，HTTP/2 也可以承载 REST，不能把 REST 等同于 HTTP/1.1 + JSON。严格 REST 还包含通过超媒体引导交互的要求，只有名词 URL 并不足以证明满足全部约束。

GraphQL 是有类型的数据查询语言及执行模型：客户端提交字段选择，服务端依据 Schema（类型契约）验证并执行 Resolver（字段解析函数）。它不规定必须用某种数据库，也不由核心规范固定某一种传输。常见部署用 HTTP 处理查询和变更，用额外传输方案承载订阅。

gRPC 是远程过程调用（Remote Procedure Call，RPC）框架，通常用 Protobuf 定义消息与服务，生成客户端 Stub 和服务端接口，并通过 HTTP/2 传输。它让远程调用具有类似方法调用的编程界面，但网络延迟、部分失败、权限和版本偏差仍然存在。

异步 API 描述的是交互时序：发送方提交消息后，不要求业务处理在同一次请求中完成。Kafka 是分区日志平台，SQS 是托管队列服务，Event 是“事件”这一消息语义，三者不是同一分类层次。异步也可以由 HTTP 创建任务再查询完成状态实现，不一定要引入消息中间件。

因此，面试中先把“资源接口、查询表达能力、RPC 编程模型、异步时序”分开。例如 REST 的 POST 可以只受理后台任务；gRPC 可以使用非阻塞客户端，但仍在同一个 RPC 内等待最终回复。“异步代码”不自动等于“业务解耦”。

### 1.2 三个成功时刻必须分别定义

以生成财务报表为例，至少有：请求被校验并持久受理、任务被执行器取走、报表成功生成且可下载。HTTP 202 或消息代理确认，只能证明契约规定的受理阶段成功，不能直接显示“报表生成完成”。

同步交互中也有差别：数据库已经提交，但响应丢失，客户端超时；客户端不知道结果，并不代表服务端失败。对于扣款、创建订单等写操作，各种协议都要定义业务操作 ID、幂等去重、结果查询和重试边界。幂等（Idempotency）指重复提交同一个逻辑操作不会重复产生业务效果，不等于每次网络响应必须完全一样。

选择技术前要回答：调用方必须立即得到确定结果，还是只要拿到可追踪的受理凭证？允许多久的数据陈旧？结果未知时谁负责查证？这三问往往比序列化格式更早决定架构。

## 二、REST：资源语义、成熟生态与可控的聚合

### 2.1 一次资源请求怎样工作

假设公开商品接口：

~~~http
GET /products/p-42?fields=id,name,price HTTP/1.1
Host: api.example.test
Accept: application/json
~~~

服务端认证、校验字段白名单，读取商品领域模型，将允许公开的字段映射为表示，再返回响应。GET 必须用于读取，不能借查询参数触发扣款；请求无状态意味着每次请求带足处理所需上下文，不意味着服务端不能有数据库、缓存或登录系统。

资源与 HTTP 方法形成统一语义，便于 SDK、网关、调试工具和跨组织调用者理解。创建订单可以 POST /orders，返回新资源位置；读取订单则 GET /orders/{id}。客户端不应依赖数据库表结构，API 里的 Order 是业务契约，不必与 ORM Entity 一一对应。

适合：外部合作方、公开 API、普通资源操作、团队希望用通用 HTTP 工具治理的系统。局限：复杂界面可能需要多个资源，统一的商品表示也可能携带当前屏幕用不到的字段。不能为了坚持“纯资源”而把业务指令拆成一串危险的客户端更新：取消订单应是受权限和状态机控制的一次业务操作，不能让前端直接改订单、库存、退款三张表。

### 2.2 “可缓存”有前提，个性化响应尤其危险

公开商品响应可以使用：

~~~http
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: public, max-age=60
ETag: "product-p42-r7"
Vary: Accept-Language
~~~

缓存可在新鲜期直接复用；过期后客户端带 If-None-Match，表示未变时服务器可返回 304，节省主体传输。ETag 是表示的校验器，必须与实际表示版本相符。若不同 fields 参数形成不同 URL，缓存应区分它们；若语言由请求头决定，Vary 声明该表示随什么头变化。

订单、余额等私人数据不能套用上述 public 示例。可按风险选择 private 缓存，或用 no-store 禁止存储；no-cache 不是“完全不存”，而是复用前需验证。鉴权请求、共享缓存和响应控制存在专门规则，不能期待 CDN 自动识别全部租户边界。上线要用两个身份实测是否串数据，同时验证刷新、注销、权限变化后的行为。

缓存减少回源，代价是陈旧性与失效治理；如果库存必须在下单时准确，页面商品缓存不能作为扣库存依据，写路径仍需权威检查。REST 的缓存能力来自正确使用 HTTP，不是路径长得像资源就自动生效。

### 2.3 Over-fetch 与 Under-fetch 不只有 GraphQL 一个解法

Over-fetch 是取回不需要的字段，例如移动端只显示名称却下载长描述；Under-fetch 是一次调用不够，需要再查关联对象。假设订单页面顺序发五次请求，每次网络往返假设 80ms，光串行往返就约 400ms，尚未算业务处理。并行可以缩短等待，但会增加并发与下游压力；这里是预算推演，不是某协议实测成绩。

可以增加受控 fields 参数、批量查询，或用 BFF（Backend for Frontend，面向特定前端的后端）返回页面需要的聚合视图。BFF 把跨域请求合并在服务器附近，也集中处理部分失败，但增加一层发布、监控与业务映射维护。它适合界面需求稳定、消费者数量有限的场景；若每个终端都不断要求不同字段组合，维护众多页面端点可能比引入 GraphQL 更贵。

无论 REST BFF 还是 GraphQL，一次外部请求都可能展开为几十次内部调用。减少客户端请求数不代表减少数据库工作量。聚合层必须限制列表长度、并行扇出和总时间，并区分必需数据与可降级数据，例如“推荐服务失败可不展示推荐，订单金额失败不能伪造为零”。

## 三、GraphQL：把字段选择权交给客户端，也把成本治理带进来

### 3.1 Schema、查询和 Resolver 如何衔接

下面是一个完整的最小教学类型定义，不包含变更与订阅：

~~~graphql
type Query {
  orders(first: Int!): [Order!]!
}

type Order {
  id: ID!
  totalMinor: Int!
  buyer: Buyer
}

type Buyer {
  id: ID!
  displayName: String!
}
~~~

ID 是标识而非可计算的数字；感叹号表示非空，方括号表示列表。orders 不为空，列表内的 Order 也不为空；buyer 可以为空，便于表达买家不可访问或依赖暂时失败。此例的金额采用最小货币单位且限定在 GraphQL Int 的有符号 32 位范围内；大金额应设计并解释自定义标量或字符串契约，不能悄悄溢出。真实多币种接口还必须返回币种。

客户端查询：

~~~graphql
query OrderCards($n: Int!) {
  orders(first: $n) {
    id
    totalMinor
    buyer { id displayName }
  }
}
~~~

变量 n 假设为 20。执行器先解析语法、检查字段和变量类型，再运行顶层 orders Resolver；它调用应用服务取得订单，每个 buyer 字段再由相应 Resolver 取得买家，最终按选择集组合响应。变量绑定避免自己拼接查询字符串，但 Resolver 内 SQL 仍须参数化。Schema 通过不代表请求便宜：first: 100000 仍然符合 Int!，必须额外限制业务范围。

领域边界要保留在应用服务：查 Order 时校验主体与租户范围，查 Buyer 时校验是否允许看到该字段。不能把 ORM 全图直接暴露为 Schema，否则一个看似普通关联可能绕过领域授权、引发懒加载扫描或泄露内部字段。客户端能选择字段，不意味着客户端有权定义数据库查询或跨租户读取。

### 3.2 N+1、DataLoader 与权限隔离

如果查订单用一次 SQL，20 个订单分别查买家，再发 20 次 SQL，就是 1+N。N 增大时即使单次查询很快，总连接占用和网络等待也会恶化。

DataLoader 是常见的“收集键 → 批量读取 → 按键还原”的加载工具，不是 GraphQL 内置保证。一次请求中把 buyerId 收集起来，用受租户和权限约束的批量接口查询，然后按原键顺序返回等长结果。数据库返回顺序不可靠，缺失项也不能被移除后让后续位置错配。请求内缓存避免同一买家重复加载，但不能代替分布式缓存。

例如原键 [b2,b1,b2,b9]，数据库只返回 b1、b2。正确对齐结果是 [买家2,买家1,买家2,null]，而不是把数据库两行直接返回。重复键是否由工具预先去重取决于配置，批量函数都必须遵守该工具的长度与顺序契约。应先在请求级创建加载器并绑定认证上下文；把不同用户共用同一个只按 buyerId 缓存的加载器，可能绕过新权限或串租户。

批量化有边界：20 个对象如果来自不同权限域或不同下游，未必能合为一个 SQL。批次太大还会超过参数限制；因此限制每批键数，控制并行批数，对缺失、无权限和依赖失败分别约定语义。变更后若同一请求还要读，必须清除或更新相应缓存，否则会读到请求内旧值。

### 3.3 深度限制不足以代表查询成本

一个深度只有两层、却列出十万个订单的查询，可能比深度五层但每层一个对象更贵。治理至少要同时考虑列表上限、嵌套乘数、别名重复选择、批量操作数、昂贵字段和主体配额。

一个自定义成本模型可以是：每个订单基础权重为 1，选择 buyer 时每订单再加 2，则 first=20 的估算成本为 20×(1+2)=60。这里的“2”是本服务根据执行路径校准的相对权重，不是 GraphQL 标准，也不是毫秒。若有嵌套列表，还需乘以子列表上限。对超出预算的查询应在访问下游前拒绝，而不是等连接池耗尽后再取消。

Persisted Query（持久化查询）将操作文本登记为 ID 或哈希。只有“生产环境仅允许已审核操作”的白名单策略，才能把未知查询排除；仅仅用哈希减少传输、允许未命中后上传任意文本，不能获得同样保护。参数仍可能造成高成本，所以已登记操作也需分页上限和授权。关闭 Introspection（类型自省）最多减少暴露，不能替代成本与权限控制。

执行阶段再用总 Deadline、下游超时、并发上限与熔断兜底；客户端取消后停止无用工作，并防止“每字段重试三次”造成扇出放大。按操作名或已登记 ID 统计成本、数据库查询数、依赖耗时；不要用任意查询全文当指标标签，既高基数又可能包含敏感值。

### 3.4 部分数据、非空传播与缓存

如果 buyer Resolver 失败，本例允许返回：

~~~json
{
  "data": {
    "orders": [
      {"id": "o-1", "totalMinor": 12900, "buyer": null}
    ]
  },
  "errors": [
    {
      "message": "Buyer unavailable",
      "path": ["orders", 0, "buyer"],
      "extensions": {"code": "DEPENDENCY_UNAVAILABLE"}
    }
  ]
}
~~~

extensions.code 是本 API 约定，不是核心规范统一业务码。客户端必须同时检查 data 与 errors，不能只看到 HTTP 200 就记录全成功。HTTP 状态如何映射还取决于传输规范、内容类型和实现，核心 GraphQL 规范不等于“所有错误必须 200”。

如果失败的是非空字段，错误会沿父级传播至最近可空位置；把 buyer 改成 Buyer! 会使本例 Order 失效，而 [Order!]! 又可能使整个 data 变为 null。非空承诺提升客户端类型确定性，也扩大故障影响范围，不能只为减少前端判空而把所有字段标为非空。Query 中多个字段也不意味着跨数据库快照；Mutation 顶层字段按规范串行执行，并不自动获得跨服务原子事务。

同一路径 /graphql 上不同查询的内容不同，通用 CDN 不容易只按 URL 直接复用 POST 响应；可以设计已登记 GET 查询、私有响应缓存，或客户端按实体 ID 规范化缓存。缓存键仍需包含变量、身份与影响表示的上下文；实体缓存需处理更新和权限变化。GraphQL 不是不能缓存，而是较多缓存语义需在应用层明确定义。

### 3.5 Schema Evolution 与订阅边界

演进应先增加新字段，保留旧语义，标记弃用，观测实际操作使用，迁移消费者后删除。新增必填输入会破坏旧调用；输出新增枚举值也可能让旧客户端穷举分支崩溃。已登记操作可在 CI 对新 Schema 做校验，但仅验证语法不足以证明金额单位、排序、权限或运行成本兼容。

Subscription（订阅）让一次操作持续接收源事件并执行选择集，它解决实时通知，不自动提供离线持久保存、重放或恰好一次。使用 WebSocket/SSE 时还要定义连接认证与撤权、重连游标、断线补读、慢消费者和连接资源。若用户离线一天后必须补齐通知，需持久事件或通知表，不能只保留内存中的在线连接。仅需简单单向进度推送时，HTTP SSE 可能比完整 GraphQL 订阅栈更省维护成本。

## 四、gRPC：强契约与流式调用，不能隐藏远程失败

### 4.1 Protobuf 与 Stub 的实际价值

接口定义语言 IDL 把方法和消息结构放在 .proto 文件中，编译器插件生成 Stub 与消息类。调用者按类型构建请求，框架负责序列化、传输、解析和状态；服务器实现对应接口并执行应用服务。字段编号参与二进制编码，JSON 字段名式的思维不能直接套过来。

~~~proto
syntax = "proto3";
package interview.orders.v1;
option java_multiple_files = true;
option java_package = "example.orders.v1";

service OrderService {
  rpc GetOrder(GetOrderRequest) returns (Order);
  rpc WatchOrder(GetOrderRequest) returns (stream Order);
}

message GetOrderRequest {
  string order_id = 1;
}

message Order {
  string id = 1;
  int64 total_minor = 2;
  string currency = 3;
  optional string note = 4;
  reserved 5;
  reserved "legacy_status";
}
~~~

这是可交给生成工具的教学契约，尚未提供服务器实现。order_id 为空仍是合法编码，业务服务必须校验，并按身份判断该订单可否读取。optional note 可以表达“未提供”和“提供空字符串”的区别；不带显式存在性的 proto3 标量通常只暴露默认值，不能直接用于“缺失不改、零值重置”的补丁语义。字段存在性规则也不能机械套到 message、oneof 或其他版本语法。

删除历史字段后保留编号与名字，防止以后复用造成旧数据被解释为新含义；reserved 的名字对 JSON/文本等路径也有意义。二进制能读不等于业务兼容：把金额从分改为元，编码完全合法却会造成财务错误。ProtoJSON 与二进制有不同兼容边界，经过 JSON 网关时要额外测试字段名、枚举和大整数表示，不能只跑二进制互通测试。

强类型减少拼错字段和跨语言手写映射，但引入生成工具、运行库、插件和 SDK 发布管理。团队需锁定相互兼容的版本，审查 Schema Diff，并测试“新服务+旧客户端”和“旧服务+新客户端”，不能只让全部最新版本一起通过。

### 4.2 四种调用形态与 Streaming 的容量边界

| 形态 | 消息方向 | 场景与要补的控制 |
|---|---|---|
| Unary | 一请求、一响应 | 查订单；设置 Deadline，限制响应大小 |
| Server Streaming | 一请求、多响应 | 连续订单状态；定义断线恢复点和订阅寿命 |
| Client Streaming | 多请求、一响应 | 分块上传；限制累计大小、校验完整性，定义部分接收是否可恢复 |
| Bidirectional Streaming | 两方向各自连续发送 | 实时协作；定义应用级序号、确认、慢端与重连行为 |

流内消息顺序不等于多个连接间全局顺序。断开后建立新流，框架不会凭空知道上次业务处理到哪一条，必须用序号或游标恢复。HTTP/2 的流量控制限制传输中的数据，不代表应用队列有界；如果 onNext 后把每条消息丢入无界工作队列，内存仍会持续增长。

长期连接会消耗内存、连接额度和代理状态，且升级时需要优雅关闭与重连分散，避免所有客户端同时重连。双向流两端还需避免互相等待对方读完再发送造成停滞。判断是否需要 Streaming，要看业务是否持续产生结果以及对延迟、重放的要求，而不是因为框架支持就把所有查询改成长连接。

### 4.3 Deadline、取消、重试和业务结果未知

Deadline 是最晚愿意等到的时间点，Timeout 是一段等待时长。gRPC 默认不替应用设定合适期限，应由业务预算显式设置。假设入口预算 300ms，前序已经耗时 80ms，返回编码预留 20ms，下游最多只能使用约 200ms，不能每一跳重新获得完整 300ms。Java 等实现支持传播已有期限，但应用仍应核对上下文和拦截器是否保留它；不是所有语言默认行为相同。

超时后客户端得到 DEADLINE_EXCEEDED，不证明写事务回滚；取消也只能通知和协作停止，已经提交的扣款不会被“取消 RPC”撤销。服务器要把取消传给可取消任务，对已经开始的数据库或外部调用明确其实际支持范围。需要补偿时执行新的业务指令并记录状态。

UNAVAILABLE 可以是瞬时网络或依赖不可用，INVALID_ARGUMENT 是输入问题，PERMISSION_DENIED 是权限拒绝；不能对所有非 OK 状态一律重试。对可重试操作设置总期限、尝试上限、退避和抖动，并保证幂等。gRPC 有限定条件下的透明重试及可配置策略，不能概括为“完全不会自动重试”或“默认替你安全重试所有调用”。RPC 重试机制不提供业务去重。

写接口可带 operation_id，并由服务器在持久化事务中去重。第一次提交后响应丢失，第二次携同 ID 查询或返回已记录结果。流式 RPC 中应用已处理若干条后失败，通常要按业务检查点恢复，而不是从头无条件重放。重试责任应集中协调，网关、客户端、服务内三层各重试三次，可能放大到 27 次尝试。

### 4.4 Browser、代理、安全与真实性能

浏览器通常不能像原生客户端一样直接控制完整的原生 gRPC 传输细节，常需 gRPC-Web 与代理或服务端适配。所用客户端、模式及代理对不同 Streaming 形态的支持必须实测，不能把原生双向流能力直接许诺给 Web。TLS 终止、HTTP/2、超时、消息大小、尾部状态和负载均衡都要在生产链路验证；只在 localhost 通不能证明公网代理支持。

内部服务也需认证和授权。mTLS（双向 TLS）能验证连接双方工作负载身份，但不自动判断“服务 A 是否可读取租户 B 的订单”；仍要基于可信身份执行业务权限。用户上下文转发要防伪造，不能相信调用方随便填的 tenant-id 元数据。日志应记录方法、状态、延迟和关联 ID，避免原样打印令牌与完整消息体。

Protobuf 的紧凑编码、代码生成和连接复用可能降低某些开销，但“gRPC 总比 REST 快”没有普遍保证。数据库、网络地域、负载、压缩、消息大小和连接数都可能主导延迟。需要比较相同语义和负载下的 p95/p99、吞吐、CPU、内存、网络和运维成本；p99 是 99% 请求不超过的延迟，不能把各阶段 p99 相加当成严格端到端 p99。若瓶颈在慢 SQL，先优化 SQL 通常比换协议更有价值。

## 五、异步 API：用时间解耦换取可追踪的状态与恢复责任

### 5.1 Command、Event 与 Queue/Log

Command（命令）表达希望指定能力执行的意图，例如 GenerateInvoice，可能被拒绝；Event（事件）表达已发生的事实，例如 InvoiceIssued，不能把“还没成功开票”命名为已开票事件。发送命令并收到代理确认，不等于业务接受命令，更不等于开票完成。

工作队列通常由竞争消费者分担任务；发布订阅让不同订阅方独立处理一份事件。Kafka 的主题分区是有保留期的日志，消费者组维护消费位置，不同组可独立读取；SQS 标准队列通过接收、可见性超时与删除来处理任务，不能把某个 Kafka 分区的有序日志语义当作所有队列保证。选择产品要依据保留/重放、路由、分组顺序、规模和团队运维能力，而不是只看“有消息队列”四个字。

适合：邮件、报表、审计投递、订单后的物流联动等不必占住前台请求的工作。同步库存确认或即时支付授权如果是下单前置条件，不能用“消息最终会处理”替代明确结果；可改业务为待确认状态，但必须让产品接受失败、取消与等待体验。

异步 HTTP 入口可以把“受理凭证”做成资源：POST /reports 成功持久受理后返回 202，并给 Location: /report-jobs/j-7。客户端 GET 该地址，读取本系统定义的状态 ACCEPTED → RUNNING → SUCCEEDED 或 FAILED；SUCCEEDED 才附可受权访问的下载地址，FAILED 给稳定错误码和可否重试的说明。状态转换应由服务端控制，并按租户与所有者鉴权，不允许客户端任意把 RUNNING 改为 SUCCEEDED。取消请求若与完成竞态，要返回实际终态或明确取消尚在进行，不能承诺一定撤销。

提交时用幂等键避免请求重传创建两份昂贵报表；客户端轮询设置退避和上限，也可辅以 SSE（Server-Sent Events，服务器通过 HTTP 持续向客户端单向推送事件）提示状态变化，断线后仍以持久任务资源为准。把任务设为 FAILED 不代表此前所有外部效果已回滚，若报表过程中还做了收费等动作，需另有费用状态和补偿规则。这比单纯“丢进队列返回成功”多出状态存储与恢复成本，却让失败能被解释和操作。

### 5.2 Outbox 与消费幂等解决两个不同崩溃窗口

问题一：数据库提交订单后进程崩溃，事件没发出；若先发事件再写库，又可能产生订单不存在的幽灵事件。Outbox（事务发件箱）把订单和待发消息写入同一个本地数据库事务，独立转发器持续发送待发记录。转发器在代理已接受后、标记已发之前崩溃，仍可能重复发送，所以它解决数据库与事件的可靠衔接，不消除重复。

问题二：消费者已写数据库，尚未确认消息就崩溃，消息被再次投递。把消费标识和业务修改放在同一事务中：

~~~text
begin transaction
  insert processed_message(consumer_name, event_id)  // 唯一键
  apply local business change
commit
acknowledge message
~~~

唯一键冲突表示该消费者已处理，确认重复消息即可；若业务修改失败，整个事务回滚，去重记录不能单独提交。consumer_name 用于区分独立业务处理方，同一事件可被发票与通知各处理一次；event_id 在同一次转发重试中保持不变。去重窗口必须覆盖可能的消息重放期限，不能任意一天后清空。

这里仅保护同一数据库内的修改。事务中调用外部支付后本地回滚，并不能撤回支付；需外部幂等键、持久操作状态、结果查证或业务补偿。Kafka 的事务与恰好一次能力有具体覆盖范围，不能扩张为任意数据库、邮件和支付都全局恰好一次。SQS 标准队列则明确要求应用容忍重复。业务效果的“恰好一次”需要精确定义边界，不能只报一个中间件配置名。

### 5.3 乱序、积压、毒消息与最终一致性

假设订单状态事件包含 order_id、event_id、aggregate_version。相同订单按同一键路由到同一 Kafka 分区，有利于保留该分区的顺序，但并行处理、重试主题、多个生产者或迁移都可能改变业务观察顺序，不能省略应用防护。

若事件携带完整状态快照，消费者可在原子条件更新中仅接受更高版本，避免“已取消”被旧“已创建”覆盖；若是余额增量，版本 12 不能简单覆盖缺失的版本 11，应等待补齐、查权威源重建或按契约报错。比较版本与写入必须原子完成，否则并发仍可能让旧值最后落库。跨订单通常不需要全局顺序，强行所有消息一个分区会限制并行度。

队列只能吸收暂时峰值，不能修复长期吞吐不足。教学假设：每秒流入 1000 条、处理 800 条，积压以 200 条/秒增长；持续十分钟约积压 120000 条。峰值后若流入降至 400 条/秒、处理仍为 800，净清理速度 400 条/秒，还要约五分钟。实际还需考虑失败重试、消息大小与分区热点。应监控最老未完成消息年龄和业务完成延迟，不只看队列条数；达到容量或期限边界时限制受理、丢弃仅明确允许丢弃的消息，或扩容处理能力。

毒消息是持续处理失败的消息，例如不支持的版本、缺失必需业务数据。用有限重试与退避区分瞬时故障，超过阈值进入 DLQ（Dead-Letter Queue，死信队列），同时告警并指派处理人；死信不代表业务完成。修复后按原 ID 安全重放，检查去重、顺序和是否已被补偿。要求严格顺序时跳过毒消息会形成语义缺口，可暂停该业务键并隔离其他键，但需权衡可用性。

最终一致性（Eventual Consistency）不是“总有一天会对”：需要在故障恢复且处理机制继续工作的前提下收敛。应约定正常完成时间、超时报警、补偿/对账、永久失败终态，以及前台如何显示处理中。读模型落后时，写后读取可返回权威结果、操作回执，或显式版本水位；不要让用户把暂时未显示误认为操作丢失而重复提交。

### 5.4 异步契约、Schema Registry 与安全

建议消息至少明确事件 ID、业务实体 ID、事件类型、版本、发生时间和载荷。关联 ID 用于连接同一业务过程，因果 ID 指向直接触发该消息的前一操作；它们不替代业务去重 ID。时间戳受时钟偏差影响，不能直接当全局序号。长期流程可能跨多条 Trace，需要保留关联关系，而不是把一个 HTTP 请求无限延长。

AsyncAPI 文档描述应用的 channel（通道）、message（消息）与 send/receive operation（发送/接收操作）等契约；3.x 的组织方式与 2.x 不同，复制旧版 publish/subscribe 示例前要对齐版本。Schema Registry（模式注册服务）保存并检查消息格式的演进兼容性，但具体兼容模式由产品和配置决定，它不是 Kafka 核心协议自动提供的统一业务语义保证。两者可以配合，不能替代交付、顺序、保留期、失败责任和 SLA（Service Level Agreement，对外约定的服务水平及责任）的文字约定。

例如给 OrderCreated 新增可选字段通常比删除必需字段风险低，仍要测试老消息重放给新消费者、新消息给旧消费者；金额单位变更即使结构校验通过也不兼容。消息在日志中可能保存数周，迁移时不能只检查当天在线消费者，还要考虑历史数据、回滚版本和离线订阅方。

Topic/Queue ACL（访问控制表）限制谁能发和读，载荷中的 tenant_id 还需可信来源与消费端约束。广播个人数据会增加副本、保留和删除治理成本；应最小化载荷，必要时只给受权引用并由消费者读取。不要把访问令牌塞入长期保存的事件，重放时它既可能失效，也可能泄露权限。

## 六、用同一个业务场景比较并组合

### 6.1 先写可验证的选择依据

| 维度 | 应澄清的问题 | 对选择的实际影响 |
|---|---|---|
| 消费者与网络 | 浏览器、移动端、合作方还是内部受控服务？代理支持什么？ | 公网通用工具偏向 HTTP API；内部生成 SDK 可支撑 gRPC；浏览器复杂读图可考虑 GraphQL |
| 同步结果 | 受理即可，还是必须立刻确定是否扣款？ | 长流程适合异步状态机；即时业务条件必须有权威结果 |
| 数据形状 | 表示稳定还是多个 UI 的字段组合快速变化？ | 稳定资源/页面用 REST/BFF 即可；选择自由度足以抵偿治理成本时再选 GraphQL |
| 延迟与吞吐 | 瓶颈是 RTT（Round-Trip Time，网络往返时间）、序列化、SQL 还是排队？ | 先测瓶颈；协议更换不能代替容量治理 |
| 契约与版本 | 谁升级客户端，历史消息保留多久？ | 不受控外部客户端需长期兼容；生成接口与消息也需双向版本测试 |
| Streaming | 实时、单向/双向、断线补读分别需要什么？ | gRPC 流适合受控链路；SSE/订阅与持久日志解决不同部分 |
| 缓存与一致性 | 能否共享，能旧多久，写后读怎么办？ | 公共 GET 易结合 HTTP 缓存；私人聚合需隔离；异步读模型要显式陈旧性 |
| 故障和运维 | 谁重试、谁补偿，团队能否值守代理/消息平台？ | 可靠性能力不足时减少技术栈，避免用新组件增加无人负责的故障面 |

表格是思考入口，最终决策不能只打主观分。先排除不满足硬约束的方案，例如合作方只能调用普通 HTTPS；再比较满足约束的方案在维护、成本和演进上的差别。成本包括计算、网络、平台、生成工具升级、监控、值班和消费者迁移，而不只是单次请求费用。

### 6.2 订单平台的完整推导

教学假设：合作方创建订单，Web 与移动端显示差异很大的订单页面；库存服务由公司控制；开票允许一分钟内完成。团队已有 HTTP 与数据库运维经验，消息平台已有专职团队，尚无 gRPC 平台。

第一步，公开入口用 REST。创建操作携幂等键，校验后提交订单；如果库存确认是订单成立前置条件，就在预算内获取权威预留结果，或把订单明确定义为待确认，不能在消息尚未处理时返回“已保证有货”。

第二步，前端先用 REST BFF 聚合。如果多个前端的字段差异和变更频率持续增加，且团队愿意维护成本分析、字段授权和 Schema 治理，再迁移读聚合到 GraphQL。它仍调用应用服务，不直接穿透各数据库；订单金额等必需字段失败时给明确错误，推荐信息等可选字段失败时可部分降级。

第三步，内部库存调用暂用已有 HTTP。只有实测发现连接/序列化或 Streaming 能力是主要问题，且收益超过生成 SDK、代理、链路与升级成本时，才引入 gRPC。不能为了凑齐“公开 REST、前端 GraphQL、内部 gRPC、领域事件 Kafka”而部署全部技术；该组合可行，但需要每一层有独立理由。

第四步，订单事务通过 Outbox 发出已成立的事实，开票消费者幂等处理，记录开票状态，提供状态查询；一分钟只是业务目标，必须有监控和超时处理，不能靠“异步”自动保证。若开票永久失败，订单与发票关系按业务策略补偿或人工处理，不能静默丢入死信。

此方案把必须即时确认的行为留在权威路径，把容许等待的工作移出请求链。其代价是多种契约与状态都要治理；若团队不能承担，保留较少技术也可能是更好的架构选择。

### 6.3 如何演进与验证，而不是一次换完

迁移从一个可逆读路径开始，先固定原行为契约，再让新实现离线回放或影子读取比较结果、权限与成本。影子流量不能重复执行扣款等写操作，也要计入额外下游负载。用特定消费者或小比例流量灰度，保留回退入口和 Schema 兼容窗口；停止旧接口前确认实际调用与历史重放需求都已迁移。

验收至少包含四类证据：相同语义下的输出与权限测试；兼容性和旧客户端测试；带真实消息大小、并发与慢依赖的负载测试；超时、断线、重复、乱序及消费者崩溃的恢复测试。比较成功率时区分“HTTP/RPC 成功”“消息受理成功”和“业务最终完成”，否则异步系统可能把错误移到后台后看起来成功率更高。

## 七、从症状定位问题

### 7.1 页面只发一次请求，数据库却被打满

先按 GraphQL operation ID 或 REST 聚合入口定位下游次数与耗时，再查每个 Resolver/聚合步骤的列表长度、批次、缓存命中与连接等待。若是 N+1，用请求级批量化；若查询本身返回十万行，先收紧分页与成本上限。只增加 Web 线程可能把数据库压得更严重。修复验收应比较相同页面负载的 DB 查询数、扫描行、尾延迟及授权结果，而不只看外部请求数。

### 7.2 RPC 频繁超时，写入却偶尔重复

沿操作 ID 查服务器是否已经提交，再核对各层期限和重试次数。若已提交但响应未到，应恢复已记录结果；若服务器未去重，先修业务唯一性与事务边界。延长超时可能减少表面错误，却增加排队与资源占用，不是根治。应同时观测排队、依赖耗时、CPU 与连接池，判断是预算不合理还是系统过载；在真实代理链路检查是否有更短的中间超时。

### 7.3 消息都已接收，用户仍一直看到处理中

分别检查 Outbox 未发送、代理积压、消费者失败、业务数据库提交和读模型推进。按 event_id/业务 ID 找最后可靠检查点；只看生产者 ack 无法判断消费者业务完成。若消费位点持续前进但业务没更新，检查是否提前确认、异常被吞或死信被当成功；若业务已完成但页面没变，检查缓存、投影版本与前端刷新。补救从真实状态恢复并安全重放，不能直接把状态批量改为成功掩盖缺失效果。

## 八、可直接表达的面试回答与深入追问

### 8.1 “这四种方式怎么选？”

完整回答示例：“我先确认消费者、同步结果要求和可接受的数据陈旧性。对跨组织资源接口，我通常从 HTTP API 开始，使用通用鉴权、缓存和契约工具。多个 UI 对复杂关联数据有持续变化的选择需求时，我会考虑 GraphQL，但同时预算 Resolver 成本、字段权限和部分失败。内部受控调用若强类型、多语言生成或 Streaming 的收益足够，可选 gRPC，并统一 Deadline、代理与版本治理。对允许延迟完成的流程，我用异步消息与状态查询解耦，承担重复、顺序、重放和对账责任。我会根据现有平台能力尽量减少技术栈，而不是用协议名称替代业务设计。”

追问：“为什么不所有接口都 GraphQL？”答：“简单稳定资源可以用更低治理成本的 HTTP 接口。GraphQL 的查询自由度会把不受控工作量带到服务器；若没有成本分析、权限和 Schema Owner，减少前端改动可能换来后端容量与安全风险。只有自由度确实有业务价值时才值得。”

追问：“为什么不都异步？”答：“异步把即时失败转为状态机中的等待、重试和终态。需要立刻授权支付或确认库存的业务不能只返回受理成功；若愿意改成待确认，必须连同用户体验、超时、补偿与查询一起设计。”

### 8.2 “gRPC 看起来是方法调用，为什么还要幂等？”

完整回答：“Stub 隐藏了序列化，但没有消除网络的不确定性。服务端提交写入后响应丢失，客户端只知道超时；重试可能再执行一遍。因此我用稳定操作 ID、持久唯一约束和与业务同事务的结果记录识别重复，并提供结果查证。取消 RPC 也不是撤销已提交事务。”

追问：“只给 UNAVAILABLE 配重试够吗？”答：“不够。状态只能描述调用观察，不能证明业务没执行。还要检查操作语义、总预算、重复保护、退避和其他层是否也重试。读取虽无写副作用，也可能因过载重复读取而加重故障，所以同样需要容量和次数限制。”

### 8.3 “怎样证明 GraphQL 或异步真的改善性能？”

完整回答：“先定义相同业务输出与可靠性条件，再测端到端完成延迟、每个入口的下游工作量、CPU/内存/网络和成本。GraphQL 少了几次客户端往返可能改善页面延迟，也可能触发更多 SQL。异步降低受理延迟不等于缩短完成延迟，我会单独测排队时间和最终完成 SLO（Service Level Objective，量化的服务水平目标）。没有这种口径一致的测量，我不会声称换技术就更快。”

追问：“API p99 降了但发票晚了十分钟？”答：“这说明指标只覆盖受理。把订单成立到发票成功的业务时延作为另一项 SLI（Service Level Indicator，服务水平指标），监控积压年龄、失败率和恢复时长，决定扩容、限流或调整业务承诺，不能把后台等待从报表里隐藏。”

## 九、扫雷自测：答案与推理

### 9.1 REST 必然不能 Streaming，gRPC 必然比 REST 快吗？

**答案：都不是。** HTTP API 可用流式响应或 SSE；gRPC 提供明确的流式方法模型，但速度取决于相同业务下的实际瓶颈。用 REST/HTTP/1.1/JSON 与 gRPC/HTTP/2/Protobuf 混为一组比较还同时改变了多个变量，不能把结果归因给单一架构风格。应保持语义、硬件、并发与可靠性条件一致再测。

### 9.2 GraphQL first=100000 通过类型检查，为什么仍要拒绝？

**答案：类型有效不代表资源预算有效。** Int! 只限制输入类型与非空，不限制业务列表规模；大列表与嵌套字段可能放大 SQL、RPC 和内存。先校验 first 上限、估算字段成本和嵌套乘数，再用执行超时和并发限制兜底。只做深度限制抓不到浅而宽的查询。

### 9.3 DataLoader 查询返回顺序与请求键不同，会怎样？

**答案：不重新对齐可能把甲的数据返回给乙。** 批量函数按键索引构建结果，再按原键顺序返回等长数组，缺失项填约定的 null 或错误。权限过滤不能把缺失项直接删除。请求级加载器还需绑定主体与租户，避免共享缓存泄露；性能优化不能改变身份边界。

### 9.4 GraphQL 返回 data 和 errors，监控只看 HTTP 200 可以吗？

**答案：不可以。** 部分字段已失败，业务是否成功取决于该字段对场景是否必需。需观测操作级和字段级错误，客户端处理可空数据；非空错误会向上传播，甚至使整个 data 为 null。HTTP 层成功与 GraphQL 执行成功要分开，具体 HTTP 状态映射按实际传输实现约定。

### 9.5 删除 proto 字段 5，下一版用编号 5 表示新字段安全吗？

**答案：不安全，应保留编号和旧名字。** 老消息携带字段 5，新消费者可能按新含义解释；即使线格式可解码，语义也会损坏。新增字段使用新编号，并测试双向版本组合。经过 ProtoJSON 的接口还要检查 JSON 层兼容，不能仅以二进制能解析作为证明。

### 9.6 客户端 DEADLINE_EXCEEDED 后可以立刻用新 ID 再扣款吗？

**答案：不可以。** 第一次可能已提交，新 ID 会被视为另一笔业务。沿用原操作 ID 查证或幂等重试，遇到结果未知保留可恢复状态。Deadline 限制等待，取消传达停止意图，两者都不等于支付撤销或数据库回滚。

### 9.7 已用 Outbox，还要消费端去重吗？

**答案：要。** Outbox 转发器可能在代理接收后、标记已发前崩溃而重发；消费者也可能提交数据库后、确认消息前崩溃而重收。去重标识与本地业务修改需同事务，提交后再确认。外部副作用不在这个事务内，仍要外部幂等和结果查证，不能声称全局恰好一次。

### 9.8 同一订单按相同键发送 Kafka，就能忽略版本吗？

**答案：不能。** 它有助于同分区有序，但消费端并行、失败转移路径和重放仍需审视。快照可按版本原子拒绝旧值；增量遇到缺口不能直接跳过，须补齐或重建。跨连接、跨分区和跨业务实体的全局顺序并未自动获得。

### 9.9 队列十分钟积压 120000 条，处理速率 800 条/秒，何时清完？

**答案：还取决于新流入。** 若流入 400 条/秒，净消化 400，需约 300 秒；若流入仍为 1000，积压继续增加；若停止流入，理想情况下约 150 秒。还需计入重试、热点和暂停。单报消费者吞吐，无法推导用户等待时间与恢复承诺。

### 9.10 已有公开 REST，是否应立即加 GraphQL、gRPC 和 Kafka？

**答案：不应只为统一技术蓝图而增加。** 先定位字段变化、内部瓶颈和长流程需求，再逐一判断新增能力是否超过治理成本。可以只加异步报表，也可以保持内部 HTTP；架构一致性应体现在安全、契约、可观测与恢复原则，而不是所有团队强用同一协议或凑齐所有组件。

## 十、面试前速记与验证边界

- 先分清交互时序、业务语义和传输机制，再谈产品。
- REST：资源与统一 HTTP 语义；缓存要声明且隔离身份；复杂读可用 fields、批量或 BFF。
- GraphQL：选择集不等于低成本；Resolver 守领域与权限；批量加载需顺序对齐与请求隔离；非空影响失败传播。
- gRPC：IDL、生成 Stub 与四种流；字段编号不可复用；Deadline/取消不回滚业务；浏览器与代理能力单独验证。
- 异步：受理不等于完成；Outbox、消费幂等、版本/顺序、死信与对账各解决不同问题。
- 一切选型都要回答：谁拥有契约、谁承受失败、谁值守、怎样演进和怎样证明收益。

本章协议片段、GraphQL 类型/操作/响应、Protobuf 契约及事务流程均为教学示例，不是完整运行项目。编写时检查了示例间的类型与字段一致性、原主题覆盖和全部正文小节的自足性；算术与批量结果对齐逻辑进行了独立验证。未运行 GraphQL 执行器、protoc/gRPC 服务、真实 HTTP 缓存或 Kafka/SQS 故障实验，不能据此宣称协议集成、权限隔离或负载目标已通过。工程落地应执行第六节所述四类验证。

## 十一、一手来源与适用范围

来源用于核验，可选阅读；理解与答题所需的机制和边界已在正文解释。

- [RFC 9110：HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html)、[RFC 9111：HTTP Caching](https://www.rfc-editor.org/rfc/rfc9111.html)：资源交互所用 HTTP 语义与缓存规则，不把 REST 风格等同于单一传输版本。
- [GraphQL October 2021 规范](https://spec.graphql.org/October2021/)：类型、验证、执行、非空错误传播与 Mutation 顺序；本文不把特定 HTTP/订阅传输实现当核心规范。
- [GraphQL Security](https://graphql.org/learn/security/)：查询需求控制、深度/宽度/成本与受信操作；[DataLoader 官方仓库](https://github.com/graphql/dataloader)：批量结果对齐与请求内缓存。通用治理指南，具体 Java/JS 集成行为以所用库版本为准。
- [gRPC Core Concepts](https://grpc.io/docs/what-is-grpc/core-concepts/)、[Deadlines](https://grpc.io/docs/guides/deadlines/)、[Retry](https://grpc.io/docs/guides/retry/)：调用形态、期限传播与重试；[gRPC-Web 官方仓库](https://github.com/grpc/grpc-web)：浏览器适配及当前支持范围。库和代理升级需复核。
- [Protobuf proto3 Guide](https://protobuf.dev/programming-guides/proto3/)：编号、保留字段、存在性与演进；[ProtoJSON](https://protobuf.dev/programming-guides/json/)：JSON 映射与兼容边界，不能与二进制规则混用。
- [Apache Kafka 4.1 Design](https://kafka.apache.org/41/design/design/)：分区日志、交付与事务语义范围；[SQS 标准队列至少一次投递](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/standard-queues-at-least-once-delivery.html)：应用需容忍重复。二者不可互相套用保证。
- [AsyncAPI 3.0.0](https://www.asyncapi.com/docs/reference/specification/v3.0.0)：应用、通道、消息和操作描述；不把规范文档视为代理交付保证。
