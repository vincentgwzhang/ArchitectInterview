# 01. REST 资源建模、HTTP 语义与状态码

> 本章以 RFC 9110（HTTP Semantics）、RFC 9111（HTTP Caching）、RFC 9457（Problem Details）为协议基线，PATCH 格式分别注明。HTTP/1.1 报文用于展示语义，不代表 API 只能运行在 HTTP/1.1。所有订单场景和参数均为教学设计，不是实际项目经历。

## 1. REST 的价值：把业务契约建立在可共享的语义上

REST（Representational State Transfer，表述性状态转移）是一组架构约束，不是“路径用名词、响应是 JSON”的同义词。它强调客户端与服务器分离、无状态交互、可缓存性、统一接口、分层等；完整 REST 还包括通过超媒体表达可用交互。很多工程中的所谓 REST API 实际是资源导向的 HTTP API，应准确说明采用了哪些约束，而不因没有超媒体就无法设计可靠接口。

资源（Resource）是系统提供身份和交互边界的概念，例如订单、取消申请、导出任务。表述（Representation）是某时刻向调用者提供的可交换数据，如 JSON；它不是数据库行的原样复制。资源身份、内部存储与表述结构解耦，才能在更换数据库、拆分服务、增加字段时保持契约稳定。

无状态不是服务端不能保存订单或会话数据，而是请求处理不依赖调用者省略的会话上下文来理解这次操作；客户端应携带必要请求信息和凭证。HTTP 应用可以使用 Session，但要说明这与严格 REST 无状态约束的关系，而不能用“我没有进程内变量”证明协议无状态。

贯穿例子：电商订单可创建、查询、取消；取消可能触发库存释放和退款。业务目标是调用方能判断“操作是否完成、失败怎样恢复、重试会不会重复副作用”。方法、状态码与 Header 应服务于这个目标。单独把 /cancelOrder 改名为 /cancellations，并不会自动提供这些保证。

## 2. 资源建模：从身份、生命周期和不变量决定 URI

### 2.1 集合、成员与关系

~~~http
POST /orders
GET /orders/ord-42
GET /customers/cus-7/orders
POST /orders/ord-42/cancellations
GET /orders/ord-42/cancellations/can-9
~~~

/orders 是订单集合，POST 表示由服务端按此资源语义处理创建请求；/orders/ord-42 是已识别成员；客户下的订单集合表达受客户范围约束的查询。路径可用复数名词是常见约定，不是 HTTP 规范硬性要求；真正重要的是一致的身份、方法和响应契约。

嵌套深度应反映有意义的所属关系，不必把数据库外键链全部展开。若明细不能脱离订单存在，/orders/{id}/items 合理；若商品有独立身份与生命周期，应有独立 /products/{id}。多层路径会放大客户端对内部模型的依赖，也增加转移归属时的 URI 稳定性问题。

URI 中出现 tenantId 或 customerId 不代表授权已经成立。必须验证当前主体是否可在该范围操作，并确认路径父子关系真实存在。否则调用者可把自己的客户 ID 与别人的订单 ID 拼在一起绕过范围检查。

### 2.2 把复杂动作建模成资源，还是 Command Endpoint

取消不是简单修改 status 字段：可能需要理由、操作者、时间、退款状态和拒绝原因。建模取消申请资源有助于跟踪生命周期、查询结果与审计。创建申请成功可以是 201，但它只表示“申请资源已创建”；订单取消是否完成由申请状态表达，不能让客户端误解。

若动作极简单、没有独立生命周期，明确的命令端点也可以合理，例如 POST /orders/{id}/cancel。它采用资源导向 API 的工程折中，应文档化幂等与失败语义。不要为了名词纯度凭空创建五层空资源，也不要把所有业务动作都变成可任意覆盖 status 的 PATCH。

建模要保护不变量：已发货订单不能按普通规则直接取消；允许取消时，订单状态、取消记录与待发布事件需在可证明的一致性边界协调。HTTP 表达不能代替数据库事务、幂等键和补偿流程。

### 2.3 表述与输入模型不要直接等同 Entity

创建订单输入只允许商品、数量、配送信息等可写字段；订单 ID、价格计算结果、所有者、审计字段由服务端决定。否则直接把 JSON 绑定持久化 Entity，可能允许调用者修改 ownerId 或 totalPrice，这叫过度绑定风险。

读取表述可以按角色隐藏敏感字段，但要设计缓存隔离。身份相同资源的不同语言、媒体类型、权限视图可能是不同表述；ETag 和缓存键也必须与实际表述一致。内部数据库 version 可辅助构造验证器，但不能不加分析把它当作所有视图的强 ETag。

## 3. HTTP 方法：安全、幂等与业务副作用

### 3.1 Safe 不表示服务器什么都不能改变

安全（Safe）方法表示客户端没有请求改变业务状态。GET 可以产生访问日志、统计或缓存填充，这些附带行为不使它变成业务写接口。GET 不应用于扣款、删除、确认收货等动作，因为浏览器、爬虫、链接预取和缓存可能自动触发读取。

HEAD 获取与 GET 相对应的响应元数据而不返回响应内容，适合检查资源/缓存信息；服务端不应为 HEAD 执行业务写入。OPTIONS 可描述通信能力，但不是身份认证或业务授权替代品。即使路径名看起来只读，也必须检查其实际实现是否改变业务状态。

GET 请求体没有普遍定义的语义，代理和客户端支持不一致。不要依赖 GET Body 传递关键过滤条件；普通过滤用 Query，大而敏感的复杂查询可设计 POST 查询资源/搜索接口，同时明确其缓存和副作用规则。

### 3.2 Idempotent 不表示响应必须相同

幂等（Idempotent）关注重复相同请求的预期作用与执行一次相同，而不是每次状态码、时间戳或日志都一样。DELETE 第一次删除成功返回 204，再次返回 404，目标仍是不存在，并不因此违反幂等性。协议也允许每次写审计日志等附带动作，业务关键效果仍需受控。

幂等方法便于在连接断开、响应丢失时考虑重试，但不保证任何重试都安全：调用方仍应尊重前提条件、并发变化、重试预算与具体契约。重复 DELETE 不能实现成“每调用一次退款一次”，否则目标状态虽相同，业务副作用却错了。

| 方法 | 常见意图 | 安全 | 协议幂等属性 | 主要边界 |
|---|---|---|---|---|
| GET/HEAD | 读取表述/元数据 | 是 | 是 | 不执行用户请求的业务写操作 |
| PUT | 在指定 URI 创建或替换可写表述 | 否 | 是 | 不偷偷改成累加操作 |
| PATCH | 按补丁文档修改 | 否 | 不保证 | 由格式和操作决定是否幂等 |
| POST | 按目标资源语义处理输入 | 否 | 不保证 | 创建、命令等需业务幂等设计 |
| DELETE | 移除目标 URI 与当前功能的关联 | 否 | 是 | 不等同物理清除全部历史数据 |

### 3.3 PUT 与 PATCH 必须说明“完整”和“部分”的范围

PUT 的客户端选择目标 URI，例如 PUT /preferences/current 替换该资源的可写配置。若资源不存在且允许创建，成功可返回 201；替换已存在资源可返回 200 或 204。完整替换针对定义好的可写表述，不意味着客户端必须写服务端 ID、计算字段或内部存储列；缺失可写字段如何处理要在契约中说明。

PATCH 不是任意 JSON 天然获得“只更新非 null 字段”。JSON Merge Patch（application/merge-patch+json）对对象字段进行合并，null 表示移除成员，数组通常整体替换；如果业务必须区分“字段存在且值为 null”和“删除成员”，它不总是合适。

JSON Patch（application/json-patch+json）是一组 add、remove、replace、move、copy、test 操作，通过路径描述修改。向数组末尾 add 元素重复执行可能重复追加，故不能默认幂等。服务端还需限制可修改路径、操作数量和展开成本，不能让补丁修改租户/价格/权限字段。

PATCH 文档的应用应遵循原子性要求，不能第三步失败却悄悄保留前两步的部分变更；这通常需要业务与事务实现配合。涉及并发编辑时应结合 If-Match，而不是仅因请求字段少就认为不会丢更新。

## 4. 状态码不是装饰：表达调用方下一步该做什么

### 4.1 成功的四种主要阶段

200 表示请求成功，常带查询结果或处理结果；201 表示创建了资源，可用 Location 告诉客户端资源位置；202 表示已接受处理，但尚未完成，甚至后续可能失败；204 表示成功且没有响应内容，不能再附一份 JSON Body。

不要为了“统一 DTO”给所有请求返回 200。客户端若需要知道是否创建、是否仍在处理中，强行塞进 status 字段会绕开协议工具。反过来，也不能仅因返回 201 就推断支付、发货等所有后续工作均已完成，应明确创建的到底是哪一个资源。

异步接受需要可靠的承诺边界：收到 202 前是否已持久化任务？进程崩溃后能否继续？任务结果能保留多久？这些不是 202 状态码自动提供的能力。应提供任务状态资源或其他受支持的结果通知机制，不让客户端只能盲目重复提交。

### 4.2 请求、认证与政策错误

| 状态 | 适用判断 | 调用方常见动作 |
|---|---|---|
| 400 Bad Request | 请求语法、结构或一般无效请求 | 修正输入，不原样无限重试 |
| 401 Unauthorized | 缺少有效认证凭证 | 按认证协议处理；响应应含适用 WWW-Authenticate |
| 403 Forbidden | 服务端理解但拒绝执行 | 检查权限/政策，不靠无限刷新 Token 修复 |
| 404 Not Found | 目标无当前可用表述，或不愿透露存在性 | 检查地址/权限；不等同已证明永久删除 |
| 405 Method Not Allowed | 目标不支持该方法 | 参考 Allow Header 选择支持方法 |
| 406 Not Acceptable | 无法提供满足 Accept 的表述 | 调整可接受响应媒体类型 |
| 413 Content Too Large | 请求内容超限 | 缩小内容或使用适合上传机制 |
| 415 Unsupported Media Type | 请求内容媒体类型/编码不支持 | 修正 Content-Type 和格式 |
| 422 Unprocessable Content | 内容格式可理解但指令语义不能处理 | 按字段/业务约束修正 |

401/403 的日常简记是“未认证/无权限”，但不能只靠登录页面判断。Token 过期或 audience 错误属于凭证不可接受；403 也可表达不只角色缺失的拒绝政策。隐藏对象存在性可用 404，但相应计数、错误细节和时序也要避免泄露。

400 与 422 在 API 实践中有约定差异，应在团队保持一致。例如 JSON 破损选 400，数量为负选 422；不要宣称所有业务拒绝都只能用 422。状态应辅助客户端判断恢复方式，稳定业务码解释更具体原因。

### 4.3 冲突、条件失败与限流

409 Conflict 表达与当前资源状态冲突，例如已发货订单不能按普通流程取消。412 Precondition Failed 表达请求 Header 中的条件不成立，例如 If-Match 的版本已过时。若接口要求条件更新但请求未带前置条件，可以用 428 Precondition Required。不能把缺条件、条件过期、业务状态拒绝都机械归为 409。

429 Too Many Requests 表达请求超过限额，可以返回 Retry-After 提示等待，具体按用户、租户、凭证、IP 还是全局计数由服务契约决定。Retry-After 可以是等待秒数或 HTTP 日期，但不是保证到点必成功；客户端仍需有抖动、次数和总时限，避免大量请求同一秒再次冲击。

错误码体系中应区分“配额已满且需人工处理”和“瞬时速率超限”。同样一个 429，恢复策略可能不同，不能让 SDK 自动无限重试直到预算耗尽。

### 4.4 5xx 与结果未知：失败不是自动重试许可

500 表示服务端遇到未预期情况；502 常用于网关/代理收到不合适的上游响应；503 表示临时不可服务或过载，可给恢复提示；504 表示作为网关/代理等待上游超时。这些状态应对应实际部署角色，不是所有数据库错误都固定映射 502。

依赖不可用可能使本服务无法履行契约，但不应无差别转发依赖的状态和内部文本。用户库存不足不是 500；内部数据库连接泄漏也不应伪装成用户参数错误。分类会影响告警、SLO 与客户端行为。

最危险的情况是写入已提交而响应丢失。客户端看见超时或 5xx 可能只知道“结果未知”，不能得出“未执行”。需要幂等请求键、资源查询和对账协议。即使错误标记 retryable=true，SDK 也必须确认重试该操作不会制造第二次业务效果。

## 5. 创建与取消的完整交互设计

### 5.1 创建订单：201 与 Location

以下报文是契约示例，省略 Host、认证和内容长度等传输细节，非已运行测试。假设订单创建事务已可靠提交，后续履约仍通过业务状态表达。

~~~http
POST /orders HTTP/1.1
Content-Type: application/json
Accept: application/json
Idempotency-Key: req-create-7

{"items":[{"productId":"p-1","quantity":2}]}
~~~

~~~http
HTTP/1.1 201 Created
Content-Type: application/json
Location: /orders/ord-42
Cache-Control: no-store

{"id":"ord-42","state":"PENDING","links":{"self":"/orders/ord-42"}}
~~~

Location 指向新资源，不是描述当前响应媒体类型；Content-Type 描述实际响应内容，Accept 表达客户端接受的类型。links 是本 API 自定义的导航形状，不应冒称通用标准超媒体格式。若想让链接引导交互，还需定义关系、方法、输入与状态变化等约定。

Idempotency-Key 在这里是明确约定的应用契约，不应仅因 Header 名称常见就认为所有服务器、网关和 SDK 具有相同实现。服务端要定义键的作用域、有效期、并发同键处理与相同键不同 Body 的拒绝方式；数据库唯一约束等机制协调创建与去重结果。同一键不能跨租户共用结果，也不应保存无限长或含敏感数据的键。

### 5.2 取消操作：接受请求不等于完成退款

~~~http
POST /orders/ord-42/cancellations HTTP/1.1
Content-Type: application/json
Idempotency-Key: req-cancel-9

{"reason":"CUSTOMER_REQUEST"}
~~~

~~~http
HTTP/1.1 202 Accepted
Content-Type: application/json
Location: /operations/op-9
Retry-After: 3
Cache-Control: no-store

{"operationId":"op-9","state":"PENDING","statusUrl":"/operations/op-9"}
~~~

这里契约选择“处理尚未完成”的 202，并明确把 Location 约定为操作监控地址；不是 HTTP 要求所有 202 必须如此。客户端轮询操作资源时，GET 成功返回 200，Body 可为 RUNNING、SUCCEEDED 或 FAILED。GET /operations/op-9 的 200 表示成功读取任务状态，不代表订单取消一定成功。

任务可能因已发货竞争而 FAILED，也可能订单已取消但退款仍处理中。状态模型需区分这些阶段和可补偿边界。用户取消任务本身也不是无条件撤销远端退款；应定义已开始、已完成时能否取消。任务资源属于谁、何时过期、到期后如何查最终订单，都必须说明。

若设计选择同步创建取消申请资源并返回 201，同样可以合理，但务必强调“创建申请”与“实际取消完成”的不同。状态码选择要匹配本接口承诺，不存在所有取消 API 唯一正确的一个码。

## 6. 条件请求：缓存校验与并发写入各解决什么

### 6.1 ETag 和 If-None-Match 降低重复传输

ETag 是服务端给某个选定表述的验证器，不要求一定是内容哈希，也不应由客户端猜测其格式。强 ETag 表达字节层面的严格等价条件，弱 ETag 以 W/ 标记，适用于较弱等价判断。生成策略要考虑内容协商、编码和权限视图，不能复用一个标签代表不同内容。

~~~http
GET /orders/ord-42 HTTP/1.1
Accept: application/json
If-None-Match: "order-42-json-v7"
~~~

若已授权且选定表述仍匹配，GET/HEAD 可返回 304 Not Modified，不带响应内容，让客户端复用缓存表述。304 不是 204：前者说明已有表述仍可用，后者是成功但无内容。若客户端没有缓存却收到 304，它无法凭空恢复内容，应检查缓存/代理状态。

验证器不是授权凭证。必须先按正常请求检查身份、权限和目标语义，不能因为 ETag 相同就跳过对象授权。否则用户 A 缓存的标签可能帮助用户 B 探测对象或错误复用数据。

### 6.2 If-Match 防止丢失更新

用户甲乙都读取 v7；甲先修改成功得到 v8；乙若无条件覆盖，可能把甲的新值抹掉。乙带 If-Match: "order-42-json-v7"，服务端在执行修改时要求当前验证器匹配，失败则 412，让乙重新读取并处理冲突。

关键是“比较和修改”要原子协调。HTTP 层先比较一次，随后无条件 SQL UPDATE，中间仍可能被第三个请求改写。可把版本条件带入数据库更新并检查受影响行数，使协议条件落到真实写入边界。多个相关资源的不变量还需事务/锁等保证，单个 ETag 不提供全局事务。

If-Match 用强比较，不能把弱 ETag 当可靠的丢失更新保护。If-Match: * 检查当前表述是否存在，不检查是否仍是客户端读到的具体版本。客户端指定 URI 创建且不允许覆盖时，可考虑 If-None-Match: *，让已有资源导致条件失败。

条件失败后不能自动去掉 If-Match 再重试，那相当于主动放弃并发保护。只有用户/业务确认重新基于最新状态执行，才生成新的条件请求。条件请求和业务幂等也不同：前者防旧版本覆盖，后者协调重复同一业务意图。

## 7. 缓存：性能收益必须与权限和新鲜度一起设计

Cache-Control 控制响应如何保存与复用。no-store 要求缓存不要存储该交换；no-cache 允许存储，但复用前需验证；private 限制共享缓存保存，仍可允许用户代理的私有缓存；max-age 指定新鲜期。no-cache 不是“绝对不缓存”，private 也不是“禁止所有缓存”。

公开商品列表可采用明确短 TTL，减少读取成本；敏感订单可采用更保守策略，如 no-store，或经过风险评估的 private + 验证。不应因后端有认证就假设 CDN 配置永远不会缓存用户数据；Authorization、Cookie 与共享缓存规则、平台覆盖配置都要实际验证。

Vary 描述哪些请求 Header 影响选定响应，缓存据此区分表述，例如 Accept-Language。它不是业务授权协议，也不应随意让每个高基数字段成为缓存维度，否则命中率低、容量膨胀。若响应随主体而变，应明确禁止共享或采用严格隔离策略，不能只寄希望 Vary 随便填一个值就安全。

写入成功后，本地和中间层缓存失效并不自动覆盖所有关联路径。例如更新订单成员后，/customers/{id}/orders 列表和统计仍可能旧。需要 TTL、失效通知、版本键或读取一致性策略；强一致展示会提高成本，短暂陈旧可以接受的场景应明确承诺窗口。

某些失败响应也可能被缓存，404 尤其要小心：创建资源前的“不存在”如果被长期保存，新资源创建后客户端仍看不到。对权限隐藏的 404 更需避免跨用户复用。测试应穿过真实代理/CDN，而不是只对应用进程 curl。

## 8. 错误契约：Problem Details 让机器决策与人类诊断分开

RFC 9457 定义 application/problem+json。type 标识问题类型，title 是简短概述，status 若提供应与实际 HTTP 状态一致，detail 解释这次发生的情况，instance 可标识这次问题发生。code、traceId、fieldErrors 是应用扩展，不是该 RFC 保证所有 API 都有的标准字段。

~~~http
HTTP/1.1 409 Conflict
Content-Type: application/problem+json
Cache-Control: no-store
~~~

~~~json
{
  "type": "https://api.example.invalid/problems/order-not-cancellable",
  "title": "订单当前不能取消",
  "status": 409,
  "detail": "订单已进入配送流程，请使用售后流程。",
  "instance": "/problems/occurrences/err-7",
  "code": "ORDER_NOT_CANCELLABLE",
  "traceId": "trace-7"
}
~~~

客户端依据稳定 type/code 选择动作，不通过解析中文 detail 判断错误。文案可以本地化，机器标识不随措辞改变；新增错误类型时客户端仍应有未知类型回退，不能直接崩溃或把未知错误视为成功。type URI 在本例是占位文档地址，生产应有稳定解释与恢复指引。

字段校验可附 fieldErrors，但路径和错误码格式需要约定；不要把密码、银行卡输入原值或内部 SQL 放进 detail/扩展。traceId 用于关联受控日志，不是让公网用户凭此查询内部任意日志。instance 也不要求公开内部堆栈页面。

异常映射要覆盖过滤器/安全链、反序列化、领域拒绝与提交失败，不能只保护 Controller 正常进入后的异常。网关可能自行返回另一种格式，SDK 必须能安全处理非 JSON 错误。HTTP 状态是处理结果的权威信号，不能 Body 写 500、外层仍 200，让监控、缓存和调用方各作不同判断。

## 9. 安全与可观测：资源引用不是访问许可

URI 和 Query 可能进入浏览器历史、代理日志、监控和 Referer 等路径，所以不要把 Access Token、密码和敏感个人资料放进去。HTTPS 保护传输路径，不会自动清除端点日志和历史。Body 也需要脱敏与访问控制，不能把“移到 Body”当作全部安全治理。

每个资源访问都做 Ownership/Tenant Authorization，批量、导出、计数、子资源和操作状态同样受保护。路径 ID 不能直接决定可信租户；选择不可猜 ID 只减少枚举，不能替代授权。对删除/退款/审批等动作还需检查当前状态和操作者角色，字段级可写权限也应限定。

Correlation ID 是关联一次调用链的标识，W3C Trace Context 等是另一种可采用的标准传播机制；任意自定义 X-Correlation-ID 不因普遍出现而自动是 HTTP 核心标准。外部 ID 需要长度、字符和日志安全校验，避免注入、伪装或高基数指标；必要时生成内部可信 ID，保留受控映射。

观测分别记录 HTTP 状态、稳定业务码、延迟、依赖原因和结果未知次数。不要将每个路径中的订单 ID 当作指标标签，应用路由模板聚合，避免时间序列爆炸与个人数据暴露。日志记录请求体也应按字段最小化，而不是为了调试输出全部资料。

## 10. 失败推演：订单创建成功，客户端为何重复下单

教学场景：服务端事务已经提交，但网络在 201 响应到达前断开。客户端不知道订单 ID，自动以新键重试 POST，创建第二张订单。监控显示两次请求都没有明显数据库错误，业务却出现重复订单。

首先区分“未执行”“已执行”“未知”。连接错误只证明交付失败，不证明业务没发生。客户端应保留本次业务意图的同一幂等键，用它查询/重试；服务端同键、同主体、同输入应映射到同一个结果。相同键不同输入应拒绝，而不是拿旧响应假装新请求成功。

去重记录与订单写入必须协调。若先建订单后单独写缓存去重，崩溃窗口仍会重复；若先标成功后事务失败，可能返回不存在订单。可通过同库事务和唯一约束持久化请求记录/订单/结果，或采用清晰的可恢复状态机，处理并发同键与处理中请求。

随后检查外部副作用。如果创建订单后调用支付，即使订单去重成功，支付也可能重复；需将同一业务标识传播到受支持的支付幂等协议，并可靠记录结果。HTTP 的 POST/201 不提供 exactly-once；可实现的是在明确定义范围、期限和故障模型下去重业务效果。

本章说明接口必须承诺什么；具体去重表、锁竞争与补偿实现应在系统设计中独立落实，不能用一个 Header 名称掩盖实现缺口。

## 11. 面试完整回答与深入追问

### 11.1 “怎样设计创建、查询、取消订单 API？”

可表达回答：“我先明确订单与取消申请的身份和生命周期。POST /orders 创建订单并在提交后返回 201 与 Location；GET 成员和集合保持安全读取。取消若涉及退款等长流程，我会创建可跟踪操作，202 表示接受而非完成，提供状态地址、终态错误和结果保留策略。并发修改用条件请求，重复提交用作用域明确的幂等协议，所有查询与状态资源都受租户和归属授权。”

追问：“为什么不直接 PATCH status=CANCELLED？”答案：若取消只有简单状态替换且业务明确允许，可以设计；但实际退款、库存释放和审计使它通常不是任意字段更新。命令/申请资源更能表达过程，避免让调用者跳过状态机。

### 11.2 “PUT、PATCH、POST 的区别？”

可表达回答：“PUT 针对客户端已选择 URI 的创建/替换，可写表述范围要定义清楚，预期效果幂等。PATCH 按媒体类型定义的补丁修改，不保证幂等；POST 按目标资源语义处理，常用于创建或命令，也不默认幂等。选择不是看 Body 大小，而是看身份由谁决定、修改语义和重复执行效果。”

追问：“重复 PATCH 设置名字是否幂等？”答案：相同替换操作可以幂等，但重复向数组追加就可能增加多个元素。必须按具体补丁操作判断，不能由方法名统一推导。

### 11.3 “409 和 412 怎样选？”

可表达回答：“If-Match 等请求前置条件不成立用 412；当前业务状态与操作冲突，如已发货不能取消，可用 409；若政策要求条件请求却没提供，可用 428。对每类错误提供稳定 type/code，让客户端知道是重新读取合并、修改业务动作还是补条件。”

追问：“版本过期后自动拿最新版本覆盖呢？”答案：这会隐藏并发编辑冲突。应重新读取并按业务合并或让用户确认，不能悄悄放弃原前提。

### 11.4 “为什么不能所有错误都返回 200？”

可表达回答：“HTTP 状态会被客户端、网关、缓存和监控共同使用。把失败塞进 200 Body，会使重试、告警和成功率失真，还可能缓存错误结果。我会用适当状态表达通用阶段，再用 Problem Details 的稳定类型和业务码表达具体原因，公众消息与内部诊断分开。”

追问：“返回 500 就安全重试吗？”答案：不保证，写入可能已提交。应按操作幂等性和结果查询协议决定，限制重试次数和总预算，而不只看状态码。

## 12. 扫雷自测与完整答案

### 12.1 GET /orders/{id}/cancel 能否通过“文档说会取消”变合理？

不能。它违反 GET 的安全语义，预取、爬虫和链接访问可能无意触发动作。应改用有明确写语义的方法，并保留认证、授权和防重机制；文档不能让中间层知道该 GET 不应自动访问。

### 12.2 DELETE 第一次 204，第二次 404，是否不幂等？

仍可幂等。幂等比较预期作用，删除一次与多次后的资源目标状态相同，响应可以不同。若每次都再次退款，就在业务副作用上破坏幂等，不能只看资源已不存在。

### 12.3 202 后 GET 任务返回 200 且 state=FAILED，是否自相矛盾？

不是。202 表示接受处理，GET 的 200 表示成功读取任务表述，业务失败由该表述的终态说明。契约应提供稳定失败原因和恢复方式，而不是让客户端只看轮询状态码猜业务结果。

### 12.4 no-cache 和 no-store 哪个允许存储？

no-cache 允许存储，但复用前要验证；no-store 要求不存储。处理敏感资料时不能误把 no-cache 当彻底禁止缓存，也不能认为 private 禁止浏览器私有缓存。

### 12.5 If-Match: * 是否能保证用户读到的版本未变化？

不能。它主要要求当前存在表述，不校验具体版本。丢失更新保护要使用适合强比较的实际验证器，并使比较与写入原子协调；弱 ETag 也不能替代这个要求。

### 12.6 同一请求键同 Body，跨两个租户能否共用去重响应？

不能。去重命名空间和结果读取必须包含可信授权范围，否则一方可获得另一方订单结果。键不可猜也不能代替权限。应同时定义输入指纹、有效期与并发状态。

### 12.7 422 是否应该包含原始密码帮助用户排障？

不应该。字段错误应给安全的字段标识与原因码，不回显秘密或内部实现。错误响应可能被浏览器、代理、日志和支持系统留存，最小披露必须贯穿全链。

### 12.8 204 能否附 {"success":true}？

不能把它作为有内容响应使用。需要 JSON 结果选合适的 200；选 204 就没有响应内容，客户端也不应强行 JSON 解析。统一封装工具要尊重这一边界。

### 12.9 内容一样但租户不同，ETag 相同能否跳过授权返回 304？

不能。条件验证不是权限证明。先确定调用方可访问哪个选定表述，再处理验证条件；缓存也要正确隔离，避免重用别人的响应或泄露存在性。

## 13. 验收方法与本次执行边界

逐个接口检查资源身份、输入可写字段、方法副作用、成功阶段、失败恢复、并发与重复语义。创建测试应覆盖响应丢失后同键重试、相同键不同输入、并发同键和键过期；取消覆盖可取消/已发货/重复提交、任务失败和任务状态越权。

协议测试断言状态、Content-Type、Location、WWW-Authenticate、Allow、ETag 和缓存指令等与契约一致；验证 204/304 无响应内容，错误 status 与实际状态一致。条件更新应同时启动两个基于旧版本的写入，确认不会丢更新，而不只顺序测 Header 解析。

缓存测试需穿过实际代理/CDN，覆盖语言/媒体类型变化、主体变化、404 后新建和写入后的列表刷新；安全测试覆盖成员、集合、子资源、任务、导出和字段级写权限。SDK 测试应包含非 JSON 网关错误、未知 Problem type、无 Body 成功和结果未知，确保不会无限重试或将错误当成功。

本次 HTTP/JSON 报文为人工核对的契约示例，未连接真实服务运行端到端、代理或数据库并发测试。已检查原主题逐项覆盖、所有正文小节自足性、协议与应用约定边界、状态/示例一致性及 Markdown 结构。没有把这些人工检查声称为生产服务验证通过。

## 14. 面试前速记

- 资源不是数据库表，表述不是 Entity；URI 身份应稳定，复杂动作按业务生命周期建模。
- Safe 管请求的业务意图，Idempotent 管重复作用；日志可变化，状态码也可不同。
- PUT 替换、PATCH 按补丁格式、POST 按资源语义；方法名不提供去重实现。
- 201 创建、202 接受、200 成功读取/处理、204 无内容；任务成功与 HTTP 查询成功分开。
- 409 管状态冲突，412 管条件失败，428 管要求条件；5xx 不证明写入未发生。
- ETag 校验表述，If-Match 防旧版本覆盖；条件比较必须落到原子写入边界。
- no-cache 可存但需验证，no-store 不存，private 限共享；缓存必须纳入权限范围。
- Problem Details 标准字段与业务扩展分清，客户端读稳定码，不解析文案。
- Header、URI 与 Token 都可能泄露信息；对象授权、输入白名单、日志脱敏共同保护契约。
