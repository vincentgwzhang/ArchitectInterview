# 03. API 版本、向后兼容、幂等性与错误模型

> 本章讨论 HTTP/JSON API 的演进与可靠写入。协议基线为 RFC 9110、RFC 9457、RFC 9745 与 RFC 8594；数据库示例以 PostgreSQL 17 为参考。Idempotency-Key 的冲突、重放与保留规则在这里是明确的应用契约，不假设所有平台行为相同。场景和数字均为教学设计。

## 1. API 契约比 JSON Schema 更大

API 是生产者（Provider/Producer）与消费者（Consumer）之间可独立发布的边界。契约不仅包括路径和字段，还包括单位、默认值、排序、权限、错误、超时、幂等窗口和性能预算。Schema 能通过，不代表旧客户端仍能正确完成业务。

贯穿案例：订单 API 最初返回金额分值 totalCents，后来需要多币种、异步支付和新的订单状态。直接把 totalCents 改成小数元、将创建订单从同步变成异步，可能完全不改变 JSON 类型却破坏客户端。版本策略必须围绕“调用者还会不会作出正确决定”，而不是只看能否反序列化。

兼容性的方向要说清：新服务能接受旧客户端请求，旧客户端能理解新服务响应；如果允许新客户端先发布，还要旧服务能接受新请求、新客户端能理解旧响应。滚动发布时新旧实例并存，这些组合都可能真实发生。不能只测最新版客户端连最新版服务。

目标不是永不改变，而是让变化有可控路径：尽可能兼容扩展，确实无法保持语义时提供新 Major 契约，迁移有观测、有期限、有回滚。API 版本与内部服务构建号是两件事，内部每天部署不应强迫外部客户每天改版本。

## 2. 向后兼容：从请求与响应分别推理

### 2.1 为什么“增加 Optional Field”也有条件

新请求字段若可省略，服务端在省略时保持旧行为，通常有利于旧客户端继续工作。但新增字段默认值如果改变计价或配送方式，语法兼容仍不等于行为兼容。省略、显式 null、空字符串和空集合也可能表达不同意图，不能一律变成同一默认值。

新响应字段只有在旧消费者忽略未知字段、签名与缓存等机制允许变化时才安全。严格反序列化器、完整对象相等断言、未知属性拒绝、按原始响应字节验签的程序都可能失败。发布前应验证真实 SDK 和已知客户端，而不是凭 JSON 可以增加属性就宣布无风险。

示例：旧请求没有 captureMode，新服务若默认为 IMMEDIATE，会让原先仅授权不扣款的流程变成立即扣款。正确做法是保持省略时的旧行为，显式选择新能力；若无法表达安全默认，则考虑新端点/版本或迁移阶段，不强塞一个“合理”默认。

### 2.2 兼容矩阵与反例

| 变更 | 常见风险 | 更稳妥的路径 |
|---|---|---|
| 删除/重命名响应字段 | 旧客户端取不到值 | 先并存新旧字段与映射，迁移后再收缩 |
| 修改金额单位/时间时区 | 类型未变但业务计算错误 | 新增明确单位字段或新契约 |
| 请求可选改必填 | 旧请求被拒绝 | 服务端先兼容缺失，再收敛客户端 |
| 响应新增枚举值 | 旧 switch/生成 SDK 无分支 | 客户端 UNKNOWN 回退并保留原值，必要时能力协商 |
| 收紧长度/校验/权限 | 曾合法请求开始失败 | 分析真实使用与风险，明确兼容影响 |
| 改排序/分页默认值 | 重复/遗漏或页面含义变化 | 版本化查询契约或显式选择 |
| 同步完成变 202 异步接受 | 调用方提前认为业务完成 | 提供新操作模型与迁移指引 |
| 错误码/重试策略变化 | SDK 重复执行或不再恢复 | 将错误与恢复规则纳入契约测试 |

请求和响应的可选性不能混用。响应原先承诺字段必有，新服务改为偶尔缺失，虽然 Schema 更“宽松”，却让旧读取逻辑失败。新服务接受更宽范围的输入有时兼容，但如果该输入推动旧消费者无法理解的新状态，仍需端到端评估。

未知枚举的回退也不能把不认识的支付状态当成功。展示类客户端可显示“状态更新中”并保留原字符串；资金动作客户端应停止危险操作、查询或升级处理。容错是安全处理未知，不是静默将未知映射为默认业务状态。

### 2.3 协议、行为、性能与安全都属于兼容

改变 HTTP 状态、Content-Type、分页游标有效期或幂等键保留期，会影响客户端恢复。把原 409 改成 500 可能触发 SDK 重试；把页大小上限从 100 改为 20 可能令写死遍历逻辑漏数据。性能从 200ms 变为几秒，即使响应结构没变，也可能超出客户 deadline。

修复安全漏洞有时必须拒绝过去错误放行的访问，不能以“向后兼容”为由继续越权。应将它标记为安全行为修正，评估影响、通知受影响使用者、准备安全迁移与审计，而不是假装完全兼容或为旧客户保留不安全后门。

消费者应容忍未知非关键响应字段，同时严格验证会驱动危险动作的关键语义；服务端应明确拒绝拼错或未经授权的输入字段，避免无声忽略用户意图。不要把“宽进严出”当成所有边界都适合的口号。

## 3. 版本策略：在哪一层选择契约

### 3.1 URI、Header 与 Media Type 的取舍

| 选择 | 示例 | 优点 | 成本/注意 |
|---|---|---|---|
| URI Major | /v2/orders | 日志、路由、文档和调试直观 | 多路径并存、链接迁移和适配维护 |
| 自定义 Header | API-Version: 2 | URI 可保持稳定 | Header 传播、路由、缓存和可见性需额外设计 |
| Media Type | Accept: application/vnd.example.order.v2+json | 明确表述协商 | 客户端/工具复杂，输入与输出版本要分清 |

这些是设计方案，没有一种因形式而保证兼容。Accept 选择响应表述，Content-Type 描述请求内容；不能只设置一个 Accept 就默认输入字段也按新格式解释。Header/媒体类型影响响应时，缓存必须正确区分，必要时使用 Vary 或禁止共享，不能让 v1 客户端收到缓存的 v2。

要规定未指定版本的行为。公开 API 常宜显式选择或固定稳定默认；若“默认就是最新”，新部署可能悄悄改变旧客户端。未知/不支持版本的错误应可诊断，而不是自动降到某个可能误解业务的版本。

Major 用于破坏契约的变化，普通兼容增加尽量不创建新 Major。SDK 包的语义版本、OpenAPI 文档版本和 API Major 不必一一对应；升级 SDK 修复重试 Bug，可能完全不改变线上 API 版本。

### 3.2 不要让版本进入每一层业务代码

在 API 边界做输入/输出适配，共享经过明确设计的核心用例，例如 v1 的 totalCents 与 v2 的 money 对象都映射为内部金额类型。内部类型应能无损表达新旧数据，不能为了复用强行把新货币精度塞回旧整数。

适配器有语义边界：v1 只有 EUR 分，v2 支持 JPY 和不同小数位，不能无损地把所有 v2 数据回传 v1。可限制旧契约支持的资源范围，或返回明确不支持错误，并在迁移方案中解释，而不是做可能错误的四舍五入。

每个长期版本增加测试、修复和安全维护成本。给所有代码写 if(version==1) 会让核心流程分叉并产生组合爆炸；尽可能在边界隔离差异，为每个受支持版本跑独立契约与共享业务不变量测试。

## 4. Expand-and-Contract：让新旧消费者安全共存

扩展（Expand）阶段先增加新字段/表述，保持旧能力；迁移（Migrate）阶段更新消费者与数据；收缩（Contract）阶段在证据充分后移除旧契约。它不等于永久同时维护两套字段。

金额演进示例：旧响应 totalCents=1234 固定 EUR，新响应可增加 money={currency:EUR,minorUnits:1234}。先保证两字段由同一内部事实生成，再更新消费者读取 money；观测迁移后，只有在新的 Major 或既定移除政策下才删除旧字段。不要让两个字段分别由不同逻辑维护，否则出现不一致时客户端无从判断。

请求同时接受旧新字段时要定义冲突：两者同时出现且不一致应拒绝，不能由 JSON 顺序决定谁覆盖。默认值、舍入、货币代码与精度必须一致测试。若未知币种无法在旧契约表达，不应伪造 EUR 金额。

发布顺序通常是服务端先接受旧新输入，客户端再发送新输入，最后服务端收紧；响应则需先让客户端能够容忍新增内容，再逐步启用。具体顺序依变化方向决定，不能把一个固定顺序用于所有迁移。

回滚还受数据格式限制：新代码已写旧代码读不懂的状态或币种时，回滚镜像可能直接读失败。先做读兼容和可逆写入，或明确只能向前修复；回滚计划必须包含数据库、异步消息、缓存和在途请求，不只是重新部署旧包。

## 5. 怎样验证兼容，而不靠“应该没问题”

Schema Compatibility 检查结构：字段类型、必填、范围、枚举和媒体类型等。它适合快速发现明显破坏，但不知道金额单位、状态含义和业务副作用；结构检查通过只能形成部分证据。

Consumer-driven Contract（消费者驱动契约）由消费者表达它实际发送的请求和依赖的响应，服务端对这些交互进行验证。以 Pact 为例，消费者测试验证自己的代码正确构造/理解交互，并产生契约；提供方验证真实实现满足契约和对应前置状态。不能只有 mock 返回预设 JSON，就宣称生产服务兼容。

契约要关联消费者版本、提供方构建和部署环境，发布前检查真实可能共存的组合。仅验证仓库中最新版消费者，漏掉线上旧移动端和外部合作方，仍会出事故。契约测试也不证明网络超时、吞吐、授权全覆盖和数据库迁移正确，需补集成、故障和性能测试。

流量观察验证实际使用：按已登记 client identity、API Major、SDK 版本与路由聚合，不把 token、用户个人信息或原始请求当无限指标标签。低频月结客户可能数周没流量，不能因最近一天为零就判断无人使用。回放或影子流量要脱敏，写请求不能对真实下游再执行一次造成副作用。

## 6. 幂等性：固定的是业务意图，不是网络尝试

### 6.1 Key、Fingerprint、状态、结果缺一不可

支付、订单创建等 POST 不默认幂等。应用可约定 Idempotency-Key 标识同一业务意图，客户端首次提交前生成并持久保存，所有恢复尝试沿用此键。用户确实要再下另一单才使用新键；每次 HTTP 重试随机换键会绕过去重。

服务端保存至少包括可信作用域、业务动作、键、请求指纹（Request Fingerprint）、执行状态和可重放结果/资源引用。作用域应包括租户与必要主体/商户边界，避免不同客户相同键相互冲突或泄露结果。服务端每次仍要认证授权，键不是绕过权限的通行证。

相同键与相同语义输入返回已保存结果；同键不同输入在本章契约中返回 409 和稳定 IDEMPOTENCY_KEY_REUSED 码；正在处理中可返回相同操作状态地址或有界等待，不能无限占线程。409 是本文选择，不是凭 Header 名称就自动存在的跨平台规则。

指纹应覆盖影响业务的输入、目标资源、操作语义与相关版本。排除 traceId 等每次尝试变化字段，但不能排除金额、币种或收款方。保存指纹摘要不等于脱敏完成，低熵敏感信息仍可能被猜测，应按数据风险处理。

### 6.2 字节相同与语义相同的选择

原始 JSON 字节哈希简单，但字段顺序或空白变化会得到不同指纹。先解析再规范化可将某些表示差异视为相同，不过 1、1.0、null、缺失和默认值是否等价必须按领域明确，不能靠“排序 JSON key”解决全部语义。

例如 amountMinor 应为整数，currency 统一验证后使用允许的代码；缺省 captureMode 与显式旧默认是否相同，应在输入模型中定义。拒绝重复 JSON 成员名和模糊数字解析，避免验证器与业务解释不同内容。RFC 8785 是可参考的 JSON 规范化方案，不能把任意语言 json.dumps(sort_keys=true) 冒称其完整实现。

规范化/指纹算法要版本化并在保留窗口内兼容旧记录。若发布后改变默认值或规范化规则，同一键旧请求重试可能产生冲突甚至再次执行。稳定操作身份和迁移期指纹策略必须随 API 版本设计。

## 7. 本地数据库幂等：把并发与崩溃窗口讲完整

### 7.1 唯一约束仲裁，而不是先查再写

下面是 PostgreSQL 17 的教学表结构，展示约束关系，未包含生产所需加密、清理分区和完整索引策略：

~~~sql
CREATE TABLE api_requests (
    tenant_id text NOT NULL,
    operation_name text NOT NULL,
    request_key text NOT NULL,
    fingerprint bytea NOT NULL,
    state text NOT NULL CHECK (state IN ('IN_PROGRESS','COMPLETED')),
    resource_id text,
    response_status integer,
    response_body jsonb,
    expires_at timestamptz NOT NULL,
    PRIMARY KEY (tenant_id, operation_name, request_key),
    CHECK (state <> 'COMPLETED'
        OR (resource_id IS NOT NULL AND response_status IS NOT NULL))
);
~~~

正常同步本地写入可在同一短事务中：尝试插入请求记录，创建订单，保存完成状态与稳定结果，最后共同提交。主键唯一约束让并发同键只能有一个请求获得创建权；不能先 SELECT 不存在再各自 INSERT 订单。

可用 INSERT ... ON CONFLICT DO NOTHING RETURNING ... 判断是否获得该键。冲突方还需按数据库隔离与快照规则重新读取已提交记录、比较指纹并按状态响应，不能假设单个 SQL 的所有并发结果都自动可见。等待唯一约束也可能阻塞，必须设定可接受等待与错误恢复。

不应在 JPA 中捕获唯一约束异常后继续复用已经失败的事务；可用合适的冲突语句，或结束该事务后在新事务读取原结果。实现要验证事务管理器与实际数据库行为，不能从 Java catch 成功推断数据库事务可继续提交。

### 7.2 三个关键故障点

| 故障时点 | 同事务设计的预期结果 | 恢复动作 |
|---|---|---|
| 事务提交前进程崩溃 | 业务与请求记录共同未提交 | 同键可重新竞争执行 |
| 提交成功，HTTP 响应丢失 | 业务与完成结果均持久存在 | 同键查询/重放既有结果 |
| COMMIT 时连接中断，客户端不知道提交是否成功 | 结果未知，不能直接断言回滚 | 新连接按唯一键查询并按协议恢复 |

完整实现还要为数据库故障恢复、主从切换和备份还原定义保证。若灾难恢复回滚了幂等记录，却保留外部实际扣款，仅靠本地表无法防重复，需要外部业务引用和对账。

该同步模式中 IN_PROGRESS 在事务提交前通常不对其他正常隔离事务可见，冲突请求更多是等待/超时后再查。若想立即返回“正在处理”，需将接受记录先单独持久化，再由 worker 执行；这变成有状态操作模型，不能假装仍是原来那一笔事务。

### 7.3 持久 IN_PROGRESS 需要恢复协议

异步设计可先提交 PENDING/IN_PROGRESS 与待处理记录，返回操作 ID。worker 必须处理崩溃、重复领取和结果保存；状态中要有执行代次、租约/心跳、恢复策略和唯一业务效果保护。

租约过期不等于旧 worker 已停止，它可能因长暂停或网络分区仍在执行。新 worker 接管后需要 fencing token（单调执行代次，存储/下游拒绝旧代次）或其他能防重复效果的协议，不能只设置 Redis 锁超时便宣布安全。对于无法支持 fencing 的外部支付，依赖稳定支付幂等键、结果查询与对账，而非仅依赖本地锁。

## 8. 外部副作用、重放结果与跨版本边界

### 8.1 本地幂等不能包住支付商的事务

本地数据库提交与远端 HTTP 扣款没有共同本地事务。若先扣款再写请求结果，进程在两者之间崩溃，重试可能再次扣款；先标成功再调用支付又可能假成功。不能为了“锁住键”持有数据库事务等待任意长的外部网络。

可在本地短事务记录支付意图和 Outbox（与业务数据同事务保存的待发送消息），提交后发送者重试，使用稳定外部业务键调用支持幂等的支付 API；记录返回并推进状态。发送与确认之间仍可能重复，因此接收方幂等不可省略。

如果远端没有去重能力，发生响应丢失应尽可能查状态、进入人工/自动对账和补偿，不能保证恰好一次。Saga（长业务流程的本地事务与补偿协议）可协调失败，但退款也可能失败，补偿不是时间倒流。应明确承诺的故障模型与风险边界。

### 8.2 “返回原结果”要区分业务结果和传输元数据

可重放原业务状态码、资源引用和稳定响应内容，但 Date、traceId 等可能按本次尝试生成。不要重放旧 Set-Cookie、已失效签名下载地址或其他不适合复用的敏感 Header。若原响应资源需要重新授权，重放前仍检查当前访问权。

若保存的响应包含敏感数据，要加密/最小化并设置保留策略；可保存资源引用后按当前授权生成结果，但这会改变“字节相同”承诺，需公开说明是同一业务结果还是完全相同表述。资源后来被删除，也要明确同键重放返回历史创建结果还是当前查询状态。

跨 API 版本重试尤其危险：客户端从 v1 升到 v2 后对同一支付意图再次提交，若作用域按 URI 版本隔离，会绕过去重。可用稳定的内部 operation identity 跨版本关联，再按请求版本投影结果；若两个版本语义确实不同，就要求明确的新业务意图，而不是静默复用。应设计业务唯一键作为第二道保护。

### 8.3 保留期、权限与成本

保留时间至少覆盖公开的客户端重试窗口，还要考虑离线客户端、队列重投、合作方补发与时钟差。窗口之外删除记录后，同键可能再次执行，不能对外宣称永久幂等。某些资金操作需长期保留业务唯一引用或轻量墓碑记录，即使完整响应已清理。

容量可估算为请求速率乘保留秒数，再乘平均记录大小与索引/复制开销。教学假设每秒 100 个新键、保留 24 小时，就有 864 万条记录；即使每条有效负载只有 1 KiB，也已是数 GiB 量级，实际还要加存储结构。需限制键长度、按租户配额、分批清理并防止键洪泛。

过期清理不能直接删除仍运行或结果未知的操作。必须先按恢复协议判定，避免旧 worker 仍在执行、新请求因键消失又开始一次。权限撤销后也不能为兑现“同键返回”而继续向已无权主体泄露订单。

## 9. 错误模型：让客户端知道改输入、重试还是查状态

RFC 9457 的 Problem Details 提供 type、title、status、detail、instance；code、traceId、retryable、fieldErrors 等是应用扩展。机器依赖稳定 type/code，人类读可本地化 detail。内部 SQLException、连接串、堆栈、凭证和个人数据不得直接出现在公众错误。

~~~http
HTTP/1.1 409 Conflict
Content-Type: application/problem+json
Cache-Control: no-store
~~~

~~~json
{
  "type":"https://api.example.invalid/problems/idempotency-key-reused",
  "title":"请求键已用于不同输入",
  "status":409,
  "code":"IDEMPOTENCY_KEY_REUSED",
  "detail":"请核对原请求；新的业务意图需要新的请求键。",
  "traceId":"trace-attempt-2",
  "retryable":false
}
~~~

retryable 不是全能开关。客户端还需检查操作类型、幂等保护、总 deadline、限流与尝试次数。服务端不知道调用方剩余预算，无法通过 true 授权无限重试。错误码本身也属于兼容契约，不能随文案重构改变其含义。

| 情况 | 推荐恢复方向 | 不应做的事 |
|---|---|---|
| 字段校验失败 | 修正对应输入，保留可定位字段错误 | 原样不断重试 |
| 认证凭证过期 | 按协议刷新/重新认证，有限恢复 | 将权限不足一律当过期 |
| 版本前提失败 | 重新读取并合并/确认 | 去掉条件覆盖 |
| 瞬时过载 | 尊重恢复提示、抖动和总预算 | 每层各重试多次放大请求 |
| 网络超时/结果未知 | 同键查状态或恢复 | 换新键假定未执行 |
| 业务永久拒绝 | 改变业务动作或人工处理 | 用技术重试制造第二笔意图 |

Trace ID 标识某次诊断链路，幂等键标识跨尝试业务意图，资源 ID 标识业务对象，三者不应混为一个字段。日志可关联它们，但应按敏感性脱敏，且不把高基数字段作为无限指标标签。

客户端必须容忍未知错误类型和非 JSON 的代理错误，提供安全回退；不能对无法解析的 503 响应崩溃，也不能解析失败后默认成功。HTTP 状态与 Problem status 保持一致，别让 Body 说失败而外层 200 干扰告警和缓存。

## 10. 弃用与 Sunset：停止支持要有证据

Deprecation 表示资源/能力被弃用，未必立即改变行为；Sunset 表达预计何时停止响应。RFC 9745 定义 Deprecation Header，RFC 8594 描述 Sunset Header，两者不是同一个日期语义。弃用不应在未通知情况下偷偷改变旧接口行为。

可通过 Header 与 Link 指向迁移文档。Deprecation 使用其规范定义的结构化日期表达，Sunset 使用 HTTP 日期格式，不能都随手写 true 或任意 ISO 时间。具体样例应由日期格式库生成并测试，避免过期与时区错误。

弃用流程先登记消费者和负责人，记录真实调用版本与最后使用；再提供破坏点清单、前后报文、字段映射、SDK/Adapter、测试环境与截止时间。对长期离线移动端、月结客户和外部合作方，应选择覆盖真实使用周期的观察窗口，不把“最近 24 小时零流量”当作完成迁移。

Usage Dashboard 至少区分已迁移、已确认停用、仍使用和无法联系的消费者；流量为零也需业务负责人确认或按公开生命周期政策处理。公布日期还要有应急支持和回退条件，不能只发一封邮件便关闭资金关键接口。

移除时可以保留受控的明确错误与迁移链接，例如按政策对已永久退役路径返回 410，而不是误路由到不兼容的最新版本。保留适配器也有安全与维护成本，需明确支持期限。对外 API 的寿命可能远长于某个内部实现，版本退役应作为产品运营任务。

## 11. 综合案例：金额升级与重复扣款事故

教学场景：v1 金额单位是分，新版本保持 number 类型却改为元；SDK 发生超时后又生成新幂等键。结果旧消费者计算金额错误，网络故障又触发重复支付。

第一处是语义破坏，Schema number 没变不能证明兼容。应恢复旧字段单位或隔离新版本，提供显式 money 类型并做旧消费者回归。第二处是业务意图丢失，应在客户端持久化同一键，服务端按稳定操作身份与作用域去重。仅将接口返回 500 改成 200 不会修复任一问题。

如果扣款已经发生，回滚服务只阻止后续影响，还需按商户引用和支付流水对账、对重复支付执行受控退款。数据库已恢复备份的情况下，还要核对外部真实效果，不能让丢失的幂等表记录触发再扣款。

后续发布采用扩展、客户端迁移、收缩，契约覆盖单位与错误恢复；故障测试包含提交后断连和跨版本重试。指标区分 API 失败、业务结果未知和重复效果，不只观察 HTTP 成功率。这样才能证明消费者与提供方可独立发布，而不是依赖同一夜同时升级。

## 12. 面试完整回答与追问

### 12.1 “怎样保证 API 向后兼容？”

可表达回答：“我把请求接受范围、响应保证和行为语义分开评估。优先增加可选能力，省略时保持旧行为，不删改现有字段单位和含义；未知枚举安全回退。结构检查、真实消费者契约、SDK 和流量观测共同提供证据。破坏性变化采用明确新 Major，并通过扩展—迁移—收缩控制新旧并存和数据回滚风险。”

追问：“新增字段一定兼容吗？”答案：不一定。严格客户端可能拒绝未知属性，签名和完整响应断言也可能依赖旧形状；请求新字段的默认行为也可能改变业务。要验证实际消费者与语义，而不只是 Schema。

### 12.2 “如何实现支付 POST 幂等？”

可表达回答：“客户端为业务意图持久保存稳定键，服务端绑定可信租户、操作身份和语义指纹，用数据库唯一约束仲裁并发。本地写入与结果记录同事务提交；响应丢失后同键返回既有结果。外部支付通过稳定下游键、可靠意图记录和查询对账协调，超时视为结果未知，保留期覆盖公开重试窗口。”

追问：“Redis SETNX 加过期够吗？”答案：不够。锁可能过期而旧执行者仍运行，业务提交与结果缓存也有崩溃窗口。需要持久业务唯一性、恢复状态机和下游去重，不能把抢锁成功当作恰好一次。

### 12.3 “URI 与 Header 版本哪个更好？”

可表达回答：“我按路由可见性、缓存、工具、客户习惯和维护成本选择。URI 直观，Header/媒体类型保留 URI 但需传播和缓存隔离；一致和可验证比形式重要。只有契约破坏才增加 Major，内部构建版本独立；默认版本要稳定，未知版本不静默降级。”

追问：“同一支付从 v1 重试到 v2 呢？”答案：必须按业务意图判断是否是同一操作。若只是新投影/适配，应跨版本关联稳定操作身份并防重复；若语义改变，明确拒绝或要求新意图，不能因路径版本不同自动再次扣款。

### 12.4 “如何退役旧 API？”

可表达回答：“先登记和观察消费者，再提供迁移清单、SDK/适配、测试环境和时间表，用 Deprecation 与 Sunset 等信号补充沟通。观测窗口覆盖实际低频客户，确认迁移证据和支持安排后再移除。退役响应明确，不静默路由新版本；适配器也有期限与安全维护责任。”

追问：“没流量能关吗？”答案：不必然。可能有离线或月度任务，应结合消费者登记、业务负责人和公开支持政策，不用短期零流量替代确认。

## 13. 扫雷自测与推理答案

### 13.1 金额从分改成元但仍是 number，是否兼容？

不兼容。类型相同但数值解释改变，消费者可能误算百倍。使用新明确字段/契约并保留旧语义，结合前后实例验证，不靠 Schema 类型判定。

### 13.2 新枚举 UNKNOWN 回退能否映射为支付成功？

不能。未知值可能代表处理中、拒绝或新阶段，映射成功会触发危险业务。应保留未知原值，展示降级或暂停高风险动作，并提供查询/升级路径。

### 13.3 同键同输入但换租户，是否返回原响应？

不能跨授权范围重放。键要按可信租户/操作等命名空间隔离，当前权限也要重新检查。否则幂等接口本身成为数据泄露通道。

### 13.4 两个线程先 SELECT 不存在再各创建订单，为什么不安全？

检查与创建之间有竞态，两者可能同时通过。需要数据库唯一约束等原子仲裁，并让业务效果与记录协调提交；应用局部锁也不能保护其他实例。

### 13.5 提交后返回前崩溃，客户端应换新键吗？

不应。同一业务意图沿用原键，查找已持久的完成结果。换新键可能绕过去重；若提交结果未知，则按恢复协议查询，不直接断言未执行。

### 13.6 IN_PROGRESS 租约到期能否立即让新 worker 无条件扣款？

不能。旧 worker 未必停止，两个执行者可能并行。需要执行代次隔离/下游稳定幂等键及结果查询，状态机接管不能只依赖时间。

### 13.7 retryable=true 是否代表 SDK 可以无限重试？

不能。还受幂等性、次数、剩余预算、限流和业务意图约束。服务端提示只提供部分依据，每层自动重试还会乘法放大下游负载。

### 13.8 保存 24 小时是否等于永久不会重复？

不等于。超出窗口，键记录可能不存在；若需要更长期约束，应保留业务唯一键/墓碑及必要查询能力。保留期要覆盖实际恢复需求并对外公开。

### 13.9 契约测试全部通过，能否跳过真实故障演练？

不能。它主要证明记录的交互和消费者预期，不证明提交后断连、并发同键、数据库切换、身份撤销或资源预算。还需按真实故障模型验证关键窗口。

## 14. 验证方案与本次执行边界

兼容矩阵覆盖旧/新服务与旧/新消费者共存：字段新增/缺失/null、未知枚举、单位、默认值、同步/异步、错误与重试；请求双字段冲突要拒绝，不能因序列化顺序随机决定。适配测试应断言业务不变量与金额精度，而不仅 JSON 快照相等。

幂等测试覆盖同键并发、不同载荷、跨租户、事务提交前崩溃、提交后响应丢失、COMMIT 结果未知、过期清理与处理中记录。故障注入还应覆盖旧 worker 接管后继续运行、外部支付成功但回执丢失、跨版本重试及灾难恢复后本地记录缺失。

错误测试验证稳定码、公众消息脱敏、未知错误回退和网关非 JSON；弃用测试确认日期格式、作用范围、文档链接、实际使用观测与退役后的预期响应。监控不得输出令牌、支付凭证或完整敏感请求。

本次 SQL、HTTP、并发与支付恢复方案未在真实服务/数据库/支付平台运行；它们是教学设计，不是可直接部署的完整实现。已人工核对原主题、逐节自足性、状态与事务窗口、版本/错误一致性和 Markdown 结构。容量数字为推导假设，不能当作生产 benchmark。

## 15. 面试前速记

- API 契约包含行为、单位、默认、错误和恢复，不止 Schema。
- 兼容方向分请求接受与响应保证，新增可选也要真实消费者证据。
- Major 隔离破坏变化，内部构建号独立；版本边界适配，核心语义不撒满 if。
- 扩展—迁移—收缩，回滚同时考虑已写数据、消息、缓存与在途请求。
- Key 固定业务意图，指纹固定语义输入，唯一约束仲裁并发，事务协调结果。
- 超时是结果未知，换新键可能重复；锁过期不是旧执行者停止。
- 外部副作用靠下游幂等、可靠意图与对账，本地事务不覆盖 HTTP。
- 错误码稳定、文案可变，retryable 受预算与幂等限制，诊断不泄密。
- Deprecation 与 Sunset 不同；先有使用证据与迁移支持，再移除。
