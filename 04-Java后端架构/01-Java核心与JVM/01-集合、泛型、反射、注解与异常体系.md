# 01. 集合、泛型、反射、注解与异常体系

> 本章目标不是背 API，而是能回答三个层次：**怎么用、为什么这样实现、在并发和工程场景中会出什么问题**。回答统一采用：**结论 → 原理 → 限制 → 工程选型**。

## 一、Java 集合体系

### 1. 接口关系必须先记住

```text
Iterable
└── Collection
    ├── List：有序、可重复、可按下标访问
    │   ├── ArrayList
    │   ├── LinkedList
    │   └── CopyOnWriteArrayList
    ├── Set：元素不重复
    │   ├── HashSet
    │   ├── LinkedHashSet
    │   └── TreeSet
    └── Queue / Deque：队列 / 双端队列
        ├── ArrayDeque
        ├── PriorityQueue
        └── BlockingQueue 的各种实现

Map：键值映射，不属于 Collection
├── HashMap
├── LinkedHashMap
├── TreeMap
├── Hashtable（历史遗留）
└── ConcurrentHashMap
```

集合选型不能只报类名，要从六个维度回答：

1. 是否需要插入顺序、排序或去重；
2. 访问模式是随机读、遍历、头尾操作还是中间插删；
3. 数据规模以及时间、空间复杂度；
4. 是否存在并发读写；
5. 是否允许 `null`；
6. 是否需要范围查询、阻塞、快照、LRU 等特殊语义。

### 2. 常用集合对比

| 集合 | 底层结构 | 典型复杂度 | 顺序 | `null` | 线程安全 |
|---|---|---|---|---|---|
| `ArrayList` | 动态数组 | 下标 O(1)，尾插摊销 O(1)，中间增删 O(n) | 插入顺序 | 允许 | 否 |
| `LinkedList` | 双向链表 | 定位 O(n)，已定位后增删 O(1) | 插入顺序 | 允许 | 否 |
| `HashSet` | 基于 `HashMap` | 平均 O(1) | 无保证 | 一个 `null` | 否 |
| `LinkedHashSet` | 哈希表 + 双向链表 | 平均 O(1) | 插入顺序 | 一个 `null` | 否 |
| `TreeSet` | 红黑树 | O(log n) | 排序顺序 | 通常不允许 | 否 |
| `HashMap` | 数组 + 链表/红黑树 | 平均 O(1) | 无保证 | 一个空 Key，多个空 Value | 否 |
| `LinkedHashMap` | 哈希表 + 双向链表 | 平均 O(1) | 插入或访问顺序 | 允许 | 否 |
| `TreeMap` | 红黑树 | O(log n) | Key 排序 | 通常不允许空 Key | 否 |
| `ConcurrentHashMap` | 哈希桶 + 并发控制 | 平均 O(1) | 无保证 | Key/Value 均不允许 | 是 |
| `CopyOnWriteArrayList` | 写时复制数组 | 读 O(1)，写 O(n) | 插入顺序、快照迭代 | 允许 | 是 |

> HashMap 的最坏 O(log n) 需要桶已经树化。恶意碰撞、糟糕的 Hash 或未满足树化条件时，仍可能经历链表 O(n)。

## 二、ArrayList、LinkedList 与 ArrayDeque

### 1. ArrayList 的扩容和复杂度

`ArrayList` 本质是 `Object[] elementData`：

- 现代 JDK 的无参构造通常先使用共享空数组，第一次添加时再分配；
- 容量不足时通常扩为原容量的约 1.5 倍，具体细节以目标 JDK 为准；
- 扩容要创建新数组并复制元素，单次 O(n)；
- 不是每次添加都扩容，所以尾部 `add` 是**摊销 O(1)**，不是严格 O(1)；
- 中间插入、删除要移动后续元素，是 O(n)；
- 已知规模时预设容量，减少扩容、数组复制和短命对象；
- 删除元素后容量不会自动缩小，`trimToSize` 也会产生复制成本。

`remove` 重载是高频陷阱：

```java
List<Integer> list = new ArrayList<>(List.of(10, 20, 30));
list.remove(1);                    // 删除下标 1，即 20
list.remove(Integer.valueOf(10)); // 删除值 10
```

`Arrays.asList` 与 `List.of`：

- `Arrays.asList(array)` 返回定长视图，支持 `set`，不支持改变大小的 `add/remove`；
- 对象数组与该视图相互影响；
- `Arrays.asList(new int[]{1, 2})` 得到 `List<int[]>`，不是 `List<Integer>`；
- `List.of` 返回不可修改集合，而且不允许 `null`；
- 需要普通可变列表时使用 `new ArrayList<>(source)`。

### 2. LinkedList 为什么通常不是更好的选择

“链表插入删除 O(1)”只描述**已经拿到目标节点之后**。按下标定位仍是 O(n)。它的每个节点还保存前驱、后继和元素引用，内存开销大，节点分散导致 CPU Cache Locality 差。

- 普通列表优先 `ArrayList`；
- 栈、队列和双端队列通常优先 `ArrayDeque`；
- 只有频繁通过迭代器在已定位位置插删等特定模式，才考虑 `LinkedList`。

### 3. 为什么用 ArrayDeque 代替 Stack

`ArrayDeque` 使用循环数组，头尾操作通常摊销 O(1)，不允许 `null`。

```java
Deque<String> stack = new ArrayDeque<>();
stack.push("A");
String top = stack.pop();

Deque<String> queue = new ArrayDeque<>();
queue.offer("A");
String first = queue.poll();
```

`Stack` 继承 `Vector`，带有历史设计和不必要的同步负担。面试应明确说：**栈优先用 Deque 接口，常用实现是 ArrayDeque**。

## 三、HashMap：必须能追到底层

### 1. put/get 核心流程

以现代 JDK 的典型实现说明：

1. 非空 Key 先取 `hashCode`，并对高低位做扰动；
2. 使用 `(n - 1) & hash` 定位桶，所以容量保持 2 的幂；
3. 桶为空直接插入；
4. 桶非空，先比较 Hash，再用引用相等或 `equals` 判断同一 Key；
5. 相同 Key 覆盖 Value，不同 Key 追加到链表或红黑树；
6. 元素数量超过 `capacity × loadFactor` 时扩容。

默认负载因子通常是 0.75，是时间和空间的折中。负载高会增加冲突，负载低会浪费桶数组空间。

### 2. 容量为什么是 2 的幂

- `hash % n` 可转换为 `(n - 1) & hash`；
- 扩容为两倍后，元素的新位置要么不变，要么移动 `oldCapacity`；
- 迁移时可按新增的那一个有效位拆分桶。

若预计放入 `expectedSize` 个元素且希望避免扩容，应考虑：

```text
initialCapacity >= ceil(expectedSize / loadFactor)
```

还要考虑容量会向 2 的幂调整及整数上限。不要在业务代码中到处复制魔法公式。

### 3. 什么时候树化

JDK 8 之后，冲突桶达到阈值也不一定立即树化：

- 典型树化阈值 `TREEIFY_THRESHOLD = 8`；
- 桶数组容量还要至少达到 `MIN_TREEIFY_CAPACITY = 64`；
- 容量不足 64 时优先扩容；
- 桶缩小到一定程度可能退化回链表，典型阈值为 6。

这些数字是典型实现细节，不是 Java 语言规范承诺。面试重点是讲清**为什么小表先扩容，大表高冲突才树化**。

### 4. equals/hashCode 契约

必须背熟：

- `equals` 相等，`hashCode` 必须相等；
- `hashCode` 相等，`equals` 不一定相等；
- `equals` 满足自反、对称、传递、一致，与 `null` 比较为 `false`；
- 重写 `equals` 必须同时重写 `hashCode`；
- Key 放入 Hash 容器后，不应改变参与 Hash 的字段；
- 优先使用不可变对象作为 Key。

```java
Map<UserKey, String> map = new HashMap<>();
UserKey key = new UserKey("tenant-a", 100L);
map.put(key, "value");

key.setTenantId("tenant-b"); // 若参与 hashCode，后续 get 很可能失败
```

### 5. HashMap 为什么线程不安全

不要只背“JDK 7 扩容可能形成环”。现代 JDK 并发写仍可能产生：

- 更新丢失；
- 可见性和结构一致性问题；
- 读取到不符合业务预期的瞬时状态；
- “先检查再执行”的复合竞态。

```java
// 有竞态
if (!map.containsKey(key)) {
    map.put(key, createValue());
}

// 使用并发 Map 的原子复合 API
map.computeIfAbsent(key, k -> createValue());
```

`computeIfAbsent` 的函数应短小，避免长时间阻塞、递归修改同一 Map 和难以回滚的外部副作用。

## 四、LinkedHashMap、TreeMap 与 Set

### 1. LinkedHashMap 与 LRU

`LinkedHashMap` 在哈希表外维护双向链表：

- 默认按插入顺序迭代；
- `accessOrder=true` 时按访问顺序维护；
- 重写 `removeEldestEntry` 可实现简单有界 LRU。

```java
Map<String, Object> lru = new LinkedHashMap<>(16, 0.75f, true) {
    @Override
    protected boolean removeEldestEntry(Map.Entry<String, Object> eldest) {
        return size() > 1_000;
    }
};
```

它不线程安全，也没有过期、加载合并、权重淘汰和统计。生产缓存通常用成熟缓存组件。

### 2. TreeMap/TreeSet 的比较器契约

`TreeMap` 基于红黑树，操作 O(log n)，支持 `firstKey`、`floorKey`、`ceilingKey`、`subMap` 等范围操作。

有序集合把比较结果为 0 的对象视为同一个排序 Key。比较器最好与 `equals` 一致，否则会出现“equals 不同但只能存一个”。

```java
Comparator<Person> comparator = Comparator
        .comparing(Person::getLastName)
        .thenComparing(Person::getFirstName)
        .thenComparing(Person::getId);
```

不要用 `return a - b` 写比较器，可能整数溢出；用 `Integer.compare(a, b)`。

### 3. Set 如何去重

- `HashSet` 通常把元素作为 `HashMap` 的 Key，Value 使用共享占位对象；
- `HashSet` 去重依赖 `hashCode + equals`；
- `LinkedHashSet` 额外保留插入顺序；
- `TreeSet` 根据比较结果是否为 0 去重。

## 五、迭代器、Fail-Fast 与集合视图

### 1. Fail-Fast 不是线程安全保证

普通集合迭代器会记录结构修改计数。迭代期间检测到非迭代器自身造成的结构修改时，通常抛 `ConcurrentModificationException`。

```java
Iterator<String> iterator = list.iterator();
while (iterator.hasNext()) {
    if (shouldDelete(iterator.next())) {
        iterator.remove();
    }
}
```

必须注意：

- 增删一般属于结构修改，仅替换元素/Value 未必属于；
- 增强 `for` 底层是迭代器，直接调集合 `remove` 容易出错；
- Fail-Fast 是尽力发现 Bug，不保证每次竞态都抛异常；
- “没有抛异常”不能证明线程安全；
- 并发集合常用弱一致或快照迭代器。

### 2. 视图联动

`Map.keySet()`、`values()`、`entrySet()` 通常是视图而非副本；修改视图可能影响原 Map。

`subList` 也是原列表视图。原列表发生不协调的结构变化后再访问子列表，可能抛 `ConcurrentModificationException`。需要独立数据时：

```java
List<String> copy = new ArrayList<>(list.subList(from, to));
```

## 六、并发集合

### 1. ConcurrentHashMap

JDK 8 以后不再以旧式固定 `Segment` 数组作为主要结构，而是通过桶数组、CAS、桶级同步等机制协调更新，读取大多不加互斥锁。

必须记住：

- Key 和 Value 均不允许 `null`，让 `get(key) == null` 明确表示当前不存在；
- 迭代器弱一致，可看到遍历期间的部分更新，但不是全局快照；
- `size()` 在高并发变化时适合估计，不适合强一致业务决策；
- `putIfAbsent/compute/merge` 等有各自原子语义；
- 多个原子方法拼在一起仍不一定构成原子事务；
- 对某 Key 的非空更新，对随后成功读取该值的线程提供相应可见性保证。

### 2. CopyOnWriteArrayList

写操作复制整个数组，完成修改后发布新数组；读不加锁，迭代器持有创建时快照。

适合：读极多、写极少、数据量有限，如监听器列表、配置快照。

不适合：频繁写、大列表、要求迭代立刻看到最新修改。成本包括 O(n) 复制、瞬时内存放大和 GC 压力。

### 3. BlockingQueue

| 方法组 | 队列满/空时行为 |
|---|---|
| `add/remove/element` | 抛异常 |
| `offer/poll/peek` | 返回特殊值 |
| `put/take` | 阻塞 |
| 带超时 `offer/poll` | 最多等待指定时间 |

常见实现：

- `ArrayBlockingQueue`：固定容量的有界数组；
- `LinkedBlockingQueue`：链式，可设容量；默认容量很大，要防止堆积；
- `SynchronousQueue`：不存元素，每次交付直接匹配消费者；
- `PriorityBlockingQueue`：按优先级，逻辑上无界；
- `DelayQueue`：元素到期后才能获取。

### 4. 各 BlockingQueue 实现与背压、过载保护、拒绝策略

这里讨论的是 `BlockingQueue` 实现类本身，以及它们作为 `ThreadPoolExecutor` 工作队列时的差异，不展开到系统级限流、熔断等架构设计。

先区分三个概念：

- **背压**：生产者直接调用队列的 `put` 或限时 `offer` 时，队列满会让生产者等待，生产速度因此被迫降低；
- **过载保护**：使用有界队列限制内存中最多积压多少任务，避免任务无限堆积；
- **拒绝策略**：`ThreadPoolExecutor.execute` 不会通过 `put` 无限等待；当线程数和队列都达到上限时，它调用 `RejectedExecutionHandler` 处理无法接收的任务。

因此，`BlockingQueue` 的“阻塞能力”不代表线程池提交任务时也一定会阻塞。直接使用队列和把队列交给线程池，是两种不同语义。

#### 4.1 实现类对比

| 实现类 | 容量与顺序 | 直接调用 `put` 时 | 作为线程池队列时 | 背压、过载与拒绝特点 |
|---|---|---|---|---|
| `ArrayBlockingQueue` | 必须指定固定容量；数组；FIFO；可选公平锁 | 满时阻塞生产者 | 队列满后，线程池可继续创建线程直到 `maximumPoolSize`，再触发拒绝 | 容量边界最明确，同时限制内存积压；最适合演示背压、过载保护和拒绝全过程 |
| `LinkedBlockingQueue` | 链表；FIFO；可指定容量；无参构造容量为 `Integer.MAX_VALUE` | 达到容量时阻塞；默认情况下几乎不会满 | 有界时与 `ArrayBlockingQueue` 类似；默认近似无界时任务持续入队，通常不会扩到 `maximumPoolSize`，也很难触发拒绝 | 指定容量才有清晰过载保护；默认容量可能隐藏过载并造成大量积压 |
| `SynchronousQueue` | 容量为 0，不保存元素；每次插入必须与一次取出直接交接 | 没有消费者接手就阻塞 | 任务无法入队，因此通常直接创建新线程；达到 `maximumPoolSize` 后立即拒绝 | 几乎不缓冲，背压/拒绝最敏感；适合任务可快速移交、不希望排队的场景 |
| `PriorityBlockingQueue` | 按优先级出队；逻辑无界；不保证同优先级 FIFO | 通常不会因满而阻塞 | 任务持续入队，通常只使用核心线程，`maximumPoolSize` 和拒绝策略基本不生效 | 能调度优先级，但不能依靠它做容量保护；低优先级任务还可能长期饥饿 |
| `DelayQueue` | 元素到期后才能取；按到期时间组织；逻辑无界 | 通常不会因满而阻塞 | 可作为延迟任务容器，但不适合作为普通线程池过载控制队列 | 提供延迟语义，不提供容量保护；生产过快仍可能积压 |

补充：`LinkedBlockingDeque` 是支持两端插入/移除的可选有界阻塞双端队列；`LinkedTransferQueue` 是无界队列，支持生产者直接把元素移交给消费者。它们同样要先看“是否有界”，再判断能否提供过载保护。

#### 4.2 直接使用 BlockingQueue 时，背压由操作方法决定

同一个有界队列，使用不同方法会产生不同的过载行为：

| 插入方法 | 队列满时行为 | 是否形成背压 | 适合场景 |
|---|---|---|---|
| `add(e)` | 立即抛 `IllegalStateException` | 否，属于立即失败 | 调用方希望通过异常感知队列已满 |
| `offer(e)` | 立即返回 `false` | 否，属于非阻塞拒绝 | 调用方自行决定丢弃、记录或重试 |
| `offer(e, timeout, unit)` | 最多等待指定时间，超时返回 `false` | 有限背压 | 既允许短暂等待，又不希望永久阻塞 |
| `put(e)` | 一直等待，直到有空间或线程被中断 | 强背压 | 生产者允许被阻塞，且必须设计中断和停机逻辑 |

示例：容量为 2，第三次 `put` 会等待消费者腾出位置；改用 `offer` 则立即得到 `false`。

```java
BlockingQueue<String> queue = new ArrayBlockingQueue<>(2);
queue.put("A");
queue.put("B");

boolean accepted = queue.offer("C"); // false：立即拒绝
boolean acceptedLater = queue.offer("C", 200, TimeUnit.MILLISECONDS);
// 最多等待 200ms：期间消费者取走元素则成功，否则返回 false
```

所以不能只说“`ArrayBlockingQueue` 有背压”。更准确的说法是：**有界队列提供背压所需的容量边界，`put` 或限时 `offer` 才把这个边界反馈给生产者。**

#### 4.3 作为 ThreadPoolExecutor 队列时的执行顺序

假设线程池参数为：

```java
new ThreadPoolExecutor(
        2,                      // corePoolSize
        4,                      // maximumPoolSize
        60, TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(3),
        new ThreadPoolExecutor.AbortPolicy());
```

持续提交执行时间很长的任务时，接收顺序是：

1. 第 1～2 个任务：创建 2 个核心线程执行；
2. 第 3～5 个任务：放入容量为 3 的队列；
3. 第 6～7 个任务：队列已满，创建线程，线程数从 2 扩到最大值 4；
4. 第 8 个任务：线程数已达 4 且队列已满，执行拒绝策略。

面试高频陷阱：线程池不是先创建到 `maximumPoolSize` 再排队，而是**核心线程满 → 入队 → 队列满 → 扩到最大线程 → 拒绝**。

将队列替换后，表现会明显变化：

- 换成默认的 `new LinkedBlockingQueue<>()`：第 3 个及以后的任务几乎都入队，线程数通常保持为 2，`maximumPoolSize = 4` 基本失效；
- 换成 `new SynchronousQueue<>()`：没有排队位置，第 3、4 个任务直接促使线程池扩到 4，第 5 个任务就会被拒绝；
- 换成 `new PriorityBlockingQueue<>()`：任务按优先级堆积，但因为队列逻辑无界，线程数通常保持为 2，也很难触发拒绝策略；提交的 `Runnable` 还必须可比较，或在构造队列时提供 `Comparator`，否则可能抛 `ClassCastException`。

#### 4.4 四种拒绝策略如何与队列配合

拒绝策略只在线程池无法接收任务时触发：线程池未关闭的正常情况下，需要同时满足**工作队列无法入队**和**线程数已经达到 `maximumPoolSize`**。

| 策略 | 被拒绝任务如何处理 | 与背压的关系 |
|---|---|---|
| `AbortPolicy` | 抛 `RejectedExecutionException` | 不减慢提交线程，但把过载明确反馈给调用方；默认策略 |
| `CallerRunsPolicy` | 由调用 `execute` 的线程亲自执行 | 调用者被占用，提交速度自然下降，因此可形成简单背压；线程池已关闭时不会执行该任务 |
| `DiscardPolicy` | 静默丢弃当前任务 | 没有背压，也没有异常；必须确认任务允许丢失 |
| `DiscardOldestPolicy` | 丢弃队头等待最久的任务，再尝试提交当前任务 | 没有阻塞式背压；让新任务替代旧任务，不适合不可丢任务；用于优先队列时，“队头”是最高优先级元素，尤其要谨慎 |

对逻辑无界的 `LinkedBlockingQueue`、`PriorityBlockingQueue`、`DelayQueue` 而言，队列通常不会报告“满”，所以运行中的线程池几乎不会走到拒绝策略。此时配置哪种拒绝策略都不能解决任务持续积压问题。

#### 4.5 可运行的小实验

下面的实验把任务执行时间拉长，使线程和队列保持占用。只需替换 `queue` 或 `handler`，就能比较不同实现与拒绝策略。

```java
import java.util.concurrent.*;

public class QueueOverloadDemo {
    public static void main(String[] args) throws InterruptedException {
        BlockingQueue<Runnable> queue = new ArrayBlockingQueue<>(2);
        // 依次替换观察：
        // new LinkedBlockingQueue<>()
        // new LinkedBlockingQueue<>(2)
        // new SynchronousQueue<>()

        RejectedExecutionHandler handler =
                new ThreadPoolExecutor.AbortPolicy();
        // 依次替换观察 CallerRunsPolicy、DiscardPolicy、DiscardOldestPolicy

        ThreadPoolExecutor pool = new ThreadPoolExecutor(
                1, 2,
                30, TimeUnit.SECONDS,
                queue,
                handler);

        for (int i = 1; i <= 6; i++) {
            int taskId = i;
            try {
                System.out.printf("提交 task-%d：pool=%d, queue=%d%n",
                        taskId, pool.getPoolSize(), queue.size());
                pool.execute(() -> {
                    System.out.printf("执行 task-%d，线程=%s%n",
                            taskId, Thread.currentThread().getName());
                    try {
                        TimeUnit.SECONDS.sleep(2);
                    } catch (InterruptedException e) {
                        Thread.currentThread().interrupt();
                    }
                });
            } catch (RejectedExecutionException e) {
                System.out.println("拒绝 task-" + taskId);
            }
        }

        pool.shutdown();
        pool.awaitTermination(20, TimeUnit.SECONDS);
    }
}
```

使用 `ArrayBlockingQueue<>(2)`、核心线程 1、最大线程 2 和 `AbortPolicy` 时，在前面的任务尚未完成这一前提下，典型过程是：

```text
task-1：核心线程执行
task-2、task-3：进入队列
task-4：队列满，创建第 2 个线程执行
task-5、task-6：线程和队列都满，抛 RejectedExecutionException
```

实验时应观察：

- `ArrayBlockingQueue<>(2)` 与 `LinkedBlockingQueue<>(2)` 都能触发扩容和拒绝，主要差异在内部结构，而非线程池接收流程；
- 默认 `LinkedBlockingQueue` 会让 5 个任务在核心线程之后继续排队，通常不会创建第 2 个线程；
- `SynchronousQueue` 不保存任务：前两个任务分别使用核心线程和最大线程，后续任务立即进入拒绝策略；
- 换成 `CallerRunsPolicy` 后，被拒绝的任务会显示由 `main` 线程执行；在它执行期间，`main` 无法继续提交，这就是最直观的背压现象；
- 换成 `DiscardPolicy` 后不会抛异常，但部分任务没有任何执行输出，说明它们被静默丢弃；
- 换成 `DiscardOldestPolicy` 后，队列中等待最久的任务可能没有执行，而较新的任务得到执行机会。

#### 4.6 面试结论

> `ArrayBlockingQueue` 和指定容量的 `LinkedBlockingQueue` 能限制积压，是线程池过载保护最直接的选择；直接调用 `put` 时，队列满会阻塞生产者形成背压，但 `ThreadPoolExecutor.execute` 不会用 `put` 等待，而是在核心线程满后入队、队列满后扩到最大线程，最后触发拒绝策略。默认 `LinkedBlockingQueue`、`PriorityBlockingQueue` 和 `DelayQueue` 逻辑上近似无界，通常会持续积压，使最大线程数和拒绝策略难以生效；`SynchronousQueue` 不存任务，会优先扩线程，达到最大线程后最快触发拒绝。四种拒绝策略中，只有 `CallerRunsPolicy` 会通过占用提交线程产生明显背压，`AbortPolicy` 明确失败，另外两种会丢任务。

## 七、泛型：不靠背口诀，从方法能读什么、能写什么开始

泛型在多数欧洲 Java 面试中通常不是独立的大题，但会藏在集合、Stream、Repository、反序列化和 API 设计里。实际需要掌握的不是复杂语法，而是能解释四件事：

1. 泛型如何把类型错误从运行期提前到编译期；
2. 为什么 `List<Integer>` 不能赋值给 `List<Number>`；
3. `T`、`? extends T`、`? super T` 分别允许读写什么；
4. 类型擦除对运行时检查、反射和框架有什么影响。

### 7.1 先建立心智模型：泛型表达类型之间的关系

没有泛型时，容器只能返回 `Object`，错误常常推迟到取值时才发生：

```java
List values = new ArrayList();
values.add("42");
values.add(100);                // 编译器不阻止

Integer number = (Integer) values.get(0);
// 运行到这里才抛 ClassCastException
```

使用泛型后：

```java
List<Integer> values = new ArrayList<>();
values.add(100);
values.add("42");              // 编译错误

Integer number = values.get(0); // 不需要手工转换
```

但“省掉强制转换”只是表面价值。更重要的是泛型可以表达输入和输出之间的关系：

```java
static <T> T first(List<T> values) {
    if (values.isEmpty()) {
        throw new NoSuchElementException();
    }
    return values.get(0);
}

String name = first(List.of("Ana", "Tom"));
Integer id = first(List.of(10, 20));
```

这里的 `T` 不是 `Object` 的别名，而是“传入列表的元素类型与返回类型必须相同”这一约束。编译器根据实参分别推断出 `String` 和 `Integer`。

三个容易混淆的声明位置：

```java
// 泛型类：每个 Box 实例在声明时确定 T
final class Box<T> {
    private final T value;
    Box(T value) { this.value = value; }
    T get() { return value; }
}

// 泛型接口：实现类决定实体类型
interface Repository<ID, E> {
    Optional<E> findById(ID id);
    void save(E entity);
}

// 泛型方法：每次调用都可以推断不同的 T
static <T> List<T> singleton(T value) {
    return List.of(value);
}
```

`static` 方法不能直接使用类级别的 `T`，因为它不属于某个 `Box<T>` 实例；它必须自己声明 `<T>`：

```java
final class Box<T> {
    // static T invalid();             // 编译错误
    static <T> Box<T> of(T value) {   // 方法自己的 T
        return new Box<>(value);
    }
}
```

### 7.2 为什么泛型是不变的

已知：

```java
Integer extends Number
```

但下面不成立：

```java
List<Integer> integers = new ArrayList<>();
List<Number> numbers = integers; // 编译错误
```

假设编译器允许它：

```java
numbers.add(3.14); // 对 List<Number> 完全合法
Integer value = integers.get(0); // 现在整数列表里出现了 Double
```

所以 `List<Integer>` 不是 `List<Number>` 的子类型。这叫不变性，它保护了可写容器的类型安全。

数组采用另一种历史设计——协变：

```java
Number[] numbers = new Integer[1]; // 编译通过
numbers[0] = 3.14;                 // 运行期 ArrayStoreException
```

数组在运行时知道自己是 `Integer[]`，因此能在写入时检查。泛型集合选择在编译期拒绝不安全赋值，避免把错误推迟到运行期。

面试中如果只回答“泛型不变、数组协变”仍然不够；要能用“如果允许，就能把 `Double` 放进整数列表”推导出原因。

### 7.3 `T` 与 `?` 不是同一种用途

`T` 是一个有名字的类型变量，可以表达多个位置必须是同一类型：

```java
static <T> void replaceFirst(List<T> list, T newValue) {
    list.set(0, newValue);
}
```

调用关系由编译器检查：

```java
List<String> names = new ArrayList<>(List.of("Ana"));
replaceFirst(names, "Bob"); // 合法
replaceFirst(names, 10);    // 编译错误
```

`?` 表示“存在某个确定但当前不知道的类型”：

```java
static int sizeOf(List<?> values) {
    Object first = values.get(0); // 只能保证读成 Object
    // values.add("x");           // 编译错误
    return values.size();
}
```

`List<?>` 不是 `List<Object>`：

- `List<Object>` 明确表示元素类型就是 `Object`，可以添加任意对象；
- `List<?>` 可能实际是 `List<String>` 或 `List<Integer>`，不能安全添加任何具体非 `null` 值。

如果一个方法只是调用 `size`、`isEmpty`、`clear`，并不关心元素类型，`List<?>` 通常比声明一个无意义的 `<T>` 更准确。

### 7.4 从读写权限推导 `extends` 和 `super`

不要先背 PECS，先问：“这个参数在方法里主要提供数据，还是接收数据？”

#### 7.4.1 `? extends Number`：具体类型未知，但上界是 Number

```java
static double total(List<? extends Number> values) {
    double result = 0;
    for (Number value : values) {
        result += value.doubleValue();
    }
    return result;
}
```

它可以接收：

```java
total(List.of(1, 2, 3));       // List<Integer>
total(List.of(1.5, 2.5));      // List<Double>
total(List.<Number>of(1, 2.5));
```

方法只知道真实元素类型是 `Number` 的某个子类型，不知道究竟是哪一个，因此：

```java
void inspect(List<? extends Number> values) {
    Number value = values.get(0); // 安全

    // values.add(1);             // 可能实际是 List<Double>
    // values.add(1.5);           // 可能实际是 List<Integer>
}
```

所以 `extends` 不是“只读集合”；`clear()`、`remove()` 等操作仍可能合法。准确说法是：不能安全地向其中添加具体的 Number 值。

#### 7.4.2 `? super Integer`：具体类型未知，但它是 Integer 的父类型

```java
static void addSequence(List<? super Integer> destination) {
    destination.add(1);
    destination.add(2);
}
```

它可以接收 `List<Integer>`、`List<Number>` 或 `List<Object>`。写入 `Integer` 一定安全，但读取时只知道是 `Object`：

```java
void fill(List<? super Integer> values) {
    values.add(10);              // 安全
    Object value = values.get(0);
    // Integer n = values.get(0); // 编译错误，实际可能是 List<Object>
}
```

现在再记 PECS 才有意义：

- Producer Extends：参数主要向方法提供 `T`，用 `? extends T`；
- Consumer Super：参数主要接收方法写入的 `T`，用 `? super T`。

完整例子是复制方法：

```java
static <T> void copy(
        List<? super T> destination,
        List<? extends T> source) {
    for (T value : source) {
        destination.add(value);
    }
}

List<Integer> source = List.of(1, 2, 3);
List<Number> destination = new ArrayList<>();
copy(destination, source);
```

`source` 生产 `T`，`destination` 消费 `T`。如果一个参数既要精确读又要精确写，通常直接使用 `List<T>`。

### 7.5 边界不是为了炫技，而是为了说明方法需要什么能力

上界让方法能够调用某类 API：

```java
static <T extends Number> double twice(T value) {
    return value.doubleValue() * 2;
}
```

多个边界的语法是“一个类在前，接口在后”：

```java
static <T extends Number & Comparable<T>> T max(T left, T right) {
    return left.compareTo(right) >= 0 ? left : right;
}
```

JDK 中常见更灵活的比较边界：

```java
static <T extends Comparable<? super T>> T max(List<? extends T> values) {
    // T 可以与自己或自己的父类型比较
    return values.stream().max(Comparator.naturalOrder()).orElseThrow();
}
```

实际开发不必随手写出最后这种签名，但应该能从里向外读：`values` 提供 `T`；`T` 必须支持与其父类型进行比较。

### 7.6 类型擦除：为什么很多限制都同时出现

Java 泛型主要通过编译器实现，以保持与泛型出现前的字节码生态兼容。可以用下面的近似转换理解擦除：

```java
final class Box<T> {
    private T value;
    T get() { return value; }
}
```

擦除后近似为：

```java
final class Box {
    private Object value;
    Object get() { return value; }
}
```

调用方写：

```java
Box<String> box = new Box<>();
String value = box.get();
```

编译器在字节码层面插入必要的类型转换。无界 `T` 通常擦除为 `Object`，`T extends Number` 通常擦除为 `Number`。

由此可以统一解释多条看似零散的规则。

#### 不能 `new T()`

```java
static <T> T create() {
    // return new T(); // 编译错误
}
```

擦除后运行时不知道要调用 `String`、`User` 还是其他构造器。让调用方提供创建能力：

```java
static <T> T create(Supplier<? extends T> factory) {
    return factory.get();
}

User user = create(User::new);
```

如果需要反射构造，可显式传入 `Class<T>`，但这只适合已知构造方式的简单类型：

```java
static <T> T create(Class<T> type) throws ReflectiveOperationException {
    return type.getDeclaredConstructor().newInstance();
}
```

#### 不能检查 `instanceof List<String>`

```java
if (value instanceof List<?>) {       // 合法：只检查它是不是 List
    List<?> list = (List<?>) value;
}

// value instanceof List<String>     // 编译错误
```

运行时通常只能看到 `ArrayList`，无法根据普通实例区分 `List<String>` 与 `List<Integer>`。

#### 不能按泛型参数重载

```java
void process(List<String> values) {}
void process(List<Integer> values) {} // 擦除后都是 process(List)，签名冲突
```

#### 不能直接创建 `new T[]`

数组需要在运行时知道元素类型以执行写入检查，而 `T` 已被擦除。多数场景应直接使用 `List<T>`；确实需要数组时，让调用者提供数组工厂：

```java
static <T> T[] toArray(List<T> values, IntFunction<T[]> factory) {
    return values.toArray(factory);
}

String[] names = toArray(List.of("Ana", "Tom"), String[]::new);
```

### 7.7 “擦除”不等于所有泛型信息都从 Class 文件消失

下面两件事必须同时成立：

1. 普通对象在运行时通常不知道自己的实际泛型参数；
2. 类、字段、方法声明中的泛型签名可能保存在 Class 文件元数据中，供反射读取。

例如：

```java
final class UserController {
    private List<User> users;
}
```

反射字段声明可以读到 `List<User>`：

```java
Field field = UserController.class.getDeclaredField("users");
Type type = field.getGenericType();

if (type instanceof ParameterizedType parameterized) {
    System.out.println(parameterized.getRawType());
    System.out.println(Arrays.toString(
            parameterized.getActualTypeArguments()));
}
```

但是，仅拿到这个普通实例通常恢复不了 `User`：

```java
List<User> users = new ArrayList<>();
System.out.println(users.getClass()); // class java.util.ArrayList
```

这也是 JSON 框架反序列化嵌套类型时不能只接收 `Class<T>` 的原因：

```java
List<User> users = mapper.readValue(
        json,
        new TypeReference<List<User>>() {});
```

匿名子类把 `List<User>` 写入了父类泛型签名，框架再通过反射读取。TypeToken 没有突破擦除，而是把类型信息保存在可读取的声明位置。

### 7.8 Raw Type 与堆污染：为什么警告不应随手压掉

Raw Type 是没有类型参数的泛型类型：

```java
List raw = new ArrayList<String>();
raw.add(123);                    // 只有 unchecked 警告

List<String> names = raw;        // 只有 unchecked 警告
String name = names.get(0);      // 运行期 ClassCastException
```

变量表面声明为 `List<String>`，实际容器却混入了 `Integer`，这叫堆污染。它最危险的地方是：污染发生处与异常出现处可能相距很远。

对比：

- `List` 绕过类型检查，只应出现在兼容遗留 API 的边界；
- `List<?>` 保留“元素类型未知”这一约束，不能随意写入，因而更安全；
- `@SuppressWarnings("unchecked")` 应放在最小范围，并能解释为什么转换安全；
- `@SafeVarargs` 是作者对泛型可变参数实现安全的承诺，不会自动修复不安全代码。

泛型可变参数的风险来自数组与擦除组合：

```java
static void unsafe(List<String>... lists) {
    Object[] array = lists;
    array[0] = List.of(42);
    String value = lists[0].get(0); // ClassCastException
}
```

业务代码中优先传 `List<List<String>>`，通常比泛型数组更容易保证安全。

### 7.9 Bridge Method：只在框架和反射场景需要重点关注

```java
class Parent<T> {
    T get() { return null; }
}

class Child extends Parent<String> {
    @Override
    String get() { return "ok"; }
}
```

`Parent<T>.get()` 擦除后近似为 `Object get()`，而 `Child` 声明的是 `String get()`。编译器会在字节码中生成一个返回 `Object` 的桥接版本，并转调返回 `String` 的真实方法，以维持重写与多态。下面只是帮助理解的伪代码；两个方法不能按这种形式同时写在 Java 源码中：

```java
// 字节码层面的近似含义，不是合法 Java 源码
Object get_bridge() {
    return get(); // 调用 String get()
}
```

普通业务开发知道结论即可。编写反射扫描框架时，才需要使用 `Method.isBridge()`、`isSynthetic()` 避免把桥接方法当成额外业务方法处理。

### 7.10 写泛型 API 时的实用决策顺序

看到一个方法参数，不要立刻套 PECS，按下面顺序判断：

1. 方法完全不关心元素类型：使用 `List<?>`；
2. 多个参数或返回值必须保持同一类型关系：声明 `<T>`；
3. 参数主要提供数据给方法：考虑 `? extends T`；
4. 参数主要接收方法写入的数据：考虑 `? super T`；
5. 参数既要精确读取又要写入：通常使用 `List<T>`；
6. 只有确实需要调用某种能力时才增加 `extends` 上界；
7. 不要为了“看起来通用”引入调用者难以理解的类型参数。

例如，下面的 API 过度限制了调用者：

```java
static void printAll(List<Object> values) {
    values.forEach(System.out::println);
}

// printAll(List.of("A", "B")); // List<String> 不是 List<Object>
```

方法只读元素，正确需求是：

```java
static void printAll(List<?> values) {
    values.forEach(System.out::println);
}
```

而下面的方法必须表达来源与目标之间的类型关系，不能只用两个 `List<?>`：

```java
static <T> void copy(
        List<? super T> destination,
        List<? extends T> source) {
    destination.addAll(source);
}
```

### 7.11 面试前真正值得能说清的六个问题

#### 问题一：泛型有什么价值？

把不兼容类型的错误提前到编译期，减少显式转换，并表达参数、返回值和多个容器之间的类型关系。

#### 问题二：为什么 `List<Integer>` 不是 `List<Number>`？

因为如果允许赋值，就能通过 `List<Number>` 引用把 `Double` 写入原来的 `List<Integer>`，破坏类型安全。Java 泛型默认不变。

#### 问题三：`? extends T` 和 `? super T` 有什么区别？

`extends` 接收元素类型为 `T` 子类型的容器，可安全读成 `T`，但不能安全写入具体 `T`；`super` 接收元素类型为 `T` 父类型的容器，可安全写入 `T`，读取只保证 `Object`。使用时先根据参数是生产数据还是接收数据来判断。

#### 问题四：`List<?>` 与 `List<Object>` 有什么区别？

`List<?>` 表示元素类型未知，可能是 `List<String>`，因此不能添加具体对象；`List<Object>` 的元素类型明确是 `Object`，可以添加不同类型的对象。

#### 问题五：类型擦除带来哪些限制？

不能直接 `new T()`、`new T[]`、`T.class`，不能检查 `instanceof List<String>`，也不能只按泛型实参重载方法。运行时普通实例通常无法恢复实际类型参数。

#### 问题六：既然擦除了，TypeReference 为什么能获得 `List<User>`？

擦除不代表声明处的泛型签名元数据全部消失。匿名子类把 `List<User>` 保存在其泛型父类签名中，框架通过反射读取；它不是从一个普通 `ArrayList` 实例中猜出 `User`。

## 八、反射：能力、成本和边界

### 1. 获取 Class

```java
Class<String> c1 = String.class;
Class<?> c2 = "hello".getClass();
Class<?> c3 = Class.forName("com.example.User");
Class<?> c4 = ClassLoader.getSystemClassLoader()
        .loadClass("com.example.User");
```

- 类字面量最清晰且有编译期检查；
- `Class.forName(name)` 默认触发类初始化；
- `ClassLoader.loadClass(name)` 通常只加载，不主动初始化；
- 初始化最终还受 JVM 主动使用规则影响。

### 2. getXxx 与 getDeclaredXxx

- `getFields/getMethods` 获取公开成员，方法包含继承的公开方法；
- `getDeclaredFields/getDeclaredMethods` 获取当前类声明的成员，不自动包含父类私有成员；
- 扫完整继承链要沿 `getSuperclass()` 逐级处理；
- `setAccessible(true)` 不是无条件通行证，JPMS 强封装等仍可能限制深反射。

### 3. 反射异常与性能

```java
try {
    Object result = method.invoke(service, request);
} catch (InvocationTargetException e) {
    throw new IllegalStateException(
            "invoke process failed", e.getCause());
}
```

`Method.invoke` 将目标方法异常包装成 `InvocationTargetException`，转换时必须保留真实 Cause。

反射可能有查找、访问检查、装箱、间接调用和妨碍 JIT 优化等成本，但不要机械背“慢几十倍”：

- 启动期扫描和注册通常可接受；
- 缓存 `Class/Method/Field` 元数据，避免热路径反复扫描；
- 极热路径可评估 `MethodHandle`、代码生成或编译期处理；
- 先用 JMH/Profiler 测量，再优化。

### 4. 框架、模块化和 Native Image

反射支撑 DI、ORM、序列化、RPC，但也带来：

- 字符串类名/方法名缺少编译期验证；
- 动态引用不易被重构工具发现；
- JPMS 模块边界可能禁止深反射；
- AOT/Native Image 的闭世界分析无法自然发现动态访问，常需配置或生成元数据；
- 过度反射让依赖和控制流隐式化。

## 九、注解：元数据不等于行为

### 1. 元注解与保留策略

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
@Documented
public @interface Audited {
    String action();
}
```

- `@Target`：允许标注的位置；
- `@Retention`：生命周期；
- `@Documented`：是否进入 Javadoc；
- `@Inherited`：类级注解是否按原生规则被子类查询到。

Retention：

- `SOURCE`：仅源码期；
- `CLASS`：写入 Class 文件，运行时反射默认不可见，也是默认策略；
- `RUNTIME`：写入 Class 文件，运行时反射可见。

### 2. @Inherited 误区

`@Inherited`：

- 只影响类上的注解；
- 不使方法、字段注解自动继承；
- 不使实现类自动继承接口注解；
- `getAnnotation` 与 `getDeclaredAnnotation` 行为不同。

框架可实现更复杂的合并注解语义，不能把框架行为当成 JDK 原生行为。

### 3. 注解为什么会“执行”

注解自身不执行逻辑，行为来自：

- 编译器或 Annotation Processor；
- 运行时反射扫描器；
- 动态代理、AOP 拦截器；
- 字节码增强；
- 生成的注册代码。

编译期处理适合生成代码、提前发现错误、减少反射；运行时处理更灵活，但增加扫描、隐式控制流和 AOT 配置。

### 4. 同类调用为什么导致事务注解不生效

基于代理的 AOP 中，外部调用先进入代理，拦截器根据注解开启事务，再调用目标对象。同一对象内部 `this.method()` 没有经过代理。

```text
外部调用者 -> 代理对象 -> 拦截器/事务逻辑 -> 目标对象
目标对象 this 调用 --------------------------> 目标方法（绕过代理）
```

这不是注解本身失效，而是承载行为的代理边界未经过。解决方案可能是拆分 Bean、通过代理调用、使用编织机制，或重设事务边界。

## 十、异常体系：从语法到工程治理

### 1. Throwable 体系

```text
Throwable
├── Error
│   ├── OutOfMemoryError
│   ├── StackOverflowError
│   └── LinkageError
└── Exception
    ├── RuntimeException（Unchecked）
    │   ├── NullPointerException
    │   ├── IllegalArgumentException
    │   └── IllegalStateException
    └── 其他 Exception（Checked）
```

- Checked Exception：编译器要求捕获或声明，适合调用者确有恢复策略的失败；
- RuntimeException：常表示编程错误、前置条件破坏或当前层无法恢复；
- Error：JVM、链接或资源层严重问题，业务代码通常不处理。

“Checked 都是业务异常、Runtime 都是系统异常”是错误的。关键是**调用者能否以及是否应该恢复**。

### 2. catch 原则

- 只捕获当前层能处理、补偿、转换或增加有效上下文的异常；
- 先捕获具体异常，再捕获父类；
- 不要 `catch (Exception)` 后记录日志并返回伪成功；
- 通常不要捕获 `Throwable`，避免吞掉 `Error`；
- 转换异常必须保留 Cause；
- 不要每层重复打印同一个异常；
- 不把密码、Token、证件号、完整请求体写入异常消息。

```java
try {
    repository.save(order);
} catch (DuplicateKeyException e) {
    throw new OrderAlreadyExistsException(order.getId(), e);
}
```

### 3. finally 与 try-with-resources

- `finally` 通常执行，但进程强制终止等情况除外；
- 不要在 `finally` 中 `return`，会覆盖返回值或原始异常；
- 资源管理优先 try-with-resources；
- 资源按声明的逆序关闭；
- 主逻辑和 `close()` 都抛异常时，主异常保留，关闭异常进入 Suppressed Exceptions。

```java
try (InputStream in = openInput();
     OutputStream out = openOutput()) {
    in.transferTo(out);
} catch (IOException e) {
    for (Throwable suppressed : e.getSuppressed()) {
        // 关闭资源时的附加异常
    }
    throw e;
}
```

### 4. InterruptedException 绝不能吞

阻塞方法抛 `InterruptedException` 时通常会清除中断标记。当前层不能真正处理取消时，应向上抛，或恢复中断状态后尽快退出：

```java
try {
    queue.take();
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    throw new TaskCancelledException("task interrupted", e);
}
```

吞中断会破坏任务取消、线程池关闭和超时控制。

### 5. 分层转换与错误契约

```text
数据库/HTTP 客户端异常
        ↓ 保留 cause，屏蔽供应商细节
领域或应用异常
        ↓ 全局异常处理器
HTTP/gRPC 状态 + 稳定业务码 + traceId
```

- Repository 层把具体约束异常转换为领域可理解的冲突；
- Service 层表达 `OrderNotFound`、`InsufficientBalance` 等语义；
- API 层统一映射状态、错误码、用户消息和 `traceId`；
- 5xx 对外不暴露堆栈和 SQL，对内保留完整 Cause 和链路信息；
- 不要所有失败都返回 HTTP 200，否则会破坏网关、监控、重试和缓存语义。

### 6. 异常与重试

适合重试需要同时满足：

- 瞬时错误，如明确超时、限流、临时不可用；
- 操作幂等，或有幂等键/去重机制；
- 有次数上限、指数退避和抖动；
- 总超时预算允许；
- 不会形成重试风暴。

参数错误、权限失败、余额不足、唯一键冲突通常不应盲目重试。异常分类会直接决定重试、熔断、告警和降级。

### 7. 异常性能

创建异常通常要采集堆栈，抛出和展开也有成本，所以异常不用于正常流程。但异常路径本应低频，正确性和可诊断性优先。若异常高频，先判断它是否其实是正常分支或系统正在持续故障。

## 十一、高频问题标准回答

### 1. ArrayList 和 LinkedList 怎么选？

> 普通列表优先 ArrayList。它随机访问 O(1)、尾插摊销 O(1)，内存连续且缓存友好。LinkedList 的插删 O(1) 只在已经定位节点后成立，按下标定位仍是 O(n)，每个节点还有额外指针成本。队列和栈通常使用 ArrayDeque。

### 2. HashMap 的 put 流程？

> 先计算扰动 Hash，通过 `(n - 1) & hash` 定位桶。空桶直接放入；非空桶比较 Hash 和 equals，相同 Key 覆盖，否则加入链表或红黑树。元素超过容量乘负载因子的阈值时扩容。JDK 8 的桶达到典型阈值 8 且数组容量至少 64 才树化，否则通常先扩容。

### 3. 为什么 equals 相等必须 hashCode 相等？

> Hash 容器先通过 hashCode 找桶，再用 equals 确认。若 equals 相等但 hashCode 不同，逻辑相同对象可能进入不同桶，导致查找和去重失败。hashCode 相等则允许碰撞，再靠 equals 区分。

### 4. HashMap 和 ConcurrentHashMap 的区别？

> HashMap 不支持并发写且允许 null。ConcurrentHashMap 通过 CAS、桶级同步和可见性机制支持并发，Key/Value 均不允许 null，提供 putIfAbsent、compute、merge 等原子复合 API；迭代器弱一致。多个原子调用拼起来仍不自动成为事务。

### 5. Fail-Fast 是什么？

> 普通集合迭代器记录结构修改计数，发现迭代期间存在非迭代器自身修改时，尽力抛 ConcurrentModificationException。它是 Bug 检测机制，不是线程安全保证，也不保证每次竞态都能发现。

### 6. `? extends T` 和 `? super T`？

> extends 是生产者，可安全读成 T，但不能安全写具体 T；super 是消费者，可安全写 T，读出来只能保证 Object。口诀是 PECS：Producer Extends, Consumer Super。

### 7. 为什么不能 `new T()`？

> Java 泛型采用类型擦除，运行时通常没有足够信息知道 T 的具体类型和构造器。常见做法是传入 Class、Supplier 或 Factory；嵌套泛型传 Type/TypeToken。

### 8. 注解为什么能让事务生效？

> 注解只是元数据。框架扫描注解并通过代理或字节码增强拦截调用，在方法前后开启、提交或回滚事务。若基于代理，同类内部 this 调用可能绕过代理。

### 9. Checked 和 Unchecked 怎么选？

> 看调用者是否有明确、合理的恢复动作，而不是机械按业务/系统分类。Checked 强制处理或声明，适合确实可恢复并希望 API 显式表达的条件；RuntimeException 适合编程错误、前置条件破坏或当前链路无法恢复的问题。边界处都要转换为稳定错误契约并保留 Cause。

### 10. 为什么不能吞 InterruptedException？

> 中断是线程协作的取消信号，阻塞方法抛异常时中断标记通常已清除。吞掉后上层误以为任务没取消，会破坏线程池关闭和超时机制。不能处理时向上抛，或恢复 interrupt 状态并尽快结束。

## 十二、场景化选型

### 场景 1：统计用户访问次数

```java
ConcurrentHashMap<UserId, LongAdder> counters = new ConcurrentHashMap<>();
counters.computeIfAbsent(userId, id -> new LongAdder()).increment();
```

继续追问：计数是否强一致、是否允许丢失、是否跨节点、Key 是否无限增长。单机集合不能自动解决分布式一致性和容量治理。

### 场景 2：最近访问的 1,000 个对象

单线程简单场景可用访问顺序的 `LinkedHashMap`；并发生产环境优先成熟缓存库。还要明确按数量还是权重淘汰、是否过期、加载失败和缓存穿透。

### 场景 3：读多写少的监听器列表

可用 `CopyOnWriteArrayList`，遍历不加锁且快照稳定。若监听器频繁变更或数量巨大，复制成本不可接受。

### 场景 4：按时间范围查询

少量内存数据可用 `TreeMap<Instant, ...>` 的范围视图；大规模、持久化、多节点场景应交给带索引的数据库或搜索系统。

## 十三、面试前速记

- `ArrayList`：动态数组，随机读 O(1)，尾插摊销 O(1)，扩容通常约 1.5 倍；
- `LinkedList`：双向链表，定位 O(n)，节点开销和局部性差；
- `HashMap`：2 的幂、扰动、负载因子 0.75、扩容、树化 8/64、equals/hashCode；
- `ConcurrentHashMap`：不允许 null、CAS + 桶级同步、弱一致迭代、原子复合 API；
- `TreeMap`：红黑树 O(log n)，比较器与 equals 最好一致；
- `ArrayDeque`：栈和队列常规首选；
- 泛型：不变性、PECS、擦除、桥接方法、Raw Type、Type Token；
- 反射：Class 获取、Declared/Public、InvocationTargetException、缓存、模块/AOT；
- 注解：Retention、Target、Inherited；行为来自处理器、代理或增强；
- 异常：只捕获能处理的、保留 Cause、TWR、Suppressed、恢复中断；
- 架构：边界转换、稳定错误码、可观测、明确重试性，选型考虑并发、容量和生命周期。

## 总结

集合的核心是数据结构、复杂度与并发语义；泛型的核心是编译期类型关系和擦除边界；反射与注解的核心是框架如何发现元数据并注入行为；异常的核心是失败分类、恢复策略与跨层契约。

高级面试不会止于“HashMap 查询 O(1)”或“反射性能差”，而会继续追问这些结论的前提、实现边界和生产事故。
