# 03. 如何在准确率、延迟与成本之间进行权衡

## 第一步：定义目标

按 Use Case 定义 Quality、P95 Latency、Cost per Successful Task 和风险。不要为所有请求使用相同等级。

例如：

```text
FAQ: quality >= 85%, P95 < 2s, €0.01/request
Contract analysis: quality >= 95%, P95 < 30s, €1/task, human review
```

## 建立 Baseline

用代表性 Dataset 测当前 Model + Prompt + Retrieval 的质量、TTFT、Total Latency、Token 和失败率。没有 Baseline 无法判断优化收益。

## 优化杠杆

### 提高质量

- 更好 Retrieval/Rerank。
- 强 Model/Reasoning。
- Tool Verification。
- Fine-tuning。
- Human Review。

### 降低延迟

- 缩短 Prompt/Context。
- 并行独立步骤。
- Streaming。
- Cache。
- 小 Model。
- 限制 Output。

### 降低成本

- Model Routing/Cascade。
- Exact/Semantic Cache。
- Batch。
- Context Compression。
- 小 Model 或自托管 Break-even。

## Routing

简单任务先走小 Model；低 Confidence、复杂或高风险任务升级。Router 使用规则 + 分类器，并评估错误路由。不要只根据 Prompt 长度判断复杂度。

## Pareto Frontier

比较多个配置，找出无法在不牺牲另一维度下继续改善的方案。由业务选择处于哪一点，而不是架构师单方面追求最高质量。

## Guardrail

安全与权限不是普通可交换指标。任何成本优化都不能跨越数据泄露、未授权 Tool 和法规底线。

## 持续治理

按 Model/Prompt/Route 监控质量、P95 和 Unit Cost。价格、流量和任务分布变化后重新评估。

## 面试亮点

用数字定义目标，展示 Cascade、Context、Cache 和 Human Review 的组合，并明确最重要的是 Cost per Successful Outcome，而非每次调用最低价格。
