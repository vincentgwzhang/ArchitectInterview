# 01. 文档采集、清洗、切分、元数据与版本管理

## Ingestion Pipeline

```text
Source -> Connector -> Parse/OCR -> Normalize -> Classify
       -> Chunk -> Enrich Metadata -> Embed -> Index
```

每一步应 Idempotent、可重试、可观测，并保留 Source Lineage。

## 采集

来源可能是 Google Drive、SharePoint、S3、Database、Wiki 和 Ticket System。Connector 需要处理增量同步、删除、权限变化、Rate Limit 和 Webhook 丢失。

为每份文档保存稳定 `source_id`、版本、Checksum、更新时间和同步状态，避免每次全量重复 Embedding。

## 解析与清洗

- 删除 Header/Footer 和导航噪音。
- 保留标题层级、表格、列表和页码。
- OCR 标记置信度。
- 统一编码与空白。
- 不要丢失 Citation 所需位置。
- 对扫描 PDF、图片、代码使用不同 Parser。

清洗过度可能改变法律文本或数字含义，需要保留原文链接和 Hash。

## Chunking

方法：固定 Token、句子/段落、标题语义、Recursive、Parent-child。选择取决于文档结构和 Query。

Chunk 太小缺少 Context，太大降低 Retrieval Precision 并增加 Token Cost。Overlap 可以保留边界信息，但增加重复 Index 与结果冗余。

## Metadata

至少考虑：

- Source/Document/Chunk ID。
- Title、Section、Page。
- Version、Updated At。
- Language、Content Type。
- Tenant、ACL、Classification。
- Product/Region/Effective Date。
- Parser/Chunker/Embedding Version。

Metadata 同时支持 Filter、Citation、Debug 和 Reindex。

## Versioning 与删除

新版本 Index 完成后再原子切换，避免查询半成品。删除源文档时必须传播 Tombstone，清除 Vector、Keyword Index 和 Cache。

保留 Pipeline Version，使离线评测能重现“哪种 Chunk + Embedding + Retriever”产生结果。

## 监控

Document Lag、Parse Failure、Empty Chunk、Duplicate、Embedding Failure、ACL Missing 和 Index Count Drift。

## 总结

RAG 质量从 Ingestion 开始。可追溯的文档版本、结构感知 Chunk、丰富 Metadata 和可靠删除比单纯选择 Vector Database 更重要。
