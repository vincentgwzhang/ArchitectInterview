# 01. 面向技术团队和业务方表达架构方案

> 架构沟通的交付物是可理解、可执行、可验证的决定。本章案例均为虚构教学场景，不代表用户经历。示例中的目标与预算是待验证假设，不是生产测量或行业基准。

## 一、架构师为什么必须会沟通

架构影响多个团队的工作、预算和风险，设计者通常没有对所有参与者的直接管理权。影响力来自清楚的问题定义、可信证据（Evidence）、对利益相关方（Stakeholder）的理解、诚实的取舍（Trade-off）以及稳定共同语言。仅凭职位或组件复杂度，不能保证实施者理解意图，更不能保证运营方能恢复系统。

沟通是降低协调错误的工程活动。例如“下单成功”可能分别表示 API 接收、订单落库或支付确认；若不同团队各按自己的定义实现，接口都通过测试，业务仍可能失败。架构师应把术语、边界、验收和责任显式化，并请对方复述关键行为以检查理解。

沟通成功不等于所有人喜欢同一方案。合适的结果可能是批准、拒绝、带条件批准或先做验证；每一种都应说明依据和下一步。八十页幻灯片一次发给所有人，容易把关键信息埋在细节里；更好的做法是统一事实底稿，按受众分层展示。

## 二、识别 Audience：改变粒度，保持事实一致

Audience（受众）分析先问：对方需要做什么决定，有什么权限，承担什么后果，缺少什么信息。不是按职位假定对方“不懂技术”；财务负责人可能深入理解承诺成本，工程师也需要商业目标。

| 受众 | 决策问题 | 应给的证据与边界 |
| --- | --- | --- |
| Executive 高管 | 投资是否支持业务目标，何时见效 | 收益假设、范围、投资区间、关键风险和停止条件 |
| Product 产品 | 哪些用户问题优先，怎样分期 | 用户旅程、Scope 范围、依赖、验收及被延后的能力 |
| Engineering 工程 | 谁实现什么，失败时怎么办 | 边界、Contract 契约、数据权威源、并发和迁移规则 |
| Operations/SRE 运维 | 是否能安全运行与恢复 | SLO、容量、告警、Runbook、值班与演练证据 |
| Security/Legal 安全法务 | 哪些数据和义务受影响 | 威胁、用途、控制、保留和待确认的合规适用 |
| Finance 财务 | 总成本及现金风险是否可控 | TCO、预测、单位成本、供应商承诺和退出费用 |

SLO（服务水平目标）规定用户体验的目标口径与窗口；TCO（总拥有成本）涵盖选定范围内建设、运行、人员和迁移退出成本，不只是云报价。Runbook 是按症状执行的受控处置手册，不是一张运维系统链接。

同一 Multi-region（多地区）方案，向高管说明客户服务连续性与投资，向工程解释流量路由、数据复制和冲突规则，向运维解释故障切换、演练与告警。三种表达必须共享同一恢复承诺：如果异步复制可能丢失最近写入，就不能对高管说“绝不丢数据”，再在工程附件里悄悄写例外。

先建立相关方清单，区分决定者、实施者、受影响者和提供意见者。邀请没有决策权但承担值班的人，可以提前发现隐性运营成本；不需要把所有人都变成每个细节的批准者，否则会拖慢可逆决定。

## 三、通用结构：让听众知道要决定什么

开头先说问题、建议和本次需要的决定，再逐步展开。下面十项构成一条论证链，不能变成彼此无关的目录。

| 内容 | 应回答什么 | 虚构订单案例 |
| --- | --- | --- |
| Context 背景 | 当前边界和触发变化是什么 | 下单链路同步调用通知供应商 |
| Problem 问题 | 不解决有何可观察影响 | 通知超时拖慢或阻断下单 |
| Goals / Non-goals | 本次成功与范围外是什么 | 隔离通知失败；暂不改支付确认 |
| Drivers 驱动因素 | 哪些约束决定取舍 | 订单可靠、交付窗口、团队运营能力 |
| Options 选项 | 可行替代包括维持现状吗 | 超时隔离、数据库任务、消息平台 |
| Recommendation 建议 | 推荐什么、为什么 | 先做可靠任务记录与异步通知 |
| Trade-offs | 获得什么、承担什么 | 前台隔离，后台增加积压与重试治理 |
| Risks / Mitigations | 剩余风险由谁负责 | 重复通知靠去重，积压靠告警与限额 |
| Roadmap 路线 | 如何分期验证和切换 | 小流量、故障测试、扩大、退役旧路径 |
| Decision Needed | 谁何时批准哪一范围 | 负责人确认第一阶段预算与验收条件 |

Drivers 应可排序。例如“支付正确性必须满足，通知可延迟，第一阶段人力有限”，比“高性能、高可用、低成本都要”更能筛选选项。硬约束（Constraint）先过滤，偏好再比较；违法或无法满足安全底线的选项，不因总分高就可用。

推荐不是隐藏替代方案。至少说明最简单可行方案为什么不足，以及什么条件下它反而更好。还应考虑不做或延期的机会成本：如果通知问题很少且简单超时隔离足够，立即引入新平台可能不值得。

## 四、面向业务方：把机制翻译成结果与承诺

### 4.1 从结果开始，但保留因果链

“我们要引入 Kafka 和 CQRS”只说了技术。Kafka 是事件流平台，CQRS 是把读与写职责分开的设计方法；它们不天然保证业务连续性。更有用的表述是：

“当前通知供应商故障会影响下单。建议先把通知从订单确认的同步路径移出，让客户在订单可靠保存后得到确认；通知允许延迟，并由后台补发。这样能隔离这一类故障，但不能解决支付失败，也需要积压监控、去重和客服可见的状态。”

这段话说明了结果、机制、边界和新责任。不要把“异步”翻成“即时且必达”，也不要承诺系统从此不会故障。业务方仍要确认通知延迟是否可接受、是否有必须同步告知的特殊场景。

### 4.2 用业务指标讲投资，不伪造收益

讨论 Downtime（不可服务时间）、转化率、客户流失、SLA（服务水平协议）、投资和人员时，先定义统计范围。Release Lead Time 是从约定起点到可用发布的时间；若团队把起点定义不同，横向对比会误导。SLA 可能带合同后果，不能把内部 SLO 自动当客户承诺。

例如“目标把通知故障导致的下单失败降到约定范围”需先有失败归因和基线。不能从技术延迟下降直接推导收入增长；转化率还受价格、流量与营销影响。用“假设、预测区间、验证方法”表达不确定性，必要时用试点验证而不是一次批准全面重写。

TCO 要计入实现、平台、监控、值班、培训、迁移双运行和退役；成本节省也区分现金减少与释放人员时间。若释放时间用于别的工作，不能同时当裁员节省和新增产出重复计算。明确不做的风险也包括趋势与替代缓解，不能只靠事故恐吓争取预算。

### 4.3 可填写的业务摘要

可以使用以下模板，每个空格都应填实际证据或明确标为待验证：

~~~text
问题与影响：[用户旅程] 在 [条件] 下发生 [结果]，证据为 [期间/口径/来源]。
建议：[第一阶段改变]，主要通过 [一句机制] 改善 [目标]。
替代：[简单方案/延期]；未选原因：[约束及证据]。
投入：[人力/预算范围]，包含 [运营与迁移]，不包含 [范围外项]。
风险：[最重要剩余风险]，由 [Owner] 执行 [验证/缓解]。
验收与停止：[指标/窗口/门槛]，未满足时 [停止、回退或重评]。
本次决定：[Decider] 在 [时间] 确认 [具体范围]。
~~~

不能填写的字段本身就是待解决的信息缺口。早期探索可以提出“批准验证”而非假装可以批准正式上线。

## 五、面向技术团队：把建议变成可实施契约

### 5.1 技术说明的最小完整面

技术文档应让未参会工程师能实现并判断失败，不仅能画出组件。

| 信息 | 具体内容 | 遗漏后果 |
| --- | --- | --- |
| 边界与 Ownership | 负责团队、接口归属、变更批准和排障责任 | 跨团队故障互相等待 |
| API / Event Contract | 字段、版本、校验、错误、幂等、顺序与兼容 | 重试重复执行或消费者升级失败 |
| Data Model / Source of Truth | 状态转换、权威写入者、事务边界 | 多方写同一事实产生冲突 |
| NFR / Capacity | 非功能需求、峰值、大小、并发、增长与假设 | 看似低延迟却在峰值崩溃 |
| 安全控制 | 身份、租户授权、敏感数据与审计 | 内部调用误认为天然可信 |
| 失败与恢复 | 超时、重试、部分成功、积压、补偿 | 超时被误当一定未执行 |
| 演进与发布 | 迁移、测试、灰度、兼容、回滚与退役 | 代码回退后无法读取新数据 |

Source of Truth 是某一事实的权威系统，不意味着所有数据必须放一个库。NFR（非功能需求）如延迟、可用性和可恢复性，需要可测量的场景；“支持大流量”无法成为验收标准。

### 5.2 同一订单例子的失败语义

建议订单记录与待发送事件在同一数据库事务写入 Outbox（事务发件箱），后台再发布通知任务。这避免“订单已保存、进程崩溃导致任务永久没写”的窗口，但后台发送成功后标记前崩溃可能重复发送，因此不能宣传端到端 Exactly Once（只执行一次）。

契约需要定义 eventId 去重、orderId 关联、租户、版本和允许消费者读取的最小字段；通知消费者记录处理状态，对可重试超时设上限与退避，不能无限压垮供应商。消息去重记录和外部发送副作用仍有原子性边界：供应商支持幂等键时利用同一键，不支持时必须接受并说明剩余重复风险。

验收应覆盖提交后进程崩溃、重复投递、供应商超时但已接收、旧消费者遇新字段、积压超阈值和未授权租户事件。回滚时不能直接删除未处理任务；保留兼容消费者、排空或受控转交，并核对重复与遗漏。这样技术说明才真正支持部署与值班。

### 5.3 明确语句的约束强度

Constraint 是不可违背的限制；Decision 是在确定范围已批准的选择；Recommendation 是待讨论建议；Example 是解释用示例。四者应显式标注状态与适用范围，避免团队把伪代码当生产规范。

例如“租户授权是约束，第一阶段采用 Outbox 是待批准建议，eventId 字段示例不是完整事件模式”。Decision 也可能被新证据替代，需要记录新决定与原因，不能悄悄覆盖历史使维护者不知道为何迁移。

## 六、图与叙事：每张图只解决一个理解问题

Context Diagram（上下文图）说明系统与用户、外部系统的边界；Container Diagram（容器图）说明应用和数据存储等主要运行单元，C4 的 Container 不等于 Docker 容器。Sequence Diagram（时序图）讲一次关键旅程中的先后、并发和失败；Deployment Diagram（部署图）解释运行节点、故障域与安全边界。

可以从上下文到构成，再选一条用户旅程和部署场景，不必机械画全所有层级。C4 的核心静态层级是上下文、容器、组件、代码，时序图是可配合使用的行为表达，不应把它误称为 C4 第三级。

每个箭头写明方向、协议、数据语义及同步/异步；图例标识信任边界、已存在与计划新增部分。图无法容纳完整契约时，链接到有版本的接口说明，不能依靠读者猜。图中的运行单元名称与日志、仓库和责任清单保持一致，避免一个服务有三种叫法。

虚构订单案例可用以下时序图解释“可靠保存、异步补发、可能重试”：

~~~mermaid
sequenceDiagram
    participant C as 客户端
    participant A as 订单服务
    participant D as 数据库
    participant W as 后台发布器
    participant N as 通知供应商
    C->>A: 提交订单及幂等键
    A->>D: 同一事务保存订单和待发事件
    D-->>A: 提交成功
    A-->>C: 返回订单确认及通知待处理
    W->>D: 读取待发事件
    W->>N: 发送通知及稳定幂等键
    alt 确认成功
        N-->>W: 接收确认
        W->>D: 标记事件已处理
    else 超时或结果未知
        W->>D: 保留任务并安排有界重试
    end
~~~

图只表达协议意图，不保证供应商真的支持幂等，也未表示完整支付流程。讲解时沿一条订单走，再用“供应商已收到但响应丢失”检验听众是否理解风险，比堆更多方框有效。

## 七、Evidence：事实、假设与意见必须分开

Fact（事实）是限定条件下可核查的观察；Assumption（假设）是设计暂依赖但尚未充分验证的前提；Opinion（意见）是基于经验或偏好的判断。事实也有范围与误差，不是贴上标签就永远正确。

“当前 p99 为 1.8 秒”必须带期间、端点、流量、成功/失败口径和采集位置。p99 表示约 99% 观测不超过该值，不能平均不同实例的 p99 来得到全局值。“用户增长 50% 后数据库会成为瓶颈”则是待验证假设，增长可能改变读写比例与热点，不能只乘平均请求数。

| 证据 | 能支持什么 | 不能直接证明什么 |
| --- | --- | --- |
| Production Metric | 指定期间的真实行为 | 未来所有峰值都安全 |
| Incident / Postmortem | 故障条件、影响和控制缺口 | 相似症状必定同根因 |
| Load Test 负载测试 | 给定模型下的边界 | 测试数据一定代表生产 |
| Cost Report | 所选期间和分摊口径的费用 | 下一年现金支出一定相同 |
| Customer Feedback | 用户痛点和使用情境 | 小样本代表所有客户 |
| Prototype / Spike | 关键可行性、集成或学习结果 | 已具备生产安全和运营能力 |
| Security Assessment | 已评估范围的风险 | 未测试路径不存在漏洞 |

为假设指定验证任务，例如“两周内用代表性读写与故障模型测试三倍当前峰值，并记录通过/失败门槛”。三倍是案例自定场景，不是统一容量标准。无法在决定前验证时，减少承诺范围、保留余量、设置复审触发；不要把未知转写为确定性能收益。

可用决策表比较方案，但权重和分数也是判断，必须给理由。先筛硬约束，再做敏感性分析：如果人力不足或流量预测减半，推荐是否改变？加权总分不能让存在不可接受数据丢失的方案自动通过。

## 八、处理提问与异议：把争论变成可验证问题

先复述 Concern（关切）并确认理解，再映射到 Driver，给证据与边界。比如“你担心重复通知造成客户投诉，核心是副作用可控，而不是反对异步本身”。随后说明幂等能力、剩余风险和验证，不以“对方不懂技术”结束讨论。

未知时可以完整回答：“目前没有证据证明供应商超时后一定未发送。我会由接口负责人确认幂等契约，并做超时后查单测试。在结果前，只批准沙箱验证，不批准正式自动重试；结果记录在本决定的开放问题中。”这比即兴猜测或只说“会后再看”更可靠。

若两个 Reviewer 提出互斥意见，把冲突写成同一个公开问题，说明各自优化的目标与证据，请有权限的 Decider（决定者）裁定。架构师可以推荐，不能假借沟通自行授予预算或接受安全例外。若只是局部可逆实现差异，可由实现团队在约束内决定，不升级成全员委员会。

对新证据修订建议不是失去权威；隐瞒反证才会破坏信任。人身或重复偏题争论可终止并回到共同标准，但保留实质异议、风险接受人与复审条件。记录不同意并执行合法已批准决定，不等于要求参与者假称从未有异议。

## 九、架构会议：为决定设计流程

### 9.1 会前让不同时间区都有参与机会

Pre-read（预读材料）包含一页摘要、备选、证据和标记的 Open Questions（开放问题），提前给约定评论时间。明确本次是信息说明、征求意见还是正式决定，指定 Decider、主持人、记录者及受影响团队。尚未明确预算权或安全责任时，不能把会议出席当作批准权限。

提前收集异议，尤其是运维、安全、依赖团队的约束。异步评论要有响应期限和关闭规则，但“没有回复”不能自动等于批准，除非现有治理流程明确允许且适用于这类决定。

### 9.2 会中聚焦争议与结论

重申目标和 Timebox（时间限制），先确认硬约束与证据，再讨论真正有差异的选项，不逐字朗读文档。Parking Lot（暂存议题）保存偏题事项，并给负责人决定后续是否处理，不能作为永久掩埋重大风险的工具。

主持人邀请受影响者提出执行障碍，区分事实争议、价值排序争议与权限争议。事实争议安排验证；价值取舍交决定者；权限不清先澄清。到时间仍缺关键证据，输出“延期及必要条件”，比强行投票制造假共识好。

### 9.3 会后形成可追踪闭环

Decision Summary（决定摘要）写明选项、依据、批准范围、条件、未接受选项原因、异议、Owner、Deadline 和复审触发。行动项不是决定本身：“张三两周内调查消息平台”仅是验证任务，不能写成“已批准迁移”。

更新 RFC（征求意见提案）与 ADR（架构决定记录），向未参会相关方同步，按期限检查行动结果。ADR 保存一个重要选择、上下文与后果；不要求所有小实现都建 ADR，也不应把会议聊天全文当作决定日志。

## 十、书面沟通：一页可决策，附件可实施

文档首页应能读懂问题、推荐、范围、关键代价和需要决定什么；随后按受众放证据、图、接口与迁移细节。写 Status、Owner、Review Date、版本与变更历史，让读者区分草案、已批准和被替代。

稳定术语与可定位段落支持异步评论。每个重要评论应有答复和处理结果，不能在新版本悄悄删掉未解问题。证据链接注明快照日期或版本；只链接一个不断变化的仪表盘，未来可能无法重建当时决定依据。敏感资料限制访问，同时在正文保留可公开的结论与限制。

可填写的技术决定模板如下，按风险规模裁剪：

~~~text
标题/状态/负责人/版本/复审日期：
决定范围与决定者：
业务问题与证据口径：
目标、非目标、约束和排序：
可行选项及未选理由：
建议与状态（建议/已批准/带条件）：
接口、数据权威、失败语义与安全边界：
投入、依赖与承担的新运营责任：
迁移、验证、发布、回退和退役：
未知、验证负责人/期限、停止与复审条件：
决定结果、行动项及通知对象：
~~~

模板的价值是防遗漏，不是每个字段都写相同长度。小范围可逆选择可以短记录；涉及多团队、数据迁移和合同的选择应更完整。过多文档也有维护成本，优先保持权威入口与版本关联。

## 十一、面试场景：给完整回答和追问

### 11.1 如何向非技术高管解释重构投资？

**完整示例回答（虚构）：**“我先用当前发布等待、事故和受影响用户的证据说明问题，并区分已观察事实与未来风险。不会只说代码不好维护或要求全面重写。我建议先把经常阻塞交付的订单通知边界拆清，保留订单和支付核心。第一阶段批准的是有期限试点，包括实现、运维和迁移成本；以既定发布时间口径、故障隔离和重复通知风险验收。达标后再决定扩展，若收益不足或关键幂等能力不存在就停止并重评。我定期同时报告业务结果、投入和风险，不把技术改动直接包装为确定收入。”

**追问：高管说业务功能更重要，怎么办？** 认可机会成本，把维持现状、局部修复和分期重构在同一交付窗口下比较。若当前风险可控，允许延期并定义复审触发；若触及不可接受安全或数据风险，明确需要有权限的人处理，而不是私下用加班掩盖冲突。

### 11.2 同一个 Cloud Migration 怎样讲给 CFO 和后端工程师？

**完整回答：**“我给 CFO（财务负责人）看当前费用基线、迁移投入、双运行、承诺折扣风险、人员与退出成本，解释现金和单位业务成本的情景范围。给后端工程师看接口兼容、身份、数据迁移、一致性、超时与重试、发布和回退步骤。两者共享同一业务范围、时间线和恢复要求，成本不能遗漏工程团队新增的值班责任。”

**追问：供应商报价很低，能承诺节省吗？** 不能仅凭报价。核对实际用量、出网、支持、闲置承诺和迁移成本，做试点和敏感性分析，再报告条件下的预测。费用降低但恢复能力不达标的方案不能视为达成同一目标。

### 11.3 团队不接受推荐方案，怎样推进？

**完整回答：**“我先请团队具体说明障碍，判断是证据不足、运营能力欠缺还是驱动排序不同。如果是缺经验，比较培训、托管或简单替代，不强行把复杂度交给值班。如果是性能争议，预先约定测试模型和判定门槛；如果是风险接受与预算冲突，交明确的决定者。记录结论、异议与复审条件，让执行者能理解为何选，即使不是自己首选。”

**追问：到了期限仍无共识呢？** 在已明确的决策机制内，由有权者决定或延期；说明延期代价与可逆临时方案。不能把沉默当同意，也不能让“大家再研究”成为没有负责人和期限的无限阻塞。

## 十二、常见错误与修正

从技术组件开场会让听众猜价值，应先给问题、建议与决策请求。给所有受众同一细节会让人过载，应共享事实而按需要调整粒度。只展示推荐方案会隐藏机会成本，应呈现最简单替代和不做的后果。

隐藏代价与未知，会把合理方案变成不可信承诺；改为写明假设、验证与停止条件。漂亮图没有责任、契约和故障语义，会让实施者自行猜测；用关键旅程和反例检查。会议没有决定或下一步，会让不同团队带走不同结论；书面确认批准范围与行动项。

把异议解释为“对方不懂”会错过风险并破坏合作。先复述问题，再判断证据与权限；必要时改变推荐。沟通不是提高说服技巧直到别人同意，而是让组织承担经过理解的选择。

## 十三、扫雷自测与完整答案

1. **如何向 CFO 和 Backend Engineer 解释同一云迁移？** CFO 需要投入、现金、TCO、情景与退出风险；工程师需要契约、数据迁移、失败、安全和回退。双方恢复承诺、范围与时间线必须一致，否则财务会批准一个工程实际上无法兑现的方案。
2. **开头最重要的三个内容是什么？** 当前业务问题、推荐方向、需要谁作什么决定。详细背景随后补充，因为听众先知道判断对象，才能理解组件与证据为何相关。
3. **为什么区分 Fact、Assumption 和 Opinion？** 它们需要不同处理：事实检查口径，假设安排验证，意见暴露偏好与理由。混淆会把未测容量或个人偏好误写成强制约束。
4. **如何处理当场无法回答的质疑？** 复述问题、说明已知与未知，记录负责人、验证方法、期限及对批准范围的影响。不能猜测答案；关键风险未明时只批准可控验证，不扩大正式承诺。
5. **有效会议结束应产生什么？** 明确批准、拒绝、带条件批准或延期，以及原因、范围、Owner、期限、行动和复审条件。一个调查任务不是最终架构决定。
6. **异步通知是否意味着绝不丢也不重复？** 不意味着。事务记录减少遗漏窗口，发布或消费重试仍可能重复；外部副作用需要幂等能力或明确剩余风险。表达收益时必须包含这些边界。
7. **图里 Container 是否必然是 Docker？** 不是，C4 用它表达应用和数据存储等运行单元。部署技术另在部署视图说明，混用会让读者把逻辑责任误当运行实例。
8. **没有人反对是否等于批准？** 通常不能这样推断，可能有人没读、缺权限或不在场。按明确治理规则获取必要决定，保持评论期限与升级路径。
9. **回滚代码为什么未必恢复原状？** 数据格式、已发送通知和外部支付可能已经变化。需要兼容、排空与补偿，架构说明不能只给旧镜像版本。
10. **方案评分最高是否必须采用？** 不一定。硬约束先过滤，分数依赖主观权重与证据；应检验关键假设变化后排序是否稳定。评分帮助透明，不能替代责任与判断。

## 十四、速记与验证范围

速记：**受众与权限 → 问题与结果 → 约束和选项 → 证据与未知 → 取舍和失败 → 决定范围 → Owner、路线与验证。**
