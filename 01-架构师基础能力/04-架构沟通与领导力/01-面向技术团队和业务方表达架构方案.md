# 01. 面向技术团队和业务方表达架构方案

## 学习目标

1. 根据 Audience 调整架构信息的深度和语言。
2. 用 Problem、Driver、Decision、Trade-off 表达方案。
3. 把技术选择映射到业务结果和风险。
4. 主持高效的架构说明与决策会议。

## 一、架构师为什么必须会沟通

架构方案只有被理解、接受并正确执行才会产生价值。架构师通常没有对所有团队的直接管理权，因此影响力主要来自：

- 清楚的问题定义。
- 可信的 Evidence。
- 对不同 Stakeholder 的理解。
- 对 Trade-off 的诚实说明。
- 持续建立共同语言。

沟通不是把同一份 80 页 Slide 发给所有人，而是让每个 Audience 获得做决策所需的信息。

## 二、识别 Audience

| Audience | 最关心的问题 |
| --- | --- |
| Executive | 业务结果、投资、风险、时间线 |
| Product | 用户价值、Scope、依赖、交付顺序 |
| Engineering | Boundary、Contract、Failure、实施细节 |
| Operations/SRE | SLO、容量、监控、恢复、On-call |
| Security/Legal | Threat、Data、Control、Compliance |
| Finance | TCO、Forecast、Unit Cost、Vendor Commitment |

同一个 Multi-region 方案：

- 对 Executive：强调收入保护、客户 SLA 和投资。
- 对 Engineering：强调 Routing、Replication、Conflict 和 Deployment。
- 对 Operations：强调 Failover、Runbook、演练和 Alert。

## 三、通用表达结构

推荐结构：

```text
1. Context：当前发生了什么？
2. Problem：不解决会有什么影响？
3. Goals / Non-goals：本次要解决与不解决什么？
4. Drivers：哪些指标和约束最重要？
5. Options：有哪些可行方案？
6. Recommendation：推荐什么？
7. Trade-offs：获得什么、放弃什么？
8. Risks and Mitigations：如何降低风险？
9. Roadmap：如何分阶段实施？
10. Decision Needed：希望谁在什么时候决定什么？
```

先讲问题和决策，再讲组件。不要让听众在大量技术细节中猜测重点。

## 四、面向业务方表达

### 4.1 从结果开始

较差表达：

> 我们要引入 Kafka 和 CQRS。

更好表达：

> 当前订单处理与通知同步耦合，通知供应商故障会阻止客户下单。我们建议把非关键处理异步化，使 Checkout 在通知故障时仍可用，并支持大促峰值削峰。

技术是手段，业务连续性和峰值处理才是结果。

### 4.2 使用业务指标

- 预计减少多少 Downtime？
- 对转化率、客户流失或 SLA 有何影响？
- 需要多少投资和人员？
- 何时产生收益？
- 不做的风险是什么？

### 4.3 避免不必要术语

不是禁止术语，而是确保术语对决策有帮助。第一次出现时可以用一句话说明其业务含义。

## 五、面向技术团队表达

技术团队需要可实施信息：

- Context/Container/Sequence Diagram。
- Service Boundary 与 Ownership。
- API/Event Contract。
- Data Model 与 Source of Truth。
- NFR 和 Capacity Assumption。
- Security Control。
- Failure Mode 与 Recovery。
- Migration、Testing、Deployment 和 Rollback。

架构师应清楚区分：

- Constraint：必须遵守。
- Decision：已经选择。
- Recommendation：建议但可讨论。
- Example：说明思路，不是强制实现。

否则团队容易把示例代码误认为完整规范。

## 六、使用图和叙事

推荐从简单到复杂：

1. Context Diagram 建立共同边界。
2. Container Diagram 说明主要构成。
3. Sequence Diagram 走一遍关键 User Journey。
4. Deployment Diagram 解释 Reliability 与 Security。
5. 深入一个重要 Trade-off。

图中每个箭头都应能说清：谁调用谁、使用什么 Protocol、传递什么数据、失败时怎样处理。

## 七、数据与 Evidence

有说服力的方案使用：

- Production Metric。
- Incident/Postmortem。
- Load Test。
- Cost Report。
- Customer Feedback。
- Prototype/Spike。
- Security Assessment。

区分事实与假设：

```text
Fact: 当前 P99 为 1.8 秒。
Assumption: 用户增长 50% 后数据库将成为瓶颈。
Validation: 两周内完成 3 倍 Peak Load Test。
```

## 八、处理提问和异议

面对异议时：

1. 先复述对方 Concern，确认理解。
2. 把 Concern 映射到 Decision Driver。
3. 用 Evidence 回答。
4. 如果未知，明确未知并安排验证。
5. 记录影响决策的新信息。

不要把技术质疑视为个人挑战。高质量反对意见可以发现盲点。

## 九、架构会议设计

会前：

- 发送 Pre-read。
- 明确 Decision 与 Decider。
- 邀请受影响团队。
- 标出 Open Question。

会中：

- 重申目标和 Timebox。
- 聚焦争议点，不逐字朗读文档。
- 使用 Parking Lot 保存偏题内容。
- 明确结论、Owner 和 Deadline。

会后：

- 发布 Decision Summary。
- 更新 ADR/RFC。
- 跟踪 Action Item。
- 向未参会的相关方同步。

## 十、书面沟通

好的架构文档应：

- 第一页就能理解问题和建议。
- 标注 Status、Owner、Review Date。
- 链接到 Evidence 和 Diagram。
- 明确 Assumption 与 Non-goal。
- 可以被异步评论。
- 使用稳定术语。
- 有 Change History 或 Version Control。

书面沟通降低会议依赖，也让跨时区团队有平等参与机会。

## 十一、面试场景

问题：如何向非技术高管解释重构投资？

回答框架：

1. 用业务影响描述当前问题，如 Release Lead Time、Incident、客户流失。
2. 说明不采取行动的风险和趋势。
3. 给出分阶段方案，而不是要求全面重写。
4. 明确投资、里程碑和可量化收益。
5. 提供风险控制与停止条件。
6. 定期用 Business/Engineering Metric 报告进度。

## 十二、常见错误

- 从 Technology 开始，不说明问题。
- 对所有 Audience 使用相同细节。
- 只展示推荐方案，不展示替代方案。
- 隐藏代价和未知信息。
- 图很漂亮，但没有 Decision 和 Owner。
- 会议结束没有结论或下一步。
- 把不同意见归因为“对方不懂技术”。

## 十三、自测题

1. 如何向 CFO 和 Backend Engineer 分别解释同一 Cloud Migration？
2. 架构方案开头最重要的三个内容是什么？
3. 为什么要区分 Fact、Assumption 和 Opinion？
4. 如何处理无法当场回答的技术质疑？
5. 一次有效的架构会议结束时应产生什么？

## 十四、总结

- 架构沟通必须围绕 Audience 的决策需求。
- 先讲 Context、Problem 和 Outcome，再讲 Technology。
- Trade-off、Risk、Assumption 和 Unknown 必须透明。
- 图、数据和叙事共同建立可信方案。
- 沟通的最终结果应是清晰的 Decision、Owner、Roadmap 和验证方式。
