# 02. RFC、ADR、架构评审与技术路线图

> 本章讲如何让重要选择从讨论走到执行与验证。所有项目、编号、时间和指标案例均为虚构教学材料，不代表用户经历、行业基准或已获得的组织批准。

## 一、四种工具分别解决什么问题

RFC（Request for Comments，征求意见提案）让决定前的方案、约束与未知可被异步挑战；ADR（Architecture Decision Record，架构决定记录）保存重要选择的理由与后果；Architecture Review（架构评审）结构化检查质量与风险；Technology Roadmap（技术路线图）安排能力、依赖、投资与演进顺序。

RFC 是信息与讨论载体，Review 是活动，ADR 是决定及理由的记录，Roadmap 是有条件的演进安排。它们不是四个必须依次填完的表格。小型团队可以一份短提案完成讨论并形成 ADR；复杂项目可能一个 RFC 产生多个决定，也可能被拒绝且不进入路线图。

通常先讨论和验证，再记录决定与实施安排，最后反馈实际结果。但 Roadmap 也会提前提出能力方向，引发新的 RFC；实施事故也可能反过来推翻假设。治理（Governance）的价值是让组织清楚谁有权决定、依据是什么、结果如何核验，而不是增加签字人数。

本章贯穿虚构场景：多个团队需要发布订单事件。问题不是“要不要买消息产品”，而是怎样让业务变更可靠传播、避免跨租户泄露，并在现有人员和预算内运营。工具选择只是其中一个决定，事件契约、责任和迁移同样重要。

## 二、RFC：让尚未决定的设计可以被审查

### 2.1 什么值得写 RFC

跨团队 Contract（契约）、新平台、高成本或难逆转选择、敏感数据变化和大规模 Migration（迁移）值得提前讨论。一个服务内部可逆的小重构通常在普通代码评审解决，不需要等待中央委员会。

按影响判断，而非按代码行数：增加一个事件字段可能泄露个人信息或破坏消费者；大段内部实现重构也可能不改变外部行为。评估受影响团队、故障半径、数据恢复难度、长期承诺和团队经验，决定是否升级。

RFC 不等于已经批准，也不是作者必须捍卫到底的作品。发现更简单替代、关键前提不成立或业务取消时，应允许缩范围、撤回或拒绝，同时保存原因以免反复重开相同讨论。

### 2.2 各部分怎样形成完整论证

| 部分 | 必须解释的内容 | 订单事件案例 |
| --- | --- | --- |
| 标题、状态、作者、Reviewer | 谁负责，当前能否执行 | 草案可评论，不能据此采购 |
| Context / Problem | 当前行为与业务影响的证据 | 同步集成导致下游故障影响订单 |
| Goals / Non-goals | 成功标准与范围外内容 | 可靠传播订单状态，暂不重构支付 |
| Requirements / Constraints | 功能、质量与不可违背限制 | 租户隔离、恢复目标、可用人员 |
| Options | 包含最简单方案及维持现状 | 同步隔离、数据库任务、消息平台 |
| Proposed Design | 边界、数据流、权威源及失败处理 | 事务内记录事件，后台投递 |
| Data / API / Security / Operations | 契约版本、授权、保留、监控和值班 | 谁可消费，积压如何恢复 |
| Trade-offs | 收益、代价与剩余风险 | 解耦增加重复投递和运营复杂度 |
| Migration / Rollback | 兼容、分期、验证、停止与退役 | 小流量切换，重复与遗漏核对 |
| Open Questions / Deadline | 未知、验证负责人、何时决定 | 幂等能力未明，先做限时验证 |

NFR（Non-Functional Requirement，非功能需求）如延迟、可用性和可恢复性，应写成场景与门槛。Capacity Assumption（容量假设）要包含峰值速率、消息大小、保留、增长与消费者数量，不能只有平均流量。硬约束先排除不可行项，再比较偏好，不能用总分抵消安全底线。

Source of Truth（权威源）明确某项事实的负责系统。订单事件可能是状态变更通知，不能因为消费者收到了就变成可以任意改订单的权威写入者。需要说明丢失、乱序、重复、版本升级、超时和部分成功，不把组件框图当完整设计。

### 2.3 可填写模板与开放问题

~~~text
RFC 编号/标题/状态/版本：
作者、受影响团队、评审人、决定者：
问题、证据期间与口径：
目标、非目标及排序后的约束：
选项（含简单替代/不做）与未选理由：
建议设计、数据权威及契约：
安全、隐私、容量、失败与运营：
成本范围、能力缺口及依赖：
迁移、验证、上线、回退与退役：
开放问题：[问题/为何影响决定/验证/负责人/期限]
请求决定：[范围/所需证据/决定者/截止时间]
~~~

开放问题不能仅写“待定”。例如“供应商是否支持稳定幂等键，决定是否可安全自动重试；接口负责人本周验证，未确认前不批准正式切换”。期限用于触发处理和升级，不是时间一到所有未知自动消失。

## 三、RFC Review：角色、评论与决定权

### 3.1 角色并不等于人人拥有否决权

Author 准备方案、组织证据并回应反馈；Reviewer 从领域角度挑战设计；Decider 对约定范围作最终决定；Consulted 提供安全、SRE（站点可靠性工程）、数据等专业意见；Informed 需要知道结果但不必批准。决定预算、接受风险与批准上线可能分别属于不同角色，不能由一个技术签字替代全部授权。

确定范围内只有一个明确最终责任归属，涉及多种权限时列出各自必须批准的部分。作者可以推荐风险取舍，但不能替法务判断适用义务，也不能替运维接受新增值班。缺席和沉默不等于同意，除非组织现有规则明确允许且适用于此类决定。

### 3.2 把评论分成可行动类型

| 标签 | 含义 | 有效评论示例 |
| --- | --- | --- |
| Blocking | 未解决不能接受该范围 | 未验证跨租户隔离，违反已确认访问要求 |
| Important | 强烈建议处理，需说明处置 | 积压仪表盘缺少最老消息年龄，建议上线前补齐 |
| Suggestion | 非阻塞改进 | 字段命名可更清楚，与已用术语统一 |
| Question | 澄清信息，不默认阻塞 | 该超时包含排队时间吗？ |

Blocking 必须关联 Requirement、Risk、Standard 或 Evidence（要求、风险、标准或证据）及解除条件。“我不喜欢”不足以成为阻塞，但作者也不能仅因不喜欢反馈就降级真实风险。Question 揭示关键缺口后可升级，标签帮助分流，不取代判断。

处理评论写明接受、拒绝或待验证及理由，链接修改版本。两个 Reviewer 要求相互冲突时，把冲突放到同一公开问题，比较驱动与证据，请有权者裁决；不要私下分别答应互不相容的实现。

### 3.3 评审状态与停止条件

组织可以约定 Draft、In Review、Accepted、Rejected、Withdrawn 等状态；这些是本章示例流程，不是全行业统一标准。In Review 仍允许修改，重要改动需让受影响评审人重新检查，不能在批准后替换核心设计而沿用旧批准。

带条件接受应说明批准的是验证、试点还是生产范围，以及哪些条件必须在下一门槛前满足。无法解除关键阻塞时选择延期、缩范围或拒绝；不能把“先上线再说”包装成已经接受的风险。紧急例外也要有授权、限时、补偿控制和事后复核，不能永久绕开治理。

## 四、ADR：保存理由，不把历史改成今天的答案

### 4.1 ADR 与 RFC 怎样关联

RFC 可以包含多个候选、实验和讨论；ADR 聚焦一个重要选择、上下文、替代与后果。比如 RFC-0012 评估事件传播方案，ADR-0028 记录在特定条件下采用托管事件流平台；具体产品如 Amazon MSK 只是可能选项，不能因模板出现产品名就视为推荐。

ADR 链接对应 RFC、PoC（Proof of Concept，概念验证）与证据版本，正文仍应独立解释为何选择。只写“使用平台 X”不足以支持后来维护者判断是否还适合；只保存会议链接也无法保证几年后能还原依据。

### 4.2 可填写 ADR 与虚构实例

~~~text
ADR 编号、标题、状态、日期、Owner：
决定范围及批准者：
Context：业务需求、约束、现有条件：
Decision：选择及适用范围：
Alternatives：可行替代及未选理由：
Consequences：收益、代价、剩余风险：
验证证据及尚未成立的假设：
实施链接、复审触发、替代关系：
~~~

虚构实例：第一阶段保留订单数据库为状态权威，在同一事务写待发事件，后台向选定平台投递。选择理由是避免订单已提交但发送前进程崩溃导致永久遗漏；代价是发布器、去重、积压监控与值班。该决定不承诺端到端只处理一次，因为投递成功而标记前崩溃可能重复。

替代一是同步发送，简单但延长关键路径且存在双写窗口；替代二是只用数据库任务，团队成本更低，在消费规模小且无独立重放需求时可能更合适。若后续流量、重放需求或平台成本改变，应复审，而不是把旧理由当永恒真理。示例不代表已验证任何厂商保证。

### 4.3 Superseded 与当前有效决定

Accepted（已接受）说明组织选择了什么，不等于已经实现、已上线或验证有效。实施进度与验证结果应关联追踪，不能用文档状态代替运行证据。

新证据要求改变核心决定时，新建 ADR，解释改变原因并链接旧记录；旧记录标为 Superseded（被替代），保留当时上下文。Rejected（被拒绝）也保留理由。已接受的核心理由与后果不应被静默改写；排版修正、补充实施链接和状态索引可按团队规则留痕维护。AWS 指南提供更严格的不可变记录实践，这是实践选择而非所有组织的统一规范。

若两份 ADR 对同一范围冲突，检查适用时间、范围与替代关系，更新有效决定索引；不能让工程师自行猜哪份“看起来新”。运行偏离已接受决定时，要么修实现，要么经授权改变决定，不能仅靠补一篇文档把偏差合法化。

## 五、Architecture Review：检查质量与执行风险

### 5.1 先用场景检验，后讨论风格

架构评审不是代码命名会议，也不是看图是否漂亮。让方案接受正常、峰值、故障、恢复和迁移情景挑战，形成问题、证据、风险与处置，而非只说“看起来合理”。

| 维度 | 关键问题及所需证据 |
| --- | --- |
| 功能与 NFR | 用户旅程、成功定义与延迟窗口是否可测，验证是否覆盖关键业务 |
| 容量与扩展 | 峰值、热点、消息大小与故障余量是否合理，哪个资源先饱和 |
| 数据与一致性 | 谁能写，事务在哪结束，重复/乱序/部分成功怎样处理 |
| 安全、隐私、合规 | 身份、租户边界、用途、保留和适用责任是否明确 |
| Failure / SLO / DR | 失败模式、服务目标、灾难恢复及恢复验证是否完整 |
| Operability / Migration | 告警、手册、值班、兼容、切换、回退与退役是否能执行 |
| 成本与能力 | 平台、网络、人员和承诺费用是否完整，谁承担学习与运营 |
| 简单替代 | 能否以更小范围、更低复杂度满足同样关键约束 |

SLO 是约定窗口内的服务目标，DR 是灾难恢复安排。需要明确恢复时间目标 RTO 与允许数据恢复点损失 RPO；“已有备份”不能证明两者可达。Recovery（恢复）验收应核对业务数据与外部副作用，不只是实例启动。

### 5.2 按风险调整深度

低风险：边界不变、可逆、影响有限，由团队自主和普通同行评审，重要理由做短记录；中风险：领域或跨团队同行检查契约与运营；高风险：跨职能评审、关键假设原型验证与正式 Sign-off（授权签署）。

风险分级同时看影响、发生条件、可发现性、可恢复性和不确定性，不用一个机械分数代替讨论。新工具不必总是高风险，熟悉工具处理高敏数据也不一定低风险。随新证据升级或降级，并记录原因；开始时评级不应成为以后不复查的借口。

PoC 应围绕最危险假设，而不只是顺利跑通 Hello World。事件平台可验证断连重连、重复、权限和积压恢复；PoC 成功也不证明备份、所有数据量或全天候运营已经成立。评审结论应明确证据未覆盖处。

## 六、避免 Bottleneck：把治理变成可自助能力

Bottleneck（瓶颈）通常来自所有选择集中审批、权限不清、等待无期限或标准不可操作。先把决策权下放到合适边界，再提供 Reference Architecture（参考架构）和 Golden Path（推荐实施路径）：预先验证的身份、部署、观测和依赖模板，让团队少重复解决已知问题。

Golden Path 应写适用条件、Owner 和版本；偏离有可申请路径，不能因“不在模板里”自动拒绝合理创新。Self-service Checklist（自助检查表）帮助团队定位证据，但打勾不能代替恢复演练和风险判断。可编码的规则如依赖边界、凭证泄露扫描和部署策略进入持续集成，业务语义及法规适用仍需人判断。

Review SLA 在这里指内部响应时限约定，区别于客户合同 SLA。定义收件完整性、首次响应、完成评审目标、等待作者补证据的处理，以及超期升级人。超时不自动批准；通过排队透明、限在制品与按风险优先缓解，而不是关闭风险。

Exception（例外）记录偏离规则、业务原因、影响范围、授权者、补偿控制、Owner、到期与退出计划。到期触发整改或重新授权，不能自动无限续期。临时共享高权限凭证也不会因有例外单就安全，应优先选更受限方案。

衡量治理同时看评审等待、返工、重大缺陷漏检、例外逾期和上线结果。只考核审批速度会鼓励草率通过，只考核阻止多少方案会鼓励制造阻塞。Enablement（赋能）的目标是安全地提高团队自主交付能力。

## 七、技术路线图：从业务结果走到能力与里程碑

路线图不是工具 Wishlist（愿望清单）。它连接 Business Objective（业务目标）、Required Capability（必要能力）、Architecture Initiative（架构举措）和 Milestone/Metric（里程碑与指标）。一个举措必须说明能解锁什么结果、投资与机会成本，不能长期只说“打地基”。

虚构案例：计划进入欧洲企业市场。先确认客户需求、数据处理路径、合同与法务意见；EU Data Residency（欧盟数据驻留）指相关数据被安排在指定区域，不自动等于满足所有隐私与跨境义务。99.95% SLA 若作为候选商业目标，应经业务、运营和合同负责人验证后承诺，不能由架构师直接写进客户保证。

| 能力或举措 | 为什么需要 | 里程碑证据 |
| --- | --- | --- |
| EU Landing Zone | 建立区域账户、网络、身份与策略基座 | 自动建环境及权限负向验证 |
| 租户感知数据放置 | 按确认规则决定数据与副本位置 | 主库、备份、日志和支持访问路径核验 |
| 跨区域发布流水线 | 在区域隔离中受控交付 | 版本兼容、小流量发布与回退演练 |
| 审计与保留控制 | 解释谁访问何数据并执行生命周期 | 约定控制的证据与保留执行测试 |

Landing Zone 是受治理的云环境基座，不是一个产品购买动作。候选分期可以是 Q1 基础、Q2 试点、Q3 一般可用，但只是本案例规划表达，需依赖和容量评估后才成为承诺。试点必须定义租户范围、人工兜底和退出条件，一般可用不能只等于开放注册。

候选验收如“环境开通小于一天”需定义从完整申请到可用的起止和排除项；“RTO 小于一小时”需通过指定故障与完整恢复验证；“合规控制证据 100% 自动化”容易掩盖人工判断，应限定为明确控制清单、可自动采集部分及完整性抽查，不承诺自动证明全部合规。

## 八、Now、Next、Later：表达不同置信度

Now 是已获资源与依赖承诺、范围清晰的近期工作，仍需管理风险；Next 是较高置信度但尚有验证或资源前提；Later 表达方向与 Trigger（触发条件），不为两年后的具体产品版本制造虚假确定性。

每项包括预期结果、Owner、资源范围、依赖、门槛与复审时间。远期写“具备跨地区恢复能力”，比写某日必须采用某工具更能保持有效；近期则应具体到谁做什么、如何通过验收。三层不是把所有工作都承诺、只改日期的装饰。

触发可来自客户合同确认、流量达到已定义阈值、事故暴露恢复缺口或供应商支持结束。触发后重新评估价值、成本和容量，不自动无条件开工。业务取消时可以停止技术举措并记录已产生资产和遗留责任，不能因沉没成本继续建设。

## 九、管理依赖、关键路径与风险降低

Team Dependency 包括契约和人力；Vendor/Contract Dependency 包括采购、配额与许可；Data Migration 涉及数据清理、验证和切换；Compliance Deadline 是经负责方确认的义务时间；Hiring/Skill Gap 是人员技能缺口。依赖必须有对方负责人和承诺，不只是箭头。

Critical Path（关键路径）决定给定依赖与资源条件下最早完成时间；增加其他任务人数不一定缩短它。虚构算例：基座两周后，身份集成三周与数据放置四周并行，二者完成后试点两周，最短为 2 + max(3,4) + 2 = 8 周。若身份与数据由同一人做且不能并行，至少变为 11 周，说明图上并行不等于资源可并行。均未计缓冲、采购等待和返工。

Risk Reduction Milestone（风险降低里程碑）应尽早验证会推翻计划的未知，例如先验证副本位置约束和恢复可行性，再大量迁移。Enabler（使能工作）如身份基座可以先做，但要链接它解锁的试点，并防止依赖方长期未启动导致基座无效闲置。

每次更新路线图记录依赖变化、范围选择、成本与影响；预计延期要及早给可选方案：缩试点、换可逆实现或调整日期，而不是到截止日才宣布。缓冲不能代替关键未知验证，频繁调整也不能悄悄抹掉原预测与学习。

## 十、治理闭环：上线只是验证开始

Standard/Roadmap 给方向，RFC 解释方案，Review 挑战风险，ADR 留下选择，Implementation 实现后，通过 Fitness Function、SLO、成本及反馈检查效果。Fitness Function（架构适应度检查）是持续检验某项架构特性的机制，如禁止领域层依赖基础设施的自动依赖规则，或定期恢复演练；并非仅指一套单元测试。

规则应能失败并指向可行动原因。依赖边界测试通过不证明服务可恢复，负载测试通过不证明租户授权正确，因此按风险选择互补证据。可编码检查尽量自动化，难自动的保留定期审查和负责人，避免把没有测到写成“全部通过”。

上线后对比 SLO、真实成本与预测、事故暴露和 ADR 假设；指定复查窗口或触发条件。例如消息重放成本远超预计，应检查需求、保留和规模，再决定优化、缩范围或新建替代 ADR。复审不意味着每次小波动推翻平台，要区分测量误差、暂时变化和结构性前提改变。

若实际实现违反决定，建立偏差项、风险负责人和处理期限，确认修代码、申请例外或改变决定。Roadmap 随学习更新，并同步依赖团队。只在设计评审盖章，之后无人核验数据、权限与恢复，是未完成治理。

## 十一、贯穿案例与可执行会议产出

虚构 RFC-0012 不直接请求“批准整个平台迁移”，而请求批准有限概念验证：比较数据库任务和托管平台在权限、重复、重放、恢复与人员成本上的适用性。评审指定跨租户风险为阻塞，吞吐预测为待验证，命名意见为建议。

假设验证支持第一阶段选择后，ADR-0028 记录适用范围、替代与重复风险；具体产品须另核对实际条款与能力，本例不提供选型结论。Now 安排两组消费者试点，Next 等待恢复验收与值班准备，Later 的广泛迁移以试点价值和成本达标为触发。

会议摘要应明确：“批准沙箱验证；接口负责人负责契约，安全负责人核对隔离，运行负责人确认恢复与值班；在门槛通过前不批准生产切换”。这是一种有效决定，而非失败会议。若需要正式投产，再核对预算、访问、运营与变更权限，防止把技术通过误当所有批准齐全。

可以使用下面的结束检查表：

~~~text
决定结果与范围：[批准/拒绝/带条件/延期]
依据及关键证据版本：
决定者及各专项授权：
已解除阻塞/未解除阻塞：
接受的剩余风险及责任人：
行动：[交付物/Owner/期限/验收]
执行与路线图链接：
复审触发与通知对象：
~~~

## 十二、常见错误与修正

RFC 没有决定者和期限，会变成无限讨论；补明确权限与未知验证。ADR 只写产品名，无法解释为什么；保留条件、替代与后果。所有改动上中央委员会，会让低风险团队也排队；用风险边界和自助能力下放。

Review 盯命名却漏失败与迁移，应以场景检查。Roadmap 只列工具，难以判断投资价值；映射能力与业务验收。远期精确到产品和日期且从不更新，会制造假承诺；按置信度和触发管理。

决定完成却没有测量，会让错误前提永久固化；用上线检查和复审闭环。另一方面，不能每次运行指标波动就重开全部决定，也不能为了追求统一模板让作者大量复制重复文字；治理文档要能维护并真正被实施者使用。

## 十三、面试完整回答与深入追问

### 13.1 怎样设计轻量架构治理？

“我按影响、可逆性与未知程度分级。局部低风险由团队决定，跨团队、高成本或涉及敏感数据的选择先写 RFC，异步收集具体反馈，再按质量属性、失败、安全与迁移做评审。角色明确到决定者与风险接受者，阻塞关联证据和解除条件。决定用 ADR 保存理由与后果，能力进入有资源与依赖的路线图，上线后按 SLO、成本和适应度检查验证。平台提供推荐路径和自动检查，减少重复中央审批。”

**追问：作者和 Reviewer 一直争论呢？** 区分事实、偏好和权限。事实安排有限验证，偏好按已排序驱动比较，有权者在范围内裁定并记录异议；关键风险未解除可缩范围或延期，不能把时间压力当证据。

### 13.2 如何避免 ADR 过时或变成官僚文档？

“只记录架构上重要的选择，每条有上下文、理由和复审触发，链接到代码、验证与现行索引。Accepted 不等于已实现，运行结果另外跟踪。新条件改变核心选择时建新记录并替代旧记录，保留历史解释。小可逆实现不要求写长 ADR。”

**追问：能直接把旧 ADR 改成新方案吗？** 不应静默重写核心理由，否则失去当时为什么选择的历史。按团队规则允许留痕修正文书或链接，核心改变通过新决定表达。

### 13.3 如何向业务解释技术路线图？

“我从客户目标反推能力，再列举措、投资、依赖和可验收里程碑。近期承诺对应资源和明确范围，下一阶段保留验证条件，远期只表达方向与触发。每个基座工作都链接可交付价值，并定期比较效果、成本与假设，必要时停止或重排。”

**追问：业务要求所有远期日期固定呢？** 给条件与置信范围，说明关键依赖和精确承诺需要的证据；可以固定决策点和验证窗口，不把未知实施日期伪装为确定事实。若必须合同承诺，交有权限者结合资源与风险作决定。

## 十四、扫雷自测与完整答案

1. **RFC 与 ADR 核心区别？** RFC 支持选择前讨论，ADR 保存重要决定的理由与后果。RFC 可拒绝，一个 RFC 可产生多个 ADR；ADR 草案也可评审，文件名不等于批准状态。
2. **什么决定需要正式 Review？** 跨团队契约、高成本、难逆转、敏感数据、大迁移或恢复风险较高的选择。按真实影响与不确定性，不按代码行数或是否使用新工具。
3. **如何避免降低交付速度？** 下放低风险决定，提供参考架构、自助检查和自动规则，明确响应时间与升级，异步先处理证据。超时不默认批准，速度与缺陷漏检一起衡量。
4. **Roadmap 为什么不是工具清单？** 工具不能说明投资带来什么能力及客户价值。需要从业务目标连接能力、举措、依赖和验收；业务变化时工具选择也可能改变。
5. **怎样形成 Feedback Loop？** 把决定链接实现、SLO、成本、事故与适应度证据，按窗口或触发复查，处理偏差并更新 ADR/路线图。上线签字不等于长期有效。
6. **Blocking 能否只写“我不喜欢”？** 不能，应给要求、风险或证据与解除条件。主观偏好可以建议，真实安全缺口也不能被作者单方面降级。
7. **Accepted 是否等于上线完成？** 不等于，它表示选择获接受。实现、迁移、运行验证和正式变更授权分别跟踪，否则文档与系统会分离。
8. **两任务画成并行就能缩短日期吗？** 不一定，资源和依赖要允许。案例在资源可并行时八周，同一人不能并行时十一周；不能只看箭头而忽略人员。
9. **所有合规证据自动化是否等于合规？** 不等于，自动采集只证明约定范围的执行信息，适用义务、控制设计和判断仍需负责方确认。明确分母与抽查，避免“100%”掩盖缺口。
10. **紧急例外怎么防永久化？** 限定范围、授权、补偿控制、到期、退出计划和复核负责人。到期触发整改或重新评估，不自动续期；紧急也不能制造无法接受的新风险。
