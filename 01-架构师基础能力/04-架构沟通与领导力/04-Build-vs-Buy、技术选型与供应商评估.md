# 04. Build vs Buy、技术选型与供应商评估

> 选型不是证明喜欢的产品最好，而是在业务约束下购买、构建并持续验证一种能力。本文数字、产品场景和门槛均为虚构教学假设，不代表真实报价、用户项目或厂商 benchmark。合同与法规适用由采购、法务、安全等相应负责人确认。

## 一、Build vs Buy 不是二元选择

| 模式 | 买到或承担什么 | 适用边界 |
| --- | --- | --- |
| Build 自研 | 控制业务流程、代码与演进，也承担开发运营 | 能力差异化且组织有长期资源；不等于无依赖 |
| Buy SaaS | 购买完整在线能力，供应商运行主要平台 | 功能匹配时减少初期建设；仍需集成、权限与退出 |
| Managed Service | 托管数据库、队列等基础能力 | 减少部分基础运维，应用正确性与配置仍由自己负责 |
| Open Source Self-hosted | 使用开源软件并自行运行 | 可控制环境，升级、安全、备份和值班不能省 |
| Open Core / 商业发行版 | 开源核心加商业能力或支持 | 核对所需功能、许可与商业版本边界 |
| Hybrid 混合 | 核心业务自研，通用组件购买 | 兼顾差异化与复用，但集成与责任更需清楚 |

真正问题是哪些能力形成独特客户体验、数据资产或业务优势，哪些只是达成目标所需的通用能力。Payroll（薪酬处理）、邮件发送和常规监控通常值得优先评估成熟方案，但“通用”不代表任意产品都满足地区、流程和安全要求。

Build 也使用语言、库和云平台；Buy 也可能需要大量定制。按能力边界拆分，避免把“整套系统自研或整套购买”当唯一选择。混合方案若把关键逻辑散落在多个供应商工作流中，反而可能更难维护和退出。

## 二、Decision Drivers：先确定需要优化什么

### 2.1 差异化与控制

Strategic Differentiation（战略差异化）说明能力为什么值得长期拥有。例如独特的风险决策规则可能自研，身份登录采用成熟服务。拥有源代码不自动意味着拥有竞争优势；若代码多年无人维护，控制权只是名义上的。

Control 与 Customization（控制和定制）包括流程、数据、部署位置、发布节奏与故障处置。自研提升修改自由，但团队承担 Roadmap（路线图）、Reliability（可靠性）、Security（安全）与 Support（支持）。供应商能定制也要核对升级后兼容、交付时间和费用，不把销售口头答复当承诺。

### 2.2 上市时间与组织能力

Time to Market（上市时间）应算从决定到安全可用，而非 Demo 到运行。Buy 可能加速初期，但采购、安全评估、身份集成、数据清洗、迁移与培训都可能在关键路径上。自研若已有稳定组件可能更快，不能预设购买必然节约时间。

Capability 与 Skill（能力和技能）要看开发、恢复、漏洞响应、升级与 24×7 值班的持续能力。Prototype（原型）证明少量条件下能跑，不证明关键人员离开后仍能运营。估算人员时包括替补、培训与文档，不能把某位工程师无限加班当架构前提。

### 2.3 规模与经济性

小规模 SaaS 可能摊薄固定建设成本，大规模用量价格可能增加；自研固定成本高也可能有较低边际成本，但两者都受容量台阶、折扣和维护影响。不要用当前低用量报价对比自研最大容量，也不要用未来最乐观规模证明今天自研必胜。

先定义硬约束，例如租户隔离、恢复目标与合法数据用途，再排序成本、速度和灵活性。硬约束不满足的方案不能靠低价总分补偿。需求变化时允许重新评价，不能把最初选择变成个人身份。

## 三、TCO：比较同范围、同周期的真实投入

### 3.1 完整成本范围

TCO（Total Cost of Ownership，总拥有成本）包括建设、运行、维护与退出。三年可作为案例比较窗口，实际应按产品生命周期、合同承诺和技术淘汰周期选择，不机械规定所有项目三年。

Build 包含开发、基础设施、Operations/On-call（运营值班）、安全合规、升级维护和 Opportunity Cost（机会成本）。Buy 包含订阅用量、集成迁移、供应商管理、培训及退出切换，还包括组织自己保留的运维与安全责任。开源没有许可费不代表免费，托管也不代表所有人工归零。

把现金支出、分摊人工和机会成本分栏。若人力费用已按全成本计入，不要再把同一人员时间全额算一次“损失工资”；机会成本可以另列失去的业务机会并说明估算，避免重复加总。数据出网、支持级别、双运行、税汇率、承诺闲置与退出窗口都可能改变比较。

### 3.2 可核验的三年教学算例

以下单位为千欧，均是假设且不含税、折现和风险损失；两方案必须满足相同业务范围和质量底线。

| 项目 | Build | Buy |
| --- | ---: | ---: |
| 初始建设或集成迁移 | 240 | 60 |
| 每年运营或内部支持 | 90 | 30 |
| 每年外部用量费用 | 0（已含运营范围） | 60 |
| 三年末退出准备 | 20 | 40 |
| 三年总额 | 530 | 370 |

Build = 240 + 3×90 + 20 = 530；Buy = 60 + 3×(30+60) + 40 = 370。这里 Buy 的用量费不增长，不能据此推断长期一定更便宜。若用量费第一年 60、第二年 120、第三年 180，则 Buy 为 60 + 3×30 + 60+120+180 + 40 = 550，排序反转。

在简化模型中，Buy 每年外部费为 x，三年总额为 190 + 3x；与 530 相等时 x 约为 113.33 千欧/年。这只是其他条件固定时的交点，不是现实统一切换阈值；自研增长也会增加容量与人力，迁移还会产生一次性风险和时间。

### 3.3 敏感性、风险与现金时间

至少做低、基准、高用量及价格变化情景，记录参数来源、日期、折扣期限和含不含支持。按成功订单、活跃用户或有效业务处理计算 Unit Cost（单位成本），防止失败重试增加分母使效率看起来更好。零业务量时单位成本无定义，展示闲置成本。

长期现金流可用折现比较今天与未来支出，但折现率和财务口径需负责人确认。预付最低承诺降低单价却占用现金，不能只看摊销单价。风险可用情景与区间表达，确有依据时估期望损失；缺乏概率不能编精确数字，也不能用低概率平均值掩盖不可接受的灾难后果。

## 四、选型评分：硬门槛、证据和敏感性

| 维度 | 应检查什么 | 有效证据 |
| --- | --- | --- |
| Functional Fit | 核心用例、限制和必要定制 | 代表流程验收 |
| NFR | 延迟、规模、可用性与灾难恢复 | 同负载模型测试和恢复记录 |
| Security | 身份、权限、加密、审计、漏洞响应 | 配置、负向测试与范围明确报告 |
| Compliance | 数据位置、相关证明和处理协议 | 适用范围与合同审阅 |
| Integration | API、SDK、事件、单点登录及导出 | 实际集成和版本兼容测试 |
| Operability | 监控、支持、升级、事故处理 | 手册、故障演练及支持验证 |
| Economics | TCO、增长、价格与出网 | 可复算报价和情景 |
| Vendor Risk | 财务、产品方向、收购风险 | 经核实材料与持续监测 |
| Lock-in | 数据和流程迁移、兼容边界 | 导出、导入与替代演练 |
| Team Fit | 技能、招聘、学习与值班 | 团队试用和明确资源计划 |

先定义权重、评分含义和证据门槛，再评候选。可用 1 到 5 分但需说明“3 分”的实际含义；未验证标未知，不能为了凑表填中间分。先进行硬门槛筛选，再加权，改变最不确定权重观察排序是否稳定。

品牌、个人关系和销售演示可提供线索，不能替代证据。一个高分产品若只有单人会维护，也可能不适合组织。评估应有业务、工程、安全、运营、采购和财务参与，技术选择与合同批准分别由有权限者承担。

## 五、供应商 Due Diligence：从问题清单到核验

### 5.1 技术与运营

Architecture 与 Scaling Model 要问瓶颈、分区、热点、容量扩展时间和配额提升路径。Quota 是容量/用量额度，Rate Limit 是时间窗口调用限制；客户端需处理拒绝、退避和总超时，不能无界重试。请求已处理但响应丢失时，是否支持幂等键或结果查询决定重复副作用风险。

SLA 是服务协议，核对统计窗口、排除、赔付和是否覆盖自己使用的区域与功能；服务积分通常不能补偿业务全部损失。历史可靠性看影响、恢复与事故透明度，不能从一个状态页绿色推断无故障。

Backup、RTO 与 RPO 要看谁发起、能否逐租户恢复、密钥依赖、恢复验证及不可变/隔离机制。RTO 是恢复耗时目标，RPO 是允许的数据恢复点损失；有备份不证明达标。Versioning 与 Deprecation（版本及弃用）需提前通知、兼容期、测试环境和回退，避免被供应商升级强制改变关键行为。

Observability 与 Export 包括指标、日志、审计、状态与数据能否导出，是否额外收费、限速和有保留期。Support Tier（支持级别）的响应不等于修复承诺，需确认升级联系人、时区、严重度和实际响应方式。

### 5.2 安全、隐私与数据责任

IAM（身份访问管理）要覆盖 SSO（单点登录）、账号停用、权限和机器身份。SCIM 是用于跨系统配置用户等身份资源的协议体系；有 SSO 不代表员工离职后所有会话和本地账号都被撤销。RBAC 按角色授予能力，ABAC 按主体、资源与环境属性判断，最终仍需验证租户和资源授权。

Encryption 与 Key Option 核对链路、静态存储、备份、密钥所有权、轮换与恢复。客户管理密钥不自动保证供应商永远看不到明文，应用处理和支持路径需另问。审计记录包括管理员、支持访问和数据导出，明确完整性、权限和保留。

Tenant Isolation（租户隔离）用负向测试与架构边界验证。Secure SDLC（安全开发生命周期）、Pen Test（渗透测试）报告需核对测试范围、时间与未修项；认证或报告不等于本系统所有配置安全。Incident Notification（事故通知）约定触发、渠道、信息与配合，具体义务交专业负责人确认。

Subprocessor（分处理方）、数据位置与远程支持路径应有清单和变更流程。DPA（数据处理协议）明确处理目的、责任与相关条款；数据驻留不自动证明全部跨境处理适用。Data Deletion 要覆盖主存储、备份、日志、派生索引和处理方，记录例外与期限，不能只测试删除 UI。

### 5.3 商业与法律

Pricing Metric 要确定按用户、MAU（月活跃用户）、请求、存储、吞吐或功能计价的精确定义；Overage 是超量收费，测试、机器人、重试与灾备是否计量也要核对。Minimum Commitment（最低承诺）可能用不完仍付费，Renewal Cap（续约涨价上限）需明确基数与适用条件。

Liability（责任）、Indemnity（赔偿责任安排）、数据所有权、终止协助、收购或破产处理由法务采购审阅。不要凭技术人员解释承诺法律效果。即使条款允许退出，也要验证导出能力和迁移窗口；“数据归你”不等于随时可完整低成本取走。

供应商财务与产品方向可能改变，应区分已证实事实、声明和推测，设置持续审查。开源及商业发行版也核对许可证、再分发和升级版本条件，不把开源当没有许可义务。

## 六、PoC：优先证伪最大的风险

### 6.1 向量数据库的可操作试验

PoC（Proof of Concept）需 Timebox（时间限制）、预算、负责人、停止条件和固定测试计划。使用合法且适当脱敏的数据，生产式分布不等于可任意复制客户数据。供应商帮助调参要保留配置、版本、硬件和费用口径，不能只接受最好一次截图。

原示例的候选门槛可以保留为教学需求：一千万向量、Recall@10 ≥ 0.92、p95 <150ms、写入 ≥每秒两万向量、月成本低于已批准 X、恢复小于两小时。它们不是行业标准，也不表示任何产品能同时达到。

Recall@10 可定义为每个查询返回前十项与精确参考前十项的交集数量除以十，再对测试查询平均；参考结果必须采用同一距离、过滤与数据快照。p95 是约 95% 观测不超过的耗时，指定是否含网络、过滤、排队和客户端重试。固定查询并发、热点、维度、索引参数、读写混合与冷/热状态，不能把不同条件下最佳写入和最佳查询拼成同时达标。

“租户过滤正确率 100%”应改述为指定测试矩阵内零越权结果的硬门槛，不代表统计证明所有未来路径绝无漏洞。覆盖跨租户、缺失权限、过滤绕过、批量查询、缓存、备份恢复与管理员路径。任何越权先停止接受，不能用平均准确率抵消。

### 6.2 故障、演进、导出与运营

验证节点或连接故障、超时、限流与重试后是否重复写入、部分批次怎样确认，恢复后数量和查询结果是否一致。安全集成测试身份停用、权限与审计；升级/Schema Change 测旧客户端、新字段、索引重建与维护窗口。

Data Export 不只下载向量，还包含业务 ID、元数据、过滤属性和索引重建所需配置。用替代系统导入并验证查询与访问语义，测耗时、限速、费用和人工。Operational Complexity 记录告警、扩容、备份恢复、故障定位和需要多少专门知识。

按门槛出具通过、失败或证据不足；缺关键验证只能批准受控下一阶段，不能等同生产通过。PoC 结果具版本与条件范围，扩大规模或改变配置后需重验证。限时不是赶期限把未测项自动标绿。

## 七、Lock-in：计算交换，而不是追求零依赖

Vendor Lock-in（供应商锁定）可能来自专有 API、数据格式、工作流、身份、运维技能、合同和生态。高层托管能力能节约交付与运营，接受一定锁定可能合理。完全可移植也有当前成本：抽象开发、功能最小公分母、双平台测试和错失原生能力。

量化时列出退出触发、替代成熟度、受影响应用、数据量与导出速度、重建/双运行/切换时间、费用和业务中断。概率有依据才估“退出概率×影响”，否则用情景范围；极端不可接受损失先作为约束，不只平均进成本。

降锁定可保留开放格式导出、把 SDK（软件开发工具包）依赖放在边界层、保留关键业务规则并测试替代；使用开放协议也不保证所有扩展和语义一致。不要写一个覆盖所有供应商的庞大接口却从未迁移；优先隔离真正难替换处并验证导出恢复。

## 八、Exit Strategy：签约前设计、运行中演练

Exit Plan（退出计划）不是立即离开，而是保证有时间和技术手段改变选择。明确全量数据和历史审计如何导出、格式、加密密钥、身份映射、速度、费用及合同结束后的读取窗口；删除证明覆盖什么范围与备份期限也要明确。

迁移通常先全量复制，再捕获增量，核对数量、校验和、业务查询与权限；切换写入需防止新旧系统同时成为权威。使用稳定 ID、幂等重放、明确截点与回退门槛。双写不是免费保险，部分成功和顺序冲突会增加对账难度，优先选择可追踪单一权威及增量同步。

假设需迁移 12TB，持续有效传输 100MB/s，按十进制单位纯传输下界为 120000 秒，即约33.33小时。还没算生成导出、限速、重试、增量追平和重建索引，因此一天窗口不够，压缩率或并行能力须实测。无法达到窗口就延长过渡、提前预迁移或缩范围，不靠愿望承诺。

退出验收包括应用已不依赖专有 API、历史审计可检索、权限与结果一致、账单与承诺处理、旧密钥撤销及按约删除。先导出验收再删除，避免为满足终止日期提前毁掉唯一副本。每次演练记录瓶颈并更新合同或架构。

## 九、Authentication Platform：买成熟能力也要设计失败

### 9.1 自研与购买的责任

身份平台自研能完全控制流程与数据，但需要 Password Security（密码安全）、MFA（多因素认证）、Account Recovery（账号恢复）、Attack Detection（攻击检测）、合规协作和全天候支持。找回流程往往比正常登录更容易成为攻击入口，不能把实现登录表单当身份平台完成。

购买 Identity Provider（身份提供方）可快速获得成熟能力，但带来 MAU 计费、登录关键依赖、定制与迁移限制。多数不以身份为差异化的业务应优先评估成熟提供方，而非默认自研；实际仍按约束、证据和 TCO 决定。

### 9.2 映射、令牌验证与中断

Local User Mapping（本地用户映射）用内部稳定用户 ID 关联外部签发者与主体标识，不只依赖可变邮箱；更换提供方需受控绑定和验证，不能邮箱相同就自动合并高权限账号。

OIDC（OpenID Connect）在 OAuth 2.0 上提供身份层，ID Token 面向登录客户端，Access Token 面向资源访问，不能互换。令牌验证需使用成熟库按协议与格式检查签名、可信签发者、受众、时效和相应上下文；不能只 Base64 解码或接受任意算法。具体流程按 OIDC Core 1.0 errata set 2 与 OAuth 安全 BCP RFC 9700（2025）核验。

Token Validation Resilience 依赖架构：自包含签名令牌可在持有可信有效密钥和合适策略时本地验证，但撤销时效与密钥轮换有边界；依赖在线查询的令牌校验需要相应在线服务。密钥缓存要有受控刷新、轮换与未知密钥失败策略，不能供应商失联就跳过验证。现有会话是否继续、多久以及高风险动作限制需事前明确。

Provider Outage 时新登录、刷新、账号恢复和管理操作可能不可用，不能假设现有会话一切正常。定义用户提示、重试预算和降级；业务资源授权仍由后端执行，不因供应商发了令牌就允许任意租户访问。

### 9.3 Break-glass、导出与合同

Break-glass（紧急访问）应是受限、强保护、审计和定期演练的管理恢复通道，有审批或双人控制及使用后复查，不能给全部终端用户开启无认证登录。备用通道依赖是否同源也要验证，避免主供应商故障时备用身份同样失效。

导出核对账号、关系、角色、MFA 与密码材料可迁移范围；密码和因素可能不能安全直接移植，必要时受控重新注册或重置，并评估客服和账户接管风险。合同 SLA 要覆盖登录所用组件，确认通知、支持和退出协助，不把赔付当服务连续性设计。

## 十、决定与复审：把选型作为持续责任

ADR（架构决定记录）保存驱动和权重、候选、PoC 证据、TCO 假设、安全法务结论、风险缓解、合同条件、退出和 Revisit Trigger（复审触发）。决定采购不自动等于允许生产启用，实施验收、权限和运营准备应另跟踪。

~~~text
能力/业务目标/非目标：
硬门槛、驱动与权重：
候选模式与方案：
证据：[版本/日期/测试范围/未知]
TCO：[窗口/用量/人员/承诺/退出/敏感性]
安全、采购、法务结论及批准范围：
选择理由、代价与风险责任人：
集成、迁移、上线、运营和退出计划：
触发：[用量/价格/可靠性/产品方向/义务变化]
负责人、复审日期与指标：
~~~

使用量增长、涨价、SLA 失败、路线图偏离或新义务会触发复审，先判断暂时异常还是结构性改变。不要每次小事故就立刻迁移，也不要因沉没成本拒绝新证据。未兑现条件可缩范围、修复、重新谈判或退出，由相应权限人决定。

## 十一、常见错误与改正

只比较 License Price（许可价）会漏运营、集成和退出；使用同范围 TCO。把开源当免费会隐藏升级和安全责任；核对许可、人力与支持。只跑 Demo 会遗漏容量、故障和权限；PoC 以最大风险为中心。

忽略采购法务安全提前期会让计划不真实，应与工程关键路径一起安排。为零锁定拒绝所有托管会损失价值，反过来只信开放协议也会低估语义迁移。购买基于关系或品牌时，要用相同门槛、可核查证据与风险责任纠偏。

没有导出和终止安排，会在最需要迁移时失去窗口；签约前验证并运行中演练。抽象层不等于退出能力，合同数据所有权也不等于实际可完整取出。

## 十二、面试完整回答与追问

### 12.1 如何作 Build vs Buy 决定？

“我先拆能力边界，识别真正差异化和不可违背的安全、数据与恢复要求，再比较自研、SaaS、托管、开源自托管和混合。按同业务范围估生命周期成本与人员，考虑增长、承诺、集成和退出。关键未知用限时 PoC，覆盖故障、权限、迁移与支持。决定记录理由、剩余风险和合同条件，上线后用成本和业务结果复审，不只看许可价。”

**追问：自研看起来三年更便宜呢？** 核对是否计入全天候运营、升级与机会成本，增长是否同口径，团队是否真有资源。便宜且满足底线可以自研，不能仅因“非核心一般买”否定证据。

### 12.2 如何评估供应商可靠性？

“我把合同 SLA 与实际应用恢复分开，核对统计范围、排除和通知，检查依赖、配额、版本、备份与恢复路径。PoC 模拟断连、超时结果未知、限流和恢复，观察数据与业务一致性。支持响应、导出和密钥权限也要实测或明确证据缺口。”

**追问：对方有认证能省掉安全测试吗？** 不能，报告有时间、系统和控制范围，自己的配置、租户权限与集成仍需核验。由安全负责人判断可复用证据，不以证书代替所有责任。

### 12.3 怎样管理锁定？

“我比较使用专有能力获得的当前价值与退出影响，列出数据、工作流、身份和合同依赖。优先保留可用导出与关键规则，在业务边界隔离 SDK，并演练替代导入和切换。只为真正需要的可移植性付成本，不建设没有验证的万能抽象。”

**追问：供应商突然要求终止服务呢？** 先按合同与实际窗口启用退出方案，确认导出、增量与替代容量，优先关键能力并管理业务降级。若从未验证迁移，不能承诺瞬间切换；这正是签约前应减少的风险。

## 十三、扫雷自测与完整答案

1. **哪些能力适合 Build 或 Buy？** 差异化、控制要求和长期能力支持自研；成熟通用能力可优先采购。仍需需求、安全、TCO 和组织证据，不能按标签自动决定，混合常可更精确拆分责任。
2. **TCO 最易遗漏什么？** 集成迁移、值班、安全升级、最低承诺、培训、双运行、出网与退出；机会成本另说明避免重复计人工。仅比较许可会扭曲排序。
3. **PoC 为什么优先最大风险？** 最危险未知可能直接淘汰候选，先验证能减少后续浪费。跑通正常查询不足以证明隔离、恢复或全量导出，门槛要在测试前写清。
4. **怎样量化锁定？** 列退出触发、替代、应用依赖、导出导入时间、双运行、停机与合同费用；概率有依据才估期望值，否则做情景。当前可移植性成本也进入比较。
5. **退出策略什么时候设计？** 签约前明确能力、费用与窗口，并在运行中演练更新；事故后才发现不能导出通常已失去选择空间。
6. **向量库 Recall 高能抵消越权吗？** 不能，检索质量和权限是不同门槛。测试矩阵零越权是必要验收，但不保证所有未来路径无漏洞，还需设计与持续验证。
7. **SLA 积分能代替灾备吗？** 不能，经济补偿不恢复数据和客户流程。仍需实际恢复、依赖行为与运营安排，核对 RTO/RPO。
8. **有源码就没有锁定吗？** 不对，技能、数据、插件、许可、运维和业务工作流都可能形成迁移障碍。源码可得只是控制的一部分。
9. **身份平台中断能跳过验证吗？** 不能。按事先确定策略使用可信密钥和会话，未知或不满足条件应拒绝；紧急管理通道不等于为所有用户关闭认证。
10. **12TB 在 100MB/s 下能一天迁移吗？** 按十进制单位纯传输已约33.33小时，尚不含重建与增量，不能承诺一天。压缩、并行和实际吞吐需验证，窗口应留真实余量。

## 十四、速记、验证范围与来源

速记：**拆能力 → 设硬门槛 → 同范围算 TCO → 证据评分 → 风险 PoC → 合同与退出 → 验收运营 → 触发复审。**
