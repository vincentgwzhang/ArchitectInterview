# 05. 项目复盘、风险管理与架构治理

> 本章将事故学习、风险处理和持续架构约束连成闭环。所有项目、时间线、风险数字与行动项均为虚构教学案例，不代表用户经历或实测收益。方法需按组织规模与授权裁剪。

## 一、复盘目的：重建发生条件，改变下一次结果

Postmortem（事后复盘）先回答发生什么、影响谁、当时可见什么信息、哪些防线没有工作、哪些处置有效，再提出可验证改进。复杂系统通常由变更、权限、依赖、告警和恢复条件共同促成事故；把一切停在“某人操作错误”会漏掉相似错误再次造成损害的路径。

复盘与现场响应不同：事故中优先止损、恢复和保留必要证据，不为争论根因阻碍处置；恢复后再深入分析。事先约定触发条件，如用户显著受损、数据完整性事件、关键监控失效或高价值险情，避免只对被关注的人或团队要求复盘。小问题可短记录，重大问题需更完整，不能让文书负担阻止报告。

“下次不会再发生”通常无法保证。合理目标是降低同类条件出现概率、缩小故障半径、加快发现和恢复，并知道哪些剩余风险仍存在。复盘质量最终看控制是否有效，而非报告长度。

## 二、Blameless 与 Accountability

Blameless（不责备式）是以系统学习为目的，让参与者安全提供完整信息，而非围绕羞辱个人组织证据。Accountability（责任落实）仍要求角色清楚、如实记录、落实行动和履行职责。没有责任人和期限的“大家都有责任”，同样不能改进系统。

分析应按当时信息判断，不用后来知道的答案倒推参与者“早应看出”。例如看似不合理的重启，可能是当时手册唯一推荐动作且缺少数据库等待指标。应检查手册、工具与可见性，而非简单评价能力。

这不表示任何行为都无须处理。若有独立行为或授权问题，应按组织既有程序分别处理，避免把学习会议变成隐蔽惩罚或假称复盘可以替代其他责任机制。事实记录保持诚实，具体人员信息与敏感材料按必要范围共享。

## 三、复盘结构、Timeline 与因果分析

### 3.1 每一部分应产生什么信息

| 部分 | 内容与边界 |
| --- | --- |
| Summary | 事件范围、当前状态、最重要学习，区分已证实与待查 |
| Customer/Business Impact | 失败、延迟、数据与业务影响，统计口径及未知范围 |
| Timeline | 发布、告警、用户报告、调查、缓解与恢复的证据时间 |
| Detection and Response | 怎样发现、谁协调、哪些动作有效或扩大影响 |
| Causes / Contributing Factors | 触发与促成条件、防线缺口，保留多条因果路径 |
| What Went Well | 应保留或推广的机制，不只是表扬 |
| What Did Not Go Well | 工具、流程和信息缺口，不贴个人标签 |
| Where We Got Lucky | 未形成控制但偶然避免损失的条件 |
| Action Items | Owner、期限、风险目标与验收 |
| Lessons / Follow-up | 跨团队推广、风险登记与后续验证 |

“恢复了”应区分入口恢复、积压处理、数据修复与最终业务核对。API 返回正常不代表重复扣款或丢失订单已处理。影响数字注明分母、窗口、去重规则与估算限制，不能把重试次数直接当受影响用户数。

### 3.2 时间线如何避免误导

使用统一时区和可追溯证据，区分事件发生时间与日志到达时间。记录部署版本、告警、用户报告、假设与动作结果。日志缺失时标为未知，不为了故事连贯补造时间。跨系统时钟偏差需注明，事件因果也可借请求和业务 ID 关联。

虚构时间线：10:00 执行表结构迁移；10:02 旧实例请求开始失败；10:05 客户报告；10:07 值班确认错误；10:12 暂停发布并限制受影响入口；10:20 兼容修复恢复服务；10:40 完成积压与数据核对。实际复盘要链接每条证据，不能仅凭回忆精确到分钟。

从 10:02 用户受损到 10:20 服务恢复是18分钟，至全部业务核对结束为38分钟；不同定义会改变“恢复时间”。发布到客户报告是5分钟，不等于故障检测耗时，后者还需明确故障起点与发现点。

### 3.3 Root Cause 不能停在人为错误

Root Cause（根因）与 Contributing Factor（促成因素）可帮助组织解释，但不要为追求单一词语隐藏因果网络。“执行了错误命令”还需问：为什么权限可影响整个生产？为什么没有范围预览？为什么没有审批？为什么不可恢复？为什么手册指向危险操作？为什么监控没有及时发现？

Five Whys（连续追问原因）适合沿一条路径深入，但不必恰好五次，也不能把所有路径强行归到“培训不足”。Fault Tree（故障树）用 AND/OR 表示哪些条件组合造成顶层失败；Causal Graph（因果图）表达多条件联系。图中的边应有证据或标为假设，不把相关当因果。

反事实检查能检验建议：如果只有提醒员工谨慎，错误命令仍可删除全库；若加范围限制与可恢复删除，后果可能缩小。也要检查控制自身失效模式，例如审批者只点确认、预览与执行范围发生变化，不能把新增流程当无条件保证。

## 四、Action Item：从完成任务到验证风险下降

好的行动具体、有 Owner、Due Date（期限）、目标风险与验收。优先工程控制，同时承认培训、文档和人员准备也有作用；问题是不能只依赖记忆和警觉。

| 薄弱表述 | 改进表述及验收 |
| --- | --- |
| 以后更小心 | 限定删除操作的资源范围，测试越界请求被拒绝 |
| 加强审批 | 高风险删除绑定范围摘要与双人授权，防修改后沿用旧批准 |
| 多做备份 | 隔离环境完成指定恢复场景并核对数据与耗时 |
| 改进监控 | 注入约定故障验证告警到值班和业务影响口径 |
| 更新文档 | 修订危险步骤，由非作者按手册演练验证 |

原示例“12月15日前为 Production Delete API 加范围预览、双人批准和24小时可恢复软删除，由平台团队负责”是可用教学行动，但还需明确适用资源、绕过路径、恢复权限、容量和保留义务。软删除不是所有资源都能简单支持，也不能替代隔离备份；24小时只是此案例要求，不是行业标准。

为每项指定一个明确负责归属，协作方可多名。风险 Owner 负责接受与跟踪风险，执行 Owner 负责交付控制，两者不必相同。跨团队行动必须有资源承诺；无法按期完成则升级、调整范围或重新接受剩余风险，不默默延期。

关闭条件包含实现、部署和效果验证。测试通过但生产未启用不能关闭；配置启用但旁路未覆盖也不能算完成。控制上线后观察复发与误报、人工负担和副作用，避免为防事故增加一个更危险的集中权限。

## 五、项目复盘与 Pre-mortem

事故之外，重大迁移、Launch（发布）和架构 Initiative（举措）也应复查目标是否达成、预测与实际成本/性能差异、错误假设、决策效率、依赖沟通和可复用模式。交付日期达到但关键用户不用、运维负担翻倍，也可能没有达成项目目标。

固定原预测版本与统计范围，再对比结果。预算差异拆为用量、单价、范围、返工与遗漏，不因目标后来改变就抹去原假设；性能变化也区分测试模型和生产流量不同。成功项目同样可能靠偶然低负载或关键人员加班，属于需要管理的幸运条件。

Pre-mortem（事前预演失败）在启动前假设“项目已失败”，请不同角色独立列原因，再按影响、可验证性与早期信号归类。例如采购超期、数据质量不足、回退不可行或无人值班。把重要项转成验证、依赖和风险记录，不停留在集体表达担忧。它不能预测所有问题，也不能代替上线前实际测试。

~~~text
项目目标、基线与原预测版本：
实际结果及证据窗口：
偏差：[范围/用量/单价/性能/交付/运营]
当时假设与已知信息：
决策、依赖和沟通中的促进/阻碍：
可复用模式及适用边界：
行动：[风险目标/Owner/期限/验收/复查]
~~~

## 六、Architecture Risk Management：持续管理未知后果

### 6.1 风险记录应能触发行动

Risk（风险）是未来可能发生且影响目标的不确定事件，Issue（问题）是已发生的情况。事故已发生不意味着后续风险消失，例如已修当前数据仍可能再次被同一重放任务覆盖。

~~~text
风险ID、描述、触发条件与受影响范围：
类别及业务后果：
可能性、影响、证据与置信度：
现有控制与控制缺口：
Mitigation：[行动/负责人/期限/验收]
Contingency：[触发/处置/权限/演练]
风险Owner、接受者及授权范围：
剩余风险、复审时间与触发：
关联事故、ADR、路线图和当前状态：
~~~

风险类别覆盖可用性/性能、安全/隐私、数据完整性、供应商/锁定、交付/依赖、成本/容量、技能/运营准备和合规。类别帮助分配专业输入，不意味着一个风险只能属一类；同一供应商故障可能同时造成服务和合同影响。

### 6.2 Likelihood × Impact 的正确边界

Risk Exposure（风险暴露）可用 Likelihood（可能性）× Impact（影响）帮助排序。只有明确窗口、可比概率和相同损失单位时，乘积才可解释为简单期望损失。例如假设某年度事件概率0.1、发生损失20万欧，期望2万欧；控制后概率0.02、相同损失，期望4000欧，差额16000欧。控制若年成本10000欧，在此简化模型下净期望改善6000欧。

这不是建议仅凭此数字接受风险：概率可能无依据，损失有长尾，多个事件有关联，合规或不可承受损失也不能被平均值抵消。“高、中、低”或1到5的等级通常是排序尺度，不应伪装成精确金额；不同风险的分数不一定可直接相加。

记录置信度与情景，优先验证会改变决定的未知。风险登记表不是仓库：按业务变化、事故、控制失败、供应商变化和复审日期更新，持续无人处理的高风险需暴露资源与授权问题。

### 6.3 Mitigation 与 Contingency

Mitigation（缓解）在事件前降低概率或后果，例如兼容性测试、防越权和备份隔离；Contingency（应急预案）是在触发后怎样响应，例如停止发布、切换或受控恢复。两者相互补充，不能用“出事时再重启”替代预防，也不能因为预防存在就不准备失败。

预案要有触发、权限、顺序、停止条件与恢复核对，按场景演练。自动动作设次数、范围和冷却，防止反复切换制造新故障。风险接受也需要预案或明确为什么不需要，不能仅写“业务已知晓”。

## 七、四种风险响应与剩余责任

Avoid（规避）改变方案移除风险来源，例如取消不必要的敏感数据收集；代价可能是功能范围缩小。Mitigate 降低概率或影响，例如租户隔离与限流，但仍保留剩余风险。

Transfer（转移）通过合同、保险或托管转移部分责任或经济影响；并不自动转移全部客户承诺和运营责任。托管数据库仍需自己配置权限、确认恢复并处理应用一致性，赔偿也不恢复已丢数据。

Accept（接受）需要有权 Risk Owner 明确范围、原因、剩余影响、期限与监控，工程师不能替组织默默接受重大业务或合规风险。接受不是永不处理，环境变化或超阈值应重评。可以组合响应，如取消高危功能、缓解其余部分并接受有界残余，但不能借词语掩盖未解除底线。

## 八、Architecture Governance：方向、证据与自治

治理保护重要质量属性和组织目标，不集中决定所有实现细节。

| 工具 | 用途与限制 |
| --- | --- |
| Principle / Standard | 原则给方向，标准给可核验最低要求；不止口号 |
| Reference Architecture | 参考边界、失败与控制；注明适用场景 |
| Golden Path | 推荐模板、工具与支持降低采用成本；允许受控例外 |
| RFC / ADR | 提案讨论与决定理由；批准不等于实现 |
| Risk-based Review | 高影响或难逆转决策深入检查；小改动留团队 |
| Fitness Function | 持续检验架构特性的规则或演练；单项不能证明全部质量 |
| Technology Radar | 技术采用/试验/限制状态与理由；不是时髦清单 |
| Exception Process | 有授权的偏离、补偿与退出；不是永久豁免 |
| SLO / Security / Cost Dashboard | 服务、安全、成本结果；关注口径与盲点 |

SLO（服务水平目标）连接用户体验与统计窗口。Fitness Function（架构适应度检查）可为依赖测试、兼容性检验或恢复演练，不只代码测试。Technology Radar（技术雷达）写清技术适用条件、Owner 和复查，避免把“试验中”误当可用于所有关键系统。

治理循环是标准与方向、设计与决定、实现与验证、运行反馈与修订。若生产偏离决定，明确修实现、申请例外或改变决定，不能事后补文档就假称从未偏离。

## 九、Guardrail 与 Gate：自动检查不等于自动安全

Guardrail（护栏）在已知边界内支持团队自主，Gate（门禁）要求在特定节点满足条件或获得授权。二者不完全是技术与人工的二分：门禁也可自动化，护栏也可有人工例外；重点是是否需要每次中央排队及风险是否得到适当处理。

| 示例 | 如何工作 | 漏洞与补充 |
| --- | --- | --- |
| IaC Policy 检查公开存储 | 扫基础设施代码中访问配置 | 还需发现线上漂移与其他创建路径 |
| CI 阻止严重漏洞 | 按规则拦截受影响制品 | 需可达性/暴露分流、限时例外与修复，严重级别不等于全部实际风险 |
| ArchUnit 依赖规则 | 检查 Java 类之间不允许的依赖 | 反射、动态调用和外部服务不一定覆盖 |
| API Lint | 检查结构、规范和部分兼容性 | 字段语义、业务行为仍需契约测试 |
| Deployment Policy | 检查健康探针和资源上限 | 配置存在不等于探针正确或容量足够 |
| Cloud Budget Alert | 发现偏离预算并通知负责人 | 账单有延迟，告警本身不等于硬支出上限 |

IaC 是基础设施即代码，CI 是持续集成，API Lint 是接口静态检查。本表讨论能力边界，不提供依赖某工具版本的可直接运行配置。

高风险、不可逆和跨边界选择适合人工专业评审；低风险可逆实现尽量自助。规则版本、负责人、误报处理与异常路径清楚，权限平台故障时的失败策略按风险确定，不能一律静默放行或无边界停全组织。规则上线先观察影响、验证误报并提供修复路径，避免安全控制成为团队绕开的负担。

## 十、Exception Management：偏离要能发现、到期和退出

标准无法覆盖所有环境，例外需记录偏离哪条标准、Business Justification（业务理由）、Risk Assessment（风险评估）、Compensating Control（补偿控制）、Risk Owner、Expiry Date 和 Migration Plan。补充授权范围、退出验收与到期升级人，不能只写“暂时允许”。

例如遗留服务短期无法升级，可能限制网络、权限和暴露面，安排迁移与持续监测；这些控制是否足够应由相应负责人判断，不能因有工单就自动合法安全。到期前复查，未完成则整改、缩功能、停用或重新授权，不自动无限延期。

退出要看运行状态：旧凭证撤销、旧路径关闭、数据按规则处理，而不只是文档改为完成。例外集中视图有助发现同类缺口；多数团队都要同种例外，可能说明标准或平台能力需要调整，不应只增加审批。

## 十一、衡量治理：同时看 Safety 与 Flow

Safety（安全与可靠）和 Flow（交付流动）要同时观察，不能用会议数或文档数代替结果。

| 指标 | 需要定义的口径与解释 |
| --- | --- |
| Change Failure Rate | 哪些生产变更计分母、何种失败计分子；避免拆分变更游戏化 |
| Lead Time for Change | 从代码提交还是需求开始到生产，起止必须一致 |
| MTTR | 是恢复、修复还是响应，明确起止并看分布，缩写本身不够 |
| SLO Compliance | 服务目标、窗口与合格事件分母，不能故障时删失败 |
| Critical Vulnerability Age | 从发现到修复生效，仍开放和已关闭分开看 |
| 例外数量与逾期率 | 定义在期、到期、退出与重复延期，数量少不等于风险小 |
| Cloud Unit Cost | 同范围成本除有效业务量，含质量和失败费用 |
| Platform Adoption | 符合适用范围的采用及体验，强制安装不等于价值 |
| 依赖交付时间 | 从完整请求到对方可用交付，区分排队与处理 |
| 行动完成率与复发 | 按验收关闭并检查同机制复发，不能只看工单状态 |

例如十项到期行动八项验收通过，完成率80%；若剩下两项是最高风险，仍不能称风险已下降80%。复发也按故障机制与暴露情况判断，不是换服务名就不算同类事件。

比较改善前后要注意流量、团队和发布类型变化，不能直接把所有好转归因治理。观察趋势、分布和案例证据，避免给个人排名导致少报事故、隐藏例外。指标用于提问与资源决策，不制造新的行为扭曲。

## 十二、Architecture Debt：把持续代价放进投资组合

Architecture Debt（架构债务）是结构或决定使未来改变、运营和风险控制付出额外代价。可以是主动换取交付速度，也可能源于环境变化；不是所有旧技术或不同风格都属于债务。

在统一 Risk/Portfolio（风险与投资组合）视图记录业务影响、持续 Interest（利息）、Owner、触发、偿还方案与依赖。利息可以是每次变更额外对账时间、事故暴露或扩容成本，不一定能可靠换算成货币。比较偿还投入与释放能力，并与 Feature Roadmap（功能路线图）结合，而非只说“技术需要”。

例如共享数据库阻碍独立发布，先明确数据权威和契约，按业务边界迁移，再用策略阻止新增跨 Schema 访问。仅加依赖测试但数据库凭证仍能访问所有表，不能证明债务不复发；代码、权限与运行检查要相互补充。

可以接受或延期债务，但明确条件与复审。全面重写可能引入更大迁移风险，优先分阶段偿还并验证价值；已经投入很多也不构成必须继续的理由。

## 十三、发布事故：从 Schema 失败到系统改进

### 13.1 发生机制与现场恢复

虚构事件：滚动发布期间新旧应用共存，迁移直接重命名旧列，旧实例仍查询旧名而失败。Schema 是数据结构，Rolling Deployment（滚动发布）是逐批替换实例，因此数据库变化必须考虑仍运行的旧代码、后台任务和延迟消费者。

现场先停止继续扩大发布，确认失败查询、变更与实际运行版本。仅回滚应用不会恢复被改的结构，重跑旧脚本也可能破坏新数据。判断兼容修复或 Roll-forward（前向修复）是否更安全，必要时限制写入并核对影响。恢复后处理积压和部分成功副作用，不能盲目重放非幂等付款。

### 13.2 Expand-and-Contract 的完整边界

Expand-and-Contract（扩展再收缩）先加入兼容结构，部署能兼容过渡状态的代码，迁移和验证数据，切换读写，确认旧消费者退役后才移除旧结构。例如增加新列期间保留旧列，明确哪个值为权威、怎样同步并发新写，再按批回填；不能回填旧快照覆盖刚产生的新数据。

同库双列更新可放在同一业务事务中；跨系统双写则不自动原子，需要事件、重试和对账。分批回填有检查点、幂等、限速和错误停止，监测锁、数据库负载和复制延迟。验证行数、差异、业务不变量与权限，不能只看脚本退出码。

PostgreSQL 17 中 ALTER TABLE 的锁和表重写成本取决于具体操作；官方文档说明未另注明时使用 ACCESS EXCLUSIVE 锁，不能把“只加一列”普遍宣称为零停机。需在目标版本和代表规模下验证，设受控等待/执行窗口与失败处置。这里不提供未运行的生产 SQL。

### 13.3 复盘因果、行动与验收矩阵

浅层结论“开发者忘兼容”之外，检查迁移指南缺模式、CI 无兼容测试、回滚只测代码、发布清单无责任人及告警未覆盖旧版本。What Went Well 可以是发布暂停及时；Where We Got Lucky 可以是影响范围尚小，这种幸运应转成正式灰度控制。

| 行动 | 验收与边界 |
| --- | --- |
| 兼容迁移模式 | 有旧新代码和旧/扩展结构的允许组合说明 |
| Schema Compatibility Test | 真实查询、写入、后台任务与数据不变量，不只比较 DDL 文本 |
| Canary 小流量发布 | 同时观察新旧版本、关键租户与后台路径，不能只给新实例流量 |
| 高风险迁移 Review | 评审锁、数据转换、恢复与权限，不审核所有普通小改 |
| 回退与前向演练 | 切换前后分别判断可逆性，含已写入数据及外部副作用 |

Contract 阶段移除旧列后，旧应用可能再也不能直接运行。明确安全回退窗口及其关闭条件，不把“永远能回旧版本”写进手册。复盘行动验收后再更新 ADR、标准与路线图，形成从学习到运行机制的闭环。

## 十四、面试准备：真实材料、完整回答与追问

### 14.1 可填写经历模板

~~~text
背景及用户影响：[口径/证据/未知]
我的职责与权限：[实际做什么，谁指挥]
恢复过程：[当时信息/假设/动作/验证]
促成因素：[触发/防线/流程与信息缺口]
短期修复与长期控制：
行动：[Owner/期限/验收及部署]
效果：[基线/窗口/结果/仍有风险]
个人学习：[误判与修正，未被验证的部分]
~~~

用真实经历填写，区分个人行动与团队成果；没有指标就如实给可核验定性结果，不捏造节省和复发率。不能把“我协调复盘”讲成“我独自修复全部系统”。

### 14.2 如何复盘一次生产事故？

“我先说明用户影响和恢复边界，明确自己在事故响应中的职责。复盘统一时间与证据，区分当时已知和后来发现，分析触发与多层防线为何失效，不停在人为错误。行动按风险排序，每项有负责人与验收，部署后复测并观察同机制是否复发。重要学习更新标准、ADR 和风险视图，既检查控制效果，也避免新增不必要交付阻塞。”

**追问：不追责会不会没人负责？** 不责备是为完整信息和学习，不取消真实职责、行动期限和授权；必要行为问题按独立既有流程处理。把所有人骂一遍既不能证明责任清晰，也不能防复发。

### 14.3 架构治理怎样避免官僚化？

“我按影响和可逆性分级，低风险团队自主，高风险跨边界接受专业评审。标准配套推荐路径、模板和自动检查，例外有期限与退出。结果看变更失败、恢复、漏洞、成本和依赖等待，不能只数会议。规则本身也复查误报与维护成本，必要时修订。”

**追问：自动检查通过能否跳过所有评审？** 不能，自动化只覆盖能编码的部分。新业务风险、数据用途和不可逆迁移仍需判断，但也不应把无关低风险改变全送中央审批。

### 14.4 没钱偿还架构债务怎么办？

“我把债务影响具体到交付、运营和风险，比较分期偿还、缩功能、补偿控制和明确接受。高风险需要有权者决定资源或范围，低收益债务可以延期并设触发。优先结合正在做的功能边界偿还，验证实际效果，不默认全面重写。”

**追问：风险表里登记了就够吗？** 不够，登记只是可见性。没有 Owner、行动、接受权限和复审，风险仍无人管理，事故后不能以‘早写过’代替职责。

## 十五、常见错误与修正

复盘变成羞辱会减少真实信息，改为证据与系统条件；只“加强培训”会把可靠性压在记忆上，补工程控制和效果验收。登记后不再复查让风险表过期，用日期与事件触发更新。

所有技术选择都中央审批会降低流动，标准无工具支持又会诱使绕行；风险分级与自助能力应结合。例外无期限形成永久分叉，关闭需验证运行退出。活动指标取代结果会鼓励写更多文档，同类事故复发则应复查行动是否上线、覆盖是否足够与假设是否错误，不能再加一句提醒。

## 十六、扫雷自测与完整答案

1. **Blameless 与没有 Accountability 的差别？** 前者避免以惩罚为目标妨碍学习，后者缺少职责和落实。应保留诚实事实、负责人与可验证行动，必要行为问题另按既有流程处理。
2. **人为错误为何不够？** 它只描述触发，不解释权限、防线、信息与恢复为何允许大损害。类似操作可能再发生，改进应降低它造成事故的条件。
3. **Mitigation 与 Contingency 区别？** 缓解提前降低风险，应急在触发后执行处置。兼容测试与故障后停止发布不同，两者都需明确有效性边界。
4. **Guardrail 与 Gate 怎么选？** 已知低风险可逆行为用护栏支持自主，高风险不可逆跨边界选择加适当门禁与专业判断；两者都可能自动或人工，不能机械二分。
5. **哪些指标说明治理效果？** 失败率、交付时间、恢复、SLO、漏洞年龄、例外逾期、单位成本、采用体验、依赖等待和行动复发等互补；同时看口径、暴露和环境变化，不能只数会议。
6. **Risk Exposure 可以精确排名一切吗？** 不可以，概率影响有置信范围，等级乘积不等于金额，相关和灾难尾部也可能被隐藏。底线与不可承受后果先判断。
7. **八成行动完成等于风险降低八成吗？** 不等于，行动风险权重和覆盖不同；两个未完成高风险项可能最重要。检查实际控制效果与复发而非工单比例。
8. **回滚应用能修复破坏式 Schema 变更吗？** 通常不能自动修复，数据库与已写数据已变化。需要兼容修复、前向处置或受控数据恢复，并核对业务副作用。
9. **预算告警是不是支出硬限额？** 不是，计量可能延迟且通知不阻止使用。需额外配置适当配额和应急动作，并评估停止服务的业务风险。
10. **拆分共享数据库后怎样防复发？** 明确数据契约和权威，限制凭证与跨 Schema 路径，配合依赖规则和运行检查。仅改变代码目录或增加一条静态测试不够。
