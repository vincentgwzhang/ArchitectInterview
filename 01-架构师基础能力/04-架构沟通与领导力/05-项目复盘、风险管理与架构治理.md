# 05. 项目复盘、风险管理与架构治理

## 学习目标

1. 使用 Blameless Postmortem 从事故和项目中提取系统性改进。
2. 建立持续的 Architecture Risk Management。
3. 设计支持自治而非阻塞交付的治理机制。
4. 用指标验证治理是否产生实际效果。

## 一、复盘的目的

复盘不是寻找“谁犯了错”，而是理解：

- 当时发生了什么？
- 为什么现有系统和流程允许它发生？
- 哪些防线没有工作？
- 团队当时基于什么信息做出行动？
- 如何降低相同或相似问题再次发生的概率和影响？

复杂系统事故通常来自多个条件共同作用，而不是单个人的单一错误。

## 二、Blameless Postmortem

Blameless 不表示没有 Accountability。它表示不以惩罚个人为目标，而是让参与者安全地提供完整信息。

推荐结构：

```text
Summary
Customer/Business Impact
Timeline
Detection and Response
Root Causes and Contributing Factors
What Went Well
What Did Not Go Well
Where We Got Lucky
Action Items
Lessons and Follow-up
```

### 2.1 Timeline

使用统一时间和 Evidence：

- Deployment。
- Alert。
- 用户报告。
- Investigation。
- Mitigation。
- Recovery。

避免用事后知识评价当时决策。应该说明当时可见的信息。

### 2.2 Root Cause

“工程师执行了错误命令”通常不是足够 Root Cause。继续问：

- 为什么该命令能影响生产？
- 为什么没有 Approval 或 Scope Guard？
- 为什么删除不可恢复？
- 为什么 Monitoring 没有提前发现？
- 为什么 Runbook 引导到危险操作？

可以使用 Five Whys、Fault Tree 或 Causal Graph，但不要为了形式强行得到单一根因。

## 三、Action Item

好的 Action Item 应：

- 具体。
- 有 Owner。
- 有 Due Date。
- 能降低概率、影响或检测时间。
- 可以验证完成。

较差：

> 工程师以后更加小心。

更好：

> 在 12 月 15 日前为 Production Delete API 加入 Resource Scope Preview、Two-person Approval 和 24 小时可恢复软删除；Owner：Platform Team。

优先选择系统性改进，而不是只增加培训或文档。

## 四、项目复盘

复盘不只用于 Incident。重大 Migration、Launch 或架构 Initiative 完成后也应 Review：

- 目标是否达成？
- Forecast 与真实 Cost/Performance 有何差异？
- 哪些 Assumption 错误？
- 决策流程是否有效？
- Dependency 和沟通哪里出现问题？
- 哪些 Pattern 可以复用？

使用 Pre-mortem 还可以在项目开始前假设“项目已经失败”，倒推可能原因并提前降低风险。

## 五、架构风险管理

风险可以表示为：

```text
Risk Exposure = Likelihood × Impact
```

每个 Risk 应记录：

- 描述与触发条件。
- Category。
- Likelihood/Impact。
- Business Consequence。
- Mitigation。
- Contingency。
- Owner。
- Review Date。
- Residual Risk。

常见类别：

- Availability/Performance。
- Security/Privacy。
- Data Integrity。
- Vendor/Lock-in。
- Delivery/Dependency。
- Cost/Capacity。
- Skill/Operational Readiness。
- Compliance。

## 六、风险响应策略

- Avoid：改变方案，消除风险来源。
- Mitigate：降低概率或影响。
- Transfer：通过保险、Contract 或 Managed Service 转移部分责任。
- Accept：明确接受并监控。

接受风险必须有具备相应权力的 Risk Owner，不能由工程师替业务默默接受。

## 七、Architecture Governance

治理的目标是确保重要质量属性和组织目标持续得到保护，而不是集中控制所有技术细节。

治理工具包括：

- Principle 和 Standard。
- Reference Architecture。
- Golden Path。
- RFC/ADR。
- Risk-based Review。
- Architecture Fitness Function。
- Technology Radar。
- Exception Process。
- SLO、Security 和 Cost Dashboard。

## 八、Guardrail 而非 Gate

Gate 是每次都需要中央审批；Guardrail 是团队在明确边界内自主行动。

可自动化 Guardrail：

- IaC Policy 检查 Public Storage。
- CI 阻止 Critical Vulnerability。
- ArchUnit 检查 Dependency Rule。
- API Lint 检查兼容性。
- Deployment Policy 检查 Health Probe 和 Resource Limit。
- Cloud Budget Alert 检查异常成本。

只有高风险、不可逆或跨边界决策才进入人工 Review。

## 九、Exception Management

标准不可能覆盖所有情况。例外记录应包括：

- 违反哪个 Standard。
- Business Justification。
- Risk Assessment。
- Compensating Control。
- Risk Owner。
- Expiry Date。
- Migration Plan。

没有 Expiry 和 Owner 的例外容易变成永久架构分叉。

## 十、衡量治理效果

不要用“举行了多少评审会议”衡量治理。更有价值的 Outcome Metric：

- Change Failure Rate。
- Lead Time for Change。
- MTTR。
- SLO Compliance。
- Critical Vulnerability Age。
- Architecture Exception 数量与逾期率。
- Cloud Unit Cost。
- Platform Adoption。
- 跨团队 Dependency Lead Time。
- Postmortem Action 完成率与复发率。

治理既要降低风险，也不能造成不必要 Delay。应同时观察 Safety 与 Flow。

## 十一、架构债务治理

Architecture Debt 进入统一 Risk/Portfolio 视图：

1. 说明业务和运营影响。
2. 估算持续 Interest。
3. 确定 Owner 与触发条件。
4. 与 Feature Roadmap 结合偿还。
5. 通过 Fitness Function 防止复发。

例如完成共享数据库拆分后，加入 Policy 禁止新 Service 访问不属于自己的 Schema。

## 十二、场景示例：发布事故

一次 Schema Migration 导致旧版本 Application 失败。

浅层结论：开发者忘记兼容旧版本。  
系统性分析可能发现：

- Rolling Deployment 意味新旧版本共存。
- Migration Guide 没有 Expand-and-Contract。
- CI 没有兼容性测试。
- Rollback 不能恢复已修改 Schema。
- Release Checklist 没有 Owner。

改进：

- 建立向后兼容 Migration Pattern。
- 加入 Schema Compatibility Test。
- Canary 验证旧新版本。
- 为高风险 Migration 引入 Review。
- 演练 Roll-forward 与 Rollback。

## 十三、面试回答框架

回答生产事故或失败项目时：

1. 说明用户和业务影响。
2. 说明你在恢复中的具体职责。
3. 展示如何基于 Evidence 找到系统性因素。
4. 说明短期修复和长期改进。
5. 用指标说明改进效果。
6. 诚实描述个人学习，而不是把责任推给别人。

## 十四、常见错误

- Postmortem 变成责任追究。
- Action Item 只有“加强培训”。
- 风险登记后从不 Review。
- 所有技术选择都要中央审批。
- Standard 没有自动化支持。
- Exception 没有期限。
- 用 Process Activity 而不是 Outcome 衡量治理。
- 同类事故反复发生，却没有检查 Action 效果。

## 十五、自测题

1. Blameless 与没有 Accountability 有什么区别？
2. 为什么“人为错误”通常不是充分 Root Cause？
3. Risk Mitigation 与 Contingency 有什么区别？
4. Guardrail 和 Gate 如何选择？
5. 哪些指标可以说明架构治理有效？

## 十六、总结

- 复盘应恢复完整 Context，并把重点放在系统性学习。
- Action Item 必须有 Owner、期限和可验证风险下降。
- 架构风险需要持续识别、量化、响应和 Review。
- 有效治理使用 Guardrail、Golden Path 和自动化支持团队自治。
- 应以 Reliability、Security、Flow 和 Cost Outcome 衡量治理，而不是文档与会议数量。
