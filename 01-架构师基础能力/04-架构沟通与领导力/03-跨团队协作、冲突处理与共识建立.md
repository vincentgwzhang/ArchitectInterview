# 03. 跨团队协作、冲突处理与共识建立

## 学习目标

1. 理解跨团队冲突背后的目标、边界和激励差异。
2. 使用结构化方法建立共识并明确决策权。
3. 在没有直接管理权时产生技术影响力。
4. 处理无法达成一致的情况而不让工作停滞。

## 一、跨团队协作为什么困难

冲突通常不只是技术观点不同，还可能来自：

- 团队 KPI 不同。
- Roadmap 和 Deadline 不同。
- 风险由一方承担、收益由另一方获得。
- System Ownership 不清晰。
- 信息不对称。
- 历史信任不足。
- 资源和人员有限。

例如 Platform Team 希望统一标准，Product Team 希望快速交付。双方目标都合理，问题在于局部优化发生冲突。

## 二、从立场转向利益

立场：

> 必须使用 Kafka。  
> 绝对不能使用 Kafka。

背后的利益可能是：

- 需要削峰和异步解耦。
- 团队没有 Kafka 运维能力。
- 担心增加交付时间。
- 希望重用已有 Platform。

先问“你担心什么”和“成功标准是什么”，比继续争论工具更容易找到方案。

## 三、建立共同问题定义

共同文档至少应包含：

- Problem Statement。
- Goals 与 Non-goals。
- Decision Drivers。
- Constraints。
- Facts 与 Assumptions。
- Affected Teams。
- Decision Deadline。

如果团队对问题都没有共识，不可能对解决方案达成稳定共识。

## 四、明确决策模型

### 4.1 RACI

- Responsible：执行工作。
- Accountable：对结果负责。
- Consulted：提供意见。
- Informed：需要知情。

### 4.2 DACI

- Driver：推动决策。
- Approver：最终决定。
- Contributors：提供专业输入。
- Informed：同步结果。

### 4.3 Advice Process

决策者在决定前咨询受影响者和领域专家，然后对结果负责。适合去中心化组织。

共识不等于所有人都有 Veto。必须知道谁在何时作最终决定。

## 五、建立技术共识

推荐过程：

1. 共同确认 Requirement 和 NFR。
2. 收集每方 Concern。
3. 生成至少两个真实可行方案。
4. 使用相同 Criterion 比较。
5. 对关键未知做 Spike/Test。
6. 记录 Trade-off 和 Residual Risk。
7. Decider 作决定。
8. 即使不同意，也执行已确定方案，即 Disagree and Commit。

Disagree and Commit 的前提是异议被公平听取、决策过程透明，并且没有忽略重大安全或合规风险。

## 六、处理冲突

### 6.1 区分冲突类型

- Task Conflict：方案和事实不同，通常有价值。
- Process Conflict：谁决定、如何推进不清楚。
- Relationship Conflict：信任和沟通问题。
- Resource Conflict：时间、预算、人员争夺。

不同冲突需要不同处理方式。用更多技术数据无法自动解决 Ownership 或信任问题。

### 6.2 冲突处理步骤

1. 私下了解各方 Context，避免公开场合先入为主。
2. 陈述共同目标。
3. 分离 Fact、Assumption、Preference。
4. 明确不可妥协 Constraint。
5. 寻找可验证的小实验。
6. 需要时由明确 Decider 决定。
7. 记录结果和后续检查点。

### 6.3 降低情绪温度

- 讨论方案，不评价个人能力。
- 使用“这个方案的风险是……”而不是“你的设计错了”。
- 复述对方观点直到对方确认。
- 对不确定性保持诚实。
- 避免在大会议中突然否定他人方案。

## 七、跨团队 Contract

协作不能只依赖会议和关系。应建立清晰 Contract：

- API/Event Schema。
- SLO 与 Support Model。
- Ownership。
- Versioning/Deprecation Policy。
- Incident Escalation。
- Change Notification。
- Cost Allocation。

Team API 不只是网络 API，还包括团队提供能力的使用方式和责任边界。

## 八、影响力而非权力

架构师建立影响力的方法：

- 提供清楚的分析和 Evidence。
- 帮助团队解决真实问题。
- 创建 Reusable Pattern 与 Golden Path。
- 在 Incident 中承担责任，不只做评论。
- 公开承认错误并更新决策。
- 让团队参与设计而不是接收命令。
- 持续跟进实施结果。

只发布标准、不提供工具和支持，很难形成长期影响。

## 九、处理标准与团队自治

标准适合保护：

- Security Baseline。
- Observability。
- API Compatibility。
- Data Classification。
- Deployment Safety。

团队可以在 Guardrail 内自治。对例外建立：

- Business/Technical Justification。
- Risk Owner。
- Compensating Control。
- Expiry Date。
- Review Trigger。

例外机制比假装所有系统完全一致更现实。

## 十、场景示例

Team A 希望直接读取 Team B 的数据库以赶上 Deadline，Team B 担心 Schema Coupling。

处理方式：

1. 确认 Deadline 和所需数据字段。
2. 明确跨库访问对 Ownership、Security 和发布的风险。
3. 比较 API、Data Product、CDC Event 和临时 Read Replica 等方案。
4. 如果短期只能使用临时方案，限制只读权限和字段。
5. 记录 ADR、Owner、Migration Target 和 Expiry Date。
6. 将长期 Contract 纳入双方 Roadmap。

结果不一定是“绝不妥协”，而是透明、受控且可退出的决策。

## 十一、常见错误

- 把共识理解为所有人完全同意。
- 没有 Decider，会议反复循环。
- 把组织冲突当作纯技术问题。
- 架构师只在 Review 末期出现并否决方案。
- 标准没有工具、模板和迁移支持。
- 口头同意后没有 Contract、Owner 和 Deadline。
- 通过 Escalation 解决所有分歧，损害长期信任。

## 十二、面试回答框架

使用 STAR：

- Situation：两个团队的目标和冲突是什么？
- Task：你需要达成什么结果？
- Action：如何建立共同 Driver、收集 Concern、验证假设并明确 Decider？
- Result：决策、交付、指标和关系有什么改善？

重点说明个人如何创造决策条件，而不是简单说“我说服了他们”。

## 十三、自测题

1. 立场与利益有什么区别？
2. 共识是否意味着所有人拥有否决权？
3. DACI 中 Driver 和 Approver 的职责是什么？
4. 如何处理临时架构例外？
5. 架构师如何在没有管理权时建立影响力？

## 十四、总结

- 跨团队冲突经常来自目标、激励、Ownership 和资源，而不只是技术。
- 先建立共同 Problem 与 Decision Driver，再比较方案。
- 清楚的 Decider 能防止无期限追求全员一致。
- Contract、Guardrail 和 Exception Process 让协作可持续。
- 长期影响力来自可信 Evidence、实际支持、公平过程和结果跟进。
