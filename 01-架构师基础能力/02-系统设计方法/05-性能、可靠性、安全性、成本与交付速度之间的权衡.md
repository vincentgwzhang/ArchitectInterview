# 05. 性能、可靠性、安全性、成本与交付速度之间的权衡

## 学习目标

1. 理解架构设计是多目标优化，不存在脱离 Context 的“最佳方案”。
2. 识别 Performance、Reliability、Security、Cost 与 Delivery Speed 的冲突。
3. 使用可重复的方法比较方案并记录决策。
4. 在面试中清楚说明为什么接受某项代价。

## 一、架构的本质是权衡

常见目标包括：

- 更低 Latency。
- 更高 Availability。
- 更强 Consistency。
- 更严格 Security。
- 更低 Cloud Cost。
- 更快 Time to Market。
- 更高 Maintainability。

这些目标不可能全部同时最大化。例如：

- Multi-region Active-Active 提升 Availability，却增加 Cost 和数据一致性复杂度。
- 同步安全检查降低风险，却增加 Latency。
- 自建 Platform 提供控制力，却减慢初期交付。
- Cache 提升 Performance，却增加 Stale Data 风险。

架构师的责任不是隐藏代价，而是让 Trade-off 可见、可讨论、可验证。

## 二、先建立决策标准

在比较方案前，定义 Decision Driver：

```text
Availability: 99.95%
P99 latency: < 300 ms
RPO: < 5 minutes
Launch deadline: 12 weeks
Monthly infrastructure budget: €30,000
Compliance: EU data residency
Team: 8 engineers, limited Kubernetes experience
```

没有这些约束，“Serverless 还是 Kubernetes”只是个人偏好争论。

## 三、Performance 权衡

### 3.1 Cache

收益：降低 Latency、减少 Database Load。  
代价：一致性、Invalidation、Memory Cost、Cache Stampede。

### 3.2 Denormalization

收益：减少 Join、提高读取性能。  
代价：重复数据、更新复杂度、最终一致性。

### 3.3 Asynchronous Processing

收益：缩短同步路径、削峰。  
代价：用户不能立即获得最终结果，排障与补偿更复杂。

### 3.4 Precomputation

收益：读取快。  
代价：Storage、刷新延迟、计算资源和复杂 Pipeline。

Performance 优化必须基于 Measurement。不要为了假设的瓶颈提前引入复杂度。

## 四、Reliability 权衡

### 4.1 Redundancy

多 AZ、多 Replica 和 Backup 提升可靠性，也增加 Cost 和运维面。

### 4.2 Retry

Retry 可以屏蔽短暂故障，却可能放大流量形成 Retry Storm。必须结合 Backoff、Jitter、Deadline 和 Circuit Breaker。

### 4.3 Strong Consistency

强一致保护业务 Invariant，但同步 Quorum 可能增加 Latency，并在 Partition 时降低 Availability。

### 4.4 Graceful Degradation

关闭 Recommendation、Analytics 或高级搜索，可以保持核心交易路径，但用户体验会下降。

Reliability 设计应区分 Critical 与 Non-critical Capability，不应所有组件使用相同等级。

## 五、Security 权衡

Security 不是可以任意牺牲的可选项，尤其是法律和合规要求。但不同控制方式仍存在权衡。

示例：

- MFA 提升 Account Security，但增加登录摩擦。
- 全量 Audit Log 提升追溯能力，但增加 Storage Cost 和隐私风险。
- Network Isolation 降低攻击面，但增加连接和运维复杂度。
- 数据加密提升保护能力，但需要 Key Management 和 Rotation。
- 极短 Token Lifetime 减少泄露影响，但增加 Refresh Traffic 与用户中断风险。

更成熟的方法是 Risk-based Security：根据 Asset、Threat、Impact 和 Likelihood 选择控制，而不是简单追求最多控制。

## 六、Cost 权衡

成本不仅是 AWS 账单，还包括 Total Cost of Ownership：

```text
TCO = Infrastructure + License + Engineering + Operations
    + Security/Compliance + Migration + Opportunity Cost
```

自建 Kafka 看起来没有 License Fee，但需要专业人员、升级、监控、容量管理和 Incident Response。

常见成本策略：

- Managed Service 换取更低运维负担。
- Reserved/Savings Plans 换取使用承诺。
- Spot Instance 换取中断风险。
- Cold Storage 换取更高读取延迟。
- Single Region 换取更低 Disaster Recovery 能力。

成本优化不能破坏明确的 SLO 和 Compliance Requirement。

## 七、Delivery Speed 权衡

快速交付的合理方式包括：

- 缩小 Scope。
- 使用 Managed Service。
- 先采用 Modular Monolith。
- 复用成熟 Platform 和 Golden Path。
- 通过 Feature Flag 分阶段发布。
- 延后非关键的自动化，但记录退出条件。

危险方式包括：

- 跳过身份鉴权。
- 不做 Backup。
- 没有最基本的 Test 和 Observability。
- 接受无法恢复的数据损坏风险。
- 产生无 Owner、无期限的“临时代码”。

Time to Market 很重要，但必须明确哪些 Guardrail 不可跨越。

## 八、可逆决策与不可逆决策

可以使用 Two-way Door / One-way Door 思维：

- Two-way Door：容易撤销，快速试验即可。例如内部 Library、UI Framework 的局部使用。
- One-way Door：撤销昂贵，需要更多分析。例如数据模型、Public API、Vendor Contract、跨区域数据策略。

不要用相同流程处理所有决策。可逆决策应该去中心化和快速完成；高成本不可逆决策需要更多 Evidence、Review 和 ADR。

## 九、方案比较矩阵

假设在 MVP 中选择 ECS Fargate 或 EKS：

| Criterion | Weight | ECS Fargate | EKS |
| --- | ---: | ---: | ---: |
| 12 周内交付 | 5 | 5 | 2 |
| 团队现有技能 | 4 | 4 | 2 |
| 复杂 Workload 支持 | 3 | 3 | 5 |
| Portability | 2 | 2 | 5 |
| 运维成本 | 4 | 4 | 2 |

评分只是讨论工具，不能代替判断。更重要的是把 Driver 和 Assumption 暴露出来。

## 十、风险与实验

当关键信息未知时，不要通过争论假装确定。可以设计 Spike 或 Proof of Concept：

- Load Test 验证数据库吞吐量。
- Chaos Test 验证 Failover Time。
- Security Review 验证权限模型。
- Cost Model 比较 Managed 与 Self-hosted。
- 用户实验验证额外认证步骤的影响。

实验必须有明确问题、时间盒和成功标准，否则容易演变为无期限原型。

## 十一、场景示例：全球 SaaS

需求：12 周上线，初期 2,000 客户，未来支持全球部署。

可能决策：

1. 初期使用 Single Region Multi-AZ，而非立即 Active-Active。
2. 使用 Modular Monolith，内部按 Domain 分界。
3. 使用 RDS、ECS Fargate 等 Managed Service 加快交付。
4. 为 Tenant 和 Region 信息预留清晰数据边界。
5. 跨 Region Backup 并演练 Restore。
6. 达到付费客户或 SLA Trigger 后再建设 Multi-region。

这不是忽略未来，而是用可演进设计控制当前成本和交付风险。

## 十二、面试表达模板

```text
我优先考虑的 Driver 是 A 和 B，因为它们直接关联业务目标。
方案 X 能提供……，但代价是……。
方案 Y 在……方面较弱，却更符合当前团队和 Deadline。
因此第一阶段选择 Y，同时通过……降低风险。
当指标达到……时，我们重新评估并迁移到 X。
这个决策会记录在 ADR，并用……验证假设。
```

## 十三、常见错误

- 声称方案只有优点，没有代价。
- 在没有指标时追求极致 Scalability。
- 用复杂 Technology 展示知识，而不是解决问题。
- 只计算 Infrastructure Cost，不计算人员与运维成本。
- 把 Security 当作上线前最后一步。
- 说“以后再优化”，却没有 Trigger、Owner 和演进路径。

## 十四、自测题

1. Cache 在性能、一致性和成本上分别有什么影响？
2. Managed Service 如何影响 Delivery Speed 和 TCO？
3. 什么是 One-way Door Decision？
4. 如何在 99.9% 和 99.99% Availability 之间做选择？
5. 如何让“先做简单方案”不变成永久技术债？

## 十五、总结

- 架构是受约束的多目标优化问题。
- 决策必须从业务目标、NFR、团队和预算出发。
- 每项收益通常对应复杂度、成本或风险。
- 对不可逆决策投入更多分析，对可逆决策快速实验。
- 清楚记录 Assumption、Consequence、Mitigation 和 Revisit Trigger，才能支持长期演进。
