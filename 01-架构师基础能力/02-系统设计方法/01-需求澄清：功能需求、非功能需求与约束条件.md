# 01. 需求澄清：功能需求、非功能需求与约束条件

## 学习目标

1. 区分 Functional Requirement、Non-functional Requirement 与 Constraint。
2. 在系统设计面试开始阶段快速缩小问题范围。
3. 把“高并发、实时、高可用”等模糊表达转化为可验证指标。
4. 识别 Stakeholder、核心 Use Case、优先级和隐含假设。

## 一、为什么先澄清需求

系统设计不是根据题目中的几个名词立即画图。相同的“设计一个聊天系统”，可能是 100 人使用的企业工具，也可能是支持数亿用户的全球平台，两者架构完全不同。

架构师首先要确认：

- 我们解决谁的问题？
- 最重要的 User Journey 是什么？
- 系统规模和质量目标是什么？
- 有哪些不能改变的限制？
- 哪些内容明确不在本次范围内？

澄清需求的目的不是拖延，而是建立可共同验证的 Design Target。

## 二、Functional Requirement

Functional Requirement 描述系统必须提供的业务行为，即“系统做什么”。

以短链接系统为例：

- 用户提交长 URL，系统生成短 URL。
- 访问短 URL 时重定向到原始 URL。
- 用户可以设置过期时间。
- 管理员可以禁用恶意链接。
- 系统记录点击统计。

面试时间有限，应区分：

- Must-have：本轮设计必须覆盖。
- Should-have：时间允许时讨论。
- Out of scope：明确不设计。

可以对面试官说：

> 我先聚焦创建短链接和重定向两个核心 Use Case，Analytics 只保留 Event 接口，稍后有时间再展开。

这体现 Scope Management，而不是遗漏需求。

## 三、Non-functional Requirement

Non-functional Requirement（NFR）描述系统“运行得怎么样”。常见维度包括：

- Availability：例如 99.95%。
- Latency：例如 Redirect API P99 小于 100 ms。
- Throughput：例如 Peak 50,000 RPS。
- Durability：已创建链接不能丢失。
- Consistency：新链接生成后是否必须立即可访问。
- Scalability：未来三年增长预期。
- Security：认证、授权、加密和审计。
- Compliance：GDPR、PCI DSS、数据驻留。
- Maintainability：发布频率、恢复效率和技术约束。
- Cost：预算或单次请求成本目标。

“系统应该很快”不是有效 NFR。更好的表达是：

```text
Redirect API: P95 < 50 ms, P99 < 100 ms
Create API: P95 < 300 ms
Availability: 99.99% for redirects
Data durability: 99.999999999%
```

NFR 会直接影响架构。例如 99.9% 和 99.999% Availability 的设计与成本差异很大。

## 四、Constraint

Constraint 是方案必须遵守的边界，而不是希望优化的目标。

常见 Constraint：

- 必须部署在 AWS。
- Backend 必须使用 Java。
- 数据必须留在 EU Region。
- 必须兼容现有 SAP 和 Identity Provider。
- 项目必须在三个月内上线。
- 团队只有 6 名工程师。
- 不允许使用某类 Open Source License。
- 预算上限固定。

Constraint 可能导致理论上最优的技术方案不再适用。架构师不能只优化技术，还必须在真实环境中交付。

## 五、Stakeholder 与质量属性

不同 Stakeholder 对系统的关注不同：

| Stakeholder | 典型关注点 |
| --- | --- |
| End User | 响应速度、易用性、可靠性 |
| Product | Feature、上线时间、转化率 |
| Engineering | 可维护性、测试、开发效率 |
| Operations | 可观测性、恢复、自动化 |
| Security | 权限、攻击面、审计 |
| Finance | Cloud Cost、License、ROI |
| Legal | 隐私、数据驻留、保留策略 |

NFR 经常互相冲突。例如 Security 要求增加检查，可能提高 Latency；Finance 希望降低冗余，可能降低 Availability。架构师需要让这种冲突显式化。

## 六、需求澄清问题清单

### 6.1 用户与业务

- 谁是主要用户？是否有不同角色？
- 最重要的三条 User Journey 是什么？
- 成功如何衡量？
- 哪些失败是业务不可接受的？

### 6.2 规模

- DAU、MAU 和并发用户是多少？
- 平均与 Peak RPS 是多少？
- 读写比例如何？
- 数据保存多久，每条记录多大？
- 增长率和季节性峰值是多少？

### 6.3 质量

- Latency 目标看 P50、P95 还是 P99？
- Availability 目标是多少？
- 能否接受 Eventual Consistency？
- RTO 和 RPO 是多少？
- 哪些操作必须 Idempotent？

### 6.4 安全与合规

- 数据是否包含 PII、Payment 或 Health Data？
- 谁可以访问什么？
- 是否需要 Audit Trail？
- 是否有 Data Residency 和 Retention 要求？

### 6.5 范围与约束

- 本轮设计明确不包含什么？
- 是否必须复用现有系统？
- 团队技能和交付期限是什么？
- Build、Buy 或 Managed Service 是否有限制？

## 七、管理假设

面试官不一定提供全部信息。可以做合理假设，但必须说出来：

> 如果没有额外限制，我假设读写比例是 100:1，链接创建后允许 1 秒内传播到所有 Region，但同一用户必须立即读到自己的写入。

显式假设具有三个价值：

1. 面试官可以及时纠正。
2. 后续架构决策有可追溯依据。
3. 避免不同人使用不同前提讨论。

真实项目中，可以维护 Assumption Log，并为高风险假设指定验证方法和 Owner。

## 八、需求冲突与优先级

常见冲突包括：

- Strong Consistency 与低 Latency。
- 高 Availability 与低 Cost。
- 快速交付与长期 Extensibility。
- 严格 Security 与用户便利性。

可以使用 Quality Attribute Scenario 表达优先级：

```text
Source: 已登录用户
Stimulus: 在大促峰值提交订单
Environment: 单个 Availability Zone 故障
Artifact: Checkout Service
Response: 接受请求并防止重复订单
Measure: P99 < 800 ms，成功率 > 99.9%
```

这比“系统要高可用”更容易驱动设计和测试。

## 九、面试开场模板

```text
1. 我先确认核心用户和 Use Case。
2. 然后确认规模：用户数、RPS、读写比例和数据量。
3. 接着确认关键 NFR：Latency、Availability、Consistency、Durability。
4. 最后确认 Security、Compliance、预算和技术限制。
5. 我会列出假设和 Out-of-scope，再开始容量估算与高层设计。
```

整个阶段通常控制在 5 到 10 分钟，不应无限追问。

## 十、常见错误

- 没有澄清就直接画 Microservices。
- 只问 Feature，不问 NFR。
- 把 Technology Choice 当成 Requirement。
- 追问大量对架构没有影响的产品细节。
- 不说明假设，却在后面依赖这些假设。
- 试图满足所有质量属性的最高等级。
- 没有明确 Out-of-scope，导致设计失去重点。

## 十一、自测题

1. Functional Requirement 与 NFR 的区别是什么？
2. 为什么“高并发”不是合格的 NFR？
3. Constraint 如何改变技术选择？
4. 如何处理面试官无法提供的需求信息？
5. 写出一个完整的 Availability Quality Attribute Scenario。

## 十二、总结

- 系统设计从共同理解问题开始，而不是从画图开始。
- Functional Requirement 定义行为，NFR 定义质量，Constraint 定义边界。
- 模糊质量目标必须转化为可度量指标。
- 通过优先级、Out-of-scope 和显式假设控制设计范围。
- 好的需求澄清能让后续每个架构决策都有清晰依据。
