# 04. 安全、合规、隐私、审计与数据治理

## 学习目标

1. 将 Security、Privacy、Compliance 和 Governance 纳入架构起点。
2. 使用 Threat Modeling 识别风险与控制。
3. 理解 IAM、Encryption、Audit、Data Lifecycle 等关键能力。
4. 区分合规证明与真实安全能力。

## 一、Security by Design

Security 不是上线前添加 WAF 或做一次 Penetration Test。它应贯穿：

```text
Requirement -> Design -> Implementation -> CI/CD -> Runtime -> Incident Response
```

核心原则：

- Least Privilege。
- Defense in Depth。
- Zero Trust。
- Secure by Default。
- Fail Securely。
- Separation of Duties。
- Assume Breach。

## 二、Threat Modeling

Threat Modeling 的基本过程：

1. 画 Data Flow 和 Trust Boundary。
2. 识别 Asset、Actor 和 Entry Point。
3. 分析 Threat。
4. 评估 Likelihood 与 Impact。
5. 设计 Mitigation。
6. 记录 Residual Risk 和 Owner。

STRIDE 是常用检查框架：

- Spoofing：身份冒充。
- Tampering：数据篡改。
- Repudiation：否认操作。
- Information Disclosure：信息泄露。
- Denial of Service：拒绝服务。
- Elevation of Privilege：权限提升。

Threat Model 应聚焦高风险路径，如 Login、Payment、Admin、File Upload 和 AI Tool Calling。

## 三、Authentication 与 Authorization

- Authentication：你是谁？
- Authorization：你能做什么？

常见机制：

- OAuth 2.0 / OpenID Connect。
- MFA。
- RBAC、ABAC、ReBAC。
- Short-lived Token。
- Workload Identity。

Authorization 必须在可信 Backend 执行，不能只依赖 React 隐藏按钮。

需要防范：

- IDOR/BOLA：用户修改 ID 后访问他人资源。
- Tenant Boundary Bypass。
- Privilege Escalation。
- Confused Deputy。
- 长期 Access Key 泄露。

## 四、数据分类

建立统一分类，例如：

| Level | 示例 | 典型控制 |
| --- | --- | --- |
| Public | 公开产品信息 | 完整性保护 |
| Internal | 内部文档 | 员工身份访问 |
| Confidential | 客户合同、PII | 加密、最小权限、审计 |
| Restricted | 支付、密钥、健康数据 | 强隔离、严格审批、Tokenization |

数据分类决定：

- 存储位置。
- 加密要求。
- Access Review。
- Retention。
- Masking。
- Backup 与删除策略。

## 五、Encryption 与 Key Management

### 5.1 In Transit

使用 TLS，内部 Service 通信同样需要身份和加密。敏感场景可使用 mTLS。

### 5.2 At Rest

Database、Object Storage、Backup 和 Log 都应根据分类加密。

### 5.3 Key Management

需要设计：

- Key Ownership。
- Rotation。
- Access Policy。
- Separation of Key and Data。
- Revocation。
- Audit。
- Disaster Recovery。

加密不是终点。如果 Application Role 可以读取全部明文数据，攻击者获得该 Role 后仍能访问。

## 六、Secret Management

Secret 不应存在于 Source Code、Docker Image、普通配置文件或 Log。

使用 Secret Manager 和 Workload Identity，并做到：

- Short-lived Credential。
- 自动 Rotation。
- Environment Isolation。
- Access Audit。
- 禁止开发者共享生产凭证。
- CI 使用 OIDC 等临时身份，而非长期 Cloud Key。

## 七、Privacy by Design

隐私不只是加密。关键原则包括：

- Data Minimization：只收集必要数据。
- Purpose Limitation：只用于声明目的。
- Consent 与合法处理依据。
- Retention Limitation。
- Right to Access/Correction/Deletion。
- Pseudonymization/Anonymization。
- Data Residency 与跨境传输控制。

删除请求需要覆盖 Primary Database、Search Index、Cache、Data Lake、Backup Retention 和下游 Processor。必须设计可追踪的数据血缘。

## 八、Audit Trail

Audit Log 应回答：

- Who 做了什么？
- 对哪个 Resource？
- 何时、从哪里？
- 之前和之后的关键状态是什么？
- 操作是否成功？
- 使用了哪个身份和权限？

Audit Log 应防篡改、访问受限、保留期明确。避免记录 Password、Token、完整 Card Number 等 Secret。

普通 Debug Log 不能自动成为合格 Audit Trail，因为它可能缺字段、可被修改或保留期不符合要求。

## 九、Compliance

常见框架或法规包括 GDPR、PCI DSS、SOC 2、ISO 27001 等。架构师需要理解适用范围，但应与 Legal、Privacy、Security 专家共同工作。

重要区别：

- Compliance 是满足特定控制和证据要求。
- Security 是持续管理真实风险。

通过审计不表示系统不会被攻击；安全设计也必须能够产生可验证 Evidence。

Evidence 可以包括：

- Access Review 记录。
- CI Security Scan。
- Change Approval。
- Backup Restore Test。
- Incident Exercise。
- Cloud Configuration Report。

## 十、Data Governance

Data Governance 解决数据的 Ownership、Quality、Lineage、Access 和 Lifecycle。

关键问题：

- 谁是 Data Owner 和 Steward？
- 哪个系统是 Source of Truth？
- 数据定义是否一致？
- 数据从哪里来、流向哪里？
- 谁能访问，为什么？
- 保存多久，何时删除？
- Quality 问题如何发现和处理？

在 Event-driven 和 AI 系统中，Lineage 尤其重要，因为数据会被复制到 Kafka、Lake、Vector Database 和 Training/Evaluation Dataset。

## 十一、Secure SDLC

典型 Pipeline Control：

- Code Review。
- SAST。
- Dependency/SCA Scan。
- Secret Scan。
- Container Scan。
- IaC Scan。
- DAST。
- SBOM 与 Artifact Signing。
- Deployment Policy。

发现漏洞后需要 Risk-based Triage 和 Remediation SLA，不能只生成无人处理的报告。

## 十二、Incident Response

安全事件准备包括：

- Detection 和 Alert。
- Incident Role 与 Escalation。
- Credential Revocation。
- Evidence Preservation。
- Containment。
- Customer/Regulator Notification Process。
- Recovery。
- Post-incident Improvement。

Runbook 和 Tabletop Exercise 可以显著降低真实事件中的混乱。

## 十三、常见错误

- 只在 Network Perimeter 做安全控制。
- 把 Authentication 当成 Authorization。
- 在 Log 中记录 PII 和 Token。
- 使用共享管理员账号。
- 只加密数据却不治理 Key Access。
- 不知道敏感数据复制到了哪些下游。
- 把“通过合规审计”等同于“系统安全”。
- 所有控制都依赖人工流程，无法持续验证。

## 十四、自测题

1. STRIDE 的六类威胁是什么？
2. RBAC 与 ABAC 的差别是什么？
3. 为什么 React 隐藏按钮不能作为 Authorization？
4. Audit Log 与普通 Application Log 有什么区别？
5. 删除 PII 为什么需要 Data Lineage？

## 十五、总结

- Security、Privacy 和 Compliance 必须进入 Requirement 与 Architecture。
- Threat Modeling 用系统化方法识别 Asset、Trust Boundary 和风险。
- Identity、Least Privilege、Encryption、Secret Management 和 Audit 是基础能力。
- Data Governance 明确 Ownership、Lineage、Quality 和 Lifecycle。
- 控制必须自动化、可验证，并配合持续的 Incident Response 与演练。
