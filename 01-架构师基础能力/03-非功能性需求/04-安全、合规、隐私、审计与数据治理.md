# 04. 安全、合规、隐私、审计与数据治理

## 一、安全必须成为业务设计的一部分

安全（Security）保护机密性、完整性与可用性；隐私（Privacy）关注个人信息为何、如何以及在什么范围被处理；合规（Compliance）是满足适用义务与证据要求；数据治理（Data Governance）明确数据责任、定义、质量、流向和生命周期。它们互相支持，却不能用“数据库已加密”或“通过一次审计”互相替代。

本章使用**虚构多租户订单与文档分析平台**：顾客查订单，客服协助退款，用户上传文档，后台可能调用 AI 工具。案例、角色和测试均为教学设计，不代表用户项目。本文解释架构与工程机制；具体法规适用、处理依据、保留与通知义务由组织的法务、隐私和安全负责人结合事实确认。

### 1.1 Security by Design 的落地顺序

需求阶段识别敏感资产与不可接受结果，例如跨租户泄露、未授权退款、秘密进入日志；设计阶段明确身份、信任边界和数据流；实现阶段落实可信校验；CI/CD 检查代码与供应链；运行阶段监控权限与异常；事件后完成隔离、恢复与改进。上线前加 WAF（Web Application Firewall，Web 应用防火墙）或做一次渗透测试只能补充，不能修复缺失的数据所有权和授权模型。

最小权限（Least Privilege）限制身份只能执行当前任务需要的操作、资源与时间。纵深防御（Defense in Depth）让应用授权、数据库权限、网络和审计相互补充，但不能把多层同一错误策略当独立保护。默认安全（Secure by Default）要求新资源默认不可公开，例外必须显式启用。

Zero Trust（零信任）不依据“来自内网”自动信任，每次敏感访问都需要可验证身份与策略。Fail Securely（安全失败）要求授权信息缺失或校验异常时不放行高风险动作。职责分离（Separation of Duties）避免同一人无审查地申请、批准并执行高风险变更；Assume Breach（假设已入侵）进一步检查一个身份被控制后能扩散到哪里、怎样发现和限制。

这些原则不是要求所有请求执行最重审批。公开商品读取与管理员批量导出应采用不同强度，目标是风险相称、能持续运行和验证的控制，避免为了复杂而导致团队绕过流程。

## 二、Threat Modeling：从数据流找到可利用的路径

### 2.1 资产、入口、信任边界与风险记录

威胁建模（Threat Modeling）先画数据从浏览器到 API、数据库、对象存储、事件平台和外部处理器的流向。信任边界是身份或权限假设改变的位置，不等于防火墙位置：浏览器代码属于本系统，也仍可被用户修改；内部 Worker 也不应拥有任意租户管理员能力。

识别资产（订单、凭证、文档、密钥）、参与者（用户、客服、服务账号、攻击者）和入口（登录、上传、回调、管理接口）。再按可行攻击路径评估发生条件与影响，选择缓解，并记录剩余风险（Residual Risk）、Owner、期限和验证。没有证据时用情景和区间，不伪造精确攻击概率。

| 场景 | 威胁与前提 | 控制与剩余风险 |
| --- | --- | --- |
| 顾客改 orderId | 已登录但能猜到他人资源 | 每次校验租户与归属，负向测试；仍检查导出与缓存路径 |
| 客服退款 | 客服身份被盗或权限过宽 | 金额范围、临时授权、必要复核与审计；审批者也需独立保护 |
| 上传文档 | 恶意内容或超大压缩包 | 隔离解析、大小与解压预算、恶意文件检查；扫描不是绝对无害证明 |
| AI 工具调用 | 文档指令诱导读取别租户资料 | 文档按不可信数据处理，工具按用户权限重新授权；模型判断不代替权限 |
| 支付回调 | 伪造、重放或错配交易 | 验签、业务身份/金额核对、幂等；来源可信不表示内容符合本单条件 |

模型随新入口、第三方、权限或数据用途变化更新。只在项目开始开一次会，后面新增批量导出却不复查，控制很快失效。

### 2.2 STRIDE 的六类威胁与工程问题

STRIDE 是检查提示，不是自动风险评分，也不保证覆盖全部业务滥用。

| 类别 | 含义 | 在案例中怎样检查 |
| --- | --- | --- |
| Spoofing | 冒充身份 | 伪造令牌、假回调、共享账号是否可被识别 |
| Tampering | 篡改数据 | 客户端改总价、事件改金额是否被校验 |
| Repudiation | 否认操作 | 能否关联退款人、审批、结果和策略版本 |
| Information Disclosure | 信息泄露 | 错误、日志、缓存、搜索是否跨租户暴露 |
| Denial of Service | 拒绝服务 | 导出、上传、解压、工具循环是否耗尽资源 |
| Elevation of Privilege | 权限提升 | 普通账号是否能修改角色或调用管理路径 |

登录、支付、管理、上传和 AI 工具调用优先展开。还需考虑合法功能被滥用，例如批量查询和优惠券刷取，不能只找传统注入字符串。风险排序同时考虑暴露面、可达性与业务损失，不能仅凭漏洞名称决定优先级。

## 三、身份认证与资源授权

### 3.1 OAuth、OIDC、MFA 与工作负载身份

Authentication（认证）回答是谁，Authorization（授权）回答这个身份对这项资源能做什么。OAuth 2.0 处理委托访问授权，OpenID Connect（OIDC）在其上增加终端用户身份层。ID Token 面向登录客户端的身份验证，Access Token 用于访问相应资源；不能把任意有效 ID Token 当通用 API 通行证。

按 OAuth 安全最佳实践设计流程，公开客户端不能安全保存固定 client secret；采用适合的授权码与 PKCE（Proof Key for Code Exchange，授权码兑换证明密钥）等机制并校验重定向。PKCE 将授权码兑换绑定到发起者持有的验证材料，不能代替资源权限。令牌验证还需检查可信签发者、受众、有效期、允许的算法与相应上下文，不能只做 Base64 解码。

MFA（多因素认证）让登录不仅依靠一个秘密，但账户恢复、会话盗取和审批路径仍需保护。短期 Token 降低部分泄露窗口，也增加刷新与撤销设计成本；高风险操作可要求近期认证和额外确认，但每次仍要资源授权。

Workload Identity（工作负载身份）让服务或 CI 以可验证运行身份换取受限短期凭证，替代复制长期云密钥。信任策略绑定具体工作负载、仓库、分支或环境等已验证声明，不能只看到 OIDC 签名有效就把所有流水线都当生产发布者。

### 3.2 RBAC、ABAC、ReBAC 怎样组合

RBAC（Role-Based Access Control）按角色授予能力，适合“客服能处理退款”这种岗位分工，但只有角色不够表达“只能处理本租户、未发货、限额内订单”。ABAC（Attribute-Based Access Control）结合主体、资源、动作和环境属性，例如租户、金额、时间与认证强度；属性必须来自可信源。

ReBAC（Relationship-Based Access Control）依据关系，如文档所有者、项目成员或被授权协作者。它适合共享协作，但关系变更和缓存失效必须及时生效。多种模型可以组合，不需要为所有简单场景引入复杂独立策略平台；平台化收益来自一致执行、可解释与可测试，而非缩写数量。

后端是最终可信执行点。React 隐藏按钮只改善界面，调用者可直接发 HTTP 请求。所有入口，包括批量导出、后台重试、下载链接和内部 API，都需要一致授权。策略缓存减少远程调用却引入撤销窗口，必须与风险和时效要求匹配。

### 3.3 BOLA、租户边界与 Confused Deputy

IDOR（Insecure Direct Object Reference，不安全直接对象引用）和 BOLA（Broken Object Level Authorization，对象级授权失效）描述相关越权问题，例如通过修改对象引用访问无权资源；UUID 难猜只能降低发现概率，不能代替授权。租户 ID 应由已验证会话/成员关系确定，不能直接相信请求体的 tenantId。数据库查询带租户条件、缓存键包含租户和权限范围、对象下载校验归属，避免在其他路径绕过。

Confused Deputy（混淆代理）指高权限服务被低权限调用者诱导，借服务自己的权限访问本来不允许的资源。比如 AI 工具接受任意对象存储 URL 并用平台管理员身份下载。正确做法是解析受控资源标识、验证原调用者权限、限制工具动作与网络出口，而非因为“服务有密钥”就执行。

修改时还要注意 TOCTOU（检查与使用之间的竞态）：先确认用户是管理员，随后角色已撤销但任务仍继续执行。高风险执行前重校验，或使用短期受限授权与策略版本，并明确已开始事务与外部副作用的处理边界。不能承诺所有撤销瞬间自动取消已完成动作。

### 3.4 可执行的最小授权模型

以下 Python 模型说明可信主体、资源归属与默认拒绝，限定读取和取消；它不验证 Token，调用前必须已经完成认证。

~~~python
def allowed(subject, action, order):
    if not subject.get("authenticated"):
        return False
    if not subject.get("active"):
        return False
    if not subject.get("tenant") or not order.get("tenant"):
        return False
    if subject.get("tenant") != order.get("tenant"):
        return False
    if action == "read":
        return (subject["id"] == order["owner"]
                or "support_read" in subject.get("roles", set()))
    if action == "cancel":
        return (subject["id"] == order["owner"]
                and order["status"] in {"PENDING", "CONFIRMED"})
    return False
~~~

客服读取权限不自动授予取消或退款权限。未知动作默认拒绝。生产必须校验属性完整性、可信来源，并将状态条件更新与业务写入原子关联；上面函数的成功不能防止检查后订单被发货。集成测试要直接调用后端，不能只测试界面按钮是否隐藏。

## 四、数据分类与责任：控制强度有依据

| 分类示例 | 内容 | 控制设计重点 |
| --- | --- | --- |
| Public | 已批准公开的产品信息 | 防篡改、发布审批与可用性 |
| Internal | 内部工程文档 | 员工身份、用途与外发限制 |
| Confidential | 客户合同、个人信息 | 最小访问、加密、审计与生命周期 |
| Restricted | 密钥、支付或高敏感健康资料 | 强隔离、专门权限、最小化与严格操作流程 |

这些是组织可采用的分类示例，不是法规统一命名；PII（可识别个人的信息）和健康等数据的法律分类需另确认。分类决定存储位置、访问复核、脱敏、备份、保留和删除，而不只是贴标签。

Data Owner 对业务定义、用途和风险负责，Data Steward 负责日常质量、目录和规则协调，技术保管者执行平台控制。写清谁能批准新用途、谁处理质量错误、谁执行删除；“安全团队负责所有数据”通常会造成业务责任真空。

分类会随组合改变：公开数据与内部标识关联后可能揭示个人，日志加入 IP 与身份后也可能敏感。派生到搜索、数据湖或向量库不等于自动降低等级；新输出继承适当控制并重新评估。

## 五、加密与 Key Management

### 5.1 传输、静态与应用访问的区别

TLS（Transport Layer Security，传输层安全协议）提供链路加密与端点认证能力，必须正确验证证书和身份。内部服务也不能因在私网就跳过身份；敏感场景可用 mTLS（双向 TLS）让双方出示证书，但证书证明工作负载身份，不自动允许读取任意租户数据。

静态加密覆盖数据库、对象、备份和日志介质，降低介质或副本泄露的部分风险。应用角色若能读取所有明文，被攻陷后仍可能批量导出；应缩权限、限制出口与查询规模，并对敏感字段采用额外隔离或令牌化。

Tokenization（令牌化）以替代标识引用真实敏感值，映射库本身需要更严格保护。掩码只是展示截断，不一定删除底层原值。密码存储需要适当的专用密码哈希机制，不能为了可逆找回而当普通字段加密保存。

### 5.2 密钥生命周期与恢复

密钥管理包括生成、归属、访问策略、轮换、撤销、审计和灾备。常见信封加密把数据用数据密钥加密，再用主密钥保护数据密钥，降低直接接触主密钥的范围；实际采用成熟 KMS/库，不自行设计密码协议。

轮换可能只改变新加密使用的密钥版本，旧数据是否重加密要按产品机制与风险决定。误删密钥可能让保留期内所有备份不可恢复，撤销与删除需审批、延迟保护和恢复测试。密钥权限与数据权限分离能降低单点失陷，但若同一个管理员仍可自行获取两边所有权，隔离效果有限。

密钥服务故障时先查业务是否可以使用受控短期缓存，不对高风险数据无条件明文降级。验证恢复账号能访问正确版本的密钥，也验证无关环境无权解密。加密控制必须在正常、故障与恢复三条路径都成立。

## 六、Secret Management 与 CI 身份

Secret 不应写进源码、镜像层、普通共享配置或日志。容器镜像里删除一个文件不保证旧层没有内容；密钥提交后从最新文件删掉也不代表历史与制品没有副本。发现暴露先撤销/轮换并评估使用痕迹，再按流程清理历史。

使用秘密管理服务、短期凭证和环境隔离，按工作负载授予最小读取权限。自动轮换需支持新旧凭证过渡、验证与回退，避免同步更新一边导致全站认证失败。定期访问审计，生产凭证不能成为开发群共享资料。

CI OIDC 信任策略应约束可信签发者、受众和具体项目/环境，发布角色只允许相应制品与资源。来自不可信 PR 的代码不应获得生产秘密，即使流水线文件本身受信。运行身份、构建身份和发布身份分开，降低供应链入侵扩散。

## 七、Privacy by Design 与数据生命周期

### 7.1 处理目的与个人权利

隐私不仅是保密：应明确目的、最少收集、适用处理依据、保留期限与访问/更正/删除流程。Consent（同意）只是可能的依据之一，不能对所有处理都默认套同意。GDPR 的具体适用、特殊数据条件与例外由负责方确认；删除权存在适用条件和例外，不能承诺所有数据一律立刻物理删除。

假名化（Pseudonymization）用受控标识替换身份，但可能借额外信息重新关联；匿名化（Anonymization）则需评估是否仍可合理识别。普通邮箱哈希可能被枚举，不自动成为匿名数据。数据驻留与跨境传输也不是同一概念，区域选择不能独自证明全部处理路径合法。

### 7.2 可追踪删除的工程流程

本案例为每个主体维护数据集与处理器清单：主库、搜索、缓存、事件、数据湖、向量库、评测/训练数据和备份。删除请求先认证请求人并确认范围与保留例外，产生稳定任务身份，分别向各数据集发送最小必要删除操作；各方返回结果并允许重试，对未完成项告警。

删除与新写入并发时，需要主体状态/版本或删除标记阻止旧事件重新创建个人资料；消费者和重建任务也要识别该标记。只删除当前搜索文档但让历史事件重放重建，属于流程未闭环。删除标记本身也有最小化、访问与保留要求。

备份可能依既定保留与隔离政策过期，不能随意修改不可变备份；恢复流程必须在重新对外服务前应用仍有效的删除/限制记录，避免被删除资料复活。是否可如此处理及哪些记录需保留，由相应负责方确认，架构应提供可执行证据。

### 7.3 AI 与事件系统的特殊扩散

文档切片、Embedding（向量表示）、索引、提示日志和评测样本都是潜在数据副本。删除原文不意味着向量和上下文缓存消失，权限变化也要传播到检索过滤与结果输出。检索前后都检查授权，避免用不可信过滤参数跨租户搜索。

训练后的模型不一定支持按一条样本直接删除影响，因此是否允许把敏感数据送入训练必须在进入前确定，记录数据来源、许可、用途和供应商政策。不要把“事后能删原文件”当作可撤销所有派生影响的保证。

## 八、Audit Trail：能解释、可信且最小化

### 8.1 一条审计记录要证明什么

审计需要关联谁以何种身份和权限、何时、从何可信入口、对哪个资源执行何动作、结果与重要状态变化。示例不含原始文档、密码或 Token：

~~~json
{
  "eventId": "audit_demo_1",
  "occurredAt": "2026-11-19T06:30:00Z",
  "actorId": "support_7",
  "actorType": "human",
  "tenantId": "tenant_a",
  "action": "refund.request",
  "resourceId": "order_42",
  "policyVersion": "refund-policy-3",
  "decision": "deny",
  "reasonCode": "AMOUNT_EXCEEDS_LIMIT",
  "traceId": "trace_demo_1"
}
~~~

前后状态只保存解释所需差异，避免复制完整敏感对象。来源 IP 或设备信息如确有用途也受最小化和保留约束。客户端传入的 actorId 不可信，必须由已认证上下文产生；时间同步和事件排序影响调查，要区分发生时间与接收时间。

### 8.2 防篡改与失败语义

审计记录写入受限的追加存储，生产应用不应拥有删除历史权限；集中导出、保留锁、完整性验证和访问审计组合降低篡改风险。哈希链可帮助发现修改，但攻击者若能重写整链且没有独立锚点，不能凭“用了哈希”声称绝对防篡改。

关键业务写入与审计意图可通过同一事务的 Outbox（事务发件箱）可靠关联：业务表与待投递事件在同一数据库事务提交，后台读取事件发送成功后标记，崩溃重试可能重复发送，但不依赖数据库与远端日志服务同时成功。再异步投递审计平台；重复用 eventId 去重，缺失以序列或业务对账检测。若审计平台不可用，明确哪些操作允许受保护缓冲、哪些高风险动作必须暂停，队列满后怎样告警与阻止继续丢证据。

普通 Debug Log 可能被采样、覆盖或修改，字段和期限也不稳定，不能自动充当合格审计。日志也可能遭注入，应结构化编码、限制长度，避免把换行和控制字符解释为伪造事件。审计平台同样是敏感资产，不可为排障向所有开发者开放。

## 九、Compliance：适用范围与可验证证据

GDPR 是个人数据保护法规；PCI DSS 是支付卡数据安全标准；SOC 2 是相关控制的鉴证报告体系，不应称作政府颁发的通用安全认证；ISO/IEC 27001:2022 定义信息安全管理体系要求。四者性质与范围不同，不能把供应商一个证书当成本系统全部义务已转移。

先确认组织、服务、数据流和供应商边界，记录适用版本、评估周期与责任。即使采用托管支付或云服务，仍需核对自己负责的集成、访问和配置。审计报告关注指定期间或范围，报告有效不代表所有新变更都已被验证。

Evidence（证据）应可追溯到控制、资源、时间、执行者与结果，例如访问复核、扫描与修复、变更批准、备份恢复、事件演练和配置报告。只截图一个绿色扫描页，无法证明覆盖了正确版本或发现项已处理。安全管理实际风险，合规要求可证明的控制；二者要同时成立。

## 十、Data Governance：数据可靠且有人负责

数据治理覆盖 Ownership、Quality、Lineage、Access 和 Lifecycle。Source of Truth（权威源）是某项事实的指定负责系统，不意味着一个库自然拥有所有事实；订单状态与供应商支付事实可能需要对账关联。统一术语、单位和字段定义，避免财务“成功”与技术“已接单”混用。

数据质量可检查完整性、唯一性、合法范围、引用关系、新鲜度和对账差异。异常数据进入隔离与修复流程，不悄悄截断后继续算报表。质量规则有 Owner 与版本，修复需保留来由，不能让数据工程师无审计改资金事实。

Lineage（血缘）记录源数据经哪些转换进入哪些输出和处理器。可用数据目录、稳定数据集 ID、作业版本与事件元数据维护，自动采集技术流向，再由业务补充目的和责任。Kafka、Lake、Vector Database、训练/评测集尤其易扩散，必须关联保留、权限与删除流程。

治理不是只采购目录工具。若没人批准新用途、没人修复质量问题或无人核验下游删除，目录再完整也不会执行。先覆盖敏感与关键数据，逐步自动化，以访问复核完成、删除积压、质量失败与血缘覆盖缺口衡量运作。

## 十一、Secure SDLC：从发现到修复闭环

Secure SDLC 是将安全实践嵌入软件生命周期。NIST SSDF 1.1 可作为组织实践框架，不是“运行这些工具就自动合规”的清单。

| 控制 | 主要发现什么 | 不能单独证明什么 |
| --- | --- | --- |
| Code Review / SAST | 人工设计缺陷、静态代码危险路径 | 不能穷尽运行配置与业务越权 |
| SCA / 依赖扫描 | 已知组件漏洞与许可风险 | 组件有漏洞不自动等于可达，未命中也不等于无风险 |
| Secret Scan | 可能的凭证泄露 | 删除扫描结果不撤销已暴露凭证 |
| Container / IaC Scan | 镜像组件、基础设施危险配置 | 不能证明线上无漂移或运行身份正确 |
| DAST | 运行接口的可观察弱点 | 未覆盖身份和状态路径可能漏业务漏洞 |
| SBOM / 签名 | 组件清单、制品来源和完整性验证 | 签名制品仍可能包含恶意或有漏洞代码 |
| Deployment Policy | 阻止不符合规则的制品或权限部署 | 策略本身错误仍会放行错误配置 |

SAST 是静态应用安全测试，DAST 是动态测试，SCA 是软件组成分析，IaC 是基础设施即代码，SBOM 是软件物料清单。制品签名必须在发布端验证可信签名者、来源与摘要，不能只“生成签名文件”而从不校验。

漏洞分流（Triage）综合严重性、暴露、可达性、资产与可用缓解，指定修复时限、Owner 与复测。风险接受有批准、期限和补偿控制，不是永久忽略。修复后重新构建、发布并确认运行版本，不能扫描报告关闭而生产仍旧。避免把大量误报变成团队手工负担，应校准规则但保留负向测试。

## 十二、Incident Response：限制损失并安全恢复

事件响应准备包括检测、分级、角色升级、凭证撤销、取证、遏制、通知、恢复和复盘。指定指挥、技术处置、证据、业务和隐私沟通角色；值班需要权限与受控手册，不能事故发生才寻找管理员账号。

凭证泄露场景先识别可用权限与活动范围，尽快撤销或限制受影响身份，并轮换相关秘密；同时按流程保留日志、时间线、制品与必要快照，控制证据访问与交接。不要为了清理痕迹盲目删除日志，也不要为无限收集证据放任攻击持续。

Containment（遏制）可限制出口、隔离工作负载、暂停高风险功能；恢复要使用可信制品、修补入口、重建权限并核对数据，而不是直接恢复已受污染镜像。通知客户或监管的触发、时限和内容交由既定法律/隐私流程判断，工程及时提供事实，不编造全行业统一通知规则。

桌面推演（Tabletop Exercise）验证谁决定、谁联系和如何取证，技术演练验证撤销、隔离、恢复和审计链真的可用。事后记录根因、影响、控制缺口、Owner 与期限，并复测；“提醒大家注意安全”不是系统性修复。

## 十三、面试完整回答与深入追问

### 13.1 主问题：怎样把安全与治理放进架构？

**示例回答：**“我先识别租户数据、支付与凭证等资产，沿登录、订单、上传和工具调用画数据流与信任边界，用 STRIDE 和业务滥用场景确定风险。身份使用成熟协议，后端对每个资源校验租户、归属和动作，服务与 CI 使用受限短期身份。数据分类决定存储、加密、审计与保留，密钥和数据权限分离并验证恢复。个人数据最小化，血缘覆盖搜索、事件、向量和评测副本，删除有状态、重试与恢复后防复活机制。SDLC 把扫描与修复、制品验证闭环，运行时有异常检测和演练。合规范围与专业负责人确认，证据关联具体版本与控制，不把一次审计当安全保证。”

**追问：这些控制是否拖慢交付？** 有维护和摩擦成本，可以用平台默认、权限模板与自动证据减少重复工作，并优先高风险路径；不能为赶日期跳过跨租户授权。若资源不足，缩功能与暴露范围，而非假装风险不存在。

### 13.2 追问：RBAC 已有客服角色，还会越权吗？

**回答：**“角色只给能力类别，不证明这个客服能访问该租户与订单。还要资源关系、金额范围、状态和审批条件；属性来自可信源，后端每条路径一致执行。批量导出和后台重试也受同样约束。”

**再追问：缓存策略怎样撤销？** 定义可接受撤销窗口，高风险执行前重校验或短期受限授权，缓存按主体、资源范围与策略版本隔离，权限服务故障不能默认放行。已经完成的外部动作另走补偿，不承诺时间倒流。

### 13.3 追问：数据已加密为什么仍会泄露？

**回答：**“加密保护链路或介质的特定风险，应用角色能解密全部数据时，角色被攻陷仍可导出。应限制资源权限、查询规模和出口，保护密钥并记录审计。备份、日志和派生数据也要同样治理。”

**再追问：把邮箱哈希能当匿名吗？** 不能自动认定。可枚举输入、其他属性关联和额外映射都可能重识别；需要评估识别风险与用途，不能仅看原文不在就宣布匿名。

### 13.4 追问：删主库记录为什么不够？

**回答：**“搜索、缓存、事件、湖和向量可能有副本，历史重放又会重建。先建立主体与数据集血缘，再以可追踪任务删除，处理并发新写与旧事件，恢复备份后应用仍有效的限制记录。保留例外由负责方确认，并保留最小完成证据。”

**再追问：审计不能删和隐私删除冲突怎么办？** 先在收集时最小化并定义用途和期限，避免审计复制原始个人载荷。具体保留与权利例外需确认，工程提供按目的隔离、访问限制和期限执行能力，不自行决定所有记录永留或全删。

## 十四、扫雷自测与完整答案

### 14.1 STRIDE 六类是什么，怎样使用？

身份冒充、篡改、否认操作、信息泄露、拒绝服务、权限提升。把它们沿入口和数据流逐项检查，例如回调验身份、订单金额防篡改、退款留审计、日志防泄露、上传限资源、角色变更防提权。框架提供提问，不自动代替业务风险与优先级判断。

### 14.2 RBAC 与 ABAC 的差别？

RBAC 用角色归纳能力，ABAC 用主体、资源、动作与环境属性表达上下文条件。客服能退款是角色，限本租户和额度是属性条件。两者可以组合，属性不可信或策略散落会使模型再复杂也无效。

### 14.3 React 隐藏按钮为何不是授权？

客户端可被修改，也可绕过页面直接请求 API。后端必须按可信身份验证每个资源与动作；隐藏按钮只反映界面能力提示。测试应直接构造跨租户和无权限调用，而不只截图按钮不可见。

### 14.4 Audit Log 与普通 Application Log 有何不同？

审计围绕责任、资源、权限、动作与结果，有明确完整性、访问和保留要求；调试日志面向排障，可能采样或滚动覆盖。审计还要处理投递失败和业务写入关联，且不能为了“全”记录密码、Token 和完整敏感载荷。

### 14.5 删除 PII 为什么需要 Lineage？

因为一个主体的数据可能派生到多个数据集和外部处理器。无血缘就无法确定范围、确认完成或防止重放复活。删除流程还要处理保留例外、备份恢复与并发新写，不是单条 DELETE 即完成。

### 14.6 mTLS 是否保证订单级权限？

不保证。它验证通信端点身份并保护链路，不判断某个用户对某张订单的权限。应用仍需租户与资源策略，服务自己有证书也不能成为借高权限代查任意资源的混淆代理。

### 14.7 Secret 从 Git 最新提交删除是否已解决？

未解决，历史、镜像、日志与缓存可能仍有副本，凭证也可能已被使用。先撤销轮换并调查权限与活动，再清理泄露副本和修复发布流程，不能只关闭扫描告警。

### 14.8 签名和 SBOM 能证明制品无漏洞吗？

不能。签名帮助验证完整性与来源，SBOM 列出组件，可信来源也可能构建有漏洞或恶意代码。需要验证签名策略、来源、扫描、审查与运行权限，修复还需部署生效。

### 14.9 授权服务超时直接放行是否合理？

对高风险资源不合理，无法确认不等于允许。可采用事先评估的受限缓存或公开内容降级，但要明确撤销窗口与适用范围；不能用可用性目标覆盖安全责任。

### 14.10 SOC 2、ISO 27001 是否等于不会被攻击？

不等于，它们关注相应范围与控制证明，系统与威胁持续变化。仍要跟踪新入口、配置、权限与漏洞，验证证据覆盖当前版本；合规证明和实际风险控制需要一起维护。
