# 02. 延迟、吞吐量、并发性与容量规划

## 一、先定义统计边界，再讨论容量

性能设计的目标是在约定负载和故障条件下，持续交付满足延迟、错误率和正确性要求的业务结果，而不是让压测图上的 RPS 最大。本章使用**虚构订单查询与任务处理系统**，所有容量、时间和资源数字均为教学假设，不是用户项目或产品基准。

### 1.1 四个量不能互换

延迟（Latency）是单个操作从指定起点到终点的时间；吞吐量（Throughput）是单位时间完成的工作；并发数（Concurrency）是同一时刻系统内尚未结束的操作数量；利用率（Utilization）是资源占用或忙碌程度。必须附单位和范围：RPS 是请求/秒，消息/秒不是字节/秒，一条请求可能执行多条 SQL。

连接数不等于正在执行的请求数。空闲长连接可能没有工作，一个 HTTP/2 连接也可以承载多个并发流；线程数不等于 CPU 同时执行数。内存占用率与 CPU 忙碌率更不是同一种利用率，不能统一以“70%”解释是否安全。

提高并发可以让 I/O 等待期间资源继续工作，但超过瓶颈后只会增加等待、上下文切换和内存。评估吞吐时至少区分发起量、到达量、接纳量、完成量和**正确成功完成量**。大量快速 503 使总响应数上升，不代表业务容量提高。

### 1.2 需求必须包含负载形状

“需要 10,000 RPS”还不完整。读写比例、分页大小、租户倾斜、缓存命中、单请求 CPU/IO、突发持续时间与可接受排队都影响容量。同样 100 RPS，一个是单键读取，另一个是导出百万行，成本可能完全不同。

先定义用户旅程和服务目标，例如“正常与单节点故障下，指定查询混合的 p99 小于 300ms，范围内请求错误率低于目标”。再确定安全容量与资源预算。面向管理者的容量计划还应解释何时需采购、扩容或减少范围，以及持续成本，而不是只列服务器数量。

## 二、端到端 Latency 与关键路径

### 2.1 分解时间，避免漏掉排队

一次调用可经历 DNS 查询、TCP/TLS 建连、网络传输、负载均衡等待、应用准入与线程排队、CPU 处理、连接池等待、数据库、下游 API、序列化和响应传输。连接复用时不会每次重新 DNS/TLS，缓存、连接生命周期和网络位置会改变占比，不能机械相加固定常数。

分布式追踪（Distributed Tracing）记录跨组件操作，结合应用剖析与数据库执行计划定位关键路径（Critical Path）。并行分支等待全部完成时，由最慢分支决定该阶段等待；串行依赖则依次占用时间。不要把同一网络等待同时计入父 Span 和子 Span 再相加，也不能把各服务 p99 相加就得到整体 p99。

教学例子：入口 10ms、CPU 20ms、并行数据库 40ms 与外部查询 80ms、返回 10ms，忽略其他等待时总计约 120ms，而不是 160ms。若外部调用必须等数据库结果才发起，才会变为约 160ms。优化前必须知道真正依赖关系，不能为了并行破坏授权、事务或数据前置条件。

### 2.2 Tail Latency 与 Fan-out

尾延迟（Tail Latency）是分布高分位处的体验，p99 表示约 99% 观测不超过该值，不是最大值。它比均值更能发现少数慢请求，但样本量、测量范围和失败处理必须一致。不能通过排除超时请求使尾部“变好”。

Fan-out 是一个请求分发到多个依赖。若每个分支在某阈值内完成的概率为 0.99，50 个分支独立且全部必须完成，至少一个超过阈值的概率约为 1-0.99^50，即 39.5%。独立是假设，实际共享数据库或网络会造成相关故障；这个算例说明放大机制，不是实际服务的预测值。

优先减少必须等待的依赖、合并重复查询、缩小返回范围。慢租户或昂贵查询应有资源隔离和成本配额，避免拖慢普通操作。缓存和 Request Coalescing（请求合并，让相同查询共享一次回源）减少重复工作，但需要陈旧边界、取消语义和容量限制，不能无条件用于不同用户权限数据。

### 2.3 Deadline 与 Hedged Request 的代价

Deadline 是整次操作的截止时间，向下游传递剩余预算，包含连接获取、排队、调用和重试。每层都用完整 1 秒超时，可能导致上游早已放弃、下游还继续消耗资源。超时应触发协作取消或后续结果处理，但取消不保证外部业务没执行；写请求仍需幂等和查询恢复。

Hedged Request（延迟发出的冗余请求）在原请求变慢后向另一副本补发，取可用结果，可能减少部分独立慢尾，却增加负载。只适用于可安全重复且成本受控的操作，设置延迟触发、额外请求预算与取消。写操作不能盲目双发；过载时加倍流量反而恶化尾部，副本共享瓶颈时收益也有限。

## 三、吞吐量由资源需求与最窄瓶颈决定

### 3.1 用每业务操作的需求换算

如果数据库安全处理 2,000 Query/s，每个 API 平均四次查询，无缓存且忽略其他限制，则该负载约受限于 500 API RPS，而不是 2,000 RPS。应用能接收 20,000 RPS 不能改变这一事实。先统一工作单位，再谈整链路上限。

CPU 也可用服务需求做粗估：每请求消耗 2ms CPU，4 核在理想 100% 下约 2,000 RPS；若目标 CPU 预算 60%，粗估 1,200 RPS。它尚未包含共享开销、调度、GC 与负载分布，不能代替实测。CPU 时间不是包含阻塞的墙钟延迟，两者混用会使估算失真。

网络用字节计算，磁盘区分吞吐 MB/s、IOPS 与单次延迟，存储还看增长与保留。小随机读受 IOPS 限制，大对象导出可能先占满带宽；“磁盘未满”不证明 I/O 有余量。

### 3.2 瓶颈证据与常见假象

| 候选瓶颈 | 典型证据 | 先排除的误判 |
| --- | --- | --- |
| CPU/节流 | 持续忙碌、运行队列、容器 throttling | 宿主 CPU 空闲不代表容器无配额限制 |
| GC/内存 | 停顿、分配速率、堆或原生内存增长 | 内存高不自动等于泄漏，缓存也会占用 |
| 数据库连接池 | 获取等待、活跃连接与事务时长 | 连接池满可能是慢查询或连接泄漏，不一定要扩池 |
| 锁竞争 | 等待链、热点键、事务阻塞 | 低 CPU 不表示系统没饱和 |
| 网络/磁盘 | 带宽、IOPS、延迟与队列同时变化 | 平均吞吐低仍可能存在突发或单盘热点 |
| 外部配额 | 429、供应商限流与并发上限 | 本地加实例无法扩大合同配额 |

瓶颈会迁移：优化查询后 CPU 可能成为主要限制，应用扩容后数据库连接可能先耗尽。每轮优化重新测整个链路，保留与基线同口径的延迟、错误、成功吞吐和成本，避免只报告单组件收益。

## 四、Little's Law：平均并发的边界

### 4.1 公式如何使用

Little 定律 L=λW，其中 L 是边界内平均在途数量，λ 是同一边界的平均流量，W 是平均停留时间。稳定条件下长期到达与离开大体平衡，且统计包含同一批工作。它不要求固定服务时间，但不应把发起到无限增长队列的速率与已完成请求的延迟混在一起。

5,000 RPS、平均 0.2 秒，平均在途约 1,000；若同样流量能维持且平均增至 2 秒，则约 10,000。这个推导说明下游变慢会放大资源需求，但若上限已触发拒绝或积压持续增长，不能再假装稳定条件成立，需分别跟踪接纳、完成与积压变化。

W 包含边界内排队时，L 也包含排队请求；若只算数据库连接持有时间，得出的 L 是平均被占用连接，而非整个 HTTP 并发。p99 不能直接代入平均定律当作平均并发，也不能凭算出 1,000 就精确设置线程池为 1,000。

### 4.2 内存与连接预算的推导

若 10,000 在途操作各保留约 64KiB，请求载荷粗占 625MiB，尚未计对象头、缓冲、线程、连接和运行时。大队列不只是“多等一会”，还可能引发 GC 和内存压力，进一步变慢形成级联。

数据库 100 个连接、每次占用平均 50ms，理想无额外限制下约支持 2,000 次连接占用/秒；如果一个请求持连接进行远程等待，持有时间上升会显著降低容量。先缩短事务、修复慢查询与泄漏，再评估扩池；数据库本身资源不够时扩池可能更差。

## 五、排队、Saturation 与过载保护

### 5.1 为什么接近满载时延迟突然上升

饱和（Saturation）是某个受限资源已无法及时接受更多工作，等待和拒绝开始主导体验。利用率平均未到 100% 也可能因瞬时突发、热点和服务时间方差出现长尾，所以生产安全水位必须实测，而非统一指定 70%。

用理想单服务台 M/M/1 模型说明非线性：到达服从泊松、服务时间指数分布、无限队列且 λ<μ 时，平均总停留 W=1/(μ-λ)，利用率 ρ=λ/μ。若 μ=100/s，λ=50 时 W=20ms；λ=90 时 100ms；λ=99 时 1 秒。现实系统多核、有限队列和非指数服务不一定符合该模型，但“余量变小使等待急增”的直觉有用。

观测队列深度和等待时长、active/max 工作线程、连接池等待、CPU 节流、GC 停顿及拒绝。只看 queue depth 不够：同样 100 件，短任务可很快消化，大任务可能阻塞很久，最老任务年龄更直接反映用户时限风险。

### 5.2 Admission Control、背压与 Load Shedding

准入控制（Admission Control）在昂贵处理前限制同时接受的工作，防止无限在途；背压（Backpressure）将消费能力反馈给生产者减速；负载卸载（Load Shedding）主动拒绝部分工作以保核心能力。三者可以配合，但拒绝必须有明确错误、重试建议和客户端预算，避免重试风暴。

在线请求适合短有界等待，无法在截止时间内完成就尽早拒绝；离线任务可持久排队，但仍有字节、数量、保留与恢复限制。队列上限可先用等待预算×处理能力粗估，再验证分布。例如消费能力 1,000/s、允许平均排队约 0.1 秒，对应约 100 个平均等待工作，不是“最大 100 就保证所有请求等于 100ms”。

不要在数据库提交后因客户端断开就假装事务没发生，也不要用丢弃策略处理不可丢任务。过载时优先保护已经接纳且有正确性承诺的工作，停止继续积累无人恢复的半成品。

## 六、并发模型：先看等待与资源，再选机制

### 6.1 Thread-per-request

平台线程每请求一个的模型直观，调用栈和事务上下文容易理解，适合团队现有同步库。大量阻塞时线程持有栈与操作系统资源，线程池和等待队列会限制并发。

线程池大小不是越大越好。CPU 密集任务通常受核心和调度约束；I/O 密集可容纳更多等待，但仍要限连接、外部调用和内存。使用有界队列与拒绝策略，避免任务无限堆积；父任务占满同一线程池又等待子任务，还可能出现线程饥饿。

### 6.2 Event Loop / Reactive

事件循环（Event Loop）用少量线程处理就绪事件，等待 I/O 时不为每个请求占用平台线程；响应式调用链表达异步信号和需求。适合高 I/O 并发且依赖支持非阻塞的场景，但编程、上下文传播和排障更复杂。

在事件线程执行阻塞 JDBC、文件读或长 CPU 计算，会阻塞同一循环中的其他请求。需要使用真正非阻塞库或移交受控工作池，后者只是转移限制，不能无限扩。流内部的需求控制也不自动限制客户端、数据库和整个集群的并发。

### 6.3 Virtual Thread

Java 21 虚拟线程（Virtual Thread）由 JVM 调度到平台承载线程，在支持的阻塞等待时释放承载资源，让同步风格承载大量 I/O 等待。它不是执行代码更快的线程，也不增加 CPU 核数、数据库连接或供应商配额。

采用时对数据库与外部 API 设信号量等并发限制，等待也有截止时间；不要为了限制业务并发而把虚拟线程当昂贵平台线程一概池化。运行时细节随 JDK 变化，本章只按 Java 21 解释基本机制，不把特定版本的 pinning 行为泛化到所有后续版本。

选型可以比较现有库兼容、团队能力、I/O 比例和诊断工具。若当前瓶颈是慢 SQL 和持锁冲突，切到 Reactive 或虚拟线程可能只是让更多请求更快排到数据库门口。

## 七、容量规划：峰值、余量、故障与增长

### 7.1 从业务预测到安全容量

完整计划记录当前负载基线、增长区间、峰值与季节性、读写混合、单实例安全容量、故障情景、发布余量、扩容速度及下游限制。预测应有上中下情景和置信度，不能把“客户翻倍”自动换成 QPS 翻倍。

安全容量是满足目标且能持续运行的容量，不是压测崩溃前的最高点。测试时指定版本、机器配置、数据量、缓存状态和依赖延迟。若单实例安全容量已包含某种利用率余量，再额外加余量要解释用途，防止无意重复计算。

### 7.2 正确解释 Headroom 和故障因子

本例“30% Headroom”定义为在预测峰值上乘 1.3，而非“始终有 30% 配置容量闲置”。后者需要除以 0.7，两种定义不同。预测峰值 10,000 RPS、乘数 1.3、失去三分之一容量后仍需保留该余量，则正常配置能力至少为：

~~~text
C × (2/3) >= 10,000 × 1.3
C >= 19,500 RPS
~~~

该算例要求故障发生后的剩余容量也有 30% 峰值上浮能力。若业务只要求故障时勉强承载 10,000，结果会不同，不能隐藏需求差异。故障因子假设流量可重分配且其他依赖仍正常，真实故障还可能降低单实例效率。

假设每实例安全 1,500 RPS，分三 AZ 均匀部署，单独失一 AZ 至少需每区 5 个，共 15 个；剩余 10 个能力 15,000。若还要求同时再下线一个实例，剩余 9 个为 13,500，仍满足 13,000。每区 4 个在失区后只剩 12,000，不满足。不能把理论 19,500 除以 1,500 得到 13 个后随意分布，离散放置会改变最坏情景。

### 7.3 下游、配额与发布峰值

应用最大实例数约束连接总量：每实例最多 30 个连接，正常 15 个可达 450；若发布允许临时增加 3 个，则可达 540。数据库若只分配 500 个给这项服务，发布可能先失败，需调整池、发布策略或明确数据库预算，不能只看正常时。

若峰值每请求四次查询，10,000 API RPS 需要约 40,000 Query/s；必须验证数据库、缓存与查询设计，而非用 15 个应用实例证明整系统可达。重试、后台对账、回填和重放也消耗下游预算，故障恢复期经常比正常更重。

存储规划同时包含每日新增、保留、索引、复制、备份和临时迁移空间，网络考虑响应体、跨区复制和出口。容量计划应列出限制、Owner、告警水位与申请提前期，配额提升和采购不一定即时完成。

## 八、Auto Scaling：控制回路与时间差

### 8.1 选能反映需求的指标

自动扩缩容是测量、决策、启动、预热到接流量的控制回路。CPU 适合部分 CPU 受限负载，RPS per target 适合成本相对稳定的请求，队列按每消费者积压或任务年龄更能反映工作压力。绝对总请求量不一定随实例数变化，不能不加转换就当作目标利用率。

目标值、最小最大容量、预热、冷却与缩容保护必须按平台和负载验证。不同产品对 cooldown 与 warmup 的含义不同，不能把它们当万能相同参数。AWS EC2 Auto Scaling 的目标跟踪可按目标指标调整容量，但本章不承诺任意服务有同样策略细节。

慢任务队列 CPU 可能很低，因为线程全在等外部接口；此时只按 CPU 扩容不会响应积压。反过来，依赖已经限流时继续加消费者可能扩大失败，应受下游并发上限约束。

### 8.2 扩容期间谁吸收峰值

假设负载从 8,000 突升到 12,000/s，现有安全能力 9,000/s，新容量可用要 120 秒，若全部接纳，将积压约 360,000 个操作。低延迟 API 通常不能靠排队两分钟满足 300ms 目标，应预留容量、预扩容、降低非关键需求或准入拒绝。

异步任务可按完成目标容忍缓冲，但仍要计算容量、恢复净速度与字节。缩容前停止接新工作，排空或安全交接持久任务，不能把尚未提交操作直接终止。配置最大值和预算告警，防止异常流量导致无限扩容或账单失控。

## 九、负载测试：测到目标，而不只是发出请求

### 9.1 六类测试各回答什么

| 类型 | 主要问题 | 必须记录 |
| --- | --- | --- |
| Baseline | 正常情况下什么表现 | 版本、环境、数据与目标 |
| Load | 预测峰值能否持续达标 | 实际到达、成功吞吐、尾延迟 |
| Stress | 何处开始失守、拒绝是否有界 | 饱和点、错误、恢复能力 |
| Spike | 突发时扩容与准入怎样反应 | 突发斜率、持续时间、积压 |
| Soak | 长时间是否资源累积或退化 | 内存、连接、磁盘、GC 与周期任务 |
| Failover | 节点/AZ 故障后能否服务 | 剩余容量、切换、数据正确性 |

Soak Test 不只找泄漏，还能发现日志磁盘、连接增长、缓存膨胀和周期性任务干扰。Stress Test 找极限不是为了把生产运行点设在极限，而是了解拐点和保护机制。

环境需接近生产的拓扑、数据规模、倾斜和依赖行为。均匀小数据隐藏热分区与慢查询，固定快速 Mock 隐藏下游尾延迟。故障实验先受控验证，不未经准备直接打断真实支付；结果清理、预算与恢复也属于测试方案。

### 9.2 Coordinated Omission 与开放/闭环

协调遗漏（Coordinated Omission）指生成负载随系统变慢而自动减少，从而漏测本应到达并等待的工作。闭环固定并发模型中，每个虚拟用户完成一次再发下一次；100 个用户、每次 0.1 秒、无思考时间约 1,000/s，变为 1 秒就约 100/s。工具看起来延迟还能接受，实际已悄悄减压。

开放到达模型让新任务按预定到达率独立发起，适合模拟外部持续流量；闭环仍适合有限用户等待再操作的真实场景，并非一律错误。选择应与业务一致，并报告工具实际能否维持目标。

开放模型也不能免除工具自证：生成器 CPU、网络、虚拟用户不足会丢弃迭代。记录 scheduled、started、dropped、completed、success 以及中途取消，区分计划发起时间与实际发起时间的等待。不能只统计已发送且完成的请求，把未发出、超时或截止时仍在途的任务全部排除。

## 十、优化与排障：每次用证据缩小范围

### 10.1 推荐改进顺序

先建立用户 SLI 和基线，再用 Profiling（剖析）、Tracing 和 Query Plan（执行计划）定位 CPU、锁、连接或 I/O 瓶颈。优先减少算法工作、无效查询、缺失索引与过大 Payload；接着减少不必要同步依赖，在语义允许时使用缓存、批处理和请求合并。

批处理减少固定开销，但增加等待、单次内存和部分失败处理；缓存增加陈旧治理；水平扩容适合可分散的无状态工作，但要重算连接和配额。只有单库容量和数据边界证据支持时再分区，并处理热点、跨分区查询和迁移成本。

复测不仅看吞吐，还看成本/成功业务操作、错误、尾延迟和恢复。若只用更大机器掩盖无限队列，故障仍会在新阈值出现；若加索引使读取改善但写入退化，也需明确取舍。

### 10.2 一个排障推演

教学场景：流量未增长，p99 从 200ms 变成 2 秒，CPU 低，连接池等待高。先怀疑 I/O 或锁等待而非 CPU 算力不足，查看连接持有时间、慢查询、锁链与依赖延迟，并对齐发布和数据变化。

若发现某查询扫描大量行，先验证执行计划和索引，再灰度修复；若连接在等待远程调用时被占用，缩短事务边界。紧急缓解可减少昂贵请求并限并发，保护数据库，而不是把连接池翻倍。修复后同负载复测，并验证故障恢复和连接总预算。

## 十一、面试完整回答与追问

### 11.1 主问题：怎样规划 10,000 RPS？

**回答示例：**“我先澄清请求混合、峰值持续时间、数据规模和 p99/错误目标，区分到达与正确完成吞吐。通过代表性压测得到单实例安全容量和下游每请求需求，用 Little 定律估平均在途与内存，再验证队列和连接。假设峰值 10,000、上浮系数 1.3、要求失三分之一容量仍保余量，则正常能力至少 19,500；但实例数必须按 AZ 离散放置，并检查发布额外实例。自动扩容有启动延迟，低延迟服务需要基线余量和准入保护。最后做峰值、突发、持续和故障测试，列出数据库、外部配额、成本与扩容触发器。”

**追问：为什么不直接用最大压测值？** 最大值可能已经牺牲尾延迟和正确性，也未包含冷启动、故障和长期退化。安全容量是在约定条件下持续满足目标的上限，须留与不确定性相称的空间。

### 11.2 追问：吞吐没增长，并发为什么突然变大？

**回答：**“同边界内平均停留时间变长会增加平均在途。可能是下游变慢、锁等待或排队，并不代表业务流量增加。我会分别看接纳率、完成率、队列增长与持有资源，判断是否仍稳定；不能在无限积压时机械套稳定公式。”

**再追问：加线程有用吗？** 若平台线程等待是限制可能有帮助；若数据库或配额已饱和，会扩大内存和排队。先找到限制并设有界并发，再决定模型或资源。

### 11.3 追问：虚拟线程是否能替代所有容量限制？

**回答：**“不能。它减少支持的 I/O 阻塞对平台线程的占用，仍使用真实 CPU 执行，也需要真实连接。Java 21 下我保留同步风格，但用许可控制数据库和外部调用，限制等待时间与在途载荷，并验证驱动和运行时表现。”

**再追问：Reactive 是否更快？** 需要同负载比较。非阻塞链路可能高效，但阻塞库和长 CPU 任务需要隔离，团队理解成本也不同；模型选择不能替代 SQL、锁和资源预算优化。

### 11.4 追问：CPU 很低，队列很长，为什么不继续扩容？

**回答：**“可能在等下游配额、锁或连接，CPU 不是这类饱和的信号。先看任务年龄、等待和外部限流；有独立可扩消费能力才扩，依赖固定时限并发、减少无效工作或协调配额。扩容目标同时受下游与成本上限约束。”

**再追问：如何验证没被压测工具误导？** 对照计划到达、实际发出、丢弃迭代与完成，检查生成器资源，并用符合业务的开放/闭环模型。超时和未完成都要报告，避免只统计成功样本。

## 十二、扫雷自测与完整答案

### 12.1 Throughput 增加时 Latency 为什么可能突然恶化？

利用率接近受限资源能力时，突发和服务时间波动没有余量被吸收，排队非线性增长。增加线程只是扩大等待容器，可能引发内存与 GC 连锁；需定位瓶颈、限接纳并验证安全运行区间。

### 12.2 10,000 RPS、500ms 对应多少并发？

若是同一统计边界的平均值且系统稳定，L=10,000×0.5=5,000。若 500ms 是 p99，不能直接当平均值；若队列一直增长，也需要另外分析净积压，不能宣称稳态并发固定为 5,000。

### 12.3 Virtual Thread 为什么不能解决连接不足？

虚拟线程减少的是部分线程等待成本，不会创建数据库执行能力。100 个连接仍只能同时被相应数量的操作持有。无限任务等待连接可能耗尽内存，应缩短持有、优化查询并限制并发。

### 12.4 Stress 与 Soak 分别发现什么？

Stress 逐步超出预期负载，找饱和、失守、拒绝和恢复；Soak 在较长时间观察泄漏、资源累积、周期任务和退化。前者最大吞吐不能替代后者的持续安全性，两者也都不能替代故障测试。

### 12.5 容量规划为什么包含故障？

用户流量不会随节点或 AZ 失效等比例减少，剩余资源还要接管，恢复和重试可能增加额外工作。必须按最坏放置、流量重分配、数据库与配额验证，不仅用正常总能力相加。

### 12.6 数据库 2,000 Query/s 是否支持 2,000 API RPS？

只有每 API 一次查询且其他约束满足时才可能。每 API 四次查询粗约 500 RPS，还需考虑成本分布和事务冲突。工作单位必须统一，不能把组件数字直接等同业务吞吐。

### 12.7 为什么 p99 不能跨实例取平均？

分位数不是线性平均，实例流量和分布不同会失真。应合并相容直方图或原始样本后算全局分布，同时按关键地区或租户类别观察，避免总体掩盖局部差。

### 12.8 开放到达模型是不是一定产生目标流量？

不是，生成器也受 CPU、网络和可用虚拟用户限制。看实际开始、丢弃与完成指标，检查目标是否真的到达服务。遗漏的计划请求和超时不能从报告静默删除。

### 12.9 保留 30% 空闲与峰值乘 1.3 一样吗？

不同。峰值乘 1.3 意味着容量比需求多 30%，需求约占配置 76.9%；保留配置容量 30% 空闲则需求最多占 70%，需要除以 0.7。容量公式必须先定义余量语义。

### 12.10 压测发现应用扩容后变慢，可能是什么？

数据库连接总量、查询竞争或外部配额被放大，热键和共享锁也可能成为瓶颈。检查下游等待和资源分布，回退到受控并发，修复工作需求后再扩。更多应用实例不保证全链路能力增加。
