# 02. 延迟、吞吐量、并发性与容量规划

## 学习目标

1. 理解 Latency、Throughput、Concurrency 与 Utilization 的关系。
2. 分析 End-to-end Latency 和 Tail Latency。
3. 使用 Load Test 与排队理论识别 Saturation。
4. 制定包含峰值、故障和增长空间的 Capacity Plan。

## 一、四个关键概念

- Latency：单个操作从开始到完成的时间。
- Throughput：单位时间完成的操作数量，如 RPS 或 messages/sec。
- Concurrency：同一时间正在处理的操作或连接数量。
- Utilization：资源被使用的比例，如 CPU、Memory、Connection Pool。

它们彼此关联，但不能互换。提高并发不一定提高吞吐量；超过系统容量后，排队增长会让 Latency 急剧上升。

## 二、Latency 分解

一次 API 请求可能包含：

```text
DNS + TLS + Network
+ Load Balancer Queue
+ Application Processing
+ Database Query
+ Downstream API
+ Serialization
```

端到端 Latency 不是只优化 Java method。需要通过 Distributed Tracing 找到 Critical Path。

### 2.1 Tail Latency

用户请求常常 Fan-out 到多个依赖。即使单个调用 P99 尚可，并行调用 50 个 Shard 时，至少一个慢调用的概率会显著提高。

处理手段包括：

- 减少 Critical Path 依赖数。
- Timeout 与 Deadline Propagation。
- Hedged Request（谨慎使用）。
- Cache。
- Request Coalescing。
- 隔离慢 Tenant 或慢 Query。

### 2.2 Coordinated Omission

Load Test 工具如果在系统变慢时也减少发出请求，可能低估真实 Tail Latency。测试应模拟预期 Arrival Rate，并正确记录排队等待。

## 三、Throughput 与瓶颈

系统吞吐量由最窄的 Bottleneck 决定：

```text
Client -> ALB -> Application -> DB -> External API
```

即使 Application 可处理 20,000 RPS，如果数据库只能完成 2,000 Query/s，整体容量仍受数据库限制。

常见 Bottleneck：

- CPU Saturation。
- GC Pause。
- Memory/Swap。
- Disk IOPS。
- Network Bandwidth。
- Thread Pool。
- Database Connection Pool。
- Lock Contention。
- External API Quota。

## 四、Little's Law

稳定系统中：

```text
L = λ × W
```

- `L`：系统中的平均请求数。
- `λ`：平均到达率。
- `W`：平均停留时间。

例如 5,000 RPS、平均 Latency 200 ms：

```text
Concurrency ≈ 5,000 × 0.2 = 1,000
```

如果 Latency 因下游变慢增加到 2 秒，并发会增长到约 10,000，可能耗尽 Thread、Connection 和 Memory，形成 Cascading Failure。

## 五、排队与 Saturation

当 Arrival Rate 接近 Service Rate 时，Queue Wait 往往非线性上升。长期把 CPU 或 Connection Pool 运行在接近 100%，系统没有吸收波动的空间。

需要观察：

- Queue Depth。
- Queue Wait Time。
- Active/Max Thread。
- Connection Pool Wait。
- CPU Throttling。
- GC Pause。
- Rejected Request。

Backpressure 和 Load Shedding 可以保护系统，避免无限排队。

## 六、并发模型

### 6.1 Thread-per-request

传统 Spring MVC 常使用每请求一个工作线程。模型直观，但大量阻塞调用会占用线程。

### 6.2 Event Loop / Reactive

适合大量 I/O-bound 并发，但要求调用链避免阻塞，编程和排障复杂度更高。

### 6.3 Virtual Thread

Java Virtual Thread 可以用同步编程风格处理大量 I/O-bound 并发，但不会消除数据库连接、外部 API Quota 或 CPU 等实际瓶颈。

并发模型应根据 Workload、团队能力和依赖特征选择，而不是追逐流行技术。

## 七、Capacity Planning

完整 Capacity Plan 包括：

1. 当前 Baseline。
2. 业务增长 Forecast。
3. Peak Factor 与季节性。
4. 单实例安全容量。
5. Failure Scenario。
6. Deployment Headroom。
7. Auto Scaling 速度与上限。
8. 下游 Limit 和 Quota。

公式示例：

```text
Required capacity = forecast peak × headroom × failure factor
```

如果预测 Peak 为 10,000 RPS，Headroom 为 30%，并要求失去三分之一节点后仍服务：

```text
Normal provisioned capacity >= 10,000 × 1.3 / (2/3)
                            ≈ 19,500 RPS
```

## 八、Auto Scaling

Auto Scaling 不是无限容量。需要明确：

- Scaling Metric：CPU、RPS、Queue Depth 或自定义指标。
- Target Value。
- Cooldown/Warmup。
- Min/Max Capacity。
- Instance Startup Time。
- Database 和 Dependency 是否能承受扩容后的流量。

对突发 Queue Workload，基于 Queue Age/Depth 扩容通常比 CPU 更直接。对低延迟 API，可以结合 RPS per target 和 CPU。

## 九、Load Test 类型

- Baseline Test：建立正常性能基线。
- Load Test：验证预期 Peak。
- Stress Test：寻找 Break Point。
- Spike Test：验证突发流量。
- Soak Test：发现 Memory Leak、资源累积和长期退化。
- Failover Test：验证节点/AZ 故障下容量。

测试环境应尽量接近生产的拓扑、数据分布和依赖行为。只用少量均匀测试数据可能无法暴露 Hot Partition 和慢 Query。

## 十、性能改进顺序

1. 建立 SLI 与 Baseline。
2. 使用 Profiling、Tracing 和 Query Plan 找到瓶颈。
3. 优化算法、Query、Index 和 Payload。
4. 减少不必要的同步调用。
5. 引入 Cache 或 Batch。
6. 水平扩容无状态部分。
7. 必要时 Partition 数据。
8. 重新测试并比较 Cost。

先测量再优化。盲目增加 Instance 可能只是把瓶颈转移到数据库。

## 十一、常见错误

- 只关注 Average，不看 P99。
- 把最大压测吞吐量当作安全生产容量。
- 忽略 Failover 和 Rolling Deployment。
- Application 扩容却不控制数据库连接。
- 使用 CPU 作为所有 Workload 的 Scaling Metric。
- 压测不包含真实数据倾斜和依赖延迟。
- 没有 Admission Control，过载时无限排队。

## 十二、自测题

1. Throughput 增加时 Latency 为什么可能突然恶化？
2. 10,000 RPS、500 ms Latency 对应多少平均并发？
3. Virtual Thread 为什么不能解决数据库连接不足？
4. Stress Test 和 Soak Test 分别发现什么问题？
5. 容量规划为什么必须包含故障场景？

## 十三、总结

- Latency、Throughput 与 Concurrency 通过排队和资源限制相互影响。
- Tail Latency 比 Average 更能反映最差用户体验和 Fan-out 风险。
- Capacity Plan 必须包含 Peak、Headroom、Failure 和 Growth。
- Auto Scaling 需要合适指标、启动速度和下游容量支持。
- 性能工作应从测量和瓶颈证据开始，并同时评估 Reliability 与 Cost。
