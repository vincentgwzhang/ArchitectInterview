# 05. 可观测性、可运营性与成本优化

> 本章使用虚构订单与 AI 问答平台，所有数字均为教学假设，不是用户项目或产品基准。目标是能从用户影响走到证据、处置与成本决策，而非背监控产品名称。

## 一、Monitoring 与 Observability：先定义要回答的问题

Monitoring（监控）持续检查已知条件，例如错误率是否超标；Observability（可观测性）是借助系统输出推断内部状态的能力，支持调查事先没预设的问题。二者互补：仪表盘能发现付款失败增多，但要判断是否只影响新版本、某地区与某支付通道，仍需可关联、可筛选的证据。安装三个采集器并不自动获得这种能力。

从用户旅程定义 Business Signal（业务信号）：下单、支付授权、订单最终确认分别是什么成功，多久内完成。HTTP 200 可能只代表接单，后台最终失败仍是业务失败。基础设施健康也不证明用户流程成功；反过来，CPU 高也不一定影响用户。

调查顺序是确认用户影响及开始时间，按 Tenant（租户）、Region（地区）、版本与依赖缩小范围，再比较发布、配置和流量变化，验证假设，最后检查修复是否消除业务影响。相关性不等于根因：发布同时遇到上游故障，不能只因时间接近就认定发布有错。无流量、无数据与零错误要分开显示。

## 二、Metrics：把问题变成有口径的时间序列

### 2.1 Golden Signals、RED 与 USE

Metric（指标）是随时间记录的数值，Time Series（时间序列）由指标名和标签集合确定。每个指标应有单位、统计边界、更新规则和 Owner（负责人），否则同名“成功率”可能统计不同业务。

| 方法 | 观察项及含义 | 适用与陷阱 |
| --- | --- | --- |
| Golden Signals | Latency 延迟、Traffic 流量、Errors 错误、Saturation 饱和 | 从服务表现到容量；成功请求与失败请求延迟宜分开看 |
| RED | Rate 请求速率、Errors 错误、Duration 耗时 | 面向请求服务；异步任务还需积压年龄和最终结果 |
| USE | Utilization 使用率、Saturation 等待需求、Errors 资源错误 | 面向 CPU、磁盘、线程池等资源；使用率不等于排队程度 |

例如线程池活跃线程已满且等待队列增长，说明存在饱和，即使整机 CPU 很低也可能在等待数据库。数据库连接池等待时间、队列最老消息年龄往往比“队列数量”更接近超时风险；相同一千条消息在每秒处理十条和一万条时含义完全不同。

### 2.2 Counter、Gauge 与延迟分布

Counter（计数器）累计事件，通常随进程重启归零，应通过理解重置的速率函数观察单位时间增量，不能直接用累计值比较两个实例。Gauge（瞬时值）记录当前连接数、队列长度等可升可降的状态，不能对所有 Gauge 套计数器速率。

Histogram（直方图）把观测归入桶，可聚合多个实例的桶计数再估计分位数。p99 表示约 99% 观测不超过该值，不是最慢请求，也不是平均值。经典桶的边界决定误差，SLO 阈值附近应有合适桶；Summary 的客户端预计算分位数通常不能直接跨实例合并。不要平均各实例 p99：一个实例只有十个请求，另一个有十万个，分位数不具备这种可加性。

看延迟要同时看流量与错误。超时请求未被记录、负载发生器等待前一请求后才发下一请求，都可能隐藏最差等待；明确从请求何时开始计时、超时与取消是否进入分母。监控分布是采集口径的结果，不是无条件的真实全景。

### 2.3 Cardinality：维度乘法会消耗预算

Cardinality（基数）是标签值及其组合的数量。假设 20 服务、10 路由、5 状态类别、3 地区，每种组合一条序列，理论上可有 3000 条；再加十万用户维度，理论组合上界升至三亿。实际只有出现的组合产生序列，但仍可能快速耗尽内存、索引和查询预算；直方图多个桶还会放大序列数。

路由使用模板 /orders/{id}，不使用实际完整 URL；用户 ID、订单 ID 通常放受控日志或 Trace，不作为全局 Metric Label。租户排障可用日志检索、分层聚合或明确限额的专用指标，不能为了隔离分析无限加标签。删除标签会降低定位粒度，因此先约定业务必须回答的维度，再设每服务预算与超限告警。

## 三、Logs：记录离散事实而非复制请求

Log（日志）解释某次状态或失败，适合高基数关联与细节调查；Metric 更适合聚合趋势。生产使用稳定事件名、类型一致的字段与错误码：

~~~json
{
  "timestamp": "2026-11-19T18:30:00Z",
  "level": "ERROR",
  "service": "order-service",
  "version": "1.42.0",
  "traceId": "demo_trace_1",
  "orderId": "demo_order_789",
  "event": "payment_authorization_failed",
  "errorCode": "PROVIDER_TIMEOUT"
}
~~~

示例 ID 仅供教学。错误表示当前层已无法完成职责，应包含超时阶段、依赖名和安全的结果信息，不能假称付款一定未发生：远端超时可能已授权成功，需要幂等查询与对账。每层重复打印堆栈会放大费用并掩盖真实事件，通常在能提供完整上下文的边界记录一次，其他层保留 Cause（原因链）。

禁止记录访问令牌、密码及无必要个人信息（PII）。先在源头最小化，再在采集管道防护；只在存储后脱敏不能避免传输与缓冲泄露。结构化编码和长度限制可防换行注入伪造事件。保留期限、查询权限、租户隔离和删除流程与数据分类一致，Debug 日志不能无限保留。

采样普通重复日志可控量，但审计证据与不可丢业务事实有独立可靠性要求。异步日志队列要有上限与丢失计数；遥测平台故障不能无界阻塞业务线程或撑爆磁盘。高风险审计失败是否暂停业务需单独设计，不能把所有日志都设为静默丢弃。

## 四、Distributed Tracing：还原因果与等待

Trace（调用链）由 Span（一次操作区间）组成，记录操作名、开始、耗时、状态、属性、父子或关联关系。通过 HTTP 或消息元数据传播上下文，才能连接网关、订单、库存和支付；每个服务自行生成不关联的 ID，无法自动拼出一次请求。

耗时不能把所有 Span 相加：并行库存查询可能重叠，真正影响端到端时间的是 Critical Path（关键路径）。大量短数据库调用可能揭示 N+1，即查列表后逐条补查；多层重试则会在一个用户请求下产生多次依赖调用。优化应针对实际串行等待、排队或重复工作，不能只挑最长单个 Span。

队列发送与消费应区分消息等待、处理时间与重投递。跨数小时的流程可用独立 Trace 加 Span Link（因果关联），再用业务 ID 连起来；一条永久增长的 Trace 会带来存储、查询和语义问题。Saga 是由多步本地事务与补偿组成的流程，补偿也要记录原业务关联，不能假装是同一数据库事务。

OpenTelemetry（开放遥测）提供插桩、上下文与导出等组件，后端仍需另选。SDK（开发工具包）或自动插桩产生数据，Collector（采集处理服务）可批处理、过滤与导出；它不自动提供所有存储和告警能力。外部上下文不可信，不要把传入 Baggage（随链传播的附加键值）当授权依据或携带秘密，必须约束大小与字段。

### 4.1 Head 与 Tail Sampling 的取舍

Head Sampling（头部采样）在请求开始做决定，开销可控但未知结局，可能漏掉罕见失败。Tail Sampling（尾部采样）收集一段 Trace 后依据错误、慢请求等决定保留，能偏向有价值样本，却需要缓存、等待和把相关 Span 路由到可共同决策的位置；晚到数据、内存上限或采集丢失仍会造成不完整。

“错误全留”不能找回 SDK 头部已丢弃的 Span。采样策略要端到端设计，监控导出失败、队列、丢弃与采样比例。错误优先样本有偏，不能直接由这些 Trace 推断全量错误率；全量指标与抽样证据承担不同职责。

## 五、Correlation：让三种证据与业务连接

Trace ID 连接一次技术执行，Order/Payment ID 连接业务生命周期，Version 连接发布，Region/AZ（可用区）连接故障域，Tenant 支持受权限控制的影响范围分析。业务重试可能换 Trace ID，同一订单也可能有多次合法动作，需再记录动作类型、尝试号与稳定事件 ID。

日志、Trace、发布事件和指标应使用一致服务身份与时间口径。时钟不同步会扭曲跨服务顺序，单机耗时宜用单调时钟，跨机墙上时间只能结合因果关系解释。不要把所有上下文放入指标标签；可由聚合图跳转带 Trace 关联的样本，再按业务 ID 查事件。

关联不是授权，知道订单号或 Trace ID 不代表能看其内容。遥测查询本身需要权限、审计与敏感字段控制，避免故障排查平台成为跨租户数据出口。

## 六、Alert：用错误预算决定何时叫醒人

SLI（服务水平指标）是实际测量，例如合格订单中按时成功的比例；SLO（服务水平目标）规定统计窗口及目标。定义哪些请求合格、超时和依赖失败是否算坏事件，不能故障后临时从分母剔除。Error Budget（错误预算）是允许的坏事件比例。

假设 SLO 为 99.9%，允许坏事件比例为 0.1%；当前坏事件比例 1%，Burn Rate（消耗速率）为 1% / 0.1% = 10。若未来流量与当前测量条件相似，预算消耗会明显加快，但不能把短期速率当精确预测。流量变化时请求预算与时间预算不可随意互换。

长窗口防抖、短窗口确认问题仍在持续，可组合多窗口与快慢消耗级别：快速大规模失败通知值班，较慢持续消耗进入有期限工单。阈值按窗口、流量、发现和处置时间选择，不机械抄别人的数字。低流量服务一个失败就可能比例很高，需要最少事件量、合成探测或更长观察，同时不能无限压住真实小客户故障。

Page（即时值班告警）必须有当前或即将发生的显著影响、可行动作、Owner、严重度和 Runbook（处置手册）。CPU 70% 通常只是诊断信号；磁盘即将耗尽且会中断写入则可以是提前行动告警。队列最老年龄、业务最终失败率与 SLO 消耗优先反映用户风险。

告警分组减少同根因重复通知，维护静默有期限，升级有人接手。长期无人行动的告警先查责任与必要性，再修订、降级或删除，不能为美化噪声统计屏蔽真实风险。遥测缺失与告警通道故障也要独立检查，最好有外部探测验证业务和通知路径。

## 七、Operability：交付时证明能运行

Operability（可运营性）是可安全部署、观察、诊断、恢复和变更的能力。Definition of Done（完成标准）要成为可核验证据，而非勾选“有 Dashboard”。

| 交付项 | 验收方法 | 不通过的典型表现 |
| --- | --- | --- |
| Dashboard、SLI/SLO、Alert | 注入可控错误，看到业务影响并收到通知 | 图很多但分母错误、无人接收 |
| Log、Trace、依赖图 | 由一次测试订单找到版本和依赖失败 | 上下文在异步边界丢失 |
| Health Endpoint | 区分活性与接收流量能力 | 上游慢导致全实例循环重启 |
| 备份与恢复 | 用隔离环境恢复并核对业务数据 | 只看备份任务绿色 |
| 回滚与发布 | 小流量发布、触发条件和兼容性验证 | 新数据格式使旧版本无法读取 |
| 容量、限额、Owner | 负载边界及过载行为有记录，值班可联系 | 队列无界、权限不可用 |

健康检查不应暴露秘密或把昂贵全链路查询变成自身负载。Rollback（回滚）代码不自动回滚已发出的支付、邮件或数据迁移，需兼容设计、前向修复或业务补偿。运行证据纳入交付审查，平台可提供默认模板降低团队重复成本，但业务成功定义仍由团队负责。

## 八、Runbook 与受约束的自动修复

好的 Runbook 写清症状、影响、验证查询、已知原因、缓解步骤、前提权限、回滚/切换条件、升级联系人和恢复验证。命令应限定环境、资源范围与最大动作，避免复制到错误集群；手册版本随系统变化维护，通过演练证明能执行。

虚构队列年龄告警的处置：先确认消息仍在到达且消费者有推进，检查最近发布、重试率与下游延迟；若下游正常但 Worker 饱和，在数据库连接和消费分区允许的范围扩容；若下游故障，先限制重试与入口，不盲目加 Worker 放大压力。恢复后核对最老年龄、处理成功、重复副作用与失败消息，不能只看实例变绿。

重启卡住消费者、扩 Worker、切 Feature Flag（功能开关）适合自动化的前提是条件可判定、动作有限且可验证。用冷却时间、尝试上限、并发限制、审计和停止开关防循环修复；先小范围执行。消费者重启可能重投递，必须有幂等与确认点设计。自动化无法确定原因时升级人工，不重复执行不可逆操作。

## 九、成本可观测性与 Unit Economics

FinOps 是业务、工程与财务共同持续管理技术价值与成本的实践。先确定账单口径：实际现金支出、承诺费用摊销、折扣、共享平台、网络、存储和人工是否包含。日账单可能延迟回补，不能把实时遥测估算当已结算事实。

按 Account、Team、Service、Environment、Tenant 建立 Cost Allocation（分摊）。Tag（标签）记录资源归属，但共享数据库不能靠一个标签自动知道各租户费用；可用测量的存储量、处理时长或请求权重分摊，公开假设与无法分配项。Showback 是展示归属，Chargeback 是实际内部计费，需要更严格认可与对账。

Unit Cost（单位成本）= 同范围同期间成本 / 有效业务量。可按成功订单、活跃用户、千次 API、合格 AI 回答或处理 GB 计算。分母必须有价值含义，失败重试不能被算成额外“产出”稀释成本。零业务量时单位成本无定义，应显示成本和闲置状态，不伪造为零。

假设成本由 10000 增至 15000，成功订单由 100000 增至 200000，单位成本由 0.10 降至 0.075，效率改善 25%，但总预算压力仍增加。还要按产品和租户分层，避免业务组合变化掩盖昂贵路径。Budget（预算）管理可接受支出，Anomaly（异常）检测偏离预期；促销增长可能合理，凭证滥用或重试循环则需立即调查。

## 十、Inform、Optimize、Operate 的闭环

### 10.1 Inform：建立透明、分摊与预测

Inform 收集账单和业务驱动、补齐归属、识别固定与随量成本，并做 Forecast（预测）。新功能预测不只给一个总数：用请求量、存储增长、出网、峰值余量和失败重试情景说明范围，记录实际与预测偏差。没有归属就先修观测，不能只按最贵团队排名处罚。

### 10.2 Optimize：先修浪费，再改变承诺与架构

| 手段 | 如何节省 | 适用边界与验证 |
| --- | --- | --- |
| Rightsizing 资源匹配 | 按实测 CPU、内存、IO 和峰值余量调整规格 | 平均低不代表峰值足够，验证故障时容量 |
| Auto Scaling 自动伸缩 | 随负载增减资源 | 冷启动、配额与下游容量约束，缩容要排空 |
| Spot 可中断容量 | 用较低成本承接可重做工作 | 中断、检查点与重试费用可能抵消节省 |
| 承诺折扣，如 Savings Plans | 交换用量承诺与价格优惠 | 产品条款不同，闲置承诺仍有成本，先确认稳定基线 |
| 存储生命周期与闲置清理 | 迁移冷数据或删除无用资源 | 取回延迟/费用、保留和恢复要求先核对 |
| 网络、Query、Cache | 减少传输、扫描与重复计算 | 跨 AZ/Region 价格依厂商；缓存失效与权限隔离有成本 |

以上是机制，不提供统一折扣率或保证收益。跨区数据本地化可能降低传输费，却可能增加副本与一致性成本；缓存只看命中率不够，大对象低命中可能反而更贵。每个实验记录成本、延迟、错误、质量与回退条件，同范围对照后再推广。

### 10.3 Operate：让决定持续生效

Operate 把预算、成本回归检查、Owner、异常响应和优化复盘放入架构评审、交付与规划。用明确期限管理优化事项，跟踪实际而非理论节省；删除闲置实例后若账单仍被承诺覆盖，现金节省可能未立即发生。不同团队可以并行处于不同阶段，三阶段是循环，不是每年一次运动。

## 十一、可靠性、安全与成本的共同边界

先定义 Guardrail（不可跨越的约束），例如故障后仍满足关键负载、敏感数据查询隔离、必要日志保留、恢复目标。减少 Replica（副本）会削弱故障容量；降低日志期限可能妨碍调查；减少备份会提高不可恢复风险。选项应在约束内比较，不能把转移到事故和人工的成本当节省。

Scale-to-zero（空闲缩至零）适合可接受启动等待的负载，交互式请求可能因 Cold Start（冷启动）恶化尾延迟。Spot 不适合没有重做或迁移机制的关键状态工作；即便任务可重做，也要保证完成期限。用负载、故障和恢复演练检查优化后的边界，费用下降不是唯一通过条件。

遥测本身也要成本预算：采集量、标签数、保留、冷热分层与查询扫描共同决定费用。先删除无意义重复、降低低价值明细保留，再考虑采样；保留业务聚合、关键事故证据和合规所需数据。减少遥测要验证能否仍回答关键调查问题。

## 十二、AI 问答服务：成本降低必须保留有效答案

端到端 Latency 从用户提交到完成计时；Time to First Token（首 Token 时间）衡量开始输出等待，不代表全答完成。模型错误/超时、输入输出 Token（模型计量片段）、检索延迟、引用质量、缓存命中与用户反馈分别测量，不能用输出成功代替回答正确。

检索质量可用已标注问题集检查相关材料是否被找回，再检查回答是否有支持、是否越权。质量集需覆盖难题与租户权限，线上用户反馈有偏，应与离线评估、抽检和业务完成率组合。新增模型或缩上下文后，以同集比较合格率和成本，不能只挑简单问题。

简单请求路由小模型要有分类与失败升级；缩无效 Context（上下文）应保留必要证据。Semantic Cache（语义缓存）复用相似问题结果，必须把租户、权限、知识版本与适当时效纳入隔离，语义相似不保证答案可共享。Batch Embedding（批量向量化）摊薄调用开销，但增加等待与失败重试粒度。高成本租户 Quota（限额）明确硬拒绝、排队或降级，并告知产品方体验影响。

单位成本宜使用“每个合格回答”：假设旧方案成本 100、合格 80 次为 1.25，新方案成本 80、合格 50 次为 1.60，Token 更省但有效产出更贵。失败请求、检索、向量存储、重试和缓存都进入相同成本范围。这里仅讲设计与假设算例，未调用任何收费模型服务。

## 十三、面试完整回答与追问

### 13.1 怎样设计可观测性？

“我先定义下单到最终确认的成功和时间边界，用全量指标显示业务成功率、延迟、流量及饱和，再用结构化日志与抽样 Trace 解释具体失败。身份统一关联版本、地区和业务 ID，订单号不进入无限基数标签。告警按错误预算、队列年龄和可行动作分级，每项有 Owner 与演练过的 Runbook；采集丢失与外部业务探测也要监控。”

**追问：Trace 已采样，怎样确认错误率？** 使用有明确分母的全量计数，Trace 用来解释样本。错误偏向采样不能直接估总体错误率；遥测缺失则标记不确定并交叉验证业务记录。

### 13.2 怎样降成本又不损可靠性？

“先统一成本范围与成功业务量，分摊共享资源，区分增长、浪费与单价。优先清闲置、优化查询与重复传输，再按峰值和故障余量匹配资源；稳定基线才考虑承诺，可重做任务才考虑中断容量。每项改变同时检验 SLO、质量、安全与恢复，不靠关闭关键副本节省。”

**追问：为何不直接选最便宜规格？** 内存不足、磁盘瓶颈或恢复更慢会产生更多重试和人工。比较总拥有成本与业务约束，价格低只是一项输入。

### 13.3 告警很多且没人看怎么办？

“先确认哪些是显著业务风险、谁能做什么，再合并重复根因，补 Runbook 和升级路径。可观察但不需即时行动的信号进入 Dashboard 或工单，真正快速消耗预算的事件保留 Page。用演练与实际响应复盘验证，不能简单全关。”

**追问：修复后 CPU 正常就关闭事故吗？** 还需确认成功率、端到端延迟、队列年龄和业务副作用恢复，并检查失败请求是否需要补偿。资源恢复是证据之一。

## 十四、扫雷自测与推理答案

1. **Monitoring 与 Observability 的区别？** 前者持续判断已知条件，后者借输出调查内部状态与未知问题。付款失败率告警发现问题，按版本和依赖关联证据解释问题；二者共同构成反馈闭环。
2. **RED 与 USE 分别看什么？** RED 看请求速率、错误与耗时，USE 看资源使用、等待需求和错误。CPU 低但连接池等待高时，请求仍会慢，因此需要两个视角。
3. **为什么 userId 不宜做 Metric Label？** 每个不同值和其他标签组合都可能产生新序列，放大索引、内存与查询成本。把明细放权限受控日志/Trace，保留有边界的聚合维度。
4. **何种告警叫醒值班？** 显著当前或临近影响且能采取明确行动，有责任、严重度和处置路径。单次无害 CPU 波动通常不满足；磁盘即将写满且可清理或扩容可能满足。
5. **单位成本为何比总账单更能解释效率？** 它把投入与有效产出关联，业务翻倍成本仅增五成时单位成本下降。但范围、质量和业务组合必须一致，不能代替总预算管理。
6. **能平均实例 p99 吗？** 不能，分位数不可线性合并，样本数和分布不同。聚合兼容的直方图桶后估计整体分位数，并说明桶误差。
7. **Tail Sampling 能恢复已丢错误吗？** 不能，只能在收到的数据上决策。前段丢弃、传输失败和缓存不足必须分别治理，并监控采集链自身。
8. **重启 Consumer 总能安全恢复吗？** 不能，可能重投递造成重复扣款，也可能下游故障导致循环重启。先识别卡点，再依赖幂等、确认点、动作上限与恢复验证。
9. **账单下降是否证明优化成功？** 不证明，可能流量或质量下降，或支出转移到其他账户与人工。对齐范围、业务产出及约束，验证实际持续收益。
10. **只保留 Trace ID 足够吗？** 不足，跨小时重试或批处理可能跨多条 Trace。业务 ID、尝试和事件 ID 连接生命周期，同时控制访问，不无限扩展一条链。

## 十五、速记、适用范围与核验来源
