# 05. 可观测性、可运营性与成本优化

## 学习目标

1. 区分 Monitoring 与 Observability。
2. 设计 Logs、Metrics、Traces 与 Business Signal。
3. 将 Operability 纳入架构和交付标准。
4. 使用 FinOps 思维优化单位业务成本，而不是盲目压缩资源。

## 一、Observability 是什么

Observability 是通过系统外部输出推断内部状态的能力。Monitoring 主要回答已知问题，Observability 还帮助调查未预见的问题。

目标不是收集最多数据，而是快速回答：

- 用户是否受到影响？
- 哪个 Tenant、Region、Version 或 Dependency 有问题？
- 故障从何时开始？
- 最近发生了什么变化？
- 根因在哪里？
- 修复是否有效？

## 二、Metrics

常见 Golden Signals：

- Latency。
- Traffic。
- Errors。
- Saturation。

常见 RED Method：

- Rate。
- Errors。
- Duration。

资源层可使用 USE Method：

- Utilization。
- Saturation。
- Errors。

有效 Metric 应具备清楚的名称、单位、Label 和 Owner。

### Cardinality 风险

不要把 `userId`、`orderId`、完整 URL 作为 Metric Label，否则 Time Series 数量可能爆炸。高 Cardinality 数据更适合 Log 或 Trace。

## 三、Logs

生产 Log 应结构化：

```json
{
  "timestamp": "2026-11-03T10:15:00Z",
  "level": "ERROR",
  "service": "order-service",
  "version": "1.42.0",
  "traceId": "abc123",
  "orderId": "ord_789",
  "event": "payment_authorization_failed",
  "errorCode": "PROVIDER_TIMEOUT"
}
```

原则：

- 使用稳定 Event Name 和字段。
- 记录业务上下文，但避免 PII/Secret。
- 不要重复打印同一异常堆栈。
- 设置 Retention 和 Access Control。
- Error Log 应具有可执行意义。

## 四、Distributed Tracing

Trace 将跨 Service 的一次请求连接起来：

```text
Web -> API Gateway -> Order -> Inventory -> Payment
```

每个 Span 记录：

- Operation。
- Start/Duration。
- Status。
- Attributes。
- Parent/Child Relationship。

Tracing 可以发现：

- Critical Path。
- 慢 Dependency。
- Retry 放大。
- N+1 调用。
- Queue Processing Delay。

OpenTelemetry 可以统一采集 Metrics、Logs 和 Traces，但仍需设计 Sampling、Storage 和敏感数据控制。

## 五、Correlation

至少关联：

- Trace ID：技术调用链。
- Business ID：Order ID、Payment ID。
- Deployment Version。
- Region/AZ。
- Tenant（注意 Cardinality 与权限）。

只有 Trace ID 可能无法定位跨数小时的异步流程；Business ID 对 Saga、Kafka 和 Batch Job 更重要。

## 六、Alert 设计

好 Alert 应该：

- 对应用户或业务影响。
- 需要明确行动。
- 有 Owner 和 Runbook。
- 控制 Noise。
- 使用合适 Severity。

优先对 SLO Burn Rate、Error Rate、Queue Age 和业务失败率告警，而不是单纯对 CPU 70% 告警。

如果 Alert 长期无人处理，应删除、调整或降级为 Dashboard Signal。

## 七、Operability

Operability 是系统能够被安全部署、监控、诊断、恢复和变更的能力。

架构 Definition of Done 可以包括：

- Dashboard。
- SLO 和 Alert。
- Structured Log 与 Trace。
- Health Endpoint。
- Runbook。
- Backup/Restore。
- Rollback。
- Capacity Limit。
- Dependency Map。
- On-call Ownership。

一个不能安全运行的 Feature 不能算真正完成。

## 八、Runbook 与 Automation

Runbook 应包含：

- 症状和影响。
- 验证步骤。
- 常见原因。
- 安全缓解动作。
- Rollback/Failover 步骤。
- Escalation Contact。
- 恢复验证。

频繁执行且风险可控的操作应自动化，例如重启卡住 Consumer、扩容 Worker、切换 Feature Flag。高风险自动修复需要 Guardrail 和 Audit。

## 九、成本可观测性

成本也应具备 Ownership 和 Feedback Loop：

- 按 Account、Team、Service、Environment、Tenant 分摊。
- 使用 Tagging 和 Cost Allocation。
- 监控 Budget 与 Anomaly。
- 计算 Unit Cost。

常见 Unit Cost：

```text
Cost per order
Cost per active user
Cost per 1,000 API calls
Cost per AI answer
Cost per GB processed
```

只看总账单可能误导：业务增长 100% 而成本增长 50%，总成本变高但效率实际上改善。

## 十、FinOps 生命周期

### 10.1 Inform

建立成本透明度、Allocation 和 Forecast。

### 10.2 Optimize

- Rightsizing。
- Auto Scaling。
- Spot/Savings Plans。
- Storage Lifecycle。
- 删除闲置资源。
- 减少跨 Region/AZ Transfer。
- 优化 Query 和 Cache。

### 10.3 Operate

将成本检查纳入 Architecture Review、Planning 和持续运营，而不是一年一次削减项目。

## 十一、成本与可靠性边界

成本优化必须保护 SLO 和安全要求：

- 缩减 Replica 可能降低故障容量。
- 降低 Log Retention 可能影响调查和 Compliance。
- 使用 Spot 需要 Workload 能处理中断。
- aggressive Scale-to-zero 可能增加 Cold Start。
- 减少 Backup 会提高数据风险。

应先定义 Guardrail，再在 Guardrail 内优化。

## 十二、场景：AI 问答服务

应观察：

- End-to-end Latency 和 Time to First Token。
- Model Error/Timeout。
- Token Input/Output。
- Retrieval Latency 和 Hit Quality。
- 每次回答成本。
- Cache Hit Ratio。
- 用户反馈与答案质量。

优化可能包括：

- 简单请求路由到较小 Model。
- 缩短无效 Context。
- Semantic Cache。
- Batch Embedding。
- 对高成本 Tenant 设置 Quota。

不能只降低 Token，而忽略答案质量，否则单位成本下降但产品价值也下降。

## 十三、常见错误

- 收集大量 Telemetry，却无法回答用户影响。
- Metric Label 使用高 Cardinality ID。
- Alert 没有 Runbook 和 Owner。
- 只监控 Infrastructure，不监控 Business Flow。
- Log 包含 Token 或 PII。
- 为节省成本关闭关键 Backup 或冗余。
- 只优化总账单，不关注 Unit Economics。

## 十四、自测题

1. Monitoring 与 Observability 有什么区别？
2. RED 和 USE 分别适用于什么视角？
3. 为什么 `userId` 不适合做 Metric Label？
4. 什么样的 Alert 才应该触发 On-call？
5. Unit Cost 为什么比总成本更适合衡量效率？

## 十五、总结

- Observability 应帮助团队从用户影响定位到根因。
- Metrics、Logs 和 Traces 必须通过 Trace ID、Business ID 和 Version 关联。
- Operability 包括部署、诊断、恢复、Runbook 和 Ownership。
- Cost 是需要持续观察和优化的架构指标。
- 最佳优化是在 Reliability、Security 和业务价值 Guardrail 内降低 Unit Cost。
