# 02. 高内聚、低耦合、模块化与分层设计

## 学习目标

1. 理解 Cohesion 和 Coupling 的含义及判断方法。
2. 能够设计清晰的 Module Boundary。
3. 理解 Layered Architecture 的职责和依赖方向。
4. 能够识别 Big Ball of Mud、循环依赖和跨层调用等问题。
5. 能够解释模块化单体与 Microservice 的选择依据。

## 一、高内聚与低耦合

高内聚、低耦合是模块设计的核心目标：

- Cohesion 描述一个模块内部元素彼此相关的程度。
- Coupling 描述不同模块之间相互依赖的程度。

理想状态是：同一个业务能力相关的代码聚集在一起，不同业务能力之间通过小而稳定的契约协作。

### 1.1 高内聚

一个高内聚的 `Pricing` Module 可能包含：

- Price、Discount、Tax 等 Domain Model。
- 价格计算规则。
- 折扣策略。
- 与价格相关的测试。

如果修改折扣规则只需要进入 `Pricing` Module，并且不需要同时修改 User、Shipping 和 Notification，说明它具有较好的内聚性。

低内聚的典型信号：

- 一个 `CommonService` 同时处理用户、订单、邮件和文件。
- 同一个业务能力散落在 Controller、Util、SQL 和前端中。
- 一个模块的文件只是因为技术类型相同而放在一起。

例如下面这种纯技术分包，在小系统中简单，但系统扩大后，一个 Feature 会横跨所有目录：

```text
controllers/
services/
repositories/
models/
```

按业务能力组织通常更容易保持内聚：

```text
order/
  api/
  application/
  domain/
  infrastructure/
payment/
  api/
  application/
  domain/
  infrastructure/
```

### 1.2 低耦合

低耦合不是完全没有依赖，而是依赖数量少、方向清晰、契约稳定。

耦合可能来自：

- Compile-time dependency。
- 共享数据库和跨模块直接查表。
- 同步 API 调用。
- Event Schema。
- 共享 Library。
- 部署与运行时依赖。
- 团队流程和发布节奏。

一个 Service 即使通过 Kafka 通信，也不一定是低耦合。如果消费者依赖 Producer 的大量内部字段，或者双方必须同步发布，仍然是强耦合。

## 二、耦合的常见类型

### 2.1 Implementation Coupling

调用者了解被调用方内部实现。例如直接访问另一个模块的数据库表。

### 2.2 Temporal Coupling

两个组件必须同时在线，或者操作必须按严格顺序发生。同步 HTTP 调用通常具有 Temporal Coupling。

### 2.3 Data Coupling

多个组件依赖相同数据结构。共享一个包含几十个字段的 DTO，会导致任何字段变化都影响多个消费者。

### 2.4 Deployment Coupling

组件必须一起构建、测试或发布。即使代码分成多个 Repository，如果每次都必须协调发布，它们仍然存在 Deployment Coupling。

### 2.5 Organizational Coupling

一个改动必须经过多个团队排期和审批。架构边界与团队边界不一致时，这种问题尤其明显。

## 三、如何提高内聚、降低耦合

常用方法包括：

1. 围绕 Business Capability 划分边界。
2. 让数据归属单一模块，不允许随意跨库访问。
3. 通过明确的 API 或 Event Contract 交互。
4. 使用 Information Hiding，隐藏内部 Model 和实现细节。
5. 避免把易变化的细节放进公共接口。
6. 使用 Dependency Rule 保持单向依赖。
7. 对共享 Library 保持谨慎，尤其是包含业务逻辑的 Library。

## 四、模块化设计

Module 不只是一个文件夹。一个有效模块应该具备：

- 明确职责。
- Public API。
- 隐藏的内部实现。
- 自己的数据或数据访问边界。
- 可独立测试的业务行为。
- 明确的依赖关系。

### 4.1 好的 Module Boundary

好的边界通常围绕变化划分。如果订单规则和支付规则由不同角色决定、以不同频率变化，就应该属于不同 Module。

可以用以下问题验证边界：

1. 这个 Module 能否用一句话描述？
2. 谁拥有这个 Module？
3. 它因为什么原因变化？
4. 它公开哪些能力，隐藏哪些细节？
5. 删除或替换它时，影响范围有多大？

### 4.2 模块化单体

Modular Monolith 在一个部署单元中保留清晰的 Domain Module：

```text
Application
├── Order Module
├── Payment Module
├── Inventory Module
└── Notification Module
```

它的优点包括：

- 本地调用简单，延迟低。
- Transaction 处理相对直接。
- 部署和运维成本低。
- 容易进行 Refactoring。

它的限制包括：

- 通常必须整体部署。
- 隔离不严格时容易退化为 Big Ball of Mud。
- 不同模块难以独立扩容。
- 大团队可能产生发布协调问题。

对于业务边界尚未稳定、团队规模不大或系统规模有限的场景，Modular Monolith 往往比 Microservice 更合理。

### 4.3 从模块到 Microservice

只有在出现明确驱动力时才考虑拆分，例如：

- 不同模块需要独立扩容。
- 不同团队需要独立发布。
- 故障隔离具有明显价值。
- 技术栈或合规要求不同。
- 模块边界已经稳定。

如果单体内部没有清晰模块，直接拆 Microservices 通常会得到 Distributed Monolith。

## 五、分层设计

Layered Architecture 按职责组织系统。常见的四层结构如下：

```text
Presentation Layer
        ↓
Application Layer
        ↓
Domain Layer
        ↑
Infrastructure Layer
```

### 5.1 Presentation Layer

负责 HTTP、GraphQL、CLI 或 Message Consumer 等入口：

- 解析输入。
- 基础格式校验。
- 身份上下文传递。
- 调用 Application Use Case。
- 把结果转换为 Response。

Presentation 不应该实现核心业务规则。

### 5.2 Application Layer

负责 Use Case 编排：

- 定义 Transaction Boundary。
- 调用 Domain Object。
- 调用 Repository Port。
- 发布 Domain Event。
- 协调外部 Service。

Application Layer 决定“做什么步骤”，Domain Layer 决定“业务规则是什么”。

### 5.3 Domain Layer

负责核心业务知识：

- Entity、Value Object 和 Aggregate。
- Domain Service。
- Business Invariant。
- Domain Event。

Domain Layer 应尽量不依赖 Spring、数据库或网络 Client。

### 5.4 Infrastructure Layer

负责技术实现：

- JPA Repository。
- Kafka Producer/Consumer。
- REST Client。
- S3 Adapter。
- Cache 和外部 SDK。

基础设施应该实现核心层定义的 Port，而不是让 Domain 依赖基础设施细节。

## 六、依赖规则

分层设计最重要的不是文件夹，而是 Dependency Direction。

常见规则：

- 外层可以依赖内层。
- 内层不能依赖外层。
- Domain 不依赖 Framework。
- 跨模块调用必须经过 Public API。
- 禁止循环依赖。

可以使用 ArchUnit 自动验证 Java 架构规则：

```java
@ArchTest
static final ArchRule domain_must_not_depend_on_infrastructure =
    noClasses()
        .that().resideInAPackage("..domain..")
        .should().dependOnClassesThat()
        .resideInAPackage("..infrastructure..");
```

架构规则如果只存在于文档中，很容易随着时间失效。能自动化验证的规则应尽量放进 CI。

## 七、典型反模式

### 7.1 Big Ball of Mud

缺少稳定边界，任何功能都可以访问任何数据和代码。一次小改动可能影响整个系统。

### 7.2 Shared Database

多个 Service 直接读写同一组表，导致数据所有权模糊、Schema 变更困难、无法独立发布。

### 7.3 Circular Dependency

Order 依赖 Payment，Payment 又依赖 Order。循环依赖通常说明职责或抽象方向有问题。

解决方式可能包括：

- 提取稳定抽象。
- 重新分配职责。
- 通过 Event 解除直接依赖。
- 合并本来就属于同一边界的模块。

### 7.4 Layer Bypass

Controller 直接访问 Repository，或者 React 直接复制 Backend 的核心规则。这会绕过 Application 和 Domain Boundary。

### 7.5 Chatty Interface

完成一个 Use Case 需要频繁跨模块或跨网络调用。它会增加延迟、故障概率和认知负担。

## 八、度量与评审方法

架构师可以关注：

- 一个 Feature 需要修改多少个 Module。
- 模块之间依赖边的数量和方向。
- 是否存在循环依赖。
- 公共 API 的大小和变化频率。
- 一次发布需要协调多少团队。
- 一个故障能够影响多少业务能力。

这些指标不是最终目标，但可以帮助发现架构退化。

## 九、面试场景

问题：如何拆分一个包含 User、Order、Payment 和 Inventory 的大型单体？

推荐回答思路：

1. 先基于 Domain 和业务能力识别 Boundary。
2. 在单体内部重构为 Module，并禁止跨模块直接访问内部表。
3. 为模块定义 Public API 和 Event。
4. 用监控确认调用关系、数据流和变化频率。
5. 根据独立扩容、发布、所有权和隔离需求选择拆分目标。
6. 使用 Strangler Fig 逐步迁移，而不是一次性重写。

## 十一、总结

- 高内聚让相关知识和变化集中在同一边界。
- 低耦合让不同边界能够相对独立地变化、测试和部署。
- Module 必须有职责、Public API 和隐藏的实现，而不只是目录。
- 分层设计的关键是职责与依赖方向，而不只是命名。
- Microservice 不是模块化的替代品；好的 Microservice 通常始于好的模块边界。


## 十二、如何真正判断内聚与耦合

前面建立概念地图，下面用可验证的边界、代码和故障场景展开。以下电商、库存与团队数据均为教学假设，不代表读者真实项目经历。原则本身没有产品版本；Java 示例以 Java 17 为基线，ArchUnit API 按核查时官方指南 1.5.1 说明。

### 12.1 高内聚不是“有关订单的东西全部放一起”

订单邮件模板、支付清算和订单状态都包含 orderId，但它们可能分别由运营、财务和交易规则驱动变化。仅因共享标识就放进同一模块，会让一个模块承受多种独立变化。反过来，把价格、折扣和税放在 Pricing 内也不是永远正确：税务若已有独立合规团队、外部税务引擎和独立规则生命周期，可能需要单独边界。

判断内聚要结合三类证据：

1. **语义与不变量**：哪些规则必须一起理解，哪些状态变化必须一起保证正确？
2. **变化来源**：哪些需求通常一起修改，是否由同一业务决策驱动？
3. **责任与交付**：谁能对行为和数据负责，修改是否需要反复跨团队协商？

Git 中经常同时变化是线索，不是证明。统一升级和格式化也会让不相关文件一起变化。一个功能横跨两个模块并不自动意味着边界错误：下单本来就可能需要库存和订单合作；危险的是每次改库存内部表示都迫使订单、报表和通知一起修改。

### 12.2 信息隐藏比“文件拆开”更关键

Information Hiding 隐藏的是容易变化的设计决定，而非单纯把字段改成 private。例如库存模块隐藏“按仓分配、预留表结构、锁策略”；对外只提供带清晰语义的 reserve 和 release。调用者不应先 getAvailable、再自行计算、最后 setReserved，否则库存不变量已经暴露给消费者。

典型反例：

```java
// 反例：跨模块持有可变内部对象，绕开库存规则。
InventoryRow row = inventoryRepository.find(sku);
if (row.available >= quantity) {
    row.reserved += quantity;
}
```

即使把这几行包成公共方法，若调用者仍控制“先检查再更新”的时序，并发竞态也未消失。更好的 API 是表达业务意图，并由数据拥有者原子执行检查与更新，返回确定的预留结果或明确失败。

**高内聚的关键效果**：库存并发控制从乐观版本改为数据库条件更新时，消费者仍只依赖“是否成功预留”的行为契约。内部可以变化，外部的业务承诺不能悄悄变化。

### 12.3 低耦合要分维度，不存在一个总分包打天下

| 维度 | 诊断问题 | 常见改善方式 | 不能消除的代价 |
|---|---|---|---|
| 源码依赖 | 是否导入别的模块内部类？ | 窄API、隐藏内部实现、构建规则 | 契约仍需维护 |
| 数据与语义 | 是否依赖他方表结构和状态含义？ | 明确数据所有权、版本化契约 | 消费者仍需理解业务含义 |
| 时间 | 对方是否必须即时可用？ | 异步处理、缓存或本地读模型 | 延迟、一致性与积压处理 |
| 部署 | 任一变动是否要求同步升级？ | 向后兼容、分阶段迁移 | 并存版本与清理成本 |
| 故障与资源 | 一个慢调用能否拖垮全系统？ | 超时预算、并发隔离、容量限制 | 配置与运维复杂度 |
| 组织 | 是否需要多个团队协调一个小需求？ | 单一owner、清晰决策权限 | 跨业务需求仍要协作 |

“改用事件后就低耦合”是不完整回答。事件可以解除请求链路上的即时在线依赖，却可能增强 Schema、顺序和历史数据依赖。新增字段若消费者严格拒绝未知字段，仍可能需要同步发布；生产者停机后消费者虽可处理存量，新的业务流程仍可能停止推进。

### 12.4 耦合预算：把依赖放到能承担风险的位置

假设结账同步依赖用户、促销、库存、支付、通知五个系统。不能把五个可用率直接相乘后当作精确生产可用率：调用是否每次发生、失败是否相关、是否有缓存与降级都会影响结果。但同步依赖越长，需要同时正常工作的组件通常越多，端到端延迟和恢复就越难控制。

先区分“必须在当前响应前完成”的能力。库存确认和资金处理可能关系业务正确性；营销通知通常可延迟。把非关键通知移出主链路有价值，但要持久保存发送意图并监控失败，而不是启动一个不受管理的后台线程后立刻返回成功。

## 十三、模块边界必须覆盖代码、数据与行为

### 13.1 从业务能力到公开契约

一个库存预留接口不应只记录 Java 方法签名，至少明确：

| 契约项 | 教学示例 |
|---|---|
| 意图 | 为订单预留某SKU数量 |
| 输入 | tenantId、reservationId、sku、quantity |
| 不变量 | 数量为正；可用库存不得因本操作变为负 |
| 重复调用 | 同键同参数重放结果；同键不同参数拒绝 |
| 并发 | 不同请求竞争同SKU时，不超卖 |
| 一致性 | 成功返回后，权威库存已持久化预留 |
| 失败 | 不足、参数冲突、暂时不可用、结果未知分别表达 |
| 生命周期 | 预留过期、确认消耗与释放由谁负责 |
| 安全 | tenantId来自可信上下文，不能仅信任请求体 |
| 版本 | 增加新状态时消费者如何处理 |

接口小不等于信息可以含糊。只返回 boolean 会让消费者混淆“库存不足”和“超时但可能成功”。若远程调用出现未知结果，先查询或按同幂等键重试，而不是直接换一个新键再预留。

### 13.2 数据所有权不等于必须每模块一个数据库实例

模块化单体可以共用一个数据库实例，同时约定每组表只有一个模块负责写入，其他模块通过API或受控的只读模型访问。物理共库、逻辑共享表、共同写入不是同一个问题。

跨模块直接 JOIN 的取舍：

- 优点是查询简单、通常容易利用数据库优化器，并可在合适事务隔离下获得一致视图。
- 代价是报表依赖他方表字段、索引和删除策略，Schema变更扩大影响范围。
- 对稳定的小型内部系统，可把受控查询视图作为显式例外，写明owner和兼容承诺。
- 对计划独立发布的模块，应优先评估API聚合或事件驱动读模型；后者会增加存储、同步和数据新鲜度治理。

**禁止跨模块写表**通常比“每个查询都必须HTTP化”更有价值。不要为追求纯粹性把一个高效本地查询改成上千次网络调用。

### 13.3 公共模型泄漏的具体后果

直接把 JPA Entity 暴露给其他模块或HTTP响应，消费者可能依赖懒加载、关联对象、持久化状态和字段布局。于是一次字段重命名同时变成数据库迁移、业务变更和对外API变更。

边界DTO的目的不是给每一层复制完全相同的类，而是隔离有不同生命周期的契约。对不可变、语义一致的内部值对象，可以复用；对外传输对象则应明确可空性、枚举扩展和兼容规则。切勿通过“万能DTO加几十个可选字段”隐藏差异。

## 十四、分层的三张图：不要混淆依赖与执行

本章前文四层图采用“核心定义端口、基础设施实现端口”的依赖反转风格。它不是所有传统分层架构的唯一形式。传统三层可能让业务层直接依赖数据访问接口或实现；采用哪一种必须写清，而不是用同一箭头同时表示所有关系。

### 14.1 源码依赖

核心规则：

- Presentation 依赖 Application 的输入用例。
- Application 依赖 Domain，以及用例所需的输出端口。
- Infrastructure 实现这些端口，因此源码依赖相应核心接口。
- Composition Root 负责创建适配器和用例，允许它知道具体实现。
- Domain 不导入 Controller、HTTP客户端或持久化实现。

端口属于领域层还是应用层要按语义决定。表示领域集合的 Repository 可放领域；发送通知、查询外部评分等用例能力可放应用。不要为机械满足目录规则把所有接口塞进 domain。

### 14.2 运行时调用

一次取消订单可能是 Controller 调用 CancelOrderUseCase，用例调用 OrderRepository 接口，实际执行的是数据库适配器。运行时进入 Infrastructure，不等于核心源码依赖 Infrastructure；动态分派和装配解释了两者为何不同。

构造器循环、源码模块循环和业务消息回路也要区分。Order发起支付，支付随后发出结果事件，不一定有源码循环；但可能存在无限互相触发的业务循环。仅消除 import 不能证明流程会收敛，应使用状态转换、关联标识和重复检测验证。

### 14.3 部署拓扑

逻辑层不是独立机器。同一个Java进程可以包含四层和多个业务模块；多个容器也可能共享同一数据库、共同发布，形成 Distributed Monolith。

| 边界 | 解决什么 | 不自动保证什么 |
|---|---|---|
| Java package | 命名与有限可见性 | 架构规则、子包私有访问 |
| Maven/Gradle子项目 | 构建依赖与产物 | 数据隔离、运行时故障隔离 |
| JPMS named module | 显式可读性与包导出 | 进程隔离、性能和数据所有权 |
| 独立进程或服务 | 部署、资源与故障隔离机会 | 合理业务边界、兼容性 |
| 团队owner | 维护与决策责任 | 技术上无法越界 |

Java的子包不是父包的访问特权区域。order.api 与 order.internal 是不同包；package-private 类型不能因为目录都在 order 下就互相访问。若要跨包实现而保持边界，需结合构建模块、JPMS exports或架构测试，不要把Java命名层级误当访问控制继承。

## 十五、代码级例子：把取消规则与持久化并发分开

下面是 Java 17 单文件教学程序，只演示领域不变量、用例编排和乐观版本端口。为了独立阅读使用嵌套类，生产项目应放入相应模块与包；**此文件本身不验证包边界**。

场景约束：PAID和SHIPPED订单不能直接取消；同一取消操作可重复得到CANCELLED；所有写入者必须遵守版本协议。内存仓库用于示例，不代表数据库事务实现。

```java
import java.util.HashMap;
import java.util.Map;
import java.util.Objects;

public class ModuleBoundaryDemo {
    enum State { NEW, PAID, SHIPPED, CANCELLED }

    record Order(String id, State state, long version) {
        Order {
            Objects.requireNonNull(id);
            Objects.requireNonNull(state);
            if (id.isBlank() || version < 0) {
                throw new IllegalArgumentException("invalid order");
            }
        }

        Order cancel() {
            if (state == State.CANCELLED) return this;
            if (state != State.NEW) {
                throw new IllegalStateException("order cannot be cancelled");
            }
            return new Order(id, State.CANCELLED, version);
        }
    }

    interface Orders {
        Order load(String id);
        void save(Order changed, long expectedVersion);
    }

    static final class VersionConflict extends RuntimeException {}

    static final class CancelOrder {
        private final Orders orders;
        CancelOrder(Orders orders) { this.orders = orders; }

        State execute(String id) {
            Order before = orders.load(id);
            Order after = before.cancel();
            if (after != before) {
                orders.save(after, before.version());
            }
            return after.state();
        }
    }

    static final class MemoryOrders implements Orders {
        private final Map<String, Order> rows = new HashMap<>();

        synchronized void seed(Order order) {
            rows.put(order.id(), order);
        }

        public synchronized Order load(String id) {
            Order value = rows.get(id);
            if (value == null) throw new IllegalArgumentException("not found");
            return value;
        }

        public synchronized void save(Order changed, long expectedVersion) {
            Order current = load(changed.id());
            if (current.version() != expectedVersion) {
                throw new VersionConflict();
            }
            rows.put(changed.id(), new Order(
                    changed.id(), changed.state(), expectedVersion + 1));
        }
    }

    static void check(boolean value, String message) {
        if (!value) throw new AssertionError(message);
    }

    public static void main(String[] args) {
        MemoryOrders memory = new MemoryOrders();
        memory.seed(new Order("o-1", State.NEW, 0));
        Order stale = memory.load("o-1");
        CancelOrder useCase = new CancelOrder(memory);
        check(useCase.execute("o-1") == State.CANCELLED, "cancel");
        check(useCase.execute("o-1") == State.CANCELLED, "replay");
        check(memory.load("o-1").version() == 1, "single transition");
        try {
            memory.save(stale.cancel(), stale.version());
            throw new AssertionError("stale write accepted");
        } catch (VersionConflict expected) {
            check(memory.load("o-1").version() == 1, "state preserved");
        }
        memory.seed(new Order("o-2", State.PAID, 0));
        try {
            useCase.execute("o-2");
            throw new AssertionError("paid order cancelled");
        } catch (IllegalStateException expected) {
            check(memory.load("o-2").state() == State.PAID, "invariant");
        }
        System.out.println("PASS: cancellation, replay, conflict, invariant");
    }
}
```

保存为 ModuleBoundaryDemo.java 后使用 JDK 17：`javac --release 17 ModuleBoundaryDemo.java && java ModuleBoundaryDemo`。本次环境未提供javac，未实际运行，不能把预期PASS当成执行记录。

### 15.1 为什么不能把 save 变成无条件覆盖

假设取消与支付同时读到NEW、version=0；取消先写入CANCELLED、version=1，支付随后用旧数据覆盖成PAID，会破坏状态规则。版本检查让后写者失败后重新读取，重新判断业务操作是否仍合法。

数据库适配器可使用类似条件更新（SQL是语义示意，参数语法以实际驱动为准）：

```sql
UPDATE orders
SET state = :new_state, version = version + 1
WHERE id = :id AND version = :expected_version;
```

更新行数为0时不能当成功；需要区分不存在或版本冲突，并由用例决定是否重试。**所有写入路径**都必须遵守相同协议，跨模块直接写表可能绕过它。仅给一个类加锁也无法协调其他进程、后台脚本和数据库客户端。

示例重放在先前读到CANCELLED时不再写入；两个并发取消中仍可能有一个收到版本冲突，调用方需按契约重读或重试。它没有实现HTTP幂等键、跨租户隔离或外部退款。若“取消已付款订单”意味着退款，应定义新的用例及状态机，而非放宽此规则后偷偷调用支付SDK。

### 15.2 Application 与 Domain 的边界在哪里

cancel()决定当前状态是否允许取消；用例决定加载、调用规则、保存的顺序。Repository负责持久化和并发检查，但不应在各个适配器中分别定义不同取消规则。

简单CRUD应用可以使用事务脚本，不一定要引入完整Aggregate与Domain Service。关键是规则只有明确归属、写入路径不能绕过它，复杂度与收益匹配。Controller直接调用查询端口在经过授权且有意采用查询模型时可以合理；危险的是绕过应用授权、事务与领域不变量。原文“跨层调用”应结合具体分层契约判断，不能机械认定少一层调用必然错误。

## 十六、让边界可执行：构建、测试与数据访问控制

### 16.1 ArchUnit规则不应只禁止一条依赖

原文的 domain不依赖infrastructure 规则不能阻止订单访问payment.internal，也不能发现跨模块SQL。可以补充以下规则；本段为ArchUnit 1.5.1风格片段，需已有JUnit/ArchUnit配置、已编译业务类及对应包，未在本环境运行：

```java
// 需要静态导入：ArchRuleDefinition.noClasses、SlicesRuleDefinition.slices。
// classes 是已导入 com.acme.shop 的 JavaClasses。
noClasses()
    .that().resideOutsideOfPackage("com.acme.shop.inventory..")
    .should().dependOnClassesThat()
    .resideInAPackage("com.acme.shop.inventory.internal..")
    .check(classes);

slices()
    .matching("com.acme.shop.(*)..")
    .should().beFreeOfCycles()
    .check(classes);
```

要按实际包布局确定slice，例如 api/application/domain 位于各业务模块内时，业务模块循环和模块内部层循环应分别检查。若把全局bootstrap也当业务slice，装配依赖可能误报，应该显式排除或重新定义规则，而不是忽略所有失败。

验证规则时，临时引入一个禁止依赖，确认测试真的失败，再移除违规；这是测试架构规则自身是否覆盖目标的有效方式。不要只看“测试绿色”：导入空包、错误包名或未编译类可能导致漏检或规则无法评估。

### 16.2 更强边界及其限制

JPMS可以在module-info.java中只导出API包，不导出内部包；外部named module还需声明requires。exports控制通常的类型访问，opens针对反射访问，不能为了ORM方便无差别开放所有模块。

架构测试分析字节码依赖，不会自动理解SQL字符串、HTTP目的地址、反射加载、消息Schema或数据库权限。补足方式包括：数据库账号写权限、明确表owner、契约测试、运行时调用观测和Schema迁移评审。不要以“ArchUnit通过”宣称不存在运行时耦合。

### 16.3 测试组合

| 测试 | 验证问题 | 不覆盖什么 |
|---|---|---|
| 领域单元测试 | 状态转换和不变量正确吗？ | 数据库锁与映射 |
| 适配器集成测试 | 版本冲突、约束和转换可靠吗？ | 完整业务链路 |
| 消费者/提供者契约测试 | API和事件演进兼容吗？ | 所有真实故障 |
| 架构测试 | 静态依赖符合边界吗？ | 动态访问和共享表 |
| 端到端/故障测试 | 超时、重复与恢复是否可控？ | 对任意流量的形式化保证 |

## 十七、事务与事件：拆边界后最容易踩的雷

### 17.1 模块化单体的本地事务是便利，也是潜在耦合

同一数据库事务可以协调订单和库存，但必须明确哪个用例拥有事务、锁顺序如何约定、事务持续多久。不能在持锁时无限等待支付HTTP响应；长事务会扩大锁竞争和连接池压力。

若未来计划拆开，先清点哪些业务必须“同生共死”。不是每个跨模块事务都应马上改为事件；若强一致不变量密集、数据规模有限且拆分收益小，保留同一边界可能更合理。

### 17.2 内存发布事件不等于可靠通信

事务中调用监听器，监听器失败可能回滚主事务；事务后直接发布，进程若在提交后崩溃，事件可能永久丢失；事务前发送，后续数据库回滚则消费者已看到不存在的事实。

一个常见方案是数据库事务中同时记录业务状态和Outbox发送意图，后台重试投递。它仍需处理重复、顺序、积压和消费者幂等，不自动带来“恰好一次业务效果”。事件模型应携带eventId、业务标识、必要版本等，是否包含完整快照由消费者需要和隐私决定；避免把内部ORM对象原样序列化。

### 17.3 同步改异步是语义变更

同步预留成功后再返回“订单已确认”，改为异步后应该返回“受理/处理中”，并定义查询、失败通知和超时补偿。若仍返回原来的确定成功，却让后台稍后发现库存不足，调用方契约已被破坏。

事件解除直接依赖不等于流程没有依赖。异步工作流需要终态、超时和可运营状态；否则只是把可见的请求失败变成难以发现的长期卡住。

## 十八、从模块化单体演进到服务：一份可执行迁移思路

假设订单和库存已有清晰API，库存出现明显独立扩容需求。不要同时迁移所有模块，先限定一个垂直业务切片。

1. **描绘现状**：列出入口、读写表、调用方、后台任务、跨模块事务与锁，检查是否有隐藏脚本写入。
2. **在进程内收口**：库存表只能经库存模块访问；把外部调用收敛到窄API，并建立行为测试。
3. **定义新契约**：保留同键重放、并发不足、超时未知结果与库存查询语义；不把本地方法签名原样暴露成RPC。
4. **迁移读路径**：可比较新旧读结果，但要标明数据快照时点，避免把同步延迟误判为错误。
5. **迁移写所有权**：优先设计某一时刻只有一个权威写入者，或按租户/分片明确归属；不是对新旧系统各写一次就完成迁移。
6. **处理数据转换与增量**：校验总量、不变量和业务样本，定义删除与更正如何传播。
7. **小流量切换与观察**：关注预留失败、重复、积压、p95/p99延迟、业务对账和恢复步骤。
8. **退出旧路径**：确认消费者迁完，移除旧写权限、适配层和临时同步任务，避免永久保留双系统。

**回滚不是简单切回路由。**新系统若已接收独有写入，切回旧系统可能丢状态。要预先定义反向同步、短暂停写、重放或只回滚代码不回滚数据的具体条件。无法安全回退时，应降低切换范围并采用向前修复计划。

模块化单体往往更便于原子修改，但共享堆、线程池和发布单元会形成资源与故障耦合；微服务提供隔离机会，却要承担网络、契约和运维成本。选择取决于当前业务约束与团队能力，不能按“服务越多越成熟”评分。

## 十九、排障与架构评审：从症状找到依赖

| 症状 | 需验证的机制 | 可操作证据与对策 |
|---|---|---|
| 改库存字段导致订单接口失败 | ORM实体或Schema泄漏 | 查消费者字段引用，改为稳定边界DTO |
| 多服务必须同时上线 | 契约不兼容或共享库锁步升级 | 画版本兼容矩阵，采用先扩展后收缩 |
| CPU不高但接口慢 | 聊天式调用、连接池或锁等待 | 用Trace定位重复调用，批量化并控制事务 |
| 积压持续增长但HTTP仍成功 | 异步链路吞错或消费者不足 | 查看事件年龄、失败重试与业务终态 |
| 包依赖无环但业务无限重试 | 事件回路没有收敛条件 | 检查状态机、eventId和重复投递路径 |
| 单个模块耗尽线程导致全站卡住 | 共享资源池放大故障 | 限制并发、隔离关键资源并测试降级 |

度量不能只数import边。模块A调用一次库存API与直接读取库存十张表，不是同样风险。对同类需求记录修改范围、owner数量、契约变化和发布步骤，再比较一段时间的趋势。

可以计算静态扇入/扇出辅助定位：扇入高的稳定API变化影响大，扇出高的模块可能承担过多编排。但数据定义、依赖粒度和工具规则必须一致；不要用一个所谓“耦合分数”直接决定拆服务。

## 二十、面试问题与深入追问

### 20.1 “我已经按订单、支付分包，为什么仍不是模块化？”

**回答：**目录只是命名。我要检查公开API、内部类型访问、数据写入所有权、循环依赖和测试边界。若订单能直接更新支付表，支付又返回内部Entity，那么分包并未隐藏变化。先建立可执行的访问规则，再决定是否需要独立构建或进程。

**追问：package-private够不够？**只限制同一个Java包，子包没有特权；跨包内部实现还需其他机制。静态边界也不能替代数据库权限和运行时契约。

### 20.2 “事件驱动是不是一定比同步调用低耦合？”

**回答：**它常降低即时在线耦合，但会引入Schema、顺序、积压、重复和最终一致性问题。我会先问业务能否等待、何时算成功、失败由谁恢复。需要即时确认的关键步骤可能继续同步，通知或读模型更新可异步。

**追问：有消息队列为什么还会丢业务事件？**数据库提交与发送不原子时有窗口；即使消息可靠，消费端也可能确认后未完成业务操作。要分析完整链路，不只看Broker。

### 20.3 “Controller访问Repository是不是绝对不允许？”

**回答：**按团队规定和用例风险判断。复杂写操作绕过授权、用例事务和领域不变量，风险很高。只读查询若设计为专用查询服务或读模型，并集中处理权限，可以避免无意义的四层转发。重要的是保留约定的职责，不是凑层数。

### 20.4 “订单和库存相互调用，该不该上Kafka解环？”

**回答：**先区分源码循环与业务协作。可能是编排职责放错，可由应用用例协调；也可能是两个模块其实共享同一强一致不变量，应合并；也可能适合事件。改为Kafka若不定义状态机，只会把显式循环变成异步回路。

### 20.5 “什么证据足以支持拆微服务？”

**回答：**独立扩容、发布或隔离需求已存在，边界与数据owner稳定，收益能覆盖分布式一致性和运营成本。我会提出一个切片的目标、迁移步骤和回退条件，验证后再扩大，而不是先定服务数量。

**追问：独立数据库是否必须立即做？**先明确写入所有权，物理隔离可渐进实施；共享实例仍可能共享资源与故障域，应如实说明。不能在共同写表的状态下宣称已完成独立演进。

### 20.6 “如何判断分层是否过度？”

**回答：**如果层只做无语义转发，增加导航和映射而未隔离变化，需要精简。若领域复杂、外部依赖多，独立用例和端口可能显著降低测试与替换成本。用一次实际需求和一次故障恢复证明收益，而非以代码行数或层数判断。

## 二十一、扫雷自测与速记

| 自测 | 答案应涉及 |
|---|---|
| 相同orderId足以决定同模块吗？ | 语义、不变量、变化来源与owner |
| 私有字段就是信息隐藏吗？ | 是否隐藏可变化决定，是否泄漏可变对象 |
| 进程内方法改成RPC能保持语义不变吗？ | 超时、未知结果、重试与一致性 |
| 分包后能防止跨模块写表吗？ | 不能，需数据权限和访问治理 |
| 模块化单体是否没有隔离价值？ | 逻辑隔离有价值，但不等于资源/故障隔离 |
| ArchUnit能发现SQL字符串中的跨表写吗？ | 一般不能自动解释，需要补充检查 |
| 用事件消除import循环就完成解耦了吗？ | 仍有业务、Schema与时间依赖 |
| 两次独立写入能代替同一事务吗？ | 有部分成功窗口，需恢复方案 |
| 旧系统可随时作为回滚目标吗？ | 新写入必须能恢复到旧权威状态 |
| 一个Feature改两个模块一定边界错误吗？ | 正常业务协作可能跨边界，检查变化传播原因 |

速记：**按业务与变化聚合；公开意图与失败契约；代码、数据、流程一起封装；源码依赖、运行时调用、部署拓扑分别画；单体先模块化；服务拆分必须付清一致性与运营成本；边界用自动检查加真实故障证据守住。**
