# 03. 可扩展性、可维护性、可测试性与可演进性

## 学习目标

1. 区分 Scalability、Extensibility、Maintainability、Testability 和 Evolvability。
2. 理解这些质量属性如何影响架构决策。
3. 能够把模糊的“系统要可扩展”转化为可验证指标。
4. 能够识别质量属性之间的冲突并进行权衡。

## 一、先明确“可扩展”的含义

中文语境中的“可扩展性”经常同时指两件不同的事：

- Scalability：流量、数据量或用户增长后，系统仍能满足性能目标。
- Extensibility：增加新业务能力时，现有设计不需要大范围修改。

架构讨论中必须明确是哪一种，否则不同参与者可能在回答不同的问题。

本节同时讨论：

- Scalability：容量扩展。
- Extensibility：功能扩展。
- Maintainability：维护性。
- Testability：可测试性。
- Evolvability：可演进性。

## 二、Scalability

Scalability 描述负载增长时，系统通过增加资源维持目标服务水平的能力。

### 2.1 Vertical Scaling 与 Horizontal Scaling

Vertical Scaling 是增加单个节点的 CPU、内存或磁盘。它简单，但存在硬件上限和单点风险。

Horizontal Scaling 是增加更多节点。它具有更高上限，但要求处理：

- 无状态化。
- Load Balancing。
- Session 管理。
- 分布式数据。
- 并发控制。
- 故障和网络不确定性。

### 2.2 Stateless Service

如果 Session 只保存在某台 Application Instance 的内存中，请求就必须固定路由到同一节点，扩容和故障转移会变得困难。

常见做法是：

- 使用无状态 Token。
- 把 Session 放入 Redis 等共享存储。
- 把文件放入 S3，而不是本地磁盘。
- 通过数据库或 Message Broker 维护持久状态。

无状态不表示系统没有状态，而是计算节点不拥有无法转移的持久状态。

### 2.3 Cache

Cache 可以显著降低数据库压力和延迟，但会引入一致性问题。

常见模式：

- Cache Aside。
- Read Through。
- Write Through。
- Write Behind。

设计时需要回答：

- Cache Key 是什么？
- TTL 多久？
- 数据变化后如何失效？
- Cache Miss 时如何保护数据库？
- 是否允许短暂 Stale Data？

### 2.4 Partitioning

单个数据库无法承载数据量时，可以按 Tenant、User ID、Region 或时间进行 Partitioning/Sharding。

好的 Partition Key 应该：

- 分布相对均匀。
- 与主要查询模式一致。
- 避免 Hot Partition。
- 尽量减少 Cross-partition Query。

### 2.5 Asynchronous Processing

把非即时任务放入 Queue，可以减少请求延迟并吸收流量峰值，例如：

```text
API -> Persist Order -> Publish Event -> Return
                              ↓
                   Email / Analytics / Fulfillment
```

代价是引入 Eventual Consistency、重复消息、延迟处理和更复杂的排障流程。

### 2.6 用指标定义 Scalability

不要只说“支持高并发”。应该定义：

```text
Peak traffic: 10,000 requests/second
P95 latency: < 200 ms
Error rate: < 0.1%
Availability: 99.95%
Expected annual growth: 80%
```

有了明确指标，才可以进行 Capacity Planning、Load Test 和成本评估。

## 三、Extensibility

Extensibility 指增加新功能时，系统是否能够在稳定边界上扩展。

常见手段：

- Strategy 和 Plugin Mechanism。
- 稳定的 API Contract。
- Event-driven Integration。
- 配置化规则。
- 清晰的 Domain Boundary。
- 向后兼容的 Schema Evolution。

例如，通知平台支持 Email、SMS 和 Push。可以定义：

```java
public interface NotificationChannel {
    ChannelType type();
    DeliveryResult send(Notification notification);
}
```

新增 WhatsApp Channel 时，不需要改动核心分发流程。

但 Extensibility 需要基于真实变化方向。为了所有可能的未来设计通用框架，往往会降低可理解性和交付速度。

## 四、Maintainability

Maintainability 指团队修复缺陷、理解行为、更新依赖和增加功能的效率与安全性。

### 4.1 影响 Maintainability 的因素

- 代码和架构是否容易理解。
- Module Boundary 是否清晰。
- 命名是否表达 Domain Language。
- 自动化测试是否可靠。
- 文档是否与实现同步。
- Observability 是否足够。
- Build 和 Deployment 是否可重复。
- 技术栈数量是否合理。

### 4.2 可维护性不仅是代码质量

如果系统代码很整洁，但每次发布需要手工执行 30 个步骤，或者生产问题没有 Trace 和 Metrics，它仍然很难维护。

Maintainability 同时包括：

- Development Maintainability。
- Operational Maintainability。
- Dependency Maintainability。
- Data Maintainability。

### 4.3 控制认知负担

团队能够同时理解的复杂度有限。以下做法可以降低 Cognitive Load：

- 限制每个 Service 的职责。
- 统一常见的技术方案。
- 提供 Golden Path 和项目模板。
- 删除不再使用的 Feature Flag 和兼容代码。
- 保持 Runbook 和架构图更新。

## 五、Testability

Testability 指系统能够被有效、稳定、快速验证的程度。

### 5.1 可测试设计的特征

- 依赖可以被控制或替换。
- Domain Logic 与 I/O 分离。
- 时间、随机数和外部状态可以注入。
- 输出明确且容易观察。
- Component Boundary 清晰。
- 测试不需要共享不可控环境。

例如，不要在 Domain Logic 内直接调用当前时间：

```java
public final class SubscriptionService {
    private final Clock clock;

    public SubscriptionService(Clock clock) {
        this.clock = clock;
    }
}
```

测试可以传入固定的 `Clock`，避免测试结果随时间变化。

### 5.2 Test Pyramid

常见层次包括：

1. Unit Test：快速验证局部逻辑。
2. Component/Integration Test：验证数据库、Kafka 或 Framework 集成。
3. Contract Test：验证 Service 之间的契约。
4. End-to-End Test：验证少量关键业务流程。

大量 E2E Test 通常运行慢、定位困难且容易不稳定。测试组合应该以快速反馈为基础，并用较少的高层测试覆盖关键链路。

### 5.3 Test Double 的边界

Mock 太多可能导致测试只验证实现细节。更合适的原则是：

- 对纯 Domain Object 使用真实对象。
- 对外部系统边界使用 Stub、Fake 或 Mock。
- 用 Integration Test 验证 Adapter 与真实技术的兼容性。
- 用 Contract Test 验证跨 Service 协作。

### 5.4 生产环境中的 Testability

现代系统的测试能力也包括：

- Feature Flag。
- Canary Release。
- Synthetic Monitoring。
- Shadow Traffic。
- 自动化 Smoke Test。
- 快速 Rollback。

Feature Flag是运行时行为开关，必须有owner与清理条件；Canary Release先让少量流量使用新版本，比较错误和业务指标后扩大；Synthetic Monitoring用受控账户定期执行关键路径；Shadow Traffic把请求复制到新实现比较行为，但写操作必须隔离副作用；Smoke Test在部署后快速确认基本功能；Rollback将流量或程序恢复到前一版本，但不能自动撤销数据和外部操作。

这些方法验证的对象不同。开关关闭只能阻止后续行为，不能撤销已经扣款；金丝雀样本太小可能漏掉罕见故障；影子写流量若真的发邮件，会给用户造成二次副作用。因此需要明确隔离、观测窗口、成功判据和失败处置。

测试不只发生在 CI，也贯穿整个 Delivery Lifecycle。

## 六、Evolvability

Evolvability 是系统长期适应未知变化的能力。它比 Extensibility 更宽，关注的不只是增加一个 Feature，还包括替换技术、改变边界、迁移数据和调整组织结构。

### 6.1 演进式架构

演进式架构通常具有三个特征：

1. Incremental Change：小步变化，而非大型重写。
2. Fitness Function：自动检查关键架构属性。
3. Appropriate Coupling：边界允许局部独立演进。

### 6.2 Architecture Fitness Function

Fitness Function 是对架构质量的可执行验证，例如：

- Domain Layer 不能依赖 Infrastructure Layer。
- API P95 Latency 必须低于 200 ms。
- Container Image 不允许存在 Critical Vulnerability。
- 一个 Service 的 Availability 必须达到 99.95%。
- Event Schema 的变化必须向后兼容。

它可以通过 Unit Test、ArchUnit、Performance Test、Security Scan 或生产监控实现。

### 6.3 可替换性

外部变化最快的部分应该被隔离，例如：

- Payment Provider。
- AI Model Provider。
- Cloud Storage。
- Search Engine。
- Identity Provider。

但“未来可能替换”必须有合理概率和业务价值。为几乎不会替换的组件建立复杂抽象，可能得不偿失。

### 6.4 数据演进

代码可以快速回滚，数据迁移通常更困难。安全演进需要：

- 向后兼容 Schema。
- Expand-and-Contract Migration。
- 双读或双写期间的一致性验证。
- Backfill 和校验机制。
- 明确 Rollback Plan。

## 七、质量属性之间怎样取舍

### 7.1 拆服务：独立扩容收益与交付成本

假设报表任务很吃CPU，交易接口要求稳定低延迟。把报表计算隔离部署，可以避免竞争应用CPU，并允许单独扩容。但如果它仍与交易共享数据库重查询，故障隔离并未完成。还要限制查询资源、选择副本或读模型，并说明数据新鲜度。

服务拆分增加网络、身份验证、兼容、监控和部署成本。先证明共享资源或发布协调是实际问题，再比较进程内并发限制、独立worker与完整微服务，不应直接选择最复杂方案。

### 7.2 缓存：性能收益不能覆盖正确性约束

商品展示通常允许短暂陈旧，适合缓存；最终结算价格与库存裁决需要权威确认。若对所有读取加缓存，p95可能下降，却引入错误价格或超卖风险。应按数据用途设置规则，而非按“读多”一概缓存。

缓存还需要容量、键设计、过期与miss保护。热点同时失效时，数据库请求可能集中爆发；可考虑加载合并、限并发和分散过期，但它们不能保证强一致。方案要同时描述命中和失效时怎样运行。

### 7.3 抽象：可替换性与理解成本

对支付网关建立业务端口，可以控制外部失败并进行测试；对每个纯内部类建立接口，可能只增加导航。判断标准是抽象能否吸收一个真实变化或隔离副作用。

可替换性也有边界：两家供应商在回执、限额和结算上有差异，接口不能抹掉业务需要的信息。越通用的接口越可能退化为可选参数集合，反而难维护。

### 7.4 异步：响应快不等于业务完成快

把通知异步化可缩短下单响应，但需要持久保存发送意图、处理重复并观测最老任务年龄。消费者处理能力不足时，请求接口仍可能很快，用户却很久收不到结果。

若库存确认也变异步，就要调整订单状态和用户承诺。异步的代价不仅是技术排障，也包括业务接受“受理但未确认”的流程变化。

### 7.5 测试与交付速度：优化反馈而不是减少保证

大量共享环境E2E可能慢且不稳定，团队容易忽略失败；减少它们之前应把规则、协议与数据库行为迁移到相应测试层，保留关键旅程。不能为了CI快而只留下Mock测试。

每项决策应写明优先目标、不能违反的约束、可接受代价和重新评估条件。例如先保资金正确性，再优化延迟；先满足恢复要求，再降低资源成本。把所有指标都说成“最高优先级”等于没有排序。

## 八、场景分析：从100 RPS增长到10,000 RPS

先确认增长是持续、峰值还是短时突发；请求是查询、下单还是批处理；数据量与热点分布如何变化。100倍流量不代表所有组件都要100倍扩容，也不能只按CPU估算。

假设读取占大多数，Trace显示重复数据库查询是主要耗时。第一步固定请求组合与数据规模，建立延迟、错误、CPU、连接池和数据库等待基线；第二步减少重复查询并验证索引与执行计划；第三步在允许陈旧的读路径评估缓存，同时测试冷启动与集中失效。

若应用CPU随后成为瓶颈，可无状态化并水平扩容，但要计算总连接数和下游容量。若通知耗时影响响应，可在可靠保存通知意图后异步处理，同时监控业务完成时间。每一步使用相同负载对比，解释收益来自哪里。

只有当证据指向单库容量、热点写入或其他明确约束时，才评估分片；分片键要匹配主要查询，并计划跨片事务、迁移与热点处理。这个顺序是基于假设的推理，不是所有系统的固定菜单。若真实瓶颈是供应商配额，应该先处理该约束。

最后测试超载与故障：一个实例退出、缓存清空、数据库变慢时是否能保护关键请求，扩容需要多久，如何恢复积压。满足正常峰值但故障后无限排队，不能算已经具备可靠扩展能力。

## 九、面试回答：把澄清问题转成方案

### 9.1 为什么要问这些问题

“可扩展”首先要区分容量与功能。容量目标决定资源和负载测试，功能扩展决定稳定边界。读写比例、数据增长、延迟与一致性要求决定缓存和分片是否适合；预算、团队与交付期限限制可维护的复杂度。

澄清不能只停在提问。如果面试官不给数据，可明确教学假设，例如“先假设读多写少、读取允许短暂陈旧、订单确认需要权威写入”，然后在这个范围内推理；不能把假设伪装成事实。

### 9.2 一段可展开的回答示例

> 我先用最简单满足当前业务的方案建立基线，不提前分库。假设目标是峰值10,000 RPS，我会固定请求比例、数据量和热点分布，通过压测与Trace找瓶颈。如果主要耗时来自重复查询，先减少工作量；对允许陈旧的查询加缓存，但验证miss时数据库仍受保护。
>
> 应用水平扩容之前，我会核算每实例连接池总量和下游限制。通知可异步，但需要持久发送意图、重复处理和积压监控；订单是否确认不能只看消息是否入队。只有单库或热点约束经过验证后，才讨论分片及数据迁移。
>
> 验证包括正常负载、超载、冷缓存和实例故障，还要计算每个成功业务操作的成本。每个阶段都有回退条件，避免同时引入多个机制后无法解释收益与故障。

这段是设计练习，不是个人项目陈述。追问时应能继续解释连接预算、缓存竞态、积压恢复和数据迁移，而非只列组件名。

## 十、自测题与参考答案

### 10.1 Scalability与Extensibility怎样区分？

前者应对工作量增长，通过增加资源或降低单位工作量维持目标；后者应对新业务能力，通过稳定契约限制修改范围。系统可能容易增加渠道但无法承受更多流量，也可能吞吐很高但每个新功能都要改很多模块，二者必须分别验证。

### 10.2 Stateless Service为什么利于水平扩容？

因为请求不必回到持有唯一会话或文件状态的实例，负载均衡可把请求分配给其他健康实例，实例可替换。状态并未消失，而是交给数据库、共享会话存储或对象存储；这些依赖也需要容量与故障设计。Token同样涉及撤销、权限变化和密钥管理。

### 10.3 容易做单元测试是否必然容易做E2E？

不是。纯规则可用固定输入快速验证，E2E还受真实网络、认证、配置、共享数据和异步时间影响。单元测试不能证明数据库事务和外部协议正确。需要不同层次互补，并用独立数据与受控环境降低不稳定性，而不是用大量Mock代替所有真实边界。

### 10.4 Fitness Function具体是什么？

是持续验证某项架构属性的机制。例如禁止领域层依赖基础设施的静态规则、固定负载下的延迟门禁、按明确SLI窗口计算可用性的监控。目标“可用性99.95%”本身不是完整检查，必须说明如何观测、在哪个窗口、失败后由谁处理。

### 10.5 怎样证明维护性，而不是说代码干净？

选择真实变更或事故，记录理解、定位、修改、验证、部署与恢复的过程。观察修改触及的模块、协调owner、失败测试定位、可重复构建和数据修复能力。减少手工步骤、消除必须找某个人才能恢复的流程，都比单看命名整齐更能证明维护收益。

## 十一、复习总结：同一系统要经得起五种变化

流量增长考验Scalability；新增渠道考验Extensibility；修bug、升级依赖与恢复事故考验Maintainability；能否稳定复现边界和故障考验Testability；新旧版本共存、迁移数据与替换结构考验Evolvability。

设计时要分别给出场景、机制和证据：容量用工作量模型与实测，扩展用真实变更范围，维护用完整操作路径，测试用可控依赖与有效断言，演进用兼容、回填、校验和退出计划。任何一项都不能由“采用某框架”直接推出。

面试前复习应能沿一次请求解释正常结果、并发冲突、超时、重试与恢复，再说明当前方案的上限和下一步触发条件。做到这一点，才能把架构视角与工程细节连接起来。

## 十二、把质量属性变成架构可以验证的承诺

前面给出知识地图；下面从机制、工程验证和面试推理展开。所有负载、成本、订单与订阅例子均为教学假设，不是实测benchmark或读者个人项目数据。

### 12.1 五个概念为什么不能混为一谈

| 属性 | 核心变化 | 一个能验证的场景 | 一个常见误判 |
|---|---|---|---|
| Scalability | 工作量增长 | 增加实例后，在规定数据分布下仍满足延迟和错误率 | 部署了Kubernetes就已经可扩展 |
| Extensibility | 新能力增加 | 增加通知渠道无需修改现有渠道实现 | 所有类都有接口就能方便扩展 |
| Maintainability | 日常理解与修改 | 新成员能按Runbook定位并修复指定故障 | 代码短、没有重复就是好维护 |
| Testability | 验证系统行为 | 能稳定复现过期边界、失败和并发冲突 | Mock多、覆盖率高就是可靠 |
| Evolvability | 长期结构变化 | 新旧版本并存完成数据迁移，不中断已约定服务 | 只要能增加插件就能演进 |

功能扩展性是维护与演进的一部分，但不能替代技术替换、数据迁移和组织调整。一个系统新增渠道很方便，却可能因全局共享表而无法拆分；一个系统单元测试很容易，却可能因测试环境共享状态而无法稳定完成集成验证。

### 12.2 质量属性场景的六个要素

把“要快”“要好维护”展开为：**刺激来源、刺激、环境、受影响对象、系统响应、响应度量**。

例如容量场景：在促销峰值、一个实例失效的条件下，外部客户以规定读写比例发起10,000 RPS，订单查询服务仍满足p95小于200ms、规定错误率和成本上限。需要补充数据规模、请求分布、缓存命中率、持续时间及错误定义，才是可复现测试。

维护场景：在工作时间，一个不熟悉该模块的维护者需要更改退款期限。要求修改局限于退款规则和对应测试，按既定发布流程上线，并能观察是否出现错误退款。这里可以度量修改范围、验证耗时与需要协调的owner，但不能承诺“所有改动都只需一天”。

演进场景：滚动发布期间，新旧应用并存；新增数据库字段不破坏旧版本；迁移任务可暂停、重启与校验；经过观察窗口后才移除旧字段。这比“数据库向后兼容”更能指导实施。

### 12.3 指标必须有分母、窗口和观测位置

“错误率低于0.1%”要说明哪些请求纳入分母、预期业务拒绝是否计入、客户端取消怎样统计。“可用性99.95%”要写明测量窗口和SLI定义，不能拿压测30分钟无错误证明整月可用性。

p95是分位数，不是平均耗时；不能把多个实例的p95做算术平均当作全局p95。聚合时需要可合并的分布或足够粒度的原始观测。测试还应覆盖p99、超时和排队长度，避免95%的简单查询掩盖关键写操作失败。

## 十三、Scalability深入：增加资源前先建立工作量模型

### 13.1 Scalability、性能与弹性的区别

单请求耗时从100ms优化到50ms是性能改进；负载翻倍时增加资源仍维持目标，是容量扩展；根据负载及时增加和释放资源，是Elasticity。三者相关，但不等价。

水平扩容通常提升可并行工作部分的吞吐，不能自然消除单个热点键、串行锁、数据库日志或第三方限额。垂直扩容可快速缓解内存或CPU压力，也可能把恢复和迁移时间放大。单点风险取决于冗余、故障转移和数据保护，**不应把垂直扩容本身等同于必然单点，或把多实例等同于已经高可用**。

### 13.2 用服务时间而非响应时间估算CPU

假设10,000 RPS，每请求实际CPU时间为4ms，理论CPU需求约为40个核的持续计算能力。若希望正常情况下CPU利用率不超过60%，粗略资源下界约67核。它不是采购承诺：实例性能、GC、运行时、并发、数据局部性和故障余量都需实测。

若请求端到端平均耗时100ms，不能把100ms全部当CPU；其中可能有数据库和网络等待。对稳定系统，Little's Law用平均值关联平均在途数、完成速率和平均停留时间：L = λW。此例约1,000个平均在途请求。**不要用p95代替平均值，也不要把在途数直接当线程数。**

以下Python 3脚本仅检查估算算术和假设输入，不模拟真实队列或预测p95：

```python
from math import ceil

def estimate(rps, cpu_ms, mean_response_ms, utilization):
    if rps < 0 or cpu_ms < 0 or mean_response_ms < 0:
        raise ValueError("negative input")
    if not 0 < utilization <= 1:
        raise ValueError("invalid utilization")
    return {
        "cpu_cores_lower_bound": ceil(rps * cpu_ms / 1000 / utilization),
        "mean_inflight": rps * mean_response_ms / 1000,
    }

def backlog(arrival_per_sec, service_per_sec, burst_seconds):
    if min(arrival_per_sec, service_per_sec, burst_seconds) < 0:
        raise ValueError("negative input")
    return max(0, arrival_per_sec - service_per_sec) * burst_seconds

def recovery_seconds(queued, arrival_per_sec, service_per_sec):
    if min(queued, arrival_per_sec, service_per_sec) < 0:
        raise ValueError("negative input")
    if queued == 0:
        return 0.0
    if service_per_sec <= arrival_per_sec:
        return float("inf")
    return queued / (service_per_sec - arrival_per_sec)

assert estimate(10000, 4, 100, 0.6) == {
    "cpu_cores_lower_bound": 67,
    "mean_inflight": 1000.0,
}
assert backlog(12000, 10000, 30) == 60000
assert recovery_seconds(60000, 8000, 10000) == 30
assert recovery_seconds(60000, 10000, 10000) == float("inf")
print("PASS: capacity arithmetic and backlog recovery")
```

60,000个积压不是“有队列就安全”。按上述假设，恢复时新流量8,000/s、处理能力10,000/s，净排空速度只有2,000/s，约30秒；新流量一直为10,000/s就永远没有剩余能力消化存量。真实处理能力会随任务类型变化，需要观察最老任务年龄和业务完成率。

### 13.3 扩应用实例可能把数据库压垮

假设数据库连接预算200，每个应用实例配置连接池50。由4个实例扩到12个时，配置总量变成600，数据库不会因此获得三倍处理能力；等待、超时和重试反而可能放大故障。

应一起规划应用并发、连接池、数据库容量和后台任务预算。容量预算还要给管理、迁移与故障恢复预留空间。外部依赖限额也一样：消费者越多不代表供应商配额越高。

热点场景中，即使分片分布整体均匀，一个大租户或热门SKU仍可能集中到单个分区。随机分散可以改善写入，却让按租户聚合查询和事务更贵；选择分片键时要同时解释数据分布、查询与迁移成本。数据库表分区也不自动等于跨机器分片。

### 13.4 无状态化的边界

把Session放到共享存储能帮助应用实例替换，但共享存储成为新依赖，需要过期、容量和故障策略。无状态Token也不解决所有会话问题：撤销、权限变化、密钥轮换和敏感信息仍需设计。

本地缓存可以存在，但不能保存唯一权威业务状态。扩容时新实例缓存冷启动，可能出现DB流量突增；缩容前要停止接收新请求、完成或安全中断在途任务。无状态服务依旧可能因本地临时文件、长连接或未完成异步任务而需要优雅停机。

### 13.5 缓存四种模式不能只背名称

| 模式 | 执行机制 | 主要好处 | 必须回答的失败语义 |
|---|---|---|---|
| Cache Aside | 应用查缓存，miss查DB并回填 | 控制灵活 | 回填与失效竞态、击穿 |
| Read Through | 缓存层加载缺失数据 | 调用方简单 | loader失败、并发加载合并 |
| Write Through | 经缓存组件写入并同步持久化 | 集中写入口 | 组件如何确认DB与缓存结果 |
| Write Behind | 先接受缓存写，后异步持久化 | 写延迟可低 | 未落库数据丢失、顺序与重放 |

这些是模式名称，不是所有产品都具有同样原子性保证。Cache Aside的典型竞态：读请求读到旧DB值后暂停；写请求更新DB并删除缓存；读请求随后把旧值回填，缓存再次变旧。仅规定“更新后删除”不能证明强一致。

措施要按允许陈旧窗口选择：版本化数据、短TTL、受控回填、事件失效或直接绕过缓存读取关键状态。TTL限制并不等同于严格端到端陈旧上限，还要考虑加载耗时、事件延迟和实现。对余额、库存裁决等权威写规则，应在持久化事务或相应权威服务内完成，不能让缓存旧值裁决正确性。

### 13.6 自动扩容与过载保护是互补能力

扩容需要观测、调度、启动和预热时间，不能替代即时限流、并发上限、有界排队与负载丢弃。CPU低但等待数据库很久时，仅以CPU驱动扩容可能不动作，或扩容后更坏。

选择能反映瓶颈的信号：CPU工作负载看CPU及运行队列，队列消费者看年龄和有效处理率；同时检查下游容量。限流返回怎样的错误、是否允许重试、重试预算和幂等都属于API契约。过载情况下应优先保住关键业务，避免把所有任务都接收后在内存里超时。

## 十四、Extensibility深入：扩展点的完整生命周期

原文通知接口隐藏了渠道选择，但真实渠道差异还包括：目标地址、消息长度、模板、附件、速率限制、回执和退订。不能把所有差异都做成Notification上的可空字段，再宣称核心流程无需变化。

可以在核心层保留统一的发送意图和结果状态，在适配器中映射渠道参数；如果渠道语义确实不兼容，例如“事务通知”与“营销活动”，应划分不同用例，不强行共享万能send。

### 14.1 扩展点必须约定成功意味着什么

DeliveryResult的ACCEPTED若表示服务商接收，不代表用户已收到。新渠道只提供受理确认，旧渠道却提供到达回执，不能直接把两者都映射为DELIVERED。必须区分业务结果、异步状态更新、失败和未知结果。

注册新实现还需要配置、凭证、权限、监控和部署，这是合理装配成本。是否做到功能扩展，应看稳定用例是否需要理解新供应商内部协议，而不是追求“零文件修改”。

### 14.2 配置化与插件化的隐藏成本

配置改变算法行为时，应具有Schema校验、版本、审批和回滚；复杂表达式可能接近一门编程语言。插件引入第三方代码时，还需要兼容性、资源限制和安全隔离。把代码改成配置，只是转移了复杂度，不会免除测试与治理。

共享插件API一旦发布，消费者依赖范围会扩大。尽量先基于真实变化建立少量能力接口，再在多次扩展中验证稳定性。对暂时只有一种实现的纯内部函数，可直接保持清晰实现，不必预先开发通用框架。

## 十五、Maintainability深入：维护成本是一条端到端路径

### 15.1 维护一次问题需要走完哪些步骤

可以把维护工作拆成“发现 → 定位 → 理解 → 修改 → 验证 → 发布 → 确认恢复”。整洁代码只改善其中一部分。

例如订单金额不一致，维护者需要知道使用了哪个规则版本、输入快照和修改路径，而不仅是一个HTTP500。日志、traceId、业务标识与审计记录要能关联，但不能泄漏凭证或个人敏感数据。错误记录应保留cause，避免层层重复打印造成噪音。

Runbook至少包含症状、影响判断、安全诊断命令、恢复动作、成功判据和升级责任人。恢复动作若可能重放支付或通知，必须说明幂等与授权。不要用一个“重新跑任务”的脚本替代失败语义分析。

### 15.2 怎样证明维护性改善

选择真实变更样本，比较：

- 相同复杂度需求触及多少模块与团队；
- 测试失败需要多久找到根因，是否经常重跑碰运气；
- 能否从干净环境重复构建和部署；
- 依赖升级是否需要大范围同时修改；
- 数据修复能否审计、重试和校验；
- 故障恢复是否依赖某个特定人的记忆。

不能用单一平均修复时间跨团队排名：事故严重度、值班安排和报告方式不同。指标用于发现摩擦，最终要回到具体故障和变更证据。

### 15.3 依赖与认知负担管理

统一Golden Path可以减少重复选型，但模板生成后会分叉；需考虑持续升级而不是一次复制。公共库若混入大量业务规则，会造成锁步发布；应该明确owner、支持版本和弃用周期。

遗留Feature Flag、临时兼容代码、无人使用的队列和过时文档都增加认知负担。新增兼容路径时同步记录移除条件、owner和观察指标，避免“暂时双写”变成永久系统。

## 十六、Testability深入：可控、可观察、可隔离

### 16.1 可控制的时间：测试精确边界而非sleep

Java 17示例使用到期时刻语义：now小于expiresAt才有效，相等时已过期。它不处理“某地区当天23:59到期”的日历规则，后者需显式ZoneId和日期定义。

```java
import java.time.Clock;
import java.time.Instant;
import java.time.ZoneOffset;

public final class ExpiryPolicy {
    private final Clock clock;
    public ExpiryPolicy(Clock clock) {
        this.clock = java.util.Objects.requireNonNull(clock);
    }

    public boolean isActive(Instant expiresAt) {
        return Instant.now(clock).isBefore(expiresAt);
    }

    public static void main(String[] args) {
        Instant expiry = Instant.parse("2026-11-08T12:00:00Z");
        ExpiryPolicy before = new ExpiryPolicy(
                Clock.fixed(expiry.minusNanos(1), ZoneOffset.UTC));
        ExpiryPolicy exact = new ExpiryPolicy(
                Clock.fixed(expiry, ZoneOffset.UTC));
        ExpiryPolicy after = new ExpiryPolicy(
                Clock.fixed(expiry.plusNanos(1), ZoneOffset.UTC));
        if (!before.isActive(expiry) || exact.isActive(expiry)
                || after.isActive(expiry)) {
            throw new AssertionError("expiry boundary");
        }
        System.out.println("PASS: before, exact, after");
    }
}
```

Clock注入让业务时间可控，但测量耗时和deadline还涉及单调时钟。墙上时钟可能校正，不能把两个Instant的差值当作所有超时实现的最佳方案。线程调度、随机数、ID生成和外部响应也应按需要可控，而不是只注入Clock就宣称测试确定。

### 16.2 测试替身各自验证什么

Stub提供指定响应；Fake提供简化可用实现；Mock可验证边界交互；Spy观察真实或部分真实行为。选择取决于要证明的性质，不是所有外部依赖都必须Mock。

单元测试若断言内部调用顺序和私有辅助方法次数，重构容易破坏测试却不改变行为。另一方面，对发送邮件、扣款等外部副作用，“是否调用且是否重复”可能正是行为契约，不能一律禁止交互断言。

Fake数据库通常不模拟事务隔离、唯一约束、排序、锁和SQL方言。与真实数据库的适配器测试用于覆盖这些差异；不能因为Fake通过而跳过并发冲突测试。测试环境还需独立数据、清理策略与可重现种子，避免相互污染。

### 16.3 并发与异步测试不要依赖偶然调度

用sleep等待100ms再断言消息“应该到了”会随机器速度波动。更可控的方式是：通过latch/barrier建立明确执行阶段，用有上限的等待观察目标状态；超时给出队列与任务诊断信息。并发测试需要构造实际竞态，例如两个写者都先读到旧版本，再放行写入。

不要将不断重试测试直到通过视为修复；要区分外部瞬时故障和隐藏竞态。轮询必须设总超时与间隔，避免无限等待或忙循环。测试通过只能证明所覆盖调度和输入，不是对所有线程交错的形式化证明。

### 16.4 Test Pyramid是反馈策略，不是配额

没有“单元70%、集成20%、E2E10%”的通用正确比例。纯规则多的系统可有大量单元测试；主要整合数据库或协议的适配器，需要真实集成验证。

Contract Test检查约定交互的兼容，不自动证明真实供应商所有行为、性能和安全。E2E适合少量关键用户旅程，但上线时还要核对配置、凭证、网络和迁移状态。代码覆盖率表示哪些语句被执行，不表示断言有意义；关键不变量应有正反例、边界与失败路径。

### 16.5 生产验证要防止二次副作用

Canary需要按租户或流量切分、定义观察窗口和回退阈值；低流量或短窗口可能无法发现罕见失败。Synthetic Monitoring应使用受控账号和可清理数据。

Shadow Traffic复制写请求可能真实扣款、发邮件或消耗库存。必须隔离外部副作用并处理敏感数据，不能只把流量复制到新服务就叫安全验证。Feature Flag能快速关闭某行为，但无法自动撤销已经发送的通知或不可逆数据变更。

## 十七、Evolvability深入：安全变化需要兼容矩阵与退出条件

### 17.1 Fitness Function必须可测且有owner

原文“可用性达到99.95%”是目标；对应的fitness function应是按指定SLI与窗口收集数据、计算是否达标并触发评审。CI几分钟不能证明长期可用性。p95门禁也必须固定负载模型与测试环境，不能因共享runner抖动随意阻塞所有发布。

对架构规则可立即阻止新增循环依赖；对遗留系统可建立基线禁止新违规，并逐步偿还旧违规。安全扫描的“无Critical”需要规则库版本、误报处理、例外到期与修复owner，不能把一次扫描作为永久安全证明。

这些检查最好与质量目标对应，而不是采集几十个没人响应的指标。每个失败都要有解释、责任人和处置方式，否则只是增加报警负担。

### 17.2 Expand-and-Contract：字段重命名不是直接RENAME

假设将customer_name改为display_name。滚动发布时旧实例只认识旧字段，新实例认识新字段。直接改列名可能立即使旧实例失败。

一种受控演进流程：

1. **Expand**：增加新字段，暂不删除旧字段；确认DDL锁与执行时间。
2. **升级写路径**：新应用在同一数据库事务内维护两个表示；先清点旧版本、批任务和外部写者。
3. **Backfill**：分批、限速、可恢复地填充历史记录，记录进度与失败。
4. **验证与切读**：确认新字段与旧语义一致，逐步切换读路径；观察回退读取次数。
5. **停止旧写**：确认旧实例和脚本全部退出，权威写路径已统一。
6. **Contract**：经过约定回退窗口后，移除旧字段、兼容逻辑和迁移任务。

新增字段并不意味着DDL一定零阻塞。PostgreSQL 17的不同ALTER TABLE子操作具有不同锁、扫描或重写条件；应根据实际子命令、表大小和长事务检查，设置合适的lock_timeout与执行计划。不能把某版本的优化泛化为“所有加列都在线无锁”。

### 17.3 Backfill最危险的是覆盖并发新值

朴素流程“读旧值 → 算新值 → 无条件更新”可能覆盖在线新写。需要确定权威来源与并发协议，例如在旧写者已退出或被同步机制覆盖的前提下，对尚未填充记录做条件更新，并在一个受控SQL操作中读取当前源值；更复杂变换可以带版本比较，冲突后重读。

“只更新新字段为NULL”不是万能方案：旧应用随后若只更新旧字段，新字段仍会陈旧。要么确保旧写者已经停用，要么在迁移窗口提供能覆盖全部写入口的同步机制，并为顺序、循环和故障设计规则。

验证不能只数非NULL行。需要比较样本和全量业务不变量、非法值、跨表关联、大小写与编码转换；对增量写入要持续校验，直到切换完成。

### 17.4 双写不等于原子写

同一数据库事务内维护两个字段，与两个独立系统各写一次不同。跨系统第一写成功、第二写失败会产生部分成功，需要持久化发送意图、重放和对账；还要避免旧事件覆盖新版本。

回滚代码不等于回滚数据。Contract后旧应用可能无法运行；新格式若已产生旧格式表达不了的数据，简单切旧版本会丢语义。计划应明确可回滚窗口和不可逆点，必要时选择向前修复，不承诺随时一键回退。

## 十八、从100 RPS到10,000 RPS：如何做有证据的决策

原文扩展步骤是一种常见路径，不是每个系统都必须按该顺序实施。若当前瓶颈是外部服务配额，先加索引不会解决主问题；如果写热点导致锁竞争，读取缓存也不会修复它。

### 18.1 建立Baseline

固定请求组合、数据规模、热点分布、实例规格和依赖状态，记录吞吐、端到端分位数、错误、CPU、GC、连接池、DB等待与队列年龄。预热与冷启动分开测，避免只测小数据全在内存的理想状态。

采用不同测试回答不同问题：

| 测试 | 要回答的问题 |
|---|---|
| Load Test | 目标负载下是否满足SLO？ |
| Stress Test | 超过容量时怎样失败、是否能恢复？ |
| Spike Test | 突增时扩容前能否保护关键请求？ |
| Soak Test | 长时间运行是否泄漏、积压或退化？ |
| Fault Test | 实例、依赖故障与恢复时是否仍满足承诺？ |

负载发生器本身也可能成为瓶颈。固定并发、等待响应后再发请求的测试可能因系统变慢而自动降低施压，掩盖按固定到达速率进入的真实流量。应说明开放/封闭负载模型、客户端超时与延迟统计方式。

### 18.2 每次只验证一个主要假设

如果Trace显示每请求几十次重复DB查询，先消除N+1或改批量查询，比较相同负载下的变化；若CPU已满，评估热点计算与实例扩容；若数据库日志或锁成为瓶颈，检查写模型、批量和事务长度。

不要一次加入缓存、分片和异步后只报告“快了”。那样无法解释收益来源、成本和失败模式，回退也更困难。优化后重新找瓶颈，它通常会移动。

### 18.3 把成本与业务结果一起算

单位成本可以定义为“该窗口资源成本 / 成功完成的业务操作数”，并保留窗口、资源范围和成功定义。若仅降低每个HTTP请求成本，却导致更多重试和失败订单，业务效率可能更差。

成本评估包括常驻实例、峰值余量、缓存、存储、网络、备份与维护工作，不能只比较机器单价。服务拆分带来独立扩容，也可能增加常驻最低副本、观测与值班成本。安全、可靠性和交付速度是约束，不应为便宜而悄悄牺牲。

## 十九、面试追问与推理示例

### 19.1 “多加实例为什么吞吐不涨？”

先定位瓶颈：共享数据库锁、连接预算、热点键、单分区、网络或供应商限额都可能限制整体。比较扩容前后各组件利用率、等待与成功吞吐，不能仅凭应用CPU下降宣布扩容成功。再针对瓶颈选择降低工作量、批量、缓存或数据布局调整。

**追问：是不是应该直接分库？**先验证单库瓶颈与查询/写模式，分库会增加跨分片事务、查询和迁移成本，不能替代不合理查询治理。

### 19.2 “怎么证明功能容易扩展？”

选择一个有代表性的变更，例如增加通知渠道，展示需要修改哪些稳定契约、哪些适配器、哪些测试和配置；说明渠道结果语义差异如何处理。不是数接口，也不是保证零修改。若新需求改变核心业务假设，本来就可能需要调整设计。

### 19.3 “把所有外部依赖Mock掉，就足够测试了吗？”

Mock可以控制响应和失败，但不能验证真实SQL、事务、序列化和协议兼容。应以纯规则单元测试加关键适配器集成、契约和少量端到端组成证据链。对并发和恢复再设计专项验证，而不是用更多Mock断言冒充真实边界验证。

### 19.4 “可演进性是否要求统一所有云和AI供应商接口？”

不必。先确认替换概率、成本与业务价值，隔离真正影响核心策略的差异。过薄接口会泄漏厂商语义，过度统一会损失关键能力。即使代码适配简单，数据迁移、权限、运营和质量评估仍可能使替换昂贵。

### 19.5 “数据库字段迁移失败，回滚应用就行了吗？”

要看处于Expand、Migrate还是Contract，以及新旧写入兼容性。新增字段阶段可保留旧读路径，但并发同步可能已出现差异；删旧字段后旧代码可能不能运行。必须检查数据权威、不可逆写入与回退窗口，必要时暂停迁移并向前修复。

### 19.6 “如何在面试中表现Solution Architect的高度？”

先给场景与约束，再给最小可行方案和关键假设；说明怎样测量、何时扩展、失败如何处理、代价由谁承担。接着能进入连接池、缓存回填竞态、时间边界或迁移条件更新等具体机制。只讲愿景不足，只背实现细节也不足。

## 二十、扫雷自测与面试前速记

| 自测 | 必须答出的边界 |
|---|---|
| 10,000 RPS、平均100ms是否需要1,000线程？ | 约1,000平均在途，不等于线程数 |
| 端到端100ms能直接算CPU核数吗？ | 需实际CPU服务时间，等待不等于计算 |
| 队列能永久解决消费者处理不足吗？ | 不能，需净排空能力及容量保护 |
| 无状态Token是否消除全部状态？ | 撤销、权限、密钥与业务状态仍存在 |
| Cache Aside更新后删缓存是否强一致？ | 仍有旧读回填竞态 |
| Clock注入能证明异步测试确定吗？ | 调度、外部I/O和随机仍需控制 |
| 测试覆盖率100%是否证明正确？ | 需有效断言、边界、不变量与失败测试 |
| 可用性目标能靠一次CI测试证明吗？ | 需明确SLI与时间窗口的持续观测 |
| Backfill只更新NULL是否总安全？ | 旧写者可能继续造成陈旧 |
| Feature Flag关闭能撤销已扣款吗？ | 不能撤销不可逆副作用 |
| 双写是否自然支持回滚？ | 部分成功、数据表达与并存协议需设计 |
| 扩展性好是否意味着演进性好？ | 增加能力与替换结构、迁移数据不同 |

速记：**先澄清增长维度；以场景与度量定义质量；用工作量模型和实测找瓶颈；把测试依赖与失败变得可控；维护覆盖发布和恢复；演进要兼容、迁移、校验、退出；每个收益都说明代价和证据。**
